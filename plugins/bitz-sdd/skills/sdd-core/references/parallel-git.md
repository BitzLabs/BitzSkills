# 並列実行と git 運用・権限マトリクス

## ブランチ規約

- feature ブランチ = `.spec/specs/<feature>/` と1対1対応
- **STATE.md はブランチローカル**（`.gitattributes` で `merge=ours`）。living memory のブランチ間共有は文脈汚染を招く
- requirements/ への変更（採番・状態遷移）は main 直コミットまたは最優先マージ。契約は全ブランチから同一に見えること

## マージ競合の構造的回避

- 1要件1ファイルなので異なる要件への変更は物理的に衝突しない
- `_index.md` / `_counter.md` は自動生成物。競合したら**再生成で解決**（手マージ禁止）
- 並列PR・worktreeの検証は `spec_inspect.py --check-only` を使い、
  `inspection-report.md` を生成・更新しない。全PR統合後、締め工程の専用ブランチで通常検査を
  1回実行してレポートを更新する。各作業ブランチでレポート差分をコミットしない

## 共有作業ツリー（複数セッションが同一リポジトリを見る場合）

上の2節は**各作業者が隔離されている前提**で書かれている。実際には複数のエージェント
セッションが同一リポジトリのメイン作業ツリーを共有し、他セッションの作業途中のファイルが
そこに現れることがある。この経路が未定義だと、無関係な変更を巻き込んだ PR を作ってしまう。

**単一セッション・単一 worktree で作業している場合、本節は不要**（`git worktree list` が
1行だけなら以降は読み飛ばしてよい）。

- **着手前に稼働中の作業を把握する** — `git worktree list` で他の作業ツリーを確認する
- **ブランチは既定ブランチのリモート追跡から明示的に切る** —
  `git checkout -b <name> origin/<default>`。いま何がチェックアウトされているかに依存して
  切ると、他セッションのコミットを自分の PR に取り込む。squash マージでは祖先関係が
  残らないため、後から重複・衝突として現れる
- **広いパス指定でステージしない** — `git add -A` や `git add -A -- <広いディレクトリ>` は
  他セッションの未コミット変更を巻き込む。自分が触れたファイルだけを個別に指定する
- **コミット直前にステージ内容を確認する** — `git diff --cached --name-only` を見て、
  自分の関心事以外のファイルが1つでも混ざっていたら unstage する

## 測定値は確定した ref から読む

`.spec/` の成果物へ件数・ファイル数などの測定値を記録するときは、作業ツリーの `ls` / `grep` を
根拠にしない。他セッションの途中状態を含み、確定値として記録すると誤りになる。

- `git show <ref>:<path>` や `git ls-tree <ref>` のように**確定した ref から読む**
- レビュー・報告・設計成果物へ数値を書くときは、測定の出典となる ref（commit SHA または
  ブランチ名）を併記する
- 作業ツリーで測る場合は、`git status --short` が空であることを確認してから測る

## 並列サブエージェントのスコープ

- tasks/ の依存グラフで `depends_on` が空のタスク群のみ並列投入
- 各サブエージェントの書き込み範囲 = 担当タスクの `boundary:` 列挙パス + テストディレクトリ + STATE.md 追記
- feature 単位のコスト予算（トークン/時間）を tasks/ メタデータに宣言。超過で全停止→人間へ

## 権限マトリクス

| 行為 | 人間 | plan（直列） | 実装サブ（並列） | 検証 |
|------|:----:|:----:|:----:|:----:|
| docs/ 読み取り | ✓ | ✓ | ✓ | ✓ |
| docs/ 書き込み | ✓ | ✗（Gateドラフトのみ） | ✗ | ✗ |
| 要件の起票（draft） | ✓ | ✓（直列区間のみ採番） | ✗（spec-issueのみ） | ✗ |
| draft→approved 承認 | ✓ | ✗ | ✗ | ✗ |
| 要件本文の変更 | ✓ | ✗ | ✗ | ✗ |
| deprecated 裁定 | ✓ | ✗ | ✗ | ✗ |
| spec-issues/ 起票 | ✓ | ✓ | ✓ | ✓ |
| tasks/ 生成 | ✓ | ✓ | ✗ | ✗ |
| 実装コード書き込み | ✓ | ✗ | ✓（boundary内） | ✗ |
| verified 判定 | ✗ | ✗ | ✗ | ✓（機械） |
| Promotion Gate | ✓ | ✗ | ✗ | ✗ |
| LESSONS_LEARNED 追記 | ✓ | ✗ | ✗ | ✗ |
| 他セッションの作業中ファイル 読み取り | ✓ | ✓ | ✓ | ✓ |
| 他セッションの作業中ファイル 変更・移動・削除・コミット | ✓ | ✗ | ✗ | ✗ |

最下2行は共有作業ツリーの原則（上の「共有作業ツリー」節）。他セッションが未コミットで
触っているファイル（`.spec/` や docs/ を含む）は**読み取りのみ**とし、自分の関心事に
必要でも勝手に直さない。必要なら spec-issue で起票して調整する。

可能な範囲でツール設定（rules.md・FS権限・ブランチ保護）で技術的に強制する。プロンプト指示だけに依存しない。
ただし**ステージ内容が宣言した `boundary:` を超えていないかの機械強制は本書の範囲外**
（`SI-SDD-033` 提案4）。Git 運用の実行責任は bitz-flow へ移す方針であり、強制層の所有者が
決まるまで bitz-sdd 側へ実装しない。それまでは上記の規律で運用する。
