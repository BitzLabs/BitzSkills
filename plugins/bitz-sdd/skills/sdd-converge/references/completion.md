# 完了の提案と状態変更

SDDフローの完了条件を直接証拠へ対応付ける。

| 確認する条件 | 不足している場合 |
|---|---|
| 起点・MUST規範文・変更境界が特定されている | 起点の特定、計画へ戻す |
| 実装前contextが完全解決し、最初の書込み直前にdigestを再照合している | 実施時の証拠不足を残し、前提からの再開を提案する |
| 前後check、verifyが同じ範囲で通過している | 原状態と対象別診断を残し、原因に応じた戻り先へ戻す |
| 未テストMUSTが0件で、必須テストの実結果が成功している | 該当規範文と実assertの不足を列挙する |
| 省略事項・未証明事項が表示されている | 不足を追加し、証明した範囲を狭く報告する |
| 人間が最終差分・実試験・未証明事項を確認している | TASKはopenのまま、人手レビュー待ちとする |
| TASK起点ならdoneへの変更後に最終checkが通過している | 完了済みとせず、状態・原結果と修正の戻り先を示す |
| 完了結果がGitへ記録されている | 既存の許可に従って記録し、許可がなければ記録待ちとする |
| 横断作業なら全workspaceのcheck・verifyも通過している | 部分成功を全体の完了へ変えない |

完了条件を満たせる見込みと、完了済みの事実を分ける。品質レビューの助言やCoreの成功だけを
人間の最終差分確認へ変換しない。人間の確認を求めるときは、対象ref・変更・実出力・不足を先に揃え、
確認する判断を具体的にする。すでに同じ対象の確認と許可があるなら同じ質問を繰り返さない。

状態変更は実際のユーザー指示とプロジェクトの状態遷移に従う。
要求承認やapprovedの意味変更をTASK完了に紛れ込ませない。TASKのdone後のcheckが非成功なら
非成功を保存して完了宣言を止める。doneのまま完了扱いせず、状態訂正も公開遷移と許可に沿って行う。

独立品質レビューを実施できない場合、Q2／Q3では不足として停止する。
Q0／Q1でも必須証拠や人間確認の不足を条件付き完了へ移さない。
not_readyの重大事項、unknownの必須不足、ready_with_conditionsの非重大条件をそれぞれ保持し、
収束の報告で助言を書き換えたり独立性を自己申告したりしない。
出荷・マージ・配布はSDDの完了結果とは別の利用者判断である。
