# 仕様、フローと引渡し

## 文書とEARS-AI

標準配置は.spec/requirements/、.spec/technical/、.spec/decisions/、.spec/tasks/。
所有者を公開設定から確認し、メンバー外の参照は修飾IDを使う。
独立した複数ワークスペースの起点を1つのcontextへまとめない。

REQは利用者が期待する動作・制約、TECHは外部から観測できる技術契約。
ADRは判断と理由で、EARS-AIやコード・テストの所有先にしない。TASKは一時的な作業分割。
フロントマターはid・title・種別に対応するstatusを持ち、最初のH1を `# <id> <title>` に一致させる。
種別は配置から決まるためtypeを追加しない。関係はrelations内のrequires／refines／addresses／supersedes／related。
1系のrefs、独自のdepends_on／boundary、TASKのimplementsを標準フィールドとして追加しない。

REQは非空のIntent／Acceptance Criteria／VerificationのH2を持つ。
規範文はREQのAcceptance Criteria、TECHのContractまたはConstraintsへ置く。
TASKは規範文を再掲せず、addressesで対象の規範文IDを列挙する。
規範文を持つ文書を文書IDだけでaddressesしない。規範文のないTECHだけは文書IDを指定できる。

現行EARS-AI 1.0を使い、旧検討版のタグを持ち込まない。
規範文IDは `<文書ID>:<local-id>`。主体、条件、強度MUST／SHOULD／MAY、応答・制約と観測境界を分ける。
未合意の測定値、未再現の原因、未実装のテストを埋めない。
Verificationでは本番の入口、重要な失敗条件、予定と未証明事項を区別する。
存在しないテストのパスをtestsに登録せず、必要なテストを計画に残す。

[REQ草案例](../examples/REQ-001.md)と[TASK例](../examples/TASK-001.md)はコピー元の見本。
使用前にID・主体・契約・所有者・パス・前提を相談へ合わせる。
REQはdraft、TASKはopenで、この組合せのまま実装できる見本ではない。
changesは許可するファイルまたは末尾/のディレクトリ接頭辞。glob、絶対パス、..は使わない。
空のchangesは許可パスなし。requiresで参照する先行TASKは実装・検証時にすべてdoneが必要。

## フローとリスク

| 条件 | フロー |
|---|---|
| 通常のバグ修正、局所的な機能、リファクタリング | 簡易 |
| 公開API、永続データ、セキュリティ、費用、法令、SLO、複数モジュールの影響 | 完全 |
| 要求の確定前に技術的証拠が必要 | 時間・隔離・終了条件を定めたスパイク |

Q0は可観測な動作を変えない文言・コメント、Q1は局所的で可逆な既存契約内の変更。
Q2は公開契約・永続データ・複数モジュール・性能、Q3はセキュリティ・不可逆・法令・大きな影響を目安にする。
重大な観点が1つでもあれば上位へ上げ、総合点で消さない。降格には理由と人間の承認を残す。
Q0／Q1でも完全フローの条件があれば完全フローを選ぶ。
Q2／Q3は品質計画と独立した品質レビュー、Q3は専門観点・人手承認・復旧や攻撃の証拠も必要。
準備できなければ不足を示し、コード実装への引渡しを止める。

簡易フローは起点→実装用context→実装前check→実装→実装後check→verify→人手レビュー→完了。
完全フローは先に解釈用context・要求レビュー・人間の承認を行い、実装用contextの後に設計レビューを加える。
実装用contextは完全解決・通過状態・digestを必要とし、書込み直前にdigestを再照合する。
要求・依存・設定が変わればcontextを取り直す。TASKは人手レビュー後にdoneと最終checkを行ってGitへ記録する。
スパイク結果を本番へ直接取り込まず、採否をREQ・TECH・ADR・Issueへ短く記録し、採用実装を通常フローで計画する。

## 停止と再開

| 問題 | 戻り先 |
|---|---|
| 意味を左右する利用者・期待・禁止事項・互換性が未決 | 意図と要求の確認 |
| 承認済み要求の意味変更、例外、外部仕様変更、費用・権限の判断 | 人間へ影響を示して停止 |
| Core不在、結果不明、非成功、引数不正 | 導入・対象・設定・診断の修正 |
| 古い／不完全なcontext、依存・設計不足 | 起点とcontextの取り直し |
| 草案の構文・参照・パスの不合格 | 診断に対応する草案の修正 |
| 高リスクで品質計画・独立レビュー不足 | 証拠とレビューの準備 |

現在までの実観測、停止理由、担当者、具体的な再開条件を返す。
承認が必要な意味変更は自動修復しない。停止を完了へ読み替えない。
後続のverifyには登録テストの副作用とホストの制約を別に確認する。
Coreの公開結果は実行前の正確なargv previewを提供しないため、それが安全上必要なら起動せず停止する。
Core成功を要件実証・総合品質・出荷可能へ拡張しない。

## 後続の公開引渡し

起点・所有者、フロー、意味の差分、境界、前提、証拠の予定と不足を渡す。
計画だけでは品質レビュー用の確定ref・最終差分・実検証結果がない。
後続の公開引渡し形式を埋めるために、実行していない結果やhashを作らない。
