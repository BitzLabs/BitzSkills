# 裁定記録 — SI-SDD-016（検証結果の機械可読証跡）

- **日付**: 2026-07-29
- **裁定者**: hide（リポジトリ所有者）
- **対象**: SI-SDD-016 の Design Gate（artifact schema の確定）と要件化
  （SDD-FR-151 / 152 / 153 / 154）
- **裁定の形式**: 代行可視化経路（`--on-behalf-of hide`）。エージェントが3つの裁定点を
  推薦つきで提示し、裁定者は個別選択を行わず、前セッションで与えた自動進行の明示承認と
  本セッションの指示「SI-SDD-016 の着手をしましょう」「進めてください」に基づいて委任した。
  したがって**各裁定点は推薦（第1候補）を採用**した。本人性は機械検証されておらず、
  Promotion Gate で裁定者が内容を確認・差し戻しできる。

## 背景

FLW-FR-001 の反復検証で、同じ pytest を複数回実行して 3.66 / 3.96 / 3.80 秒と実行時間が揺れ、
test-spec へ手書きした数値と会話上の最新値が食い違った。green 判定の再現性が人手に依存している。

## 裁定点1: 証跡ファイルの粒度

**採用: 実行ごとに1ファイル（`.spec/verification/<command-id>--<commit短縮>.json`）**

- 1回の pytest が複数要件を同時に green にするのが実態であり、要件ごとに1ファイルにすると
  同じ実行結果を N 重に複写し、一部だけ更新されて矛盾する。
- ファイル名が commit と command-id で決まるため、**同一 commit の再実行は同じファイルを
  上書きして冪等**。実行時間を `observed` へ隔離してあるので、再実行しても diff が出ない
  （起票の動機そのものの解消）。
- 却下: 要件ごと1ファイル（重複と不整合）。
  却下: ワークスペースに1つの台帳ファイル（並列 PR・worktree で全ブランチが同じファイルを
  編集しマージ衝突が頻発する。`--check-only` が存在するのと同じ問題）。

## 裁定点2: 証跡の生成方法

**採用: 記録スクリプトが検証コマンドを実際に実行する（ラッパー方式）**

- `spec_verify.py record <ws> --command-id pytest --implements <ID> -- <コマンド>` の形。
  終了コードと件数を実出力から取るため、人手が数値を書き写す余地がない。
- 却下: 既存の stdout を貼り付けて解析する方式（「どの出力を渡すか」に人手が介在し、
  古い出力を渡す事故を防げない＝起票の引き金になった事象そのもの）。

## 裁定点3: ゲート強度

**採用: 欠落は WARN、壊れていたら FAIL**

- 証跡が無いこと自体を FAIL にすると、既存 59 件の verified 要件に証跡が無いため
  導入直後に全7ワークスペースが FAIL し、遡及記録が終わるまで CI が通らない。
  SI-SDD-016 自身が「新 artifact を加法的に導入」と述べている。
- 一方、証跡が**存在するのに**壊れている（schema 不正・必須キー欠落・非ゼロ終了・
  failed 件数・参照切れ）のは明確な異常であり FAIL とする。記録しただけで通してしまうと
  機械可読化が偽の安心になる。
- HEAD と違う commit の証跡、未コミット状態の暫定証跡（`dirty`）は WARN。
- `manual-check` の要件は自動証跡が原理的に生じないため、欠落 WARN の対象から外す。
- 却下: verified 遷移時に必須化（manual-check と既存 verified の扱いを同時に決める必要があり、
  今回のスコープを超える）。却下: 欠落も FAIL（上記のとおり導入不能）。

## 実装上の判断（裁定点に上げなかったもの）

- **`scripts/spec` ラッパーには追加しない**。ラッパーは sdd-core の4ツールすべてを
  必須解決する設計（CORE-FR-011）のため、`verify` を足すと `spec_verify.py` を含まない
  既存のプラグインキャッシュ版で `inspect` を含む全ツールが解決不能になる。
  `sdd_sync.py` / `docs_inspect.py` / `sdd_report.py` と同じく、スキル同梱スクリプトを
  直接実行する形とした（既存の運用と一貫する）。
- **記録が自分自身を dirty にしない**。証跡ディレクトリ配下の差分は dirty 判定から除外する。
  除外しないと、1回目の記録が作業ツリーを dirty にして2回目の記録が拒否される自己ブロックが起きる。

## 残余リスク

- 既存の verified 要件 59 件には証跡が無く、当面 WARN が並ぶ。遡及記録の要否は別途裁定する。
- 件数の解析器は現状 pytest 形式のみ。他ツールでは `counts` が `null` になり、
  判定は終了コードだけに依存する。解析器の追加は加算的に行える。
- 証跡の真正性（誰が記録したか）は検証しない。commit との紐づけと CI での再実行が担保になる。
