# 裁定記録 — bitz-sdd Design Gate（ドメインモデル SDD-DSN-009）

- **日付**: 2026-07-29
- **裁定者**: hide（リポジトリ所有者）
- **対象**: SDD-DSN-009 が「未解決」として提示した6件の設計裁定点
- **裁定の形式**: **対話裁定**。エージェントが各裁定点を選択肢・トレードオフ・推奨つきで提示し、
  裁定者が6件すべてを個別に選択した。うち**裁定1 は推奨（案A）と異なる案B が選ばれている**。
  これまでの代行可視化経路（推奨案の自動採用）とは異なり、実際の選択が行われた裁定である。
- **前提の明示**: 破壊的変更は許容（人間裁定 2026-07-29）。
  bitz-flow との境界（sdd-git 移管）は本 Gate の対象外（保留）。

## 前提条件の定義が循環していた（本 Gate 実行時の訂正）

SDD-REV-006 は「GP-001〜GP-005 の消化前に Design Gate を通さないことを推奨する」と書いた。
しかし実際に Gate を実行すると、**GP-001 と GP-005 は Gate の前に済ませるものではなく、
Gate で決めるべきこと**だった:

- **GP-001**（レビュー指摘の追跡機構）— 裁定3 がその答えそのものである
- **GP-005**（呼び出し規約の統一）— 裁定1 の案B を選んだことで、逆に Gate の**帰結**として
  前提条件になった（下記「実装順序」を参照）

前提条件の書き方が強すぎ、かつ循環していた。SDD-REV-006 の `gate_preconditions` は
「Gate 通過前に消化する条件」と「Gate で決める論点」を区別していない。
**この区別自体が SI-SDD-031（レビュー指摘の追跡機構）の設計で扱うべき事項**であり、
本記録をその入力とする。

## 裁定1 — 検証判定の帰属

**採用: 案B「判定機能を sdd-test へ移設する」**（推奨案 A ではない）

- 証跡は sdd-test が書き、判定は sdd-core が行うため、「証跡が宣言どおりの検証手段か」という
  不変条件の持ち主がどちらにもいなかった（SI-SDD-030 の構造的理由）。
- 案A（証跡 schema に検証手段を持たせ、`spec_inspect` を Conformist と明示）は実装が小さいが、
  **不変条件の所有者が曖昧なまま**である。裁定者は境界を正す側を選んだ。
- **帰結（重要）**: sdd-test 側に判定ツールが増えると、`scripts/spec` ラッパーが
  sdd-core の4ツールすべてを必須解決する設計（CORE-FR-011）と衝突する。
  `spec_verify.py` がラッパーに載せられなかったのと同じ制約であり、
  **SI-CORE-038（ラッパーの任意ツール対応）が裁定1の実装前提になる**。
- 分割の範囲は実装時に定める。`spec_inspect` は孤児・幽霊・トレース・docs 乖離・委託も
  同じ走査で判定しており、検証関連だけを切り出す境界は自明ではない。

## 裁定2 — GatePassage の導入

**採用: 導入する**

- Pass 2 の CRUD マトリクスで、**Gate 通過を表す成果物をどの機能も生成していない**ことが
  判明した。手順としては定義されているのに実体が無いため、「Promotion Gate が一度も
  実行されていない」ことを機械が言えなかった（SI-SDD-028）。
- 最低限の属性: 対象・日付・裁定者・確認した `DecisionReference` の集合。
- 加法的であり既存要件に影響しない。未通過の滞留が集計可能になる。

## 裁定3 — ReviewFinding の独立と `tracked_by` 必須化

**採用: 独立させ `tracked_by` を必須にする**

- レビュー指摘が synthesis の内部データであるため追跡先を持てず、SDD-REV-004 の P1 が
  7日以上消えた（SI-SDD-031）。
- P0/P1 は `tracked_by`（spec-issue ID）を必須とし、**未紐づけの P0/P1 がある状態で
  `decision: PASS` を出せないようにする**。
- SDD-REV-006 は手作業で追跡表を作った。移行対象のレビューは4回分のみでコストは小さい。

## 裁定4 — 集約分割（破壊的変更）

**採用: 種別ごとに分割する（段階的）**

- SDD-DSN-005 が requirement / spec-issue / task / design を `Specification Artifact` の
  一語で括ったが、4者はライフサイクルも権限も語彙も異なる（`open→accepted` と
  `draft→approved` は別物）。遷移ポリシーが種別分岐の塊になっている。
- 共通に残すのは **ID 採番** と **Decision の記録** だけ。
- **要件本体63件は無変更**。変わるのは `spec_update` の内部構造と、場合により CLI 契約。
- 破壊的変更であり bitz-sdd の major bump を伴う可能性がある。段階的に分離する。

## 裁定5 — manual-check の扱い（破壊的変更）

**採用: 実施記録を成果物として定義し、証跡の一種へ格上げする**

- `manual-check` は統制語彙にありながら検証コンテキストに成果物を生まない
  「検証しない検証手段」であり、ユビキタス言語の矛盾語だった。これが 42.5%（51/120）と
  二重の検査免除を許した（SI-SDD-029）。
- 格上げにより語彙の矛盾が消え、`spec_inspect` の証跡欠落 WARN から manual-check を
  除外する必要も無くなる。
- **既存51件へ遡及して実施記録を求めるかは本 Gate では決めない**。実装時に別途裁定する。
- 実施記録は SDD-FR-152 の許可リスト制約（秘密値・環境固有情報を保存しない）を継承する。

## 裁定6 — sdd-usecase の配置

**採用: コンテキスト3「上流と設計」へ配置する**

- ユースケースはジョブ（Discovery）から要件（仕様ライフサイクル）への橋渡しであり、
  Core へ入れると Core の語彙にユースケースという別語彙が混ざり境界が濁る。
- 接続は Customer-Supplier（上流が供給側）。
- これは **SI-SDD-013 の責務分界の答え**であり、同 spec-issue の前提条件が満たされた。

## 実装順序（依存を解いた結果）

裁定は相互に依存する。とくに裁定1が SI-CORE-038 を前提条件へ引き上げた点が効く。

| 順 | 内容 | 性質 | 根拠 |
|---|---|---|---|
| 1 | **SI-CORE-038** ラッパーの任意ツール対応 | 加法的 | 裁定1の実装前提。これが無いと sdd-test 側へ判定を置けない |
| 2 | **裁定2** GatePassage / **裁定3** ReviewFinding | 加法的・並行可 | 他の裁定に依存しない。滞留と指摘消失を先に止める |
| 3 | **裁定1 + 裁定5** 証跡 schema の拡張と判定移設 | 破壊的（証跡 schema） | 同じ成果物を触るためまとめて行う。schema 利用実績は現在1件 |
| 4 | **裁定4** 集約分割 | 破壊的（CLI 契約） | 最も影響が大きい。3 の完了後に着手する |
| 5 | 逆起票31件の分類（GP-003 残り） | 分類のみ | 境界が確定してから照合する |
| 6 | Promotion Gate の実行（フェーズ4） | 検収 | 裁定2 の GatePassage が前提 |

裁定6（sdd-usecase）は配置の確定のみであり、スキル新設は SI-SDD-013 本体の作業として
上記とは独立に進められる。ただし**裁定4 の完了前に新スキルを足すと分割対象が増える**ため、
順序4のあとが望ましい。

## 破壊的変更の波及と移行の担保

**依存宣言では止まらない**。bitz-ddd は `bitz-sdd>=2.0` を宣言しており上限が無いため、
bitz-sdd を 4.0.0 へ上げても `release_check` は PASS する。裁定4・5 の実装時には
移行計画を人間が明示的に持つ必要がある。対象:

- bitz-ddd（`bitz-sdd>=2.0` を宣言。SI-DDD-001 のとおり既に追随漏れがある）
- 本リポジトリ自身（bitz-sdd をリリース済み固定版として消費）
- Codex CLI / Antigravity 側のプラグインキャッシュ

## 残余リスク

- 裁定1 の分割境界が自明でない。`spec_inspect` の判定は単一の走査結果を共有しており、
  検証関連だけを切り出すと走査が二重になる可能性がある。実装時に再評価する。
- 裁定5 の遡及範囲を決めていない。51件すべてに実施記録を求めると作業量が大きく、
  求めないと格上げの効果が薄れる。中間で止まると現状と同じ矛盾が残る。
- 本 Gate は `gate_preconditions` の3件（GP-001 / GP-003 の残り / GP-005）が open の
  ままで実行された。上記「前提条件の定義が循環していた」のとおり、GP-001 と GP-005 は
  Gate の帰結として扱うのが正しい。GP-003 の残り（逆起票31件の分類）は実装順序5 で消化する。
