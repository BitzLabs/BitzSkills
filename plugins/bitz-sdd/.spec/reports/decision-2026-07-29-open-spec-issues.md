## 一括採用の根拠

4件はいずれも起票時の予備判定が **accept 推薦**であり、いずれも既存要件との矛盾・
ガードレール抵触が「なし」と確認済み。裁定を保留し続けること自体が
「open のまま放置された提案」を積み上げ、`spec_status.py` の次アクション提案を
恒常的に占有していた。採用と着手順を分離し、採用は一括、実装は優先度順に分割して進める。

## 個別の採用理由

### SI-SDD-011 — sdd-docs の Discovery 同期マッピング不足

`sdd-discovery` は vision / metrics / scope / personas / positioning の5成果物を
docs へ同期すると規定するが、`sdd_sync.py` の `DEFAULT_MAPPING` は vision と scope の2件のみ。
**スキル手順（宣言）と実装（実際の挙動）が乖離**しており、利用者はコマンドが正常終了しても
Discovery 成果物の一部が docs に現れないことに気づけない。憲法2（双方向同期）の
実効性を損なうため採用する。依存していた SI-SDD-010 は SDD-FR-135 として実施済みで、
着手の前提は満たされている。

### SI-SDD-013 — 標準ユースケース工程の新設

BitzSDD には「ペルソナ／ジャーニー」「任意の DDD ドメインストーリー」「主要ユースケースから
FR を派生する」という断片的な規定はあるが、ユースケースを**採番・検証し、要件／テストへ
トレースして docs へ同期する独立フロー**がない。docs の必須6章には
`02_ユースケース/` が既に存在しており、章はあるのに生成源が `.spec` 側に無い状態になっている。
この構造的欠落は放置すると章そのものが手書き運用へ退行するため採用する。

ただし本件は新スキル追加を含む最大案件であり、`bitz-ddd` の `ddd-story` との責務分界
（ハッピーパス記述 vs 代替フロー・トレース契約）を Design Gate で確定させる必要がある。
実装着手は他3件の後とする。

### SI-SDD-014 — monorepo の workspace 外テスト参照の集約

canonical 実行（`spec inspect --workspace . plugins/*`）でも参照判定が各 workspace 配下の
`tests` / `test` / `src` に閉じているため、モノリポルートの `tests/` から参照される
プラグイン要件が「テスト/実装からの参照がない」と誤警告される。FLW-FR-001 が
verified・テスト green にもかかわらず警告を受けた実例がある。

**検証中心（憲法3）の前提は「機械の排出を人間が信用できること」**であり、
verified 要件に誤警告が残る状態はトレース率指標の信頼性を直接損なう。読み取り専用検査の
範囲内で修正でき、影響も `spec_inspect.py` の参照集計・レポート・回帰テストに限定される。
**4件のうち最も費用対効果が高いため、先行して実装する。**

### SI-SDD-016 — 検証結果の機械可読証跡

同一コミット・同一結果の再検証でも実行時間が揺れ、test-spec へ手書きした数値と
会話上の最新値が食い違う事象が発生している。green 判定に必要な安定情報
（commit SHA・終了コード・passed/failed 件数）と観測値（duration）を分離し、
コマンド実出力に基づく機械可読証跡へ一本化する。手書き数値を正としている限り
検証結果の再現性が人手に依存するため採用する。

新しい仕様成果物 schema と複数スキルの接続を伴うため、通常フロー + Design Gate 必須。

## 実装順序（本裁定に含む）

1. **SI-SDD-014**（先行・本裁定の直後に着手）— 誤警告の解消。影響範囲が明確で回帰テストも書きやすい
2. **SI-SDD-011** — 宣言と実装の乖離解消。SI-SDD-010 実施済みで前提が揃っている
3. **SI-SDD-016** — Design Gate を通して新 artifact schema を確定してから実装
4. **SI-SDD-013** — 責務分界を Design Gate で確定。新スキル追加のため最後

## 残余リスク

- 一括採用により accepted かつ未着手の spec-issue が3件積まれる。`spec_status.py` は
  参照元要件が verified/promoted の場合にのみ実施記録欠落を警告するため、
  未着手のまま滞留しても機械的な検出はされない。滞留の可視化は本記録の
  「実装順序」節と `.spec/STATE.md` の記録に依存する
- SI-SDD-013 / SI-SDD-016 は Design Gate 前であり、設計裁定の結果によっては
  要件化の段階でスコープが縮小・分割される可能性がある。採用はスコープを固定しない
