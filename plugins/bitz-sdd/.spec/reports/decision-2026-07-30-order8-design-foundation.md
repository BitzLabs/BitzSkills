## 裁定I — `SI-SDD-032`（sdd_sync の mtime 精度と mutation lock 不参加）

**採用: accept。V4 設計前に解消する。内容ハッシュ比較へは進まない**

- 比較側を `st_mtime_ns` へ揃え、`sdd_sync` / `migrate_docs` を workspace mutation lock へ
  参加させる。どちらも**加法的**で、公開契約 `SDD-FR-100`（新しい方を残す）の意図を
  精度面で満たしに行く変更であり、契約の改訂を伴わない。

  ターゲット設計で再検討する。
- V4 設計は `.spec/` と `docs/` の同期を多用する。**無音のデータ損失は検証で気づけない**

  よって 3.x 無破壊準備フェーズ（順序18〜）へ後回しせず、設計着手前に解消する。

## 残余リスク

- 裁定H で提案4 を見送った結果、**ブランチ跨ぎの ID 衝突は依然として起こる**。検出は
  マージ後（または `origin/main` へ rebase 後）の inspect に依存し、衝突時は改番の手戻りが
  発生する。V4 設計は並行セッションで進むため、DSN の払い出しが集中する期間はこの手戻りを
  引く可能性がある。運用上は「設計成果物の採番は origin/main へ追随した直後に行う」で緩和する。
- 裁定I で mutation lock へ参加させると、`sdd_sync` が他の変更 CLI と直列化される。
  長時間の同期がロック待ちを生む可能性がある。lock の粒度・タイムアウトは実装時に実測する。
- 裁定J の `done` 抑止は `phase_code` の**返り値の分布**を変える（JSON の公開契約自体は
  維持するが、同じワークスペースが返す値が変わる）。`phase_code` を条件分岐に使っている
  スキル・スクリプトの棚卸しを実装時に行う。
- 裁定K で機械強制を見送るため、共有作業ツリーの汚染は**規律の遵守に依存**する。
  bitz-flow V2 の Promotion Gate まで、この穴は文書だけで塞がれた状態が続く。
