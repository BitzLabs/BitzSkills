## 実測（本裁定の根拠 — basis: verified）

### 1. 両 spec-issue の消化状況

`SI-SDD-035` の4提案のうち、提案1（裁定記録の訂正）と提案2（ROADMAP の順序見直し）は
PR #135 で、提案3（前提条件の `verified` / `assumed` 区別）は PR #140 の `SDD-FR-161` で
消化済みである。ただし提案2 のうち **`SI-CORE-038.md` 側へのスコープ縮小の追記は未了**。
残るのは提案4（呼び出し規約の明文化）と、この追記の2点だけである。

`SI-CORE-038` は提案2（全直接実行へ統一）が却下、提案1（任意ツール概念）が先送り済みで、
残るのは提案3（後方互換）と提案4。**提案4 は `SI-SDD-035` 提案4 と同一の作業**である。

### 2. 呼び出し規約は「2系統」ではなく「曖昧」だった

bitz-sdd の SKILL.md にあるスクリプト呼び出し32件を数えた結果:

| 形式 | 件数 |
|---|---|
| `python3 scripts/<name>.py`（どこ基準か書かれていない） | **31** |
| `python3 <このスキル>/scripts/<name>.py` | 1 |

`scripts/sdd_sync.py` は7件あるが、実体は
`plugins/bitz-sdd/skills/sdd-docs/scripts/sdd_sync.py` であり、本リポジトリの `scripts/` には
存在しない（あるのは `agy_guard.py` / `bump_version.py` / `release_check.py` / `spec`）。

`SI-CORE-038` が「利用者はどのツールがラッパー経由でどれが直接実行かを暗記する必要がある」と
書いた状態は実際にはより悪く、**大半の呼び出しが repo 相対ともスキル相対とも判別できない**。
また `SI-SDD-035` が「スキル内からの呼び出しはスキル相対で解決できる」と根拠に挙げた
`sdd-report/SKILL.md:37` は、**32件中1件の例外**であった（同 spec-issue の記述は実態の
一般化としては弱かった）。

### 3. `REL` 一般化の必要性は現時点で assumed

`scripts/spec:40` の `REL = ("skills", "sdd-core", "scripts")` の一般化が必要になるのは、
「裁定1 で sdd-test 側に立つツールを**ラッパー経由で公開する**」場合に限られる。しかし:

- 裁定1 の追跡先 `SI-SDD-030` は accepted・**未着手**で、移設の形は設計されていない
- 裁定B（新規サブコマンドの公開）は `decision-2026-07-30-implementation-order.md` で
  「必要になってから」として先送り済み

したがって現時点で `basis` は **assumed** である。

## 裁定E — 順序7 のスコープ

**採用: 呼び出し規約の明文化だけに縮め、`REL` 一般化は順序8（裁定1）へ移す**

- 実測3 のとおり `REL` 一般化の必要性は assumed であり、**`basis: assumed` を根拠に
  `kind: blocking` な先行タスクを立てられない**（`SDD-FR-161` で機械検証まで入れた不変条件）。
  これを自分自身に適用する。2026-07-29 の Design Gate が `SI-CORE-038` を最先行に置いた
  判断（`SI-SDD-035` が是正した）と同じ形を繰り返さない。
- `REL` 一般化は裁定1 の設計の中で必要性が `verified` になった時点で同時に行う。
  移設の形によっては不要になる可能性も残る。
- 結果として順序7 は**加法的かつ小さい**（規約の明文化と31件の呼び出し修正）。
  順序8 の破壊的変更（bitz-sdd 4.0.0）と混ぜないことで revert 粒度も保てる。

## 裁定F — 呼び出し規約の形

**採用: AGENTS.md へ明記し、あわせて `CORE-CON-*` 要件として機械検証する**

- `CORE-CON-011`（CLI スクリプトの未知引数拒否）＋ `tests/test_cli_contract.py` が、
  規約を EARS 要件にしてスクリプトを動的収集で検証する前例を作っている。呼び出し規約も同型。
- 散文だけの宣言に留めると、実測2 の31件のようなドリフトを再発防止できない。
  **宣言だけして機械集計を伴わない指標**（`manual-check` 比率 20%）と同じ失敗の形になる
  （`SI-SDD-029`）。
- 新規に追加される SKILL.md も動的収集で自動的に検査対象へ入る。

## 残余リスク

- 順序7 で規約を確定しても、`REL` 一般化を伴わない限り「ラッパー経由 = sdd-core の4ツール」の
  境界は変わらない。裁定1 の設計次第でこの境界を再度動かす必要が生じ、規約の再改訂が要る。
  加法的な追記で済む見込みだが、AGENTS.md と `CORE-CON-*` の両方を同時に直す手間は残る。
- 31件の呼び出し修正は SKILL.md の記述変更であり、各スキルの `metadata.version` bump を伴う。
  bitz-sdd の広い範囲に触れるため、他セッションの作業との競合に注意する。
