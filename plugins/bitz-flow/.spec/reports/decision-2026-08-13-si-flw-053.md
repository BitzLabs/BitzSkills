## 3. 上位計画への伝達経路 — 案A ＋ 案B 併用

`plugins/bitz-sdd/.spec/ROADMAP.md:485-487` は
「bitz-flow V2 の公開 operation / result / SDD opaque ID 接続が安定してから、
bitz-sdd V4 Charter と正式設計を開始する」と定めており、
**bitz-flow V2 は bitz-sdd V4 の直列の前提**（並行不可）である。

ところが同 `:660-663` のフェーズ4 の記述は**2行のみで budget 値を持たない**。
上流が膨張しても**消費側に記録する欄が存在しない**。影響評価が「書かれていない」のではなく
「書く場所が無い」。

- **案A**: `bitz-sdd/.spec/ROADMAP.md` のフェーズ4 へ **bitz-flow V2 の budget 総計を
  参照値として明記**し、「上流 budget が再校正されたら本欄を追随させる」義務を書く。
  **正は `FLW-DSN-014` に置き、消費側は参照のみ持つ**
- **案B**: 参照値の一致を `release_check.py` で機械照合する。
  ワークスペースを跨ぐ照合は `SI-FLW-052` の枠組みに乗せる

案A だけでは人間の規律に依存し、同じ断絶が M3→M4、M4→M5 で再発する。併用する。

**`plugins/bitz-sdd/` は別ワークスペースかつ他セッションが触る可能性があるため、
bitz-flow 側の変更とは別 PR に分ける**（1 PR = 1 関心事）。

## 4. M2 early quick win — M2-3 完了時に `worktree.audit` を公開

現在 M2 は「全部終わるか、M0 read-only へ縮退するか」の二値であり、
**20 session を投じて出荷可能増分ゼロ**になり得る。

**M2-3（create / resume / audit ＋ enum 三者照合）完了時点で `worktree.audit`（read class）を
出荷可能増分として公開する。** read のみであるため縮退規則3（worktree write の公開条件）に
触れず、利用者は早い段階で worktree の列挙・分類を得られる。

`create` / `resume`（local-write）を同時に公開する案は採らない。
finish / discard（M2-5）が未実装の段階で公開すると、
**「作れるが消せない」非対称**（`SI-FLW-054`(5)）を自ら作り出すためである。

## 5. 残債移送の記録 — 機械可読な成果物にする

`FLW-DSN-014` 自身が「散文の予算は機械から見えず、M0 では一度も発動しなかった」と認めている。
移送元・移送先・移送量を機械可読な形で持ち、**受け側の budget に増分が無ければ検出する**
検査を `SI-FLW-052` の検査群へ含める。

同じ検査で、上記「訂正」節が示した**「確定」「裁定済み」と主張する記述に対応する
裁定記録の実在**も照合する。今回発見した3例（`SI-FLW-053` 本文、
`decision-2026-08-13-si-flw-047-048.md`、`FLW-DSN-014.md:669`）は
いずれもこの検査があれば自動検出できた。
