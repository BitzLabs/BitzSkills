## 付随して確定した事項

裁定の過程で実ファイルを確認した結果、issue 本文に無い3点を裁定に含めた。
いずれも上記の選択を成立させるために必要な是正である。

### 付随1: 証跡の保管場所を common-dir 配下 owner-only 領域へ統一する

`FLW-DSN-016.md:355` は create 時 nonce を **registry entry 配下の owner-only file** へ
保存すると定める。しかし `remove-registry-entry` は `worktree.discard` の
**最初の mutating step** である。したがって現行のままでは **discard を始めた瞬間に
nonce が消え**、`worktree-no-effect`（＝未実行）と誤判定される。案B は証跡を
区分の一次情報にするため、この配置では成立しない。

同書 `:430` と `:674` は lock について「**worktree 実体側には置かない — discard で消えるため**」
と既に同じ判断を下している。nonce だけが同型の罠を踏んでいる。
receipt と lock が既に置かれている common-dir 配下 owner-only 領域へ統一する。

これは `SI-FLW-054`(7)（M2 永続成果物の retention。とくに「create 時 nonce が
routine な Git 保守で消える」）の一部を先行して解消する。

### 付随2: §8 の step 規約を「mutating step のみ全射」へ改訂する

`FLW-DSN-016.md:526` は「**全 step がちょうど1つの mutation target に対応する**」と
宣言するが、実体の step 列には反例が2種類ある。

- `sync-main` — 宣言 target **集合外**を変更する（本裁定 (a) の対象）
- `verify-pr-merge` / `verify-target-oid` / `verify-reachability` / `report-remote-candidate`
  — mutation target を**持たない**

規約を次へ改める。**mutating step は宣言済み mutation target 集合へ全射**とし、
**non-mutating step は型で区別**して全射性検査の対象外に置く。
non-mutating step での中断は状態を変えないため、`completed_steps` からの
残存 target 一意化はこの改訂後も成立する（むしろ中断点の場合分けが減る）。

この改訂なしには `SI-FLW-052` の全射性検査が実装できない。

### 付随3: `report-remote-candidate` を step から外し result field にする

(a) で `sync-main` を外すのと同じ「operation の責務を単一にする」判断の一貫適用。
報告は step ではなく operation の result が担う。

## 各裁定の根拠

### SI-FLW-047 — 案B（証跡軸）

現行設計では discard の中断点2箇所がいずれも解除可能な3区分のどれにも該当せず、
**中断すれば必ず恒久 quarantine へ落ちる**。加えて、解除区分 `worktree-registry-stale` の
必須証跡は「path が存在しないことの**証明**」だが、同じ文書の ABA 節が
「否定的主張は観測から導けない」と結論している。**この区分は原理的に空**である。
さらに `worktree-no-effect`（三者＋nonce 不在）は **discard 成功後の観測と完全に一致**し、
「未実行」と「成功済み」を区別できない。

案A（step 順の変更）と案C（8通り全列挙）は中断点の網羅は改善するが、
上記2件は**存在パターンだけを見ている限り原理的に解決しない**。
案B のみが両方を同時に解く。

実装コストの評価も案B に有利である。M1 は同じ問題を intent record（`FLW-DSN-015` §
`intent record v1`）と CAS receipt hash-chain で解決済みであり、`confirmed-done` という
「証跡による完了確定」区分を既に持つ。機構も置き場所（common-dir 配下 owner-only 領域）も
既存であり、**新規開発ではなく流用**になる。

### SI-FLW-048 (a) — 案A（`sync-main` を独立 operation へ）

`worktree.finish` の canonical mutation target は対象 worktree に閉じた4点
（`worktree-dir` ＋ `worktree-registry` ＋ `local-ref` ＋ `index`）と宣言されているが、
step 契約に含まれる `sync-main` は **main の branch ref と index** を変更する。
これは `FLW-REV-011:SYN-003`（guard していない target を別 operation が変更する）と
**同型の穴**であり、§8 の自己宣言にも違反している。

案B（finish の target に main を加える）は finish が main を巻き込んで排他するため、
無関係な作業まで待たされる。案C（read-only 検査へ格下げ）は利便性を落とす。
案A のみが「**宣言 target = 実変更 target**」を回復し、`SI-FLW-052` の全射性検査を
機械実行可能にする。

新設 operation の class は `SI-FLW-049`（operation class の所有権確定）で決める。

### SI-FLW-048 (b) — dev+ino への一本化

**issue 本文の推薦（`(path, dev+ino)` の組）を採らない。** 組にすると bind mount 経由では
path が異なるため別 key となり収束せず、「不一致時 `BLOCKED`」と解釈すれば正当な
bind mount アクセスが常時ブロックされる。**どちらの解釈でも `M2-FLT-006`
（別 clone・別 mount から同一 worktree 要求 → 同一 guard へ収束）を満たせない。**

guard key の役割は「**実体**への同時アクセスの直列化」であり、canonical path は実体の
**名前**にすぎない。名前で守れば別名から入られる。dev+ino は実体そのものを指し、
bind mount は同一 superblock を共有するため収束は自然に成立する。

inode 再利用（削除→作成で同じ dev+ino が別実体を指す）の検出は、
`SI-FLW-047` 案B の instance nonce が担う。`FLW-DSN-016` §5 は既に
「**instance identity を guard key へ含めてはならない**」と定めており、
**identity（実体）と instance（世代）の分離**という設計意図に合致する。

残るリスクは `st_dev` の安定性（NFS・再マウント・一部の filesystem で変動しうる）である。
これは root ごとの filesystem 能力 probe の論点として **`SI-FLW-054`(8) に残す**。
本裁定では解決しない。

### SI-FLW-048 (c) — 祖先遡り

`create` は定義上 対象 path が存在せず、実在 path の解決を前提とする方式では
key を導出できない（`FLW-REV-011:SYN-002` の guard key 側での再発）。
「最も近い実在祖先の identity ＋ そこからの相対 path」を合成する規則は
`M2-FLT-009`（不在 path の case 差）が既に要求している方式であり整合する。
(b) の dev+ino 一本化とも自然に噛み合う（祖先は実在するため inode を持つ）。

### SI-FLW-048 (d) — `git status` 出力への委譲

racily-clean（同一 mtime 秒内の編集）の判定は Git 自身が index 側で解決済みの問題であり、
再実装する理由がない。`--porcelain=v2` に untracked を含めることで、discard で失われる
untracked ファイルも CAS の対象に入る。走査コストは Git が既に払っている分に収まり、
「全ファイルを自前で hash して上限規定を別途設ける」案より**規定が1つ減る**。
