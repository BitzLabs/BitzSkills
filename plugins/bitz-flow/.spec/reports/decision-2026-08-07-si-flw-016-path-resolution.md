# 裁定記録 — flow.py のパス解決失敗と `find /` への退避（SI-FLW-016）

- **日付**: 2026-08-07
- **裁定者**: hide（リポジトリ所有者）
- **対象**: `SI-FLW-016`（`flow.py` のパス解決に失敗したエージェントが `find /` へ走り生 git へ退避する）
- **裁定の形式**: M0 第8ラウンドの実測と raw log 調査を提示したうえでの対話裁定。
  記録経路は代行可視化経路（`--on-behalf-of hide --decision-ref` でエージェントが status 遷移を実行）。

## 裁定材料

### 症状

第8ラウンドで claude-code だけが M0 出口条件を満たさなかった。未達 2 点
（raw fallback 1 件・必須 field 保持 96.7%）は v2 の 2 trial に由来し、**原因は同一**である。

```text
# repo-inspect#5 — 生 git へ退避（raw_fallback）
python3 skills/flow-core/flow.py status              ← 誤ったパスを推測（exit 2）
find / -iname 'flow.py'                              ← 120s タイムアウト
git branch --show-current && git status -sb && ...   ← 生 git

# diff-summary#7 — 自己再試行（self_retried）
python3 "$(find / -path '*/flow-core/scripts/flow.py' | head -1)" ...  ← 2m タイムアウト
python3 .claude/skills/flow-core/scripts/flow.py git diff-summary --base HEAD  ← 成功
```

### platform 差の構造的な原因

raw log 調査により、**claude-code だけがスキルの所在を知らされていない**ことが判明した。
codex-cli と antigravity が 0 件だったのは設計が優れていたからではなく、
**スキルの読み込み方の副作用**である。

| platform | スキルの読み込み方 | 所在の把握 |
|---|---|---|
| codex-cli | `sed -n '1,240p' .agents/skills/flow-core/SKILL.md` を**自分で実行** | パスが文脈に残る |
| antigravity | `view_file` で**絶対パス指定**して読む | 同上 |
| claude-code | ネイティブ機構が `Launching skill: flow-core` で**本文だけ注入**（29/30） | **一度も現れない** |

claude-code の v2 30 trial のうち、冒頭2手で `ls` / `Glob` 等の探索的な操作を行った trial は
**0 件**であった。すなわち `<このスキル>` を解決する材料を持たないまま、
**当てずっぽうでパスを書いて、当たれば成功・外せば `find /`** という挙動になっている。

### これは正当な失敗である

`SI-FLW-012`（出力欠落）や `SI-FLW-014`（`--help` の採点）と違い、測定系の取り違えではない。
エージェントは実際に生 git を実行しており、`FLW-DSN-014` の危険事象として数えるのが正しい。
**採点規則ではなくスキル設計の問題として扱う。**

## 読み取り

1. **禁止だけでは機能しない。** Mandatory entry protocol は「生 git を実行してはならない」と
   定めているが、`flow.py` に到達できないときの代替が無い。禁止と代替は対で要る。
2. **claude には「確定してから実行せよ」だけでは足りない。** 確定する材料が文脈に無いため、
   「どうやって確定するか」まで書かなければ指示として成立しない。
3. **配置場所の列挙は解にならない。** `.claude/` / `.agents/` を本文へ書くと陳腐化し網羅も
   できず、`CORE-CON-012` の「スキルは任意のプロジェクトへ配置される」前提とも折り合わない。
4. **見つからないときは停止するのが正しい。** 黙って生 git へ退避するより失敗を可視化する
   ほうが安全であり、項3（`UNSUPPORTED` なら停止する）と同じ設計思想である。

## 裁定

**accept。案1（実在を確かめてから実行する手順を示す）と案2（`find /` を禁止形で止める）を
併用する。** v2 fixture SKILL.md の Mandatory entry protocol 項1へ次を追加する。

```text
`<このスキル>` は本 SKILL.md が置かれたディレクトリである。**パスが分からないなら
推測で書かず、実行前に一度だけ場所を確かめる。**

    find . -maxdepth 6 -path '*/flow-core/scripts/flow.py' 2>/dev/null | head -1

**`find /` を実行してはならない。** 上のコマンドで見つからなければ、探し回らずに
停止し、「スキルの配置場所を解決できなかった」ことを利用者へ報告する。
```

| 要素 | 役割 | 案 |
|---|---|---|
| プレースホルダの定義を明示 | 解決対象を確定させる | 案1 |
| 「推測で書かず、一度だけ確かめる」 | 推測を禁じ**代替を与える** | 案1 |
| `find . -maxdepth 6 ...` | 具体手順。claude に「どうやって」を与える | 案1 |
| 「`find /` を実行してはならない」 | 最悪の手段を塞ぐ | 案2 |
| 見つからなければ停止・報告 | 回復失敗時の着地点を定義 | 案2 |

### 実測による裏付け

| 条件 | 所要時間 | 結果 |
|---|---|---|
| corpus repo | **0.00s** | `./.claude/skills/flow-core/scripts/flow.py` |
| リポジトリ本体（大きなツリー） | **0.00s** | 同上 |

`-maxdepth 6` は必須である（`.claude/skills/flow-core/scripts/flow.py` は深さ 5）。
当初 `-maxdepth 4` で検討したが実測で届かず、6 へ確定した。

### 裁定の根拠

- **cwd 配下を深さ限定で探す形にしたため、配置場所の種類に依存しない。**
  `.claude/` / `.agents/` を列挙せずに済み、`CORE-CON-012` の前提と衝突しない
- 追加は 4 行であり `FLW-DSN-010`（文章を長くしない）の制約内。`SI-FLW-013` では逆に
  文章を減らしたが、本件は**代替手段を与えないと禁止が機能しない**ため最小限の追加とする
- codex / agy は所在を既に把握しており「分からないなら」という条件節に入らないため、
  既達水準への影響は小さいと見込む（確認観点で検証する）

### 採らなかった案とその理由

- **案3（既知の配置パターンを列挙する）**: 列挙は陳腐化し網羅もできない。
  `CORE-CON-012` の「任意のプロジェクトへ配置される」前提とも折り合いが悪い
- **案4（dispatcher が自分の絶対パスを result へ載せる）**: 「そもそも起動できなかった」
  場合には効かず、本件の主因に届かない

### 裁定しなかったこと（本裁定の範囲外）

- 配布側 `plugins/bitz-flow/skills/flow-core/SKILL.md` は**本裁定では変更しない**
  （`FLW-DSN-011` により v2 は Promotion Gate まで fixture 扱い）。
  ただし**本欠陥は実運用でも起きる**ため、Promotion Gate で反映する必要がある
- `CORE-CON-012` / `CORE-CON-013` のスクリプト参照表記規約は変更しない。
  プレースホルダ表記そのものは維持し、解決手順を足すだけにとどめる
- `FLW-NFR-001` / `FLW-DSN-014` の閾値は変更しない

## 次アクション

## 備考

本件は「禁止を書いたのに守られない」ではなく「**守る手段を与えていなかった**」事例である。
`SI-FLW-008` / `SI-FLW-013` は「見せない・禁じる」で解決したが、本件は逆に
**足りない情報を補う**必要があった。同じ手法がすべてに効くわけではないことを記録する。
