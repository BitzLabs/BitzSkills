# 起票計画レビュー — 証拠能力と変異義務の規範化

- **日付**: 2026-08-25
- **対象**: `FLW-REV-030:GP-002` を消化するための起票計画（未起票）
- **判定**: **却下**（codex / antigravity / 自己レビューの3者一致）
- **位置づけ**: 裁定ではない。**次に再開するときの判断材料**として残す
- **前提**: `FLW-REV-030`（FAIL / 2.28）、`GP-002`（確認方法。他の3件より優先）

## 何を提案し、なぜ却下したか

M2を4回レビューして毎回FAILし、3回連続で根が同じ（**完了を確認する方法が壊れている**）で
あったため、確認方法そのものを規範化する案を立てた。中心の設計判断は次であった。

> 「変異の義務」が「証拠能力の規約」を機械的に包含する。登録した変異ごとに検出テストが
> 1件以上あることを要求すれば、source照合テストも定数照合テストも変異を検出できないので
> 自動的に落ちる。禁止リストを人間が守る規約にする必要がない。

**この主張は誤りである。実測で反証した。**

| 変異 | 定数照合テスト（=不適切なテスト）の反応 |
|---|---|
| `_AUDIT_ACTIONS[QUARANTINE] = "none"`（**定数**の変異） | **検出する**（2 failed） |
| `verify_receipt` の `valid = True`（**振る舞い**の変異） | **検出しない**（全2574 passed） |

不適切なテストでも変異はkillできる。「変異が検出された」は「公開経路の振る舞いを見ている」の
証明にならない。`FLW-REV-030` で `UNSUPPORTED → BLOCKED` 変異をkillしたのが
**ファイル指紋テスト**（cli.pyが`COMPATIBILITY_INPUTS`に入っているため）だった事実も、
同じことを示している。証拠能力と変異保証は**独立に強制する**必要がある。

## P0 所見

| # | 内容 | 出所 |
|---|---|---|
| 1 | 変異killと証拠能力は別性質。「1件以上failure」を合格条件にすると、source照合・指紋・import error・timeout・無効変異までkillに数える | codex + agy（実測で確定） |
| 2 | curated台帳は**同一主体の盲点を閉じない**。「登録した変異の検出」は保証できても「登録すべき変異の欠落」は検出できない。今回有効だった順序（外部が場所を指す→変異で確証）が計画に無い | codex + agy |
| 3 | 「安全判定」に機械的定義が無い。`FLW-CON-008` は `implements` 宣言で対象を動的収集し**対象0件でFAIL**させる閉包を持つが、本案には同等物が無い。登録しなければ対象外にできる | codex + agy + 自己 |
| 4 | **共有作業ツリーでのバックアップ復元が危険**。crash・中断・他セッションの同時編集で変異が残留する、または他人の変更を上書きする | codex |

P0-4 は自分に返る所見である。**本セッション中、実作業ツリーのファイルを直接変異させ続けた。**
並行作業を前提とするリポジトリ（AGENTS.md「並行開発」節）でこれは事故待ちであり、
`FLW-REV-030` 自身が使い捨てcloneを採ったことと矛盾している。以後、変異は原本を
変更せず使い捨てコピーで行う。

## 自己レビューが単独で見つけた点

**agyの是正案「全テストが公開ファサードを呼ぶこと」は成立しない。** 実測すると
M2テスト**355件中275件（77%）**が公開経路を通っていない。純粋関数の単体テストが多数
含まれ、一律違反にすると即座に例外規定へ逃げて空文化する。

正しい絞り込みは「**証拠として引用されるテスト**」である。`FLW-CON-008` は既に垂直接続図で
production test IDを名指しさせ、fixture注入テストの記載を禁じている。**新しい方針を作らず、
この既存機構を判定APIへ広げる**のが筋である。

生成型変異の規模も実測した（AST上の変異点をmutmut相当の演算子で数えた概算）。

| 対象 | 変異点 | 逐次実行（M2 subset 51.6s/537 test 基準） |
|---|---:|---:|
| 安全モジュール全体（6 file / 4174行） | ~2991 | 約43時間 |
| `worktree_operability.py` のみ | ~245 | 約3.5時間（8並列で~30分） |

生成型は**定期の棚卸し**、curatedは**回帰防止**。hybridが妥当という結論に数値の裏付けがある。

## 修正方針（次に再開するときの出発点）

1. **要件は2本**（証拠能力 / judgement inventoryと変異保証）。同一GateでAND評価して片直りを
   防ぐ。1本に統合する当初の論拠は弱く、`FLW-CON-008` 自身が1本でもドリフトしている
2. **judgement inventoryを先に作る** — 安定ID・公開入口・公開するcode/cause/action・
   admissible test ID・curated mutant ID。対象0件と未登録公開判定でFAIL
3. **kill判定を厳密化** — baseline PASS → 変異時に**公開経路テストのassertion failure**のみ
   `KILLED`。import error・timeout・crash・0 testは `BLOCKED`（killに数えない）
4. **隔離** — 原本を一切変更せず、変異ごとに使い捨てコピー。前後で原本hash不変を確認
5. **runnerの検証は自己変異ではなく独立fixture project**（必ずkillされる変異・必ずsurviveする
   変異を含む）。自己変異は循環している
6. **生成型は先にspike**（10〜20変異）して生成数・実行時間・equivalent率を測ってから採否を
   決める。codexはmutmut 3系が関数外コードを変異しないため `_AUDIT_ACTIONS` のような
   module-level mappingを取りこぼすと指摘している（**未検証**）
7. **既知2件のテスト是正を最初に行う** — インフラより先。`GP-002` の一部を閉じ、一般化の
   実例になる
8. Design Gateのscopeに**設計成果物**を含める（当初案は要件だけで不足）

## 見積り

当初の3〜3.5 sessionは**過小**であった。codexの暫定値は**5〜10 session**（spike後に再見積り）。
両者とも根拠が薄いことを明記している。

## 推奨する着手順

**B → C → A**

- **B**: 既知2件（`test_flow_m2_judgement_quality.py` / `test_flow_m2_platform_probe.py`）の
  テスト是正だけ先に着手する
- **C**: 生成型変異のspikeを実施し数字を揃える
- **A**: 上記2つで得た実例と数字をもとに計画を書き直し、起票する

理由: 4回のFAILはいずれも「実物より先に規範を決めた」形で起きている。まず1例を公開経路で
直し切り、その形を規範化するほうが安全である。

## 手順についての記録

**起票前にレビューしたため、誤った規範を承認する前に止まった。** `FLW-REV-028` は判定の
**後**にセカンドオピニオンをかけて覆り、`FLW-REV-029`／`030` は**前**に実施した。今回は
成果物ですらない計画段階で実施し、中心の設計判断が誤っていることを起票前に検出できた。

一方で、**3回連続して最も重い所見は自己レビュー単独では出ていない**（`FLW-REV-029`、
`FLW-REV-030`、本レビュー）。これは偶然ではなく傾向として扱う。
