## 各裁定の根拠

### SI-FLW-043 — `FLW-NFR-007` の改訂

現行の approved 要件は「対象が symlink、複数 hardlink、**repo 境界外 parent**、または
所有者不一致である THEN 原本を変更せず `BLOCKED` を返すこと SHALL」と定める。
`FLW-DSN-006` の worktree 配置は定義上つねに repo 境界外 parent を持つため、
**現行要件のままでは M2 の `worktree.create` / `discard` がすべて `BLOCKED` になる**。

改訂は禁止の解除ではなく、**「repo 境界外だから拒否」から「承認済み root 配下だと
機械検証できたから許可」への置き換え**である。許可条件は3点すべてとし、
1つでも欠ければ従来どおり `BLOCKED` とする。symlink・複数 hardlink・所有者不一致に対する
既存の禁止は緩めない。緩めるのは「repo 境界外 parent」の一項目だけである。

却下した場合は worktree root を repo 配下・同一 filesystem へ限定する縮退が必要になり、
`FLW-DSN-006` の「repo 内走査への混入を避けるため repo 外を既定とする」判断と両立しない。
配置規則自体の再設計へ戻ることになるため、accept する。

### SI-FLW-044 — `FLW-CON-006` の厳格化

`FLW-DSN-015` は可逆な `git.publish-branch` に「provider が原子的に検証する
expected remote OID CAS」を必須とする一方、`FLW-CON-006` は非可逆な remote 削除に
「削除直前に再照会し、一致しない場合は削除しない」しか課していない。
read-then-delete は TOCTOU を構造的に許し、同一 SHA へ戻す force push（ABA）は
再照会一致では原理的に検出できない。**可逆な操作より非可逆な操作の保護が弱いという
安全境界の逆転**であり、M2 の破壊操作を実装する前に是正するのが最も安い。

改訂は既存基準を緩めず**厳格化のみ**であるため、現行の負の fixture
（証跡不一致時の削除0件、禁止 command 出力0件）はそのまま通る。

ABA 検出 capability の実在性は未検証である（`FLW-REV-012:GP-004`）。
**実在性の確認を M2-5 着手前の先行タスクとし、実在しなければ capability 分岐を削除して
「削除は常に ABA 不検出を明示した承認要求を経る」単一経路へ確定させる**。
死に枝を設計に残さないことを accept の条件とする。

### SI-FLW-045 — 案A（write class での分割）

`decision-2026-08-12-m1-6-scope.md` が M2 以降へ送った被測定物 confirmation について、
受け側の `FLW-DSN-014` M2 行が未改訂であり、**送った側の裁定と受けた側の設計が
接続していない**状態だった。

案A を採る理由は、`decision-2026-07-31` の裁定3（cross-host GitHub create の
coordinator 証明手段は M3 設計へ委譲）との干渉を避けられることである。
remote-write confirmation を M2 へ取り込むと、M3 へ委譲したはずの coordinator 証明手段が
M2 の前提として降りてくる。write class で分割すれば裁定3 を変更せずに残債を回収でき、
worktree-first の安全境界（local-write 主体）は M2 で閉じるため縮退規則3 の趣旨も満たす。

案B（coordinator 証明手段の前倒し）は裁定3 の再裁定と M3 からの budget 移送を伴い、
M2 着手前の補強としては重い。案C（全体を M3 へ）は残債の行き先を再び先送りする。

**remote-write confirmation の残債は M3 の入口条件として `FLW-DSN-014` へ
受け側の記述を必ず作る。** M1→M2 で起きた断絶を繰り返さないことを accept の条件とする。

### SI-FLW-046 — accept（M2 着手前）

2026-08-12 に実際に起きた事故（未 push・PR なし・worktree 未展開のローカルブランチを
確認せずに着手し、`SI-FLW-041` / `042` / `FLW-REV-011` を二重採番したうえ、
そのブランチの人間裁定に反する成果物を作った）に対する再発防止である。

v2 は能力自体を既に持つ（`FLW-FR-007` の branch 列挙、`branch_audit_state` の `ACTIVE`）。
不足は義務化と情報追加であり、**bitz-flow が自分の開発で起こした事故を
自分のツールで防ぐドッグフーディングの直接の題材**にあたる。

適時を「M2 着手前」とするのは、branch audit が M2 の実装位置であり
M2-3（create / resume / audit）へ相乗りできれば増分が最小になるためである。
Promotion Gate 後の Should 昇格に回すと、**v2 開発そのものが同じ事故を繰り返す期間が延びる**。

提案3（採番衝突の検出）は **bitz-flow 側は可視化に留める**。
`.spec/` の採番は `spec_scaffold.py`（bitz-sdd）の所管であり、
検出・是正の所管は bitz-sdd へ委託する。

## 未確定 — budget 再提示が必要

`SI-FLW-046` の accept は **v2 の scope 追加**である。`FLW-DSN-014` は
「新しい要件、operation、platform 固有分岐を追加する場合は予算内であっても
scope 変更として人間へ提示する」と定める。M2 は `SI-FLW-045` の移送後で

それまで M2 の実装へ着手しない。
