裁定前に3件すべての発見事実を実体で再現確認した。特に `SI-FLW-072` の

`SI-FLW-072` のうち「整合的に再計算された receipt の偽装」と外部アンカーの提案は、

## 裁定2 — audit の `release_class` は実観測から per-target で算出する

選択肢は (A) 実観測から per-target 算出、(B) 分類せず `null` + `undetermined_reason`、
(C) 両者の段階適用であった。**(A) を採る**。

- 4区分の判定に必要な入力は、既に観測済みまたは receipt から導出可能である。
  `chain_valid` ← `survey.readable`、`completed_steps` / `mutation_receipts` ← `survey`、
  `all_postconditions_match` ← `not row["divergence"]`、`instance_nonce_matches` ←
  receipt の instance nonce と §5 instance identity の再導出。
- 分類の単位を**集合から divergent target 個別へ改める**。現在は survey 全体を1つの
  evidence へ畳んでおり、target ごとの事実を表現できない。
- (B) は正直だが M2 出口条件6「operation 外変更の audit 検出・quarantine 接続」を
  閉じない。検出だけして解除区分へ繋がらない状態が残るため採らない。
- ただし **推測の禁止は維持する**。target 個別に証跡が欠ける場合はその target だけ
  `release_class: null` + `undetermined_reason` とし、混在を result 上で区別する
  （(C) の性質を (A) の内部規則として取り込む）。

## 裁定3 — 承認モードの配備意図は git 追跡下の宣言ファイルに置く

`signature_mode_status` が registry の**存在**からモードを推定しているため、registry を
削除した配備と最初から plan-digest の配備が区別できず、承認強度が無言で降格する。
配備意図の宣言を鍵の実体から分離する。

| 置き場所 | 役割 |
|---|---|
| `<repo>/.bitz-flow/approval-mode.json`（git 追跡下） | 配備が意図する承認モードの宣言 |
| `$GIT_COMMON_DIR/bitz-flow-v2/trusted-worktree-keys.json`（owner-only） | 鍵の実体 |

判定は次の3値へ分ける。

| 宣言 | registry | 判定 |
|---|---|---|
| `signed-capability` | 健全 | `signed-capability` で続行 |
| `signed-capability` | 不在・破損・権限不正 | **`BLOCKED`**（降格せず停止） |
| 宣言なし | 任意 | `plan-digest`（降格ではなく素の配備） |

git 追跡下に置く理由は、削除が `git status` に現れて検知の錨になることである。
common-dir 側の別マーカー案は、マーカー自体が削除可能で問題が一段ずれるだけなので採らない。
到達最高モードを durable ledger に記録する案は錨としては強いが、台帳の初期化・移設の
運用が増えるため V2 では採らない。

既存の `FLW-CON-006` へ基準を追加する案は、1要件=1関心事が崩れるため採らない。

既存要件への受入基準の追加も本裁定に含める（accepted な spec-issue から導出した要件化であり、
