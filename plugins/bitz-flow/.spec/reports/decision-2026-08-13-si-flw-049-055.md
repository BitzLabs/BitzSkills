## 1. class 体系 — 案B（直交2軸への分離）

### 根拠

`destructive` は `local-write` / `remote-write` と**同じ軸に並んでいない**。
現行の4値語彙は「**書き先**（local / remote）」と「**可逆性**（可逆 / 破壊的）」という
直交2軸を単一 enum へ潰しており、各文書がそれぞれ別の破綻をしている。

| 文書 | 実際に使っている語彙 | 破綻 |
|---|---|---|
| `FLW-DSN-012.md:26` | 4値（`read` / `local-write` / `remote-write` / `destructive`） | `git.delete-remote-branch` が `destructive` としか言えず**書き先の情報を失う** |
| `FLW-DSN-014.md:657-660` | **2値**（`local-write` / `remote-write` のみ。`destructive` 行が無い） | confirmation を書き先で分けたいが `destructive` の置き場が無く、`worktree.*` を「全」でまとめて local-write へ押し込んでいる |
| `FLW-DSN-016.md:44-50` | 3値（`destructive` を使わない） | 書き先軸で素直に書いた結果 `FLW-DSN-012` と衝突する |

案A（`FLW-DSN-012` を唯一の正とし `FLW-DSN-016` から class 列を削除）は二重定義を消すが、
**軸の混同は残る**。`FLW-DSN-014` の confirmation 表が `FLW-DSN-012` から導出できない状態が続き、
`SI-FLW-049` 自身の確認観点「**M2 出口で公開する operation 集合が class から
機械的に導出できること**」を満たせない。案C は安全境界を無記録で緩めるため非推奨。

本欠陥は `SI-FLW-050`（`worktree_state` が直交3軸を単一 enum へ潰している）と**同型**であり、
案B は同 issue 案A と同じ方針の一貫適用である。

### 確定する軸

| 軸 | 値 |
|---|---|
| `write_target` | `none`（read） / `local` / `remote` |
| `reversibility` | `reversible` / `destructive`（`write_target: none` では該当なし） |

`approval`（`none` / `mutation` / `external-write` / `explicit-human`）は上記2軸と
**独立した第3の軸**であり、本裁定では変更しない。`issue.publish` ほかが `external-write` を
使い続けるため、語彙からの値の削除は行わない。

### 4値 class は導出値として維持する

```
write_target = none                        → read
write_target = local  かつ reversible      → local-write
write_target = remote かつ reversible      → remote-write
reversibility = destructive（書き先を問わず）→ destructive
```

この規則を M1-4 で公開済みの全行に当てた結果は**現在の値と完全に一致する**
（`git.fetch` / `stage` / `commit` / `sync` = local+reversible → `local-write`、
`git.publish-branch` = remote+reversible → `remote-write`、
`git.delete-remote-branch` = remote+destructive → `destructive`、read 系 = `read`）。

したがって **`skills/flow-core/references/operation-catalog.md` の `class` 列は1つも変わらず、
M1 の出荷済み契約は変更されない**。compatibility key に影響せず、
**qualification の再実行は不要**である（`SI-FLW-051`(b) とは連動しない）。

軸そのものは `FLW-DSN-012` にのみ置き、出荷済み catalog へは公開しない。
M2 で worktree operation を catalog へ追加する際に軸列を露出するかは、そのとき判断する。

### 各文書の従属関係

- `FLW-DSN-012` — **class 体系の唯一の正**。2軸と導出規則、および全 operation の軸値を持つ
- `FLW-DSN-016` — class 列を**削除し参照に置換**（案A の良い部分をここで取り込む）。
  M2 固有の詳細（guard target・step 契約）に専念する
- `FLW-DSN-014` — confirmation 表を **`write_target` 軸から導出**する形へ書き直す。
  「全 `worktree.*`」という力技の列挙を、`write_target: local` の機械的な帰結に置き換える

## 2. M2 出口の公開集合 — 破壊的 operation を含める

worktree-first の安全境界を M2 で閉じるという `FLW-DSN-014` 縮退規則3 の趣旨を満たすには、
`worktree.finish` / `discard` の公開が必要である。除外すると
**「作成できるが削除できない worktree」**（`SI-FLW-054`(5) が指摘する capability 縮退の非対称）
そのものになり、縮退規則3 の前提も崩れる。

ただし `worktree.discard` の recovery は現在 `manual-only` である。
**`SI-FLW-047` 案B（証跡軸）の帰結として、intent record と receipt から `completed_steps` が
一意に決まるため、`manual-only` → `reconcile-first` へ格上げできる見込みがある。**
M2-5 の設計時にこの格上げ可否を判定し、結果を `FLW-DSN-016` §8 recovery matrix に記録する。

- 格上げできた場合 — 通常公開する
- 格上げできない場合 — **`DEGRADED` として公開**し、何が自動復旧されないかを
  capability matrix で明示する（`SI-FLW-051` 案B の capability 縮退枠組みに乗せる）

縮退規則3 の解除条件は、`write_target: local` 軸から導出できる形へ書き直す。

## 3. branch tip OID の保全 — 保全 ref を作る

`worktree.discard` / `finish` はいずれも local branch を削除するが、削除前の tip OID を
保全する規定が無く、**未 push の commit が gc で恒久喪失する**。

確定する規定:

- 削除前に tip OID を証跡（intent record / receipt）へ記録する
- あわせて **common-dir 配下に保全用 ref を作る** — `refs/bitz-flow/deleted/<work-id>/<timestamp>`
- ref が存在する限り commit は gc の到達可能集合に入るため、**object 自体が残る**
  （OID の記録だけでは object が gc で消え、記録が復元に使えない）
- 保持期間を定め、期限を過ぎた保全 ref は掃除する

保持期間の具体値と、保全 ref の列挙・掃除を行う operation を catalog へ追加するかは
**`SI-FLW-054` へ送る**（(3) 診断のための read 経路、(7) 永続成果物の retention と同じ論点群）。

`git reflog` に委ねる案は採らない。worktree 削除で reflog も失われ得るうえ、
保持期間が利用者の Git 設定に依存し、v2 として保証できない。

## 4. SI-FLW-055 — catalog（実装）側へ寄せる

`FLW-DSN-012` を次のとおり修正する。出荷済み catalog・実装・テストには**一切触れない**。

| operation | 項目 | 現行（012） | 修正後 |
|---|---|---|---|
| `git.publish-branch` | `approval` | `external-write` | **`explicit-human`** |
| `git.publish-branch` | `retry` | `reconcile-first` | **`manual-only`** |
| `git.delete-remote-branch` | `retry` | `reconcile-first` | **`manual-only`** |

根拠は3点。実装とテスト（`tests/test_flow_m1_contract_rows.py`）が既にこの契約で出荷済みであること。
いずれも catalog 側が**安全側**（より強い承認・自動 reconcile の禁止）であり、
設計側へ寄せると出荷済みの安全境界を緩めることになること。
設計表2行の修正で済み、version bump も qualification 再実行も伴わないこと。

**再発防止**（`SI-FLW-052` の検査群へ含める）: 設計の公開 action catalog と
出荷済み `operation-catalog.md` を、`operation` / `class`（＝2軸からの導出値） /
`approval` / `retry` / `recovery` の5項目で機械照合する。
現在は **catalog ↔ 実装しか縛られておらず、設計 ↔ catalog が無検証**であるために
本乖離が沈黙していた。`SI-FLW-052` が指摘する「第4のコピーが三者照合の対象外」の実例である。

## 付随して確定した事項

### 付随1: `sync-main` は新設せず既存の `git.sync` を充てる

`decision-2026-08-13-si-flw-047-048.md` の `SI-FLW-048`(a) 案A は
「`sync-main` を独立した local-write operation として実行させる」ことを確定したが、
**既存の `git.sync` がそのまま該当する**ため新 operation は設けない。

| | `git.sync`（M1-4 公開済み） | finish 内の `sync-main` に必要なもの |
|---|---|---|
| class | `local-write`（＝local + reversible） | 同じ |
| approval / retry | `mutation` / `reconcile-first` | 同じ |
| postcondition | branch が expected upstream へ **ff 一致** | main を merged 済み remote へ ff |
| concurrency_key | **branch ref、index**、remote-tracking ref 集合 | main の local-ref と index |

`concurrency_key` まで一致する。新設すれば catalog・contract 表・capability matrix・fixture が
1件分ずつ増えるが、既存を充てれば増分はゼロである。

これにより `SI-FLW-049` が挙げていた「案A で新設する operation の class を決める」論点は消滅する。
また `decision-2026-08-13-si-flw-047-048.md` の「新設 operation の class は `SI-FLW-049` で決める」
という記述は**本裁定により不要になった**（同記録の「影響推定」で触れた operation catalog の
1件増加も発生しない）。

### 付随2: `REC-*` 識別子を `REC-WORKTREE-*` / `REC-REMOTE-DELETE` へ統一する

実測の結果、`FLW-DSN-016` の5識別子は**すべて同書にしか存在しない**。
`FLW-DSN-012` / `013` の系統は3文書で使われているため、少数側を寄せる。

| `FLW-DSN-016`（廃止） | 統一先 |
|---|---|
| `REC-WT-CREATE` | `REC-WORKTREE-CREATE` |
| `REC-WT-RESUME` | **`REC-WORKTREE-RESUME`（新設）** |
| `REC-WT-FINISH` | `REC-WORKTREE-FINISH` |
| `REC-WT-DISCARD` | `REC-WORKTREE-DISCARD` |
| `REC-RM-DELETE` | `REC-REMOTE-DELETE` |

`REC-RM-DELETE` は `SI-FLW-049` 本文が挙げていない**5件目の別名**であり、本裁定で併せて統一する。

`REC-WORKTREE-RESUME` の新設は事故の修復ではなく、`FLW-DSN-016.md:52` が
「`create` と `resume` は公開 operation 名を分ける（`FLW-REV-011` の P2 で未確定だった点を
ここで確定する）」と**意図的に決めた分離**に、`FLW-DSN-012`（現在は両者を
`REC-WORKTREE-CREATE` へ合併）を追随させるものである。`resume` の recovery 手順を定義する。
