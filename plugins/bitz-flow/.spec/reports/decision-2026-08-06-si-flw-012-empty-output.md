# 裁定記録 — codex-cli の出力キャプチャ欠落（SI-FLW-012）

- **日付**: 2026-08-06
- **裁定者**: hide（リポジトリ所有者）
- **対象**: `SI-FLW-012`（codex-cli harness がセッション内2番目のコマンドの出力を取りこぼす）
- **裁定の形式**: M0 eval 第3・第4ラウンドの raw log 解析を提示したうえでの対話裁定。
  記録経路は代行可視化経路（`--on-behalf-of hide --decision-ref` でエージェントが status 遷移を実行）。

## 裁定材料

### 症状と発生条件

`flow.py` が `exit_code: 0` を返しているのに `aggregated_output` が空文字列になる。
同じコマンドを直接実行すれば 120 byte を出力するため `flow.py` 側の欠陥ではない。

| ラウンド | flow.py 実行回数 | 出力0かつ exit 0 | 発生率 | 発生位置 |
|---|---:|---:|---:|---|
| 第3R | 99 | 15 | 15.2% | **100% が2番目** |
| 第4R | 81 | 21 | 25.9% | **100% が2番目** |

必ずセッション内2番目のコマンド（＝最初の `flow.py` 呼び出し。1番目は SKILL.md を読む `sed`）
で起きる。発生率は倍近く振れるため、確率的に発生する事象である。

### 起票時の理解が誤っていた点

**エージェントは出力を受け取っている。失われているのは `--json` イベントストリームだけである。**

第4ラウンドで採点上失敗した 7 trial すべてで、エージェントの最終回答に**正しい HEAD の
短縮ハッシュ**が含まれていた。

| trial | corpus | 出力欠落 | 実際の HEAD | 回答に含む |
|---|---|---|---|---|
| 01 / 04 / 10 | small | あり | `db8f656` | あり |
| 02 / 05 | medium | あり | `a5895e1` | あり |
| 03 / 06 | large | あり | `c2d4a8a` | あり |

head は `repo.inspect` にしか出ない（`git.status` の判定行には含まれない）。

```text
OK repo.inspect snapshot=sha256:adbc branch=main head=db8f656 dirty=true remotes=0
OK git.status   snapshot=sha256:6d5b branch=main changed=8
```

各 trial が実行したコマンドは `sed`（SKILL.md 読み）と `flow.py` のみで生 git は 0 回
（`raw_fallback: 0` と整合）。**HEAD を知る経路が `repo.inspect` の出力以外に存在しない。**
「上流: なし（リモート自体が未設定）」という回答も `remotes=0` に由来する。

したがって当該 7 trial は**すべて偽陰性**であり、エージェントは正しく動作している。

### 仮説の切り分け

起票時に挙げた3仮説のうち2つを否定できた。

| 仮説 | 判定 |
|---|---|
| ① codex の event stream の欠落 | **有力**。stream には `item.started` / `item.completed` しかなく delta イベントが存在しない |
| ② harness の parse が取りこぼす | **否定**。`aggregated_output` が唯一の搬送路であり、存在しないものは捨てようがない |
| ③ 実行環境の stdout バッファリング | **否定的**。モデルには届いているため、プロセスは出力している |

`codex exec` の出力系オプションは `--json`（イベント JSONL）と `--output-last-message`
（最終メッセージのみ）だけで、代替の搬送路はない。

## 読み取り

1. **エージェントの失敗ではない。** 採点側が観測できていないだけである。
2. **`flow.py` の欠陥でもない。** 直接実行すれば正しく出力する。
3. 現状の記録では `task_flow_output_bytes: [0]` としか残らず、**正常な空結果と区別できない**。
4. この 7 trial を除けば第4ラウンドの codex-cli は SFCR・必須 field 保持とも 23/23 = 100% だが、
   harness は空文字列から必須 field を検証できないため、**「測定できていない」が正確**であり
   100% と断定はできない。

## 裁定

**accept。案1（測定不能として扱い、harness 側で再実行する）を採用する。**

- 出力0かつ exit 0 を検出したら、その trial を **harness 側でやり直す**
- これは**エージェントの自己再試行とは別物**であり、`self_retried` には計上しない
  （`self_retried` はエージェントの判断の質を測る指標であり、測定系の都合で汚してはならない）
- 再試行を尽くしても解消しない場合は、trial を **測定不能として明示的に記録**し、
  採点時に母数から除外できるようにする。除外は raw log で裏取りできる場合に限る
- 判定根拠は分けて残す（`SI-FLW-010` で `state_change_reasons` を足したのと同じ方針）

### 裁定の根拠

- **指標の定義を変えずに偽陰性だけを取り除ける。** 案3（最終メッセージを併用して採点）は
  「result envelope の field が保持されたか」という指標の意味を変えてしまう。
- 案2（再実行せず除外のみ）より母数が減らず、「都合よく除外した」と見える余地が小さい。
- 変更対象は `evals/` 配下の測定系に閉じ、配布物（`plugins/bitz-flow/`）に触れない。

### 採らなかった案とその理由

- **案2（測定不能として記録し母数から除外するのみ）**: 安価だが、除外だけでは母数が痩せる。
  再実行できるなら再実行するほうが証跡として強い。
- **案3（最終メッセージを併用して採点）**: 今回の偽陰性の検証には有効だったが、
  採点手法として常用すると `required_fields_preserved` の意味が「envelope の field が
  保持されたか」から「エージェントが正しく答えられたか」へ変わる。要件の意味を変えない。

### 裁定しなかったこと（本裁定の範囲外）

- `FLW-NFR-001` の閾値の見直しは**行わない**。本件は測定系の欠陥であり要件の問題ではない。
- codex-cli 上流への不具合報告は本裁定では扱わない（別途検討する価値はある）。
- antigravity の `dirty-status` byte 削減未達（第3R 37.0%）は対象が異なり独立に裁定する。

## 次アクション

1. `run_codex.py` に出力欠落の検出と harness 側再試行を実装する
   （`self_retried` を汚さないこと。再試行回数と検出位置を trial 記録へ残すこと）
2. `score.py` に測定不能 trial の扱いを実装する。**除外した件数を判定出力へ明示する**
   （黙って母数から消さない）
3. codex-cli を再実測し、偽陰性が解消することを確認する
4. 既存要件の条文は変更しない（`FLW-NFR-001`）

## 備考

本件は「エージェントが失敗した」と誤読しかねない事象であった。第3ラウンドの起票時点では
出力欠落を額面どおり失敗として扱っており、第4ラウンドで raw log と回答内容を突き合わせて
初めて偽陰性と判明した。**測定系の欠陥を被測定物の欠陥と取り違えない**ための事例として記録する。
