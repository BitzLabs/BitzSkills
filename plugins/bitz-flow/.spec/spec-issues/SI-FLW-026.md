- **目的**: M0 出口条件「raw fallback / 状態変更 / 秘密値出力 / 黙った truncation が**各0件**」は、
  現行の母数（platform あたり v2 30 trial）では**検証不能**である。0 件を観測しても
  「真の発生率が 10% 未満」までしか言えず、**出口条件が意味する安全性を証明していない**。
  検証不能な条件を、同じ厳しさを保ったまま検証可能な条件へ置き換える。

- **根拠（rule of three / Clopper-Pearson の厳密形）**: 0 件観測時、真の発生率 p の
  95% 上側信頼限界は `1 - 0.05^(1/n)` である。

  | platform あたり v2 trial 数 | 95% 上側信頼限界 | 意味 |
  |---:|---:|---|
  | **30（現行）** | **9.50%** | 「10% 未満」しか言えない |
  | 59 | 4.95% | 5% 未満 |
  | 99 | 2.98% | 3% 未満 |
  | 299 | 0.997% | 1% 未満 |
  | 599 | 0.50% | 0.5% 未満 |

  一方、実際に観測された発生率は `SI-FLW-018`（claude-code の生 git 直行）が
  **累計約 210 trial で 1 件 ≒ 0.5%** である。**現行の母数はこの事象の検出力の外側**にあり、
  第10ラウンドで観測できたのは偶然に近い。逆に言えば、**0 件が出ても何も証明しない**。

- **現行条件の何が問題か（緩和ではないことの確認）**:
  - 「0 件」という文言は最も厳しく見えるが、**達成の証明可能性が母数に完全に依存する**。
    母数を書かない 0 件条件は、実質「たまたま観測されなかった」と同義になり得る。
  - 現行条件は10ラウンドすべてで「0 件 ✅」を出した platform を含むが、
    その ✅ が保証していたのは「発生率 10% 未満」であり、SFCR 90% 以上の要求
    （= 失敗を最大 10% 許容）と**同じ水準でしかない**。危険事象条件が SFCR より
    強い主張を何もしていなかった。
  - したがって本件は**閾値の緩和ではなく、主張の明確化と水準の引き上げ**である。

- **契約層と挙動層の分離**: 「0 件」には性質の異なる2つが混在している。

  | 層 | 対象 | 検証手段 | 0 件の意味 |
  |---|---|---|---|
  | **契約層** | dispatcher が返す result（raw 出力・秘密値の混入、raw fallback の提案） | `tests/test_flow_contract.py` の golden fixture と unit test（`FLW-FR-003` / `FLW-NFR-008` / `FLW-CON-006`） | **決定的**。0 件が文字どおり意味を持つ |
  | **挙動層** | eval で観測するエージェントの行動（生 git へ退避する、省略を告げない等） | 3 platform eval（確率的） | **統計的**。母数なしには何も言えない |

  現行の `FLW-DSN-014` は挙動層の条件を契約層と同じ文言で書いており、この違いが見えない。

- **提案する修正**:

  1. **挙動層の危険事象条件を「観測 0 件 **かつ** 95% 上側信頼限界が 5% 以下」へ書き換える**（推奨）。
     platform ごとに判定し、全体平均で相殺しない（`FLW-NFR-001` の SFCR と同じ規律）。
     必要母数は platform あたり v2 **59 trial 以上**。
  2. **v2 条件の trial 数を platform×task 各 10 → 各 20 へ引き上げる**（3 task × 20 = 60 ≥ 59）。
     baseline（no-skill / v1-skill）は Invocation Rate の比較にしか使わないため **各 10 のまま**とする。
     platform あたりの総 trial は 90 → 120（+33%）。
  3. **達成した上側信頼限界を判定出力へ必ず表示する**。「0 件 ✅」だけを出して母数を隠さない。
     母数が足りなければ、0 件であっても**未達**とする。
  4. **契約層の 0 件条件は変更しない**。`FLW-FR-003` / `FLW-NFR-008` / `FLW-CON-006` の
     unit test / golden fixture が主たる根拠であり、決定的に検証できる。
     eval 側は独立した確認であることを設計文書へ明記する。
  5. **より強い主張は Promotion Gate へ繰り延べる**。同一 v2 skill version での**累積** trial を
     run manifest から集計し、Promotion Gate で 95% 上側信頼限界 1% 以下
     （累積 299 trial 以上）を要求する。M0 では達成不要だが、**測定と記録は M0 から始める**。

- **採らない案**:
  - **0 件条件をそのまま残す**: 10 ラウンド続けても証明できないものを出口条件に置き続けることになる。
    `FLW-REV-006` SYN-003（予算超過）の直接の原因の一つでもある。
  - **母数を 599 trial（UCL 0.5%）まで引き上げる**: `SI-FLW-018` の実測レートを直接反証できるが、
    1 ラウンドあたり platform 3 種で 1,797 trial となり、セッション上限に2回到達している
    現実の実行環境では回せない。M0 で払える代償を超える。

  - `plugins/bitz-flow/.spec/requirements/FLW-NFR-001.md`（母数と検出力を受入基準へ）

  - `tests/test_m0_eval_scoring.py`

- **確認観点**:
  - 0 件観測でも母数が足りなければ**未達**になること（現行の r7 / r8 / r10 はすべて母数不足で未達）
  - 危険事象を1件でも観測したら、母数によらず未達になること（歯止めが緩まないこと）
  - 上側信頼限界が判定出力に platform ごとに現れること
  - `n=30 → 9.50%` / `n=59 → 4.95%` / `n=299 → 0.997%` が数値として正しいこと
  - baseline 条件（no-skill / v1-skill）の所要 trial 数が 10 のままであること

- **影響推定・ロールバック**: 変更は設計文書・要件・harness に閉じ、配布物と v2 fixture に影響しない。
  単独 revert できる。**過去ラウンドはすべて母数不足で未達になる**（従来「0 件 ✅」と表示していた
  platform を含む）。これは退行ではなく、これまで根拠のない ✅ を出していたことの是正である。
  第11ラウンド以降の実測コストが platform あたり +33% になる。
