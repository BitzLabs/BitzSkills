- **目的**: M0 eval 期の spec-issue 13 件（`SI-FLW-006`〜`SI-FLW-018`）のうち **6 件が
  測定系の欠陥**であり、うち 2 件（`SI-FLW-014` / `SI-FLW-017`）は**同一関数
  `_task_output` から出ている**。個別に潰しても同じ場所から再発しているため、
  個々の bug ではなく `FLW-DSN-014` の設計不足として扱う。

  | 種別 | 件数 | ID |
  |---|---:|---|
  | **測定系（harness・採点規則）** | **6** | 007, 009, 010, 012, 014, 017 |
  | 被測定物（dispatcher の契約） | 3 | 006, 011, 015 |
  | 被測定物（SKILL.md の誘導） | 4 | 008, 013, 016, 018 |

- **原因1: 測定量の定義が仕様に無く、実装が事実上の仕様になっている**。
  `FLW-DSN-014` が定めたのは閾値だけで、次を定めていない。

  - その trial の「答え」はどの呼出の出力か
  - エージェントが複数回呼んだときどれを採点するか
  - 失敗呼出・ヘルプ呼出・探索呼出をどう扱うか

  空白を埋めたのは `_task_output` の `selected = (complete or matches)[-1]` という
  1 行のヒューリスティックである。`SI-FLW-014` の裁定でも**この選択規則自体は見直さず
  `--help` フィルタを 1 つ足しただけ**であったため、`SI-FLW-017` が同じ場所から出た。

- **原因2: proxy が measurand から乖離する条件を洗い出していない**。
  測定系 6 件はすべて同じ形へ還元できる。

  | ID | 測りたかったもの | 実際の代理指標 | 乖離条件 |
  |---|---|---|---|
  | 007 | renderer の圧縮効果 | 未定義 corpus の byte | corpus の選び方で反転 |
  | 009 | 同上 | no-skill が消費した byte | 分母がエージェント任せで 5.9〜75.0% |
  | 010 | この trial が状態を変えたか | repo の前後 diff | corpus 共有で他 trial の副作用を拾う |
  | 012 | エージェントの挙動 | キャプチャできた出力 | 出力欠落を挙動の失敗と誤認 |
  | 014 | operation の実行結果 | task に一致した最後の呼出 | `--help` が一致する |
  | 017 | 同上 | 同上 | 失敗呼出が最後に来る |

  「この代理が measurand から外れるのはどんなときか」を各メトリクスへ 1 行書いていれば、
  `SI-FLW-014` の時点で `SI-FLW-017` は同時に見えていた。

- **原因3: 「良い数値」が測定系の欠陥を隠す**。測定系 6 件はすべて
  **数値が悪化して初めて発見された**。設計レビューで見つかったものは 1 件も無い。

  第10ラウンドが典型である。`--base HEAD~1` を試す挙動は agy の v2 `diff-summary`
  10 trial 中 **8 trial** にあり、第8ラウンドでも `task_flow_output_bytes` に
  64B として**記録されていた**。r8 は偶然すべて成功呼出より前に来たため 100% となり、
  誰も `matches[-1]` を疑わなかった。**記録はされていたが監視されていなかった。**

  すなわち現行設計では**合格が測定系の健全性の証明になっていない**。r8 の agy 100% は
  「測定系が壊れていない証拠」ではなく「壊れ方が偶然表に出なかった状態」であった。

- **原因4: 0 件条件に対して母数が 2 桁足りない**。「危険事象 各 0 件」を
  30 trial で確認しても統計的にほとんど何も言えない。

  | 真の発生率 | 30 trial で 0 件になる確率 | 95% で検出するのに必要な n |
  |---:|---:|---:|
  | 5% | 21.5% | 59 |
  | 3% | **40.1%** | 99 |
  | 1% | 74.0% | 299 |

  rule of three により **0/30 が保証するのは「真の発生率 10% 未満」まで**である
  （0/90 で 3.3%、claude 累計 210 trial でも 1.4%）。`SI-FLW-018` の生 git 直行は
  まさにこの領域（累計 210 trial で 1 件）にあり、**現在の母数設計では
  「0 件」は検証不能な条件を書いてしまっている**。

- **原因5: 3 つの失敗要因が 1 つのフラグに畳み込まれている**。
  `required_fields_preserved` の単一 bool に次が同居する。

  1. dispatcher が必須 field を落とした（**被測定物の欠陥**）
  2. エージェントが外れ ref を渡して失敗結果を受けた（**エージェントの挙動**）
  3. harness が採点対象を取り違えた（**測定系の欠陥**）

  切り分けに毎回 raw log を読む必要があり、`SI-FLW-012` / `014` / `017` の調査コストは
  すべてここから来ている。`measurable`（`SI-FLW-012` で導入）で 3 の一部は分離できたが、
  1 と 2 は未分離のままである。

- **提案する修正**: `FLW-DSN-014` へ次を追加する。1〜3 を必須、4〜6 は個別に裁定する。

  1. **採点規則を実装から設計文書へ昇格する**（必須）。measurand の定義節を置き、
     「何を答えとするか」「除外規則」「除外の歯止め」を仕様側で定める。
     実装（`_task_output` 等）はそれを参照する。現状は逆向きである
  2. **メトリクスごとに proxy の乖離条件を明記する**（必須）。
     乖離条件を書けない proxy は採用しない
  3. **harness の自己診断を出口条件に入れる**（必須）。次を計測し、
     **被測定物の数値が良くても閾値超過なら FAIL とする**。
     - 採点候補が 2 件以上あった trial の割合
     - **採点対象が非 OK result だった件数（0 であるべき）**
     - 除外した呼出の件数と内訳

     第10ラウンドの agy はこの 1 項目だけで即座に検出できた
  4. **0 件条件の母数を計算して母数設計へ反映する**。必要 n を確保するか、
     確保できないなら条件を「0 件」から**「95% 上側信頼限界が x% 未満」**へ書き換える。
     数値を通すための緩和ではなく、**検証不能な条件を検証可能な条件へ置き換える**趣旨である
  5. **メトリクスを 3 軸へ分解する**（dispatcher 欠陥 / エージェント挙動 / 測定不能）
  6. **再現性を出口条件にする**。同一 fixture で 2 ラウンド測り判定が一致すること。
     `SI-FLW-017` のような順序依存の反転はこれだけで検出できた

  - `evals/flow-core/m0-eval/run_codex.py`（`common`。3 runner が共用する採点関数）

- **確認観点**:
  - 過去ラウンドの trial JSONL を**再実測せずに**新しい自己診断で採点し、
    `SI-FLW-014` / `SI-FLW-017` が**発見されるより前のラウンドで検出できる**こと
    （後知恵ではなく事前検出になっているかの検証）
  - 自己診断の閾値超過が、被測定物のメトリクスに関わらず FAIL を出すこと
  - 母数条件の変更が「数値を通すための緩和」になっていないこと。
    `SI-FLW-012` の裁定で定めた「都合のよい操作をしない」方針との整合を裁定記録へ残す
  - 3 platform の既達水準を落とさないこと

- **影響推定・ロールバック**: 設計文書と harness の採点系に及ぶ。配布物
  （`plugins/bitz-flow/skills/`）と v2 fixture には影響しない。
  既存 trial JSONL は再採点で結果が変わるため、**どのラウンドをどの規則で採点したか**を
  README に明記する。案 4 は M0 の合否基準そのものを動かすため影響が大きく、
  単独 revert では過去の判定を復元できない点に注意する。
