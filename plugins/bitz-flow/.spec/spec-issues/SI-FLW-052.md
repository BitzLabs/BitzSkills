- **目的**: **文書間に散在する定数と「対応済み」という自己申告を、機械検証で塞ぐ。**
  そのうえで、**この検証の構築を文書修正より先に完了させる**という順序制約を確立する。

  `FLW-REV-013` の67件の指摘のうち、およそ3分の1は「宣言と実体の乖離」に分類される。
  個別に直しても、次の改訂で同じ形の乖離が再発する。

- **確認済みの欠陥**（`FLW-REV-013:SYN-012` 〜 `SYN-016`・`SYN-026`・`SYN-040` 〜 `SYN-047`。
  2026-08-13 に grep で機械確認）:

  | 乖離 | 実測 |
  |---|---|
  | `M2-FLT` の範囲 | `FLW-DSN-016.md:651` は **049**、`ROADMAP.md:158` と `FLW-DSN-014.md:649` は **044** |
  | quarantine 解除区分数 | 本文「3区分」/ 表 **4行** / §15「4区分」/ fixture「3区分」 |
  | M2 出口条件の「正」 | 3文書が**相互に別の文書を指している**（循環参照で解決不能） |
  | recovery 識別子 | `REC-WT-*`（`FLW-DSN-016`）と `REC-WORKTREE-*`（`FLW-DSN-012` / `013`）の2系統。`REC-WT-RESUME` は**未定義** |
  | 状態語の表記 | `FLW-FR-007.md:21` は小文字 `active` / `merged-exact`。設計 §2 は大文字閉集合 |
  | `guard_identity_kind` | 5値の閉集合が `output-contract.md` にも存在するが**三者照合の対象外**（第4のコピー） |

  **とくに重い2件**:

  1. **§15 の GP 対応表に事実と異なる記述がある**（`SYN-013`）。
     `GP-018` への回答は「実ファイル更新済み」と主張するが、`FLW-DSN-006` / `FLW-DSN-012` は
     **version だけ上がって状態語が未変換**である。
  2. **裁定記録が存在しないのに「人間へ再提示して確定した」と書かれている**（`SYN-016`）。
     `FLW-DSN-014` の budget 節の記述に対応する `.spec/reports/decision-*.md` が無い。
     SDD の証跡規律そのものへの違反である。

- **根本原因**: 「対応した」という宣言を**検証せずに受け入れる工程**が存在する。
  `FLW-REV-012`（自己レビュー 3.62）と `FLW-REV-013`（独立 2.31）の差 **+1.31** は、
  この工程が機能していないことの実測値である。

- **提案する修正**:

  1. **定数の SSOT 化と三者照合**（本リポジトリの既存手法を適用する）

     `release_check.py` は既に「実装側定数を SSOT とし、HTML コメントマーカーで
     文書側の可読表と照合する」機構を持つ（対訳辞書・フェーズ語彙・同期マッピングで実績あり）。
     同じ機構を次へ適用する:

     - `M2-FLT` の範囲（fixture catalog を SSOT とし、`ROADMAP.md` / `FLW-DSN-014` を照合）
     - quarantine 解除区分（区分表を SSOT とし、本文・§15・fixture を照合）
     - `REC-*` 識別子（**定義の実在**と**参照の解決**を双方向で検査）
     - enum 値（**要件層を三者照合の対象へ含める**。現在は設計・schema・実装のみで、
       要件層の乖離は恒久的に沈黙する）

  2. **step → mutation target の全射性検査**（`SI-FLW-048` の帰結を機械化）

  3. **中断状態の網羅性検査**（`SI-FLW-047` の帰結を決定表として機械化）。
     `SYN-003` はこの検査があれば自動検出できた

  4. **「正」の一意性検査**。同一事項について「正はこの文書」と宣言している箇所が
     複数あり相互に指し合う場合を検出する

  5. **順序制約の確立**: 上記検査を **`SI-FLW-047`〜`051` の裁定後・文書修正前**に構築する。
     検証が先にあれば、修正は「構成上正しい」状態で完了できる。
     修正してから検証を作ると、`FLW-REV-012` と同じ「直したと自己申告する」工程を反復する

- **対象ファイル**:
  - `scripts/release_check.py`（照合チェックの追加）
  - `tests/`（新規テスト）
  - `plugins/bitz-flow/.spec/design/FLW-DSN-016.md`・`FLW-DSN-014.md`・`ROADMAP.md`・
    `plugins/bitz-flow/.spec/requirements/FLW-FR-007.md`（マーカー付与と値の統一）

- **確認観点**:
  - 検査が**現在の乖離を実際に検出する**こと（修正前に走らせて FAIL することを確認する）
  - 検査が新規の設計文書・fixture を**登録なしで対象に含める**こと
    （`tests/test_skill_script_reference.py` の動的収集と同じ方式）
  - 要件層の enum 表記が照合対象に入ること

- **影響推定・ロールバック**: `release_check.py` と `tests/` への追加であり、
  `scripts/` の共有スクリプトを変更するため**全 pytest スイートの実行が必要**。
  検査追加は加算的で、既存の PASS を壊さない範囲で入れる。

- **依存**: `SI-FLW-047`〜`051` の裁定結果を検査対象の定義に使うため、**裁定後に着手する**。
  ただし本 issue の (1) 定数 SSOT 化と (4) 「正」の一意性検査は裁定に依存しないため先行できる。
  bitz-sdd の `SI-SDD-042`（レビュー指摘の受領検証）と同型の問題であり、
  そちらの裁定結果と整合させる。
