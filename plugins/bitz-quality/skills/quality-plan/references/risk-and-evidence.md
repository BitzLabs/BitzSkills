# リスクと証拠の対応

| 観点 | 失敗を考える入口 | 証拠の候補 |
|---|---|---|
| 機能・要求 | 規範文、曖昧さ、異常系、境界値 | 要求への追跡、例示・境界・負例の試験 |
| データ | 移行、削除、不可逆、個人情報 | 移行前後の不変条件、復元、バックアップ |
| セキュリティ | 認証、認可、秘密、未信頼入力、コマンド | 脅威分析、攻撃と拒否の負例、依存監査、専門レビュー |
| 互換性 | API、形式、設定、CLI、スキーマ | 契約試験、旧版入力、移行、ロールバック |
| 信頼性 | 並行、再試行、障害、外部サービス | 冪等性、障害注入、タイムアウト、縮退 |
| 性能 | SLO、上限、メモリ、待ち時間 | 基準環境と反復測定、上限前後 |
| 供給網 | 依存、CI権限、ビルド、配布 | 固定版、来歴、トークン権限、個別Scorecard検査 |
| 運用 | 観測、復旧、通知、費用 | 監視、復旧手順、費用上限、運用試験 |

候補は自動的な必須一覧ではない。変更への適用理由と未確認事項を先に残し、重大な失敗を相殺しない。
セキュリティの重大事項を、回帰テスト通過や読みやすさの改善で打ち消さない。

plannedの証拠は、担当、対象の要求/観点、何を検査するか、許可された実行条件、取得先を指定する。
保存先やargvが未確定ならnullと未決事項を残す。予定のコマンドを実行済みのchecksへ入れない。
既存テストのパスやassertが不明なら調べるか不足とし、存在するように登録しない。
必要な証拠のhashは、実際に取得してから後続のhandoffへ付ける。

handoffのrisk.dimensionsは既存契約の列挙値を使う。計画の機能/データの観点を、似た名前の別観点へ機械変換しない。
該当するhandoff観点だけを記録し、詳細な全8観点は品質計画とrequiredEvidenceで保持して一緒に渡す。
計画と確定した変更のhandoffは異なる文書であり、計画へ架空のsubjectCommitや証拠hashを埋めない。


## 既知の下限と未確定の全体分類

観点の根拠から最低帯が分かった場合は、その観点へ保持する。他の観点が不明でも、既知の下限から必要な証拠・独立検分を計画する。
例えば、変更範囲の一次資料からセキュリティ観点の最低帯がQ3と分かったが、データや互換性の影響が未確認なら、
`risk.areas.security.minimumBand`はQ3、未確認の観点と全体の`risk.band`はnull、`planningStatus`はneeds_informationとする。
Q3の専門観点・人手承認・必要な攻撃/復旧の証拠を計画し、独立レビューを予定し、完全フローまたは隔離スパイクの条件を示す。
これは未検査の案であり、実装へ渡す許可やリスク全体の確定ではない。担当や条件が未確定なら不足と停止条件を残す。

単にセキュリティが話題に出た場合や候補を挙げただけの場合は、この例を根拠にQ3を確定しない。
全観点が未知なら最低帯も全体もnullとし、質問と再開条件を返す。形式検査は、申告された最低帯と計画の整合性だけを検査する。
