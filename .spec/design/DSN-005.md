# DSN-005 docs/ 構造と sdd-docs docs_inspect の適用境界設計

- **背景 / 課題**:
  ルート `docs/` は使い方ガイド、過去計画、3プラットフォーム調査（`調査報告/`）、外部資料保全を含む大規模資料庫として運用されている。
  一方で `sdd-docs` の `docs_inspect.py` は `docs/` 配下の全 Markdown ファイルを SDD ナラティブ層（frontmatter 必須・`MASTER.md` 登録必須）とみなすため、正規検査実行時に合計 1,557 件のエラー（`FM_ABSENT` / `REG_ORPHAN` 等）が発生し、本来の文書健全性を判定できない。

- **設計判断案（Design Gate 検討項目）**:
  1. **適用境界の定義**:
     - `docs/` 内の SDD ナラティブ管理対象（例: `00_はじめに/` 〜 `05_リリース・運用/` または `01-context/` 等、`MASTER.md`）と、資料保全・調査報告（例: `調査報告/` 等）を明確に区分する。
  2. **除外パターンの宣言方式**:
     - 暗黙的なスクリプト側ハードコードを避け、リポジトリ側で監査可能な形式（例: `docs/MASTER.md` 内の `ignore:` フィールド宣言、または `.docsignore` / `.spec/config`）で検査除外パターンを定義する。
  3. **`docs_inspect.py` の改修**:
     - 除外パターンに一致するパスをスキャン対象から除外し、管理対象文書のエラー（frontmatter 欠損や無効な参照）のみを正確に集計・検出する。
  4. **既存資料の保護**:
     - 調査報告や既存の資料ファイルを一括削除・大量改変せず、除外指定により安全に現状を維持する。

- **確認観点 / リスク**:
  - `docs_inspect.py . --strict` の PASS 条件が管理対象文書のみに限定され、無関係なエラーが出ないこと。
  - 除外設定の変更が明確でコミット履歴追跡可能であること。
  - `release_check.py` および全ワークスペースの `spec inspect` が green を維持すること。

- **影響範囲・ロールバック**:
  - `plugins/bitz-sdd/skills/sdd-docs/scripts/docs_inspect.py`
  - `docs/` 構造および設定ファイル
  - `tests/test_docs_inspect.py`（回帰テスト追加）
  - 問題発生時は設定ファイル追加と `docs_inspect.py` の差分を revert することで元に戻せる。
