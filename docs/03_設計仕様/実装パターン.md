# 実装パターン

## 採用パターン

- **定型手順はスクリプトに委ねる** — 使う状況: version bump・リリース前検証・SDD ツール実行。
  理由: 手作業では3マニフェスト同値やレジストリ整合を確実に保てないため。
  `python3 scripts/bump_version.py <plugin名> [major|minor|patch]` /
  `python3 scripts/release_check.py` / `scripts/spec {inspect|scaffold|status|update}` を使う。
  反例: 1ファイルの軽微な frontmatter 修正等、スクリプト実行の往復コストが手作業を上回る場合は
  直接編集してよい。
- **スキルの自己完結** — 使う状況: 全スキル作成・変更時。理由: フォルダ単位でコピー・配置される
  ため、他スキルへの相対参照は配置後に壊れる。反例: 無し（例外を認めない規約。CORE-CON-004）。
- **委譲の相対選択** — 使う状況: 司令塔（起動モデル）が機械的作業・難調査タスクに直面したとき。
  下位ティアへの委譲・上位ティアへの相談をティアはしご上の相対位置で判定する（CLAUDE.md 委譲
  レジストリ、`.spec/design/DSN-001-delegation-registry.md` が正）。反例: 1ファイルの軽微な編集
  など、委譲の往復コストが節約分を上回る小さな単発タスク（CORE-CON-007 の損益分岐）。
- **宣言的マイグレーション（guard 必須）** — 使う状況: `<plugin名>:update` が配置先の状態形式を
  変更するとき。理由: 実行コードではなく Markdown 命令文であるため冪等性が自然に保証されず、
  guard 条件の明記を必須とする（CORE-CON-009、DSN-002）。反例: 形式変更を伴わないプラグインは
  移行機構自体を実装しない。

## 命名・構造の規約

- プラグイン内のスキル名は単一プレフィックスで統一する（`skill-*` / `sdd-*` / `ddd-*` /
  `plugin-*` / `env-*` / `flow-*`。CORE-CON-005）。
- 新規プラグインは `plugins/<name>/` に3マニフェスト（`.claude-plugin/plugin.json` /
  `plugin.json` / `.codex-plugin/plugin.json`）を必ず揃え、`marketplace.json` の `plugins[]` に
  `"source": "./plugins/<name>"` で登録する（AGENTS.md 新規プラグイン追加手順）。
- `.spec` / `docs` の frontmatter は各層のキー体系（`.spec` は id/status/version 系、`docs` は
  id/title/status/version/changeImpact/project_type/updated/owner/superseded_by）に一貫させる
  （glossary 相当は sdd-core の frontmatter 契約が正）。

## エラー処理方針

- **境界での扱い**: `scripts/*.py` は検証失敗を非ゼロ終了コード + 標準出力への `[FAIL]` 行で
  報告する（例外を握り潰さず `release_check.py` の `check()` ヘルパーに集約する）。
  委譲先エージェント・フックも同様に「失敗を握り潰さず提示する」を徹底する（CORE-CON-009 の
  安全側停止方針と整合）。
- **安全側停止**: `<plugin名>:update` のマイグレーション連鎖が途中で欠落・断裂した場合、
  書き込みを行わず停止して状況を提示する（破壊的な部分適用を避ける）。

## 依存方針

- 依存追加の基準: プラグイン間の依存は `metadata.dependencies` に semver 制約付きで宣言し、
  `release_check.py` が実在・制約充足・循環の不在を検査する（CORE-FR-013）。外部パッケージへの
  依存は現時点で導入していない（`scripts/*.py` は標準ライブラリのみで完結する方針）。
- 禁止・要注意の依存: プラグイン間の循環依存は禁止。スキル間の相対パス参照も禁止（自己完結原則
  の一部として扱う）。

## テスト成果物・観察ログの置き場所

- スキルのテスト成果物は `evals/<skill-name>/` に置く（書式は skill-tester の
  `references/test-design.md`）。
- 観察ログは `evals/observations/observations.jsonl` に1行1 JSON（JSONL）で追記のみ行う（書式は
  skill-observer の `references/observation-schema.md`）。

## コミット・PR 規約

- コミットタイトル・PR タイトルは Conventional Commits に従う（`<type>(<scope>): <説明>`、
  破壊的変更は `!` を付ける。CORE-CON-006）。
- PR は squash merge とし、マージコミットのタイトル = PR タイトル。
- 1 PR = 1 関心事とし `git revert` で丸ごと戻せる粒度を保つ。version bump は同一 PR に含める
  （コミット位置は問わない。CORE-CON-010）。
