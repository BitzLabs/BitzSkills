# アーキテクチャ

## 全体像

BitzSkills はモノレポであり、リポジトリルート自体が Claude Code / Codex CLI 共有の
マーケットプレイス `bitzskills`（`.claude-plugin/marketplace.json`）である。`plugins/` 配下の
各フォルダが1プラグインで、それぞれが Claude Code / Antigravity 2.0 / Codex CLI の3プラットフォーム
向けに配布される。プラグインはスキル（`skills/<name>/SKILL.md`）の集合として実装を持ち、
実行時の成果物は `.spec/`（仕様・設計の SSOT）・`docs/`（人間ナラティブ層）・`evals/`（テスト・観察ログ）
に書き出される。

```
marketplace bitzskills (.claude-plugin/marketplace.json)
        │
        ├─ plugins/bitz-sdd     ── EARS要件・設計・実装・検証の運用ワークフロー
        ├─ plugins/bitz-ddd     ── DDD設計手法（bitz-sdd に依存し .spec/design/ へ書く）
        ├─ plugins/bitz-flow    ── Git/GitHub フロー（単独でも使える）
        ├─ plugins/bitz-env     ── ガードレール・協調運用の展開
        ├─ plugins/skill-creator── スキル開発ライフサイクル（作成〜自己改善）
        └─ plugins/plugin-creator── プラグイン開発支援
                │
                ▼ 実行時に書き込み
        .spec/ (SSOT)  ⇄  docs/ (ナラティブ)      evals/ (テスト・観察)
```

## モジュール境界（配布単位のマッピング）

このリポジトリに C#/TypeScript/Rust のようなコンパイル単位は無い。配布単位は
「プラグイン」と「スキル」であり、公開面は3マニフェストとスキル frontmatter で表現される。

| 論理境界 | 実体 |
|---|---|
| 配布単位 | `plugins/<name>/`（3マニフェスト + `skills/`） |
| 公開面の単位 | プラグイン名・スキル名・SKILL.md frontmatter（`公開API.md` が正） |
| 内部境界 | スキルの `scripts/` `references/` `assets/`（他スキルから相対参照されない） |
| 機能分割 | プラグイン内の複数スキル。プラグイン自体は用途別に分割済み（併用は `metadata.dependencies` で宣言） |

- **プラグイン境界**: 1プラグイン = 1関心事（SDD 運用 / DDD 手法 / Git フロー / 環境展開 /
  スキル開発 / プラグイン開発）。プラグイン間の直接的なコード共有は無く、成果物（`.spec/` の
  frontmatter 契約）と併用宣言（`metadata.dependencies`）でのみ結合する。
- **スキル境界**: 自己完結が原則（CORE-CON-004）。フォルダ単位でコピー・配置されるため、
  他スキルの `references/` を相対パスで参照せず、連携はスキル名の言及にとどめる。

## レイヤと依存方向

プラグイン間の依存は宣言的かつ一方向。循環は禁止（`release_check.py` が
`metadata.dependencies` グラフの循環を検査する）。

```
bitz-ddd ──▶ bitz-sdd ──▶ .spec/（成果物 SSOT）
bitz-sdd ──▶ bitz-flow（Git/GitHub フロー）
skill-creator / plugin-creator は他プラグインに依存しない（独立）
```

`.spec/` は成果物の格納先であり実行コードの依存先ではないが、frontmatter 契約
（`sdd-core` の artifact-frontmatter 書式）を仲介した論理的な依存として扱う。

## 主要な設計決定

- 委譲レジストリを CLAUDE.md 委譲マトリクスに集約し、モデル世代交代の陳腐化を機械検証で防ぐ
  → 詳細: `.spec/design/DSN-001-delegation-registry.md`
- `<plugin名>:update` のバージョン移行を宣言的 Markdown + guard 必須の累積マイグレーションとする
  → 詳細: `.spec/design/DSN-002-update-migration.md`
- ライフサイクルスキル（init/doctor/update/uninstall）はプラグインごとに必要な操作だけを実装する
  → 詳細: `.spec/design/DSN-003.md`
- `scripts/spec` は Claude/Codex 双方の固定版インストールをバージョン非依存に解決する
  → 詳細: `.spec/design/DSN-004.md`
- `docs/` の SDD ナラティブ検査対象と調査報告等の資料保全は境界を分離し除外パターンで宣言する
  → 詳細: `.spec/design/DSN-005.md`

## library 固有

- **公開面の設計方針**: 最小公開。プラグイン名・スキル名・SKILL.md frontmatter・`scripts/spec`
  の CLI・`release_check.py` / `bump_version.py` のみを契約面とする（詳細は `公開API.md`）。
- **拡張ポイント**: 新規プラグイン追加（`add-plugin` 手順）、新規スキル追加（プラグイン内に
  自己完結フォルダを追加）。既存プラグインの内部実装（`scripts/` の実装詳細）は契約外。
- **副作用と純粋性**: `.spec/` `docs/` `evals/` への書き込みが主な副作用。リポジトリ外への
  書き込み（skill-packager の配置等）は事前確認必須（AGENTS.md ガードレール）。
- **スレッド/非同期モデル**: 該当なし（エージェント駆動の逐次実行。並列実行は worktree 単位で
  分離し、`bitz-flow:flow-worktree` が規定する「1エージェント = 1 worktree = 1ブランチ」原則に従う）。
