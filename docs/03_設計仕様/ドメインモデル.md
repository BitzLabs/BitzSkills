# ドメインモデル

## 中核エンティティと関係

```
マーケットプレイス (bitzskills)
  └─ 1..N プラグイン (plugins/<name>)
        ├─ 3マニフェスト (.claude-plugin/plugin.json, plugin.json, .codex-plugin/plugin.json)
        ├─ 0..N スキル (skills/<name>/SKILL.md)
        └─ metadata.dependencies → 他プラグイン（宣言的併用、循環禁止）

プロファイル (.claude/settings.json の enabledPlugins)
  └─ 有効化するプラグインの集合を選択（全プラグイン強制導入はしない）

委譲レジストリ (CLAUDE.md 委譲マトリクス)
  └─ 役割 → 委譲先 agent → ティア の束縛（.claude/agents/*.md と整合）

成果物
  ├─ .spec/  … 要件・設計・タスクの SSOT（frontmatter 契約は sdd-core が正）
  ├─ docs/   … 人間ナラティブ層（.spec と双方向同期。本6ファイルもここに属する）
  └─ evals/  … テスト成果物・観察ログ（skill-tester / skill-observer が書く）
```

## 不変条件 (Invariants)

- 1プラグインの3マニフェスト（Claude Code / Antigravity 2.0 / Codex CLI）の `version` は常に同値
  （CORE-CON-001）。
- `marketplace.json` の `plugins[]` と `plugins/` 実体は双方向に一致する（未列挙の実体も、
  実体のない参照も許さない。CORE-CON-003）。
- スキルは他スキルの `references/` を相対パスで参照しない。連携はスキル名の言及にとどめる
  （自己完結原則。CORE-CON-004）。
- 全 SKILL.md frontmatter は `name` / `description` に加え `metadata`（version/author/created/updated）
  を必須で持つ。内容変更時は semver で version を bump し `updated` を更新する（CORE-CON-002）。
- プラグイン内のスキル名は単一プレフィックスで統一する（`skill-*` / `sdd-*` / `ddd-*` /
  `plugin-*` 等。CORE-CON-005）。
- 委譲レジストリの委譲先 agent は実在し、ティアはしご上に重複・循環なく整合する
  （CORE-NFR-001。`release_check.py` が機械検証）。
- プラグイン間の `metadata.dependencies` は循環を持たない一方向グラフである
  （例: `bitz-ddd` → `bitz-sdd` → `bitz-flow`）。

検証可能な受入基準の正は `.spec/requirements/CORE-CON-*.md`・`CORE-NFR-001.md`。ここでは
構造とルールの要約のみを示す。

## library 固有

- ドメイン概念は次の公開型に写像される（詳細は `公開API.md`）:
  - プラグイン → プラグイン名（マーケットプレイスのインストール単位）
  - スキル → スキル名（`<plugin>:<skill>` 形式で参照されることがある）
  - 成果物 frontmatter → `.spec` 系の id 体系・必須キー
  - CLI 操作 → `scripts/spec {inspect|scaffold|status|update}` のサブコマンド
- 利用者（他プロジェクトでこのマーケットプレイスを導入する開発者）にとっての語彙は
  「プラグイン名」「スキル名」であり、内部の `scripts/*.py` 実装は語彙に含めない。
