## 2. 基本方針

1. **説明文は日本語で書く。** 英語で残すのは、機械が読む識別子（§3.1）、出力に現れる文字列（§3.2）、
   規格名・製品名・略語（§3.3）だけとする。
2. **識別子は必ずバッククォートで囲む。** バッククォートの有無で、機械が読む値か説明の語かを見分けられるようにする。
   例外メッセージ、`argparse`のヘルプ、検証プログラムがJSONへ書くエラー文など、プログラムが出す文言でも同じとする。
   ただし、f-stringで差し込む値（`{path}`など）には付けない。識別子の一部に値を差し込むときは、識別子全体を囲む
   （`` `git {args[0]}` ``、`` `environment.{field}` ``）。
3. **定義語は用語集の日本語名で書く。** 用語集にない訳語を作らない。必要なら先に用語集へ加える。
   英語名の併記は、用語集の「定義元」の列にその文書を挙げている語（その文書が定義する語）に限り、その文書の初出に
   「制約台帳（Constraint Ledger）」のように付ける。ほかの文書が定義する語には付けず、英語名は用語集で引く。
   併記の対象でも、次の場合は省く。
   - §4の一般語（ワークスペース、カタログ、カバレッジ、エッジ、終了コード、作業ディレクトリなど）
   - 同じ箇所で識別子を添える場合
   - 見出しと表の見出し行。本文の初出で併記する
4. **一般語はカタカナか定着した漢語で書く**（§4）。英語をそのまま本文に置かない。
5. **1つの概念には1つの語を使う。** 用語集の「備考」の列で「使わない:」に挙げた語は使わない。
6. **規範の意味を変えない。** 表記を直すときも、条件、例外、数値、識別子、義務の強さ（「しなければならない」「してもよい」）を保つ。
   原文が複数に読める箇所は、原文の範囲を保つ書き方を優先する。1つの読みに確定する場合は、書き直しの作業者が決めず、
   ユーザーの承認を得る。確定した読みは用語集 §14.2に記録し、そのPRの本文にも明記する。

## 3. 英語で残すもの

### 3.1 識別子

機械が読む、または機械が照合する文字列である。英語のまま、必ずバッククォートで囲む。

| 種類 | 例 |
|---|---|
| 操作名・コマンド | `bitz`、`context`、`check`、`verify`、`doctor`、`git --version` |
| CLIのオプションと値 | `--purpose`、`--format json`、`--all-workspaces` |
| 設定キー | `schemaVersion`、`multiWorkspace.members`、`verify.timeoutSeconds` |
| JSONのフィールド | `contextDigest`、`targetStatements`、`workspaceId`、`reachedBy[]` |
| 列挙値 | 状態の`passed`、`failed`、重大度の`warning`、目的の`implement`、関係型の`requires`、提示形式の`full`、文書の状態の`approved` |
| 診断コード・条件ID | `CTX-ROOT-MISSING-001`、`CONFIG-FIELD-TYPE` |
| 継続単位の語彙 | `stop-operation`、`skip-document` |
| EARS-AIのキーワード | `[MUST]`、`[WHEN]`、`[REASON]` |
| Coreが照合する本文の見出し | `Intent`、`Acceptance Criteria`、`Decision` |
| パス・ファイル名・fixture ID | `.spec/bitz.yaml`、`SINGLE-042`、`manifest.json` |
| 関数名・型名 | `TargetExpansion` |

### 3.2 出力に現れる文字列

Coreや検証プログラムが出力し、利用者や別のプログラムがそのまま読む文字列である。英語のまま、バッククォートで囲む。

- `context`のMarkdown提示の見出し（`Bundle Manifest`、`Normative Constraint Ledger`など）
- 検証プログラムの報告値（`Passed`、`Not run`、`full Gate A fresh-checkout repeatability`）
- 工程とGateの状態語彙（`Not started`、`Allowed`、`Pending`など）

### 3.3 規格名・製品名・略語

英語のまま、バッククォートで囲まずに書く。

| 区分 | 語 |
|---|---|
| 形式・規格 | JSON、JSON Schema（Draft 2020-12）、YAML、Markdown、GFM、UTF-8、UTF-16、Unicode、NFC、ASCII、BOM、SHA-256、RFC 8785（JSON Canonicalization Scheme）、EBNF、ISO/IEC 14977、ABNF、PEM、POSIX |
| 制御文字と文字の表記 | LF、CR、CRLF、NUL、TAB、SP、ESC、DEL、C0、C1、`U+XXXX`形式の符号位置（例: U+FFFD） |
| 製品・実行環境 | Git、GitHub、CPython、Python、PyPI、`uv`（コマンド名として）、Linux、macOS、Core、EARS-AI、Bitz AI-SDD、Agent Plugins、libgit2、systemd、cgroup |
| 略語 | API、CLI、CI、LLM、MCP、AI、OS、ID、PR、SDD、I/O、URL、SLO、RSS、SSD、FD、EOF、FIFO、CPU、RAM、SHA、SBOM、SAST、DNS、UTC、ULID、KISS、YAGNI、DRY、DDD |
| 単位 | KiB、MiB、GiB |
| 文書種別の記号 | REQ、TECH、ADR、TASK。種別を定義する文書（文書種別・本文テンプレート）の初出にだけ「ADR（決定記録）」のように日本語名を併記する |

### 3.4 識別子と日本語の書き分け

値そのものを指すときだけ識別子を使い、意味を述べるときは日本語を使う。識別子の前に、それが何の値かを示す語を置く。

| 書き方 | 例 |
|---|---|
| 値を指す | 「状態`failed`を返す」「目的が`verify`のとき」「フィールド`workspaceId`を持つ」 |
| 意味を述べる | 「検査に失敗した場合」「検証の目的では」 |
| 操作名 | 「`check`操作」「`verify`を実行する」。一般の動作は「検査する」「検証する」 |
| 診断を返す | 「診断`CTX-LIMIT-001`（`blocked`）を返す」。括弧の中は、その診断の結果への効果（`resultStatus`）である。重大度を示すときは「（重大度`warning`）」、両方を示すときは「（重大度`error`、結果への効果`failed`）」と書く。表では列を分ける |

英語の識別子を助詞なしで連ねない。「`purpose=verify`のBundleがbindingとして収録したcommand」ではなく、
「目的が`verify`のコンテキスト一式で、収録したテスト割当てが参照するコマンド」と書く。

## 5. 文の書き方

1. 文体はだ・である調、見出しは体言止めとする。
2. 名詞を助詞なしで3語以上つなげない。「共通argv解析、重複option、空値、target不存在」ではなく
   「引数の解析、オプションの重複、空の値、対象の不在」と書く。
3. 「〜後」「〜時」「〜別」で名詞を圧縮しない。「既定値適用後`cwd`」ではなく「既定値を適用した後の作業ディレクトリ（`cwd`）」と書く。
4. 条件と例外は文で書く。「／」は対比・組合せの併記に限り、文の代わりに使わない。
5. 選択肢の並びは「または」でつなぐ。「目的が`implement`と`interpret`のとき」は両方が同時に成り立つように読めるので、
   「目的が`implement`または`interpret`のとき」と書く。例を挙げる「や」を、条件の列挙に使わない。
6. 1文に条件を2つ以上入れるときは、箇条書きに分けることを検討する。ただし規範文を分けるときは、条件の結び付きを変えない。
7. 原文にない内容を足さない。原文にない鉤括弧の引用も付けない。ただし次の補いは許す。
   - 用語集の定義の範囲で、語の意味を明示する補い（例: 「通過状態である`passed`または`passed_with_warnings`」）
   - 見出しの語を本文で受け、初出の併記を置くための補い
   - ほかの規範文書で確定している限定の補い（例: 「アダプターのシステム指示」。品質属性と安全境界 §6による）
   - 日本語の文として成り立たせるための動詞や助詞の補い

## 6. カタカナ・漢字・送り仮名

1. カタカナ語の語末の-er、-or、-arなどに当たる音には長音符号を付ける（ユーザー、サーバー、パラメーター、アダプター）。
   語末が-yの語には付けない（カテゴリ、エントリ、レジストリ）。
2. 複合語は構成語ごとに本書と用語集の表記に従い、中黒を入れない（テストコマンド、ロックファイル）。
3. 「公用文作成の考え方」（2022年）に従い、次はひらがなで書く: できる、すべて、または、および、ただし、など、ため、とき、こと。
4. 複合名詞は送り仮名を省く（読取り、書込み、組合せ、割当て、切替え、呼出し、受取り、置換え、打切り、取止め）。
   動詞は送り仮名を付ける（読み取る、組み合わせる、置き換える）。

## 7. 記号と書式

1. 和文と英数字の間にスペースを入れない。英数字どうしの間は半角スペースを入れる（Core 1.0、64 KiB）。
2. 句読点は「、」「。」、括弧は全角の「（）」を使う。英数字は半角で書く。
3. 対比・組合せの併記は「／」、語の並列は「、」または「・」、パスの区切りは半角「/」とする。
4. 表の列見出しは日本語で書く（「フィールド」「型」「必須」「内容」）。型の列は§4.2の表記（文字列、配列など）で書き、
   JSONの型名を示す必要がある場合だけ`string`のように識別子で書く。必須の列は「○」と「—」で書く。
5. コードブロックの中は変えない。JSONの例、EBNF、コマンド例は機械が検証するか、そのまま実行される。

## 8. 変更の手順

1. 用語の抽出、用語集での確認、書き直しの順に進める。一括の自動置換はせず、出現箇所ごとに識別子か一般語かを確かめる。
2. 見出しを変えたら、そこを指すリンクを同時に直す。リンク検査は全Markdownを対象にする。
3. ハッシュ値を固定している文書（`fixtures/conformance/diagnostic-coverage.json`の`sources`、
   `fixtures/conformance/targets/cases.json`の`contractSha256`）を変えたら、再レビュー記録を残してハッシュ値を更新し、
   Gate Aを再認定する。再レビュー記録は「表記の変更のみ、規範の変更なし」とする。§2の6により読みを確定した箇所があれば、
   「表記の変更のみ。ただし次の箇所は、承認を得て読みを確定した」として、その箇所と用語集 §14.2の行を挙げる。
4. 検証プログラムが本文から照合する文字列は変えない。変えるときは同じコミットで検証プログラムを直す。

   | 文書 | 照合される文字列 |
   |---|---|
   | `06_Core実行環境・CLI基盤契約.md` | 「Core 1.0はCPython 3.12以上を対象とする」「Gitは2.30以上を対象とし」「`git --version`」 |
   | `04_適合fixture仕様.md` | matrixの行の形、環境fixtureの行の「package test \| accepted／0」。「元status」「passed/0、failed/1」は書かない |
   | `05_診断レジストリ.md` | 条件の行の9列の形と、一部の行の列の値 |
   | `12_Core-1.0実装計画.md` | 見出し「## 4. Step 1」〜「## 8. Step 5」、各節の「完了条件」、IDの並び |

5. Pythonのコメント、docstring、例外メッセージは本書に従う。識別子、検証プログラムの報告値、Coreの出力文言は変えない。
   テストがメッセージを照合している箇所は同時に直す。
6. ファイル名は見出しと同じ規則で書く。プログラムが読むファイル（`*.py`、`*.json`、`manifest.json`、`expected/`配下）、
   fixture IDのディレクトリ、`README.md`は変えない。改名したら、リンク、プログラム内のパス、ハッシュ台帳のキーを同時に直す。
7. JSON Schemaの`title`と`description`、比較タスクの課題文と正解表など、人が読むJSONの値も本書に従う。
   比較タスクの文言を変えたら、`protocol.json`のprotocol versionを上げる（`fixtures/comparison/README.md`）。
