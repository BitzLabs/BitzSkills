# ユースケース

## 1. 目的

本書は公開操作とSDDフローの受入シナリオを示す。状態遷移、CLI引数、結果Schemaを再定義せず、正本仕様を参照する。

## 2. アクター

| アクター | 役割 |
|---|---|
| 開発者 | 要求、code、test、diffを確認する |
| AI adapter / Skill | Core操作を呼び、結果を説明する |
| `bitz-core` | 決定論的な解析、解決、検査、実行を行う |
| CI | cleanな環境で全体checkとverifyを行う |

## 3. UC-01 導入診断

開発者がrepositoryで`bitz doctor`を実行すると、Coreは設定、Git、command、互換性を読取り専用で診断する。
`.spec/`がなければ作成先と最小設定を提示し、自動作成しない。

完了条件は、利用可能なら通過status、不足があれば具体的な修復手順を伴う非成功statusが返ることである。

## 4. UC-02 SPEC作成・改訂

開発者は`draft` REQをMarkdownで作成し、EARS-AI規範文へ安定IDを付ける。必要な場合だけTECH、ADR、TASKを
追加する。CoreはFrontmatter、H1、EARS-AI、関係、状態を検査する。人間が要求の意味を確認した後、REQを
`approved`へ変更して再checkする。正確な履歴はGitへ記録する。

完了条件は、`approved`への変更後に`bitz check <ID>`が通過することである。意味変更を伴う既存REQの改訂では、
先に`approved -> draft|outdated`へ戻し、review後に`approved`へ変更する。

## 5. UC-03 Context取得

adapterがSPEC IDまたは規範文IDを起点に`bitz context`を呼ぶと、Coreは強い依存を完全解決し、
Constraint Ledger、coverage、Context Digestを返す。提示量を変えても解決集合とDigestは変わらない。

参照切れ、循環、状態不適合、上限超過では部分Bundleを成功扱いしない。

## 6. UC-04 変更範囲check

開発者が引数なし`bitz check`を実行すると、CoreはGit変更集合からSPEC、所有code、所有testを選び、対象文書、
強い依存、直接逆参照を検査する。`--full`では全SPECを検査する。

実装前のPre-checkでは起点IDを明示し、対象文書、強い依存、直接逆参照を完全検査する。clean treeの対象0件を
Pre-checkの代用にしない。

TASK IDを明示した場合だけ`changes`境界を検査する。Coreはファイルを修正しない。

## 7. UC-05 実行検証

開発者がREQ、TECH、規範文、TASKを指定して`bitz verify`を実行すると、Coreは未tested `MUST`がないことを確認し、
command名ごとにtest pathをまとめて実行する。終了理由、終了コード、timeout、Context Digestを結果へ記録する。

test不足は`blocked`、非0終了は`failed`、起動失敗・signal・timeoutは`error`となる。

## 8. UC-06 通常開発

開発者またはSkillは[Small Flow](03_SDDフロー.md#3-small-flow)に従い、Context、実装前check、実装、実装後check、
verify、Human Review、Doneを順に行う。書込み直前にContext Digestが変わっていれば実装を開始しない。

## 9. UC-07 高リスク変更

公開API、永続data、security、費用、法令、SLO、複数moduleへ影響する場合、Small FlowへRequirement Reviewと
Design Reviewを追加する。Requirement Review前は`purpose=interpret`、承認後は`purpose=implement`のContextを
使用する。Coreはreview状態を持たず、同じ操作仕様を使う。

## 10. UC-08 並行branchのID衝突

統合先を取り込んだtreeで`bitz check --full --base <統合先先端>`を実行し、同じworkspace内の重複IDを検出する。
人間が片方を当該workspaceの未使用IDへ変更し、追跡可能な参照を同じ変更で更新する。別workspaceの同名
ローカルIDは修飾IDで区別し、改番しない。Coreは勝敗と新IDを提案しない。

完了条件は、現在集合のIDが一意で全参照が解決し、再checkが通過することである。

## 11. UC-09 非成功結果の復旧

`check`または`verify`が`failed`、`blocked`、`error`になった場合、Coreは再現に必要な最小reportを保存する。
開発者はDiagnosticのsource、resultStatus、存在する場合はsuggestedActionを確認し、該当箇所だけを修正して
同じ操作を再実行する。`context`と`doctor`はreportを保存せず、結果を標準出力へ返す。

秘密値、環境変数値、test全文出力はreportへ保存しない。

## 12. UC-10 状態遷移と置換

REQ／TECHの新規作成は`draft`から開始し、人間review後に`approved`へ変更する。承認済み契約の意味変更は、
先に`draft`または`outdated`へ戻してから編集し、再review後に`approved`へ戻す。`draft`の不採用は`rejected`、
`open` TASKの完了または取り止めは`done`または`cancelled`とする。

ADRは`proposed`から`accepted`または`rejected`へ進める。後継ADRを採用する場合、後継の`supersedes`と旧ADRの
`accepted -> superseded`を同じ変更へ含める。REQ／TECHの後継文書を`approved`にして`supersedes`を宣言すると、
旧文書はContextで適用不能になるが、Coreが起点を後継へ暗黙差替えすることはない。

各遷移後に`bitz check <ID>`を実行する。禁止遷移は`SPEC-STATE-TRANSITION-001`／failedとなり、次工程へ進まない。

## 13. UC-11 モノレポ横断要求

repository rootの共通REQを、webとapi memberのTECHが修飾IDで`refines`する。各TECHは自身のmember配下のcode、
test、commandだけを所有する。adapterがweb TECHを起点にContextを取得すると、共通REQまで完全解決するが、
関係しないmemberの本文はBundleへ含めない。

CIで`check --all-workspaces`と`verify --all-workspaces`を実行すると、Coreはcatalog、横断関係、所有境界を検査し、
workspace ID順のmember結果と集約statusを返す。同じローカル文書IDが別memberに存在しても修飾IDで区別する。

完了条件は、未登録member、非修飾横断参照、所有境界違反がなく、全体checkとverifyが通過することである。

## 14. 関係

```text
UC-01 導入
  -> UC-02 SPEC作成
  -> UC-03 Context取得
  -> UC-04 Pre-check
  -> code / test変更
  -> UC-04 Post-check
  -> UC-05 verify
  -> Human Review
  -> Git記録
```

UC-02の承認、UC-06／07の完了または取り止めはUC-10の状態遷移を使用する。
モノレポではUC-11のcatalog、修飾ID、所有境界をUC-02〜05へ適用し、CIで全体結果を確認する。

フローの正本は[SDDフロー](03_SDDフロー.md)、機械契約の正本は[詳細設計](../03.詳細設計/README.md)とする。
