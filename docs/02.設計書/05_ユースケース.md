# ユースケース

## 1. 目的

本書は、公開操作とSDDフローの受入シナリオを示す。状態遷移、CLIの引数、結果のスキーマを再定義せず、正本の仕様を参照する。

## 2. アクター

| アクター | 役割 |
|---|---|
| 開発者 | 要求、コード、テスト、差分を確認する |
| AIのアダプター／スキル | 公開操作を呼び、結果を説明する |
| `bitz-core` | 決定論的な解析、解決、検査、実行を行う |
| CI | クリーンな環境で、全体の`check`と`verify`を行う |

## 3. UC-01 導入診断

開発者がリポジトリで`bitz doctor`を実行すると、Coreは設定、Git、コマンド、互換性を読取り専用で診断する。
`.spec/`がなければ、作成先と最小設定を提示し、自動作成しない。

完了条件は、利用可能であれば通過状態、不足があれば具体的な修復手順を伴う非成功の状態が返ることである。

## 4. UC-02 仕様文書の作成・改訂

開発者は、`draft`のREQをMarkdownで作成し、EARS-AIの規範文へ安定したIDを付ける。必要な場合だけ、TECH、ADR、TASKを
追加する。Coreは、フロントマター、H1、EARS-AI、関係、状態を検査する。人間が要求の意味を確認した後、REQを
`approved`へ変更して、`check`を再実行する。正確な履歴はGitへ記録する。

完了条件は、`approved`へ変更した後に`bitz check <ID>`が通過することである。意味の変更を伴う既存のREQの改訂では、
先に`approved -> draft|outdated`へ戻し、レビューの後に`approved`へ変更する。

## 5. UC-03 コンテキスト取得

アダプターが、文書IDまたは規範文IDを起点に`bitz context`を呼ぶと、Coreは強い関係を完全に解決し、
制約台帳、カバレッジ、コンテキストのハッシュ値を返す。提示する量を変えても、解決した集合とハッシュ値は変わらない。

参照切れ、循環、状態の不適合、上限の超過では、一部が欠けたコンテキスト一式を成功として扱わない。

## 6. UC-04 変更範囲の検査

開発者が引数なしで`bitz check`を実行すると、CoreはGitの変更集合から仕様文書、所有するコード、所有するテストを選び、対象の文書、
強い依存、直接逆参照を検査する。`--full`では、すべての仕様文書を検査する。

実装前検査では、起点IDを明示し、対象の文書、強い依存、直接逆参照を完全検査する。クリーンな作業ツリーで対象が0件になることを、
実装前検査の代用にしない。

TASKのIDを明示した場合だけ、`changes`の境界を検査する。Coreはファイルを修正しない。

## 7. UC-05 実行検証

開発者がREQ、TECH、規範文、TASKを指定して`bitz verify`を実行すると、Coreは未テストの`MUST`がないことを確認し、
検証対象ごとにコンテキストを解決して、コマンド名ごとにテストのパスをまとめて実行する。結果は、`targetResults[]`へ検証対象ごとの
コンテキストのハッシュ値とテスト割当ての参照を、`commands[]`へ共有した実行の終了理由、終了コード、タイムアウトを記録する。

テストの不足は`blocked`、0以外の終了は`failed`、起動の失敗・シグナル・タイムアウトは`error`となる。

## 8. UC-06 通常開発

開発者またはスキルは、[簡易フロー](03_SDDフロー.md#3-簡易フロー)に従い、コンテキスト取得、実装前検査、実装、実装後検査、
検証、人手レビュー、完了を順に行う。書込みの直前にコンテキストのハッシュ値が変わっていれば、実装を開始しない。

## 9. UC-07 高リスク変更

公開API、永続データ、セキュリティ、費用、法令、SLO、複数のモジュールへ影響する場合、簡易フローへ要求レビューと
設計レビューを追加する。要求レビューの前は目的`interpret`、承認の後は目的`implement`のコンテキストを
使用する。Coreはレビューの状態を持たず、同じ操作仕様を使う。

## 10. UC-08 並行ブランチのID衝突

統合先を取り込んだ作業ツリーで`bitz check --full --base <統合先先端>`を実行し、同じワークスペースの中の重複するIDを検出する。
人間が片方を当該ワークスペースの未使用のIDへ変更し、追跡可能な参照を同じ変更で更新する。別のワークスペースにある同名の
ローカルIDは、修飾IDで区別し、改番しない。Coreは勝敗と新しいIDを提案しない。

完了条件は、現在の集合のIDが一意であり、すべての参照が解決し、再実行した`check`が通過することである。

## 11. UC-09 非成功結果の復旧

`check`または`verify`が`failed`、`blocked`、`error`になった場合も、Coreは結果を標準出力へ返し、暗黙にレポートを
保存しない。開発者は、診断のフィールド`source`、`resultStatus`、存在する場合は`suggestedAction`を確認し、該当する箇所だけを
修正して同じ操作を再実行する。永続的な証跡が必要な再実行では`--report`を明示する。`context`と`doctor`はレポートを保存しない。

秘密値、環境変数の値、テストの出力の全文は、レポートへ保存しない。

## 12. UC-10 状態遷移と置換

REQまたはTECHの新規作成は`draft`から開始し、人間のレビューの後に`approved`へ変更する。承認済みの契約の意味を変更するときは、
先に`draft`または`outdated`へ戻してから編集し、再レビューの後に`approved`へ戻す。`draft`の不採用は`rejected`、
`open`のTASKの完了または取止めは`done`または`cancelled`とする。

ADRは`proposed`から`accepted`または`rejected`へ進める。後継のADRを採用する場合、後継の`supersedes`と旧ADRの
`accepted -> superseded`を同じ変更へ含める。REQまたはTECHの後継の文書を`approved`にして`supersedes`を宣言すると、
旧文書はコンテキストで適用できなくなるが、Coreが起点を後継へ暗黙に差し替えることはない。

各遷移の後に`bitz check <ID>`を実行する。禁止された遷移は診断`SPEC-STATE-TRANSITION-001`（`failed`）となり、次の工程へ進まない。

## 13. UC-11 複合ワークスペースの横断要求

リポジトリのルートにある共通のREQを、`web`と`api`の各メンバーのTECHが修飾IDで`refines`する。各TECHは、自身のメンバーの配下にある
コード、テスト、コマンドだけを所有する。アダプターが`web`のTECHを起点にコンテキストを取得すると、共通のREQまで完全に解決するが、
関係しないメンバーの本文はコンテキスト一式へ含めない。

CIが`check --all-workspaces`と`verify --all-workspaces`を実行すると、Coreはカタログ、横断関係、所有境界を検査し、
ワークスペースID順のメンバーの結果、検証対象ごとの証跡、共有したコマンドの結果、集約した状態を返す。同じローカルの文書IDが別の
メンバーに存在しても、修飾IDで区別する。`--report`なしでは結果のファイルを生成しない。

完了条件は、Gitが認識している未登録の`.spec/bitz.yaml`、非修飾の横断参照、正規パスによる所有境界の違反がなく、
全体の`check`と`verify`が通過することである。

## 14. 関係

```text
UC-01 導入
  -> UC-02 SPEC作成
  -> UC-03 Context取得
  -> UC-04 Pre-check
  -> code / test変更
  -> UC-04 Post-check
  -> UC-05 verify
  -> Human Review
  -> Git記録
```

UC-02の承認、UC-06／07の完了または取止めは、UC-10の状態遷移を使用する。
複合ワークスペースでは、UC-11のカタログ、修飾ID、所有境界をUC-02〜05へ適用し、CIで全体結果を確認する。

フローの正本は[SDDフロー](03_SDDフロー.md)、機械契約の正本は[詳細設計](../03.詳細設計/README.md)とする。
