# システム構成

## 1. 目的

Bitz AI-SDDは、個人から数人のチームがAI支援開発で仕様の取り違え、参照切れ、検証漏れを減らすための
ローカルツールである。中心はEARS-AIで記述した要求と、Git管理されたワークスペースの`.spec/`である。
ワークスペースは単独でも、同じGitリポジトリ内で明示したカタログにより束ねて複合ワークスペースにしてもよい。

## 2. 論理構成

```text
AI CLI / 人間 / CI
        |
  adapter / Skill
        |
     bitz-core
  +-----+------+-------+--------+
  |            |       |        |
context      check   verify   doctor
  |            |       |        |
  +------ EARS-AI / SPEC -------+
                    |
       workspace / 複合workspace index
                    |
               code / test / Git
```

`bitz-core`は次を所有する。

- EARS-AIの構文解析器と意味中間表現
- ワークスペース単位の仕様文書（SPEC）モデル、複合ワークスペース、型付きの横断関係
- 強い依存の完全閉包とコンテキストのハッシュ値
- スキーマ、参照、状態、トレース、Gitの差分の静的検査
- 仕様文書が宣言したテストコマンドの実行
- 結果、診断、終了コード、最小のレポート

アダプターとスキル（Skill）はCoreの構造化結果を説明し、開発フローを進める。構文解析器、状態遷移、合否判定を
自然言語へ複製しない。Coreはコミット、プッシュ、PR、デプロイ、要求本文の自動修正を行わない。

## 3. 公開操作

| 操作 | 責務 | 副作用 |
|---|---|---|
| `bitz context` | 起点から必要な仕様を完全解決し、目的に応じたコンテキスト一式を返す | なし |
| `bitz check` | 仕様文書、関係、トレース、Gitの差分を静的に検査する | `--report`を明示したときだけ |
| `bitz verify` | 対象規範文に対応するテストコマンドを実行する | プロセスの実行と、`--report`を明示したときだけ |
| `bitz doctor` | 導入、設定、互換性、実行環境を診断する | なし |

正確な入力、処理、結果、診断は[操作仕様](../03.詳細設計/03_操作仕様/README.md)だけが定義する。

## 4. 正本と派生物

| 情報 | 正本 | 派生物 |
|---|---|---|
| 要求・技術契約・判断・TASK | `.spec/**/*.md` | 意味中間表現、索引、コンテキスト一式 |
| ワークスペースの設定と複合ワークスペースのカタログ | 各`.spec/bitz.yaml` | 実効設定、複合ワークスペースの索引 |
| コードとテスト | Gitの作業ツリー | トレースの索引、`verify`の結果 |
| 変更履歴 | Git、PR、ADR | 任意のレポート |

チャットの履歴、コンテキスト一式、キャッシュ、通常の実行のログ、明示して生成したレポートは正本にしない。

## 5. 依存方向

```text
EARS-AI言語
    ^
SPEC文書モデル ----> 共通契約
    ^                    ^
Context解決モデル ------+
    ^
操作仕様
    ^
adapter / Skill / SDDフロー
```

下位層は上位の運用手順を知らない。特に、EARS-AI言語はGit、TASK、テストコマンドを知らず、仕様文書モデルは
CLIの表示と人手レビューを知らない。

## 6. Core 1.0の境界

Core 1.0は、単一ワークスペースと、1つのGitリポジトリ内で明示登録された複数のワークスペースから成る
複合ワークスペースを対象とする。複合ワークスペースは、リポジトリのルートのカタログ、修飾ID、
所有境界、ワークスペースを横断するコンテキスト、`--all-workspaces`を持つ。
通常の操作は1つの作業ワークスペースを保ち、強い依存で到達しないメンバーの本文を処理しない。

次は1.1以降の候補であり、Core 1.0の設定、CLI、結果のスキーマ、適合条件へ含めない。

- 複数のGitリポジトリ、Gitのサブモジュール、ネットワーク越しの仕様文書による複合ワークスペース
- ID衝突の勝敗判定、自動の改番候補、`idCollisions`
- プロファイル（Profile）のマニフェスト、外部の検証プログラム、プロファイル固有の直列化器／移行
- 提示内容のハッシュ値と、文書単位の公開ハッシュ値
- LLMによる意味の監査、DDD、双方向の同期

Coreは現在の集合の重複IDを検出する。並行するブランチに由来する重複は人間が改番し、通常の`check --full`で確認する。
複合ワークスペース内ではローカルIDをワークスペースごとに一意とし、横断の参照と結果に修飾IDを使用する。

## 7. 配布と拡張

配布は、Agent Plugins準拠の`bitz-core`と、任意の独立した拡張を基本とする。LLMを使わない環境とCIでは、
自己完結のCLIを利用できる。拡張は公開操作（public operation）と結果へ依存し、別の拡張のインストール先や
内部のファイルを参照しない。

Coreのソースの木構造は`plugins/bitz-core`であり、プラグインのマニフェスト、独立した`uv`のプロジェクト、
`src`レイアウトのパッケージ`bitz`を持つ。
Core固有の試験は`tests/bitz-core/`、Coreに依存しない適合fixtureと参照harnessは`fixtures/`に置き、
`plugins/bitz-core`からどちらも参照しない（[ADR-049](10_決定記録/ADR-049_Coreのソースの配置と試験の構成を確定する.md)）。

Coreの構文解析器は`[namespace:TERM]`の形式を不透明な拡張タグとして保持するが、Core 1.0はプロファイルを実行しない。
実際のプロファイルが実証された場合だけ、独立した対応機能として互換性契約を追加する。

## 8. 設計上の禁止

- LLMの判断だけを必須の合否根拠にしない。
- 強い依存を途中で切った部分的なコンテキストを成功として扱わない。
- 仕様文書の本文からコマンド、権限、環境変数、外部の送信先を取得しない。
- 公開操作の結果を使って仕様文書の本文を自動変更しない。
- 結果の状態にかかわらず、結果のファイルを既定で保存しない。
- ADRを現在の実行契約の正本として要求しない。
