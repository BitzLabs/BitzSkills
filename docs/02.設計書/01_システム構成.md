# システム構成

## 1. 目的

Bitz AI-SDDは、個人から数人のチームがAI支援開発で仕様の取り違え、参照切れ、検証漏れを減らすための
ローカルツールである。中心はEARS-AIで記述した要求と、Git管理されたworkspaceの`.spec/`である。
workspaceは単独でも、同じGit repository内の明示catalogで連合してもよい。

## 2. 論理構成

```text
AI CLI / 人間 / CI
        |
  adapter / Skill
        |
     bitz-core
  +-----+------+-------+--------+
  |            |       |        |
context      check   verify   doctor
  |            |       |        |
  +------ EARS-AI / SPEC -------+
                    |
        workspace / federation index
                    |
               code / test / Git
```

`bitz-core`は次を所有する。

- EARS-AI ParserとSemantic IR
- workspace単位のSPEC文書モデル、モノレポ連合、型付き横断関係
- 強い依存の完全閉包とContext Digest
- Schema、参照、状態、trace、Git差分の静的検査
- SPECが宣言したtest commandの実行
- 共通結果、Diagnostic、終了コード、最小report

adapterとSkillはCoreの構造化結果を説明し、開発フローを進行する。Parser、状態遷移、合否判定を自然言語へ
複製しない。Coreはcommit、push、PR、deploy、要求本文の自動修正を行わない。

## 3. 公開操作

| 操作 | 責務 | 副作用 |
|---|---|---|
| `bitz context` | 起点から必要な仕様を完全解決し、目的別Bundleを返す | なし |
| `bitz check` | SPEC、関係、trace、Git差分を静的検査する | 非成功時または明示時のreportだけ |
| `bitz verify` | 対象句に対応するtest commandを実行する | process実行とreportだけ |
| `bitz doctor` | 導入、設定、互換性、実行環境を診断する | なし |

正確な入力、処理、結果、Diagnosticは[操作仕様](../03.詳細設計/03_操作仕様/README.md)だけが定義する。

## 4. 正本と派生物

| 情報 | 正本 | 派生物 |
|---|---|---|
| 要求・技術契約・判断・TASK | `.spec/**/*.md` | Semantic IR、索引、Context Bundle |
| workspace設定と連合catalog | 各`.spec/bitz.yaml` | 実効設定、連合索引 |
| コードとテスト | Git working tree | trace索引、verify結果 |
| 変更履歴 | Git、PR、ADR | 任意report |

チャット履歴、Context Bundle、cache、通常runのログ、成功reportは正本にしない。

## 5. 依存方向

```text
EARS-AI言語
    ^
SPEC文書モデル ----> 共通契約
    ^                    ^
Context解決モデル ------+
    ^
操作仕様
    ^
adapter / Skill / SDDフロー
```

下位層は上位の運用手順を知らない。特に、EARS-AI言語はGit、TASK、test commandを知らず、SPEC文書モデルは
CLI表示とHuman Reviewを知らない。

## 6. Core 1.0の境界

Core 1.0は、単一workspaceと、1つのGit repository内で明示登録された複数workspaceの連合を対象とする。
連合はrepository rootのcatalog、workspace修飾ID、所有境界、横断Context、`--all-workspaces`を持つ。
通常操作は1つのactive workspaceを保ち、強い依存で到達しないmemberの本文を処理しない。

次は1.1以降の候補であり、Core 1.0の設定、CLI、結果Schema、適合条件へ含めない。

- 複数Git repository、Git submodule、network越しSPECの連合
- ID衝突の勝敗判定、自動改番候補、`idCollisions`
- Profile Manifest、外部Validator、Profile固有Serializer／migration
- Projection Digestと文書単位の公開hash
- LLM意味監査、DDD、双方向同期

Coreは現在集合の重複IDを検出する。並行branch由来の重複は人間が改番し、通常の`check --full`で確認する。
連合内ではローカルIDをworkspaceごとに一意とし、横断参照と結果に修飾IDを使用する。

## 7. 配布と拡張

配布はAgent Plugins準拠の`bitz-core`と任意の独立拡張を基本とする。非LLM環境とCIでは自己完結CLIを利用できる。
拡張は公開操作と共通結果へ依存し、別拡張のインストール先や内部ファイルを参照しない。

Core Parserは`[namespace:TERM]`形式をopaqueな拡張として保持するが、Core 1.0はProfileを実行しない。
実Profileが実証された場合だけ、独立Capabilityとして互換性契約を追加する。

## 8. 設計上の禁止

- LLM判断だけを必須の合否根拠にしない。
- 強い依存を途中で切った部分Contextを成功扱いしない。
- SPEC本文からcommand、権限、環境変数、外部送信先を取得しない。
- Core操作の結果を使ってSPEC本文を自動変更しない。
- 成功runの詳細ログを既定で保存しない。
- ADRを現在の実行契約の正本として要求しない。
