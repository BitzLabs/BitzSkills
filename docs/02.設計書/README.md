# Bitz AI-SDD 軽量設計

## 1. 目的と対象

本設計は、個人から数人の信頼された開発チームがAI CLIを利用し、仕様の取り違え、参照切れ、
検証漏れ、危険な自動変更を少ない待ち時間で防ぐことを目的とする。

大企業向けの権限基盤、悪意ある内部者への防御、分散承認、包括的なコンプライアンス管理は
Core 1.0の対象外とする。Gitリポジトリとそのレビューを、設定・承認・監査の基本境界として扱う。

## 2. プロダクトの中心

**EARS-AIを本設計の中心的な利用体験とする。**

EARS-AIは、自然言語の要求へID、発動条件、規範強度、期待結果を付与する軽量な制約付き要求記法である。
人間が直接読め、Parserが決定論的に構造化でき、AIへ必要な制約だけを渡せることを価値とする。

EARS-AIが保証するのは構文、参照、語彙、機械的に検証可能な制約である。自由記述部分の意味的正しさ、
LLM出力の決定論性、実装の完全性は保証しない。これらはテスト結果と人間の判断で補う。

## 3. 設計原則

1. EARS-AIと`.spec/`を、AIと人間が共有する小さな契約面にする。
2. 既定処理はローカル・オフライン・決定論的にする。
3. 通常の`bitz check`は変更範囲だけを検査し、1秒以内を目標とする。
4. 型付き依存を完全に解決したContext Bundleを、すべてのエージェントが共通利用する。
5. LLM呼出しは必須の合否判定に使わず、提案機能として明示実行する。
6. 品質はリンクの存在だけでなく、`MUST`句ごとの実行可能なテスト対応で確かめる。
7. 設定と承認はGit履歴を基本証跡とし、外部署名基盤を必須にしない。
8. 自動修復は局所的なコード・テスト・形式修正に限定し、要求の意味を変更しない。
9. 成功時の出力と保存物を最小化し、詳細レポートは失敗時または明示指定時だけ生成する。
10. 高度な検証、DDD、複数CLI対応は、実測で必要性が確認された後に追加する。

## 4. 最小プロダクト

Core 1.0が公開する基本操作は次の4つとする。

| 操作 | 役割 |
|---|---|
| `bitz context` | 型付き依存を解決し、完全なContext BundleとDigestを返す |
| `bitz check` | EARS-AI構文、Schema、ID、参照、静的トレースを検査する |
| `bitz verify` | 対象のテストコマンドを実行し、要求と結果を対応付ける |
| `bitz doctor` | 導入状態、設定、互換性、キャッシュを診断する |

SDDの段階管理やAIエージェントの進行は、これらの操作を呼び出す薄いスキルとして実現する。

## 6. 非目標

- AIの推論を決定論的にすること
- 仕様記述だけで実装の正しさを証明すること
- すべての開発組織へ同じGateを強制すること
- Core 1.0で全言語、全CLI、全配布形態を同時対応すること
- リポジトリ管理者を敵対者とみなすこと
