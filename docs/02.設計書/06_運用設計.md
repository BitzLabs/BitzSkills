# 運用設計

## 1. 運用目標

個人から数人のチームが、既存のGitとテスト環境へ小さな追加だけで導入できることを目標とする。
常駐サービス、データベース、外部管理画面、専用認証基盤を必要としない。

## 2. 導入

AIクライアントでは、GitHub上のBitzマーケットプレイスを登録し、必須の`bitz-core`と必要な拡張だけを
導入する。通常のAI-SDD利用では`bitz-core` + `bitz-sdd`を推奨する。

```text
plugin marketplace add <bitz-marketplace-repository>
plugin install bitz-core@<bitz-marketplace>
plugin install bitz-sdd@<bitz-marketplace>   # 必要な場合
bitz doctor
bitz check --full
```

実際のコマンド名はクライアントごとに異なる。マーケットプレイスはGitHubリポジトリ内のカタログから
複数プラグインを個別に提供し、各パッケージはAgent Plugins 1.0.0へ適合させる。

CI、非LLM利用、自己完結Core実行体を同梱しない環境では、次の明示導入を使用する。

```text
uv tool install bitz
bitz doctor
```

`bitz-core`単独でもEARS-AI、Context、全検査を実行できる。拡張プラグインは任意であり、
別拡張を自動導入しない。

## 3. 日常運用

```text
変更意図の確定後:     bitz context <ID> --purpose implement
編集直前・再開時:     bitz context <ID> --purpose implement --expect-digest <digest>
実装前:               bitz check
実装後:               bitz check            # TASK起点は bitz check <TASK-ID>
検証:                 bitz verify <ID>
TASK完了時:            statusをdoneへ変更後、bitz check <TASK-ID>
取り止め時:            rejected/cancelledと理由を記録後、bitz check <ID>
CIまたは節目:          bitz check --full
モノレポCI:             bitz check --all-workspaces
                        bitz verify --all-workspaces
問題発生時:            bitz doctor
拡張の開始時:          bitz doctor <拡張の版・要求Capability>
```

通常実行はネットワークとLLMを使わず、成功時にファイルを生成しない。実装前後の`bitz check`は同じ
コマンドであり、実装後にTASK IDを明示した場合だけ`changes`境界を検査する
（[ADR-028](10_決定記録/ADR-028_開発フローの実装後検査とTASK境界の接続.md)）。

フローは専用branchまたはworktreeで行い、変更を伴うフェーズを個別commitへ分ける。読取り専用フェーズでは
空commitを作らず、その時点のHEADをcheckpointとする。フェーズcommitをsquashせず、取り消す場合は新しい順に
`git revert`する。pushは全フェーズの確認後に別操作として行う。CoreはこれらのGit操作を実行しない。

TASK起点では、VerifyとHuman Reviewの後にTASKを`done`へ変更してRevision Historyを更新し、変更後の
`bitz check <TASK-ID>`がフローの通過条件を満たしてから同じ完了結果をGitへ記録する。後続TASKは
この記録後に開始する。Coreはstatusを自動変更せず、Git commitも実行しない
（[ADR-034](10_決定記録/ADR-034_TASK完了終端とdone起点操作の確定.md)）。

checkのフロー通過条件は`passed`または`passed_with_warnings`とする。warningは表示して継続し、
`failed`、`blocked`、`error`と引数不正では停止する。Core 1.0は`--strict`を提供しない
（[ADR-035](10_決定記録/ADR-035_check空対象とフロー通過statusの確定.md)）。

フローを取り止める場合は、`draft`のREQ／TECHを`rejected`、`open` TASKを`cancelled`へ変更し、条件付き必須の
理由セクションとRevision Historyを同じ変更へ記録する。変更後の`bitz check <ID>`が`passed`または
`passed_with_warnings`であることを確認してからGitへ記録する。既に適用した`approved` REQ／TECHは
`rejected`へ変更せず、`outdated`と後続の設計判断で扱う。Coreは取り止めを推測せず、文書を削除または
自動変更しない（[ADR-036](10_決定記録/ADR-036_フロー取り止めと不採用履歴の保持.md)）。
実装差分が残る場合は、人間が破棄、保持、別TASKへの引継ぎ、Spikeへの隔離を選ぶ。Skillは差分を提示するが
自動削除せず、Stoppedのcommitへ途中実装を既定で混在させない。処遇と引継ぎ先は既存の理由欄へ記録する。

## 4. CI

CIでは`<merge-base>`をworkflowが解決し、次を標準とする。

```text
bitz check --full --base <merge-base>
bitz verify
```

モノレポ連合ではGitルートから次を標準とする。

```text
bitz check --all-workspaces --base <merge-base>
bitz verify --all-workspaces
```

Coreはdefault branchやremote名を推測しない。比較元commitを解決できない場合は終了コード4とし、
承認済みREQ保護や状態遷移を未実施のままCI成功にしない。

通常の開発ではactive workspaceだけを検査し、横断関係に必要な軽量索引と到達先だけを追加する。
全体検証はworkspace ID順に各設定のコマンドを実行し、別workspaceの同名コマンドを統合しない。

引数なしの`bitz verify`は、検証対象となる全SPECを解決する。
各`MUST`文にテスト対応がない対象は、その対象のコマンドを実行せず`blocked`とする。独立した他対象は継続し、
全体は対象別結果の最も悪いstatusで集約する。

既存のLint、型検査、SAST、テスト基盤を置き換えず、`bitz verify`から呼び出す。
CI専用の別ルールエンジンを作らない。

## 5. 性能予算

単一workspaceの基準リポジトリは、EARS-AI規範文1,000件、参照5,000件、仕様ファイル300件とする。
モノレポ基準はPhase 0で固定する。初期fixtureは5 workspace、連合全体で同じ1,000規範文、5,000参照、
300仕様ファイルとし、横断関係と同名ローカルIDを含める。

| 操作 | 目標 |
|---|---:|
| 変更範囲の`bitz check` | 1秒以内 |
| 20文書・128 KiB以下の`bitz context` | 1秒以内 |
| 基準リポジトリの`bitz check --full` | 5秒以内 |
| `bitz doctor` | 2秒以内 |
| コアの追加メモリ | 200MB以内 |

`verify`の時間は利用者のテスト時間に依存するため、コア自身のオーバーヘッドを500ms以内とする。
目標は実測に基づいて確定し、達成できない機能は既定経路から外すか増分化する。
この性能目標は上記の基準リポジトリ規模に対するものである。リソースhard limitは入力増幅を防ぐ実装境界であり、
上限近傍の性能を保証しない。
モノレポの通常操作は同じ目標を維持し、`--all-workspaces`の目標値はfixture実測後に確定する。

## 6. キャッシュ

- キャッシュなしでも正しく動く。
- キャッシュはGit revision、対象path、コア版をキーにする。
- 不整合を検出した場合は自動破棄して再生成する。
- キャッシュ削除に専用復旧手順を要求しない。

## 7. 更新

- Coreのメジャー版更新前に`bitz doctor`で互換性を確認する。
- 各拡張は開始時に`doctor`でCore APIと要求Capabilityを確認する。
- 設定とEARS-AIの移行は、決定論的に変換できる部分だけ提案する。
- 更新失敗時は既存`.spec/`を変更しない。
- プラグインがコアを自動更新しない。
- マーケットプレイスと各プラグインを同一release tagで検証し、外部sourceはcommit SHAで固定する。
- `.spec/bitz.yaml`をインストール済みプラグインの台帳にしない。

## 8. 障害時

| 状況 | 動作 |
|---|---|
| 設定の構文・型・必須項目が不正 | `error`と該当キーを返す |
| Schema majorが未対応 | 読取りを続けず`blocked`を返す |
| 強い関係の参照切れ・循環 | `failed`とsource、target、edgeを返す |
| Context上限超過 | 部分bundleを使わず`blocked`を返す |
| Context Digest不一致 | 編集を続けず`blocked`を返す |
| テスト環境不足 | `blocked`と不足コマンドを返す |
| キャッシュ破損 | 再生成して継続する |
| LLM利用不能 | 決定論的検査を継続する |
| `.spec/`または`bitz.yaml`不在 | `doctor`が最小設定と作成先を示して`blocked`を返す |
| モノレポmember不在、ID不一致、所有境界違反 | 対象workspaceとcatalog entryを示して`blocked`または`failed`を返す |
| Core API major不一致、要求Capability不足 | 拡張を開始せず`doctor`が`blocked`と更新手順を返す |
| Core不在 | 拡張が静的な`bitz-core`導入手順を返し、処理を代替しない |
| Git不在 | 差分保護とTASK境界以外を継続し、失われる保証を警告する |
| Git不在でモノレポ連合を使用 | 連合境界と所有を確定できないためモノレポ操作を`blocked`にする |

復旧の基本は、Git diffの確認、設定修正、コマンド再実行で完結させる。

## 9. バックアップと観測性

正本はGit管理された`.spec/`であり、追加バックアップ機構をCore 1.0へ実装しない。
観測性は所要時間、対象件数、キャッシュhit/miss、Diagnostic件数に限定する。
テレメトリ外部送信は既定で行わない。
