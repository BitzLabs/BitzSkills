# SDDフロー

## 1. 目的

SDDフロー（SDD flow）は、Coreの公開操作を使って開発を進める、アダプターとスキルの契約である。Coreはフローの状態、人手レビュー、
コミットを保持せず、各段階で決定論的な検査結果を返す。

## 2. フローの選択

| 条件 | フロー |
|---|---|
| 通常のバグ修正、局所的な機能、リファクタリング | 簡易フロー（Small Flow） |
| 公開API、永続データ、セキュリティ、費用、法令、SLO、複数のモジュールへ影響する場合 | 完全フロー（Full Flow） |
| 技術的な不確実性が高く、要求を確定する前に証拠が必要な場合 | スパイク（Spike） |

## 3. 簡易フロー

```text
Intent -> Context -> Pre-check -> Implement -> Post-check -> Verify -> Human Review -> Done
```

1. **起点の特定**（Intent）: `approved`のREQまたはTECH、その規範文、または`open`のTASKを起点として特定する。
2. **コンテキスト取得**（Context）: 目的`implement`の完全なコンテキスト一式を取得し、通過状態（pass status）であることを確認する。
3. **実装前検査**（Pre-check）: `bitz check <起点ID>`が通過状態であることを確認する。
4. **実装**（Implement）: 最初の書込みの直前にコンテキストのハッシュ値を再照合し、境界内のコードとテストを変更する。
5. **実装後検査**（Post-check）: `bitz check`を再実行する。TASKが起点の場合は`bitz check <TASK-ID>`で`changes`を検査する。
6. **検証**（Verify）: 目的`verify`を解決し、`bitz verify <ID>`が通過状態であることを確認する。
7. **人手レビュー**（Human Review）: 対応する規範文、テストの結果、最終差分、証明していない事項を人間が確認する。
8. **完了**（Done）: TASKが起点の場合は`done`へ変更し、最終の`bitz check <TASK-ID>`を通してGitへ記録する。

`context`、`check`、`verify`は、`passed`または`passed_with_warnings`だけを通過状態とする。`context`ではさらに
`resolution.complete: true`とコンテキストのハッシュ値を必要とする。`failed`、`blocked`、`error`、引数不正では
次の段階へ進まず、`verify`が非成功の場合は人手レビューと完了へ進まない。Core 1.0は警告を昇格する`--strict`を
提供しない。

## 4. 完全フロー

```text
Intent -> Interpret Context -> Requirement Review -> Approval
       -> Implement Context -> Design Review -> Pre-check
       -> Implement -> Post-check -> Verify -> Human Review -> Done
```

完全フローは、簡易フローへ要求と設計の明示的なレビューを追加する。要求レビュー（Requirement Review）の前は目的`interpret`を使い、
`draft`を参考として読めるようにする。要求を承認した後に目的`implement`を解決する。検査コマンド、
実装後の順序、完了条件は簡易フローと同じものを使用し、別の実行エンジンを作らない。

- 要求レビューは、目的、意味、受入条件、互換性を確認する。
- 新規または編集中のREQまたはTECHは、レビューの後に`approved`へ変更し、`bitz check <ID>`を通す。
- `approved`のREQまたはTECHの意味を変更する場合は、変更と同じ作業で先に`draft`または`outdated`へ戻し、
  レビューの後に`approved`へ変更して`check`を再実行する。
- 設計レビュー（Design Review）は、依存、変更の境界、異常系、検証方法を確認する。
- レビューの結果はCoreへ保存せず、Git／PRへ記録する。
- 要求、依存、設定を変更した場合は、承認（Approval）の後の実装用のコンテキスト取得（Implement Context）を再度行う。

## 5. スパイク

スパイクは、本番の成果物と分離した実験である。

- 実験の目的、時間、隔離の範囲を定める。
- 結果、失敗、制約、採否を、REQ、TECH、ADR、Issueのいずれかへ短く反映する。
- スパイクの成果物をそのまま本番へマージしない。
- 採用する実装は、簡易フローまたは完全フローで作る。

プロファイルのタグ、専用の実行状態、ゲートのエンジンはCore 1.0に追加しない。

## 6. 事前検査

実装の開始には次を要求する。

- 起点IDが存在する。
- `context`の結果が、状態`passed`または`passed_with_warnings`であり、`resolution.complete: true`である。
- 規範強度が`MUST`の対象規範文が列挙されている。
- 変更予定のパスが、アダプターの作業計画に列挙されている。Coreによる境界の強制が必要な場合は、TASKの`changes`へ記録する。
- テストコマンドを解決できる。
- 既存のコミットしていない変更と衝突しない。
- TASKが起点の場合は、先行するTASKがすべて`done`である。
- 高リスクの変更では、完全フローを選択している。

## 7. 失敗と戻り先

| 原因 | 戻り先 | 自動再試行 |
|---|---|---:|
| コンパイル、リンター、単体テスト、TASK境界 | 実装 | 最大2回 |
| 一時的なツールの障害 | 同じ操作 | 冪等な1回 |
| 古くなったコンテキスト一式、依存または設計の不足 | コンテキスト取得 | 0回 |
| 要求・受入条件の問題 | 起点の特定 | 0回 |
| 権限、セキュリティ、費用、法令 | エスカレーション | 0回 |

エスカレーション（`Escalate`）は、人間の判断を待って止まる点であり、完了への遷移ではない。解消した後は、起点の特定、コンテキスト取得、
または中断した操作へ戻り、そこから実装前検査、実装後検査、検証、人手レビューを省略せずに再実行する。解消しなければ取り止める。

最終の人手レビューの否決は、自動再試行の回数へ含めない。人間が、起点の特定、コンテキスト取得、実装のいずれかの戻り先、
または取止め（withdrawal）を選び、完了へ直接進めない。

## 8. 取止め

完了の前は、人間の判断で取り止められる。`draft`のREQまたはTECHは`rejected`、`open`のTASKは`cancelled`へ変更できる。
理由は任意の`Notes`、ADR、Issue、コミットへ記録し、変更した後の`bitz check <ID>`を通してGitへ記録する。

Coreは取止めを推測せず、コードとテストの差分を削除しない。すでに`approved`のREQまたはTECHは`rejected`へ戻さず、
必要なら`outdated`と後継の判断で扱う。

## 9. 複合ワークスペースの横断作業

共通の要求が複数のワークスペースへ影響する場合、ルートワークスペースに共通のREQまたはADRを置き、各メンバーのREQまたはTECHが
修飾IDで具体化する。実装とテストは所有するメンバーへ置き、作業のTASKもメンバーごとに分ける。

1. 共通の要求について、目的`interpret`のコンテキスト一式をレビューする。
2. メンバーごとに、目的`implement`のコンテキスト取得、実装前検査、実装、実装後検査、検証を行う。
3. 横断するコンテキスト一式の到達先と、各メンバーの所有境界を、人手レビューで確認する。
4. 統合の前に、同じGitリポジトリのルート／ルートワークスペースを発見できるディレクトリで、`check --all-workspaces --base <統合先先端>`と
   `verify --all-workspaces`を実行する。

独立した複数のワークスペースを、1つの`context`のリクエストの複数の起点にせず、メンバーごとにリクエストを分ける。
全体操作は、1つのワークスペースだけで行うフローの人手レビューを代替しない。

## 10. 並行開発

Core 1.0は、専用の`Integrate`段階と自動の改番支援を持たない。作業ブランチを統合先へマージまたはリベースした後、
次を実施する。

1. `bitz check --full --base <統合先先端>`を実行する。
2. 同じワークスペースの中に重複するIDがあれば、人間が片方を当該ワークスペースの未使用のIDへ改番し、フロントマター、ファイル名、
   関係、`covers`、`addresses`を更新する。別のワークスペースにある同名のローカルIDは改番しない。
3. 同じ`check`を再実行する。
4. 通過した後に、通常のレビューとマージを行う。

Coreは、勝者、敗者、新しいIDを決めない。

## 11. 完了条件

- 対象規範文が特定されている。
- 書込みの直前のコンテキストのハッシュ値が一致している。
- `context`、実装の前後の`check`、`verify`がすべて通過状態である。
- 未テストの`MUST`の規範文が0件である。
- 必須のテストが実行され、成功している。
- 省略した事項と、証明していない事項が表示されている。
- 人間が最終差分を確認している。
- TASKが起点の場合は、`done`へ変更した後に最終の`check`が通過している。
- 完了の結果がGitへ記録されている。
- 複合ワークスペースの横断作業では、すべてのワークスペースの`check`と`verify`を集約した結果が、通過状態である。
