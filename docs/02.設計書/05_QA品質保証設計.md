# QA・品質保証設計

## 1. 品質目標

最小の待ち時間で、仕様の取り違え、依存漏れ、受入条件の実装・検証漏れを発見する。文書数を増やして
完全性を装うのではなく、強い依存の完全閉包と`MUST`句単位の実行可能な証拠を優先する。

## 2. Core 1.0の検証

| レベル | 内容 | 既定 |
|---|---|:--:|
| L0 Syntax/Schema | EARS-AI、Frontmatter、ID、必須項目 | 必須 |
| L1 Dependency/Trace | 型付き依存の完全閉包、句・実装・テスト対応 | 必須 |
| L3 Executable | 対象テストコマンドと終了結果 | 必須 |
| L2 Structural | 型、API、依存境界のAST比較 | 将来・任意 |
| L4 Operational | 性能、セキュリティ、復旧性 | プロジェクト側の既存ツールへ委譲 |

番号は概念上の互換性のため維持するが、L2を実装しなければL3を実行できないとは扱わない。

## 3. 判定根拠

| 根拠 | 合否への使用 |
|---|---|
| Parser、Schema、参照検査 | 使用する |
| テスト・Lint・型検査の終了コード | 使用する |
| 人間の承認 | 要求の意味と高リスク変更に使用する |
| LLMによる意味評価 | `advisory`のみ。単独では不通過にしない |

LLMが「要求を満たしている」と判断しても、テスト未実行なら`verify`成功と扱わない。
逆にLLMの推測だけで、正常な成果物を`failed`にしない。

## 4. `bitz check`

- 変更ファイルだけを既定対象にする。
- 変更集合は解決済みGit基準版からindex、worktree、未追跡かつ非ignore pathまでを含める。
- 文書IDと正引き・逆引き関係のFrontmatter索引は、変更範囲検査でも全SPECから構築する。
- L0は対象文書、L1は対象文書の強い依存閉包と直接の逆参照を検査する。
- 変更されたcode/test pathは`implements`・`tests[].path`の逆索引から所有REQ/TECHへ正規化し、
  未所有pathは対象外として件数だけを残す。
- モノレポでは連合全体の軽量修飾ID索引を作り、完全解析は変更workspace、強い依存閉包、直接の逆参照へ限定する。
- `--full`でリポジトリ全体を検査する。
- CIはPRのmerge-baseなど比較元を`--base`で明示し、承認保護と状態遷移をbranch全体で検査する。
- 成功時は件数、範囲、所要時間だけを出力する。

## 5. `bitz context`

- 強い依存を終端まで解決し、部分bundleを成功扱いしない。
- 同一入力から同じ文書集合、順序、Context Digestを返す。
- `draft`や`outdated`を規範文書へ混ぜず、advisoryまたは`blocked`として区別する。
- `MUST`句の未addressed・未testedを明示する。
- ネットワークとLLMを使用しない。

## 6. `bitz verify`

- 全`MUST`句に対応付けられたテストを実行する。
- Context Digest、対象規範文ID、テストコマンド、終了コード、所要時間を記録する。
- テスト対応が存在しない場合と実行環境がない場合は`blocked`とする。
- カバレッジ率だけを合格条件にしない。
- 内部helperだけを通るテストを、production入口の成立証明と同一視しない。
- 高リスクな境界は、REQまたはTECHの`Verification`節で実入口、異常系、未証明事項を明示する。
- 将来、mutation testingやholdout fixtureを追加できるが、Core 1.0では必須にしない。

## 7. レビューと職務分掌

個人開発では実装者とレビュー者が同一でもよい。数人チームでは高リスク変更だけ別の人へレビューを依頼する。

別Agentや別コンテキストによるレビューは補助機能であり、独立監査とは呼ばない。決定論的検査と
実行テストを通した上で、追加の観点を得る目的に限定する。

## 8. 例外

複雑なwaiver台帳は設けない。検査を意図的に通さない場合は、次をGit管理された文書またはコミット本文へ残す。

- 対象Diagnostic
- 理由
- 影響範囲
- 見直し条件または期限

同じ例外が3回以上現れた場合、ルールか設計が現実に合っていない兆候として見直す。

## 9. レポート

- 成功時はファイルを生成しない。
- `failed`、`blocked`、`error`では再現可能な最小JSONを自動保存する。
- `passed`と`passed_with_warnings`は`--report`指定時だけJSONを保存する。
- 引数不正ではレポートを保存しない。
- 秘密情報、環境変数の値、全文ログを保存しない。

## 10. 品質指標

ツール自身について次を測定する。

- `context`、`check`、`verify`の所要時間
- 意図的な依存欠落・句単位テスト欠落の検出率
- Diagnosticのfalse positive / false negative
- EARS-AI記述時間
- 人間レビュー時間
- 仕様漏れ・テスト漏れの検出数
- 通常Markdownまたは従来EARSとの比較

EARS-AIまたは追加検証が完了時間、欠陥率、レビュー負荷のいずれも改善しない場合、その機能を
既定経路へ追加しない。
