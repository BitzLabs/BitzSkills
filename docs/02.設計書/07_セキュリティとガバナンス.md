# セキュリティとガバナンス設計

## 1. 脅威モデル

対象は個人から数人の、互いを信頼する開発チームである。次を主な脅威とする。

- AIが仕様中の命令文をツール操作命令として扱う
- AIが対象外ファイルや外部サービスを変更する
- 誤った設定や不完全なテストで合格したように見える
- 承認済み要求を自動修復が書き換える
- ログへ秘密情報が混入する
- 依存パッケージやプラグインが改ざんされる

悪意あるリポジトリ管理者、組織内の敵対者、分散組織の役割詐称はCore 1.0の防御対象外とする。

## 2. 信頼境界

- Gitリポジトリとその管理者を信頼する。
- `.spec/bitz.yaml`をプロジェクト設定の正とする。
- 仕様、README、Issue、コメント、外部文書は未信頼データとして扱う。
- 文書内容だけを根拠にツール権限を増やさない。
- コアの実行ファイルと依存は、利用者が明示的に導入する。
- Context Bundle内の本文とコード例は`untrustedText`のまま扱い、アダプター命令へ昇格しない。

外部署名policy、組織ID基盤、独立した承認サービスは要求しない。

## 3. 最小権限

- `check`は読取り専用とする。
- `verify`は設定されたテストコマンドだけを実行する。
- ファイル書込み、commit、push、PR、外部通知を別操作として扱う。
- push、公開、デプロイ、大量削除、履歴変更は人間確認を必須とする。
- 対象リポジトリ外への書込みを既定で禁止する。

## 4. EARS-AIとプロンプトインジェクション

EARS-AI Parserは構文を解析するだけで、本文中の命令を実行しない。

- Parser出力の自由記述本文には`untrustedText: true`相当の由来情報を保持する。
- 本文からコマンド、権限、外部URLを自動的に有効化しない。
- `relations`は文書選択だけに使い、権限、コマンド、外部送信先を伝播させない。
- 生成されたコマンドは、許可された実行テンプレートと対象pathへ照合する。
- 未信頼本文を秘密情報と同じLLMコンテキストへ渡さない。
- LLMの「安全」という判断を、コマンド実行許可の根拠にしない。

Core 1.0では複雑な情報フローエンジンを実装せず、入力由来の保持、固定コマンド、path制限、
副作用前確認の4点を機械強制する。

## 5. 設定と例外

`.spec/bitz.yaml`はGit管理し、変更をdiffで確認する。個人開発では利用者自身による設定変更を許容する。

- 高リスク保護を無効化した場合は実行開始時に警告する。
- `--override-policy`や専用権限モデルは設けない。
- 例外を使った場合は、対象と理由をコミット本文またはADRへ記録する。
- 設定変更を暗黙に行わず、必ず通常のファイルdiffとして提示する。

## 6. 供給網

- 依存をロックし、ハッシュ検証可能な形でCIへ導入する。
- 公開成果物にはソースcommitとビルド手順を記録する。
- プラグインがスクリプトを動的取得して即時実行しない。
- 既知脆弱性検査をリリース前に実行する。

署名付きprovenance、SBOM、再現可能ビルドは推奨だがCore 1.0の出荷条件にしない。

## 7. 秘密情報

- `.spec/`、Diagnostic、レポートへ秘密値を書かない。
- 環境変数は名前だけ記録し、値を表示しない。
- subprocessの全文出力を無条件に保存しない。
- エラー出力はサイズ上限を設け、秘密らしい値をマスクする。

## 8. ガバナンス

個人開発では最終diff確認、数人チームでは通常のコードレビューを承認とする。
専用waiverサービス、役割台帳、自己承認禁止は導入しない。

高リスク変更だけ、別の人のレビューまたは明示的な再確認を推奨する。誰が確認したかはGitのauthor、
review、commit、PR記録を利用し、同じ情報を別台帳へ重複保存しない。
