# 共通アーキテクチャ設計

## 1. 適用範囲

本書は、個人から数人の開発チーム向けBitz AI-SDDの軽量コア、EARS-AI、薄いAI CLI統合、
および`.spec/`との関係を定義する。

## 2. 論理構成

```text
Claude CLI / Copilot CLI / Codex CLI / その他クライアント
                |
   bitz-sdd / quality / ddd / sync Skills
                |
       bitz-core Plugin (MCP / CLI)
   +-------------+-------------+-------------+
   |             |             |             |
EARS-AI       context        check          verify
Parser     graph/bundle   schema/trace    test runner
   \             |             |             /
                .spec/
                  |
          対象コードとGit
```

`bitz-core`は単一の実行パッケージとし、次を所有する。

- EARS-AI Parser、Semantic IR（AST互換名）、Canonical Serializer
- `.spec/`のSchema、ID、型付き依存、静的トレース検査
- Gitモノレポ内の明示的なSPECワークスペース連合、修飾ID、所有境界
- 強い依存の完全閉包、Constraint Ledger、段階的Context Projection、Context Digest
- テストコマンド実行と結果の対応付け
- 共通Diagnosticと終了コード
- 設定読込み、安全なファイル更新、任意キャッシュ

AI CLI別プラグインは、コアを呼び出して結果を説明する薄い層に限定する。品質判定、
EARS-AI解釈、状態遷移規則を自然言語スキル内へ複製しない。

配布は[ADR-016](10_決定記録/ADR-016_Agent-Plugins準拠の複数プラグイン配布.md)に従い、GitHubで
ホストするマーケットプレイスから複数のAgent Plugins 1.0.0準拠パッケージとして行う。`bitz-core`を
必須とし、`bitz-sdd`、`bitz-quality`、`bitz-ddd`、`bitz-sync`は必要なものだけを導入する。
拡張は`bitz-core`の公開MCP契約だけに依存し、拡張同士を必須依存させない。

## 3. EARS-AIの位置づけ

EARS-AIは`bitz-core`の主要な入力言語であり、本製品の中心機能である。

```text
EARS-AI文書 --Parser--> Semantic IR --Validator--> Diagnostic
                              |
                              +--> 完全依存解決 --> Constraint Ledger
                              |                         |
                              |                  段階的Projection --> AI
                              +--> 要求・コード・テストのトレース
```

ParserとValidatorは、同一入力・同一バージョンに対して同一結果を返す。自由記述本文の意味解釈は
Parserの保証外であり、AIによる評価は`advisory`として扱う。合否を決める根拠は、機械検査、
実行したテスト、人間の確認のいずれかを明示する。

## 4. 基本操作

### 4.1 `bitz context`

- 起点SPECまたは規範文から強い依存を完全に解決する
- 解釈、実装、検証のpurpose別に、全必須制約と段階的Projectionを持つContext Bundleを返す
- 起点と直接作業資料は全文、間接制約はSemantic IR、背景・advisoryは参照として提示する
- 必要な参照は同じ解決集合から明示的に展開し、Context Digestの意味を変えない
- `MUST`句のTASK・テスト対応漏れを表示する
- Context Digestの再照合で古い文脈に基づく編集を停止する
- モノレポでは修飾された強い依存だけをworkspace境界越しに解決し、無関係なworkspaceを提示しない

参照切れ・型違反・循環は`failed`、上限超過・適用不能状態・Digest不一致は`blocked`とし、
いずれも部分解決を成功扱いしない。Projectionによる原文省略は部分解決ではない。

### 4.2 `bitz check`

- EARS-AI構文とCore語彙
- Frontmatterと配置
- ID重複、型付き関係の参照切れ・型違反・循環
- EARS-AI句からコード・テストへの静的トレース
- 変更された仕様と後続成果物の`outdated`候補
- モノレポ連合カタログ、workspace修飾ID、横断関係、所有パス

既定ではGit差分から変更範囲を求める。Gitがない場合、対象指定または全体検査へ縮退する。

### 4.3 `bitz verify`

- Contextを再解決し、全`MUST`句のテスト対応を確認する
- 対象要求に対応するテストコマンドを解決する
- subprocessとして実行し、終了コードと要約を保存する
- 要求ID、テスト、実行結果を対応付ける
- LLMを使わずに完結できる
- `--all-workspaces`ではworkspaceごとのコマンドを混合せず、結果だけを集約する

LLMによる不足テストや過剰実装の推定は、明示オプションで実行する提案機能とする。

### 4.4 `bitz doctor`

- コア版、Python版、設定、`.spec/`構造
- 未知キー、壊れたキャッシュ、実行不能なテストコマンド
- EARS-AI Core/Profile版の互換性
- 呼出し元プラグインの版、要求Core API、要求Capabilityの互換性
- モノレポ連合のmember、workspace ID、Schema/EARS-AI互換性、所有境界
- 不適合時の`blocked`と、プラグインまたは実行体の具体的な導入・更新手順

## 5. 共通結果形式

```json
{
  "schemaVersion": "1.0",
  "operation": "check",
  "status": "passed_with_warnings",
  "scope": "changed",
  "workspace": {"id": "web", "path": "apps/web"},
  "durationMs": 184,
  "diagnostics": []
}
```

通常実行では成功時に1行だけ表示する。JSONと詳細レポートは`--format json`または`--report`で生成する。

| status | 意味 | 終了コード |
|---|---|---:|
| `passed` | 問題なし | 0 |
| `passed_with_warnings` | 警告のみ | 0 |
| `failed` | 成果物が不適合 | 1 |
| `blocked` | 前提不足 | 2 |
| `error` | ツール障害 | 3 |

引数不正は終了コード4とする。設定上書き専用の終了コードは設けない。設定の構文、型、必須項目の
不正は`error`、正しい形式だが未対応のSchema majorは`blocked`として扱う。

## 6. Diagnostic

```json
{
  "code": "EAI-CORE-SYNTAX-001",
  "severity": "error",
  "summary": "規範文にMUST/SHOULD/MAYがありません",
  "source": {"path": ".spec/requirements/REQ-001.md", "line": 24},
  "specRefs": ["REQ-001:AC-02"],
  "evidence": "modality tag not found",
  "suggestedAction": "規範強度を追加してください"
}
```

必須フィールドは`code`、`severity`、`summary`、`source`だけとする。証跡や提案は必要な場合だけ付与し、
スキーマを肥大化させない。プラグイン固有情報は`extensions.<plugin-id>`へ格納する。所有者とコード形式は
[ADR-011](10_決定記録/ADR-011_Diagnostic所有者とコード命名規約.md)を正とする。

## 7. 性能と処理量の制約

- `bitz check`の通常目標は1秒以内、基準リポジトリの全体検査は5秒以内とする。
- 20文書・128 KiB以下の`bitz context`は1秒以内を目標とする。
- 既定でネットワークとLLMを使用しない。
- 変更範囲検査を既定とし、全体検査は`--full`またはCIで実行する。
- キャッシュは任意で、削除しても正本から再構築できる。
- 成功runの詳細ログを恒久保存しない。
- 並列処理は測定で効果が確認できるまで導入しない。

性能目標は[運用設計](06_運用設計.md)の基準リポジトリ規模に適用する。リソースhard limit近傍の
性能は保証しない。変更範囲検査でも関係の逆参照に必要な全SPECの軽量Frontmatter索引は構築する。

## 8. 拡張境界

Core 1.0ではEARS-AI Core、Context Resolution、L0 Schema、L1 Static Trace、対象テスト実行に集中する。
多言語AST比較、LLM意味監査、運用監査、DDD、自動逆同期はオプションまたは将来機能とする。
追加機能は、実タスクで完了時間または欠陥率を改善した場合だけ既定経路へ昇格できる。

機能拡張は独立したAgent Pluginとして提供する。移植可能な構成要素はSkillsとMCP serversに限定し、
クライアント固有のagents、commands、hooksはreverse-domain namespaceへ隔離する。別プラグインの
インストール先やファイルを実行時に参照せず、機械判定が必要な処理はCoreの公開Capabilityへ追加するか、
当該拡張自身の自己完結MCP serverとして提供する。
