# ADR-072 承認済みの契約の保護をTECHへ広げ、途中のコミットの状態で再承認を判定する

## Context

承認済み要求の保護（[文書・フロントマター・状態仕様](../../03.詳細設計/02_仕様文書モデル/02_文書・フロントマター・状態仕様.md) §8）は、
基準版の`approved`のREQと現在版を比べ、意味を変えながら`status`を`draft`または`outdated`へ戻していない場合を
`SPEC-SAFETY-APPROVED-001`（`failed`）とする。[提案34](../../04.提案資料/34_Coreと評価処理の現状整理と今後の方向性.md) §9.1の
実測で、次の2つを確かめた。

1. [SDDフロー](../03_SDDフロー.md)は、承認済みの契約の意味を変えるとき「変更と同じ作業で先に`draft`または`outdated`へ戻し、
   レビューの後に`approved`へ変更する」と定め、統合の前に`bitz check --full --base <統合先先端>`を実行すると定める。
   手順どおりに`draft`の状態をコミットしてから再承認しても、統合の前の`check`は`failed`になる。保護が基準版と現在版の2つの端点だけを比べ、
   途中のコミットを見ないためである。
2. `approved`のTECHの規範文を`approved`のまま変えても、診断は1件も出ない。`AGENTS.md`、SDDフロー、
   [ユースケース](../05_ユースケース.md)は、REQとTECHの両方について状態を戻すことを求めている。TECHを保護から外した理由を書いた決定記録はない。
   TECHの規範文は、`verify`が試験のない`MUST`を`blocked`にし、TASKが`addresses`できる点で、REQの規範文と同じ効力を持つ。

## Decision

1. **対象**。保護の対象を、基準版で`approved`のREQとTECHとする。比べる項目は今と同じ（`title`、規範文の意味フィールド、
   強い関係。規範文の追加、削除、`id`の変更を含む）とする。規範文のないTECHは、`title`と強い関係だけを比べる。
   基準版に存在しない新規の文書は、今と同じく比較の対象外とする。
2. **途中の状態**。基準版と現在版がどちらも`approved`で、1.の意味が変わっている文書について、`HEAD`から到達でき、基準版から到達できない
   コミットのうち少なくとも1つで、同じIDの文書の`status`が`draft`または`outdated`であれば、保護の違反としない。
3. **途中の状態として認める版**。コミットされた版だけとする。インデックスと作業ツリーの内容は現在版であり、途中の状態としない。
   基準版が`HEAD`と同じ場合は、途中のコミットがないので、今と同じ結果になる。IDを読めない版は、`draft`または`outdated`の版としない。
4. **文書の対応付け**。途中のコミットの文書は、基準版と現在版の対応付けと同じくIDで対応付ける。パスだけの変更は同じ文書とする。
5. **履歴を読む範囲**。途中のコミットを読むのは、端点の比較で違反になった文書がある場合だけとする。
6. **履歴を読めない場合**。浅いクローンなどで2.のコミットの集合を完全に得られないと判定した場合は、違反のままとする。
   診断の文言で、途中のコミットを読めなかったことを伝える。
7. **診断と設定**。診断コードは`SPEC-SAFETY-APPROVED-001`、重大度`error`、結果への効果`failed`のままとする。文言はREQとTECHの両方を表すよう改める。
   設定のキー`safety.protectApprovedRequirements`の名前と既定値は変えず、説明を「承認済みのREQとTECHの保護」に改める。
8. **変えないもの**。影響候補（`SPEC-IMPACT-OUTDATED-001`）、状態遷移（`SPEC-STATE-TRANSITION-001`）、削除の検出、
   複合ワークスペースで保護を作業ワークスペースの文書だけに行う規則は変えない。`accepted`のADRの本文は、保護の対象にしない。

## Consequences

- SDDフローに書かれた手順（同じ作業の中で`draft`へ戻し、再承認する）が、統合の前の`check`を通る。
- `approved`のTECHの意味を、状態を戻さずに変えると`failed`になる。今は通っている変更が`failed`になるので、Core 1.0の確定の前に入れる。
- `check`が、違反の候補がある場合に限り、基準版から`HEAD`までの履歴を読む。違反の候補がなければ、Gitの呼出しは増えない。
- Coreは、状態を戻して承認した主体を確かめない（ADR-024の`Decision`の3番目の項目のとおり）。保護が保証するのは、承認済みの契約の意味の変更が、
  状態の変更としてGitの履歴に残ることである。エージェントが2つのコミットを自分で作ることは防げない。人による確認は、レビューで行う。
- 仕様（文書・フロントマター・状態仕様 §8、`check`仕様、診断レジストリ、ワークスペース・設定仕様）と、SDDフロー、運用手順、ユースケースの記述を改める。
- 複数のコミットを持つ適合fixtureと、TECHを対象にした適合fixtureを追加する。既存のfixtureのうち、TECHの意味の変更を通過としているものがあれば、期待値を改める。
  fixtureの変更に伴い、Gate Aを再認定する（ADR-051）。

## Alternatives

1. **2つのPRに分ける**: `draft`へ戻す変更と再承認を別のPRにする。Coreを変えないが、2つのPRの間、統合先の契約が`draft`になり、
   その契約に依存する作業の実装用の`context`が`blocked`になる。採らない（ユーザーの決定）。
2. **フロントマターに意味の版を加える**: 端点の比較だけで判定できるが、`draft`を経ないので、人の確認の前に実装へ進めてしまう。
   状態の遷移で意味の変更を表すADR-024の考え方から外れる。採らない。
3. **基準版を指定した`check`では保護しない**: 統合の前に、状態を戻さない意味の変更を検出できなくなる。採らない。
4. **TECHは保護せず、文書の記述をREQだけに改める**: 技術契約を、状態を戻さずに書き換えても検出できない状態が残る。採らない（ユーザーの決定）。
5. **TECHの意味の変更を`warning`にする**: 終了コードを変えないので、統合の前の検査で止まらない。REQと扱いを分ける根拠がない。採らない。
