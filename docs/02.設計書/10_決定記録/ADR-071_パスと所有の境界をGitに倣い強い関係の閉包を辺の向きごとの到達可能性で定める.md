# ADR-071 パスと所有の境界をGitに倣い、強い関係の閉包を辺の向きごとの到達可能性で定める

## Context

実装の確認事項を直す中で、パスの扱いと閉包の規則に、原則のない例外が積み重なっていた。

- **パスと所有**
  - [ADR-042](ADR-042_複合ワークスペースの同一性・所有境界・公開契約を確定する.md)の`Decision`の5番目の項目は、存在する上位のディレクトリのシンボリックリンクを解決し、
    実際のパスで境界を照合し、コード、テスト、TASK、`cwd`は、同じ所有領域内へ解決するシンボリックリンクだけを許すとした。
  - [複合ワークスペース仕様](../../03.詳細設計/02_仕様文書モデル/05_複合ワークスペース仕様.md) §5.1は、大文字と小文字、Unicodeの正規化の扱いを、
    ファイルシステムの同一性（デバイスとiノード）に従わせた。大文字と小文字を区別しないファイルシステムでは、同じ入力でも環境ごとに結果が変わり得る。
  - TASKの`changes`の所有の判定は、シンボリックリンクのエントリをリンク先へ解決する。基準版はGitのツリーオブジェクトのリンク先の文字列から、
    現在版は`lstat`から、と別の方法で解決しており、2つの結果が一致する保証がない（複合ワークスペース仕様 §5.2）。
  - 単一ワークスペースは、ルートの中を指す末端のシンボリックリンクを「存在しない」と扱い、複合ワークスペースは自分の領域の中を指すリンクを受け付ける（C109）。
  - §5.1の手順6（Gitの境界）は実装されていない（C90）。
- **閉包**
  - [関係・トレースモデル](../../03.詳細設計/02_仕様文書モデル/04_関係・トレースモデル.md) §6.1は、`requires`を終端まで辿る一方で、
    起点の`refines`の参照先は1段だけ含め、その参照先の`requires`を辿らない。
  - 具体化文書（起点を`refines`する文書）からは`requires`だけを辿り、具体化文書が別の文書を`refines`していても、その先を含めない。
  - 状態`draft`の文書を役割`advisory`として示す規則（§6.1の6.）だけは、起点からではなく閉包のすべての文書から1段下を辿る。
  - TASKを起点とする`implement`の閉包（§6.2「起点のTASKの`addresses`と`requires`の閉包」）は2通りに読め、Coreは`addresses`の先の所有文書に§6.1を適用しない読みで実装している。
    `verify`は適用するので、同じTASKでも2つの目的で閉包が食い違う（C106）。
  - 参照計算（適合fixtureの期待値の生成）の一部に、§6.1の3.を含めない欠けがある（C107）。

ユーザーは、フォルダと複合ワークスペースの考え方はGitを参考にし、関係（リンク）の考え方は循環のない有向グラフとすることを求めた（2026-11-08）。
強い関係の循環は、§4ですでに禁止している（`requires`と`refines`を合わせた依存グラフ、`supersedes`の連鎖、TASKどうしの`requires`）。`related`の循環は許し、探索しない。

## Decision

### 1. パスと所有の境界はGitに倣う

1. **シンボリックリンクを辿らない**。Gitがシンボリックリンクを辿らずにリンクそのもの（リンク先の文字列を内容とするエントリ）として記録するのと同じく、
   Coreは、仕様文書のパス、仕様文書が宣言するパス（`implements`、`tests[].path`、TASKの`changes`）、設定が宣言するパス（`cwd`、メンバーのパス）を、
   シンボリックリンクを辿らずに扱う（ユーザーの決定）。パスのセグメントは、そのパスの基準となるルート（ワークスペースのルート、複合ワークスペースのルート）から数える。
   - 途中のセグメントがシンボリックリンクであるパスは拒否する。Gitが、シンボリックリンクの先にあるパスを追加しないのと同じである。
   - 末端がシンボリックリンクであるパスは、通常のファイルとしても、ディレクトリとしても扱わない。`implements`と`tests[].path`の
     「通常のファイルとして存在する」を満たさず、`cwd`のディレクトリとしても使えない。
   - TASKの`changes`の差分に現れたシンボリックリンクのエントリは、そのエントリ自身の字句のパスだけで、許可と所有を判定する。リンク先は判定に使わない（ユーザーの決定）。
     Coreはどこでもリンクを辿らないので、別の所有領域を指すリンクがあっても、その領域の実体を読み書きしたことにはならない。
   - 単一ワークスペースと複合ワークスペースで同じ規則とする（C109の解決）。
   - 複合ワークスペースの探索の開始位置（複合ワークスペース仕様 §2.1）は、利用者のディレクトリであって宣言したパスではないので、本ADRの範囲外とし、今の規則を変えない。
2. **パスは文字列で厳密に比べる**。Gitの既定（`core.ignorecase=false`）と同じく、パスは、セグメントごとにコードポイントの完全一致で比べ、大文字と小文字を区別する（ユーザーの決定）。
   - 比べる前に、宣言したパスとディレクトリの項目名をどちらもUnicode NFCへ正規化する（ユーザーの決定）。全体の規則（安全な入出力・互換性 §1）と、
     除外のパスの比べ方（複合ワークスペース仕様 §2.1）と同じであり、ファイル名をNFDで返すファイルシステムでも結果が変わらない
     （macOSのGitの既定`core.precomposeunicode=true`と同じ効果）。
   - 存在の検査は、各セグメントが、親のディレクトリの項目名と、上の比べ方で一致することで確かめる。大文字と小文字を区別しない
     ファイルシステムが別の綴りのパスを開けても、存在するとはみなさない。
   - 所有の判定は、正規化した字句のパスのセグメント単位の包含で行う。1.でシンボリックリンクを拒否し、2.で別の綴りによる別名を拒否するので、
     実際のパスとファイルシステムの同一性（デバイスとiノード）による比較は使わない。
   - こうして、同じ入力に対して、LinuxとmacOS、大文字と小文字を区別するかどうかによらず、同じ結果になる。
3. **Gitの境界を所有の境界とする**。サブモジュールの内部と、入れ子のリポジトリまたはワークツリーの内部は、Gitが親のリポジトリの内容として追跡しないので、
   単一ワークスペースと複合ワークスペースのどちらでも、所有領域に含めない（C90の手順6の解決）。Gitが無視するパス（`.gitignore`）は、
   親のリポジトリの作業ツリーにあるので、この規則の対象にしない。
4. **ADR-042の部分改訂**。本ADRは、ADR-042の`Decision`の5番目の項目のうち、「存在する上位のディレクトリのシンボリックリンクを解決し」、
   「実際のパスについて」の照合、「コード、テスト、TASK、`cwd`は、同じ所有領域内へ解決するシンボリックリンクだけを許す」を、上の1.〜3.のとおり部分改訂する。
   すべての所有パスに同じ手順を使うこと、Gitのメタデータとパスのセグメント単位の包含で境界を照合すること、ワークスペースの設定経路とメンバーのルートのシンボリックリンクの禁止は変えない。
   ADR-042のほかの`Decision`の項目は変えない。ADR-042の`Alternatives`の4番目（字句上のパスだけで判定する案を採らない）の理由は、本ADRの1.と2.で塞ぐ。
5. **ADR-043の部分改訂**。本ADRは、[ADR-043](ADR-043_複合ワークスペースの継続・TASK境界・適合契約を確定する.md)の`Decision`の4番目の項目のうち、
   「宣言したパスと変更パスの所有の判定は別に行い」の所有の判定で、シンボリックリンクのエントリをリンク先へ解決すること（ADR-043の`Context`の理由による）を、上の1.のとおり部分改訂する。
   許可を字句のパスで判定し、シンボリックリンクの解決先へ許可を拡張しないこと、所有の判定を許可と別に行うこと、追加、削除、変更、リネームの扱いは変えない。
   ADR-043のほかの`Decision`の項目は変えない。

### 2. 強い関係の閉包を、辺の向きごとの到達可能性で定める

閉包は、起点から「下方向」へ具体化を辿り、そこから「上方向」へ依存をすべて辿って得る。

1. **上方向（依存）**。文書から、`requires`、`refines`、`addresses`の参照先を、辺の種類を区別せず終端まで辿る（ユーザーの決定）。
   - §6.1の3.の「`refines`の参照先は1段だけで、その参照先の`requires`は辿らない」をやめる。
   - 具体化文書から`requires`だけを辿る例外もやめ、具体化文書も上方向のすべての辺を辿る。
   - `supersedes`と`related`は上方向の辺に含めない。置換済みの起点の扱い（§6.1の5.）は変えない。
2. **下方向（具体化）**。下方向の出発点の文書から、`refines`を逆向きに終端まで辿る。出発点は、REQ、TECH、ADRを起点にしたときは起点文書、
   規範文を起点にしたときはその所有文書、TASKを起点にしたときは4.による文書とし、上方向で着いた文書からは逆向きに辿らない（ユーザーの決定、今と同じ）。
   出発点の文書またはそのいずれかの規範文を`refines`する適用可能な文書が対象であり、今の§6.1の4.と同じ範囲である。
   対象規範文の展開（§6.4の規則1〜3。規範文を起点にしたときに文書IDの`refines`を辿らないことを含む）は、この閉包の範囲とは別の規則であり、変えない。
3. **閉包**。下方向の出発点の文書と、2.で得た具体化文書の集合をSとすると、閉包はSと、Sの上方向の閉包の和集合とする。
   - 状態`draft`の文書を役割`advisory`として示すのは、Sの文書またはその規範文を`refines`する`draft`の文書だけとする（ユーザーの決定）。
     §6.1の6.の「閉包内の適用可能な文書」から辿る規則を改め、例外をなくす。`advisory`の文書は規範として適用せず、その文書からは辿らない。
4. **TASKを起点とする場合**（ユーザーの決定、C106の解決）。
   - 起点のTASKは起点文書であり、距離0、役割`root`とする。TASKからは`addresses`の辺を辿り、その参照先の所有文書を距離1とし、下方向の出発点とする。
     `implement`と`verify`と`interpret`のすべてで、その出発点に2.と3.を適用する。
   - 起点のTASKの`requires`は、目的ごとに次のとおり扱う。

     | 目的 | 起点のTASKの`requires` |
     |---|---|
     | `interpret` | 上方向の辺として辿り、閉包に含める |
     | `implement` | 上方向の辺として辿り、閉包に含める |
     | `verify` | 閉包（コンテキスト）に含めない。同じ上方向の範囲の文書（TASKとADRを除く）に、適用可能性の検査だけを行う |

   - 上方向には`addresses`を含むので、起点のTASKが`requires`する先行TASKの`addresses`の参照先とその上方向の閉包も、`interpret`と`implement`の閉包に含める。
     ただし対象規範文（§6.4の`targetStatements`）には加えない（§6.4の規則4を変えない）。
   - 先行TASKの状態の検査（ADR-029、ADR-036）は、今どおり、起点のTASKの`requires`が直接指すTASKだけとする。
   - TASKを起点とする`implement`には、対象規範文を`addresses`するほかの状態`open`のTASKを加えない（今と同じ）。
5. **REQ、TECH、規範文を起点とする`implement`**。対象規範文を`addresses`する状態`open`のTASKは今どおり閉包に含め、役割`work`とする。
   そのTASKはSに入れず、そのTASKからは辿らない。
6. **役割と距離**。
   - 距離は、閉包を作るときに辿った辺1本を1段とした、起点からの最短の段数とする（§7の定義を変えない）。
   - 役割は、§7の表の上から最初に当てはまるものとし、`refinement`は「具体化文書と、`refines`の辺で上方向に着いた文書」、
     `requirement`と`constraint`は「`requires`または`addresses`の辺で上方向に着いた文書」と改める（ユーザーの決定）。
7. **変えないもの**: 強い関係の循環の禁止（§4）、対象規範文の展開（§6.4）、決定論的な並び順（§7）、閉包の上限（`context` §8）、
   状態と閉包の規則（§10。適用可能でない文書を強い関係が要求すれば閉包全体を`blocked`とする）。
8. **既存のADRとの関係**。今の閉包の規則は、主に関係・トレースモデル §6が定めており、本節はその規範を改める。
   [ADR-010](ADR-010_型付き依存とコンテキストの解決の中核化.md)の`Decision`の2番目の項目（強い関係の完全な閉包をローカル・非LLMで解決する）、
   [ADR-023](ADR-023_verifyの明示対象とパスによる入力の確定.md)の`Decision`の6番目の項目（TASKは`addresses`の規範文と`requires`の閉包を対象とする）、
   [ADR-034](ADR-034_TASKの完了終端とdoneのTASKを起点とする操作の確定.md)の`Decision`の5番目の項目（`addresses`の参照先と`requires`の閉包に適用可能性の検査を行う）は、
   本節の閉包にもそのまま当たるので、文言を変えない。

### 3. 規範と実装の移行

1. 本ADRは原則を定める。規範の書き直し、Coreの実装、適合fixtureの変更は、関心事ごとの後続のPRで行う。
   1つ目は閉包、2つ目はシンボリックリンクと厳密な比較、3つ目はGitの境界である。書き直す規範は次のとおりである。
   - 関係・トレースモデル §6、§7
   - `context`仕様 §5（役割と距離による提示）
   - 複合ワークスペース仕様 §5.1、§5.2
   - ワークスペース・設定仕様
   - 安全な入出力・互換性 §6
   - `check`仕様と`verify`仕様の該当箇所
   - 用語集（閉包、役割、距離、具体化文書）
   - 適合fixture仕様
   - 参照計算（C107も、このときに本ADRの定義に合わせて解く）
2. 既存の適合fixtureの期待値が変わるものは、ADR-051の期待値の訂正、または削除・緩和（`MULTI-010`のように`failed`が`passed`になるもの）として扱う。
   根拠は本ADRと書き直した規範文とし、PRごとに管理者の承認を得る。
3. 新しい診断と出力の文言が要る場合は、ADR-062に従い、後続のPRでユーザーの承認を得る。
4. 後続のPRが終わるまでは、今の規範とCoreの挙動がそのまま有効である。

## Consequences

- パスの扱いが作業ツリーと基準版（Gitのツリー）で揃い、シンボリックリンクの解決の方法の違いで、`check --base`の所有の判定が食い違わない。
- 同じ入力に対して、LinuxとmacOS、大文字と小文字を区別するかどうかによらず、同じ結果になる。複合ワークスペース仕様 §5.1の手順5の、
  macOSの大文字と小文字を区別しないファイルシステムでの動作を検証済みとしないという注記は、要らなくなる。macOS全体を検証済みとしないこと（ADR-055）は変わらない。
- シンボリックリンクでコードやテストを共有している利用者は、その構成を使えなくなる。
- 閉包は、親のREQが`requires`する前提や、具体化文書が`refines`する別の文書を含むようになり、今より広がる。
  - 閉包の上限に当たりやすくなる。
  - 上方向で着いた文書が適用可能でない（`draft`の親など）と、閉包全体が`blocked`になる場合が増える（§10）。
  - 複合ワークスペースで、閉包が届く他のワークスペースの文書と、その検査の範囲も広がる。
- 一方で、`draft`の`advisory`を含め、どの文書が閉包に入るかを、下方向の出発点、下方向、上方向の3つで説明できる。
- `implement`と`verify`と`interpret`で、TASKを起点とする閉包の作り方が一致する（`requires`の扱いを除く）。
- 文書IDの重複の候補を、閉包と同じ到達可能性で絞り込める（C112の解決の前提）。
- 閉包とシンボリックリンクの変更は、承認済みの規範の意味の変更であり、既存の適合fixtureの期待値の訂正と緩和を伴う。

## Alternatives

1. **シンボリックリンクを解決し、所有領域の中なら許す（ADR-042の今の規則）**: 作業ツリーと基準版で解決の方法が違い、単一と複合でも扱いが食い違っていた。採らない（ユーザーの決定）。
2. **Gitの設定（`core.ignorecase`、`core.precomposeunicode`）に従って比べる**: Gitの挙動には忠実だが、同じ入力でも環境ごとに結果が変わる。採らない（ユーザーの決定）。
3. **ファイルシステムの同一性で比べる（今の規則）**: 大文字と小文字を区別しないファイルシステムで、違う綴りのパスが同じファイルになり、環境ごとに結果が変わる。採らない（ユーザーの決定）。
4. **Unicodeの正規化をせずに比べる**: 全体のNFCの規則と除外の比べ方を改める必要があり、ファイル名をNFDで返すファイルシステムでは、NFCで書いたパスが存在しない扱いになる。採らない（ユーザーの決定）。
5. **TASKの`changes`のシンボリックリンクのエントリの所有を、リンク先で判定し続ける**: 「辿らない」の原則に例外が残る。Coreがリンクを辿らない以上、リンク先の所有は迂回の経路にならない。採らない（ユーザーの決定）。
6. **閉包の挙動を変えず、今の規則を辺の種類ごとの表に書き直すだけにする**: 例外が残り、C106のような食い違いを原則から判断できない。採らない（ユーザーの決定）。
7. **上方向で`refines`は1段のままにする**: 例外が1つ残る。採らない（ユーザーの決定）。
8. **下方向を閉包のすべての文書から辿る**: 共通のREQを多くの文書が`refines`する構成で、関係のない兄弟の文書まで閉包に入り、閉包が大きく広がる。採らない（ユーザーの決定）。
9. **`draft`の`advisory`を、今どおり閉包のすべての文書から1段下を辿って示す**: 上方向が広がる分だけ`advisory`の文書が増え、下方向の原則に例外が残る。採らない（ユーザーの決定）。
10. **TASKを起点とする`verify`も、`requires`の閉包をコンテキストへ含める**: `requires`の閉包には適用可能性の検査だけを行う扱い（関係・トレースモデル §6.3、ADR-034）を変える。採らない（ユーザーの決定）。
