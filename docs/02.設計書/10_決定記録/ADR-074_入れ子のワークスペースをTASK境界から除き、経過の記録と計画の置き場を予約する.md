# ADR-074 入れ子のワークスペースをTASK境界から除き、経過の記録と計画の置き場を予約する

## Context

利用者は、本体と関係のない検証を`sandbox/`の下のディレクトリで、仕様文書を作って行い、結果を残したいと考えている
（[提案34](../../04.提案資料/34_Coreと評価処理の現状整理と今後の方向性.md) §12.4）。あわせて、ロードマップ（§12.2）と途中の経過の記録（§12.3）を
仕様文書として持つことを、Core 1.0の後に加える予定である。実測で次を確かめた。

1. 単一ワークスペースの下位に`.spec/bitz.yaml`を持つディレクトリ（入れ子のワークスペース）を置くと、その中で実行した`bitz`は、
   そこを独立のワークスペースとして扱う。外側のワークスペースの`doctor`と`check --full`も通る。
2. 入れ子のワークスペースの配下を変更している間に、外側で`check <TASK>`を実行すると、その変更がTASKの境界の外として
   `SPEC-TASK-BOUNDARY-001`（`failed`）になる。
3. `.spec/`の中の未知のディレクトリは`SPEC-WORKSPACE-UNKNOWN-001`（`warning`）になる。

[`check`仕様](../../03.詳細設計/03_操作仕様/02_check.md) §7は、リポジトリのルートがワークスペースのルートより上にある場合、
ワークスペースの外の変更をTASK境界の比較の対象から除く。入れ子のワークスペースの配下は別のワークスペースの範囲であり、同じ考え方を当てられる。
複合ワークスペースでは、登録していない設定は全体事前検査で止まり、除く範囲は`multiWorkspace.exclude`で宣言する（ADR-064）。

2.と3.を後から変えると、`check`の結果が変わる。Core 1.0の確定の前に入れる。

## Decision

1. **入れ子のワークスペース**。単一ワークスペースで、作業ワークスペースのルートの下位にあり、現在版または基準版で`.spec/bitz.yaml`を持つ
   ディレクトリを、入れ子のワークスペースのルートとする。作業ワークスペース自身のルートは含めない。
2. **TASK境界**。単一ワークスペースのTASK境界は、入れ子のワークスペースのルートとその配下の変更を、比較の対象から除く。
   TASKの`changes`が入れ子のワークスペースの配下を指す場合の扱いは、仕様の改訂で定める。
3. **複合ワークスペース**。複合ワークスペースの規則は変えない。登録していない設定の扱いと、`multiWorkspace.exclude`による除外は今のままとする。
4. **予約するディレクトリ**。`.spec/journal/`と`.spec/plans/`を予約する。Core 1.0は、この2つのディレクトリとその中身を
   `SPEC-WORKSPACE-UNKNOWN-001`にせず、仕様文書として読まない。中身の形式は、Core 1.0の後の決定で定める。
5. **変えないもの**。ワークスペースの決定（現在のディレクトリから親の方向へ最初の`.spec/bitz.yaml`を探す）、変更範囲の`check`の対象の選び方、
   所有境界は変えない。

## Consequences

- `sandbox/<名前>/`に独立のワークスペースを置いて検証を行っても、本体のTASKの境界の検査を妨げない。
- 入れ子のワークスペースの配下の変更は、外側のTASKの境界では検出されない。その変更の検査は、入れ子のワークスペースの中で行う。
- Core 1.0で検査を通ったワークスペースへ、後から経過の記録と計画を加えても、Core 1.0が警告を出さない。
- 仕様（`check`仕様 §7、ワークスペース・設定仕様 §2、診断レジストリ）を改め、適合fixtureを追加する。Gate Aを再認定する（ADR-051）。

## Alternatives

1. **TASKの`changes`に`sandbox/`を書く**: 本体のTASKごとに、関係のないパスを許可することになる。採らない。
2. **単一ワークスペースにも除外の設定を加える**: 設定が増える。入れ子のワークスペースは`.spec/bitz.yaml`の有無で判定できる。採らない。
3. **予約をCore 1.0の後に行う**: Core 1.0のCoreが、後の版の文書を持つワークスペースで警告を出し続ける。採らない（ユーザーの決定）。
