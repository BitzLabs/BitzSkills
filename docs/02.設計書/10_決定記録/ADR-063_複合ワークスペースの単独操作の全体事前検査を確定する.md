# ADR-063 複合ワークスペースの単独操作の全体事前検査を確定する

## Context

[複合ワークスペース仕様](../../03.詳細設計/02_仕様文書モデル/05_複合ワークスペース仕様.md) §8は、カタログ、ワークスペースのIDとパス、メンバーの設定の対応、
Gitの境界、未対応のメジャーバージョン、リソースの上限を全体事前検査とし、非成功ならワークスペースの処理を始めないと定める。
[診断レジストリ](../../03.詳細設計/00_共通契約/05_診断レジストリ.md)は、これらの条件（`MULTI-CONFIG`〜`MULTI-LIMIT`）の`operations`を`all`、
`continuation`を`stop-multi-workspace`とする。一方、全体事前検査の規則は`--all-workspaces`の節（§8）にあり、
単独の`context`、`check`、`verify`、`doctor`が非成功のときにどうするかは書かれていなかった。

Coreは、単独の操作でも全体事前検査を行っていたが、非成功のときは診断を返さずに単一ワークスペースの経路へ進んでいた（実装の確認事項C27）。
このため、カタログに登録していない`.spec/`の中で実行すると、その設定を単独のワークスペースとして使って成功した。
§3の手順4は、この場合を診断`SPEC-MULTI-UNREGISTERED-001`（`blocked`）と定めており、実装が規範に反していた。

また、次も定められていなかった。

- 単独の操作で照合する未登録の設定の範囲（§2は「選択した経路上の未登録の設定だけを拒否する」とだけ書く）
- ルートの設定を読めないときと、Gitを利用できないときに、複合ワークスペースかどうかをどう判定するか
- 停止した単独結果の`workspace`、`revision`、操作ごとのフィールド

## Decision

1. **停止**。複合ワークスペースの単独の`context`、`check`、`verify`、`doctor`は、作業ワークスペースの処理の前に全体事前検査を行う。
   非成功なら、作業ワークスペースの処理、コンテキストの解決、テストコマンドの実行を始めず、全体事前検査の診断を最上位の
   `diagnostics`に置いた単独結果を返す（ユーザーの決定）。
2. **未登録の設定の範囲**。単独の`context`、`check`、`verify`は、Gitが認識する設定の列挙と比較を行わず、§3の手順2で選んだ最も近い
   `.spec/bitz.yaml`だけをカタログと照合する。それより上にある未登録の`.spec/`は照合しない。単独の`doctor`は、`doctor`仕様 §3のとおり、
   `--all-workspaces`と同じく`HEAD`と現在のスナップショットでGitが認識する設定を比較する（ユーザーの決定）。
3. **指定との関係**。`--workspace`または修飾IDで作業ワークスペースを置き換える場合も、2.の照合を行う（§3の手順4の後に手順5を適用する順）。
   `--workspace`のIDがカタログにない場合でも、全体事前検査が非成功なら終了コード4にせず、1.の結果を返す（ユーザーの決定）。
4. **判定できない設定**。ルートの設定の構文、型、必須フィールドが不正で読めない場合は、複合ワークスペースと判定せず、単一ワークスペースとして扱う。
   スキーマまたはEARS-AIのメジャーバージョンが非対応の場合は、`multiWorkspace`の宣言があれば複合ワークスペースと判定し、1.により停止する
   （ユーザーの決定。構文が不正な設定まで推測すると、入れ子の単一ワークスペースを誤って止めるため）。
5. **Gitを利用できない場合**。リポジトリのルートを確定できないときは、§3の手順2の探索で最も近い設定が`multiWorkspace`を宣言していれば
   複合ワークスペースとし、診断`SPEC-MULTI-GIT-001`（`blocked`）で停止する。最も近い設定が`multiWorkspace`を宣言していなければ、
   単一ワークスペースとして扱う（メンバーの中では、Gitなしではルートを発見できないため、単一ワークスペースの縮退契約のままとする。ユーザーの決定）。
6. **停止した単独結果**。
   - `workspace.id`は、選択した設定がカタログに登録されていて有効なIDを持つときはそのID、未登録のとき、または有効なIDを構成できないときは`null`とする。
     `workspace.path`は、選択した設定のワークスペースの候補のリポジトリのルートからの相対パスとする（ユーザーの決定）。
   - `revision`は、Gitの境界を確定できずに停止した場合（`SPEC-MULTI-GIT-001`）だけ`null`とし、それ以外は通常の規則に従う。
     `--all-workspaces`の停止結果も同じである。
   - `context`の停止結果は、到達ワークスペースを確定しないため、複合ワークスペース固有のフィールド（`resolution.workspaces`、
     `resolution.crossWorkspaceEdges`）を持たない。
   - `doctor`の停止結果は、ワークスペース固有の検査項目を置かず、`--all-workspaces`の停止結果と同じ最上位の検査項目を同じ順と状態で置く。
7. **文言**。2.の照合で未登録と判定したときの`SPEC-MULTI-UNREGISTERED-001`の`summary`は「選択した設定ファイルがカタログに登録されていません」とする。
   Gitが認識する設定の比較の「Gitが認識する設定ファイルがカタログに登録されていません」と同じ文型であり、[ADR-062](ADR-062_Coreの出力文言の規範と適合fixtureの期待値の扱いを確定する.md)
   により管理者が承認した。
8. **上限**。単独の`verify`の全体事前検査は、`commandDefinitionCount`を含むすべての次元を判定する。単独の`verify`が実行計画の
   `verifyBindingCount`と次元の優先（§10）を判定していない点は、本ADRの範囲外の欠陥として別に扱う（実装の確認事項C40）。

## Consequences

- カタログの不備や未登録の設定があるとき、単独の操作が単一ワークスペースとして誤って成功しなくなる。
- Gitを利用できない環境で、複合ワークスペースのルートまたはメンバーでないディレクトリから実行した単独の操作は、
  単一ワークスペースとして動く代わりに`blocked`になる（行動の変更。ユーザーが承認した）。
- 単独の`context`、`check`、`verify`は、リポジトリ全体の設定を列挙しないため、無関係な場所にある未登録の`.spec/`では止まらない。
  リポジトリ全体の完全性は`--all-workspaces`と`doctor`で検査する。
- 単独の操作で停止を固定する適合fixtureを追加する（ADR-051の追加）。既存のfixtureの入力と期待値は変えない。

## Alternatives

1. **作業ワークスペースと到達先に関係する不備だけで止める**: 無関係な不備で止まらないが、到達性が実行ごとに変わり、仕様の記述が大きくなる。採らない（ユーザーの決定）。
2. **現状のまま単一ワークスペースへ進む**: 規範（§3の手順4、診断レジストリの`operations: all`）に反する欠陥が残る。採らない。
3. **選択した経路上のすべての設定を照合する**: 最も近い設定で探索を止める§3の手順2と食い違う。採らない（ユーザーの決定）。
4. **`--workspace`または修飾IDがあるときは照合しない**: §3の手順の順と、全体事前検査を終了コード4より優先する扱いに反する。採らない（ユーザーの決定）。
5. **2つの`summary`を「設定ファイルがカタログに登録されていません」にそろえる**: 既存のfixtureの期待値の訂正が必要になる。採らない（ユーザーの決定）。

## Notes

- 実装の確認事項C27の解決であり、A群（Coreの欠陥）の決定D1〜D4に、着手時の決定（照合の範囲、指定との関係、文言、Gitを利用できない場合）を加えた。
- 単独の`doctor`の全体事前検査と、成功したときの検査項目`catalog`は、C24・C38の修正で先に`doctor`仕様 §3へ明記した。
