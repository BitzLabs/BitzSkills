# ADR-031 変更コード・テストからの検査対象選択

## Context

引数なしの`bitz check`はGit変更集合を起点にすると定めている。一方、通常実行の詳細な記述は
「変更されたSPEC、その強い依存先、その直接の逆参照を再検査する」であり、変更されたコードpathと
テストpathをどのSPECへ正規化するかを定義していなかった。SPECを変更せずコードとテストだけを変更した
commitでは、検査対象が空になり得た。

さらに`docs/02.設計書/02_specディレクトリ仕様.md`の状態表は`outdated`を「上位要求または実装変更の
影響候補」と説明していたが、影響候補Diagnostic`SPEC-IMPACT-OUTDATED-001`は変更されたREQ/TECHへ強く
依存する`approved`文書だけを対象としており、実装変更を起点にしていなかった。

## Decision

1. 引数なし`bitz check`の起点は、Git変更集合の各pathを次のとおり正規化して決定する。

   | 変更path | 正規化先 |
   |---|---|
   | SPEC path | 所有文書ID |
   | code path | `implements`の逆索引が示す所有REQ/TECH |
   | test path | `tests[].path`の逆索引が示す所有REQ/TECH |

2. どの逆索引にも該当しないcode/test pathは検査対象外とし、Diagnosticを出さない。対象外となったpathの
   件数だけを結果へ残す。
3. 逆索引は§2のID解決が全SPECから構築する軽量Frontmatter索引から作る。`implements`と`tests[].path`は
   Frontmatter項目であり、追加のファイル走査を必要としない。
4. 正規化して選択した文書に対し、従来どおり強い依存閉包と直接の逆参照を検査する。
5. 影響候補は変更されたREQ/TECHへの逆参照に限る現行契約を維持し、コード・テストの変更を
   `SPEC-IMPACT-OUTDATED-001`の起点にしない。
6. `outdated`の説明から「実装変更」を削除し、上位要求または依存仕様の変更による影響候補とする。

## Consequences

- コードとテストだけを変更したcommitでも、所有するREQ/TECHとその依存閉包が検査される。
- SPECをまだ持たないコードの変更は、検査対象を増やさず、警告も出さない。段階的にSPECを整備する
  リポジトリで、通常のコード変更が常時`passed_with_warnings`になることを避ける。
- 逆索引が既存の軽量索引から得られるため、変更範囲`check`の1秒以内という性能目標に影響しない。
- `outdated`の意味が影響候補Diagnosticの実装と一致する。

## Alternatives

1. **未所有のcode/test pathをwarningにする**: 通常のコード変更が常時`passed_with_warnings`となり、
   影響候補warningのシグナルが埋没するため採用しない。モノレポの対象0件memberをwarning止まりにした
   [ADR-019](ADR-019_検証対象と縮退判定の明確化.md)の方針とも整合しない。
2. **コード変更を`outdated`候補の起点にする**: Coreが意味的影響を断定しない方針に反し、実装を変えるたびに
   仕様の再確認を促す偽陽性を生むため採用しない。
3. **コードpathを起点にしない**: SPEC未変更のcommitで検査対象が空になり、`implements`と`tests`の
   静的トレースが利用されないため採用しない。
