# ADR-079 承認済みの契約の保護の途中のコミットの読み方と診断の形を定める

## Context

[ADR-072](ADR-072_承認済みの契約の保護をTECHへ広げ、途中のコミットの状態で再承認を判定する.md)と
[ADR-078](ADR-078_承認済みの契約の保護で認める途中の版を変更したコミットに限り、履歴の読取りに上限を設ける.md)を仕様
（[文書・フロントマター・状態仕様](../../03.詳細設計/02_仕様文書モデル/02_文書・フロントマター・状態仕様.md) §8.1）へ落とした後の独立レビューで、
適合fixtureの期待値を仕様だけから一意に決められない点が、次のとおり残った。

1. **途中のコミットがない場合とシャロークローン**。基準版が`HEAD`と同じ場合は端点の比較だけで判定するが、深さ1のシャロークローンでは`HEAD`自身が
   境界のコミットになり、ADR-078の決定2の「境界のコミットが`HEAD`から到達できる」にも当たる。どちらの文言の診断になるかが決まらない。
2. **完全に読めない場合の範囲**。ADR-078の決定2は、完全に得られない場合は違反のままとするが、読めた範囲で条件を満たす版が見つかった場合と、
   読む範囲（どのファイルが欠けていれば読めないとするか）を明記していない。
3. **診断の形**。`SPEC-SAFETY-APPROVED-001`の件数と`source.key`を、適合fixtureは`title`を変えた場合だけ固定している。REQでも、規範文または
   強い関係だけを変えた場合の`source.key`を定める規範文がない。TECHの適合fixtureは、規範文の変更が中心になる。
4. **途中の版を読めない場合**。IDを読めない版の範囲と、途中のコミットに同じIDの文書が2つある場合の扱いが決まっていない。

## Decision

1. **途中のコミットがない場合**。途中のコミットの集合が空であると確定する場合（基準版が`HEAD`と同じ場合と、`HEAD`が基準版の祖先の場合）は、
   シャロークローンの条件を見ず、端点の比較だけで判定する。違反の診断は通常の文言とする。
2. **完全に読めない場合**。ADR-078の決定2の3つの条件のどれに当たる場合も、読めた範囲で見つかった版によらず違反のままとする。
   判定のために、途中のコミットとその親のすべてについて、現在版の作業ワークスペースのルートの配下の仕様文書のファイルを読む。
   ルートの外のオブジェクトが欠けていても、完全に読めないとはしない。
3. **診断の形**。`SPEC-SAFETY-APPROVED-001`は、意味が変わった1文書に1件とする。`source.key`は、変わった項目のうち最初のものとし、
   順は`title`、強い関係（`relations.<関係型>`。関係型は[関係・トレースモデル](../../03.詳細設計/02_仕様文書モデル/04_関係・トレースモデル.md) §1の表の順で、`requires`、`refines`、`addresses`、`supersedes`）、規範文（`statements`）とする。
   `evidence`は持たない。REQとTECHで同じとし、完全に読めない場合の診断も同じ形とする。
4. **途中の版を読めない場合**。IDを読めない版は、`check` §5の「索引に入らない」版（フロントマターの不正、ファイルごとの上限の超過を含む）と同じとする。
   途中のコミットまたはその親に、同じIDの文書が2つ以上ある場合は、そのコミットのその文書の版を途中の状態として認めず、そのコミットを親とする比較でも
   その文書を変更したかを判定しない（違反のままになる側に倒す）。

## Consequences

- 深さ1のチェックアウトで`bitz check <ID>`を実行しても、途中のコミットを読めないという文言にならない。
- 完全に読めない場合は、読む順序や、見つけた時点で読むのをやめるかによらず、同じ結果になる。
- 規範文だけ、または強い関係だけを変えた場合の診断を、REQとTECHの両方の適合fixtureで固定できる。
- 仕様（文書・フロントマター・状態仕様 §8.1、診断レジストリ）へ、同じ作業で書き足す。

## Alternatives

1. **途中のコミットがなくてもシャロークローンの条件を当てる**: 深さ1のチェックアウトで、読めない履歴がないのに読めないという文言になる。採らない（ユーザーの決定）。
2. **読めた範囲で条件を満たす版があれば通過とする**: ADR-078の決定2と食い違い、読む順序で結果が変わり得る。採らない（ユーザーの決定）。
3. **`source.key`を`title`のときだけ付ける**、**変わった項目ごとに1件とする**: 前者は規範文の変更を区別できず、後者は1文書の診断の件数が増え、
   今の`title`の適合fixtureの扱いとも変わる。採らない（ユーザーの決定）。
