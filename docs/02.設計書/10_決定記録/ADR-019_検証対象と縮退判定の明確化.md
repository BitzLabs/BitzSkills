# ADR-019 検証対象と縮退判定の明確化

## Context

レビュー03のP2として、`bitz verify`の対象の選択、複合ワークスペースでの縮退の判定、`doctor`の判定の区分、
公開文法に、6件の不整合が見つかった。いずれも単独では小さいが、段階導入中のモノレポでCIが常に停止する、
宣言したテストが一度も実行されないなど、運用開始後に効く。

## Decision

1. 未知の拡張は重大度`warning`に固定し、Core 1.0に厳格モードを設けない。
2. 引数なしの`bitz verify`の対象へ、規範文を持たず`tests`を宣言している`approved`のTECHを含める。
   規範文を持たないTECHは、規範文単位のカバレッジの判定の対象外とし、テストの実行結果だけで判定する。
   除外した対象は、理由ごとの件数を返す。
3. `verify --all-workspaces`でのメンバー単位の対象が0件の場合は、診断`SPEC-VERIFY-BLOCKED-002`（重大度`warning`）とし、
   複合ワークスペース全体で0件の場合だけ、重大度`error`として`blocked`にする。単一ワークスペースの動作は変更しない。
4. `doctor`の検査項目1を、バージョンの不適合（`blocked`）と起動の失敗（`error`）に分ける。
   起動の失敗用に、診断`SPEC-DOCTOR-CORE-002`を追加する。
5. `bitz verify`へ`--format text|json`を追加し、`--all-workspaces`の形を文法上で分離する。
6. `--all-workspaces`の実行済みの判定を、複合ワークスペース全体で1つの集合とし、ワークスペースをまたぐ具体化が参照する
   同じテストを、二重に実行しない。

## Consequences

- 段階導入中のモノレポでも、`verify --all-workspaces`をCIの標準にできる。
- 規範文を持たないTECHのテストが、CIで実行される。
- バージョンの不適合と障害を終了コードで区別でき、拡張プラグインが導入手順を出し分けられる。
- `verify`の結果を、ファイルを生成せずに機械で利用できる。
- ワークスペースをまたぐテストの実行回数が、複合ワークスペースの構成に依存しなくなる。
- 診断コードが1つ増える（`SPEC-DOCTOR-CORE-002`）。

## Alternatives

1. **規範文を持たないTECHで、文書IDを指す`covers`を廃止する**: 「TECHへEARS-AIを必須としない」
   （補助SPEC仕様 §2）と、TASKの`addresses`先として規範文のないTECHを許可する規則
   （Context Resolution仕様 §4）を同時に覆すため採用しない。
2. **0件のメンバーも`blocked`のままにする**: 利用者がCIから`--all-workspaces`を外すため、
   横断検証という複合ワークスペースの主目的が使われなくなる。
3. **0件用に新しい診断コードを追加する**: 同じ条件に2つのコードを持つことになる。
   条件によって重大度が変わる診断には、`SPEC-PATH-INVALID-001`に前例がある。
4. **`verify`のJSONを`--report`経由に限る**: 成功したときの保存物を最小にする設計原則9と衝突する。
