# ADR-019 検証対象と縮退判定の明確化

## Context

レビュー03のP2として、`bitz verify`の対象選択、モノレポ連合での縮退判定、`doctor`の
判定区分、公開文法に6件の不整合が見つかった。いずれも単独では小さいが、
段階導入中のモノレポでCIが常に停止する、宣言したテストが一度も実行されないなど、
運用開始後に効く。

## Decision

1. 未知拡張は`warning`固定とし、Core 1.0に厳格モードを設けない。
2. 引数なし`bitz verify`の対象へ、規範文を持たず`tests`を宣言している`approved` TECHを含める。
   規範文を持たないTECHは句単位カバレッジ判定の対象外とし、テストの実行結果だけで判定する。
   除外した対象は理由ごとの件数を返す。
3. `verify --all-workspaces`のmember単位の対象0件は`SPEC-VERIFY-BLOCKED-002`／warningとし、
   連合全体が0件の場合だけerrorとして`blocked`にする。単一workspaceの動作は変更しない。
4. `doctor`の検査1を、版不適合（`blocked`）と起動失敗（`error`）へ分ける。
   起動失敗用に`SPEC-DOCTOR-CORE-002`を追加する。
5. `bitz verify`へ`--format text|json`を追加し、`--all-workspaces`形を文法上で分離する。
6. `--all-workspaces`の実行済み判定を連合全体で1つの集合とし、横断refinementが参照する
   同一テストを二重に実行しない。

## Consequences

- 段階導入中のモノレポでも`verify --all-workspaces`をCI標準にできる。
- 規範文を持たないTECHのテストがCIで実行される。
- 版不適合と障害が終了コードで区別でき、拡張プラグインが導入手順を出し分けられる。
- `verify`の結果をファイル生成なしで機械利用できる。
- 横断テストの実行回数が連合構成に依存しなくなる。
- Diagnosticコードが1つ増える（`SPEC-DOCTOR-CORE-002`）。

## Alternatives

1. **規範文を持たないTECHの文書ID`covers`を廃止する**: 「TECHへEARS-AIを必須としない」
   （補助SPEC仕様 §2）と、TASKの`addresses`先として規範文なしTECHを許可する規則
   （Context Resolution仕様 §4）を同時に覆すため却下する。
2. **0件memberも`blocked`のままにする**: 利用者がCIから`--all-workspaces`を外すため、
   横断検証という連合の主目的が使われなくなる。
3. **0件用に新しいDiagnosticコードを追加する**: 同一条件に2コードを持つことになる。
   条件付きseverityは`SPEC-PATH-INVALID-001`に前例がある。
4. **`verify`のJSONを`--report`経由に限る**: 成功時の保存物を最小化する設計原則9と衝突する。
