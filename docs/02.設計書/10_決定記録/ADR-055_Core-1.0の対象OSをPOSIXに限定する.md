# ADR-055 Core 1.0の対象OSをPOSIXに限定する

## Context

Core 1.0の規範は対象のCPythonの版（[ADR-053](ADR-053_CPythonの下限を3.12へ引き上げる.md)）を定めているが、対象OSを
定めていない。対象OSに触れていたのは、[ADR-009](ADR-009_小規模チーム向け軽量CoreとEARS-AI中核化.md)で置き換えられた
[ADR-007](ADR-007_Core実行体の配布形態.md)の「3OS」（Linux、macOS、Windows）だけである。Gate Cの「2環境」も
CPythonの版を指し、OSを指さない。

一方、Core 1.0の規範と実装は、すでにPOSIXの機能を前提にしている。

- `verify`のタイムアウトの状態機械は、新しいプロセスグループへの起動とグループへのシグナル送信を使う
  （[`verify`仕様 §5.2](../../03.詳細設計/03_操作仕様/03_verify.md#52-タイムアウトと有限時間での終了)）
- 実行ファイルの解決は、通常ファイルと実行権限の判定を使う（同 §5.1）
- 明示したレポートの保存は、`.spec`と`.spec/reports`を、シンボリックリンクを辿らないディレクトリのFDとして開き、そのFDを基準に、
  一時ファイルの作成、確定、除去を行う（REQ-003、[結果・診断・終了コード §8](../../03.詳細設計/00_共通契約/01_結果・診断・終了コード.md#8-レポート)）

WindowsはディレクトリのFDを基準にした操作（`dir_fd`、`O_DIRECTORY`、`O_NOFOLLOW`）と、
プロセスグループへのシグナルを持たない。
Windowsを対象に含めると、レポートの保存を検査と書込みの競合に弱い方式へ戻すか、別の実装を用意する必要があり、
`verify`の有限時間での終了の保証も同じ形では成り立たない。Core 1.0は小規模チーム向けの軽量Core
（ADR-009）であり、未リリースの今、対象OSを明示するのが最も安い。

## Decision

1. **対象OS**: Core 1.0の対象OSはPOSIX系のLinuxとmacOSとする。Windowsは対象外とし、Windowsの利用者には
   WSL上での利用を案内する。
2. **必要な機能がない環境での挙動**: Coreは、安全性の保証に必要なOSの機能（ディレクトリのFDを基準にしたファイル操作、
   `O_NOFOLLOW`、プロセスグループへのシグナル）が使えない環境で、その保証を弱めた代替動作へ切り替えない。
   明示したレポートの保存は、書き込まずに診断`SPEC-REPORT-WRITE-001`を返す。
3. **適合の確認**: Gate Cの確認はLinuxで行う。macOSは検証環境を用意できないため、Core 1.0ではmacOSでの
   確認を行わず、動作を検証済みとして扱わない。macOSでの利用は、POSIXの機能だけを使う実装の設計に基づく
   ものであり、適合を保証しない。本項は[実装計画 §9.1](../../04.提案資料/12_Core-1.0実装計画.md#91-gate-c-core-10のリリース受入)の条件に反映する。
4. 対象OSの追加は、Coreのマイナーバージョン以上の変更とする（ADR-045の`Decision`の6番目の項目の下限バージョンの扱いと同じ）。

## Consequences

- Windowsでネイティブに動かすことはCore 1.0の対象外になる。WSLでは対象になる。
- 実装はPOSIXの機能を前提にでき、安全性の保証を弱める分岐を持たない。
- Gate CでOSについて確認するのはLinuxだけである。macOSでディレクトリのFDを基準にした操作やプロセスグループへのシグナルが
  期待どおり動くことは実測せず、Core 1.0ではmacOSでの動作を検証済みとして扱わない。検証環境を用意できた時点で、
  macOSでの確認をGate Cまたは後続のリリースの条件へ加えられる。

## Alternatives

1. **Windowsも対象にする**: 利用者は広がるが、レポートの保存では検査と書込みの競合を防げず、REQ-003の保証が
   成り立たない。`verify`のプロセス管理も別の実装が要る。Core 1.0の規模と釣り合わないため採用しない。
2. **対象OSを定めない**: 実装が根拠のない前提を持ち、Windowsでの挙動が規範から決まらない。採用しない。
