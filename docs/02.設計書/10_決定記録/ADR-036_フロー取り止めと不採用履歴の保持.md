# ADR-036 フロー取り止めと不採用履歴の保持

## Context

開発フローには完了と再作業の経路がある一方、検討の途中で提案または設計を取り止める終端がない。
未採用のREQ／TECHを削除すると、判断理由、比較した選択肢、再検討の条件が失われ、将来の設計で同じ検討を
繰り返す。反対に、`draft`や`outdated`のまま残すと、作業中または再確認待ちの契約と、採用しないと決めた
履歴を区別できない。

TASKにも完了せずに閉じる状態がないため、取り止めた作業が`open`のまま残り、後続TASKの依存判定を曖昧にする。
取り止めは人間の判断であり、Coreが本文や作業停滞から推測してはならない。

## Decision

1. 人間は`Done`へ到達する前の任意の段階でフローを明示的に取り止められる。フロー上の終端名を
   `Stopped`とする。`Stopped`はCore共通の操作statusでもSPECの`status`でもなく、進行支援上の結果である。
   Coreは取り止めを推測せず、文書の削除、状態変更、commitを自動実行しない。
2. REQ／TECHへ終端状態`rejected`を追加する。作成時は`draft`、`approved`、`rejected`を許可し、
   `draft -> approved|rejected`、`approved -> draft|outdated`、`outdated -> draft|approved`と同一状態の維持を
   許可する。`approved -> rejected`は禁止し、一度適用した契約を廃止または見直す場合は`outdated`を使う。
   `rejected`から他状態への遷移は禁止し、再検討時は新しいIDのREQ／TECHを作成して関連付ける。
3. `rejected`のREQ／TECHには、空でない条件付き必須H2 `Rejection Rationale`を置く。採用しなかった理由、
   根拠またはトレードオフ、再検討条件を記録し、元の`Acceptance Criteria`または`Contract`と
   `Verification`を保持する。理由がない`rejected`文書は構造違反とする。
4. `rejected`のREQ／TECHは`interpret`でHistory区分として返し、`check`の構造・ID・関係検査対象とする。
   `implement`または`verify`の起点、および強い依存先としては`CTX-STATE-001`／error／`blocked`とする。
   `related`による履歴参照は許可する。
5. `rejected`文書の`implements`、`tests`、`verify`は過去の判断を理解するため保持するが、コード・テストの
   所有逆索引、検証対象選択、coverage、パス存在検査、検証コマンド解決から除外する。型、文書ID、
   ローカルID、EARS-AI構文、本文構造、関係先の存在と型は通常どおり検査する。
6. TASKへ終端状態`cancelled`を追加する。作成時は`open`だけを許可し、`open -> done|cancelled`と同一状態の
   維持だけを許可する。`done`と`cancelled`は終端であり、`cancelled`を完了済みとして扱わない。
7. `cancelled` TASKには、空でない条件付き必須H2 `Cancellation Rationale`を置き、取り止め理由、既に得た
   知見、再開または再計画の条件を記録する。`Objective`、`Work`、`Completion Criteria`は履歴として保持する。
8. `cancelled` TASKは`interpret`でHistory区分として返し、明示`check`を許可する。`implement`または
   `verify`の起点では`CTX-STATE-001`／error／`blocked`とする。別TASKの`requires`先にある場合は未充足とし、
   `CTX-TASK-DEPENDENCY-001`／error／`blocked`で、依存の除去または代替TASKへの更新を案内する。
9. 文書を伴う取り止めでは、人間が状態と理由を同じ変更へ記録し、`bitz check <ID>`が`passed`または
   `passed_with_warnings`であることを確認してからGitへ記録する。TASK起点では`open -> cancelled`を検査する。
   該当するREQ／TECHまたはTASKがない取り止めは、Core保証外の作業記録として扱う。
10. 本ADRは[ADR-024](ADR-024_SPEC文書の状態遷移契約.md)のDecision 1、2、5だけを置き換える。
    ADR-024のDecision 3、4、6、7は変更しない。ADR-029の依存ガードとADR-034の完了終端は置き換えず、
    `cancelled`および`Stopped`の契約を追加する。

## Consequences

- 不採用の提案・設計を理由とともに検索可能な履歴として保持できる。
- `rejected`を現行契約の所有権、検証、coverageから分離し、過去のパス情報による誤選択を防げる。
- TASKの完了と取り止めを区別し、取り止めた依存を自動的に充足扱いしない。
- 取り止め時にも明示的な状態変更と検査が必要になり、理由の記録なしに文書を閉じられない。
- 終端文書を再利用せず、新しいIDで再検討するため、過去の判断と新しい判断の境界が残る。

## Alternatives

1. **取り止めた文書を削除する**: 判断理由と再検討条件が失われ、同じ設計検討を繰り返すため採用しない。
2. **`draft`のまま残す**: 作業中と不採用を区別できず、未決事項として残り続けるため採用しない。
3. **REQ／TECHを`outdated`へ変更する**: 一度適用された契約の再確認待ちと、採用前の却下を混同するため採用しない。
4. **`rejected`文書のパスと検証情報も現行索引へ含める**: 過去の候補が現行コードの所有者や検証対象として
   選ばれるため採用しない。
5. **`cancelled` TASKを依存充足とみなす**: 必要な作業が完了していないまま後続作業を開始できるため採用しない。

## Notes

- 本ADRは2026-09-01のP2追加レビューUC-FLOW-016「フロー途中の提案・設計取り止め」に対する裁定である。
- `Rejection Rationale`と`Cancellation Rationale`は履歴説明であり、EARS-AI規範文やcoverageの意味集合へ
  含めない。
- 2026-09-01の実装前異常ケースレビュー`EDGE-002`で、Implement後に残るコード・テスト差分の処遇を明確化した。
  人間が破棄、保持、別TASKへの引継ぎ、Spikeへの隔離を選び、CoreとSkillは自動削除しない。この明確化は
  Decision 1、9の人間判断とGit記録を具体化するもので、状態や必須Schemaを追加しない。
