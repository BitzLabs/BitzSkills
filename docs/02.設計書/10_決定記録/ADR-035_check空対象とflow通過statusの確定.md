# ADR-035 `check`の対象が0件の場合とSDDフローの通過状態の確定

## Context

ADR-031は、引数なしの`bitz check`で、変更されたコードまたはテストのパスをフロントマターの逆索引から、
それを所有するREQまたはTECHへ正規化し、所有されていないパスを検査の対象外として件数だけ結果へ残すと定めた。
この結果、変更集合が空の場合だけでなく、仕様文書が未整備のコードまたはテストのパスだけを変更した場合にも、
検査対象の文書が0件となる正常な経路が生じた。しかし、対象が0件の場合の結果の状態と結果スキーマは
定義されていなかった。

引数なしの`verify`は空のCIを成功として扱わないため、対象が0件の場合を診断`SPEC-VERIFY-BLOCKED-002`（`blocked`）とする。
`check`がこの規則を流用すると、検査対象の仕様文書がない通常のコードの変更までCIを停止する。`check`と`verify`では
対象が0件であることの意味が異なる。

またADR-028は「Post-checkが非成功のままVerifyへ進まない」と定め、ADR-034は、TASKの完了時の`check`が
「flowの通過条件」を満たしてからGitへ記録すると定めたが、`passed_with_warnings`を成功の側へ含めるかを
明示していなかった。共通の結果の形式では`passed`と`passed_with_warnings`がともに終了コード0であり、Core 1.0は
警告をエラーへ昇格する`--strict`を提供しない。

## Decision

1. 引数なしの`bitz check`の変更範囲を正規化した結果、検査対象の文書が0件であり、設定、索引、Gitの縮退を含む
   ほかの診断がない場合は、結果の状態を`passed`、終了コードを0とする。対象0件専用の診断は追加しない。
2. 対象が0件でも、`bitz.yaml`のスキーマと互換性、すべての仕様文書のフロントマターの軽量な索引、IDと関係の索引、
   Gitの変更集合、対象外となったコードまたはテストのパスの集計を実行する。これらから診断が生じた場合は共通の順位で集約し、
   0件を理由に`passed`へ上書きしない。
3. `Decision`の1番目の項目は、引数なしの変更範囲の検査だけに適用する。明示対象、`--full`、`--all-workspaces`の対象の選択は
   変更しない。`check --all-workspaces`は従来どおり`--full`を含意する。
4. `check`の結果へ、`scope: changed`で使う、次の`check`固有のフィールドを追加する。

   ```json
   {
     "selection": {
       "changedPathCount": 3,
       "targetDocumentCount": 0,
       "excludedCodeTestPathCount": 3
     }
   }
   ```

   - `changedPathCount`は、正規化したGitの変更集合の、変更エントリの数とする。
   - `targetDocumentCount`は、パスを所有する文書のIDへ正規化し、重複排除した後の、検査対象の文書の数とする。
   - `excludedCodeTestPathCount`は、`implements`の逆索引にも`tests[].path`の逆索引にも該当せず、対象外となった
     コードまたはテストの変更エントリの数とする。

   テキスト出力も、同じ3つの件数を1行で示す。対象外となったパスそのものは、通常の結果へ列挙しない。
5. 引数なしの`verify`の対象が0件の場合は、従来どおり診断`SPEC-VERIFY-BLOCKED-002`（`blocked`）とし、契約を変更しない。
   `check`の0件は「今回完全解析すべき、変更された仕様文書がない」、`verify`の0件は「実行して保証すべき検証対象がない」
   ことを表す。
6. 実装前検査、実装後検査、およびADR-034のTASKの完了時の`check`について、フローの通過状態を`passed`または
   `passed_with_warnings`とする。構造化クライアントは結果の状態を、CLIの利用者はそれと同値である終了コード0を、判定に使う。
7. `failed`、`blocked`、`error`を非成功とし、次の段階へ進まない。引数不正の終了コード4は操作の結果の状態を
   生成しないが、同じく次の段階へ進まない。
8. 警告は、診断、テキスト出力とJSON出力、レポートへ保持するが、Core 1.0のフローでは自動で昇格しない。
   Core 1.0へ`--strict`を追加しない。人間によるレビュー、またはCoreの外のCIのポリシーが、警告を理由に停止することは
   妨げない。
9. 本決定は、ADR-028の`Decision`の4番目の項目の「非成功」とADR-034の`Decision`の1番目の項目の「flowの通過条件」を明確化し、
   ADR-031の`Decision`の2番目の項目の対象外の件数を結果スキーマへ具体化する。既存の`Decision`を置き換えない。

## Consequences

- 仕様文書が未整備のコードまたはテストの変更だけで、通常の`check`とCIが停止しない。
- 対象が0件でも、設定と全体の索引の不適合を見逃さない。
- `check`と`verify`の空集合が、各操作の保証の目的に応じて異なる結果の状態を持つ。
- 警告を残したまま、簡易フローと完全フローを継続でき、終了コードとフローの判定が一致する。
- 対象の選択の件数がJSONで安定し、テキスト表示とfixtureを同じ値から生成できる。

## Alternatives

1. **`check`の対象0件を`blocked`にする**: ADR-031が正常な経路として除外した、所有されていないコードまたはテストの変更でCIが停止するため採用しない。
2. **`check`の対象0件を警告にする**: 所有されていないパスを警告にしないADR-031の決定を実質的に覆すため採用しない。
3. **0件のときは設定と索引を省略する**: 対象の選択に必要な設定と索引の不適合を、空の成功で隠すため採用しない。
4. **`passed_with_warnings`をフローの非成功にする**: 終了コード0との意味が分かれ、通常発生する警告でフローが完了しないため採用しない。
5. **`--strict`で警告を昇格する**: Core 1.0の共通の終了コードを、操作ごとのポリシーで変えるため採用しない。
