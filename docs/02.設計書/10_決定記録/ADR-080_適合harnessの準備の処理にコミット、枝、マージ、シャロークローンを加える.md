# ADR-080 適合harnessの準備の処理にコミット、枝、マージ、シャロークローンを加える

## Context

[ADR-048](ADR-048_適合fixtureの生成入力とGit構造の準備の処理を確定する.md)は、適合fixtureの準備の処理を閉じた集合
（`create`、`update`、`delete`、`rename`、`stage`、`submodule`、`worktree`）とし、`setup.baseCommit`が作るコミットは1つだけである
（[適合fixture仕様](../../03.詳細設計/00_共通契約/04_適合fixture仕様.md) §3.1、§3.2）。

[ADR-072](ADR-072_承認済みの契約の保護をTECHへ広げ、途中のコミットの状態で再承認を判定する.md)と
[ADR-078](ADR-078_承認済みの契約の保護で認める途中の版を変更したコミットに限り、履歴の読取りに上限を設ける.md)の保護は、
基準版から`HEAD`までの途中のコミットを読む。これを適合fixtureで確かめるには、複数のコミット、枝とマージ（親の順序を含む）、
シャロークローンの境界を作る手段が要る。

## Decision

1. **加える準備の処理**。適合fixture仕様 §3.2の閉じた集合に、次の5つを加える。どれも`setup.git: true`を要し、harnessが固定した同一性、時刻、
   ブランチ名を使う。2回の`setup`で同じGit構造とコミットIDを与える。
   - `commit`（`message`）: インデックスの内容でコミットを作る。マージの途中（2.）なら、マージコミットを作る。空のコミットを許す。
   - `branch`（`name`）: `HEAD`のコミットを指す枝を作る。`HEAD`は切り替えない。同じ名前の枝が存在すれば準備の誤りとする。
   - `checkout`（`name`）: `HEAD`を枝`name`へ切り替え、インデックスと作業ツリーをその枝のコミットに合わせる。インデックスまたは作業ツリーが
     `HEAD`のコミットと異なる場合は、準備の誤りとする。
   - `merge`（`name`）: 枝`name`を`HEAD`へマージする。早送りせず、コミットせずに止める。衝突は準備の誤りとせず、衝突の印を含むファイルを
     作業ツリーに残す。後続の`update`、`stage`、`commit`でマージコミットを作る。マージコミットの親は、1つ目が`HEAD`、2つ目が枝`name`の先端である。
   - `shallow`（`revisions`）: 列挙したリビジョンのコミットを、シャロークローンの境界のコミットとして記録する（Gitの`shallow`ファイル）。
     オブジェクトは削除しない。リビジョンを解決できなければ準備の誤りとする。
2. **マージの途中**。`merge`の後、`commit`の前は、マージの途中とする。マージの途中の`branch`、`checkout`、`merge`、`shallow`は、準備の誤りとする。
   準備の処理の最後でマージの途中なら、準備の誤りとする。
3. **起動の`--base`**。起動の`--base`には、枝の名前と、`HEAD~1`のようなリビジョンの式を書ける（Gitが解決する）。
4. **扱わないもの**。部分クローンの欠けたオブジェクトは、準備の処理で作らない。ADR-078の決定2の「Gitから読めない」場合は、Coreの単体試験で確かめる。

## Consequences

- 途中のコミット、古い枝の取込み、マージの親の順序、シャロークローンの境界を、適合fixtureで確かめられる。
- 適合fixture仕様 §3.1、§3.2を改め、参照適合harnessの準備の処理、マニフェストのスキーマ、監査の検査を、fixtureの作成と同じ作業で広げる。
- 準備の処理の集合は閉じたままとする。ここに挙げたもの以外のGitの操作は加えない。

## Alternatives

1. **Gitの履歴の構造を生成する入力を設ける**（`setup.generate`と同じ方式）: fixtureごとの履歴を書き下さずに済むが、入力から履歴を読み取りにくい。
   採らない（ユーザーの決定）。
2. **シャロークローンを実際の`git clone --depth`で作る**: 一時リポジトリを作り直す必要があり、境界の位置を自由に選べない。採らない。
3. **部分クローンも準備の処理で作る**: 一時リポジトリの外の取得元の設定が要り、準備が複雑になる。単体試験で確かめる。採らない。

## Notes

- 2026-11-21に、利用者が準備の処理を加える案を選んだ。個々の処理の名前と事前条件、`shallow`をGitの`shallow`ファイルで作ること、
  Decisionの2と3は、起票者の案である。
