# ADR-034 TASKの完了終端と`done`のTASKを起点とする操作の確定

## Context

ADR-024はTASKに許可する遷移を`open -> done`とし、ADR-029は、TASKを起点とする目的`implement`または`verify`で、
`requires`の参照先のTASKがすべて`done`であることを要求した。しかし簡易フローと完全フローには、
起点のTASKを`done`へ遷移させる段階がなく、完了した作業を`open`のまま残すと、後続のTASKが恒久的に`blocked`となる。

既存の工程`Post-check`の後にTASKを`done`へ変更し、そのままGitへ記録すると、状態遷移と`Revision History`を
変更後の入力で検査しない経路も生じる。一方、検証または人手レビューより前に`done`へ変更すると、失敗や
否決があった作業を終端状態へ置くことになる。

またContext Resolutionの状態表は、`done`のTASKを履歴の区分へ分類するだけで、`implement`、`verify`、
`interpret`の各目的で起点にした場合の結果を区別していなかった。追加の作業には新しいTASKを使うという終端の規則と、
完了済みの作業をCIやレビューで再検証する需要を両立させる必要がある。

## Decision

1. 簡易フローと完全フローの8段階は維持し、TASKを起点とする工程`Done`を次の順序で実行する。
   1. 検証に成功した後に、人手レビューを完了する。
   2. 起点のTASKを`open -> done`へ変更し、同じ差分で`Revision History`を更新する。
   3. 変更後の入力に対して`bitz check <TASK-ID>`を実行する。
   4. `check`がフローの通過条件を満たした場合だけ、完了の結果をGitへ記録する。
2. 手順3の`check`は、TASKを明示した通常の検査であり、状態遷移、フロントマター、本文の構造、関係、変更の境界を検査する。
   TASK自身のファイルは`changes`の境界の比較対象から除くが、状態遷移と文書の検査の対象からは除外しない。
3. CoreはTASKの状態（`status`）を自動で変更しない。`open -> done`は、人間またはAIクライアントが確認できる差分として行う。
   `check`が通過しない場合はGitへ記録せず、原因を修正する。未記録の`done`への編集を取り消して、基準版と同じ
   `open`へ戻すことは、記録済みのTASKに対する`done -> open`の遷移とは扱わない。
4. 後続のTASKのフローは、先行TASKの完了の結果をGitへ記録した後に開始する。これはAI-SDDのフローの運用契約とし、
   Coreへ新しいコミット操作またはGitの履歴のゲートを追加しない。
5. `done`のTASKを目的ごとに次のとおり扱う。

   | 目的 | 起点としての結果 | TASKの区分 |
   |---|---|---|
   | `implement` | 診断`CTX-STATE-001`（重大度`error`、結果への効果`blocked`） | 履歴 |
   | `verify` | 許可 | 履歴 |
   | `interpret` | 許可 | 履歴 |

   目的`implement`では、新しいTASKの作成を`suggestedAction`へ示す。目的`verify`では、`done`のTASKの`addresses`から、
   対象規範文または規範文を持たないTECHを導出し、TASK自身を規範として適用せず、作業履歴として返す。
   `addresses`の参照先と`requires`の閉包には、通常の適用可能性の検査を行う。
6. `done`のTASKを目的`verify`の起点にした場合も、`requires`の参照先のTASKに`open`が残れば、ADR-029のとおり
   診断`CTX-TASK-DEPENDENCY-001`（重大度`error`、結果への効果`blocked`）とする。目的`interpret`は停止せず、
   未完了の先行TASKを作業の区分として返す。
7. `bitz check <done TASK>`は許可する。`check`は、文書の現在の状態とGitの基準版からの遷移を検査する操作であり、
   目的`implement`の開始ではない。
8. `CTX-STATE-001`の条件を「起点または強い依存先が、指定した目的に対して適用不能」へ拡張する。
   新しい診断コードと公開操作は追加しない。
9. 本決定は、ADR-024の`Decision`の5番目の項目、ADR-028の`Decision`の1番目と4番目の項目、ADR-029の`Decision`の1番目の項目を置き換えず、
   状態遷移、フローの終端、目的ごとの適用可能性の接続を補完する。

## Consequences

- TASKを`done`にし忘れて後続の作業が停止する経路を、通常のフローの中で解消できる。
- `done`にした入力をGitへ記録する前に、状態遷移と文書の構造を検査できる。
- 完了済みのTASKから追加の実装を再開できない一方、同じ対象の再検証と履歴の参照は継続できる。
- Coreは状態を自動で変更せず、Gitのコミットも強制しないため、既存の責務の境界を維持する。
- TASKを起点とする場合は、人手レビューの後に最終の`check`が1回増える。変更後のTASKの状態を検査するために必要な呼出しである。

## Alternatives

1. **検証の前にTASKを`done`へ変更する**: 検証に失敗したときに、終端状態だけが先行するため採用しない。
2. **人手レビューの前にTASKを`done`へ変更する**: 否決されたときに、記録済みの`done`のTASKを再利用する圧力が生じるため採用しない。
3. **人手レビューの後に`done`へ変更し、`check`を行わずに記録する**: 状態遷移と`Revision History`を変更後の入力で検査できないため採用しない。
4. **`done`のTASKのすべての目的を禁止する**: 完了済みの作業の再検証と履歴の参照を妨げるため採用しない。
5. **`done`のTASKから目的`implement`を許可する**: `done`を終端とするADR-024と矛盾するため採用しない。
