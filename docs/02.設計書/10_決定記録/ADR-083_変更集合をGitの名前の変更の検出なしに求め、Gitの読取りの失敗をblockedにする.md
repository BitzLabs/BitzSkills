# ADR-083 変更集合をGitの名前の変更の検出なしに求め、Gitの読取りの失敗をblockedにする

## Context

[`check`仕様 §5](../../03.詳細設計/03_操作仕様/02_check.md#5-git基準版と変更集合)の変更集合は、基準版からインデックスへの変更、インデックスから作業ツリーへの変更、
未追跡で無視されていないパス、削除とリネームの和集合である。Coreは、Gitの名前の変更の検出（`git diff -M`）を使って変更集合を求める。

[ADR-082](ADR-082_基準版と途中のコミットの読取りで遅延取得をせず、読めない基準版と保護の設定の版を定める.md)の実装の検収で、次のことが分かった（実測）。

1. **部分クローンでの失敗**。名前の変更の検出は、似ているかを比べるためにファイルの内容を読む。ADR-082で遅延取得をやめたので、部分クローンでは欠けた内容を
   読めず、変更集合を求めるGitの呼出しが失敗する。
2. **失敗を黙って空にする**。Coreは、変更集合を求める呼出し（2つの`git diff`と`git ls-files`）の失敗を、診断なしに空の変更集合とする（既存の挙動）。
   そのため、引数なしの`check`の対象の選択、明示したTASKの境界、影響候補が、診断なしに失われる。基準版の仕様文書のパスの一覧と、入れ子のワークスペースの判定に使う
   設定のパスの一覧（[ADR-074](ADR-074_入れ子のワークスペースをTASK境界から除き、経過の記録と計画の置き場を予約する.md)）の読取りも、同じく失敗を空にする。
3. **件数の数え方**。名前の変更の検出を止めると、名前の変更は移動元の削除と移動先の追加の2つの変更になる。`selection.changedPathCount`と
   `selection.excludedCodeTestPathCount`の数え方（`check` §9）は、変更の項目ごとかパスごとかを定めていない。

名前の変更の検出は推定であり、似ているかの閾値と、Gitの版と設定（`diff.renames`、`diff.renameLimit`）で結果が変わり得る。変更されたパスの集合は、
検出の有無で変わらない（名前の変更の移動元と移動先の両方が入る）。文書の対応付けは文書IDで行い（ADR-037）、Gitの名前の変更の情報を使わない。

## Decision

1. **名前の変更を検出しない**。変更集合を求めるGitの呼出しは、名前の変更とコピーの検出をしない（`--no-renames`）。名前の変更は、移動元のパスの削除と、
   移動先のパスの追加として変更集合へ入れる。Gitの設定によらず同じ結果にする。
2. **件数はパスごとに数える**。`selection.changedPathCount`は変更集合のパスの数、`selection.excludedCodeTestPathCount`は、どの逆索引にも該当しない
   コードまたはテストのパスの数とする。名前の変更は、移動元と移動先の2つのパスとして数える。
3. **読取りの失敗をblockedにする**。単一ワークスペースの`check`で、次のGitの読取りが失敗した場合（Gitの起動の失敗、0でない終了コード、出力の形の不正）は、
   空の結果として扱わず、操作を止める。
   - 変更集合を求める読取り（基準版とインデックスの差分、インデックスと作業ツリーの差分、未追跡のパスの一覧）と、入れ子のワークスペースの判定に使う設定のパスの一覧:
     新しい条件`CHECK-GIT-CHANGES-UNREADABLE`（診断コード`SPEC-GIT-CHANGES-001`、重大度`error`、結果への効果`blocked`、発生元`environment`、
     継続単位`stop-operation`）とする。`summary`は`変更されたパスをGitから求められません`とする。
   - 基準版の仕様文書のパスの一覧: ADR-082の決定2の「一覧を読めない」場合として、`SPEC-GIT-BASE-001`（`blocked`）とする。
4. **複合ワークスペース**。複合ワークスペースの操作で同じ読取りが失敗した場合は、`SPEC-MULTI-GIT-001`（`blocked`）とする。
5. **Git不在とは区別する**。Gitを利用できない場合（Git不在）の縮退（[安全な入出力・互換性 §8](../../03.詳細設計/00_共通契約/02_安全な入出力・互換性.md)）は変えない。
   Gitを利用できるのに読取りが失敗した場合だけ、3.と4.を当てる。

## Consequences

- 部分クローンでも、変更集合を求める読取りは内容を読まないので失敗しない。対象の選択、TASK境界、影響候補が、診断なしに失われることがなくなる。
- 名前の変更を含む引数なしの`check`では、`selection`の2つの件数が増える。対象の文書と診断は変わらない。結果が変わるので、Core 1.0の確定の前に入れる。
- Gitの版と設定によって、変更集合が変わらなくなる。
- 診断レジストリに条件を1つ加える。文言は、利用者の承認を得て決める（ADR-062）。
- `check`仕様 §5、§9、診断レジストリを改める。適合fixtureを足す。読取りの失敗は準備の処理で作れないので、Coreの単体試験で確かめる。

## Alternatives

1. **全体検査へ縮退する**: Git不在と同じく、引数なしの`check`を全体検査にする。明示したTASKは境界を検査できないので別の扱いになり、規則が操作の種類で分かれる。
   採らない（ユーザーの決定）。
2. **名前の変更を検出し、1件と数える**: 今の数え方を保てるが、部分クローンで内容を読めない場合が残り、結果がGitの版と設定に依存する。採らない（ユーザーの決定）。
3. **変更集合の読取りだけを直す**: 同じ種類の問題（失敗を黙って空にする）が、ほかの2つの読取りに残る。採らない（ユーザーの決定）。
