# ADR-068 評価の停止の分類と後継台帳による継続を定める

## Context

提案31のR04（製品6スキルの発火評価）は、2026-10-11から2026-10-27までに公開92枠と保持2枠しか確定できなかった。
進捗の記録とコミットから、次の4つが遅れの主因と判断した（調査は
[公開92枠の連続した評価失敗の調査](../../../evals/skills/results/2026-10-27-public-survey-failure-streak/report.md)）。

1. 公開評価の58〜92枠目の35枠が、同じ型の取得失敗（`primary_capture_stopped`、`ValueError`）で連続して失敗した。
   起動を止める規則がなく、原因分析を全件の後へ回したため、SE-030〜SE-046の17ケースに有効な測定が1件もない。
2. 保持評価は、例外の原因を問わず`evidence_invalid`として台帳を永久停止する。2026-10-20の最初の停止は、
   評価基盤が未知の通知と配信元のモデル一覧の変化を拒否したもので、スキルの欠陥ではなかった。
   それでも同じ枠を再試行できず、継続のための専用コード（`production_heldout_continuation.py`）を作るまで5日かかった。
3. 台帳の契約が、日付ごとに変わるsource、資源証明、校正に結び付いている。日付が変わると同じ台帳を使えず、
   条件phaseの切替え（提案31のD01〜D06）を新しく開発していた。
4. 独立検分が、同じuidのローカル攻撃者によるファイルの差替え競合まで指摘し続け、是正の往復が終わらない。
   評価基盤が誰から何を守るかが決まっていない。

ADR-060は評価契約と独立検分の境界を固定したが、停止した後の継続と、評価基盤自体の障害の扱いは決めていない。

## Decision

### D1. 停止の原因を3つに分ける

停止と評価失敗には、原因の区分を必ず付ける。

| 区分 | 停止理由 | 意味 |
|---|---|---|
| `safety` | `unsafe` | 禁止操作、資源の改変など、評価対象または評価基盤が安全条件を破った |
| `evidence` | `evidence_invalid`、`independent_rejected`、`unknown_event` | 原記録を信用できない。評価基盤の障害か、改ざんか、未知の挙動かが未確定 |
| `harness` | `source_drift`、`resource_drift`、`provider_drift`、`quota_exhausted`、`auth_unavailable`、`storage_failure`、`operator_interrupted` | 評価対象と無関係な、評価環境の障害または変化 |

評価基盤のコードは、評価環境の障害を判定できる箇所で`HarnessFault`（区分と理由を持つ例外）を送出する。
それ以外の例外は`evidence_invalid`とする。

### D2. 評価基盤が原因の停止は、記録を残して同じ枠を1回だけ再試行できる

- `safety`の停止は永久に停止する。再試行しない。
- `harness`の停止と評価失敗は、原因の証拠を記録した再試行の承認（retry authorization）があれば、同じ枠を再試行できる。
- `evidence`の停止と評価失敗は、独立した文脈の検分が原因を評価基盤の障害と判断した記録を加えた場合だけ、再試行できる。
- 再試行は1枠につき1回までとする。2回目の失敗は本物の結果として扱う。
- 再試行の総数は、台帳の契約の`harnessRetries`（0〜24）までとする。予算を返却せず、元の試行の原記録と台帳のeventは消さない。
- 再試行は人または運用者が承認するものであり、自動の再試行（`automaticRetries`）は引き続き0とする。

### D3. 台帳の条件から日付を切り離し、停止と日付変更の後は後継台帳で続ける

- 新しい台帳（版`heldout-matrix-ledger-0.3.0`）の契約は、日付で変わる値（`sourceCommit`、実行契約・配置・入力契約のhash、
  校正、コンテキストの日付）を持たない。代わりに、評価の意味を決める値だけから計算した`conditionSha256`を持つ。
  その範囲は、ケースと公開入力の内容、製品の72資源、SDK、runtime、判定Schema、固定ソースのうち日付ごとの2ファイル
  （コンテキストと校正のmanifest）を除くもの、コンテキストのうち日付の項目を除く内容、モデル、予算、時間制限である。
- 当日の校正と資源証明は、枠を予約するeventに`dailyProofSha256`として記録する。1つの枠の途中で日付の証明を替えない。
  当日の校正を起動前に要求する規則は維持する。
- 日付が変わっても`conditionSha256`が同じなら、同じ台帳で続ける。
- 台帳が停止した場合や、campaignを替える必要がある場合は、前の台帳を`predecessor`として指定した後継台帳を作る。
  後継台帳は、前の台帳を読取り専用で検査し、消費、終端、再試行の資格を全eventから再計算する。
  利用者や運用者が申告した数値は使わない。
- 後継を作るときは、前の台帳の場所へ固定名の印（`condition-seal.json`）を新規作成で置く。
  旧版の読取り処理はこの印を未知のファイルとして拒否するので、旧い入口からは追記できない。
- 保持評価の現在の継続台帳（版0.2.0、2枠確定）は、この後継台帳で引き継げる。提案31のD02〜D06（条件phaseのregistry、
  seal、activation）は、この決定で置き換える。D01の読取り専用部品は、前の台帳の検査に再利用する。

### D4. 同じ型の失敗が続いたら、次の枠を起動しない

- 直前の2枠が、同じ段階・同じ型で評価失敗した場合、次の枠を予約する前に止める。予約、起動、予算の消費はしない。
- 続けるには、原因を調べた記録（失敗の確認記録）を置く。記録には、調べた枠、判断、続ける理由を書く。
- 止めることは台帳の停止ではない。台帳には何も書かない。

### D5. 評価基盤の脅威モデルを限定する

評価基盤が防ぐものは次の3つとする。

- 入力、資源、ソース、実行環境の意図しない変化
- 評価対象のモデルや運用するエージェントによる、結果の自己申告や原記録の書換え（通常の道具で行えるもの）
- 停止、中断、保存の失敗による、記録の欠落や二重計上

次は対象外とする。

- 同じuidまたはrootの権限を持つ攻撃者による、ファイルシステムの競合（hardlinkの差替え、lockファイルの名前の差替え、
  読取り中のinodeの交換など）
- 配信元やCLI自体の改ざん

独立検分で対象外の指摘を受けた場合は、対象外とする理由を1行で記録して閉じ、是正の往復を行わない。
既存の検査は削除しない。

## Consequences

- 評価基盤の障害が1回起きても、台帳の永久停止と専用の継続コードの開発が不要になる。
- 日付の変更で台帳の条件が変わらないので、日付ごとのphaseの切替えが不要になる。
- 連続した取得失敗で予算を消費し続けることがなくなる。
- 再試行を許すため、同じ枠で2回の試行の原記録が残ることがある。集計は最後の試行を採り、元の試行も件数として残す。
- 脅威モデルの限定で、対象外の攻撃には弱くなる。評価の結果を出荷の判定に使う前に、人が原記録を確認する（ADR-060）ことで補う。
- 既存の版0.1.0と0.2.0の台帳、実行契約0.1.0と0.2.0の処理は変更しない。

## Alternatives

- **条件phaseのregistry、seal、activationを完成させる（提案31のD02〜D06）**: 日付ごとに独立検分、seal、activationが必要で、
  停止の後の継続には別の設計が要る。日付変更と停止を同じ後継台帳で扱えるD3を採る。
- **停止のたびに専用の継続台帳を作る**: 2026-10-24の`production_heldout_continuation.py`のやり方である。
  停止のたびに設計と検分が要り、遅れの主因になった。
- **すべての停止で再試行を許す**: 安全違反を再試行で上書きできてしまう。`safety`は永久停止に残す。
- **失敗を分母から除く**: 結果を良く見せる操作になる。失敗は区分を付けて残す。
