# ADR-045 実行環境と配布物の確定

## Context

[ADR-009](ADR-009_小規模チーム向け軽量コアとEARS-AI中核化.md) Decision 9と
[ADR-016](ADR-016_Agent-Plugins準拠の複数プラグイン配布.md)は、Agent Plugins 1.0.0パッケージを主経路、
Python + PyPI + `uv`をCIと非LLM環境の代替経路とすることを確定している。しかし、次が確定していない。

- 対応するPythonの下限version
- 配布物名とCLI実行体名
- 第三者依存の許容範囲と、YAML解析の実装方針
- Gitの利用形態と下限version

[doctor仕様 §3](../../03.詳細設計/03_操作仕様/04_doctor.md#3-検査順序)の検査1は
「Core実行体、Python version、起動」でversion不適合を`blocked`とするが、比較すべき下限が規範に存在しない。
この検査は現状のままでは実装できない。

また、`bitz.yaml`は「UTF-8のYAML 1.2 subset、custom tag・anchor・alias・merge key禁止、重複keyをerror」と
定めているが、広く使われるYAML実装の既定挙動はこれと一致しない。実装が既定のloaderをそのまま使うと、
仕様が禁止した構文を受理し、`SPEC-CONFIG-SCHEMA-001`を返すべき入力を通す。

## Decision

1. **実行環境**: Core 1.0はCPython 3.11以上を対象とする。doctorの検査1はこの下限と比較し、
   下限未満を`SPEC-DOCTOR-CORE-001`／`blocked`とする。3.10以下はEOLまたはEOL間近であり対象にしない。
   実装は3.11で動作する構文と標準library APIだけを使い、より新しいversionでのみ利用可能な機能へ
   依存しない。
2. **配布物**: PyPI distribution名を`bitz`、import package名を`bitz`、CLI実行体名を`bitz`とする。
   Agent Plugins経路のplugin IDは`bitz-core`と`bitz-sdd`とし、`bitz-core`が本CLIを同梱または参照する。
   plugin IDとPyPI distribution名を同一にしない。利用者から見た起動commandはどの経路でも`bitz`とする。
3. **依存**: 実行時依存を標準libraryとYAML解析だけに限る。YAMLはYAML 1.2を解釈できる第三者libraryを
   1つだけ使用し、exact versionでlockする。loaderは安全読取り専用とし、custom tag、anchor、alias、
   merge key、重複key、暗黙の日時型変換をCore側で明示的に拒否してから値を解釈する。
   libraryの既定挙動を仕様の代わりにしない。
4. **Git**: GitはCLI実行体を`argv`で起動して利用し、shellを介さない。libgit2 bindingとGit実装の
   再実装を採用しない。下限はGit 2.30とし、下限未満または実行不能はGit不在として
   [安全な入出力・互換性 §8](../../03.詳細設計/00_共通契約/02_安全な入出力・互換性.md#8-git不在時)の
   縮退契約を適用する。連合では`SPEC-MONOREPO-GIT-001`／`blocked`とする。
5. **network**: Core実行体は通常操作でnetworkへ接続しない。導入と更新のnetwork利用は
   package managerとclientの責務とし、Core自身は依存物を動的取得しない。
6. **lockと再現性**: 依存はlock fileで固定し、公開物をsource commitとbuild手順へ対応付ける。
   下限version、配布物名、依存の追加・削除はCore minor以上の変更とし、patchで変えない。

## Consequences

- doctorの検査1が実装可能になり、下限未満の環境で一貫して`blocked`を返せる。
- YAML解析の責務がlibraryではなくCoreにあることが明確になり、禁止構文の受理を適合fixtureで検査できる。
- 実行時依存が1つに収まり、供給網の面が小さくなる。lockと固定の対象も少ない。
- Gitをsubprocessで使うため、Git不在・下限未満・PATH不在を同じ縮退経路で扱える。
  一方でGit操作ごとにprocess起動costがかかる。性能予算は既にこの前提で測定する。
- CPython 3.11未満しか使えない環境はCore 1.0の対象外になる。

## Alternatives

1. **下限をCPython 3.9または3.10とする**: いずれもEOLまたはEOL間近であり、security更新を受けられない
   環境を1.0の対象にすることになる。採用しない。
2. **YAMLを自前実装する**: 仕様が要求するのは1.2のsubsetだけなので不可能ではないが、
   Core 1.0の中心価値はEARS-AIとContext解決であり、YAML実装の正しさへ工数を割く理由がない。
   第三者libraryを安全読取りで使い、禁止構文をCoreで拒否する方が検査可能である。採用しない。
3. **libgit2 bindingを使う**: native依存が増え、配布物とbuildの再現性が難しくなる。
   `uv tool install`の単純さも失われる。採用しない。
4. **単一バイナリを1.0の主経路にする**: ADR-009 Decision 9が需要確認後の検討としており、
   ADR-016がAgent Plugins経路を主とした。本ADRはこれを変更しない。
5. **下限versionをdoctorの設定可能値にする**: 環境ごとに適合判定が変わり、
   「同じ入力とversionから同じ結果」という契約と両立しない。採用しない。
