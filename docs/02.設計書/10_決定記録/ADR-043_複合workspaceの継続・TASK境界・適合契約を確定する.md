# ADR-043 複合ワークスペースの継続・TASK境界・適合契約を確定する

## Context

ADR-041とADR-042により、検証対象ごとの`verify`の証跡、明示したレポートの保存、ワークスペースの同一性、全体事前検査、
正規の所有境界、公開する結果スキーマ、リソースの上限、通常の性能fixtureを確定した。一方、Core 1.0の受入までに、
横断参照の失敗の診断の優先順位、ワークスペースが非成功になった後の継続の範囲、TASKのディレクトリの接頭辞とシンボリックリンク、
利用側のロールバック、絶対上限に達したときの計算量とメモリ、期待JSONの適合matrixを確定する必要がある。

ワークスペース単位で一律に停止すると、無関係な文書とテストを検査できない。逆に、失敗の後も一律に継続すると、不完全な
強い関係の閉包から、コンテキストや`verify`の計画を作る。継続の可否は、全体事前検査と、文書、対象、テスト割当ての依存の単位に
分けなければならない。

TASK境界では、シンボリックリンクを解決した後の実際のパスを許可の接頭辞との比較に使うと、字句上は列挙していないパスへ許可が広がる。
ただし、字句の比較だけでは、別のメンバーへ解決するシンボリックリンクを防げないため、許可の集合と所有の集合を別々に検査する必要がある。

## Decision

1. 関係のエッジは、構文と型、修飾IDの字句、非修飾の横断参照、未知のワークスペース、存在するワークスペース内の参照先の不在、
   参照元／参照先の型の不適合の順に検査し、最初の1つの原因だけを主診断とする。未知のワークスペースまでは診断`SPEC-MONOREPO-REF-001`、
   存在するワークスペース内の強い関係の参照先の不在は診断`SPEC-RELATION-MISSING-001`、存在する
   参照先の型の不適合は診断`CTX-RELATION-TYPE-001`とする。`CTX-RELATION-MISSING-001`は、公開する結果では使わずに予約する。
2. ADR-042の全体事前検査が非成功の場合だけを全停止の境界とし、メンバーの処理、コンテキストの解決、コマンドの実行を開始しない。
   事前検査を通過した後は、`check`は文書と参照元のエッジ、`context`と`verify`は対象の強い関係の閉包、`verify`のコマンドは
   テスト割当てを、それぞれ独立した処理の単位とし、依存しない後続の処理を決定論的な順序で継続する。
3. 根本の原因を持つ単位とは別の対象または`doctor`の検査項目が、依存する出力を得られず実行できなくなった場合だけ、
   診断`SPEC-MONOREPO-DEPENDENCY-001`（`blocked`）を返す。すでに同じ単位に、具体的な不在、型、状態、カバレッジの
   診断がある場合は、重複させない。
4. TASKの`changes`のファイルとディレクトリの接頭辞は、正規化した、字句上のGitのパスの完全一致、またはパスのセグメント単位の接頭辞で
   許可を判定する。シンボリックリンクの解決先へ許可を拡張しない。宣言したパスと変更パスの所有の判定は別に行い、追加は現在版、
   削除は基準版、変更とシンボリックリンクの変更は基準版と現在版の双方を正規化する。リネームは、削除と追加の2つのパスとして扱う。
5. JSONの利用側は、`schemaVersion`のメジャーバージョンを確認した後、`workspace`だけを持つ単独結果と、`federation`および
   `workspaces`だけを持つ全体結果を、排他的に識別する。修飾ID、レポート名、現在のディレクトリから形式を推測しない。
   複合ワークスペースの生成側より先に、利用側を二重読取りにし、アダプターとCIは`monorepo.v1`を確認してから全体操作を有効にする。
6. ロールバックは、カタログ、メンバーの設定、修飾された関係、カバレッジ、TASKの参照、CIの全体操作、対応機能のゲート、レポートの利用側を、
   同じリリースの単位で戻す。過去のレポートを書き換えず、単一ワークスペースと複合ワークスペースの成果物の系列を混ぜない。後続の変更を失わずに
   全体を戻せない場合は、元へ戻す方向の移行を自動では行わず、複合ワークスペースの状態を、戻さずに新しい変更で修正する。
7. 全体の索引のメモリを、ファイル、規範文、エッジ、トレース、コマンドの入力のグラフの大きさに対して線形とする。検証対象のコンテキストは、
   到達済みの集合を使って、到達するグラフに対して線形に解決し、全体操作の`verify`は、検証対象ごとの完全なコンテキスト一式を同時には保持せず、
   コンテキストのハッシュ値、規範文、テスト割当ての参照へ縮約して次の検証対象へ進む。全組合せのmatrixを作らない。
8. リソースの次元ごとに、ほかの次元を通常の規模に保った`limit - 1`、`limit`、`limit + 1`のfixtureを作る。
   次元を最大にしたfixtureは、基準環境で、CoreのピークRSSの増分1 GiB以下、2 GiBのメモリの上限の下で、正常に終了させる。
   これは通常のfixtureの200 MiBの目標を緩和せず、公開するSLOではなく、絶対上限に対する安全の受入条件とする。
9. 同名のローカルID、横断関係、診断の優先順位、未登録の設定、シンボリックリンク、TASKの接頭辞、継続、複数のコンテキストの`verify`、
   共有するテスト割当て、0件、同一性、Git不在、リソースの境界、レポートの副作用、利用側、ロールバックを、バージョン管理するfixtureと
   期待JSONへ固定する。`durationMs`など指定済みの非決定の値だけを共通の正規化器で除外し、fixture固有の除外を許さない。
10. 本決定は、ADR-042でP2として残した契約を補完し、同ADRの同一性、スキーマ、リソースの数値、性能のSLOを変更しない。
    最初の失敗で停止するオプション、並列のスケジューラー、移行モード、ワークスペースの自動リネーム、元へ戻す方向の移行の自動実行は追加しない。

## Consequences

- 全体の信頼境界の失敗を越えず、局所的な不適合の後も、無関係な検査とテストを継続できる。
- 参照先の不在の診断が操作ごとに分岐せず、同じエッジへ複数のコードを返さない。
- TASKのディレクトリの接頭辞が、シンボリックリンクの解決先へ暗黙に拡張されず、基準版側だけに存在するパスも検査できる。
- 利用側の更新の順序、結果の形式の判別、ロールバックできる条件が明示され、単一ワークスペースの結果と複合ワークスペースの結果を誤って集約しない。
- 絶対上限は、件数だけでなく、線形な実装の構造、ピークRSS、期待JSONで、受入を判定できる。
- Core 1.0の実装は、適合matrixをすべて通過するまで、受入完了にならない。

## Alternatives

1. **ワークスペースが1つでも非成功なら、最初の失敗で停止する**: 無関係なメンバーの検査の証跡を失い、既存の逐次継続の方針と矛盾する。
2. **すべて継続して最後に集約する**: 不完全な強い関係の閉包から、コンテキストまたはコマンドの計画を構成しうる。
3. **TASKの接頭辞を、シンボリックリンクの解決後の実際のパスへ展開する**: 宣言していない字句上のパスまで、許可の集合へ入る。
4. **複合ワークスペースの結果を、修飾IDの有無で判別する**: 空の結果や診断だけの結果を、安定して識別できない。
5. **全検証対象の完全なコンテキスト一式を同時に保持する**: 検証対象の数と閉包の大きさの積で、メモリを消費する。
6. **fixtureごとに、期待JSONの除外するフィールドを選べるようにする**: 実装の差を、適合として隠せる。
