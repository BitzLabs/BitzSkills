# ADR-076 上限の値を設定で小さくできるようにし、実寸の上限の検証を手動にする

## Context

Coreの上限の多くは固定の値である（[複合ワークスペース仕様](../../03.詳細設計/02_仕様文書モデル/05_複合ワークスペース仕様.md) §10の次元、
診断レジストリの`SPEC-INPUT-LIMIT-001`の各規則、`verify`の引数列の上限）。上限の境界を確かめる適合fixture
（`MULTI-020-*`、`MULTI-021-*`、`MULTI-041-*`）は、上限と同じ大きさの入力を実際に生成する。

`fixtures/conformance/selection.py`が持つCIの実測から求めると、Step 5までの742件のうち、この28件が所要時間の約88%
（約804秒。そのほかの714件は約109秒）を使う（[提案34](../../04.提案資料/34_Coreと評価処理の現状整理と今後の方向性.md) §12.11）。
Gate Bの認定とCIは、この28件を毎回実行する。Core 1.0の確定までに、ADR-072〜075の実施で、Gate AとGate Bの再認定を繰り返す。

[ADR-048](ADR-048_適合fixtureの生成入力とGit構造の準備の処理を確定する.md)の`Decision`の3番目の項目は、実寸の生成の記録をGate Aの認定に求める。
[ADR-056](ADR-056_適合試験の分割実行とCIのGate-B集約を確定する.md)の`Decision`の2番目の項目は、認定は必ず`full`の全対象を使うと定め、
`Alternatives`で「境界の値を縮める」案を、実寸の保証を失うため採らないとした。当時は、上限の値を変える手段がなく、
境界の判定を確かめるには実寸の入力が要った。

## Decision

1. **設定**。`.spec/bitz.yaml`に`limits`を加える。`limits`の各キーは、対応する上限の値を、1以上、現在の値以下の整数で指定する。
   省略したキーは現在の値とする。現在の値を絶対上限とし、それより大きい値は設定の不適合とする。
2. **対象**。次の上限を対象にする。キーの名前と、既存の`context.maxDocuments`などとの関係は、仕様の改訂で定める。
   - 複合ワークスペースのスナップショット全体の次元（`specFileCount`、`inputBytes`、`statementCount`、`relationEdgeCount`、
     `traceEntryCount`、`commandDefinitionCount`、`verifyBindingCount`）と、除外のパスの数
   - 入力の上限（単一ワークスペースの仕様文書のファイル数、仕様文書1件の大きさ、フロントマターの大きさ、
     1つの文書の規範文の数、1つの文書の配列の項目の数）
   - `verify`の`{tests}`を展開した後の引数列の上限（要素数、1要素の大きさ、合計の大きさ）
3. **対象にしないもの**。`bitz.yaml`の大きさの上限（設定を読む前に当てる）と、合否に現れない内部の定数は、設定にしない。
   環境変数とCLIの引数では、上限を変えられない。
4. **複合ワークスペース**。スナップショット全体に当てる上限は、ルートワークスペースの設定だけで決める。
   メンバーの設定の扱いは、仕様の改訂で定める。
5. **`doctor`**。`doctor --format json`の結果に、実際に使う上限の値を加える。
6. **適合fixture**。上限の境界は、小さい上限を設定したfixtureで確かめる。既定の値が仕様のとおりであることは、
   5.の`doctor`の結果を固定するfixtureで確かめる。
7. **実寸の検証（ADR-048とADR-056の部分改訂）**。実寸の上限のfixtureと`fixtures/validate_scale.py`は残すが、
   Gate A、Gate B、CIの認定の対象から外し、手動で実行する検証とする。本項目は、ADR-048の`Decision`の3番目の項目のうち
   「Gate Aの認定には後者の記録を必要とする」と、ADR-056の`Decision`の2番目の項目のうち「認定は必ず`full`の全対象を使う」を部分改訂する。
   認定は、実寸の上限のfixtureを除く全対象を使う。ADR-048とADR-056のほかの`Decision`は変えない。
8. **リリースの前の実寸の検証**。Gate Cの最終の集約の前に、確定したコミットで実寸の検証を手動で1回実行し、結果を認定記録に残す。

## Consequences

- 適合試験の全件の所要時間が、CIの実測の予測で約913秒から約110秒になる。Gate Bの再認定とCIが速くなる。
- 設定のないワークスペースの結果は変わらない。`limits`は今は未知のキーとして警告になるので、追加であり、既存の結果を壊さない。
- 上限を大きくすることはできない。大きな入力からCoreを守る上限と、性能の受入の条件の前提は変わらない。
- 境界の判定の正しさは、小さい上限のfixtureで毎回確かめる。Coreが実寸の入力を扱えることは、手動の検証とGate Cの前の1回でだけ確かめる。
  その間に入った変更で実寸の入力を扱えなくなっても、すぐには検出されない。
- `contextDigest`の材料に`limits`を含めるかは、仕様の改訂で定める（`multiWorkspace.maxMembers`は含めていない）。
- 仕様（ワークスペース・設定仕様、複合ワークスペース仕様 §10、診断レジストリ、`doctor`仕様、スキーマ、適合fixture仕様）、
  `certify_gate_a.py`、`ci_gate_b.py`、CIの設定を改める。小さい上限のfixtureを追加し、Gate Aを再認定する（ADR-051）。

## Alternatives

1. **上限を大きくもできるようにする**: 安全の上限と性能の受入の条件の前提の外で動くことを許す。採らない（ユーザーの決定）。
2. **実寸のfixtureをGateの条件に残す**: 所要時間が減らない。採らない（ユーザーの決定）。
3. **実寸のfixtureをやめる**: Coreが実寸の入力を扱えることを確かめる手段がなくなる。採らない。
4. **環境変数で上限を変える**: 同じ入力から違う結果が出る。fixtureとして固定しにくい。採らない。
5. **Core 1.0の後に行う**: 追加なので後でも壊さないが、Core 1.0の確定までの再認定の時間を減らせない。採らない（ユーザーの決定）。

## Notes

- 提案34の論点11の裁定である。2026-11-16に利用者が、値は小さくできるだけとすること、実寸の検証を手動にすること、Core 1.0で行うことを決めた。
- `Decision`の8番目の項目（Gate Cの前に実寸の検証を1回実行する）は、起票者の案を、承認のときに利用者が確認した。
- `Decision`の5番目の項目の`doctor`の結果の`limits`は、設定が`limits`を宣言している場合だけ返す（`doctor`仕様 §7）。
  `Consequences`の「設定のないワークスペースの結果は変わらない」を保つためである。
