# ADR-073 複合ワークスペースの横断する参照をメンバーからルートへの向きに限る

## Context

[複合ワークスペース仕様](../../03.詳細設計/02_仕様文書モデル/05_複合ワークスペース仕様.md) §4と§5は、カタログの中のどのワークスペースの文書も、
修飾IDで参照することを許す。メンバーの文書が別のメンバーの文書を`refines`することもできる。

利用者の構想は、複合ワークスペースをピラミッドの形とし、子どうしの連携を親の仕様文書が受け持つことである
（[提案34](../../04.提案資料/34_Coreと評価処理の現状整理と今後の方向性.md) §12.7）。現在の適合fixtureを横断する参照の向きで数えると、
メンバーからルートが73件、メンバーから別のメンバーが35件、ルートからメンバーが13件であり（正規表現による概数）、利用の形はすでに
メンバーからルートが中心である。横断するTASKをルートのTASKから順序付ける規則（§5）も、すでにこの形である。

メンバーから別のメンバーへの参照を後から禁じると、通っていた検査が`failed`になる。規則はCore 1.0の確定の前に入れる。

## Decision

1. **階層**。Core 1.0の複合ワークスペースは、ルートワークスペースとメンバーの2層のままとする。
2. **メンバーからの参照**。メンバーの文書の強い関係（`requires`、`refines`、`addresses`、`supersedes`）と`tests[].covers`が
   参照できるのは、同じワークスペースの文書と規範文、およびルートワークスペースの文書と規範文だけとする。
3. **ルートからの参照**。ルートワークスペースの文書がメンバーの文書を参照できるのは、ルートのTASKの`requires`がメンバーのTASKを指す場合だけとする。
   ルートのREQ、TECH、ADRの強い関係と、ルートの文書の`tests[].covers`は、メンバーの文書と規範文を参照できない。
4. **診断**。2.と3.に反する参照は、新しい診断`SPEC-MULTI-DIRECTION-001`（重大度`error`、結果への効果`failed`）とする。
   参照先が存在しない場合と、種別の組合せが不正な場合の既存の診断は変えない。
5. **弱い関係**。`related`は、今と同じくどのワークスペースの文書も参照できる。`related`は閉包を増やさず、検査の合否に影響しないためである。
6. **メンバーどうしの契約**。2つのメンバーの間の契約は、ルートワークスペースのREQまたはTECHに置く。契約を実現するメンバーは`refines`で、
   契約を使うメンバーは`requires`で、ルートの文書を参照する。
7. **変えないもの**。修飾IDの形、所有境界、全体操作、カタログ全体から作る索引、結果の形は変えない。索引を参照できる範囲に限る作り直しと、
   3層以上の階層は、Core 1.0の後に別の決定で扱う。

## Consequences

- ワークスペースをまたぐ強い関係の循環は、ルートのTASKとメンバーのTASKの`requires`の間でしか起きなくなる。
- 契約の変更の影響が読みやすくなる。ルートの変更はメンバーへ及び、メンバーの変更は別のメンバーへ及ばない。
- 2つのメンバーだけに関わる取決めも、ルートワークスペースに文書を置く必要がある。
- 仕様（複合ワークスペース仕様 §4、§5、§6、§11、関係・トレースモデル、診断レジストリ）を改める。
- メンバーから別のメンバーへの参照、またはルートからメンバーへのTASKの`requires`以外の参照を通過としている適合fixtureの期待値を改め、
  新しい診断の適合fixtureを追加する。Gate Aを再認定する（ADR-051）。

## Alternatives

1. **今の規則のままCore 1.0を確定し、後で禁じる**: 公開の後に、通っていた検査を`failed`に変えることになる。採らない（ユーザーの決定）。
2. **3層以上の階層までCore 1.0で決める**: 修飾IDの形、入れ子のカタログ、全体操作を広く書き換える。Core 1.0の確定が遅れる。採らない（ユーザーの決定）。
3. **`related`も禁じる**: `related`は検査の合否に影響しないので、禁じても構造は単純にならない。採らない。

## Notes

- 提案34の論点9の裁定である。2026-11-16に利用者が「2層のまま、メンバーから別のメンバーへの参照を禁じる」案を選んだ。
- `Decision`の3番目の項目（ルートからの参照はTASKの`requires`だけ）と5番目の項目（`related`を禁じない）は、起票者の案を、承認のときに利用者が確認した。
