# ADR-007 コア実行体の実装言語と配布形態

## Context

[03_CLI統合設計.md](../03_CLI統合設計.md) の `bitz` コマンド群と、[06_運用設計.md](../06_運用設計.md) の「同じ処理を手動コマンドでも実行可能にする」という要求は、AI CLIに依存しないスタンドアロン実行体の存在を前提とする。実装言語と配布形態が未決定ではPhase 1の見積りとCI設計を確定できない。

スキル・コマンド群はプラグインマーケットプレイス形式で配布する。マーケットプレイスはインストーラを実行しないため、コア実行体の入手は別チャネルとなる。2層の分離と入手経路は [ADR-008](ADR-008_プラグイン配布とコア実行体の入手経路.md) に定める。本ADRはコア実行体そのものの実装言語とパッケージ形態を扱う。

## Decision

**Pythonで実装し、PyPI配布 + `uv` による導入を主経路とする。**

| 項目 | 決定 |
|---|---|
| 実装言語 | Python |
| 最小対応版 | 3.12。CIでは 3.12 / 3.13 / 3.14 を試験する |
| 主配布経路 | PyPI配布。`uv tool install bitz` による常設導入、`uvx bitz` による一時実行 |
| 補助成果物 | PyInstaller等による単一バイナリ。Python未導入かつ `uv` を導入しない環境向けにリリース成果物として提供する |
| 入手経路との関係 | [ADR-008](ADR-008_プラグイン配布とコア実行体の入手経路.md) 候補1（前提条件として別途導入）と組み合わせる |
| 既存.NET資産 | BitzParser / BitzAstFoundation は再利用しない。EARS-AI Parserは新規実装とする |

主配布経路と補助成果物は同一コードベースから生成し、[03_CLI統合設計.md](../03_CLI統合設計.md) §10 の適合試験を両形態へ適用して同一判定を保証する。

### ネットワーク前提

初回導入時のみネットワークを要し、導入後の検証実行はオフラインで完結する。これは [06_運用設計.md](../06_運用設計.md) §10.2 の「コアフローはネットワーク切断時もローカル範囲で継続できる」を満たす。

ネットワークが完全に隔離され、パッケージレジストリへ到達できない環境への配布は本決定の対象外とする。必要が生じた場合は、単一バイナリの手動配置手順を別途定める。

### 理由

- 本設計が要求する処理の大半はMarkdown字句解析、YAML/JSON Schema検証、DAG解析、トレース突合、レポート生成であり、Pythonの標準・準標準ライブラリで過不足なく実装できる。
- YAMLのラウンドトリップ保存により、「未知の拡張データを保持し無断で削除しない」要件（[01_共通アーキテクチャ.md](../01_共通アーキテクチャ.md) §6）を実装しやすい。
- 性能律速となりうる多言語コード解析（L2 Structural）は、C実装のtree-sitterバインディングへ委ねられる。純Pythonでの解析性能がSLOの制約にならない。
- `uv` によるロックファイルとハッシュ検証が、[07_セキュリティとガバナンス.md](../07_セキュリティとガバナンス.md) §6 の依存固定・脆弱性検査要件と整合する。
- AI開発の周辺ツール群と同居しやすく、貢献者を得やすい。

### 必須の実装制約

言語選択に伴い、次を Phase 1 の完了条件へ追加する。いずれも本設計の既存要求を満たすために必要であり、省略できない。

| 制約 | 理由 | 対応 |
|---|---|---|
| 全ファイル入出力で `encoding="utf-8"` を明示し、CIで未指定呼出を静的検出する | [02_specディレクトリ仕様.md](../02_specディレクトリ仕様.md) §10 のUTF-8必須要件。既定エンコーディングのロケール依存はWindowsで顕在化する | lint規則で強制する。実行時の `PYTHONUTF8=1` に依存しない |
| アトミック置換に `os.replace` を用いる | 「読込・検証・一時書込み・再検証・置換」（[01_共通アーキテクチャ.md](../01_共通アーキテクチャ.md) §7）。同一ファイルシステム上では3OSともアトミック | 一時ファイルを対象と同一ディレクトリへ作成する |
| ロックはクロスプラットフォーム実装へ集約する | `fcntl` はWindowsに存在しない。[ADR-006](ADR-006_runIdの形式と並行実行制御.md) の排他制御 | `filelock` 等の単一APIに集約し、OS APIを直接呼ばない |
| 依存をロックファイルで固定しハッシュ検証する | [07_セキュリティとガバナンス.md](../07_セキュリティとガバナンス.md) §6 | ロックファイルをリポジトリへコミットし、CIでハッシュ検証付きインストールを行う |
| 出力の決定論性を保証する | [05_QA品質保証設計.md](../05_QA品質保証設計.md) §8 の再現性要件 | 集合の反復順序に依存しない。JSON出力はキー順を固定し、浮動小数の書式を固定する |
| CLI起動経路を遅延importで最小化し、起動時間を計測対象に含める | [06_運用設計.md](../06_運用設計.md) §10 の `bitz doctor` 10秒目標 | 目標に対する余裕は大きいが、回帰を検出できるようにする |
| 対応Python版の範囲をmanifestとCIの双方で強制する | 処理系差による判定差を排除する | 最小版未満では起動時に `blocked` を返す |

## Consequences

- Phase 1 のスコープに、上表の実装制約とそのCI強制が加わる。
- 設計書本文は実装言語に依存しないため、[03_CLI統合設計.md](../03_CLI統合設計.md) の論理操作の意味は変わらない。アダプター境界は配布形態から独立している。
- BitzParser / BitzAstFoundation は再利用しない。EARS-AI Parser の新規実装コストを Phase 1 の見積りへ計上する。

## Alternatives

### 候補A: Node.jsパッケージ

対象AI CLIの多くがNode.js環境を前提とするため追加ランタイムが不要という利点があった。却下理由は、Python候補と比較して決定的な優位がなく、テキスト解析・スキーマ検証まわりの資産で下回るため。

### 候補B: 単一ネイティブバイナリ（Go / Rust）

ランタイム非依存、起動が速い、配布ハッシュ検証が単純という利点があった。却下理由は、プラットフォーム別ビルドとリリース運用のコストが、本設計の性能要求に対して過剰であるため。ただし本決定の補助成果物として単一バイナリを生成するため、この利点の一部は取り込んでいる。

### 候補C: .NET（BitzLabs既存資産との整合）

BitzParser / BitzAstFoundation を再利用できる可能性が唯一の優位点であった。却下理由は、対象AI CLIの利用者環境に.NETランタイムが存在する保証がなく、再利用の利得がこの制約を上回らないため。

### 候補D-1b単独: PyInstaller単一バイナリのみ

却下理由は、更新のたびに全プラットフォーム分のビルド・配布が必要となり、`uv` 経由の更新に比べ運用コストが高いため。補助成果物としては維持する。

### 候補D-1c: zipapp / shiv

却下理由は、単一ファイルでありながらPython処理系を要求するため、D-1a・D-1bのいずれに対しても明確な利点がないため。
