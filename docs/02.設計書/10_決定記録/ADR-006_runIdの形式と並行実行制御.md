# ADR-006 runIdの形式と並行実行制御

## Context

runIdの例が `RUN-20260825-001` という日付＋連番形式であった。この形式は採番時に既存IDの走査を要し、複数プロセスが同時に採番すると衝突する。一方、監査設計は「同一IDのレポート上書き禁止」を要求しており、ID衝突は監査証跡の破壊に直結する。

また、同一 `.spec/` に対する複数runの同時実行可否が未定義であり、ロック方針も「OSロック等を利用する」という記述にとどまっていた。

## Decision

### runId形式

`RUN-<ULID>` とする。ULIDは26文字のCrockford Base32であり、生成時に既存IDの走査を必要とせず、辞書順が生成時刻順と一致する。

```text
RUN-01K3QZJ8B4T7YV2WQ0M6XH9DFA   ; 例
```

- 採番は完全にローカルで行い、衝突検査を前提としない。
- 表示上の可読性は、レポート内の `startedAt` と対象で担保する。
- 既存の日付連番形式は使用しない。

### 並行実行

`.spec/` への影響範囲によって2種類に分ける。

| 種別 | 例 | 同時実行 |
|---|---|---|
| 読取り専用run | `bitz spec validate`、`bitz quality check`、`bitz doctor` | 制限なく並行可 |
| 書込みrun | `bitz sdd start`、`bitz sdd finalize`、`bitz init`、`bitz migrate` | 同一 `.spec/` に対し1つだけ |

- 書込みrunは `.spec/state/lock` を排他ロックとして取得する。
- ロックにはrunId、プロセスID、ホスト名、取得時刻を記録する。
- ロック取得に失敗した場合、待機せず `blocked` を返し、保持者のrunIdを診断へ含める。
- ロックには有効期限を設け、期限切れロックは保持プロセスの生存確認後に限り破棄できる。破棄は監査イベントとして記録する。
- 読取り専用runは書込みrunと並行しうるため、読み取った `.spec/` のリビジョン（Git commit IDまたは対象ファイルハッシュ）をレポートへ必ず記録する。

### 理由

- 採番の衝突可能性を設計から排除する方が、衝突検出とリトライを実装するより単純で確実である。
- 読取り専用runを直列化すると、CIでの並行検証が実行できず、SLO目標の達成が困難になる。
- 待機ではなく即時 `blocked` を返すことで、CLIの応答性と、`blocked` / `failed` / `error` の意味分離を保つ。

## Consequences

- runIdの採番がローカルで完結し、衝突検査とリトライを実装しなくてよい。
- 読取り専用runを直列化せず、CIでの並行検証を維持できる。
- 本決定はADR-009で置換され、現在の設計判断には使用しない。永続runとロック台帳は
  Core 1.0の共通契約に含めない。

## Alternatives

1. **UUIDv4**: 却下。時刻順序を持たず、レポートディレクトリの一覧が実行順に並ばない。
2. **日付＋連番を維持しロック採番**: 却下。読取り専用runにまでロックを要求することになる。
3. **全runを直列化**: 却下。並行検証の実用性を失う。
