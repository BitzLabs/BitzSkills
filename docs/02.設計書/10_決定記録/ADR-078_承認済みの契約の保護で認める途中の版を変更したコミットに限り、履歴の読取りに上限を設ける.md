# ADR-078 承認済みの契約の保護で認める途中の版を変更したコミットに限り、履歴の読取りに上限を設ける

## Context

[ADR-072](ADR-072_承認済みの契約の保護をTECHへ広げ、途中のコミットの状態で再承認を判定する.md)は、基準版と現在版がどちらも`approved`で
意味が変わっている文書について、`HEAD`から到達でき、基準版から到達できないコミット（以下、途中のコミット）の少なくとも1つで、
同じIDの文書の`status`が`draft`または`outdated`であれば、保護の違反としないと決めた（決定2）。仕様へ落とす前の検討で、次の3点が残った。

1. **古い枝の抜け道**。承認の前に分かれ、その文書に触れていない枝を取り込むと、その枝のコミットは途中のコミットに入り、承認の前の`draft`の版を
   そのまま持つ。決定2の文言どおりでは、これが途中の状態として認められ、状態を戻さない意味の変更が統合の前の`check`を通る。
   保護が保証する「承認済みの契約の意味の変更が、状態の変更としてGitの履歴に残ること」（ADR-072の`Consequences`）が成り立たない。
2. **完全に得られない場合の判定**。ADR-072の決定6は、浅いクローンなどで途中のコミットの集合を完全に得られないと判定した場合は違反のままとするが、
   判定の条件を定めていない。
3. **読む量の上限**。途中のコミットの数に上限がないと、古い基準版を指定したときに読む量が際限なく増える。後から上限を足すと結果が変わるので、
   Core 1.0の確定の前に決める（[提案34](../../04.提案資料/34_Coreと評価処理の現状整理と今後の方向性.md)の1.0と1.1の振り分けの考え方）。

あわせて、[ADR-062](ADR-062_Coreの出力文言の規範と適合fixtureの期待値の扱いを確定する.md)に従い、診断`SPEC-SAFETY-APPROVED-001`の文言を利用者が承認する。

## Decision

1. **認める途中の版**（ADR-072の決定2の部分改訂）。途中の状態として認めるのは、途中のコミットのうち、そのコミットが文書を変更した版だけとする。
   変更したとは、そのコミットの親の少なくとも1つで、同じIDの文書が存在しないか、文書のファイルの内容（バイト列）が異なることをいう。
   親のないコミットでは、すべての文書を変更したものとする。そのほかのADR-072の決定2から決定4の規則（コミットされた版だけ、IDで対応付ける、
   IDを読めない版は認めない）は変えない。
2. **完全に得られない場合**（ADR-072の決定6の判定の条件）。次のどれかに当たる場合は、途中のコミットの集合を完全に得られないとし、違反のままとする。
   - 浅いクローンの境界のコミットのいずれかが、`HEAD`または基準版から到達できる。境界のコミットがどちらからも到達できない場合は、通常どおり判定する。
   - 途中のコミット、その親、またはそれらの文書の内容を、Gitから読めない（部分クローンで欠けたオブジェクトなど）。
   - 途中のコミットの数が、3.の上限を超える。
3. **上限**。[ワークスペース・設定仕様](../../03.詳細設計/02_仕様文書モデル/01_ワークスペース・設定仕様.md)の`limits`に、途中のコミットの数の上限
   `limits.historyCommitCount`（最大値と既定値は10,000）を加える。ADR-076と同じく、最大値より小さい値だけを設定できる。
   途中のコミットの各ファイルには、現在版と同じファイルごとの上限（`limits.specBytes`、`limits.frontmatterBytes`）を当て、超えたファイルはIDを読めない版とする。
4. **文書の列挙**。途中のコミットの文書は、基準版の仕様文書の一覧と同じ規則で、現在版の作業ワークスペースのルートの配下から列挙する。
   複合ワークスペースで、途中のコミットの間にメンバーのルートを移した場合は、移す前のコミットの文書を対応付けない（違反のままになる側に倒す）。
5. **文言**。`SPEC-SAFETY-APPROVED-001`の`summary`は、文書の種別を差し込む次の2つとする（`{種別}`は`REQ`または`TECH`）。
   - 通常: `状態approvedの{種別}の意味変更時に文書の状態が戻されていません`
   - 2.に当たる場合: `状態approvedの{種別}の意味変更時に文書の状態が戻されていません（途中のコミットを完全には読めません）`

## Consequences

- 承認の前の古い枝を取り込むだけでは、保護を通らない。途中の状態として認められるのは、途中のコミットで実際に`draft`または`outdated`へ変えた版である。
- 浅いクローンでも、境界が基準版と`HEAD`の履歴に関係しない場合は、判定できる。CIで基準版と`HEAD`の履歴を取得していれば、ADR-072の手順が通る。
- `limits`のキーが1つ増え、設定のスキーマと`limits`の表を改める。
- REQの文言は変わらないので、REQの既存の適合fixtureの期待値は変わらない。TECHの文言と、途中のコミットを読めない場合の文言を、適合fixtureで固定する。
- 仕様（文書・フロントマター・状態仕様 §8、`check`仕様、診断レジストリ、ワークスペース・設定仕様、安全な入出力・互換性 §4.1）を、ADR-072の改訂と同じ作業で改める。

## Alternatives

1. **ADR-072の決定2の文言どおり**: 途中のコミットのどの版でも認める。古い枝の抜け道が残る。採らない（ユーザーの決定）。
2. **浅いクローンなら一律に完全に得られないとする**: 判定は単純だが、関係のない枝だけが浅い場合も違反のままになる。採らない（ユーザーの決定）。
3. **途中のコミットの数を制限しない**: 古い基準版で読む量が際限なく増え、後から上限を足すと結果が変わる。採らない（ユーザーの決定）。
4. **種別を差し込まない固定の文言**（`状態approvedのREQまたはTECHの…`）: REQの既存の適合fixtureの期待値も変わり、どちらの種別かを文言から読めない。採らない（ユーザーの決定）。
