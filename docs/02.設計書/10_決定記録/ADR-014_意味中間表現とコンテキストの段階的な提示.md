# ADR-014 意味中間表現とコンテキストの段階的な提示

## Context

EARS-AIをLLMへ渡す方法には、原文Markdownをそのまま渡す案、抽象構文木のJSONだけを渡す案、両方を渡す案がある。
原文だけでは、規範文、説明、例をLLMが実行ごとに再解釈するため、規範文ごとの検査、網羅性、ハッシュ値を決定論的に
扱えない。一方、すべての依存文書について抽象構文木と原文を同時に渡すと情報が重複し、遠い依存の背景説明によって
起点の意図が希釈される。

依存深度で探索自体を打ち切る案は、末端の`MUST`や禁止事項を欠落させる。必要なのは依存解決の省略ではなく、
完全に解決した結果からLLMへ渡す表現を段階化することである。

## Decision

1. Markdownを人間が編集する正本として維持し、構文解析器は規範文を軽量な意味中間表現へ変換する。
   既存の互換名称として`AST`を残すが、字句解析器のトークンやMarkdownの装飾を公開する具象構文木にはしない。
2. 意味中間表現はID、出典、主体、発動条件、規範強度、処理、拡張、参照を保持し、Core、プロファイル、
   コンテキストの解決が共通に使う機械契約とする。LLMにEARS-AIの構文解析を委ねない。
3. コンテキストの解決は強い依存を先に完全解決し、型、状態、循環、上限を検査してから提示を生成する。
   段階的提示を探索打切りや部分成功として扱わない。
4. 完全解決した適用可能な文書の規範文を制約台帳へ収録する。すべての`MUST`は依存距離にかかわらず
   LLMへ明示し、深い依存にあることを理由に参照だけへ落とさない。
5. 文書の提示を`full`、`normative`、`reference`の3段階とする。既定の提示形式は規範強度、目的、役割、
   TASKの対象かどうかを優先し、依存距離はその後の判断材料にする。
6. 追加参照は、同じ起点と目的に対する`bitz context --expand <document-id>`で行う。改訂履歴は
   `--expand <document-id>#revision-history`で明示展開する。常駐サービスや
   セッションの状態を新設せず、同じ入力から同じ結果を返す。
7. コンテキストのハッシュ値は完全解決した意味集合から計算し、提示形式の違いを含めない。実際の提示内容には
   別の提示内容のハッシュ値を付ける。
8. Coreとアダプター間の正規契約はJSONとする。LLM向けのMarkdownはJSONと意味中間表現から生成し、
   独立した意味解釈を加えない。仕様文書由来のテキストは引き続き未信頼データとして扱う。

## Consequences

- 構文解析器と意味中間表現は引き続きフェーズ1の必須の成果物となるが、詳細な具象構文木は不要になる。
- LLMはすべての`MUST`と作業境界を最初に確認でき、背景・例・参考として扱う文書は、必要な場合だけ追加で参照できる。
- 完全性の判定とトークンの節約を分離でき、提示形式を変更しても、古くなったかどうかの判定の意味は変わらない。
- `context`のJSON Schemaに`resolution`、`constraintLedger`、`projection`、`projectionDigest`が追加される。
- Coreは提示の再現性と、解決集合外の文書を暗黙追加しないことを検査する必要がある。
- 構造化データだけでは伝わりにくい背景や設計理由は原文に残り、明示展開によって利用できる。

## Alternatives

1. **全原文だけを渡す**: LLMが構文と規範性を再解釈し、モデル間で判定が揺れる。
2. **意味中間表現だけを渡す**: 背景、理由、例が失われ、判断が曖昧なときに原文へ戻れない。
3. **すべての抽象構文木とすべての原文を常時渡す**: 情報が重複し、トークンの消費とコンテキストの希釈が増える。
4. **依存深度で探索を打ち切る**: 深い位置の必須制約を欠いた部分的なコンテキストを正常に見せる。
5. **LLMに参照先を自由探索させる**: 選択が非決定論的になり、参照漏れをCoreが検出できない。
