# ADR-008 plugin配布とCore実行体の入手経路

## Context

`bitz-env`、`bitz-sdd`、`bitz-quality`、`bitz-ddd` のスキル・command群は、AI CLIのpluginマーケットプレイス形式で配布する方針である。

マーケットプレイスはGit repositoryを配布単位とする機構であり、次の性質を持つ。

- 配布されるのは宣言的なfile（スキル定義、command定義、agent定義、MCP設定）である。
- **install時に任意のインストーラーを実行しない。** 依存packageの取得やruntimeの導入を行わない。
- 導入単位はユーザー環境であり、プロジェクト単位ではない。
- 更新はユーザー操作で行われ、プロジェクトの `.spec/manifest.yaml` による版固定とは独立に進行する。

一方、本設計のCore実行体（Parser、Validator、状態管理、report生成）は実行可能プログラムであり、マーケットプレイスの配布物だけでは成立しない。この不整合を解消する必要がある。

## Decision

### 2層に分離する

| 層 | 内容 | 配布チャネル |
|---|---|---|
| plugin層 | スキル定義、スラッシュコマンド、agent定義、CLI adapter、MCP設定 | pluginマーケットプレイス（Git repository） |
| Core層 | `bitz` 実行体、EARS-AI Parser、Validator、状態管理、report生成 | [ADR-007](ADR-007_Core実行体の配布形態.md) が定める経路 |

plugin層はCore層の**呼出しと結果整形だけ**を行い、仕様の解釈、判定、状態遷移を実装しない。これは [03_CLI統合設計.md](../03_CLI統合設計.md) §8 のadapter責務の再確認であり、マーケットプレイス配布によって境界が緩むことを防ぐ。

plugin層はスキル定義（自然言語）を含むため、内容がAIへの指示として解釈される。したがって**plugin層に品質判定ロジックを置いてはならない**。判定は決定論的なCore層が所有する。

### Core層の入手経路

**候補1（前提条件として別途導入）を採用する。**

利用者はCore層を明示的に導入する（[ADR-007](ADR-007_Core実行体の配布形態.md) により `uv tool install bitz`）。plugin層のスキルは `bitz` を呼び出すのみとし、自動取得を行わない。

- plugin層は、Core層の取得、install、更新を一切行わない。
- マーケットプレイス導入直後、Core層が存在しない状態が必ず発生する。この状態を異常終了ではなく、`blocked` と導入手順の提示で扱う。
- Core層の不在検出は `bitz doctor` 相当の診断へ集約し、全スキルの実行前提とする。各スキルが独自に判定しない。
- Core層が存在しない状態で、plugin層が判定や状態遷移を代替してはならない。

この経路は動的ダウンロードと即時実行を行わないため、[07_セキュリティとガバナンス.md](../07_セキュリティとガバナンス.md) §6 の既定禁止規定と矛盾しない。導入元、版、hashは利用者が導入時点で確認できる。

初回導入時のみnetworkを要し、導入後の検証実行はオフラインで完結する。networkが完全に隔離された環境への配布は本決定の対象外とし、必要が生じた場合は単一バイナリの手動配置手順を別途定める。

### 版整合

マーケットプレイス経由のplugin層は、プロジェクトの `.spec/manifest.yaml` による版固定を強制されない。ユーザーが更新した結果、プロジェクトが要求する範囲外の版が導入されうる。

- `bitz-env` は起動時に、plugin層の版、Core層の版、`manifest.yaml` の要求範囲の3者を照合する。
- 範囲外の場合は `blocked` とし、実行を継続しない。警告として続行してはならない。
- 診断には、導入されている版、要求範囲、対処手順（pluginの版指定導入、または `manifest.yaml` の更新とreview）を含める。
- plugin層とCore層の版は独立にセマンティックバージョニングし、互換範囲をplugin manifestへ宣言する。

### ユーザー単位導入と品質基準

マーケットプレイス導入はユーザー単位であり、[06_運用設計.md](../06_運用設計.md) §2 の「ユーザー単位」方式に該当する。ユーザー環境の差異がプロジェクトの品質基準へ影響してはならない。

- 品質基準に関わる設定は引き続きpolicy scopeとし、plugin層およびユーザー設定から上書きできない（[ADR-004](ADR-004_設定の上書き禁止分類.md)）。
- plugin層は品質Profile、checkpoint判定条件、waiver権限を保持しない。
- plugin層に同梱されるフック定義は既定で無効とし、有効化はプロジェクトのpolicy scope設定を必要とする。

### 採用理由

- 動的ダウンロードを行わないため、既定禁止規定との例外設計が不要になる。
- 導入元、版、hashを利用者が導入時点で確認できる。
- plugin層のrepositoryが宣言的fileのみで軽量に保たれ、版ごとのバイナリ履歴が蓄積しない。
- 2ステップ導入という欠点は、不在時に環境別の導入commandを提示する診断で緩和する。

## Consequences

- [03_CLI統合設計.md](../03_CLI統合設計.md) にplugin層とCore層の境界、および不在時の縮退を記載する。
- [06_運用設計.md](../06_運用設計.md) の導入手順と `bitz doctor` 検出項目に版整合とCore層不在を記載する。
- plugin層のスキル定義には、Core層の導入commandを環境別に提示する診断経路を含める。
- plugin層は仕様判定を持たないため、[05_QA品質保証設計.md](../05_QA品質保証設計.md) の職務分掌に変更は生じない。

## Alternatives

### 候補2: plugin repositoryへ実行体を同梱

platform別の単一バイナリをGit repositoryへ含める。

- 利点: 追加導入が不要。network隔離環境で完結する。
- 欠点: repository肥大化。版ごとに全platform分の履歴が蓄積する。Git repositoryを実行可能バイナリの配布路として使うことになり、hash検証と署名の設計が別途必要になる。却下するが、[ADR-007](ADR-007_Core実行体の配布形態.md) の補助成果物である単一バイナリを利用者が手動配置する経路は、network隔離環境向けに残す。

### 候補3: MCPサーバー宣言による都度取得

pluginのMCP設定でCore層を都度取得・起動する。

- 利点: 導入が1ステップで完結する。
- 欠点: **動的ダウンロードと即時実行に該当する。** 既定禁止規定の例外として扱うには、取得元固定、hash検証、オフライン動作、監査記録の設計が必要であり、これらを満たすと候補1との差が小さくなる。却下する。
