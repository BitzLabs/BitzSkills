# ADR-060 スキルの評価契約と独立検分の境界を固定する

## Context

Core 1.0の公開操作を利用する`bitz-core`、`bitz-sdd`、`bitz-quality`のスキルを実装する前に、
発火、行動、安全、効率の成功条件を固定する必要がある。スキルを先に実装すると、その実装に都合のよいケースと
採点へ寄せる危険がある。また、6スキル案と3入口案のどちらが発見面、安全、読取り量、費用に適するかは、
現行の正本だけからは決まらない。

OpenAIの[スキル作成仕様](https://developers.openai.com/plugins/build/skills)は、名前と説明を主な発火信号とし、
明示、暗黙、不完全、負例、未対応操作の代表要求で発火と出力を検査することを求める。
[公式の評価例](https://developers.openai.com/blog/eval-skills)は、JSONLの実行軌跡に対する決定論的検査を先に置き、
必要な場合にだけ定性的な評価を重ねる。この方針は、Coreの機械判定とスキルの推論を分ける現行設計に合う。

一方、`verify`が実行する登録テストには副作用があり得る。Core 1.0の公開結果は展開後の正確な`argv`を
実行前に返さないため、正確な事前確認を必要とするケースを、スキルだけで安全に実行可能へ変えることはできない。

## Decision

本ADRの評価境界と入口構成を採用する。公開ケースの試作評価が閾値未達であることは、
候補スキルのリリース認定を意味しない。評価集合の版とケースは引き続き検証し、
保持したケースと実動作の検証を別途行う。

1. 評価集合の正本を`evals/skills/`へ置き、ケース、実行結果、集計結果、SDDから品質管理への引渡し、
   独立検分をJSON Schemaで検査する。実行軌跡はJSONLで保存し、再採点とモデルの新規実行を区別する。
2. 評価集合の版、対象コミット、候補スキル集合のSHA-256、モデル名と版、反復、環境、ケース種別ごとの
   成功数と総数を結果へ残す。スキル間、モデル間、反復間の平均で失敗を相殺しない。
3. 決定論的検査と必須の安全ケースは100%を要求し、証拠なしの`ready`を1件も許さない。
   その後にルーブリックと独立検分を行い、後段の得点で前段の失敗を上書きしない。
4. 入口は`bitz-core`、`sdd-plan`、`sdd-implement`、`sdd-converge`、`quality-plan`、`quality-review`の
   6スキル構成を採用する。公開ケース46件を同じモデル・権限で各構成2反復した比較では、6スキル案が
   経路精度と安全不変条件で優位だった。3入口案は比較対象として記録を保持する。
   採用した入口の発火・行動・安全は保持ケースと実動作でも検証する。
5. 公開ケースは回帰と説明に使う。保持したケースは公開リポジトリへ保存せず、実行時に供給し、集合の版、件数、
   SHA-256だけを結果へ残す。保持したケースがない評価をリリース認定と呼ばない。
6. Coreへの依存は`core-compatibility.json`に記載した公開操作と結果契約に限り、`src/bitz`の内部APIへ依存しない。
7. SDDから品質管理へは、対象コミット、起点ID、変更path、リスク帯と観点、必須・取得済み・未取得の証拠、
   実行した検査を`handoff.schema.json`の形式で渡す。品質計画がないQ0／Q1でも、この形式から最低証拠を導く。
   Q2／Q3で品質計画がなければ実装を開始しない。
8. 独立検分は新しい実行識別子と文脈を持ち、作業者の非公開履歴と誘導する結論を受け取らず、差分と安全に
   再実行できる検査を直接確認する。成立条件を記録できない結果は、独立検分を要求するGateの証拠にしない。
9. `verify`またはレビューでの再実行前に、登録コマンド、関連テストの差分、作業ディレクトリ、書込み先、
   ネットワーク、資格情報へのアクセス、ホスト側の隔離を確認する。安全に制約できなければ停止する。
10. Core 1.0には実行前の展開済み`argv`を返す操作を追加しない。正確な`argv`の事前確認が必要なケースは停止する。
    評価で計画操作の必要性が確認された場合は、Coreの公開契約を変える別の決定記録を先に作る。
11. `AGENTS.md`が要求する「承認済み要件の意味変更前に`draft`」を、このリポジトリのスキル評価でも優先する。
    SDDフローの`outdated`との一般的な整合は、本ADRで既存の承認済み規範を変更せず、別の裁定へ残す。

## Consequences

- スキル実装より先に、発火と安全の失敗を再現できる。
- 空の試作、欠落したケース、平均で隠した失敗、証拠のない`ready`を機械的に拒否できる。
- 6つの入口を個別に発見・選択できるが、総読取りbyte数は3入口案より多い。
- 公開試作では6スキル案の安全不変条件が12/12だった一方、試作全体は閾値未達である。
- 保持したケースの本文は対象コミットだけから完全には再現できず、管理者が非公開入力とそのハッシュ値を管理する必要がある。
- Coreに計画操作がない間、安全上正確な`argv`確認を要する`verify`は実行できない。
- 配布用プラグインへ移す前に、採用した6スキルの行動・安全・独立検分を検証する。

## Alternatives

1. **6スキル案を計画だけで採用する**: 発火面と読取り量を実測してから採用した。
2. **3入口案を採用する**: 読取りbyte数は小さいが、公開試作で経路精度と安全不変条件が低かったため採らない。
3. **公開ケースだけで認定する**: ケースへの過学習を検出できないため採らない。
4. **モデルによる総合得点だけで判定する**: 必須の安全違反と証拠欠落を平均で隠せるため採らない。
5. **登録済みテストは常に安全として実行する**: 登録コマンドとテスト自体が変更可能であるため採らない。

## Notes

評価集合`0.3.0`の公開46ケースを`gpt-6-luna`で各構成2反復した。184実行はすべて完走した。
6スキル案は完全一致76/92、経路一致85/92、安全不変条件12/12、実行軌跡の安全92/92であり、
3入口案は順に71/92、82/92、10/12、91/92だった。候補スキルのファイル総量は6スキル案5,613 byte、
3入口案3,519 byte、中央token数は15,554.5と15,446、中央時間は13,423.5 msと14,428 msだった。
費用は両構成とも推定値が得られず、比較不能である。

公開試作の総合判定は両構成とも`Failed`である。6スキル案でも肯定発火83.3%、文脈発火66.7%、
行動一致75.0%が試作閾値に達していない。意味イベントはモデルの構造化自己申告であり、実際の
Core操作やファイル変更を実行した証拠ではない。保持ケース、別モデル系統、独立検分も未実施である。
したがって本決定は入口構成の選択であり、候補スキルの合格・公開を許可しない。

結果は[公開試作の比較記録](../../../evals/skills/results/2026-09-30-public-prototype.md)に残す。
