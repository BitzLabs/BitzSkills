# ADR-008 プラグイン配布とコア実行体の入手経路

## Context

`bitz-env`、`bitz-sdd`、`bitz-quality`、`bitz-ddd` のスキル・コマンド群は、AI CLIのプラグインマーケットプレイス形式で配布する方針である。

マーケットプレイスはGitリポジトリを配布単位とする機構であり、次の性質を持つ。

- 配布されるのは宣言的なファイル（スキル定義、コマンド定義、エージェント定義、MCP設定）である。
- **インストール時に任意のインストーラを実行しない。** 依存パッケージの取得やランタイムの導入を行わない。
- 導入単位はユーザー環境であり、プロジェクト単位ではない。
- 更新はユーザー操作で行われ、プロジェクトの `.spec/manifest.yaml` による版固定とは独立に進行する。

一方、本設計のコア実行体（Parser、Validator、状態管理、レポート生成）は実行可能プログラムであり、マーケットプレイスの配布物だけでは成立しない。この不整合を解消する必要がある。

## Decision

### 2層に分離する

| 層 | 内容 | 配布チャネル |
|---|---|---|
| プラグイン層 | スキル定義、スラッシュコマンド、エージェント定義、CLIアダプター、MCP設定 | プラグインマーケットプレイス（Gitリポジトリ） |
| コア層 | `bitz` 実行体、EARS-AI Parser、Validator、状態管理、レポート生成 | [ADR-007](ADR-007_コア実行体の配布形態.md) が定める経路 |

プラグイン層はコア層の**呼出しと結果整形だけ**を行い、仕様の解釈、判定、状態遷移を実装しない。これは [03_CLI統合設計.md](../03_CLI統合設計.md) §8 のアダプター責務の再確認であり、マーケットプレイス配布によって境界が緩むことを防ぐ。

プラグイン層はスキル定義（自然言語）を含むため、内容がAIへの指示として解釈される。したがって**プラグイン層に品質判定ロジックを置いてはならない**。判定は決定論的なコア層が所有する。

### コア層の入手経路

**候補1（前提条件として別途導入）を採用する。**

利用者はコア層を明示的に導入する（[ADR-007](ADR-007_コア実行体の配布形態.md) により `uv tool install bitz`）。プラグイン層のスキルは `bitz` を呼び出すのみとし、自動取得を行わない。

- プラグイン層は、コア層の取得、インストール、更新を一切行わない。
- マーケットプレイス導入直後、コア層が存在しない状態が必ず発生する。この状態を異常終了ではなく、`blocked` と導入手順の提示で扱う。
- コア層の不在検出は `bitz doctor` 相当の診断へ集約し、全スキルの実行前提とする。各スキルが独自に判定しない。
- コア層が存在しない状態で、プラグイン層が判定や状態遷移を代替してはならない。

この経路は動的ダウンロードと即時実行を行わないため、[07_セキュリティとガバナンス.md](../07_セキュリティとガバナンス.md) §6 の既定禁止規定と矛盾しない。導入元、版、ハッシュは利用者が導入時点で確認できる。

初回導入時のみネットワークを要し、導入後の検証実行はオフラインで完結する。ネットワークが完全に隔離された環境への配布は本決定の対象外とし、必要が生じた場合は単一バイナリの手動配置手順を別途定める。

### 版整合

マーケットプレイス経由のプラグイン層は、プロジェクトの `.spec/manifest.yaml` による版固定を強制されない。ユーザーが更新した結果、プロジェクトが要求する範囲外の版が導入されうる。

- `bitz-env` は起動時に、プラグイン層の版、コア層の版、`manifest.yaml` の要求範囲の3者を照合する。
- 範囲外の場合は `blocked` とし、実行を継続しない。警告として続行してはならない。
- 診断には、導入されている版、要求範囲、対処手順（プラグインの版指定導入、または `manifest.yaml` の更新とレビュー）を含める。
- プラグイン層とコア層の版は独立にセマンティックバージョニングし、互換範囲をプラグインマニフェストへ宣言する。

### ユーザー単位導入と品質基準

マーケットプレイス導入はユーザー単位であり、[06_運用設計.md](../06_運用設計.md) §2 の「ユーザー単位」方式に該当する。ユーザー環境の差異がプロジェクトの品質基準へ影響してはならない。

- 品質基準に関わる設定は引き続きpolicyスコープとし、プラグイン層およびユーザー設定から上書きできない（[ADR-004](ADR-004_設定の上書き禁止分類.md)）。
- プラグイン層は品質プロファイル、checkpoint判定条件、waiver権限を保持しない。
- プラグイン層に同梱されるフック定義は既定で無効とし、有効化はプロジェクトのpolicyスコープ設定を必要とする。

### 採用理由

- 動的ダウンロードを行わないため、既定禁止規定との例外設計が不要になる。
- 導入元、版、ハッシュを利用者が導入時点で確認できる。
- プラグイン層のリポジトリが宣言的ファイルのみで軽量に保たれ、版ごとのバイナリ履歴が蓄積しない。
- 2ステップ導入という欠点は、不在時に環境別の導入コマンドを提示する診断で緩和する。

## Consequences

- [03_CLI統合設計.md](../03_CLI統合設計.md) にプラグイン層とコア層の境界、および不在時の縮退を記載する。
- [06_運用設計.md](../06_運用設計.md) の導入手順と `bitz doctor` 検出項目に版整合とコア層不在を記載する。
- プラグイン層のスキル定義には、コア層の導入コマンドを環境別に提示する診断経路を含める。
- プラグイン層は仕様判定を持たないため、[05_QA品質保証設計.md](../05_QA品質保証設計.md) の職務分掌に変更は生じない。

## Alternatives

### 候補2: プラグインリポジトリへ実行体を同梱

プラットフォーム別の単一バイナリをGitリポジトリへ含める。

- 利点: 追加導入が不要。ネットワーク隔離環境で完結する。
- 欠点: リポジトリ肥大化。版ごとに全プラットフォーム分の履歴が蓄積する。Gitリポジトリを実行可能バイナリの配布路として使うことになり、ハッシュ検証と署名の設計が別途必要になる。却下するが、[ADR-007](ADR-007_コア実行体の配布形態.md) の補助成果物である単一バイナリを利用者が手動配置する経路は、ネットワーク隔離環境向けに残す。

### 候補3: MCPサーバー宣言による都度取得

プラグインのMCP設定でコア層を都度取得・起動する。

- 利点: 導入が1ステップで完結する。
- 欠点: **動的ダウンロードと即時実行に該当する。** 既定禁止規定の例外として扱うには、取得元固定、ハッシュ検証、オフライン動作、監査記録の設計が必要であり、これらを満たすと候補1との差が小さくなる。却下する。
