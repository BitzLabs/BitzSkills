# 実装ロードマップ

## 1. 戦略

横断的な基盤を先に完成させず、EARS-AIの記述から実行テストまでを通す小さな垂直スライスを先に作る。
各段階で所要時間、欠陥検出、記述負荷を測り、効果が確認できない機能は次段階へ進めない。

## 2. Phase 0: 実証条件

成果物:

- 個人・小規模チーム向けペルソナと非目標
- 通常Markdownまたは従来EARSで実行する5件のパイロットタスク
- 完了時間、仕様記述時間、レビュー時間、欠陥検出率の測定方法
- EARS-AI Coreの最小構文とSemantic IR（AST互換名）
- Agent Plugins 1.0.0の適合条件と、GitHubマーケットプレイスの最小カタログ
- 5 workspace、横断関係、同名ローカルIDを含むモノレポ基準fixture

完了条件:

- 比較対象と成功基準が実装前に固定されている。
- EARS-AIが保証する範囲と保証しない範囲が説明できる。
- Core 1.0の対象外機能が明記されている。
- EARS-AI条件の比較はParser完成後のPhase 4で行うと合意されている。
- `bitz-core`必須、拡張間依存禁止、Skills/MCP境界が合意されている。
- モノレポのworkspace識別、所有境界、全体操作と性能測定条件が固定されている。

## 3. Phase 1: EARS-AI垂直スライス

実装:

- EARS-AI Parser、Semantic IR、Canonical Serializer
- 型付き関係の索引、型検査、循環検出
- `bitz context`の完全閉包、Constraint Ledger、段階的Projection、2種類のDigest
- `bitz check`の構文、ID、関係検査
- SPEC種別ごとの状態遷移検査、`--base`による変更集合、明示`check`対象選択
- 最小`.spec/bitz.yaml`
- モノレポ連合カタログ、workspace修飾ID、横断索引、所有境界検査
- 共通Diagnosticとtext/JSON出力
- Golden fixture、異常・境界値テスト

完了条件:

- 同一入力から同一Semantic IRとDiagnosticを再現できる。
- 不正ID、ID欠落、3階層IDの規範行候補を通常本文として無視せず、通常checkbox、コード例、引用は
  規範文として誤検出しない。
- 同一グラフから同じContext BundleとDigestを再現できる。
- SHA-256の結果フィールドと`--expect-digest`が`sha256:[0-9a-f]{64}`へ適合する。
- 参照切れ、循環、上限超過、適用不能状態を部分成功にしない。
- `compact` / `standard` / `full`で解決集合、全`MUST`、Context Digestが変化しない。
- `expand`した文書だけが`full`へ昇格し、Projection Digestだけが変化する。
- 変更範囲`check`が基準環境で1秒以内に完了する。
- 20文書・128 KiB以下の`context`が基準環境で1秒以内に完了する。
- ネットワーク、LLM、フックなしで動作する。
- EARS-AIの記述負荷を通常Markdown・従来EARSと比較できる。
- 同名ローカルIDを持つmember間でも、修飾IDから同じ横断閉包とDigestを再現できる。
- 未登録member、重複・入れ子path、非修飾横断参照、所有境界違反を検出できる。
- 状態遷移matrixの全許可・禁止edgeをfixtureで再現できる。
- `open` TASKを`done`へ変更した入力を明示`check`し、TASK自身のファイルを境界違反にせず、状態遷移と
  文書構造を検査できる。
- `open -> open`と`done -> open`の先行TASK fixtureで、`implement`／`verify`の開始可否が一意になり、
  循環検査と状態ガードを別Diagnosticで識別できる。
- `done` TASKを起点とする`implement`が`CTX-STATE-001`で`blocked`となり、`interpret`がHistoryを返す。
- `draft -> rejected`と`open -> cancelled`を許可し、理由セクション欠落、終端からの再遷移、
  `approved -> rejected`をfixtureで拒否する。
- `rejected` REQ／TECHと`cancelled` TASKを`interpret`でHistoryとして返し、`implement`／`verify`起点を
  `CTX-STATE-001`で停止する。`cancelled`依存は`CTX-TASK-DEPENDENCY-001`で停止する。
- `rejected`文書の履歴パスを所有逆索引、検証対象、coverage、パス存在検査から除外する。
- HEAD既定と明示した統合先先端で、staged、unstaged、未追跡、削除、renameを同じ規則で検出できる。
- 統合先先端を含まない木へ`--base <統合先先端>`を渡した入力でSPEC削除が報告され、前提条件の記述と
  対応付けられる。
- branch内で`open -> done`まで進めたTASKが基準版に存在しない入力で、初出として許可される。
- 基準版と現在版の同一文書をworkspace IDと文書IDで対応付け、renameを移動として扱い、Git管理済みSPECの
  削除を`SPEC-STATE-TRANSITION-001`で拒否する。member削除またはpath変更でも基準版側のSPECを検査から隠さない。
- 不正UTF-8を`SPEC-INPUT-READ-001`／`failed`、権限不足、I/O障害、読取り中の消失を同コードの`error`として
  区別し、読取り後の同時編集検出をCore 1.0の保証に含めない。
- 明示`check`が許可対象を所有文書へ正規化し、コード・テストpathと`--full`併用を拒否する。
- code/testだけを変更したfixtureで、`implements`・`tests[].path`の逆索引から検査対象が一意に決まり、
  未所有pathがDiagnosticを生まない。
- 変更0件または未所有code/testだけの変更で引数なし`check`が`passed`となり、設定・全体索引の不適合が
  ある場合は0件を理由に成功へ上書きしない。
- check結果の変更path数、対象文書数、対象外code/test path数がtext／JSONで一致する。
- TASKファイルと境界外コードを変更したfixtureで、引数なし`check`はTASK文書を検査するが
  `SPEC-TASK-BOUNDARY-001`を返さず、同じ変更を`bitz check <TASK-ID>`で検査した場合だけ同Diagnosticを返す。
- `--full`と`--all-workspaces`でTASKを走査しても`changes`境界を検査せず、完了・取り止めフローでは
  TASK IDを明示したcheckによって境界を検査する。
- 現在集合内のID重複を検出し、Git基準版がない場合はSPEC削除検出を実施不能としてwarningにする。
- Diagnosticの`resultStatus`と`source.workspaceId`から、単一・連合操作を同じ順位で集約できる。
- 合流後の木で同一workspaceの重複IDを検出し、基準版での有無から勝者と敗者を一意に決定できる。
- 同一入力から同一の`proposedId`と`rewriteSites`順序を再現できる。
- `--base`未指定では`idCollisions`へ`instances`だけを返し、勝敗と改番候補を出力しない。
- 基準版が重複キーを含む入力で`SPEC-BASE-AMBIGUOUS-001`／`blocked`とし、他キーの遷移・削除・保護判定を継続する。

## 4. Phase 2: 実行可能な検証

実装:

- EARS-AI規範文から実装・テストファイルへの句単位トレース
- `bitz verify`とテストコマンド解決
- Context Digest、規範文ID、正規化command binding、timeout、終了結果の対応付け
- テスト未登録、環境不足、失敗の区別
- `check`、`verify`、`doctor`の`--all-workspaces`集約

完了条件:

- 意図的に欠陥を入れたfixtureを検出できる。
- `MUST`句を1つTASKまたはテスト対応から外したfixtureを検出できる。
- リンクだけ存在しテスト未実行の成果物を`verify`成功と扱わない。
- コア自身の追加オーバーヘッドが500ms以内である。
- workspaceごとの検証コマンドが混合されず、全体statusと結果順が決定論的である。
- commandの`argv`、`cwd`、設定timeout変更でContext Digestが変わり、CLI timeout capだけでは変わらない。
- 同一binding・複数path、別名同一binding、同名別workspace、`{tests}`なしの各fixtureで実行回数が
  一意に決まり、単一workspaceと`--all-workspaces`で同じ所有workspaceの実行回数が一致する。
- 通常終了、非0終了、起動失敗、signal、timeoutをcommand結果とDiagnosticで区別できる。
- bindingを正規識別子順に逐次実行し、失敗後も独立bindingを継続する。複数名の代表名は辞書順最小となる。
- stdoutとstderrを各64 KiB以下に保ち、超過時もメモリを増幅させず、抜粋へ`[truncated]`を表示する。
- timeout時に直接起動したprocessを停止・回収し、子孫processのOS横断管理をCore保証として要求しない。
- 規範文なしTECHを`addresses`するTASKが文書単位testsを実行し、規範文ID起点の兄弟句を`adjacent`へだけ返す。
- `done` TASKを起点とする`verify`が`addresses`から同じ検証対象を導出し、未完了の先行TASKがあれば
  `CTX-TASK-DEPENDENCY-001`で`blocked`となる。
- 成功時、非成功時、`--report`指定時、引数不正時のレポート生成有無が契約どおりである。
- レポート名がUTC basic形式となり、同一秒・同一操作の衝突時に連番で排他的に作成される。

## 5. Phase 3: Small Flowスキル

実装:

- `bitz-core`、`bitz-sdd`のAgent Plugins 1.0.0 package
- GitHubマーケットプレイスカタログと個別インストール経路
- `bitz-core`のMCP stdio serverと薄いCLI adapter
- Intent、Context、Pre-check、Implement、Post-check、Verify、Human Review、Doneの進行支援
- Done前の各段階から人間の明示判断で`Stopped`へ終了し、不採用・中止理由を検査して記録する進行支援
- 変更を伴うフェーズを個別commitへ分け、読取り専用フェーズでは現在HEADをcheckpointとして空commitを作らない
  進行支援
- TASK起点での`bitz check <TASK-ID>`による実装後の変更境界検査
- 編集直前と再開時のContext Digest再照合
- 変更境界、危険操作確認、2回までの局所リトライ
- プラグインID、版、Core API、Capabilityを検査する`bitz doctor`
- マーケットプレイス、manifest、プラグイン外参照、拡張間依存を検査するrelease CI

完了条件:

- フック、subagent、永続runなしで完走する。
- TASK起点のfixtureで、境界外のコード変更が実装後の`check`で必ず`SPEC-TASK-BOUNDARY-001`となる。
- 実装後の静的検査を経ずにDoneへ到達する経路がない。
- Human Review否決が理由に応じてIntent、Context、Implementへ戻り、戻った地点以降のcheck、Verify、
  Human Reviewを再実行せずにDoneへ到達する経路がない。
- Human Review否決を自動リトライ回数へ含めず、人間が再作業または`Stopped`を選べる。
- TASK起点では、Human Review後に`open -> done`とRevision Historyを同じdiffへ含め、変更後の
  `bitz check <TASK-ID>`を経ずにGitへ記録する経路がない。
- Pre-check、Post-check、TASK完了時checkが`passed_with_warnings`で次段階へ進み、`failed`、`blocked`、
  `error`、引数不正では進まない。
- Core 1.0の公開文法に`--strict`がない。
- CoreがTASK statusまたはGitを自動変更せず、先行TASKの完了記録後に後続TASKのフローを開始できる。
- 取り止め時は`rejected`／`cancelled`と理由を同じdiffへ含め、変更後の明示`check`を経ずにGitへ記録する
  経路がない。
- Implement後の取り止めで残存差分を提示し、人間の処遇選択なしに自動削除またはStoppedのcommitへ混在させる
  経路がない。
- フェーズcommitをsquashせず、変更のないフェーズで空commitを作らず、個別commitを新しい順にrevertできる。
- `Integrate`で統合先先端を合流させてGitへ記録し、`--base <統合先先端>`の再検査が通過してから`Done`を
  記録する経路をたどれる。合流commitと改番commitを分離できる。
- Skillが`idCollisions`の`tracked`をすべて適用し、`textual`を人間へ提示して再検査を通過させられる。
- 承認済みREQを自動変更しない。
- コア不在時に導入手順付き`blocked`を返す。
- `bitz-core`単独と`bitz-core` + `bitz-sdd`の両方をクリーン環境へ導入できる。
- 2つ目の対応クライアントでSkillsとMCPの最小互換試験が通る。
- 拡張のCore API不一致とCapability不足が`doctor`で`blocked`になる。

## 6. Phase 4: 実地評価と1.0判定

合計20件以上の実タスクを3群（各6〜7件）へ割り当て、次を比較する。同一タスクを3条件すべてで
反復することは必須にしない。

- EARS-AIなし
- EARS-AI + `check`
- EARS-AI + `context` + `check` + `verify`

1.0へ進む条件:

- 完了時間、欠陥率、レビュー負荷の少なくとも1つが改善する。
- 他の指標に許容不能な悪化がない。
- Diagnosticのfalse positiveが日常利用を妨げない。
- Small Flowの追加待ち時間が利用者に許容される。

条件を満たさない場合、GateやProfileを追加せず、構文またはワークフローを縮小する。

## 8. Core 1.0の対象外

- 必須の独立AuditAgentまたは複数モデル合議
- 常時LLM監査
- 自動的なコードから仕様への逆同期
- 多言語コードASTの完全対応
- 外部policy/承認サービス
- 分散ロックと永続run台帳
- 全AIクライアント・全自己完結実行体形式の同時提供
- DDDの必須化
- 複数Gitリポジトリ、Git submodule、ネットワーク越しのSPEC連合
