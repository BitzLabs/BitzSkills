# 実装ロードマップ

## 1. 戦略

横断的な基盤を先に完成させず、EARS-AIの記述から実行テストまでを通す小さな垂直スライスを先に作る。
各段階で所要時間、欠陥検出、記述負荷を測り、効果が確認できない機能は次段階へ進めない。

## 2. Phase 0: 実証条件

成果物:

- 個人・小規模チーム向けペルソナと非目標
- 通常Markdownまたは従来EARSで実行する5件のパイロットタスク
- 完了時間、仕様記述時間、レビュー時間、欠陥検出率の測定方法
- EARS-AI Coreの最小構文とAST

完了条件:

- 比較対象と成功基準が実装前に固定されている。
- EARS-AIが保証する範囲と保証しない範囲が説明できる。
- Core 1.0の対象外機能が明記されている。
- EARS-AI条件の比較はParser完成後のPhase 4で行うと合意されている。

## 3. Phase 1: EARS-AI垂直スライス

実装:

- EARS-AI Parser、AST、Canonical Serializer
- 型付き関係の索引、型検査、循環検出
- `bitz context`の完全閉包、Context Bundle、Digest
- `bitz check`の構文、ID、関係検査
- 最小`.spec/bitz.yaml`
- 共通Diagnosticとtext/JSON出力
- Golden fixture、異常・境界値テスト

完了条件:

- 同一入力から同一ASTとDiagnosticを再現できる。
- 同一グラフから同じContext BundleとDigestを再現できる。
- 参照切れ、循環、上限超過、適用不能状態を部分成功にしない。
- 変更範囲`check`が基準環境で1秒以内に完了する。
- 20文書以下の`context`が基準環境で1秒以内に完了する。
- ネットワーク、LLM、フックなしで動作する。
- EARS-AIの記述負荷を通常Markdown・従来EARSと比較できる。

## 4. Phase 2: 実行可能な検証

実装:

- EARS-AI規範文から実装・テストファイルへの句単位トレース
- `bitz verify`とテストコマンド解決
- Context Digest、規範文ID、コマンド、終了結果の対応付け
- テスト未登録、環境不足、失敗の区別

完了条件:

- 意図的に欠陥を入れたfixtureを検出できる。
- `MUST`句を1つTASKまたはテスト対応から外したfixtureを検出できる。
- リンクだけ存在しテスト未実行の成果物を`verify`成功と扱わない。
- コア自身の追加オーバーヘッドが500ms以内である。

## 5. Phase 3: Small Flowスキル

実装:

- 主要AI CLI 1種類の薄いアダプター
- Intent、Context、Check、Implement、Verify、Doneの進行支援
- 編集直前と再開時のContext Digest再照合
- 変更境界、危険操作確認、2回までの局所リトライ
- `bitz doctor`

完了条件:

- フック、subagent、永続runなしで完走する。
- 承認済みREQを自動変更しない。
- コア不在時に導入手順付き`blocked`を返す。

## 6. Phase 4: 実地評価と1.0判定

合計20件以上の実タスクを3群（各6〜7件）へ割り当て、次を比較する。同一タスクを3条件すべてで
反復することは必須にしない。

- EARS-AIなし
- EARS-AI + `check`
- EARS-AI + `context` + `check` + `verify`

1.0へ進む条件:

- 完了時間、欠陥率、レビュー負荷の少なくとも1つが改善する。
- 他の指標に許容不能な悪化がない。
- Diagnosticのfalse positiveが日常利用を妨げない。
- Small Flowの追加待ち時間が利用者に許容される。

条件を満たさない場合、GateやProfileを追加せず、構文またはワークフローを縮小する。

## 7. 1.0以降の候補

需要と実測があるものだけ個別に追加する。

- 2つ目のAI CLIアダプター
- EARS-AI SDD/Quality Profile
- 限定言語向けL2 Structural
- LLMによる`advisory`レビュー
- DDD Profile
- 仕様同期の提案diff
- 単一バイナリ、SBOM、署名付きprovenance

## 8. Core 1.0の対象外

- 必須の独立AuditAgentまたは複数モデル合議
- 常時LLM監査
- 自動的なコードから仕様への逆同期
- 多言語コードASTの完全対応
- 外部policy/承認サービス
- 分散ロックと永続run台帳
- 全CLI・全配布形式の同時提供
- DDDの必須化
