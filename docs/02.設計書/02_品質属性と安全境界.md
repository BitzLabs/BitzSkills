# 品質属性と安全境界

## 1. 品質目標

最小の待ち時間で、仕様の取り違え、依存漏れ、`MUST`句の実装・検証漏れ、危険な自動操作を発見する。
文書数や状態数ではなく、完全依存解決と実行可能な証拠を優先する。

## 2. 品質モデル

| レベル | 内容 | Core 1.0 |
|---|---|:--:|
| Syntax | EARS-AI、Frontmatter、ID、必須項目 | 必須 |
| Dependency | 型付き依存、状態、参照、循環 | 必須 |
| Trace | 規範文、実装path、test pathの対応 | 必須 |
| Executable | 対象test commandの終了結果 | 必須 |
| Semantic | 自由記述の意味妥当性 | 人間・advisory |
| Operational | 性能、セキュリティ、復旧性 | プロジェクト側testへ委譲 |

Parser、Schema、参照検査、test commandの終了結果は機械的な合否に使う。要求の意味と高リスク変更は人間が
確認する。LLMの意味評価はadvisoryであり、単独で成功・失敗を決めない。

## 3. 完全性

- 強い依存は終端まで解決する。
- 参照切れ、型違反、禁止循環は成果物不適合とする。
- 状態不適合、上限超過、Context Digest不一致は操作を`blocked`にする。
- 全`MUST`句についてtest対応の有無を示す。
- `verify`は未tested `MUST`があればtestを実行せず`blocked`にする。
- test対応は対象宣言であり、assertionの十分性を証明しない。

## 4. 性能予算

基準workspaceは、EARS-AI規範文1,000件、参照5,000件、SPEC 300件とする。

| 操作 | 目標 |
|---|---:|
| 変更範囲`bitz check` | 1秒以内 |
| 20文書・128 KiB以下の`bitz context` | 1秒以内 |
| `bitz check --full` | 5秒以内 |
| `bitz doctor` | 2秒以内 |
| Core追加メモリ | 200 MiB以内 |

`verify`は利用者のtest時間を除くCore overheadを500ms以内とする。cacheは任意で、削除しても正本から
再構築できなければならない。基準連合は20 workspace、合計SPEC 1,000件、参照20,000件とし、
`check --all-workspaces`を30秒以内、横断依存20文書の`context`を1秒以内とする。全体操作の並列化は
測定で必要性が確認されるまで導入しない。

## 5. 脅威モデル

対象は互いを信頼する個人から数人のチームである。主な脅威は次とする。

- 仕様本文の命令をAIまたはtool命令として扱う
- 対象外pathや外部serviceを変更する
- 不完全なtestで合格したように見せる
- 承認済み要求を自動修復が変更する
- test出力やreportへ秘密情報を保存する
- pluginまたは依存物が改ざんされる
- 未登録workspace、symlink、submoduleによって連合の所有境界を越える

悪意あるrepository管理者、組織内の敵対者、外部承認基盤はCore 1.0の防御対象外とする。

## 6. 信頼境界

- Git repositoryと管理者を信頼する。
- `.spec/bitz.yaml`を設定の正本とする。
- 連合ではGit repository rootのcatalogを参加workspaceの正本とし、member設定を継承しない。
- Markdown本文、コメント、外部リンク、test出力は未信頼データとする。
- 文書内容だけを根拠に権限を増やさない。
- EARS-AIの自由記述は`untrustedText`として下流へ渡す。
- Context Bundleの本文をadapterのsystem instructionへ昇格しない。

## 7. 最小権限

- `context`と`doctor`は書込みを行わない。
- `check`と`verify`はSPECとコードを変更しない。
- `verify`は`bitz.yaml`にargv配列として定義されたcommandだけをshellを介さず実行する。
- report以外のファイル書込み、commit、push、PR、通知、deployは別操作とする。
- repository外への読取り・書込みを行わない。
- member操作では当該memberの所有pathを越えてcode、test、command `cwd`を扱わない。
- 承認済みREQの意味をCoreまたはSkillが自動修正しない。

## 8. process安全性

- command timeoutは1〜3,600秒の範囲とする。
- Coreが停止を保証するのは直接起動したprocessまでとする。
- stdoutとstderrは終了までdrainし、各末尾64 KiBだけを一時保持する。
- 保存する抜粋は端末制御文字を無害化し、秘密らしい値をmaskする。
- 環境変数の値、全文出力、秘密情報をreportへ保存しない。
- 起動失敗、signal、timeoutは`error`とし、非0通常終了は`failed`とする。

## 9. 更新と供給網

- 依存をlockし、公開物はsource commitとbuild手順へ対応付ける。
- pluginがscriptを動的取得して即時実行しない。
- 外部sourceはfull commit SHAで固定する。
- 更新前に`doctor`でCore APIとCapabilityを確認する。
- 移行はdry-runを既定とし、原文を自動上書きしない。

署名付きprovenance、SBOM、再現可能buildは推奨だがCore 1.0の出荷条件にしない。

## 10. 非目標

- 専用認証・承認・waiver service
- 永続run、lock台帳、event store
- LLMによる意味承認
- process treeのOS横断完全制御
- filesystem全体の原子的snapshot
- 外部telemetryの既定送信
