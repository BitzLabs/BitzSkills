# 品質属性と安全境界

## 1. 品質目標

最小の待ち時間で、仕様の取り違え、依存漏れ、`MUST`の規範文の実装・検証漏れ、危険な自動操作を発見する。
文書数や状態数ではなく、完全な依存解決と実行可能な証拠を優先する。

## 2. 品質モデル

| レベル | 内容 | Core 1.0 |
|---|---|:--:|
| 構文 | EARS-AI、フロントマター、ID、必須項目 | 必須 |
| 依存 | 型付きの依存、状態、参照、循環 | 必須 |
| トレース | 規範文、実装のパス、テストのパスの対応 | 必須 |
| 実行 | 対象のテストコマンドの終了結果 | 必須 |
| 意味 | 自由記述の意味の妥当性 | 人間・参考 |
| 運用 | 性能、セキュリティ、復旧性 | プロジェクト側のテストへ委譲 |

構文解析器、スキーマ、参照の検査、テストコマンドの終了結果は機械的な合否に使う。要求の意味と高リスクの変更は
人間が確認する。LLMによる意味の評価は参考であり、単独で成功・失敗を決めない。

## 3. 完全性

- 強い依存は終端まで解決する。
- 参照切れ、型違反、禁止された循環は、成果物の不適合とする。
- 状態の不適合、上限の超過、コンテキストのハッシュ値の不一致は、操作を状態`blocked`にする。
- すべての`MUST`の規範文について、テスト対応の有無を示す。
- `verify`は、未テストの`MUST`の規範文があれば、テストを実行せず状態`blocked`にする。
- テスト対応は対象の宣言であり、アサーションの十分性を証明しない。

## 4. 性能予算

基準ワークスペースは、EARS-AIの規範文1,000件、参照5,000件、仕様文書300件とする。

| 操作 | 目標 |
|---|---:|
| 変更範囲の`bitz check` | 1秒以内 |
| 20文書・128 KiB以下の`bitz context` | 1秒以内 |
| `bitz check --full` | 5秒以内 |
| `bitz doctor` | 2秒以内 |
| Coreが追加で使うメモリ | 200 MiB以内 |

`verify`は、利用者のテストの時間を除くCoreのオーバーヘッドを500ミリ秒以内とする。Core 1.0は永続キャッシュを持たず、
同一の操作内で破棄されるメモリキャッシュだけを使用できる。基準の複合ワークスペースは、20ワークスペース、
合計で仕様文書1,000件、参照20,000件とし、`check --all-workspaces`を30秒以内、
3ワークスペースへ到達する横断依存の20文書で標準の提示が128 KiB以下の`context`を1秒以内とする。
全体操作の並列化は、測定で必要性が確認されるまで導入しない。

複合ワークスペースの性能は、バージョン管理した基準fixtureと環境のマニフェストを使い、クリーンな作業ツリー、
マニフェストのストレージの種類、ネットワークなし、`--report`なし、JSON出力で測定する。Coreの永続キャッシュは存在しない。
OSのファイルキャッシュを暖める1回を測定外とした後、5回のプロセス全体の実時間の中央値を判定値にする。
各値、キャッシュのない初回の実行、RSSのピーク増分、OSとカーネル、CPU、論理コア数、RAM、ストレージ、Python、Git、Coreのコミットを記録する。
CoreのRSSのピーク増分は200 MiB以内とする。

仕様文書10,000件は、安全上の絶対上限のfixtureであり、30秒のSLOの対象にはしない。通常規模の性能の回帰と、
上限の直前・直後で安全に完了または`blocked`にできることを、別々に検査する。

複合ワークスペースの全体の索引のメモリは、ファイル、規範文、関係、トレース、コマンドの入力グラフの大きさに対して線形とする。
コンテキストは検証対象ごとの到達グラフに対して線形に解決し、全体操作の`verify`で、すべての検証対象の完全なコンテキスト一式を
同時に保持しない。検証対象ごとに、コンテキストのハッシュ値、規範文、テスト割当ての参照へ縮約して解放し、
ワークスペースまたは文書の全組合せの表を作らない。

リソースの各次元について、`limit - 1`、`limit`、`limit + 1`を、独立したfixtureで検査する。最大の次元のfixtureは、
基準環境でCoreのRSSのピーク増分を1 GiB以下とし、2 GiBのメモリ上限の下で正常に終了させる。
この値は絶対上限の安全上の受入条件であり、通常のfixtureの200 MiBの目標を緩和せず、
すべての利用環境へ保証する公開のSLOにもしない。

基準入力、生成物のハッシュ値、環境の比較キー、測定のケース、結果のスキーマは
[`fixtures/performance`](../../fixtures/performance/README.md)を正とする。人間による仕様の作成とレビューの効果は
機械的な性能と分離する。[`fixtures/comparison`](../../fixtures/comparison/README.md)の5つの比較タスク（comparison task）は、
任意の研究用として保持し、Core 1.0のGate Cまたはリリースの条件にはしない。有効な結果を取得するまでは、
人の生産性に対する優位性を主張しない（[ADR-058](10_決定記録/ADR-058_Gate-Cから比較タスクの実測を外す.md)）。

## 5. 脅威モデル

対象は互いを信頼する個人から数人のチームである。主な脅威は次とする。

- 仕様本文の命令をAIまたはツールの命令として扱う
- 対象外のパスや外部のサービスを変更する
- 不完全なテストで合格したように見せる
- 承認済みの要求を自動の修復が変更する
- テストの出力やレポートへ秘密情報を保存する
- プラグインまたは依存物が改ざんされる
- 未登録のワークスペース、シンボリックリンク、サブモジュールによって、複合ワークスペースの所有境界を越える

悪意あるリポジトリの管理者、組織内の敵対者、外部の承認基盤は、Core 1.0の防御対象外とする。

## 6. 信頼境界

- Gitリポジトリと管理者を信頼する。
- `.spec/bitz.yaml`を設定の正本とする。
- 複合ワークスペースでは、Gitリポジトリのルートのカタログを参加ワークスペースの正本とし、メンバーの設定を継承しない。
- Markdownの本文、コメント、外部のリンク、テストの出力は未信頼データとする。
- 文書内容だけを根拠に権限を増やさない。
- EARS-AIの自由記述は`untrustedText`として下流へ渡す。
- コンテキスト一式の本文をアダプターのシステム指示へ昇格しない。

## 7. 最小権限

- `context`と`doctor`は書込みを行わない。
- `check`は、`--report`なしではファイルシステム上も読取り専用とし、`verify`もCore自身のファイルを書き出さない。
- `check`と`verify`は、仕様文書とコードを変更せず、`--report`を明示したときだけ結果のファイルを書き出す。
- Core 1.0は、永続キャッシュ、索引、ロックファイル、作業用のディレクトリを暗黙に作成しない。
  メモリキャッシュはプロセスが終了するときに破棄する。
- `verify`は、`bitz.yaml`に配列形式の引数列として定義されたコマンドだけを、シェルを介さずに実行する。
- テストコマンド自身の副作用はコマンドの所有者の責務とし、Coreは暗黙の書込みを追加しない。
- 明示したレポート以外のファイルへの書込み、コミット、プッシュ、PR、通知、デプロイは別の操作とする。
- リポジトリ外への読取り・書込みを行わない。
- メンバーの操作では、当該メンバーが所有するパスを越えて、コード、テスト、コマンドの作業ディレクトリ（`cwd`）を扱わない。
- 承認済みのREQの意味をCoreまたはスキルが自動修正しない。

## 8. プロセスの安全性

- コマンドのタイムアウトは1〜3,600秒の範囲とする。
- タイムアウトしたときは、2秒後に直接起動したプロセスを強制終了し、子孫がパイプを保持していても、
  タイムアウトに達してから5秒以内に結果を返す。
- Coreが停止を保証するのは直接起動したプロセスまでとし、プロセスグループと子孫は、プラットフォームが許す範囲で停止する。
- 標準出力と標準エラー出力は、プロセスを起動した時点から並行して汲み出し、伏せ字化した後の、それぞれの末尾64 KiBだけを保持する。
- 公開する結果とレポートの抜粋は、不正なUTF-8と端末の制御文字を無害化し、秘密らしい値をマスクして、切り詰めの有無を明示する。
- 環境変数の値、全文の出力、秘密情報をレポートへ保存しない。
- 標準入力はnullデバイスとし、環境はCoreを起動したときの値をコピーして、`PWD`だけを実効の作業ディレクトリ（`cwd`）へ合わせる。
- 起動の失敗、シグナル、タイムアウトは状態`error`とし、通常の終了で終了コードが0以外のものは状態`failed`とする。

## 9. 更新と供給網

- 依存をロックし、公開物はソースのコミットとビルドの手順へ対応付ける。
- プラグインがスクリプトを動的に取得して即時に実行しない。
- 外部のソースは、完全なコミットSHAで固定する。
- 更新の前に、`doctor`でCoreのAPIと対応機能を確認する。
- 移行はドライランを既定とし、原文を自動で上書きしない。

署名付きの来歴、SBOM、再現可能なビルドは推奨だが、Core 1.0の出荷条件にしない。

## 10. 非目標

- 専用の認証・承認・免除のサービス
- 永続的な実行、ロックの台帳、イベントストア
- LLMによる意味の承認
- OSをまたぐ、プロセスの木構造の完全な制御
- ファイルシステム全体の原子的なスナップショット
- 外部へのテレメトリの既定の送信
