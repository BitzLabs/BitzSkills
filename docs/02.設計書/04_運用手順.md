# 運用手順

## 1. 導入

通常のAI-SDDの利用では、`bitz-core`とSDD用のスキル（Skill）を導入する。CIまたはLLMを使わない環境では、自己完結したCLIを利用する。

```text
plugin install bitz-core
plugin install bitz-sdd       # 必要な場合
bitz doctor
bitz check --full
```

```text
uv tool install bitz          # CLIだけを利用する場合
bitz doctor
```

実際のプラグインのコマンドはクライアントごとに異なる。Core 1.0はネットワークなしで基本操作を実行できる。
どの経路でも、起動するコマンドは`bitz`とする。対応する実行環境、配布物名、Gitの下限のバージョンは
[ADR-045](10_決定記録/ADR-045_実行環境と配布物の確定.md)に従う。

## 2. 最小設定

```yaml
schemaVersion: "1.0"
language: ja
earsAi: "1.0"
```

検証を開始するときに`verify.commands`を追加する。正確なスキーマは
[ワークスペース・設定仕様](../03.詳細設計/02_仕様文書モデル/01_ワークスペース・設定仕様.md)を参照する。

複合ワークスペースでは、リポジトリのルートの設定へ複合ワークスペースのカタログを置き、各メンバーにも自己完結した設定を置く。

```yaml
workspace:
  id: platform
multiWorkspace:
  members:
    - id: web
      path: apps/web
    - id: api
      path: services/api
```

メンバーの登録、所有境界、修飾IDは
[複合ワークスペース仕様](../03.詳細設計/02_仕様文書モデル/05_複合ワークスペース仕様.md)に従う。

既存の単一ワークスペースを複合ワークスペース化するときは、不完全なカタログを許す段階的な移行を行わない。次を同じ変更集合へ含める。

1. ルートワークスペースの`workspace.id`と`multiWorkspace.members`
2. すべてのメンバーの設定にある`workspace.id`
3. ワークスペースを越える`relations`と`tests[].covers`の修飾ID
4. CIの全体操作と、JSONの利用側における複合ワークスペースの結果への対応

生成側を切り替える前に、すべてのJSONの利用側を、単一ワークスペースと複合ワークスペースの二重読取りへ更新する。
利用側は`schemaVersion`のメジャーバージョンを確認し、
`workspace`だけを持つ単独結果と、`multiWorkspace`および`workspaces`だけを持つ全体結果を排他的に識別する。
修飾ID、レポート名、現在のディレクトリから結果の種別を推測しない。CIは単独操作のまま、新しいCoreと`multiWorkspace.v1`の確認を
先に導入し、その後に、上記の変更集合と`--all-workspaces`を同時に切り替える。

変更した後の作業ツリーで`doctor --all-workspaces`、`check --all-workspaces`、`verify --all-workspaces`を実行してから適用する。
明示した`--report`を使うジョブだけ、複合ワークスペースのレポートの保存と成果物の収集へ切り替える。旧来の単一ワークスペースのレポートは
読取り専用の履歴として保持できるが、現在の複合ワークスペースの結果と同じ状態、件数、時系列へは集約しない。

ロールバックでは、ルートワークスペースのカタログ、すべてのメンバーの設定、修飾関係・カバレッジ・TASKの参照、CIの全体操作、
対応機能のゲート、レポートの利用側を、同じリリースの単位で戻す。二重読取りの利用側は残してよいが、単一ワークスペースと複合ワークスペースの
成果物の系列を混ぜず、過去のレポートを書き換えない。
ロールバックの後は、単一ワークスペースの`doctor`、`check --full`、`verify`を実行する。後続の変更を失わずに一式を戻せない場合は、
自動で元へ戻す方向の移行を行わず、複合ワークスペースの状態を、戻さずに新しい変更で修正する。
ワークスペースIDは永続的な同一性であり、複合ワークスペース化した後のリネームはCore 1.0では対応しない。
メンバーのパスは、IDを維持して移動する。

## 3. 日常操作

```text
意図の確定後:       bitz context <ID> --purpose implement
書込み直前:         bitz context <ID> --purpose implement --expect-digest <digest>
実装前:             bitz check <ID>
実装後:             bitz check              # TASK起点は bitz check <TASK-ID>
検証:               bitz verify <ID>
TASK完了時:          statusをdoneへ変更後、bitz check <TASK-ID>
CIまたは節目:        bitz check --full
問題発生時:          bitz doctor
memberを明示:         bitz check --workspace web --full
連合全体:            bitz check --all-workspaces / bitz verify --all-workspaces
```

通常の実行はネットワークとLLMを使わない。`check`と`verify`は、結果の状態にかかわらず、`--report`を指定したときだけレポートを保存する。
`--report`なしのCIと日常の検査は、既存のレポートを変更せず、新しいファイルも作らない。`context`と`doctor`はレポートを保存しない。

## 4. CI

検査対象の作業ツリーへ統合先の先端を含め、比較元を明示する。

```text
bitz check --full --base <統合先先端>
bitz verify
```

複合ワークスペースのCIは、同じリポジトリのルートとルートワークスペースを発見できるディレクトリで、次を実行する。
現在のディレクトリをリポジトリのルートへ固定する必要はないが、CIでは探索の条件を単純にするため、リポジトリのルートでの起動を推奨する。

```text
bitz doctor --all-workspaces
bitz check --all-workspaces --base <統合先先端>
bitz verify --all-workspaces
```

Coreは既定のブランチ、リモート、マージベースを推測しない。指定したリビジョンを解決できない場合は引数不正とする。
既存のリンター、型検査、SAST、テストランナーを置き換えず、`bitz verify`から設定済みのコマンドとして呼ぶ。
CIの成果物として結果を保存する場合だけ`--report`を明示し、通常の合否判定は標準出力と終了コードを使用する。

## 5. Git運用

- フローは、専用のブランチまたはワークツリーで行う。
- コミット、プッシュ、マージ、リベースはCoreの外で行う。
- 大きな意味の変更と整形の変更を、同じコミットへ混ぜない。
- 正確な変更履歴はGitとPRを正とする。
- 仕様文書ごとの`Revision History`は要求しない。
- 並行開発のID衝突は、統合先を取り込んだ後の`check --full`で検出し、人間が解決する。
- 複合ワークスペースのカタログの変更とメンバーの移動は、基準版を明示した`check --all-workspaces`でレビューする。
- カタログからメンバーを削除して、管理済みの仕様文書の削除検査を迂回しない。ワークスペースIDを変えず、パスだけを移動する。
- Gitを利用できない環境では複合ワークスペースを実行せず、単一ワークスペースの縮退だけを利用する。

## 6. キャッシュ

- キャッシュがなくても正しく動く。
- Coreのバージョン、スキーマのバージョン、設定、入力の内容に対応する内部のキーを使う。
- 破損、不一致、読取りの失敗があった場合は、破棄して再計算する。
- 内部のハッシュ値と保存形式は、公開APIにしない。
- キャッシュの有無で、診断と終了コードを変えない。

## 7. 更新

- Coreのメジャーバージョンを更新する前に`bitz doctor`を実行する。
- アダプターは、開始するときに、必要なCoreのAPIと対応機能を確認する。
- 移行は、決定論的な部分だけを提案する差分として出す。
- 更新に失敗した場合に、既存の`.spec/`を変更しない。
- プラグインはCoreを自動で更新しない。

## 8. 障害時

| 状況 | 対応 |
|---|---|
| 設定の構文・型・必須項目が不正 | `error`と該当するキーを確認して修正 |
| 未対応のスキーマのメジャーバージョン | `blocked`。互換性のあるバージョンへ更新または移行 |
| 強い関係の参照切れ・循環 | `failed`。参照元、参照先、エッジを修正 |
| コンテキストの上限の超過 | `blocked`。依存を分割または上限を見直す |
| コンテキストのハッシュ値の不一致 | `blocked`。コンテキストを再取得する |
| テスト環境の不足 | `blocked`。不足しているコマンドを導入する |
| キャッシュの破損 | キャッシュを破棄して再実行する |
| Git不在 | 差分保護とTASK境界の縮退を確認する |
| メンバーの設定の不在・IDの不一致 | カタログとメンバーの`workspace.id`を一致させる |
| 未登録の`.spec/bitz.yaml` | Gitが認識している設定をカタログへ登録するか、不要なら管理対象から明示的に除く |
| 横断参照・所有境界違反 | 修飾IDを確認し、コード、テスト、TASKを所有するメンバーへ移す |
| 複合ワークスペースのリソースの上限の超過 | 診断の`dimension`と`limit`を確認し、複合ワークスペースまたは仕様文書を分割する |

復旧は、Gitの差分の確認、局所的な修正、同じ操作の再実行で完結させる。

## 9. バックアップと観測性

正本はGitで管理された`.spec/`であり、Core独自のバックアップを持たない。観測性は、所要時間、対象の件数、キャッシュのヒットとミス、
診断の件数に限定し、テレメトリを外部へ送信しない。
