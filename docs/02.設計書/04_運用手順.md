# 運用手順

## 1. 導入

通常のAI-SDD利用では`bitz-core`とSDD用Skillを導入する。CIまたは非LLM環境では自己完結CLIを利用する。

```text
plugin install bitz-core
plugin install bitz-sdd       # 必要な場合
bitz doctor
bitz check --full
```

```text
uv tool install bitz          # CLIだけを利用する場合
bitz doctor
```

実際のplugin commandはclientごとに異なる。Core 1.0はnetworkなしで基本操作を実行できる。

## 2. 最小設定

```yaml
schemaVersion: "1.0"
language: ja
earsAi: "1.0"
```

検証を開始するときに`verify.commands`を追加する。正確なSchemaは
[workspace・設定仕様](../03.詳細設計/02_SPECモデル/01_workspace・設定仕様.md)を参照する。

モノレポではGit rootの設定へ連合catalogを置き、各memberにも自己完結した設定を置く。

```yaml
workspace:
  id: platform
monorepo:
  members:
    - id: web
      path: apps/web
    - id: api
      path: services/api
```

member登録、所有境界、修飾IDは
[モノレポSPEC連合仕様](../03.詳細設計/02_SPECモデル/05_モノレポSPEC連合仕様.md)に従う。

既存の単一workspaceを連合化するときは、不完全catalogを許す段階移行を行わない。次を同じ変更集合へ含める。

1. federation rootの`workspace.id`と`monorepo.members`
2. 全member設定の`workspace.id`
3. workspaceを越える`relations`と`tests[].covers`の修飾ID
4. CIの全体操作とJSON consumerの連合結果対応

producer切替前に全JSON consumerを単一／連合のdual-readへ更新する。consumerは`schemaVersion` majorを確認し、
`workspace`だけを持つ単独結果と、`federation`および`workspaces`だけを持つ全体結果を排他的に識別する。
修飾ID、report名、current directoryから結果種別を推測しない。CIは単一操作のまま新Coreと`monorepo.v1`確認を
先行導入し、その後に上記変更集合と`--all-workspaces`を同時に切り替える。

変更後treeで`doctor --all-workspaces`、`check --all-workspaces`、`verify --all-workspaces`を実行してから適用する。
明示`--report`を使うjobだけ連合reportの保存・artifact収集へ切り替える。旧単一reportは読取り専用の履歴として
保持できるが、現在の連合結果と同じstatus、件数、時系列へ集約しない。

rollbackではroot catalog、全member設定、修飾関係・coverage・TASK参照、CI全体操作、Capability gate、report consumerを
同じrelease単位で戻す。dual-read consumerは残してよいが、単一と連合のartifact系列を混ぜず、過去reportを書き換えない。
rollback後は単一workspaceの`doctor`、`check --full`、`verify`を実行する。後続変更を失わずに一式を戻せない場合は
自動down migrationを行わず、連合状態をforward fixする。workspace IDは永続identityであり、連合化後のrenameは
Core 1.0で対応しない。member pathはIDを維持して移動する。

## 3. 日常操作

```text
意図の確定後:       bitz context <ID> --purpose implement
書込み直前:         bitz context <ID> --purpose implement --expect-digest <digest>
実装前:             bitz check <ID>
実装後:             bitz check              # TASK起点は bitz check <TASK-ID>
検証:               bitz verify <ID>
TASK完了時:          statusをdoneへ変更後、bitz check <TASK-ID>
CIまたは節目:        bitz check --full
問題発生時:          bitz doctor
memberを明示:         bitz check --workspace web --full
連合全体:            bitz check --all-workspaces / bitz verify --all-workspaces
```

通常実行はnetworkとLLMを使わない。`check`と`verify`はstatusにかかわらず`--report`指定時だけreportを保存する。
`--report`なしのCIと日常検査は既存reportを変更せず、新しいfileも作らない。`context`と`doctor`はreportを保存しない。

## 4. CI

検査対象のtreeへ統合先先端を含め、比較元を明示する。

```text
bitz check --full --base <統合先先端>
bitz verify
```

モノレポ連合のCIは同じGit rootとfederation rootを発見できるdirectoryで次を実行する。current directoryを
repository rootへ固定する必要はないが、CIでは探索条件を単純にするためroot起動を推奨する。

```text
bitz doctor --all-workspaces
bitz check --all-workspaces --base <統合先先端>
bitz verify --all-workspaces
```

Coreはdefault branch、remote、merge-baseを推測しない。指定revisionを解決できない場合は引数不正とする。
既存のlint、type check、SAST、test runnerを置き換えず、`bitz verify`から設定済みcommandとして呼ぶ。
CI artifactとして結果を保存する場合だけ`--report`を明示し、通常の合否判定は標準出力と終了コードを使用する。

## 5. Git運用

- フローは専用branchまたはworktreeで行う。
- commit、push、merge、rebaseはCoreの外で行う。
- 大きな意味変更とformat変更を同じcommitへ混ぜない。
- 正確な変更履歴はGitとPRを正とする。
- SPECごとの`Revision History`は要求しない。
- 並行開発のID衝突は統合先を取り込んだ後の`check --full`で検出し、人間が解決する。
- 連合catalogの変更とmember移動は、基準版を明示した`check --all-workspaces`でreviewする。
- catalogからmemberを削除して管理済みSPECの削除検査を迂回しない。workspace IDを変えずpathだけを移動する。
- Gitが利用できない環境では連合を実行せず、単一workspaceの縮退だけを利用する。

## 6. cache

- cacheなしでも正しく動く。
- Core版、Schema版、設定、入力内容に対応する内部keyを使う。
- 破損、不一致、読取り失敗時は破棄して再計算する。
- 内部hashと保存形式は公開APIにしない。
- cacheの有無でDiagnosticと終了コードを変えない。

## 7. 更新

- Core major更新前に`bitz doctor`を実行する。
- adapterは開始時に必要Core APIとCapabilityを確認する。
- 移行は決定論的な部分だけを提案diffとして出す。
- 更新失敗時に既存`.spec/`を変更しない。
- pluginがCoreを自動更新しない。

## 8. 障害時

| 状況 | 対応 |
|---|---|
| 設定の構文・型・必須項目が不正 | `error`と該当keyを確認して修正 |
| 未対応Schema major | `blocked`。互換版へ更新または移行 |
| 強い依存の参照切れ・循環 | `failed`。source、target、edgeを修正 |
| Context上限超過 | `blocked`。依存を分割または上限を見直す |
| Context Digest不一致 | `blocked`。Contextを再取得する |
| test環境不足 | `blocked`。不足commandを導入する |
| cache破損 | cacheを破棄して再実行する |
| Git不在 | 差分保護とTASK境界の縮退を確認する |
| member設定不在・ID不一致 | catalogとmemberの`workspace.id`を一致させる |
| 未登録`.spec/bitz.yaml` | Git既知の設定をcatalogへ登録するか、不要なら管理対象から明示的に除く |
| 横断参照・所有境界違反 | 修飾IDを確認し、code／test／TASKを所有memberへ移す |
| 連合resource上限超過 | Diagnosticの`dimension`と`limit`を確認し、連合またはSPECを分割する |

復旧はGit diffの確認、局所修正、同じ操作の再実行で完結させる。

## 9. backupと観測性

正本はGit管理された`.spec/`であり、Core独自backupを持たない。観測性は所要時間、対象件数、cache hit/miss、
Diagnostic件数に限定し、telemetryを外部送信しない。
