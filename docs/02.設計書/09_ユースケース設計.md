# ユースケース設計

## 1. 目的

本書は、Bitz AI-SDD Core 1.0を利用する人間、AIエージェント、CI、拡張プラグインが、
どの入口から何を行い、どの結果を得るかをユースケースとして整理する。

本書は利用者視点の目的、基本フロー、代替・例外フロー、完了条件を定義する。コマンド文法、
対象選択、結果Schema、Diagnostic、状態遷移の機械契約は、リンク先の詳細設計を正とする。
UC-06、UC-07、§6.1の実装後検査と戻り先は、ユースケースとして期待する接続を示すが、既存設計との差分を含む。
差分は§7の提案が裁定されるまでCore 1.0の機械契約にしない。

## 2. 対象範囲

対象は、個人から数人の信頼された開発チームが、1つのGitリポジトリ内でEARS-AIと`.spec/`を使用し、
AI支援による仕様解釈、実装、静的検査、実行検証を行うCore 1.0である。

次は本書の対象外とする。

- 自由記述要求の意味的正しさの自動証明
- LLM出力の決定論性の保証
- 外部policy・承認サービス、分散ロック、永続run台帳
- 複数Gitリポジトリ、Git submodule、ネットワーク越しのSPEC連合
- Deferred DraftであるSDD、Quality、DDD Profileの実行契約

## 3. アクター

| アクター | 役割 |
|---|---|
| 開発者 | SPECの作成・改訂、コード・テストの実装、結果確認を行う |
| 人間レビュー者 | 要求の意味、高リスク変更、最終diffを確認する |
| AIエージェント | Context Bundleに従って計画・実装・検証を支援する |
| AI CLIアダプター | Core操作を呼び出し、権限確認と結果説明を行う |
| CI | 全体検査・検証を非対話で実行し、終了コードを判定する |
| 拡張プラグイン | Core APIとCapabilityを確認してから追加ワークフローを提供する |
| `bitz-core` | EARS-AI解析、Context解決、検査、検証、診断の機械判定を所有する |

## 5. ユースケース詳細

### UC-01 初回導入と利用前診断

**目的**: Coreとworkspaceを安全に利用できる前提が揃っていることを確認する。

**事前条件**:

- 開発者が対象ディレクトリを選択している。
- Coreを呼び出せるか、拡張プラグインが静的な導入案内を提供できる。

**基本フロー**:

1. 開発者または拡張プラグインが`bitz doctor`を実行する。
2. Coreは自身、Python、`.spec/bitz.yaml`、Schema、EARS-AI版、Git、検証コマンド、キャッシュを読取り専用で診断する。
3. 拡張プラグインから互換性要求が渡された場合、Core APIと要求Capabilityを照合する。
4. Coreは利用可能な機能、失われる保証、必要な修復手順を返す。
5. 前提が揃っていれば、開発者は`bitz check --full`へ進む。

**代替・例外フロー**:

- Core不在で`doctor`自体を呼べない場合、拡張プラグインは静的な導入手順だけを示す。
- `.spec/`または設定がない場合、Coreは作成先と最小設定を示して`blocked`とする。
- Git不在の単一workspaceでは処理を継続し、失われる保証を警告する。
- Git不在のモノレポ連合では所有境界を確定できないため`blocked`とする。

**完了条件**: Coreと必要Capabilityが利用可能で、workspace設定を読み取れる。または、停止理由と修復手順が明示されている。

**正本**: [`bitz doctor`仕様](../03.詳細設計/02_SPECファイル規定/11_doctor仕様.md)

### UC-02 SPECの作成・改訂・承認

**目的**: 要求、技術契約、設計判断、作業単位を、人間とAIが共有できる安定した契約として記録する。

**事前条件**: `.spec/bitz.yaml`が存在し、対象workspaceが決定している。

**基本フロー**:

1. 開発者は目的に応じてREQ、TECH、ADR、TASKを選択する。
2. Frontmatterへ安定ID、title、種別ごとのstatusを記述する。
3. REQまたは必要なTECHへEARS-AI規範文を記述する。
4. 必要な前提、具体化、実装対象、置換、関連を型付き関係で記述する。
5. 実装・検証段階で`implements`、`tests`、`verify`、TASK `changes`を追加する。
6. 主要な改訂意図を`Revision History`へ追記する。
7. `bitz check`で構文、ID、関係、状態遷移、文書構造を検査する。
8. 人間が意味を確認したREQ/TECHを`approved`としてGit diffへ記録する。

**代替・例外フロー**:

- 未完成のREQ/TECHは`draft`とし、限定された構文不備をwarningとして扱う。
- 承認済みREQの意味を変更する場合、同じ変更で`draft`または`outdated`へ戻し、改訂理由を追記する。
- ADRのDecisionを変更する場合は後継ADRを作る。
- 完了TASKへ追加作業が生じた場合は、新しいTASK IDを作る。

**完了条件**: 現在のstatusが合法で、ID、本文構造、強い関係が解決可能である。

**正本**: [SPECファイル規定](../03.詳細設計/02_SPECファイル規定/README.md)

### UC-03 目的別Contextの取得

**目的**: 起点SPECを解釈、実装、検証するために必要な強い依存を、部分成功なしで取得する。

**事前条件**: 起点となる文書IDまたは規範文IDが特定されている。

**基本フロー**:

1. 利用者またはアダプターが起点と`interpret`、`implement`、`verify`のpurposeを指定する。
2. Coreはworkspaceと起点を解決する。
3. Coreは型、状態、循環を検査しながら強い依存を終端まで探索する。
4. Coreはapplicable、advisory、work、replacementを分類する。
5. Coreは全適用規範文をConstraint Ledgerへ格納し、purpose別Coverageを計算する。
6. Coreは段階的Projection、Context Digest、Projection Digestを返す。
7. AIエージェントは全`MUST`、制約、変更境界、coverage gapを計画へ反映する。

**代替・例外フロー**:

- 参照切れ、型違反、禁止循環は`failed`とする。
- 適用不能状態、上限超過、Digest不一致は`blocked`とする。
- 解決集合外の文書を`--expand`した場合は暗黙追加せず`failed`とする。
- 置換済み起点を`implement`または`verify`へ使った場合、後継候補を示して`blocked`とする。

**完了条件**: `resolution.complete: true`のBundleを得るか、部分成功ではない停止理由を得る。

**正本**: [Context Resolution仕様](../03.詳細設計/02_SPECファイル規定/10_Context%20Resolution仕様.md)

### UC-04 SPECと変更範囲の静的検査

**目的**: EARS-AI、SPEC、関係、パス、状態遷移、変更境界の機械的不適合を検出する。

**事前条件**: workspaceとGit比較基準を決定できるか、Git不在時の縮退を適用できる。

**基本フロー**:

1. 利用者は引数なし、明示対象、`--full`、`--all-workspaces`のいずれかを選ぶ。
2. Coreは全SPECの軽量Frontmatter索引を構築する。
3. Coreは対象文書、強い依存閉包、直接の逆参照を決定する。
4. Coreは設定、配置、Frontmatter、EARS-AI、関係、パス、文書構造を順に検査する。
5. Git基準版がある場合、状態遷移、承認済みREQ保護、必要なTASK境界を検査する。
6. CoreはDiagnosticと共通statusを返す。

**代替・例外フロー**:

- 引数形式または排他条件が不正な場合は終了コード4とし、レポートを作らない。
- Git不在では全体検査へ縮退し、差分依存の保証をwarningまたは`blocked`として明示する。
- 独立して検査できるファイルは、他ファイルの構文エラー後も可能な限り診断する。

**完了条件**: 検査対象、比較基準、個別Diagnostic、集約statusが再現可能な形で得られる。

**正本**: [参照・トレース・検証仕様 §4](../03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md#4-bitz-check)

### UC-05 要求とテストの実行検証

**目的**: 対象となる全`MUST`にテスト対応があり、そのコマンドが実際に成功することを確認する。

**事前条件**: 対象SPECが適用可能で、テストpathと検証コマンドを設定から解決できる。

**基本フロー**:

1. 利用者は明示対象、引数なし、`--all-workspaces`のいずれかを選ぶ。
2. Coreは`purpose=verify`のContextを完全解決する。
3. Coreはtarget statement集合と文書単位verification bindingを確定する。
4. Coreは対象`MUST`のテスト対応、テストpath、コマンド、`cwd`、実効timeoutを解決する。
5. Coreは同一bindingのテストを重複排除し、シェルを介さずにコマンドを実行する。
6. CoreはContext Digest、対象句、argv、終了理由、終了コード、所要時間を対応付ける。
7. Coreは対象別結果と全体statusを返す。

**代替・例外フロー**:

- 未tested `MUST`、コマンド不足、環境不足は対象単位で`blocked`とする。
- 終了コード非0は`failed`とする。
- 起動失敗、signal、timeoutは`error`とする。
- 引数なし単一workspaceで対象0件の場合は`blocked`とする。
- モノレポの対象0件memberはwarningとし、連合全体0件の場合だけ`blocked`とする。

**完了条件**: 実行対象ごとのstatusとcommand結果を保持したまま、共通順位で全体statusを得る。

**正本**: [参照・トレース・検証仕様 §5](../03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md#5-bitz-verify)

### UC-06 Small Flowによる通常開発

**目的**: 通常のバグ修正、局所的機能追加、リファクタリングを、少ない待ち時間で安全に完了する。

**事前条件**:

- 変更意図と対象SPECが特定されている。
- 高リスク変更に該当しない。
- 既存の未コミット変更と衝突しない。

**基本フロー**:

1. Intentとして対象要求、規範文、または作業SPECを特定する。
2. `purpose=implement`のContext Bundleを取得する。
3. 構文、関係、既存変更を検査する。
4. 書込み直前にContext Digestを再照合する。
5. 変更境界内でコードとテストを実装する。
6. 実装後の成果物を検査する。
7. `purpose=verify`を再解決し、対象テストを実行する。
8. 人間が対応規範文IDと最終diffを確認する。
9. 完了結果をGitへ記録する。

**代替・例外フロー**:

- Contextが`blocked`または`failed`なら実装を開始しない。
- コンパイル、Lint、単体テスト失敗は変更境界内で最大2回まで局所修正する。
- 一時的ツール障害は冪等な再実行を最大1回行う。
- 仕様矛盾、権限不足、要求の意味変更は自動修復せず人間へ戻す。
- 作業中に高リスク条件が判明した場合はFull Flowへ切り替える。

**完了条件**: Context Digest、静的検査、対象`MUST`のテスト実行、最終diff確認が完了している。

**正本**: [SDDプロセス設計](04_SDDプロセス設計.md)

### UC-07 Full Flowによる高リスク変更

**目的**: 公開契約、データ、セキュリティ、費用、法令、SLO、複数workspaceへ影響する変更を明示レビュー付きで進める。

**事前条件**: Full Flow条件の少なくとも1つに該当する。

**基本フロー**:

1. Intentと影響範囲を特定する。
2. Contextを完全解決する。
3. 人間が要求の意味、受入条件、互換性をレビューする。
4. 人間が設計、変更境界、検証方法をレビューする。
5. Small Flowと同じCore検査を行う。
6. 承認された要求と設計に従って実装する。
7. 静的検査と実行検証を行う。
8. 人間が最終diff、未証明事項、運用影響をレビューする。
9. 完了結果をGitへ記録する。

**代替・例外フロー**:

- Requirement Reviewで否決された場合、IntentまたはREQ改訂へ戻る。
- Design Reviewで否決された場合、設計または変更境界の改訂へ戻る。
- 実装・検証失敗時はSmall Flowと同じ分類済みリトライ規則を使う。
- 複数workspaceの独立起点はrequestを分け、全体操作で集約する。

**完了条件**: 要求、設計、実装、検証、最終diffについて必要な人間確認が完了している。

**正本**: [SDDプロセス設計 §3](04_SDDプロセス設計.md#3-full-flow条件付き)

### UC-08 Spikeによる技術的不確実性の解消

**目的**: 要求を確定する前に、隔離された実験で技術的な実現可能性と制約を確認する。

**事前条件**: 技術的不確実性が高く、通常フローの設計判断に必要な証拠が不足している。

**基本フロー**:

1. 開発者は実験目的、時間、隔離範囲を定める。
2. 本番成果物と分離した領域で実験する。
3. 結果、失敗、制約、採否判断を整理する。
4. 学びをREQ、TECH、ADRのいずれかへ短く反映する。
5. 採用する場合はSmall FlowまたはFull Flowで本番実装を行う。

**代替・例外フロー**:

- 不採用の場合は理由を記録し、Spike成果物を本番へマージしない。
- 実験中に高リスク条件が判明した場合はFull Flowのレビュー対象へ加える。

**完了条件**: 学びと採否がSPECまたはGit管理された記録へ反映され、Spike成果物が本番実装と区別されている。

**正本**: [SDDプロセス設計 §4](04_SDDプロセス設計.md#4-spike)

### UC-09 モノレポ連合の横断操作

**目的**: 複数workspaceの独立性、所有境界、横断依存の完全性を同時に維持する。

**事前条件**: Gitルートの連合カタログに全memberが明示登録され、workspace IDとpathが一致している。

**基本フロー**:

1. Coreは最寄り設定または`--workspace`からselected workspaceを決める。
2. Coreは連合全体の軽量修飾ID索引を構築する。
3. 通常操作ではselected workspaceと強い依存で到達するworkspaceだけを完全解析する。
4. 横断参照は修飾IDで解決し、pathとコマンドは所有workspaceから取得する。
5. `--all-workspaces`では連合ルート、workspace ID辞書順に処理する。
6. 独立したworkspaceは先行workspaceの失敗後も可能な範囲で継続する。
7. 個別結果を保持したまま共通順位で全体statusを集約する。

**代替・例外フロー**:

- 未登録member、非修飾横断参照、所有境界違反は`blocked`または`failed`とする。
- `context`は`--all-workspaces`を受け付けず、独立起点はrequestを分ける。
- 異なるworkspaceの同名コマンドを統合しない。
- Git不在では連合操作を`blocked`とする。

**完了条件**: workspace別の結果、横断edge、所有者、集約statusを決定論的に再現できる。

**正本**: [モノレポSPEC連合仕様](../03.詳細設計/02_SPECファイル規定/12_モノレポSPEC連合仕様.md)

### UC-10 SPEC状態、置換、影響候補の管理

**目的**: 文書の適用可能性と人間確認の境界を、過剰なrun状態機械なしで管理する。

**事前条件**: Git基準版を利用できるか、現在値だけを検査する縮退を明示できる。

**基本フロー**:

1. 開発者は種別ごとの合法なstatusを選ぶ。
2. `bitz check`はGit基準版から現在値への遷移を検査する。
3. 強い依存先が変更された場合、Coreは直接の逆参照を影響候補として警告する。
4. 人間は必要に応じてREQ/TECHを`outdated`へ変更する。
5. 見直し後、人間は`draft`または`approved`へ明示遷移する。
6. 後継REQ/TECHは`supersedes`で旧文書を論理的に置換する。
7. 置換済み文書は実装・検証に使わず、明示した後継から再実行する。

**代替・例外フロー**:

- Coreは影響候補を自動的に`outdated`へ変更しない。
- 禁止遷移は`failed`とする。
- Git基準版がない場合、現在値の語彙だけを検査し、遷移合格を宣言しない。
- 同じ旧REQ/TECHに複数の有効な後継がある場合は`failed`とする。

**完了条件**: 現在status、置換関係、適用可能性が一意に解釈できる。

**正本**: [Frontmatter共通仕様 §5](../03.詳細設計/02_SPECファイル規定/03_Frontmatter共通仕様.md#5-状態)

### UC-11 非成功結果の復旧とレポート

**目的**: 失敗、前提不足、ツール障害を再現可能な最小情報で確認し、Git diffと再実行で復旧する。

**事前条件**: Core操作がworkspace結果を生成できる。

**基本フロー**:

1. Core操作が`failed`、`blocked`、`error`のいずれかを返す。
2. Coreは対象、Diagnostic、必要なcommand結果、revisionを最小JSONへ保存する。
3. 開発者はstatusとDiagnosticの`resultStatus`を区別して原因を確認する。
4. 開発者は設定、SPEC、環境、コード、テストの該当箇所だけを修正する。
5. 開発者はGit diffを確認して同じ操作を再実行する。

**代替・例外フロー**:

- 成功結果は`--report`指定時だけ保存する。
- 引数不正ではworkspace結果がないため保存しない。
- レポート書込みに失敗しても、元の結果とDiagnosticは標準出力または標準エラーへ保持する。
- 長期証跡が必要な場合はCI artifactまたはPR添付を使用する。

**完了条件**: 原因と再実行条件を追跡でき、秘密値や全文ログを保存していない。

**正本**: [更新・互換性・安全性](../03.詳細設計/02_SPECファイル規定/07_更新・互換性・安全性.md)

### UC-12 拡張プラグインとCoreの互換性確認

**目的**: 拡張プラグインが、互換性のないCoreを自然言語判断で代替せず、安全に開始または停止する。

**事前条件**: 拡張プラグインが自身のID、版、要求Core API、要求Capabilityを宣言できる。

**基本フロー**:

1. 拡張プラグインは開始時に互換性要求を`doctor`へ渡す。
2. Coreは実行中のCore API、Capability、EARS-AI、workspaceを照合する。
3. 互換なら拡張プラグインはCoreの公開操作を呼び出す。
4. 拡張プラグインはCoreの判定、severity、Context選択を変更せず、利用者向けに説明する。

**代替・例外フロー**:

- Core API major不一致またはCapability不足は`blocked`とする。
- Core不在時は導入手順を示し、SkillがParserやValidatorを代替しない。
- 別の拡張プラグインを必須依存または実行時ファイル参照にしない。

**完了条件**: 拡張が互換Coreを利用して開始するか、具体的な導入・更新手順を伴って停止する。

**正本**: [CLI統合設計](03_CLI統合設計.md)

## 6. ユースケース間の関係

### 6.1 期待するCore垂直フロー

次のフローはUC-FLOW-001の裁定候補を含む。現行の正本との差分は§7を参照する。

```text
UC-02 SPEC作成・改訂
  -> UC-03 Context取得
  -> UC-04 静的検査
  -> コード・テスト実装
  -> UC-04 実装後検査
  -> UC-05 実行検証
  -> 人間による最終diff確認
```

### 6.2 開発フローの選択

```text
変更意図
  ├─ 通常変更 ----------------------> UC-06 Small Flow
  ├─ 高リスク・複数境界 ------------> UC-07 Full Flow
  └─ 技術的不確実性が高い ----------> UC-08 Spike
                                         |
                                         +-> UC-06 または UC-07
```

### 6.3 状態遷移

```text
REQ / TECH
  [new] -> draft | approved
  draft -> approved
  approved -> draft | outdated
  outdated -> draft | approved

ADR
  [new] -> proposed | accepted | rejected
  proposed -> accepted | rejected
  accepted -> superseded

TASK
  [new] -> open
  open -> done
```

同一状態の維持は全種別で許可する。`verified`は文書状態ではなく、特定Context Digest、コード、テスト、
環境に対する実行時の成功述語とする。
