# EARS-AI 記述例・アンチパターン

## 1. Core例

```markdown
- [REQ-001:CONST-01] [ACTOR:TargetSystem] [ALWAYS] [MUST] [CONSTRAINT] 監査ログに秘密情報を出力しない。
- [REQ-001:AC-01] [ACTOR:TargetSystem] [WHEN] 利用者が保存操作を確定した場合 [MUST] [THEN] 入力データを永続化する。
- [REQ-001:AC-02] [ACTOR:TargetSystem] [WHILE] オフライン状態である間 [MUST] [THEN] 更新内容をローカルキューへ保存する。
- [REQ-001:AC-03] [ACTOR:TargetSystem] [WHERE] 監査機能が有効である場合 [MUST] [THEN] 操作主体と時刻を監査ログへ記録する。
- [REQ-001:AC-04] [ACTOR:TargetSystem] [IF_ERROR] 永続化処理が失敗した場合 [MUST] [THEN] エラーコード `SAVE-001` を返す。
```

## 2. Profile組合せ

ProfileはCore文書種別の規範文へ付加する。Deferred Draftの`DOMAIN`や`RULE`をCore 1.0の文書prefixとして
例示しない。

```markdown
- [TECH-020:SPEC-01] [sdd:FLOW=Small] [quality:CHECK=unit-tests] [quality:SEVERITY=error] [ACTOR:ImplAgent] [WHEN] 実装差分を作成した場合 [MUST] [THEN] 対象単体テストを実行する。
- [REQ-010:CONST-01] [ddd:BOUNDED_CONTEXT=Sales] [ddd:VALUE_OBJECT=Money] [quality:CHECK=immutability] [ACTOR:Money] [ALWAYS] [MUST] [CONSTRAINT] 生成後の金額と通貨を変更不可にする。
```

## 3. AI生成

Good:

```markdown
- [TECH-010:SPEC-01] [ACTOR:SpecAgent] [WHEN] `REQ-010` が承認された場合 [MUST] [GENERATE] 受入基準を追跡するTECH仕様案を生成する。
- [TECH-010:CONST-01] [ACTOR:SpecAgent] [ALWAYS] [MUST] [CONSTRAINT] 未承認のビジネスルールを追加しない。
```

Bad: `- [GENERATE] 良い設計を適切に作る。`

ID、ACTOR、発動条件、規範強度、入力、評価可能な制約がない。

## 4. ACTOR混同

Bad:

```markdown
- [REQ-001:AC-01] [ACTOR:HumanPO] [WHEN] ログインされた場合 [MUST] [THEN] トークンを発行する。
```

承認者はFrontmatterの `x-owners` などプロジェクト拡張へ記録し、実行主体をACTORにする。

## 5. ID階層と親子分割

Bad:

```markdown
- [REQ-001:AC-01] [WHEN] 有効な認証情報が送信された場合
  - [REQ-001:AC-01:R-01] [THEN] システムはアクセストークンを返す。
  - [REQ-001:AC-01:R-02] [THEN] システムは認証成功を記録する。
```

3階層IDであり、ACTORと規範強度を欠き、親行だけでは合否判定できない。

Good:

```markdown
- [REQ-001:AC-01] [ACTOR:AuthService] [WHEN] 有効な認証情報を受信した場合 [MUST] [THEN] アクセストークンを1件発行する。
- [REQ-001:AC-02] [ACTOR:AuthService] [WHEN] 有効な認証情報を受信した場合 [MUST] [THEN] 認証成功を監査ログへ1件記録する。
```

発動条件の繰り返しは冗長に見えるが、各文が独立して合否判定でき、トレース、差分検出、影響分析がID単位で完結する（[ADR-005](../../02.設計書/10_決定記録/ADR-005_規範文IDの階層と記法.md)）。

## 6. 複数結果

独立して失敗・変更・検証できる結果を一文へ連結しない。DB保存、通知、監査記録は別IDへ分割する。

## 7. 数値制約

Bad: `高速に応答する`

Good:

```markdown
- [REQ-100:CONST-01] [quality:LEVEL=L4] [quality:CHECK=response-time-p95] [quality:THRESHOLD="<=200ms"] [quality:EVIDENCE=benchmark-report] [ACTOR:ApiService] [ALWAYS] [MUST] [CONSTRAINT] 通常負荷時の応答時間p95を200ms以下にする。
```

`<=200ms` は `<` を含むため `quoted-value` で記述する。

## 8. 名前空間

`[STATE:Running]` のような無名前空間タグを追加しない。Coreにない概念は、正式登録済みProfileの
名前空間を使う。Deferred DraftのProfile語彙は、実装済みと誤認させない。

## 9. Profileの過剰利用

Coreだけで表現できる要求へ、SDD、Quality、DDDタグを機械的に追加しない。Profileは検索、検証、
トレースに具体的な便益がある場合だけ有効化する。

Bad: すべての規範文へ`quality:LEVEL`や`ddd:*`を付ける。

Good: 性能閾値や集約境界など、そのProfile Validatorで実際に検査する規範文だけへ付ける。

## 10. 構文上の合格と意味上の正しさ

Parserが合格した文でも、要求内容が妥当とは限らない。構文合格を「AIが同じ意味で理解した」証拠として扱わず、
要求の意味は人間が確認し、実装は実行可能なテストで検証する。

## 11. 本文中の角括弧

Bad:

```markdown
- [TECH-030:SPEC-01] [ACTOR:Parser] [WHEN] 入力が [x] 形式の場合 [MUST] [THEN] 配列として解釈する。
```

`[x]` が未知タグとして解釈され、`EAI-CORE-SYNTAX-004` となる。

Good:

```markdown
- [TECH-030:SPEC-01] [ACTOR:Parser] [WHEN] 入力が `[x]` 形式の場合 [MUST] [THEN] 配列として解釈する。
```

コードスパンで囲むか、`\[x\]` とエスケープする（[01_Core構文仕様.md](01_Core構文仕様.md) §3.3）。
