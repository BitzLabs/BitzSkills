# 関係・トレースモデル

## 1. 本書の範囲

本書は、ID解決（ID resolution）、型付きの関係（relation）、適用可能性、完全な閉包（closure）、共通の対象展開（TargetExpansion）、パス、カバレッジを定める。
操作ごとの起点（root）の入力、Gitの対象選択、プロセスの実行は各操作の仕様が所有する。

## 2. 最小トレース

```text
REQ/TECH statement
  ├── relations ----> 前提、refinement、後継
  ├── implements ---> 実装file
  ├── tests.covers -> test file
  └── command ------> bitz.yaml command

TASK
  ├── addresses ----> 対象statement / 規範文なしTECH
  ├── requires -----> 前提の文書/TASK
  └── changes ------> 許可変更path
```

別のトレース台帳を作らない。コードのシンボル、テストのアサーションの意味的な充足はCore 1.0の対象外とする。

## 3. 関係

| 関係型 | 意味 | 強さ |
|---|---|---|
| `requires` | 参照元（source）の解釈・実行の前提 | 強い |
| `refines` | 参照元が参照先（target）を具体化・制約する | 強い |
| `addresses` | TASKが対象規範文（target statements）または規範文のないTECHを実装する | 強い |
| `supersedes` | 参照元が同じ種別の旧文書を置き換える | 強い |
| `related` | 閲覧のための関連 | 弱い |

強い関係（strong relation）の参照切れ、型違反、禁止された循環（forbidden cycle）は`failed`とする。`related`は閉包を増やさず、参照切れは診断
`SPEC-RELATION-ADVISORY-MISSING-001`（重大度`warning`）とする。

## 4. 型制約

| 参照元 | 関係型 | 参照先 |
|---|---|---|
| REQ | `requires` | REQ、TECH、`accepted`のADR |
| REQ | `refines` | REQまたはREQの規範文 |
| REQ | `supersedes` | REQ |
| TECH | `requires` | REQ、TECH、`accepted`のADR |
| TECH | `refines` | REQ、TECHまたはその規範文 |
| TECH | `supersedes` | TECH |
| ADR | `requires` | REQ、TECH、`accepted`のADR |
| ADR | `supersedes` | ADR |
| TASK | `requires` | REQ、TECH、TASK、`accepted`のADR |
| TASK | `addresses` | REQまたはTECHの規範文、規範文のないTECH |
| 全種別 | `related` | 任意の文書 |

`requires`と`refines`を合わせた意味上の依存グラフの循環、`supersedes`の連鎖の循環、TASKどうしの`requires`の循環を禁止する。
`related`の循環は許可し、探索しない。

上の表の`accepted`のADRは状態を含む型制約（type constraint）であり、`requires`の参照先が`accepted`以外の状態のADRであれば
診断`CTX-RELATION-TYPE-001`とする。状態`draft`のREQなど、`accepted`以外の状態にある文書が、強い関係の参照先として
適用可能かどうかは、本節の型制約では扱わず、`context`の`CTX-STATE-*`（[状態と閉包](#10-状態と閉包)）で扱う。

## 5. ID解決と索引

Coreは、すべての仕様文書のフロントマターと本文の規範文（[EARS-AI言語・意味中間表現仕様 §5](../01_EARS-AI/01_EARS-AI言語・意味中間表現仕様.md#5-規範文の候補)の候補）から、
規範文IDを含む軽量な索引を1回で構築する。索引は次を持つ。

- 文書IDと規範文IDの正引きの索引
- 関係の正引き・逆引き
- `implements`のパスの逆引き
- `tests[].path`のパスの逆引き
- 規範文ごとのテスト対応

同じIDが複数のファイルに解決すれば`failed`とする。`reports/`、通常の`docs/`、Issue、URLをID解決の対象にしない。
単一ワークスペースでは従来のIDを索引のキーとする。複合ワークスペースでは、ワークスペースID（`workspace-id`）とローカルID（`document-id`または`statement-id`）の組を索引のキーとし、
機械可読な結果には`workspace-id::document-id`または`workspace-id::statement-id`の修飾ID（qualified ID）を使う。非修飾の参照先は参照元と同じワークスペースだけから解決し、ワークスペースをまたぐ参照先は
[複合ワークスペース仕様](05_複合ワークスペース仕様.md)の修飾IDを必須とする。

### 5.1 関係の診断の優先順位

1つの関係のエッジは次の順に検査し、最初に成立した主診断を1件だけ返す。

1. フロントマター、`relations`、値の構文または型の不正: 所有する構文・スキーマのコード
2. 修飾IDの字句の不正: `SPEC-MULTI-REF-001`
3. 参照元のワークスペースに不在で、別のワークスペースだけに同じローカルID（local ID）がある非修飾の参照先: `SPEC-MULTI-REF-001`
4. 修飾されたワークスペースがカタログに不在: `SPEC-MULTI-REF-001`
5. ワークスペースは存在するが強い関係の参照先が不在: `SPEC-RELATION-MISSING-001`
6. 参照先は存在するが参照元と参照先の型の組が不適合: `CTX-RELATION-TYPE-001`

非修飾の参照先がどのワークスペースにも存在しない場合は、ワークスペースをまたぐ意図を推測せず`SPEC-RELATION-MISSING-001`とする。
参照元のワークスペースに同じローカルIDがあれば、そのワークスペース内の参照先へ解決し、別のワークスペースの同名IDを候補にしない。構文または読取りの不正で
索引を構成できないファイルから、参照先の不在を派生させない。この規則は、構文または読取りの不正に限らず、継続単位`skip-document`の診断や
文書IDの重複で索引に入らないファイルすべてに適用する。そのファイルが宣言する関係は評価せず、そのファイルを参照元とする関係の診断を返さない。
ほかの文書がそのファイルの文書IDを参照する場合は、索引に参照先がないので、上の順位どおり（強い関係なら`SPEC-RELATION-MISSING-001`）とする。
そのファイル自身の診断（構文の不正、文書IDの重複など）をどの操作とスコープで返すかは、この規則によらず、各操作の仕様に従う。
ただし文書IDの重複（`SPEC-ID-DUPLICATE-001`）は、`context`と`verify`では、閉包を作るときに辿るID（起点、`requires`、`refines`、`addresses`の参照先、
置換の参照先（`supersedes`の参照先の旧文書と、起点を置換する後継）、逆参照で閉包に入る文書のID。`related`の参照先は含めない）が重複していれば、
その結果（`verify`は当該の検証対象）へ返す。`supersedes`の参照先の旧文書は、閉包の文書が置き換える旧文書であり、起点を置換する後継が閉包に入る目的`interpret`だけ、
その後継が置き換える旧文書も含む（`implement`と`verify`では、後継は閉包に入らないので含まない）。起点のIDが重複している場合は、`CTX-ROOT-MISSING-001`に併記する。`check`は、文書IDの一意性をカタログ全体の
検査として扱い、スコープ（明示対象、引数なし、`--full`）によらず作業ワークスペースのすべての重複を返し、閉包で辿る他のワークスペースの重複も返す。この優先順位は診断の生成規則であり、結果の中での
表示順は共通の結果契約に従う。

## 6. 目的ごとの閉包

閉包（closure）は、起点から、目的ごとの規則（§6.1〜§6.3）で関係を辿って得る文書の集合であり、対象展開の`contextDocuments`
（§6.4）と同じである。深さで打ち切らない（完全な閉包）。型、状態、循環、上限を満たさない場合は、閉包の全体を非成功とする（§3、§4、§10、`context` §8）。
文書の集合であり、規範文は対象規範文として別に扱う（§6.4）。`check`の引数なしの完全検査に使う「強い関係の閉包」（`check` §3）、
診断レジストリの閉包、P0/P1閉包は、本書の閉包とは別の語である。

### 6.1 `interpret`

閉包は、下方向の出発点から下方向へ具体化を辿り、そこから上方向へ依存を辿って得る（[ADR-071](../../02.設計書/10_決定記録/ADR-071_パスと所有の境界をGitに倣い強い関係の閉包を辺の向きごとの到達可能性で定める.md)）。

- **上方向**: 文書から、`requires`、`refines`、`addresses`の参照先（規範文が参照先なら、その所有文書）を、エッジの種類を区別せず終端まで辿る。
  `supersedes`と`related`は辿らない。
- **下方向**: 文書またはそのいずれかの規範文を`refines`する適用可能な文書を、逆向きに終端まで辿る。下方向で得た文書を、閉包の具体化文書とする。
  対象規範文を持つ具体化文書の範囲（§6.4の規則1〜3）は、規範文を起点にしたときにこれより狭い。
- **下方向の出発点**: 起点がREQ、TECH、ADRなら起点文書、規範文なら所有文書、TASKならそのTASKの`addresses`の参照先の所有文書とする。

1. 起点文書を含める。
2. 下方向の出発点と、そこから下方向で得た具体化文書を含める。この集合をSとする。上方向で着いた文書からは、下方向へ辿らない。
3. Sの上方向の閉包を含める。上方向のエッジがSの文書へ戻る場合は、その文書へ着いたとはみなさず、役割と到達したエッジの記録を変えない。
4. 起点がTASKなら、起点のTASKの`requires`の参照先と、その上方向の閉包を含める（`verify`を除く。§6.3）。
5. 置換済みの起点は、旧文書を役割（role）`advisory`、後継を役割`replacement`として示す。
6. Sの文書またはその規範文を`refines`する状態`draft`の文書は、役割`advisory`として含める。`advisory`の文書は規範として
   適用せず、その文書からは上方向にも下方向にも辿らない。ただし、3.または4.の上方向でも着く文書は`advisory`にせず、上方向で着いた文書として扱う
   （強い関係を優先する。適用可能性は§10の状態の検査で扱う）。
7. `related`、コード、テストを自動で追加しない。TASKは、起点のTASK、4.で着くTASK、§6.2の対象規範文を`addresses`するTASKだけを含める。

`implement`と`verify`は、`refines`する状態`draft`の文書を閉包へ含めない。

### 6.2 `implement`

`interpret`に加えて次を含める。

- 対象規範文（§6.4の`targetStatements`。起点と、§6.4の規則で得る具体化文書（applicable refinement）の規範文）
- 起点がTASKでなければ、対象規範文を`addresses`する状態`open`のTASK（役割`work`）。そのTASKからは辿らない。
  起点がTASKなら、ほかのTASKを対象規範文の`addresses`によって加えない（起点のTASKの`requires`で着くTASKは§6.1の4.による）。
- `implements`、テスト対応、TASKの`changes`
- 規範文ごとの対応済み（addressed）／テスト済み（tested）の状況

起点のTASKの`requires`の参照先のTASKがすべて状態`done`でなければ`blocked`とする。
検査する先行TASKは、起点のTASKの`requires`が直接指すTASKだけである。`requires`の閉包で推移的に到達したTASKの状態は検査せず、
先行TASKの未完了と`cancelled`は診断`CTX-TASK-DEPENDENCY-001`だけで示す（ADR-029、ADR-036）。

### 6.3 `verify`

`interpret`に加えて、対象規範文のテスト対応、コマンド、実装のパスを含める。TASKは起点に指定したときだけ含める。
状態`done`のTASKは再検証でき、状態`cancelled`のTASKは`blocked`とする。

起点がTASKの場合は、§6.1のとおり、その`addresses`の参照先の所有文書を下方向の出発点として閉包を作る。
`implement`と異なり、§6.1の4.（起点のTASKの`requires`の参照先と、その上方向の閉包）は`contextDocuments`へ含めない。
ただし、起点のTASKの`requires`の参照先のTASKがすべて状態`done`でなければ、`implement`と同じく`blocked`とする（ADR-029）。
§6.1の4.で着く文書のうち`contextDocuments`にないもの（TASKとADRを除く）も、コンテキストへ含めないが、通常の適用可能性の検査を行う（ADR-034）。
状態が`accepted`でないADRへの強い関係は、§4の型制約で扱う。コンテキストへ含めない閉包の文書については、
閉包を構成する`requires`の型制約だけを検査し、`refines`と`addresses`のエッジの型制約を含め、それ以外の関係は検査しない（ADR-071の後続で決めた細部。ユーザーの決定）。複合ワークスペースの他のワークスペースの文書については、閉包を構成する`requires`の型制約と、
閉包の文書が宣言する強い関係の循環（§4。ワークスペースをまたぐ循環を含む）を検査し、それ以外の関係（参照先の不在など）は検査しない。循環は§6と§7のとおり隠さず、
`check`の完全検査（`check` §6）と同じく、閉包に入ったどのワークスペースの文書が宣言する辺でも報告する。
起点のTASKの`addresses`の参照先を解決できない場合は、対象を空にせず、当該の検証対象を非成功とする。

### 6.4 `TargetExpansion(root, purpose)`

起点から対象を展開する唯一の契約を`TargetExpansion(root, purpose)`とする。`context`、明示対象の`check`、`verify`は
独自の展開の規則を持たず、この関数を使用する。入力の`root`は索引で解決済みの文書IDまたは規範文ID、`purpose`は
`interpret`、`implement`、`verify`のいずれかである。出力は次の4つの集合で、すべて正規ID（canonical ID）の重複のない配列とする。

| 集合 | 内容 | 順序 |
|---|---|---|
| `rootDocuments` | 文書を起点にした場合はその文書自身、規範文を起点にした場合はその所有文書 | IDの辞書順 |
| `contextDocuments` | 目的（purpose）ごとの閉包に含まれるすべての解釈材料。`rootDocuments`を含む | §7の文書順 |
| `targetStatements` | 目的が`implement`または`verify`のときに義務の対象となる規範文。`interpret`では空配列 | `contextDocuments`の順、行番号、IDの順 |
| `adjacentStatements` | 規範文起点と同じ文書にあるほかの規範文のうち、対象規範文でないもの | 行番号、IDの順 |

`targetStatements`は次の規則で構成する。

1. 起点がREQ、または規範文のあるTECHの文書である場合は、その所有するすべての規範文と、それらの具体化文書が持つ規範文を含める。
   起点の文書を文書IDで`refines`する適用可能な文書も具体化文書であり、その規範文を含める（規範文IDで`refines`する文書に限らない）。
2. 規範文を起点にした場合は、指定した規範文と、その具体化文書が持つ規範文を含める。所有文書のほかの規範文は
   `adjacentStatements`へ置く。
3. TASKを起点にした場合は、そのTASKが`addresses`する規範文と、その具体化文書を含める。規範文のないTECHを
   `addresses`する場合は規範文を追加せず、文書単位のテスト対応を保持する。
4. `requires`の参照先は`contextDocuments`にだけ含め、その所有する規範文を自動的に`targetStatements`へ昇格しない。
   `requires`の参照先がTASKであっても、そのTASKの`addresses`の参照先を現在の起点の義務へ追加しない。
   `verify`の起点のTASKは、§6.3により`requires`の参照先を`contextDocuments`へも含めない。
5. 規範文のないTECHを起点にした場合は`targetStatements`を空とし、文書単位のテスト対応を保持する。

具体化文書は、選択済みの文書または規範文を`refines`する適用可能な文書を逆参照し、推移的な
具体化を終端まで辿って得る。見つけた具体化文書は選択済みの文書とし、その規範文を規範文IDで`refines`する文書と、
その文書を文書IDで`refines`する文書の両方を辿る（どの起点でも同じ）。起点の文書自身を文書IDで`refines`する文書を含めるのは規則1の場合だけで、
規則2の起点の所有文書、規則3で`addresses`する規範文のないTECH、規則5の起点は、文書IDの`refines`を辿る起点にしない。各段階で正規IDにより重複を排除してから、規定の順序へ並べ替える。複数の起点を扱う操作は、
起点を正規ID化して重複を排除した後に各結果の和集合を取り、同じ順序の規則を再適用する。`adjacentStatements`は、各結果の`adjacentStatements`の和集合から、
いずれかの起点の`targetStatements`に含まれる規範文を除いたものとする。`verify`のテスト割当ては
`targetStatements`が確定した後に`(workspaceId, commandName)`で重複を排除し、各検証対象からの参照は失わない。

ADRは目的`interpret`だけで起点にでき、`targetStatements`は空とする。`context`の`implement`または`verify`の起点と
`verify` CLIの起点にはできない。`check`はADRを文書の検査対象にできるが、テストの義務へ展開しない。

## 7. 決定論的探索

1. すべてのIDと関係の軽量な索引（lightweight index）を作る。
2. 型、状態、強い関係、循環を検査する。
3. 起点をIDの辞書順に正規化する。
4. 目的ごとの規則で完全な閉包を計算する。
5. 文書を役割`root`、`requirement`、`constraint`、`refinement`、`replacement`、`work`、`advisory`へ分類する。
6. 最短距離、種別の順REQ／TECH／ADR／TASK、IDの辞書順で並べる。距離は、起点を所有する文書を0とし、閉包を作るときに
   辿ったエッジ1本を1段とした、起点からの最短の段数である。置換済みの起点の後継は、起点から`supersedes`のエッジを1本辿った距離1とする。
   起点がTASKなら、その`addresses`の参照先の所有文書は、起点から`addresses`のエッジを1本辿った距離1とする。
   §6.1の3.のSの文書へ戻る上方向のエッジは、距離の計算に使わない。
   目的`implement`で対象規範文を`addresses`するTASKは、その規範文を所有する文書から`addresses`のエッジを1本辿った段数とする
   （具体化文書の規範文だけを`addresses`するTASKは、その具体化文書の距離に1を足す）。
   起点が複数のときは起点ごとの距離の最小値とする。距離はコンテキストの
   ハッシュ値の材料に含めない。並び順と提示形式の判定（`context` §5）に使い、提示形式を通じてバイト数の上限の判定（`context` §8）に影響する。
7. 規範文を文書順、行番号、IDの順で並べる。

同一の文書が複数の経路から到達しても1回だけ収録し、到達したエッジを保持する。到達済みの集合で循環を隠さない。

役割は次の規則で決める。複数に該当する文書は、次の表の上から最初に該当する役割とする。

| 役割 | 該当する文書 |
|---|---|
| `root` | 起点を所有する文書。ただし、§6.1の5.の置換済みの起点は`advisory` |
| `advisory` | §6.1の5.の置換済みの起点、§6.1の6.の、`refines`する状態`draft`の文書 |
| `replacement` | 置換済みの起点の後継 |
| `work` | 起点以外のTASK |
| `refinement` | 具体化の関係で到達した文書（具体化文書と、上方向に`refines`のエッジで着いた文書） |
| `requirement` | `requires`または`addresses`のエッジで着いたREQ |
| `constraint` | `requires`または`addresses`のエッジで着いたTECH、`accepted`のADR |

§6.1の3.のとおり、Sの文書へ戻る上方向のエッジは、役割の判定に使わない。

## 8. カバレッジ

カバレッジの対象規範文の集合は、§6.4の`TargetExpansion(root, purpose).targetStatements`だけから得る。
`requires`の閉包をテストの義務へ含めるなど、操作固有の追加の展開をしてはならない。

| 規範強度 | `implement` | `verify` |
|---|---|---|
| `MUST` | 未対応・未テストを重大度`warning` | 未テストが1件あれば`blocked` |
| `SHOULD` | 未対応を重大度`warning` | 未テストを重大度`warning` |
| `MAY` | 情報 | 情報 |

カバレッジは`must`、`should`、`may`ごとに`total`、`addressed`、`tested`、`unaddressed`、`untested`を持つ。
テスト対応は対象の宣言であり、アサーションの十分性を保証しない。

対応済みは、対象規範文のうち、閉包（`contextDocuments`）に含まれるTASKのどれかが`relations.addresses`でその規範文IDを直接
参照しているものである。閉包に含まれるTASKは目的ごとの規則（§6）で決まる。目的`implement`で起点がREQ、TECH、規範文のときは
対象規範文を`addresses`する状態`open`のTASK、起点がTASKのときは起点のTASKと`requires`で含めたTASK、目的`verify`では、起点がTASKのときはそのTASKだけで、それ以外の起点ではTASKを含まない。
このため、目的`implement`で起点がREQ、TECH、規範文のときは、状態`done`のTASKだけが扱った規範文は未対応になる。
テスト済みは、対象規範文のうち、閉包に含まれる文書の`tests[].covers`のどれかがその規範文IDを含むものである。宣言があればよく、
テストのパスの存在とコマンドは問わない。対応済みとテスト済みは独立に判定し、`covers`は対応済みの判定に使わない。

## 9. パス

`implements`と`tests[].path`は、通常のファイルとして存在することを検査する。存在の検査は、
[安全な入出力・互換性 §6](../00_共通契約/02_安全な入出力・互換性.md#6-正規パス)の手順（基準のルートから各セグメントを、親のディレクトリの項目名とNFCで完全一致させる。
シンボリックリンクを辿らず、途中または末端のリンク、別の綴りは存在しない）で行う。状態`draft`の未作成の予定は重大度`warning`、状態`approved`は
重大度`error`とする。状態`rejected`の文書のパスは履歴であり、存在を要求しない。
同じディレクトリにNFCで同じ名前になる項目が複数あるパスは、存在しない扱いにせず拒否し、診断`SPEC-PATH-INVALID-001`の専用の文言で示す。重大度は不在と同じく、状態`draft`は`warning`、状態`approved`は`error`とする。

`changes`はファイルのパスと、末尾が`/`のディレクトリの接頭辞を許可し、対象自体の存在を要求せず、存在の検査を行わない。すべてワークスペース内に限る。
複合ワークスペースでは、別の所有領域もワークスペース外として扱う。別のワークスペースの規範文を`tests[].covers`へ指定できるのは、
宣言する文書が、その規範文またはそれを所有する文書を直接`refines`する場合に限る。

## 10. 状態と閉包

適用可能でない文書を強い関係が要求する場合、閉包全体を`blocked`とする。`advisory`の文書は別の区分で提示し、
規範として適用しない。Coreは後継へ暗黙に起点を差し替えない。同じ旧文書に複数の有効な後継があれば`failed`とする。
