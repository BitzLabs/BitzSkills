# 関係・トレースモデル

## 1. 本書の範囲

本書は、ID解決（ID resolution）、型付きの関係（relation）、適用可能性、完全な閉包（closure）、共通の対象展開（TargetExpansion）、パス、カバレッジを定める。
操作ごとの起点（root）の入力、Gitの対象選択、プロセスの実行は各操作の仕様が所有する。

## 2. 最小トレース

```text
REQ/TECH statement
  ├── relations ----> 前提、refinement、後継
  ├── implements ---> 実装file
  ├── tests.covers -> test file
  └── command ------> bitz.yaml command

TASK
  ├── addresses ----> 対象statement / 規範文なしTECH
  ├── requires -----> 前提SPEC/TASK
  └── changes ------> 許可変更path
```

別のトレース台帳を作らない。コードのシンボル、テストのアサーションの意味的な充足はCore 1.0の対象外とする。

## 3. 関係

| 関係型 | 意味 | 強さ |
|---|---|---|
| `requires` | 参照元（source）の解釈・実行の前提 | 強い |
| `refines` | 参照元が参照先（target）を具体化・制約する | 強い |
| `addresses` | TASKが対象規範文（target statements）または規範文のないTECHを実装する | 強い |
| `supersedes` | 参照元が同じ種別の旧文書を置き換える | 強い |
| `related` | 閲覧のための関連 | 弱い |

強い関係（strong relation）の参照切れ、型違反、禁止された循環（forbidden cycle）は`failed`とする。`related`は閉包を増やさず、参照切れは診断
`SPEC-RELATION-ADVISORY-MISSING-001`（重大度`warning`）とする。

## 4. 型制約

| 参照元 | 関係型 | 参照先 |
|---|---|---|
| REQ | `requires` | REQ、TECH、`accepted`のADR |
| REQ | `refines` | REQまたはREQの規範文 |
| REQ | `supersedes` | REQ |
| TECH | `requires` | REQ、TECH、`accepted`のADR |
| TECH | `refines` | REQ、TECHまたはその規範文 |
| TECH | `supersedes` | TECH |
| ADR | `requires` | REQ、TECH、`accepted`のADR |
| ADR | `supersedes` | ADR |
| TASK | `requires` | REQ、TECH、TASK、`accepted`のADR |
| TASK | `addresses` | REQまたはTECHの規範文、規範文のないTECH |
| 全種別 | `related` | 任意の文書 |

`requires`と`refines`を合わせた意味上の依存グラフの循環、`supersedes`の連鎖の循環、TASKどうしの`requires`の循環を禁止する。
`related`の循環は許可し、探索しない。

上の表の`accepted`のADRは状態を含む型制約（type constraint）であり、`requires`の参照先が`accepted`以外の状態のADRであれば
診断`CTX-RELATION-TYPE-001`とする。状態`draft`のREQなど、`accepted`以外の状態にある文書が、強い関係の参照先として
適用可能かどうかは、本節の型制約では扱わず、`context`の`CTX-STATE-*`（[状態と閉包](#10-状態と閉包)）で扱う。

## 5. ID解決と索引

Coreは、すべての仕様文書の軽量なフロントマターを1回走査し、次を構築する。

- 文書IDと規範文IDの正引きの索引
- 関係の正引き・逆引き
- `implements`のパスの逆引き
- `tests[].path`のパスの逆引き
- 規範文ごとのテスト対応

同じIDが複数のファイルに解決すれば`failed`とする。`reports/`、通常の`docs/`、Issue、URLをID解決の対象にしない。
単一ワークスペースでは従来のIDを索引のキーとする。複合ワークスペースでは`(workspaceId, localId)`を索引のキーとし、機械可読な結果には
`workspaceId::localId`の修飾ID（qualified ID）を使う。非修飾の参照先は参照元と同じワークスペースだけから解決し、ワークスペースをまたぐ参照先は
[複合ワークスペース仕様](05_複合ワークスペース仕様.md)の修飾IDを必須とする。

### 5.1 関係の診断の優先順位

1つの関係のエッジは次の順に検査し、最初に成立した主診断を1件だけ返す。

1. フロントマター、`relations`、値の構文または型の不正: 所有する構文・スキーマのコード
2. 修飾IDの字句の不正: `SPEC-MULTI-REF-001`
3. 参照元のワークスペースに不在で、別のワークスペースだけに同じローカルID（local ID）がある非修飾の参照先: `SPEC-MULTI-REF-001`
4. 修飾されたワークスペースがカタログに不在: `SPEC-MULTI-REF-001`
5. ワークスペースは存在するが強い関係の参照先が不在: `SPEC-RELATION-MISSING-001`
6. 参照先は存在するが参照元と参照先の型の組が不適合: `CTX-RELATION-TYPE-001`

非修飾の参照先がどのワークスペースにも存在しない場合は、ワークスペースをまたぐ意図を推測せず`SPEC-RELATION-MISSING-001`とする。
参照元のワークスペースに同じローカルIDがあれば、そのワークスペース内の参照先へ解決し、別のワークスペースの同名IDを候補にしない。構文または読取りの不正で
索引を構成できないファイルから、参照先の不在を派生させない。この優先順位は診断の生成規則であり、結果の中での
表示順は共通の結果契約に従う。

## 6. 目的ごとの閉包

### 6.1 `interpret`

1. 起点を所有する文書を含める。
2. `requires`を終端まで辿る。
3. `refines`の参照先を含める。
4. 対象を`refines`する適用可能な文書を逆参照で含め、その`requires`を辿る。
5. 置換済みの起点は、旧文書を役割（role）`advisory`、後継を役割`replacement`として示す。
6. 閉包内の適用可能な文書またはその規範文を`refines`する状態`draft`の文書は、役割`advisory`として含める。`advisory`の文書は規範として
   適用せず、その`requires`と、それを`refines`する文書を辿らない。
7. `related`、TASK、コード、テストを自動で追加しない。

`implement`と`verify`は、`refines`する状態`draft`の文書を閉包へ含めない。

### 6.2 `implement`

`interpret`に加えて次を含める。

- 起点と具体化文書（applicable refinement）の対象規範文
- 対象規範文を`addresses`する状態`open`のTASK
- 起点のTASKの`addresses`と`requires`の閉包
- `implements`、テスト対応、TASKの`changes`
- 規範文ごとの対応済み（addressed）／テスト済み（tested）の状況

起点のTASKの`requires`の参照先のTASKがすべて状態`done`でなければ`blocked`とする。

### 6.3 `verify`

`interpret`に加えて、対象規範文のテスト対応、コマンド、実装のパスを含める。TASKは起点に指定したときだけ含める。
状態`done`のTASKは再検証でき、状態`cancelled`のTASKは`blocked`とする。

起点がTASKの場合は、その`addresses`の参照先と、その参照先を所有する文書を`contextDocuments`へ含め、それらから
`interpret`の閉包の規則を適用する。`implement`と異なり、起点のTASKの`requires`の閉包は含めない。
起点のTASKの`addresses`の参照先を解決できない場合は、対象を空にせず、当該の検証対象を非成功とする。

### 6.4 `TargetExpansion(root, purpose)`

起点から対象を展開する唯一の契約を`TargetExpansion(root, purpose)`とする。`context`、明示対象の`check`、`verify`は
独自の展開の規則を持たず、この関数を使用する。入力の`root`は索引で解決済みの文書IDまたは規範文ID、`purpose`は
`interpret`、`implement`、`verify`のいずれかである。出力は次の4つの集合で、すべて正規ID（canonical ID）の重複のない配列とする。

| 集合 | 内容 | 順序 |
|---|---|---|
| `rootDocuments` | 文書を起点にした場合はその文書自身、規範文を起点にした場合はその所有文書 | IDの辞書順 |
| `contextDocuments` | 目的（purpose）ごとの閉包に含まれるすべての解釈材料。`rootDocuments`を含む | §7の文書順 |
| `targetStatements` | 目的が`implement`または`verify`のときに義務の対象となる規範文。`interpret`では空配列 | `contextDocuments`の順、行番号、IDの順 |
| `adjacentStatements` | 規範文起点と同じ文書にあるほかの規範文のうち、対象規範文でないもの | 行番号、IDの順 |

`targetStatements`は次の規則で構成する。

1. 起点がREQ、または規範文のあるTECHの文書である場合は、その所有するすべての規範文と、それらの具体化文書が持つ規範文を含める。
2. 規範文を起点にした場合は、指定した規範文と、その具体化文書が持つ規範文を含める。所有文書のほかの規範文は
   `adjacentStatements`へ置く。
3. TASKを起点にした場合は、そのTASKが`addresses`する規範文と、その具体化文書を含める。規範文のないTECHを
   `addresses`する場合は規範文を追加せず、文書単位のテスト割当てを保持する。
4. `requires`の参照先は`contextDocuments`にだけ含め、その所有する規範文を自動的に`targetStatements`へ昇格しない。
   `requires`の参照先がTASKであっても、そのTASKの`addresses`の参照先を現在の起点の義務へ追加しない。
   `verify`の起点のTASKは、§6.3により`requires`の参照先を`contextDocuments`へも含めない。
5. 規範文のないTECHを起点にした場合は`targetStatements`を空とし、文書単位のテスト割当てを保持する。

具体化文書は、選択済みの文書または規範文を`refines`する適用可能な文書を逆参照し、推移的な
具体化を終端まで辿って得る。各段階で正規IDにより重複を排除してから、規定の順序へ並べ替える。複数の起点を扱う操作は、
起点を正規ID化して重複を排除した後に各結果の和集合を取り、同じ順序の規則を再適用する。`verify`のテスト割当ては
`targetStatements`が確定した後に`(workspaceId, commandName)`で重複を排除し、各検証対象からの参照は失わない。

ADRは目的`interpret`だけで起点にでき、`targetStatements`は空とする。`context`の`implement`または`verify`の起点と
`verify` CLIの起点にはできない。`check`はADRを文書の検査対象にできるが、テストの義務へ展開しない。

## 7. 決定論的探索

1. すべてのIDと関係の軽量な索引（lightweight index）を作る。
2. 型、状態、強い関係、循環を検査する。
3. 起点をIDの辞書順に正規化する。
4. 目的ごとの規則で完全な閉包を計算する。
5. 文書を役割`root`、`requirement`、`constraint`、`refinement`、`replacement`、`work`、`advisory`へ分類する。
6. 最短距離、種別の順REQ／TECH／ADR／TASK、IDの辞書順で並べる。
7. 規範文を文書順、行番号、IDの順で並べる。

同一の文書が複数の経路から到達しても1回だけ収録し、到達したエッジを保持する。到達済みの集合で循環を隠さない。

役割は次の規則で決める。複数に該当する文書は、次の表の上から最初に該当する役割とする。

| 役割 | 該当する文書 |
|---|---|
| `root` | 起点を所有する文書。ただし、§6.1の5.の置換済みの起点は`advisory` |
| `advisory` | §6.1の5.の置換済みの起点、§6.1の6.の、`refines`する状態`draft`の文書 |
| `replacement` | 置換済みの起点の後継 |
| `work` | 起点以外のTASK |
| `refinement` | 具体化文書として到達した文書 |
| `requirement` | `requires`または`addresses`で到達したREQ |
| `constraint` | `requires`または`addresses`で到達したTECH、`accepted`のADR |

## 8. カバレッジ

カバレッジの対象規範文の集合は、§6.4の`TargetExpansion(root, purpose).targetStatements`だけから得る。
`requires`の閉包をテストの義務へ含めるなど、操作固有の追加の展開をしてはならない。

| 規範強度 | `implement` | `verify` |
|---|---|---|
| `MUST` | 未対応・未テストを重大度`warning` | 未テストが1件あれば`blocked` |
| `SHOULD` | 未対応を重大度`warning` | 未テストを重大度`warning` |
| `MAY` | 情報 | 情報 |

カバレッジは`must`、`should`、`may`ごとに`total`、`addressed`、`tested`、`unaddressed`、`untested`を持つ。
テスト対応は対象の宣言であり、アサーションの十分性を保証しない。

## 9. パス

`implements`と`tests[].path`は、通常のファイルとして存在することを検査する。状態`draft`の未作成の予定は重大度`warning`、状態`approved`は
重大度`error`とする。状態`rejected`の文書のパスは履歴であり、存在を要求しない。

`changes`はファイルのパスと、末尾が`/`のディレクトリの接頭辞を許可し、対象自体の存在を要求しない。すべてワークスペース内に限る。
複合ワークスペースでは、別の所有領域もワークスペース外として扱う。別のワークスペースの規範文を`tests[].covers`へ指定できるのは、
宣言する文書が、その規範文またはそれを所有する文書を直接`refines`する場合に限る。

## 10. 状態と閉包

適用可能でない文書を強い関係が要求する場合、閉包全体を`blocked`とする。`advisory`の文書は別の区分で提示し、
規範として適用しない。Coreは後継へ暗黙に起点を差し替えない。同じ旧文書に複数の有効な後継があれば`failed`とする。

## 11. 診断

本表は検索用の索引である。条件ごとの規範の値と主診断の優先順位は
[診断レジストリ](../00_共通契約/05_診断レジストリ.md)が所有する。

| 診断コード | 結果への効果 | 条件 |
|---|---|---|
| `SPEC-ID-DUPLICATE-001` | `failed` | 文書IDの重複。規範文IDの重複は`EAI-CORE-ID-002` |
| `SPEC-RELATION-LEGACY-001` | `failed` | 旧`refs`の使用 |
| `SPEC-RELATION-MISSING-001` | `failed` | 強い関係の参照先が不在 |
| `SPEC-RELATION-ADVISORY-MISSING-001` | `passed_with_warnings` | `related`の参照先が不在 |
| `CTX-RELATION-TYPE-001` | `failed` | 参照元と参照先の型の組が不正 |
| `CTX-CYCLE-001` | `failed` | 禁止された循環 |
| `CTX-TASK-DEPENDENCY-001` | `blocked` | 起点のTASKの先行するTASKが未完了 |
| `CTX-STATE-001` | `blocked` | 起点または強い関係の参照先が目的に適用不能 |
| `CTX-STATE-SUPERSEDED-001` | `blocked` | 起点または依存の参照先が置換済み |
| `CTX-STATE-SUPERSEDED-002` | `failed` | 有効な後継が複数 |
| `CTX-COVERAGE-TASK-001` | `passed_with_warnings` | 目的`implement`の対象の`MUST`が未対応 |
| `CTX-COVERAGE-TEST-001` | 警告／`blocked` | 目的`implement`では警告、`verify`では`blocked` |

`CTX-RELATION-MISSING-001`はCore 1.0の公開結果では使用せず、予約する。強い関係の参照先の不在は
`SPEC-RELATION-MISSING-001`へ統一する。
