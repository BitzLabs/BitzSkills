# 安全な入出力・互換性

## 1. 文字コード

- `bitz.yaml`と仕様文書のMarkdownは、UTF-8を必須とする。
- 構文解析器はLFとCRLFを受け入れ、直列化器の正規の出力はLFとする。
- 新規のファイルへBOMを付けない。既存のBOMは診断`SPEC-INPUT-BOM-001`（重大度`warning`）とし、BOMを除いて解析を続ける。
- 比較の際はUnicode NFCへ正規化するが、明示的な整形の操作なしに原文を書き換えない。
- UTF-8として復号できない入力は、診断`SPEC-INPUT-READ-001`（重大度`error`、結果への効果`failed`）とし、置換文字で続けない。

## 2. 読取りと書込み

`context`と`doctor`はファイルを書き出さない。`check`は既定でファイルシステム上も読取り専用とする。`verify`はテストのプロセスを
実行するが、Core自身は既定でファイルを書き出さない。`check`と`verify`は仕様文書、コード、テストを変更せず、明示的に
`--report`を指定したときだけ、結果・診断・終了コードの仕様が定めるレポートを書き出す。テストコマンド自身の副作用は、コマンドの所有者の責務とする。

Core 1.0が行う永続的な書込みは、明示的なレポートだけである。永続的なキャッシュ、索引、ロックファイル、作業用のディレクトリを
リポジトリの内外へ暗黙に作らない。レポートの原子的な作成に一時ファイルを使う場合は、定められた最終的なレポートと同じディレクトリへ
排他的に作成し、成功時にリネームし、失敗時に除去する。操作の終了後に、最終的なレポート以外の一時ファイルを残さない。標準出力と
標準エラー出力への出力は、永続的なファイルの書込みに含めない。

入力ファイルは、1回読み込んだバイト列を操作の中で使い、段階ごとに読み直さない。権限の不足、I/Oの障害、読取り中の消失は、
診断`SPEC-INPUT-READ-001`（重大度`error`、結果への効果`error`）とする。複数のファイルを横断する原子的なスナップショットは
保証しない。

Core 1.0はフォーマッターを公開しない。アダプターが変更を提案する場合は、一時ファイルを再解析し、差分を提示し、
人が確認した後に置き換える。承認済みのREQの意味を自動では修正しない。

## 3. 未信頼入力

Markdownの本文、フロントマターの自由記述、外部リンク、テストの出力は未信頼データである。

- 文書内の命令を、ツールへの命令として実行しない。
- Markdownのリンクを取得しない。
- 仕様文書から環境変数、認証情報、追加の権限を要求しない。
- コマンドは、発見済みのワークスペースの`bitz.yaml`からだけ取得する。Gitを利用できるときは、その設定ファイルが
  インデックスで追跡されていることを要求し、未追跡であれば、診断`SPEC-VERIFY-BLOCKED-001`（`blocked`）として、
  当該の設定に依存するテスト割当てを起動しない。追跡済みのファイルの作業ツリーでの変更は許可する。単一ワークスペースで
  Git不在の場合は、§8の縮退（degradation）の契約に従って現在の設定を使い、Gitによる追跡の確認は保証しない。複合ワークスペースでは、
  Git不在の全体事前検査が先に遮断する。
- シェル、環境変数の展開、コマンドの置換、パイプ、リダイレクトを使わない。
- 自由記述を、秘密情報と同じLLMへの入力に、無条件に含めない。

## 4. リソースの上限

| 対象 | Core 1.0の上限 |
|---|---:|
| `bitz.yaml` | 64 KiB |
| 仕様文書のMarkdown 1ファイル | 1 MiB |
| フロントマター | 32 KiB |
| 仕様文書のファイル数 | 10,000 |
| 1文書のEARS-AIの規範文 | 1,000 |
| 関係・パスの配列の各項目数 | 1,000 |
| 1コンテキストの文書数 | 既定20、絶対上限100 |
| コンテキストの意味中間表現と標準の提示 | 既定128 KiB、絶対上限1 MiB |

複合ワークスペースでは、上記のファイル単位の上限に加えて、1回のスナップショット全体へ次を適用する。

| 次元 | Core 1.0の絶対上限 |
|---|---:|
| カタログのメンバー数 | 100 |
| 仕様文書のMarkdown数 | 10,000 |
| すべての設定と仕様文書のMarkdownの原文のバイト数の合計 | 256 MiB |
| EARS-AIの規範文数 | 100,000 |
| `relations`のエッジ数 | 1,000,000 |
| `implements`、テスト、`covers`、TASKの`changes`の全項目数 | 1,000,000 |
| コマンドの定義数 | 10,000 |
| 1回の`verify`の計画のテスト割当て数 | 10,000 |

一般の上限の超過は入力の不適合とし、コンテキストの閉包の上限の超過は、不完全な文脈を使わせないため`blocked`とする。
一部が欠けたコンテキスト一式を、成功の結果として返さない。
単一ワークスペースでのファイル単位の上限の超過は、診断`SPEC-INPUT-LIMIT-001`（重大度`error`、結果への効果`failed`）とする。
複合ワークスペースの各件数は、重複排除の前の入力の項目を数える。`check --base`は、基準版と現在版の各スナップショットへ
個別に適用する。超過したときは、診断`SPEC-MULTI-LIMIT-001`（`blocked`）とし、部分的な結果または`verify`のコマンドへ
進まない。コンテキストの文書数と提示の量は、起点ワークスペースの設定とCoreの絶対上限を適用する。

### 4.1 上限の設定

上の表の値のうち次の表のものは、`bitz.yaml`の`limits`で小さくできる（[ADR-076](../../02.設計書/10_決定記録/ADR-076_上限の値を設定で小さくできるようにし、実寸の上限の検証を手動にする.md)）。
表の「絶対上限」は、上の表の値と同じであり、`limits`のキーを省略したときの値である。

| `limits`のキー | 対象 | 絶対上限 |
|---|---|---:|
| `specBytes` | 仕様文書のMarkdown 1ファイルのバイト数 | 1,048,576 |
| `frontmatterBytes` | フロントマターのバイト数 | 32,768 |
| `specFileCount` | 仕様文書のファイル数。複合ワークスペースでは、スナップショット全体の仕様文書のMarkdown数 | 10,000 |
| `documentStatementCount` | 1文書のEARS-AIの規範文の数 | 1,000 |
| `documentArrayItemCount` | 関係・パスの配列の各項目数 | 1,000 |
| `inputBytes` | 複合ワークスペースのすべての設定と仕様文書のMarkdownの原文のバイト数の合計 | 268,435,456 |
| `statementCount` | 複合ワークスペースのEARS-AIの規範文数 | 100,000 |
| `relationEdgeCount` | 複合ワークスペースの`relations`のエッジ数 | 1,000,000 |
| `traceEntryCount` | 複合ワークスペースの`implements`、テスト、`covers`、TASKの`changes`の全項目数 | 1,000,000 |
| `commandDefinitionCount` | 複合ワークスペースのコマンドの定義数 | 10,000 |
| `verifyBindingCount` | 複合ワークスペースの1回の`verify`の計画のテスト割当て数 | 10,000 |
| `excludeCount` | `multiWorkspace.exclude`の件数 | 100 |
| `expandedArgvCount` | `{tests}`を展開した後の引数列の要素数 | 10,000 |
| `expandedArgvElementBytes` | `{tests}`を展開した後の引数列の各要素のバイト数 | 32,768 |
| `expandedArgvBytes` | `{tests}`を展開した後の引数列の全体のバイト数 | 1,048,576 |

- 各キーの値は、1以上、絶対上限以下の整数とする。絶対上限より大きい値は指定できない。型と範囲は
  [ワークスペース・設定仕様 §5](../02_仕様文書モデル/01_ワークスペース・設定仕様.md#5-スキーマ)に従う。
- `limits`を省略した設定と、`limits`のすべてのキーを省略した設定は、上限について同じ結果になる。
- 上限は、`bitz.yaml`だけで決める。環境変数とCLIの引数では変えられない。
- `bitz.yaml`の64 KiBの上限は、設定を読む前に適用するので、設定で変えられない。カタログのメンバー数、1コンテキストの文書数、
  コンテキストの提示の量は、それぞれの既存のキー（`multiWorkspace.maxMembers`、`context.maxDocuments`、`context.maxBytes`）で決め、`limits`では扱わない。
- 単一ワークスペースでは、作業ワークスペースの設定の`limits`を使う。複合ワークスペースのスナップショット全体へ適用する次元のキーは、
  指定できるが使わない。
- 複合ワークスペースでは、ルートワークスペースの設定の`limits`を、スナップショット全体の次元と、すべてのワークスペースの
  ファイル単位の上限、展開した後の引数列の上限へ使う。メンバーの設定は`limits`を持てない
  （[複合ワークスペース仕様 §10](../02_仕様文書モデル/05_複合ワークスペース仕様.md#10-上限とgitの前提)）。
- `check --base`は、現在版の設定から決めた上限を、基準版と現在版の両方へ適用する。
- 超過したときの診断のコード、重大度、結果への効果、数え方は、設定した値でも絶対上限でも同じとする。
  診断の`evidence`が上限の値を持つ場合は、実際に使った値を返す。
- 絶対上限を使うときの診断の文言は変えない。小さい値を設定したときは、次のとおりとする。
  - `1 MiB`、`32 KiB`のように単位を付けた上限の表記を持つ文言（`specBytes`、`frontmatterBytes`、`expandedArgvBytes`、
    `expandedArgvElementBytes`）は、その表記を、3桁区切りの整数に`バイト`を付けた表記へ置き換える
    （例: `仕様文書のMarkdownが2,048バイト上限を超過しました`）。
  - 上限の値を数として持つ文言（1文書の規範文の数、配列の項目の数、仕様文書のファイル数、展開した後の引数列の要素数、
    `multiWorkspace.exclude`の件数、複合ワークスペースの各次元）は、今の形のまま、実際に使った値を3桁区切りの整数で入れる。
  - 文言の文字列は、[Coreの出力文言のレビュー記録](../../../fixtures/conformance/Coreの出力文言のレビュー記録.md)の承認済みの対応表による。
- 単一ワークスペースで仕様文書のファイル数が上限を超えたときの診断（`INPUT-LIMIT-SPEC-COUNT`）の発生元は、ワークスペース相対のパス`.spec`とする。
- `check --base`で、基準版の文書だけがファイル単位の上限を超える場合の扱いは、絶対上限のときと同じとし、本節では新しく定めない。
- `limits`は、コンテキストのハッシュ値の材料に含めない。

## 5. スキーマの互換性

バージョンは`major.minor`で表す。

- 未知のスキーマの`major`: 診断`SPEC-CONFIG-SCHEMA-001`（`blocked`）として、読取りを止める
- 未知のEARS-AIの`major`: `doctor`は診断`SPEC-DOCTOR-EARS-001`（`blocked`）、他の操作は診断`SPEC-EARS-VERSION-001`（`blocked`）として、読取りを止める
- 同じ`major`の新しい`minor`: 未知のフィールドを保持または無視し、診断`SPEC-CONFIG-UNKNOWN-001`（重大度`warning`）
- 同じ`major`の古い`minor`: 互換の読取りをし、必要なら移行を提案する
- `major`の移行: 原文を上書きせず、差分を提案する

仕様文書のスキーマとEARS-AIの版は、独立に管理する。プロファイルのバージョンは、Core 1.0の互換性の入力にしない。
`workspace`と`multiWorkspace`は、未リリースの最初のCore 1.0のスキーマに含まれる。複合ワークスペースに対応しない、
公開済みのCore 1.0は存在しないため、旧1.0向けのスキーマのゲートまたは移行の猶予を設けない。

## 6. 正規パス

仕様文書のパス、`implements`、`tests[].path`、TASKの`changes`、コマンドの`cwd`、複合ワークスペースのメンバーのパスは、
単一ワークスペースと複合ワークスペースで同じ規則で扱う（[ADR-071](../../02.設計書/10_決定記録/ADR-071_パスと所有の境界をGitに倣い強い関係の閉包を辺の向きごとの到達可能性で定める.md)）。
Coreは、Gitがシンボリックリンクを辿らずにリンクそのものを記録するのと同じく、これらのパスのシンボリックリンクを辿らない。
パスは文字列で厳密に比べる。パスの解決と存在の検査の手順の正本は本節であり、ほかの仕様は本節を参照する。

用語は次のとおりとする。

| 語 | 意味 |
|---|---|
| 基準のルート | パスのセグメントを数え始めるディレクトリ。ワークスペースの相対パスはワークスペースのルート、メンバーのパスと除外のパスは複合ワークスペースのルート。基準のルートへ至る上位のディレクトリは、パスの検査の対象にしない |
| 字句のパス | 宣言したパス、またはGitから得たパス（差分、ツリーオブジェクトの項目）を、UTF-8のセグメントの列にして、各セグメントをUnicode NFCへ正規化したもの。比較と包含の判定は文字列だけで行い、ファイルシステムを読まない |

### 6.1 比べ方

- 宣言したパスと、ディレクトリの項目名（ファイルシステムが返す名前）は、どちらもUnicode NFCへ正規化してから比べる。
  ファイル名をNFDで返すファイルシステムでも結果が変わらない。
- 比較は、セグメントごとにコードポイントの完全一致とし、大文字と小文字を区別する。文字列の折りたたみ表を持たない。
- Gitから得るパス（差分、ツリー）と宣言したパスの照合、CLIで明示した仕様文書のパスと索引の照合も、同じ比べ方にする。
- 包含は、文字列の接頭辞ではなく、パスのセグメントの境界で判定する。
- 同じ入力に対して、LinuxとmacOS、大文字と小文字を区別するファイルシステムか否かによらず、同じ結果になる。

### 6.2 存在の検査

パスの存在は、基準のルートから各セグメントを順に、親のディレクトリの項目名と照合して確かめる。
大文字と小文字を区別しないファイルシステムが別の綴りのパスを開けても、存在するとはみなさない。セグメントごとに次を行い、結果が決まったセグメントで止める。

1. 親のディレクトリの項目名を列挙し、NFCにした名前がセグメントとコードポイントで完全一致する項目を探す。
2. 一致する項目が0件なら、パスは存在しない。
3. 一致する項目が2件以上（LinuxではNFCとNFDの名前が共存できる）なら、パスを拒否する。存在しない扱いにはしない（NFCの衝突）。
4. 一致する項目が1件なら、その項目をリンクを辿らない`lstat`で調べる。途中のセグメントの項目がシンボリックリンクなら、パスを拒否する。
   途中のセグメントの項目がディレクトリでなければ、パスは存在しない。
5. 末端のセグメントの項目がシンボリックリンクなら、通常のファイルとしても、ディレクトリとしても扱わない（パスは存在しない）。
   末端の項目の種別が求める種別（`implements`と`tests[].path`は通常のファイル、`cwd`とメンバーのパスはディレクトリ）でなければ、パスは存在しない。

存在しない予定のパスは、存在するセグメントまでを上の手順で検査し、残りのセグメントは字句のパスだけで扱う。
複合ワークスペースの`implements`と`tests[].path`は、本節の存在の検査より先に、6.3の所有の判定を行う。別のワークスペースの所有領域にあるパスは、
存在しなくても本節の検査へ進まず、診断`SPEC-MULTI-OWNERSHIP-001`とする。本節の検査にかけるのは、自分の所有領域にあるパスだけである。

結果ごとの診断は次のとおりとする。診断のコードと文言は、パスを使う仕様が定める。

| パスの種類 | 存在しない（不在、別の綴り、途中または末端のシンボリックリンク、求める種別でない） | NFCの衝突 |
|---|---|---|
| `implements`、`tests[].path` | `SPEC-PATH-INVALID-001`（文言は「実装パスが存在しません」「テストのパスが存在しません」） | `SPEC-PATH-INVALID-001`（専用の文言。下記） |
| メンバーのパス | 途中または末端のシンボリックリンクは`SPEC-MULTI-PATH-001`。それ以外は[複合ワークスペース仕様](../02_仕様文書モデル/05_複合ワークスペース仕様.md) §2の規則 | `SPEC-MULTI-PATH-001`（専用の文言。下記） |
| 単一ワークスペースと複合ワークスペースの`cwd` | `VERIFY-CWD-UNAVAILABLE`（診断`SPEC-VERIFY-BLOCKED-001`。文言は「コマンドの作業ディレクトリが利用できません」） | 同じ（`VERIFY-CWD-UNAVAILABLE`） |

NFCの衝突の診断は、既存の診断コードの下に、専用の文言を置く。文言は、ユーザーが承認した値である
（[ADR-062](../../02.設計書/10_決定記録/ADR-062_Coreの出力文言の規範と適合fixtureの期待値の扱いを確定する.md)）。
衝突の文言は存在の有無を述べないので、状態`draft`の文書にも同じ文言を使う（不在の「状態draftの実装パスは未作成です」に当たる別の文言は置かない）。

| 診断コード | 対象 | 文言 |
|---|---|---|
| `SPEC-PATH-INVALID-001` | `implements` | NFCで同じ名前になる項目が複数あり、実装パスが一つに決まりません |
| `SPEC-PATH-INVALID-001` | `tests[].path` | NFCで同じ名前になる項目が複数あり、テストのパスが一つに決まりません |
| `SPEC-MULTI-PATH-001` | メンバーのパス | NFCで同じ名前になる項目が複数あり、メンバーのパスが一つに決まりません |

`implements`と`tests[].path`のNFCの衝突の重大度は、不在と同じく文書の状態で分ける（状態`draft`は`warning`、状態`approved`は`error`。
[関係・トレースモデル §9](../02_仕様文書モデル/04_関係・トレースモデル.md#9-パス)）。

### 6.3 所有の判定

所有の判定は、NFCにした字句のパスのセグメント単位の包含で行う。シンボリックリンクを拒否し（6.2）、別の綴りによる別名を拒否する（6.1）ので、
実パス（`realpath`）と、ファイルシステム上の同一性（デバイスとiノード）による比較は使わない。メンバーのパスどうしの同一、親子関係（入れ子）の判定も、
NFCにしたセグメントで行う。複合ワークスペースの所有領域と診断は、
[複合ワークスペース仕様](../02_仕様文書モデル/05_複合ワークスペース仕様.md#51-正規パスの判定)が定める。リポジトリ、ワークツリー、サブモジュールの境界を
Gitのメタデータで照合する手順（同仕様 §5.1の手順6）は、本節の手順と独立に行う。

所有の判定と存在の検査の順序は、パスの種類で決まる。

- `implements`と`tests[].path`は、所有の判定を先に行う。字句のパスが別のワークスペースの所有領域にあれば、存在しなくても、状態`draft`の未作成の予定でも、
  存在の検査へ進まず、診断`SPEC-MULTI-OWNERSHIP-001`（重大度`error`、結果への効果`failed`）とする。この診断の重大度は文書の状態で分けない。
  自分の所有領域にあるパスだけを存在の検査にかけ、不在の重大度を文書の状態で分ける（6.2）。
- `cwd`は、存在の検査を先に行い、存在するディレクトリだけの所有を判定する。

### 6.4 TASKの`changes`

`changes`の許可の判定は、実際のパスではなく、字句のパス（NFCにした、Gitのパス）で行う。ファイルは完全一致とし、
末尾が`/`のディレクトリはパスのセグメント単位の子孫一致とし、シンボリックリンクの解決先へ許可を広げない。`changes`に書いたパスについては、
6.2の存在の検査を行わず、ファイルシステムを読まない。`changes`は作る前のファイルも書ける字句の許可であり、途中のセグメントがシンボリックリンクのパスも拒否しない。
Gitはシンボリックリンクの先を追跡しないので、そのような許可は、どの差分のパスにも一致しないだけである。
差分のパスには6.3の所有の診断を出さず、判定は許可との照合（TASK境界）だけで行う。`changes`に書く許可の範囲は、複合ワークスペース仕様 §5のとおりである。

差分に現れたシンボリックリンクのエントリは、そのエントリ自身の字句のパスだけで許可を判定し、リンク先は判定に使わない。基準版のツリーオブジェクトの
リンク先と、現在版の`lstat`による解決は使わない。リネームは、移動元と移動先を別のパスとして許可と照合する。

## 7. キャッシュ

Core 1.0は、ファイルシステムその他のプロセスの外に残る永続的なキャッシュを、読取りも書込みもしない。同じ起動の中で
再利用するメモリのキャッシュだけを許可し、操作の終了時に破棄する。メモリのキャッシュのキーと形式は内部の実装であり、
公開する結果、診断、順序、結果の状態、終了コード、コンテキストのハッシュ値を変えない。

永続的なキャッシュが実測のうえで必要になった場合は、配置、明示的なオプトイン、容量、権限、シンボリックリンク、破損時の処理、
削除、適合fixtureを、同じ将来のバージョンで追加する。Core 1.0の実装固有の拡張として先行して導入しない。
既存のキャッシュらしいパスを、キャッシュとして探索、読取り、削除、修復しない。`.spec/`の直下に未知のエントリとして
存在する場合は、通常の`SPEC-WORKSPACE-UNKNOWN-001`の規則だけを適用する。

## 8. Git不在時

Git不在でも、構文、スキーマ、関係、コンテキスト、明示対象の`check`、テストの実行は続ける。失われる保証は明示する。
ただし、複合ワークスペースは、リポジトリの境界、メンバーの登録、所有領域を確定できないため、診断`SPEC-MULTI-GIT-001`
（`blocked`）とし、次の縮退は単一ワークスペースだけに適用する。

単一ワークスペースでの引数なしの`check`は診断`SPEC-GIT-DEGRADED-001`（重大度`warning`）、`doctor`は
診断`SPEC-DOCTOR-GIT-001`（重大度`warning`）を返す。`context`と`verify`は、Gitの差分の保証を要求しない起動では、
Git不在だけを理由に診断を返さない。明示したTASKの`check`は、診断`SPEC-TASK-BOUNDARY-002`（`blocked`）とする。

| 機能 | 縮退 | 効果 |
|---|---|---|
| 変更範囲の検査 | 全体検査 | `info` |
| 承認済み要求の保護 | 実施不能 | `warning` |
| TASKの`changes`境界 | 実施不能 | 診断`SPEC-TASK-BOUNDARY-002`（`blocked`） |
| 状態遷移 | 現在の値の語彙だけを検査 | `warning` |
| 管理済みの仕様文書の削除の検出 | 実施不能 | `warning` |
| 結果の`revision` | `null` | `info` |

コミットのないリポジトリでは、引数なしの`check`を全体検査とし、新規のファイルは現在の値だけを検査する。明示した`--base`を
解決できない場合は、終了コード4とする。空の木構造を、暗黙の安全な基準版として使わない。

## 9. プロセスの出力

`verify`は、標準出力と標準エラー出力を、起動時から独立に並行して汲み出し、上限に達した後もタイムアウトの状態機械が
読取り用のハンドルを閉じるまで読取りを続ける。各ストリームへ逐次的なUTF-8のデコーダーを使い、不正なバイト列をU+FFFDへ
置換する。CRLFと単独のCRをLFへ変換し、TABとLF以外のC0、DEL、C1の制御文字をASCIIの`\\uNNNN`へ置換する。ESCを含む
端末の制御シーケンスは解釈しない。

制御文字の処理の後、次をASCIIの`[REDACTED]`へ置換する。

1. 名前がASCIIの大文字・小文字を区別せずに`TOKEN`、`SECRET`、`PASSWORD`、`PASSWD`、`API_KEY`、`PRIVATE_KEY`、
   `CREDENTIAL`、`AUTH`のいずれかを含む環境変数の、空でない値
2. `Authorization:`に続く同一行の値と、ASCIIの大文字・小文字を区別しない`Bearer `に続く、空白でないトークン
3. ASCIIの大文字・小文字を区別しない`token`、`secret`、`password`、`passwd`、`api_key`、`private_key`、
   `credential`、`auth`の直後に`:`または`=`がある同一行の値
4. `-----BEGIN ... PRIVATE KEY-----`から、対応する`-----END ... PRIVATE KEY-----`まで

環境変数の値は、制御文字を処理した後の値に揃え、UTF-8のバイト長の降順、同じ長さなら変数名のコードポイント辞書順で
置換する。ストリームの処理は、固定パターンと最長の環境変数の値の照合に必要な状態を、チャンクの間で保持する。行の値と
PEMのブロックは、開始を検出した時点から終端まで伏せ字化の状態を保ち、チャンクの境界をまたぐ一致もマスクする。
環境変数の名前と値自体は、結果へ記録しない。

伏せ字化した後のストリームについて、UTF-8の末尾65,536バイトをコードポイントの境界で保持する。元のストリームの原文の
バイト数が65,536を超えた場合だけ、対応する`*Truncated`を`true`とする。伏せ字化で長くなり、公開用のバッファーが上限を
超えた場合も末尾を保持するが、元のストリームが上限の範囲内であれば`*Truncated`は`false`のままとする。結果とレポートの
`stdoutExcerpt`／`stderrExcerpt`へ同じ伏せ字化した文字列を格納し、出力がない場合は空文字列とする。テキストでの表示は、
抜粋を自動では展開しない。

Coreは、テストの出力にある自然言語を合否には使わない。
