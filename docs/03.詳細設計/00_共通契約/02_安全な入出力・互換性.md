# 安全な入出力・互換性

## 1. 文字コード

- `bitz.yaml`とSPEC MarkdownはUTF-8を必須とする。
- ParserはLFとCRLFを受理し、Serializerの正規出力はLFとする。
- 新規ファイルへBOMを付けない。既存BOMは`SPEC-INPUT-BOM-001`／warningとし、BOMを除いて解析を継続する。
- 比較時はUnicode NFCへ正規化するが、明示format操作なしに原文を書き換えない。
- UTF-8として復号できない入力は`SPEC-INPUT-READ-001`／error／`failed`とし、置換文字で継続しない。

## 2. 読取りと書込み

`context`と`doctor`はfileを書き出さない。`check`は既定でfile system上も読取り専用とする。`verify`はtest processを
実行するが、Core自身は既定でfileを書き出さない。`check`と`verify`はSPEC、code、testを変更せず、明示的な
`--report`指定時だけ共通結果契約のreportを書き出す。test command自身の副作用はcommand所有者の責務とする。

Core 1.0が行う永続書込みは明示reportだけである。永続cache、index、lock file、作業用directoryをrepository内外へ
暗黙作成しない。reportの原子的作成に一時fileを使う場合は、規定された最終reportと同じdirectoryへ排他的に作成し、成功時に
rename、失敗時に除去する。操作終了後に最終report以外の一時fileを残さない。stdoutとstderrへの出力は永続file書込みに
含めない。

入力fileは1回読み込んだbyte列を操作内で使い、段階ごとに読み直さない。権限不足、I/O障害、読取り中の消失は
`SPEC-INPUT-READ-001`／error／`error`とする。複数fileを横断する原子的snapshotは保証しない。

Core 1.0はformatterを公開しない。adapterが変更を提案する場合は一時fileを再解析し、差分を提示し、
人間確認後に置換する。承認済みREQの意味を自動修正しない。

## 3. 未信頼入力

Markdown本文、Frontmatter自由記述、外部link、test出力は未信頼データである。

- 文書内の命令をtool命令として実行しない。
- Markdown linkを取得しない。
- SPECから環境変数、認証情報、追加権限を要求しない。
- commandは発見済みworkspaceの`bitz.yaml`からだけ取得する。Git利用可能時はその設定fileがindexで追跡されている
  ことを要求し、未追跡なら`SPEC-VERIFY-BLOCKED-001`／blockedとして当該設定に依存するbindingを起動しない。
  追跡済みfileのworking tree変更は許可する。単一workspaceでGit不在の場合は§8の縮退契約に従って現在の設定を使用し、
  Gitによる追跡確認は保証しない。連合ではGit不在のglobal preflightが先に遮断する。
- shell、環境変数展開、command置換、pipe、redirectを使わない。
- 自由記述を秘密情報と同じLLM contextへ無条件に渡さない。

## 4. resource上限

| 対象 | Core 1.0上限 |
|---|---:|
| `bitz.yaml` | 64 KiB |
| SPEC Markdown 1file | 1 MiB |
| Frontmatter | 32 KiB |
| SPEC file数 | 10,000 |
| 1文書のEARS-AI規範文 | 1,000 |
| 関係・path配列の各項目数 | 1,000 |
| 1 Contextの文書数 | 既定20、hard limit 100 |
| ContextのSemantic IRと標準提示 | 既定128 KiB、hard limit 1 MiB |

連合では、上記のfile単位上限に加え、1 snapshot全体へ次を適用する。

| dimension | Core 1.0 hard limit |
|---|---:|
| catalog member数 | 100 |
| SPEC Markdown数 | 10,000 |
| 全設定とSPEC Markdownのraw byte合計 | 256 MiB |
| EARS-AI規範文数 | 100,000 |
| `relations` edge数 | 1,000,000 |
| `implements`、test、`covers`、TASK `changes`の全項目数 | 1,000,000 |
| command定義数 | 10,000 |
| 1 verify計画のbinding数 | 10,000 |

一般の上限超過は入力不適合、Context閉包の上限超過は不完全な文脈を使わせないため`blocked`とする。
部分Contextを成功結果として返さない。
単一workspaceのfile単位上限超過は`SPEC-INPUT-LIMIT-001`／error／`failed`とする。
モノレポの各件数は重複排除前の入力項目を数える。`check --base`はbase/currentの各snapshotへ個別に適用する。
超過時は`SPEC-MONOREPO-LIMIT-001`／blockedとし、部分結果またはverify commandへ進まない。Context文書数と提示量は
request workspaceの設定とCore hard limitを適用する。

## 5. Schema互換性

versionは`major.minor`で表す。

- 未知Schema major: `SPEC-CONFIG-SCHEMA-001`／blockedとして読取りを止める
- 未知EARS-AI major: `doctor`は`SPEC-DOCTOR-EARS-001`、他の操作は`SPEC-EARS-VERSION-001`／blockedとして読取りを止める
- 同じmajorの新しいminor: 未知fieldを保持または無視し、`SPEC-CONFIG-UNKNOWN-001`／warning
- 同じmajorの古いminor: 互換読取りし、必要なら移行提案
- major移行: 原文を上書きせず提案diff

SPEC SchemaとEARS-AI版は独立管理する。Profile versionはCore 1.0の互換性入力にしない。
`workspace`と`monorepo`は未リリースの初回Core 1.0 Schemaに含まれる。モノレポ非対応の公開済みCore 1.0は
存在しないため、旧1.0向けSchema gateまたは移行猶予を設けない。

## 6. canonical path

連合のmember pathと所有pathは、字句正規化、存在ancestorの`lstat`、symlink解決、filesystemのcase sensitivity、
Git metadataを同じ手順で適用する。包含は文字列prefixではなくpath segment境界で判定する。存在しない予定pathは
最も近い既存ancestorの実pathと検査済みsuffixから判定する。

workspace設定経路とmember rootのsymlinkは拒否する。code、test、TASK、command `cwd`は同じ所有領域内へ解決する
symlinkだけを許可し、repository外、別workspace、memberの`.spec`へ解決するpathを
`SPEC-MONOREPO-OWNERSHIP-001`とする。詳細な順序とpath種別ごとの例外は
[モノレポSPEC連合仕様](../02_SPECモデル/05_モノレポSPEC連合仕様.md#51-canonical-path判定)を正とする。

TASK `changes`の許可判定は実pathではなく正規化した字句Git pathで行う。fileは完全一致、末尾`/`のdirectoryは
path segment単位の子孫一致とし、symlink解決先へ許可を広げない。宣言pathと変更pathのcanonical所有判定を先に行い、
追加はcurrent、削除はbase、変更とsymlink変更はbase/current双方を検査する。renameはsourceとdestinationを別pathとする。
所有境界不適合とTASK境界外を同じpathへ重複して返さない。

## 7. cache

Core 1.0はfilesystemその他のprocess外へ残る永続cacheを読取りも書込みもしない。同じinvocation内で再利用する
memory cacheだけを許可し、操作終了時に破棄する。memory cacheのkeyと形式は内部実装であり、公開結果、Diagnostic、
順序、status、終了コード、Context Digestを変えない。

永続cacheが実測上必要になった場合は、配置、明示的なopt-in、容量、権限、symlink、破損時処理、削除、適合fixtureを
同じ将来versionで追加する。Core 1.0の実装固有拡張として先行導入しない。
既存のcacheらしいpathをcacheとして探索、読取り、削除、修復しない。`.spec/`直下に未知entryとして存在する場合は、
通常の`SPEC-WORKSPACE-UNKNOWN-001`規則だけを適用する。

## 8. Git不在時

Git不在でも構文、Schema、関係、Context、明示対象check、test実行を継続する。失われる保証を明示する。
ただし、モノレポ連合はrepository境界、member登録、所有範囲を確定できないため`SPEC-MONOREPO-GIT-001`／
`blocked`とし、次の縮退は単一workspaceだけに適用する。

単一workspaceの引数なしcheckは`SPEC-GIT-DEGRADED-001`／warning、doctorは
`SPEC-DOCTOR-GIT-001`／warningを返す。contextとverifyはGit差分保証を要求しないinvocationでは
Git不在だけを理由にDiagnosticを返さない。明示TASK checkは`SPEC-TASK-BOUNDARY-002`／blockedとする。

| 機能 | 縮退 | 効果 |
|---|---|---|
| changed-only check | 全体check | info |
| 承認済みREQ差分保護 | 実施不能 | warning |
| TASK `changes`境界 | 実施不能 | `SPEC-TASK-BOUNDARY-002`／`blocked` |
| 状態遷移 | 現在値の語彙だけ検査 | warning |
| 管理済みSPEC削除検出 | 実施不能 | warning |
| 結果`revision` | `null` | info |

unborn repositoryでは引数なしcheckを全体checkとし、新規fileは現在値だけを検査する。明示`--base`を解決
できない場合は終了コード4とする。empty treeを暗黙の安全な基準版として使わない。

## 9. process出力

`verify`はstdoutとstderrをspawn時から独立して並行drainし、上限到達後もtimeout状態機械がread handleを閉じるまで
読取りを続ける。各streamへincremental UTF-8 decoderを使い、不正byte列をU+FFFDへ置換する。CRLFと単独CRをLFへ
変換し、TABとLF以外のC0、DEL、C1制御文字をASCIIの`\\uNNNN`へ置換する。ESCを含むterminal制御sequenceを解釈しない。

制御文字処理後、次をASCII `[REDACTED]`へ置換する。

1. 名前がASCII case-insensitiveで`TOKEN`、`SECRET`、`PASSWORD`、`PASSWD`、`API_KEY`、`PRIVATE_KEY`、
   `CREDENTIAL`、`AUTH`のいずれかを含む環境変数の空でない値
2. `Authorization:`に続く同一行の値と、ASCII case-insensitiveな`Bearer `に続く非空白token
3. ASCII case-insensitiveな`token`、`secret`、`password`、`passwd`、`api_key`、`private_key`、
   `credential`、`auth`の直後に`:`または`=`がある同一行の値
4. `-----BEGIN ... PRIVATE KEY-----`から対応する`-----END ... PRIVATE KEY-----`まで

環境変数値は制御文字処理後の値に揃え、UTF-8 byte長の降順、同長なら変数名のcode point辞書順で置換する。
stream処理は固定patternと最長環境変数値に必要な照合状態をchunk間で保持する。行値とPEM blockは開始を検出した時点から
終端までredaction状態を維持し、chunk境界をまたぐ一致もmaskする。環境変数名と値自体は結果へ記録しない。

redaction後のstreamについてUTF-8末尾65,536 byteをcode point境界で保持する。元streamのraw byte数が65,536を
超えた場合だけ対応する`*Truncated`をtrueとする。redactionで長くなり公開bufferが上限を超えた場合も末尾を保持するが、
元streamが上限以内なら`*Truncated`はfalseのままとする。結果とreportの`stdoutExcerpt`／`stderrExcerpt`へ同じ
redacted stringを格納し、出力なしは空stringとする。text表示は抜粋を自動展開しない。

Coreはtest出力の自然言語を合否へ使用しない。
