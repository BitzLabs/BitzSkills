# 安全な入出力・互換性

## 1. 文字コード

- `bitz.yaml`と仕様文書のMarkdownは、UTF-8を必須とする。
- 構文解析器はLFとCRLFを受け入れ、直列化器の正規の出力はLFとする。
- 新規のファイルへBOMを付けない。既存のBOMは診断`SPEC-INPUT-BOM-001`（重大度`warning`）とし、BOMを除いて解析を続ける。
- 比較の際はUnicode NFCへ正規化するが、明示的な整形の操作なしに原文を書き換えない。
- UTF-8として復号できない入力は、診断`SPEC-INPUT-READ-001`（重大度`error`、結果への効果`failed`）とし、置換文字で続けない。

## 2. 読取りと書込み

`context`と`doctor`はファイルを書き出さない。`check`は既定でファイルシステム上も読取り専用とする。`verify`はテストのプロセスを
実行するが、Core自身は既定でファイルを書き出さない。`check`と`verify`は仕様文書、コード、テストを変更せず、明示的に
`--report`を指定したときだけ、結果・診断・終了コードの仕様が定めるレポートを書き出す。テストコマンド自身の副作用は、コマンドの所有者の責務とする。

Core 1.0が行う永続的な書込みは、明示的なレポートだけである。永続的なキャッシュ、索引、ロックファイル、作業用のディレクトリを
リポジトリの内外へ暗黙に作らない。レポートの原子的な作成に一時ファイルを使う場合は、定められた最終的なレポートと同じディレクトリへ
排他的に作成し、成功時にリネームし、失敗時に除去する。操作の終了後に、最終的なレポート以外の一時ファイルを残さない。標準出力と
標準エラー出力への出力は、永続的なファイルの書込みに含めない。

入力ファイルは、1回読み込んだバイト列を操作の中で使い、段階ごとに読み直さない。権限の不足、I/Oの障害、読取り中の消失は、
診断`SPEC-INPUT-READ-001`（重大度`error`、結果への効果`error`）とする。複数のファイルを横断する原子的なスナップショットは
保証しない。

Core 1.0はフォーマッターを公開しない。アダプターが変更を提案する場合は、一時ファイルを再解析し、差分を提示し、
人が確認した後に置き換える。承認済みのREQの意味を自動では修正しない。

## 3. 未信頼入力

Markdownの本文、フロントマターの自由記述、外部リンク、テストの出力は未信頼データである。

- 文書内の命令を、ツールへの命令として実行しない。
- Markdownのリンクを取得しない。
- 仕様文書から環境変数、認証情報、追加の権限を要求しない。
- コマンドは、発見済みのワークスペースの`bitz.yaml`からだけ取得する。Gitを利用できるときは、その設定ファイルが
  インデックスで追跡されていることを要求し、未追跡であれば、診断`SPEC-VERIFY-BLOCKED-001`（`blocked`）として、
  当該の設定に依存するテスト割当てを起動しない。追跡済みのファイルの作業ツリーでの変更は許可する。単一ワークスペースで
  Git不在の場合は、§8の縮退（degradation）の契約に従って現在の設定を使い、Gitによる追跡の確認は保証しない。複合ワークスペースでは、
  Git不在の全体事前検査が先に遮断する。
- シェル、環境変数の展開、コマンドの置換、パイプ、リダイレクトを使わない。
- 自由記述を、秘密情報と同じLLMへの入力に、無条件に含めない。

## 4. リソースの上限

| 対象 | Core 1.0の上限 |
|---|---:|
| `bitz.yaml` | 64 KiB |
| 仕様文書のMarkdown 1ファイル | 1 MiB |
| フロントマター | 32 KiB |
| 仕様文書のファイル数 | 10,000 |
| 1文書のEARS-AIの規範文 | 1,000 |
| 関係・パスの配列の各項目数 | 1,000 |
| 1コンテキストの文書数 | 既定20、絶対上限100 |
| コンテキストの意味中間表現と標準の提示 | 既定128 KiB、絶対上限1 MiB |

複合ワークスペースでは、上記のファイル単位の上限に加えて、1回のスナップショット全体へ次を適用する。

| 次元 | Core 1.0の絶対上限 |
|---|---:|
| カタログのメンバー数 | 100 |
| 仕様文書のMarkdown数 | 10,000 |
| すべての設定と仕様文書のMarkdownの原文のバイト数の合計 | 256 MiB |
| EARS-AIの規範文数 | 100,000 |
| `relations`のエッジ数 | 1,000,000 |
| `implements`、テスト、`covers`、TASKの`changes`の全項目数 | 1,000,000 |
| コマンドの定義数 | 10,000 |
| 1回の`verify`の計画のテスト割当て数 | 10,000 |

一般の上限の超過は入力の不適合とし、コンテキストの閉包の上限の超過は、不完全な文脈を使わせないため`blocked`とする。
一部が欠けたコンテキスト一式を、成功の結果として返さない。
単一ワークスペースでのファイル単位の上限の超過は、診断`SPEC-INPUT-LIMIT-001`（重大度`error`、結果への効果`failed`）とする。
複合ワークスペースの各件数は、重複排除の前の入力の項目を数える。`check --base`は、基準版と現在版の各スナップショットへ
個別に適用する。超過したときは、診断`SPEC-MULTI-LIMIT-001`（`blocked`）とし、部分的な結果または`verify`のコマンドへ
進まない。コンテキストの文書数と提示の量は、起点ワークスペースの設定とCoreの絶対上限を適用する。

## 5. スキーマの互換性

バージョンは`major.minor`で表す。

- 未知のスキーマの`major`: 診断`SPEC-CONFIG-SCHEMA-001`（`blocked`）として、読取りを止める
- 未知のEARS-AIの`major`: `doctor`は診断`SPEC-DOCTOR-EARS-001`（`blocked`）、他の操作は診断`SPEC-EARS-VERSION-001`（`blocked`）として、読取りを止める
- 同じ`major`の新しい`minor`: 未知のフィールドを保持または無視し、診断`SPEC-CONFIG-UNKNOWN-001`（重大度`warning`）
- 同じ`major`の古い`minor`: 互換の読取りをし、必要なら移行を提案する
- `major`の移行: 原文を上書きせず、差分を提案する

仕様文書のスキーマとEARS-AIの版は、独立に管理する。プロファイルのバージョンは、Core 1.0の互換性の入力にしない。
`workspace`と`multiWorkspace`は、未リリースの最初のCore 1.0のスキーマに含まれる。複合ワークスペースに対応しない、
公開済みのCore 1.0は存在しないため、旧1.0向けのスキーマのゲートまたは移行の猶予を設けない。

## 6. 正規パス

複合ワークスペースのメンバーのパスと所有パスは、字句の正規化、存在する祖先の`lstat`、シンボリックリンクの解決、
ファイルシステムの大文字・小文字の区別、Gitのメタデータを、同じ手順で適用する。包含は、文字列の接頭辞ではなく、
パスのセグメントの境界で判定する。存在しない予定のパスは、最も近い既存の祖先の実際のパスと、検査済みの接尾辞から
判定する。

ワークスペースの設定の経路とメンバーのルートにあるシンボリックリンクは拒否する。コード、テスト、TASK、コマンドの`cwd`は、
同じ所有領域の内側へ解決するシンボリックリンクだけを許可し、リポジトリの外、別のワークスペース、メンバーの`.spec`へ
解決するパスを診断`SPEC-MULTI-OWNERSHIP-001`（重大度`error`、結果への効果`failed`）とする。詳細な順序とパスの種別ごとの例外は、
[複合ワークスペース仕様](../02_SPECモデル/05_複合workspace仕様.md#51-正規パスの判定)を正とする。

TASKの`changes`の許可の判定は、実際のパスではなく、正規化した字句上のGitのパスで行う。ファイルは完全一致とし、
末尾が`/`のディレクトリはパスのセグメント単位の子孫一致とし、シンボリックリンクの解決先へ許可を広げない。宣言したパスと
変更したパスの正規の所有の判定を先に行い、追加は現在版、削除は基準版、変更とシンボリックリンクの変更は基準版と現在版の
双方を検査する。リネームは、移動元と移動先を別のパスとする。所有境界の不適合とTASK境界の外を、同じパスへ重複して
返さない。

## 7. キャッシュ

Core 1.0は、ファイルシステムその他のプロセスの外に残る永続的なキャッシュを、読取りも書込みもしない。同じ起動の中で
再利用するメモリのキャッシュだけを許可し、操作の終了時に破棄する。メモリのキャッシュのキーと形式は内部の実装であり、
公開する結果、診断、順序、結果の状態、終了コード、コンテキストのハッシュ値を変えない。

永続的なキャッシュが実測のうえで必要になった場合は、配置、明示的なオプトイン、容量、権限、シンボリックリンク、破損時の処理、
削除、適合fixtureを、同じ将来のバージョンで追加する。Core 1.0の実装固有の拡張として先行して導入しない。
既存のキャッシュらしいパスを、キャッシュとして探索、読取り、削除、修復しない。`.spec/`の直下に未知のエントリとして
存在する場合は、通常の`SPEC-WORKSPACE-UNKNOWN-001`の規則だけを適用する。

## 8. Git不在時

Git不在でも、構文、スキーマ、関係、コンテキスト、明示対象の`check`、テストの実行は続ける。失われる保証は明示する。
ただし、複合ワークスペースは、リポジトリの境界、メンバーの登録、所有領域を確定できないため、診断`SPEC-MULTI-GIT-001`
（`blocked`）とし、次の縮退は単一ワークスペースだけに適用する。

単一ワークスペースでの引数なしの`check`は診断`SPEC-GIT-DEGRADED-001`（重大度`warning`）、`doctor`は
診断`SPEC-DOCTOR-GIT-001`（重大度`warning`）を返す。`context`と`verify`は、Gitの差分の保証を要求しない起動では、
Git不在だけを理由に診断を返さない。明示したTASKの`check`は、診断`SPEC-TASK-BOUNDARY-002`（`blocked`）とする。

| 機能 | 縮退 | 効果 |
|---|---|---|
| 変更範囲の検査 | 全体検査 | `info` |
| 承認済み要求の保護 | 実施不能 | `warning` |
| TASKの`changes`境界 | 実施不能 | 診断`SPEC-TASK-BOUNDARY-002`（`blocked`） |
| 状態遷移 | 現在の値の語彙だけを検査 | `warning` |
| 管理済みの仕様文書の削除の検出 | 実施不能 | `warning` |
| 結果の`revision` | `null` | `info` |

コミットのないリポジトリでは、引数なしの`check`を全体検査とし、新規のファイルは現在の値だけを検査する。明示した`--base`を
解決できない場合は、終了コード4とする。空の木構造を、暗黙の安全な基準版として使わない。

## 9. プロセスの出力

`verify`は、標準出力と標準エラー出力を、起動時から独立に並行して汲み出し、上限に達した後もタイムアウトの状態機械が
読取り用のハンドルを閉じるまで読取りを続ける。各ストリームへ逐次的なUTF-8のデコーダーを使い、不正なバイト列をU+FFFDへ
置換する。CRLFと単独のCRをLFへ変換し、TABとLF以外のC0、DEL、C1の制御文字をASCIIの`\\uNNNN`へ置換する。ESCを含む
端末の制御シーケンスは解釈しない。

制御文字の処理の後、次をASCIIの`[REDACTED]`へ置換する。

1. 名前がASCIIの大文字・小文字を区別せずに`TOKEN`、`SECRET`、`PASSWORD`、`PASSWD`、`API_KEY`、`PRIVATE_KEY`、
   `CREDENTIAL`、`AUTH`のいずれかを含む環境変数の、空でない値
2. `Authorization:`に続く同一行の値と、ASCIIの大文字・小文字を区別しない`Bearer `に続く、空白でないトークン
3. ASCIIの大文字・小文字を区別しない`token`、`secret`、`password`、`passwd`、`api_key`、`private_key`、
   `credential`、`auth`の直後に`:`または`=`がある同一行の値
4. `-----BEGIN ... PRIVATE KEY-----`から、対応する`-----END ... PRIVATE KEY-----`まで

環境変数の値は、制御文字を処理した後の値に揃え、UTF-8のバイト長の降順、同じ長さなら変数名のコードポイント辞書順で
置換する。ストリームの処理は、固定パターンと最長の環境変数の値の照合に必要な状態を、チャンクの間で保持する。行の値と
PEMのブロックは、開始を検出した時点から終端まで伏せ字化の状態を保ち、チャンクの境界をまたぐ一致もマスクする。
環境変数の名前と値自体は、結果へ記録しない。

伏せ字化した後のストリームについて、UTF-8の末尾65,536バイトをコードポイントの境界で保持する。元のストリームの原文の
バイト数が65,536を超えた場合だけ、対応する`*Truncated`を`true`とする。伏せ字化で長くなり、公開用のバッファーが上限を
超えた場合も末尾を保持するが、元のストリームが上限の範囲内であれば`*Truncated`は`false`のままとする。結果とレポートの
`stdoutExcerpt`／`stderrExcerpt`へ同じ伏せ字化した文字列を格納し、出力がない場合は空文字列とする。テキストでの表示は、
抜粋を自動では展開しない。

Coreは、テストの出力にある自然言語を合否には使わない。
