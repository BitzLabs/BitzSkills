# 参照・トレース・検証仕様

## 1. 最小トレース

Core 1.0は次の関係を合否判定へ使用する。

```text
REQ/TECH statement
  ├── relations ----> 必須SPEC、refinement、後継文書
  ├── implements ---> 実装ファイル
  ├── tests.covers -> テストファイル
  └── command ------> bitz.yamlの検証コマンド

TASK
  ├── addresses ----> 実装対象statement
  ├── requires -----> 前提SPEC/TASK
  └── changes ------> 許可する変更パス
```

関係はFrontmatterから導出し、別のトレース台帳を作らない。Context Resolverはこの索引から完全な依存閉包と
句単位の実装・テスト網羅を計算する。コードシンボルやassertionの意味的充足はCore 1.0の対象外とする。

## 2. ID解決

`bitz check`は全SPECのFrontmatterと関係を1回走査し、文書ID、規範文ID、正引き・逆引き関係の索引を作る。
変更範囲検査でも逆参照を欠落させないため、この軽量索引だけは常に全SPECを対象とする。EARS-AI ASTの完全解析と
本文スタイル検査は、変更文書、その強い依存閉包、直接の逆参照へ限定し、`--full`では全件を対象とする。

- 宣言された強い関係のtargetが文書IDまたは規範文IDへ解決されない場合はエラーとする。強い関係を持たない文書は合法である。
- IDが複数件に解決される場合は重複IDエラーとする。
- source/targetの種別と状態を検査する。
- `requires`と`refines`の意味依存グラフ、`supersedes`連鎖、TASK依存の禁止循環を検査する。
- `related`はContextへ自動包含せず、参照切れをwarningとする。
- `reports/`、通常の`docs/`、Issue番号をID解決対象にしない。
- 外部URLは関係へ書かず、本文のMarkdownリンクとして記述する。

## 3. パスとテスト対応

`implements`、`tests[].path`、`changes`はワークスペースルートから解決する。

- `implements`と`tests[].path`は通常ファイルとして実在することを検査する。
- glob、絶対パス、ルート外参照を禁止する。
- シンボリックリンクの実体がルート外になる場合はエラーとする。
- `draft`で未解決のパスはwarning、`approved`ではerrorとする。
- `tests[].covers`は同じ文書が所有する規範文IDへ解決する。
- 規範文を持つREQ/TECHでは文書IDだけの`covers`を禁止する。

`changes`だけは末尾`/`のディレクトリ接頭辞を許可する。新規作成予定パスを扱うため、対象自体の存在を要求しない。

## 4. `bitz check`

検査順序は次のとおりとする。

1. `bitz.yaml`のSchemaと互換性
2. ファイル名、Frontmatter、IDの一意性
3. EARS-AI構文と文書ID整合
4. 型付き関係のID、型、状態、循環
5. `implements`、テスト対応、検証コマンドの解決
6. 文書スタイルと規範文の配置
7. 承認済み要求の保護
8. 明示されたTASKの変更境界
9. 変更された強い依存の逆参照による影響候補

後段に進めない構文エラーがあっても、独立して検査できる他ファイルの診断は可能な限り返す。
通常実行は変更されたSPEC、その強い依存先、その直接の逆参照を再検査する。`--full`は全件を検査する。
全SPECのFrontmatter関係索引を作る処理と、対象範囲のAST・本文を完全検査する処理を混同しない。

変更されたREQまたはTECHへ強く依存する`approved`文書は影響候補としてwarningにする。Coreは意味的影響を
断定せず、状態を自動的に`outdated`へ変更しない。`related`の変更は影響候補にしない。

TASKファイルをパスとして明示した場合、Gitの基準版からの変更パスを`changes`と比較する。境界外変更は
`SPEC-TASK-BOUNDARY-001`とする。TASK自身のファイルと明示生成した検証レポートは比較対象から除く。
Gitが利用できない場合は境界検査を`blocked`とし、暗黙に通過させない。

## 5. `bitz verify`

要求IDまたは規範文IDを指定した場合の処理は次のとおりとする。

1. `purpose=verify`のContext Bundleを完全に解決する。
2. 起点と強い依存が適用可能な状態であることを確認する。
3. 対象となる全`MUST`に1件以上のテスト対応があることを確認する。
4. テストパスとコマンドを解決する。
5. 同じコマンドを使うテストパスを重複排除する。
6. `{tests}`をargvへ安全に展開し、ワークスペースルートで実行する。
7. Context Digest、対象規範文、終了コード、所要時間を結果へ記録する。

コマンド終了コード0を`passed`、0以外を`failed`、前提・依存・カバレッジ不足を`blocked`、起動失敗や
タイムアウトを`error`とする。Coreはテスト出力の自然言語を解釈して成功へ上書きしない。

`tests[].command`があればそのコマンドを使い、なければ文書の`verify`を使う。どちらもない場合は
`SPEC-VERIFY-BLOCKED-001`とする。

### 5.1 引数なし実行

引数なしの`bitz verify`は次の規則で処理する。

1. `approved`のREQと、EARS-AI規範文を持つ`approved`のTECHを対象とする。`draft`と`outdated`は除外件数だけを返す。
2. 対象ごとに`purpose=verify`のContext Bundleを解決する。
3. 未testedの`MUST`を持つ対象はその対象だけ`blocked`とし、独立した他対象の検証は継続する。
4. 同じコマンド定義を使うテストパスは全対象で重複排除し、1回の実行へまとめる。
5. 集約statusは`error`、`failed`、`blocked`、`passed_with_warnings`、`passed`の順で最も悪い状態を採用する。
6. 対象が0件の場合は`SPEC-VERIFY-BLOCKED-002`を返して`blocked`とし、空のCIを成功扱いしない。

集約結果には対象ごとのstatusとDiagnosticを残し、一部成功を全体成功として表示しない。

## 6. 検証結果

成功時は既定でファイルを作らず、CLI結果だけを返す。`--report`指定時または失敗時に保存する場合は、
`.spec/reports/<UTC basic timestamp>-<operation>.json`を使用する。

```json
{
  "schemaVersion": "1.0",
  "operation": "verify",
  "status": "passed",
  "scope": "selected",
  "targets": ["REQ-001"],
  "contextDigest": "sha256:0123456789abcdef",
  "statements": ["REQ-001:AC-01", "REQ-001:AC-02"],
  "durationMs": 842,
  "revision": {
    "commit": "0123456789abcdef",
    "dirty": false
  },
  "commands": [
    {
      "name": "default",
      "cwd": ".",
      "argv": ["pytest", "-q", "tests/auth/test_service.py"],
      "tests": ["tests/auth/test_service.py"],
      "covers": ["REQ-001:AC-01", "REQ-001:AC-02"],
      "exitCode": 0,
      "durationMs": 817
    }
  ],
  "diagnostics": []
}
```

`commands[].argv`は`{tests}`展開後の実行argv、`cwd`はワークスペースルート相対の実行位置を表す。
レポートは実行時点の証跡であり、次回の合否判定への入力にしない。標準出力・標準エラー全文、環境変数、
秘密情報は保存しない。失敗箇所の短い抜粋を保存する場合も、Coreによるマスキングを完全な秘密検出とはみなさない。

`revision.commit`は実行時のHEAD、`revision.dirty`は追跡対象ファイルに未コミット変更があったかを表す。
`dirty: true`のレポートは長期的な再現証跡ではなく、その作業ツリーでの参考結果として扱う。

## 7. `verified`の扱い

`verified`は、特定Context Digest、コード、テスト、環境に対する`bitz verify`の成功結果を表す実行時の述語であり、
Frontmatter状態ではない。SPEC、強い関係、テスト対応の変更でContext Digestが変われば、以前の結果を
現在の成功根拠にしない。

長期証跡が必要な場合は、Gitコミットに紐づくCI結果または明示生成したレポートを使用する。

## 8. Diagnosticコード

EARS-AI構文の診断は`EAI-*`、Context Resolutionは`CTX-*`、SPECファイル契約は次を使用する。

| コード | severity | 条件 |
|---|---|---|
| `SPEC-CONFIG-SCHEMA-001` | error | `bitz.yaml`の必須項目、型、版が不正 |
| `SPEC-FILE-NAME-001` | error | ファイル名のIDとFrontmatter IDが不一致 |
| `SPEC-FM-REQUIRED-001` | error | Frontmatter必須項目がない |
| `SPEC-ID-DUPLICATE-001` | error | 文書IDまたは規範文IDが重複 |
| `SPEC-RELATION-LEGACY-001` | error | 意味が曖昧な旧`refs`を使用 |
| `SPEC-RELATION-MISSING-001` | error | 強い関係のIDを解決できない |
| `SPEC-PATH-INVALID-001` | error / warning | パスが不在、ルート外、または許可されない形式。`draft`の未作成予定だけwarning |
| `SPEC-TEST-COVERAGE-001` | error | テスト対応の対象規範文が不正または不足 |
| `SPEC-VERIFY-BLOCKED-001` | error | テストまたは検証コマンドが不足 |
| `SPEC-VERIFY-BLOCKED-002` | error | 引数なしverifyの対象が0件 |
| `SPEC-SAFETY-APPROVED-001` | error | 承認状態を戻さず要求の意味または強い関係を変更 |
| `SPEC-TASK-BOUNDARY-001` | error | 明示TASKの`changes`外に変更がある |
| `SPEC-TASK-BOUNDARY-002` | error | Git不在により明示TASKの変更境界を検査できない |
| `SPEC-IMPACT-OUTDATED-001` | warning | 強い依存先変更により再確認が必要な可能性がある |
| `SPEC-STYLE-H1-001` | error | H1が不在、複数、またはFrontmatterと不一致 |
| `SPEC-STYLE-SECTION-001` | error | 必須H2がない |
| `SPEC-STYLE-SECTION-002` | error | H2が未定義、または定義順に反する |
| `SPEC-STYLE-PLACEMENT-001` | error | EARS-AI規範文が許可セクション外にある |
| `SPEC-STYLE-PSEUDO-001` | warning | 太字ラベルが標準セクションを代替する |
| `SPEC-STYLE-EMPTY-001` | warning | 空の任意セクションがある |

Diagnosticの共通フィールドと終了コードは
[共通アーキテクチャ](../../02.設計書/01_共通アーキテクチャ.md)を使用する。同じ原因に対して
ファイル単位と規範文単位の診断を重複して出さない。OWNERとコード形式は
[ADR-011](../../02.設計書/10_決定記録/ADR-011_Diagnostic所有者とコード命名規約.md)を正とする。
