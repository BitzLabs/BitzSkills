# 参照・トレース・検証仕様

## 1. 最小トレース

Core 1.0は次の関係を合否判定へ使用する。

```text
REQ/TECH statement
  ├── relations ----> 必須SPEC、refinement、後継文書
  ├── implements ---> 実装ファイル
  ├── tests.covers -> テストファイル
  └── command ------> bitz.yamlの検証コマンド

TASK
  ├── addresses ----> 実装対象statement
  ├── requires -----> 前提SPEC/TASK
  └── changes ------> 許可する変更パス
```

関係はFrontmatterから導出し、別のトレース台帳を作らない。Context Resolverはこの索引から完全な依存閉包と
句単位の実装・テスト網羅を計算する。コードシンボルやassertionの意味的充足はCore 1.0の対象外とする。

## 2. ID解決

`bitz check`はactive workspaceの全SPECを走査し、文書ID、規範文ID、正引き・逆引き関係の索引を作る。
モノレポ連合では、横断関係と逆参照を欠落させないため全memberの軽量Frontmatterを修飾IDで索引する。
変更範囲検査でも逆参照を欠落させないため、この軽量索引だけは常に全SPECを対象とする。EARS-AI ASTの完全解析と
本文スタイル検査は、変更文書、その強い依存閉包、直接の逆参照へ限定し、`--full`では全件を対象とする。

- 宣言された強い関係のtargetが文書IDまたは規範文IDへ解決されない場合はエラーとする。強い関係を持たない文書は合法である。
- IDが複数件に解決される場合は重複IDエラーとする。
- source/targetの種別と状態を検査する。
- `requires`と`refines`の意味依存グラフ、`supersedes`連鎖、TASK依存の禁止循環を検査する。
- `related`はContextへ自動包含せず、参照切れをwarningとする。
- `reports/`、通常の`docs/`、Issue番号をID解決対象にしない。
- 外部URLは関係へ書かず、本文のMarkdownリンクとして記述する。
- 別workspaceのtargetは`<workspace-id>::<document-id>`または修飾規範文IDで指定し、非修飾の横断探索を行わない。

## 3. パスとテスト対応

`implements`、`tests[].path`、`changes`はワークスペースルートから解決する。

- `implements`と`tests[].path`は通常ファイルとして実在することを検査する。
- glob、絶対パス、ルート外参照を禁止する。
- シンボリックリンクの実体がルート外になる場合はエラーとする。
- `draft`で未解決のパスはwarning、`approved`ではerrorとする。
- `tests[].covers`は原則として同じ文書が所有する規範文IDへ解決する。モノレポでは、宣言文書が直接
  `refines`する別workspaceの規範文、または直接`refines`する文書が所有する規範文に限り、修飾IDでの
  横断テスト対応を許可する。
- 規範文を持つREQ/TECHでは文書IDだけの`covers`を禁止する。

`changes`だけは末尾`/`のディレクトリ接頭辞を許可する。新規作成予定パスを扱うため、対象自体の存在を要求しない。
モノレポmemberの各パスはmember root内に限定する。連合ルートは登録member配下を所有パスへ指定できない。

## 4. `bitz check`

明示対象にはREQ、TECH、ADR、TASKの文書ID、規範文ID、それらのSPECファイルpathを指定できる。
規範文IDとpathは所有文書IDへ正規化する。コードpath、テストpath、ディレクトリ、構文上不正なID／pathは
引数不正として終了コード4を返す。形式が正しいが存在しないIDは`CTX-ROOT-MISSING-001`、不在・範囲外の
SPEC pathは`SPEC-PATH-INVALID-001`とする。複数対象は同一selected workspaceに限定し、異なるworkspaceの
独立した起点はrequestを分ける。混在した場合は`CTX-ROOT-WORKSPACE-001`／error／`failed`とする。

明示対象は、対象文書、その強い依存閉包、直接の逆参照を完全検査する。`--full`と明示対象は排他的とし、
引数なしではGit変更集合を起点にする。いずれも全SPECの軽量Frontmatter索引を構築する。

検査順序は次のとおりとする。

1. `bitz.yaml`のSchemaと互換性
2. ファイル名、Frontmatter、IDの一意性
3. EARS-AI構文と文書ID整合
4. 型付き関係のID、型、状態、循環
5. `implements`、テスト対応、検証コマンドの解決
6. 文書スタイルと規範文の配置
7. 承認済み要求の保護
8. 明示されたTASKの変更境界
9. 変更された強い依存の逆参照による影響候補

後段に進めない構文エラーがあっても、独立して検査できる他ファイルの診断は可能な限り返す。
通常実行は変更されたSPEC、その強い依存先、その直接の逆参照を再検査する。`--full`は全件を検査する。
全SPECのFrontmatter関係索引を作る処理と、対象範囲のAST・本文を完全検査する処理を混同しない。

Git基準版は`--base <git-revision>`指定時はその解決済みcommit、未指定時は`HEAD`とする。変更集合は
基準版から現在のindexとworktreeまでの変更、および未追跡かつ非ignore pathの和集合とし、削除とrenameも
保持する。pathはworkspace相対の`/`区切りへ正規化する。同じ基準版を変更範囲、状態遷移、
承認済みREQ保護、TASK境界へ使用し、結果JSONの`revision.base`へ記録する。
指定revisionを解決できない場合は終了コード4とする。Git不在またはunborn repositoryでは
[更新・互換性・安全性](07_更新・互換性・安全性.md) §8の縮退規則を使う。

`bitz check --all-workspaces`は連合ルートでだけ使用でき、catalog、全member、横断関係、所有境界を検査する。
処理順は連合ルート、workspace ID辞書順とし、結果にworkspace別statusを残す。

変更されたREQまたはTECHへ強く依存する`approved`文書は影響候補としてwarningにする。Coreは意味的影響を
断定せず、状態を自動的に`outdated`へ変更しない。`related`の変更は影響候補にしない。

TASK IDまたはTASKファイルpathを明示した場合、同じGit基準版からの変更pathを`changes`と比較する。境界外変更は
`SPEC-TASK-BOUNDARY-001`とする。TASK自身のファイルと明示生成した検証レポートは比較対象から除く。
Gitが利用できない場合は境界検査を`blocked`とし、暗黙に通過させない。

check結果の`revision`は`base`、`commit`、`dirty`を持つ。`base`は解決済み比較元commit、`commit`は
実行時HEAD、`dirty`はindex、worktree、未追跡かつ非ignore pathのいずれかに変更があることを表す。

## 5. `bitz verify`

明示対象にはREQ ID、TECH ID、規範文ID、TASK ID、REQ／TECH／TASKのSPECファイルpathを指定できる。
SPECファイルpathはFrontmatter IDへ正規化する。コードpath、テストpath、ディレクトリ、ADR ID／pathは
引数不正として終了コード4を返す。直接テストpathを受け付けて句単位coverageを迂回してはならない
（[ADR-023](../../02.設計書/10_決定記録/ADR-023_verify明示対象とpath入力の確定.md)）。

| 明示対象 | target statementまたは実行対象 |
|---|---|
| REQ ID | 所有する全規範文と、適用される強い依存・refinement |
| 規範文を持つTECH ID | 所有する全規範文と、適用される強い依存・refinement |
| 規範文ID | 指定句と、その句へ適用される強い依存・直接refinement。兄弟句は`adjacent` |
| 規範文を持たないTECH ID | 文書に宣言された`tests` |
| TASK ID | `addresses`に列挙された句と`requires`閉包。規範文なしTECH IDは当該TECHの文書単位`tests` |
| REQ／TECH／TASKのSPECファイルpath | Frontmatter IDへ正規化後、上記と同じ規則 |

複数対象はすべてIDへ正規化し、同一request workspaceに属することを確認した後、target statement集合を
和集合にして重複排除する。異なるworkspaceが所有する独立した起点はrequestを分ける。形式が正しいが
存在しないIDは`CTX-ROOT-MISSING-001`、不在・範囲外のSPEC pathは`SPEC-PATH-INVALID-001`、
実行可能なテストまたはコマンドがない場合は`SPEC-VERIFY-BLOCKED-001`を返す。

明示対象を指定した場合の処理は次のとおりとする。

1. `purpose=verify`のContext Bundleを完全に解決する。
2. 起点と強い依存が適用可能な状態であることを確認する。
3. 上表からtarget statement集合と文書単位verification bindingを確定し、対象となる全`MUST`に
   1件以上のテスト対応があることを確認する。
   規範文を持たないTECHでは
   `MUST`が0件であり、この確認は自動的に成立する。
4. テストパスとコマンドを解決する。
5. 同じコマンド定義（`argv`と`cwd`の組）を使うテストパスを重複排除する。
6. `{tests}`をargvへ安全に展開し、解決した`cwd`で実行する。`cwd`が未指定のコマンドは、
   テストを所有するワークスペースルートを実行位置とする。
7. Context Digest、対象規範文、実効timeout、終了理由、終了コード、所要時間を結果へ記録する。

`--timeout <seconds>`は1以上3600以下の整数capとし、実効値を
`min(CLI指定値, workspaceのverify.timeoutSeconds)`で決める。未指定時は設定値を使用する。
コマンド終了コード0を`passed`、0以外を`failed`、前提・依存・カバレッジ不足を`blocked`、起動失敗、
signal終了、タイムアウトを`error`とする。Coreはテスト出力の自然言語を解釈して成功へ上書きしない。

`tests[].command`があればそのコマンドを使い、なければ文書の`verify`を使う。どちらもない場合は
`SPEC-VERIFY-BLOCKED-001`とする。

### 5.1 引数なし実行

引数なしの`bitz verify`は次の規則で処理する。

1. `approved`のREQと、`approved`のTECHのうち次のいずれかを対象とする。
   EARS-AI規範文を持つもの、または規範文を持たず`tests`を宣言しているもの。
   `draft`、`outdated`、テスト対応を持たない規範文なしTECHは、除外理由ごとの件数だけを返す。
2. 対象ごとに`purpose=verify`のContext Bundleを解決する。
3. 未testedの`MUST`を持つ対象はその対象だけ`blocked`とし、独立した他対象の検証は継続する。
   規範文を持たないTECHは句単位カバレッジ判定の対象外とし、宣言された`tests`の実行結果と
   終了コードだけで`passed`または`failed`を決める。
4. 同じコマンド定義を使うテストパスは全対象で重複排除し、1回の実行へまとめる。
5. 集約statusは[共通結果形式](../../02.設計書/01_共通アーキテクチャ.md)の最悪値規則を使う。
6. 対象が0件の場合は`SPEC-VERIFY-BLOCKED-002`を返して`blocked`とし、空のCIを成功扱いしない。

集約結果には対象ごとのstatusとDiagnosticを残し、一部成功を全体成功として表示しない。

### 5.2 モノレポ全体実行

`bitz verify --all-workspaces`は、連合ルートとmemberをworkspace ID順に処理し、各workspaceで§5.1を実行する。
テストパス、コマンド、`cwd`はテスト所有workspaceの設定と所有境界から解決する。横断refinementによる
共通規範文のテストも同じ規則で実行する。異なるworkspaceのコマンド名が同じでも重複排除・統合しない。
実行済み判定は`(workspace-id, command, test-path)`で行い、この集合を連合全体で1つだけ保持する。
横断refinementにより同じテストが複数workspaceの対象から参照される場合も、実行は1回だけとし、
後続の対象は実行結果と終了コードを参照する。結果JSONの`commands`は実行実体を持つworkspaceへ置き、
参照した側は対象別結果のstatusとして反映する。独立したworkspaceは先行workspaceの失敗後も継続し、
全体statusは共通結果形式の最悪値規則で集約する。

`--timeout`指定時もworkspaceごとの設定は継承・統合せず、各commandへCLI capとの小さい方を適用する。

連合内に検証対象が0件のworkspaceがあっても、そのworkspaceだけを
`SPEC-VERIFY-BLOCKED-002`／warningとし、statusを`passed_with_warnings`とする。
連合全体の対象が0件の場合に限り、同コードをerrorとして連合全体を`blocked`にする。
モノレポ連合は段階的に構成されるため、SPECをまだ持たないmemberの存在が
全体CIを停止する状態を作らない。0件であった事実はworkspace別結果へ残す。

## 6. 検証結果

`passed`と`passed_with_warnings`では既定でファイルを作らず、CLI結果だけを返す。`--format json`は
同じ結果を標準出力へ返し、ファイルを生成しない。`--report`指定時、または`failed`、`blocked`、`error`時は、
`.spec/reports/<UTC basic timestamp>-<operation>.json`を使用する。
引数不正の終了コード4ではworkspace結果を生成していないため、レポートを保存しない。

モノレポのmember単独操作はmemberの`.spec/reports/`、`--all-workspaces`の集約レポートはfederation rootの
`.spec/reports/`へ保存する。集約レポートはworkspace別結果を保持する。

```json
{
  "schemaVersion": "1.0",
  "operation": "verify",
  "status": "passed",
  "scope": "selected",
  "workspace": {"id": "web", "path": "apps/web"},
  "targets": ["web::REQ-001"],
  "contextDigest": "sha256:0123456789abcdef",
  "statements": ["web::REQ-001:AC-01", "web::REQ-001:AC-02"],
  "durationMs": 842,
  "revision": {
    "commit": "0123456789abcdef",
    "dirty": false
  },
  "commands": [
    {
      "name": "default",
      "status": "passed",
      "termination": "exit",
      "cwd": ".",
      "argv": ["pytest", "-q", "tests/auth/test_service.py"],
      "tests": ["tests/auth/test_service.py"],
      "covers": ["web::REQ-001:AC-01", "web::REQ-001:AC-02"],
      "exitCode": 0,
      "timeoutSeconds": 300,
      "durationMs": 817
    }
  ],
  "diagnostics": []
}
```

`commands[].argv`は`{tests}`展開後の実行argv、`cwd`はテストを所有するワークスペースルートから見た
実行位置を表す。`cwd`が未指定のコマンドでは`"."`とする。`argv`内のテストパスは
[bitz.yaml仕様](02_bitz.yaml仕様.md) §4に従い`cwd`相対へ正規化した値、`commands[].tests`は
宣言どおりのワークスペースルート相対パスとする。両者は`cwd`が`"."`でない場合に一致しない。
`commands[].termination`は`exit`、`timeout`、`spawn_error`、`signal`の4値とする。通常終了以外では
`exitCode`を`null`とし、`status: error`と該当Diagnosticを返す。非0で通常終了したテストは
`termination: exit`、`status: failed`とする。
レポートは実行時点の証跡であり、次回の合否判定への入力にしない。標準出力・標準エラー全文、環境変数、
秘密情報は保存しない。失敗箇所の短い抜粋を保存する場合も、Coreによるマスキングを完全な秘密検出とはみなさない。

`revision.commit`は実行時のHEAD、`revision.dirty`はindex、worktree、未追跡かつ非ignore pathのいずれかに
変更があったかを表す。
`dirty: true`のレポートは長期的な再現証跡ではなく、その作業ツリーでの参考結果として扱う。

## 7. `verified`の扱い

`verified`は、特定Context Digest、コード、テスト、環境に対する`bitz verify`の成功結果を表す実行時の述語であり、
Frontmatter状態ではない。SPEC、強い関係、テスト対応の変更でContext Digestが変われば、以前の結果を
現在の成功根拠にしない。

長期証跡が必要な場合は、Gitコミットに紐づくCI結果または明示生成したレポートを使用する。

## 8. Diagnosticコード

EARS-AI構文の診断は`EAI-*`、Context Resolutionは`CTX-*`、SPECファイル契約は次を使用する。

| コード | severity | result status | 条件 |
|---|---|---|---|
| `SPEC-CONFIG-SCHEMA-001` | error | `error` / `blocked` | `bitz.yaml`の構文・型・必須項目不正は`error`、形式が正しい未対応majorは`blocked` |
| `SPEC-FILE-NAME-001` | error | `failed` | ファイル名のIDとFrontmatter IDが不一致 |
| `SPEC-FM-REQUIRED-001` | error | `failed` | Frontmatter必須項目がない |
| `SPEC-REQ-STATEMENT-001` | error | `failed` | `approved` REQに妥当なEARS-AI規範文がない |
| `SPEC-ID-DUPLICATE-001` | error | `failed` | 文書IDまたは規範文IDが重複 |
| `SPEC-RELATION-LEGACY-001` | error | `failed` | 意味が曖昧な旧`refs`を使用 |
| `SPEC-RELATION-MISSING-001` | error | `failed` | 強い関係のIDを解決できない |
| `SPEC-PATH-INVALID-001` | error / warning | `failed` / `passed_with_warnings` | パスが不在、ルート外、または許可されない形式。`draft`の未作成予定だけwarning |
| `SPEC-TEST-COVERAGE-001` | error | `failed` | テスト対応の対象規範文が不正または不足 |
| `SPEC-VERIFY-BLOCKED-001` | error | `blocked` | テストまたは検証コマンドが不足 |
| `SPEC-VERIFY-BLOCKED-002` | error / warning | `blocked` / `passed_with_warnings` | 引数なしverifyの対象が0件。`--all-workspaces`のmember単位はwarning、単一workspaceと連合全体が0件の場合はerror |
| `SPEC-VERIFY-COMMAND-001` | error | `error` | 検証commandを起動できない、またはsignalにより通常終了しない |
| `SPEC-VERIFY-TIMEOUT-001` | error | `error` | 検証commandが実効timeout内に終了しない |
| `SPEC-REPORT-WRITE-001` | error | `error` | 明示または自動レポートを安全に作成できない |
| `SPEC-SAFETY-APPROVED-001` | error | `failed` | 承認状態を戻さず要求の意味または強い関係を変更 |
| `SPEC-STATE-TRANSITION-001` | error | `failed` | Git基準版から現在値への文書status遷移が許可されない |
| `SPEC-TASK-BOUNDARY-001` | error | `failed` | 明示TASKの`changes`外に変更がある |
| `SPEC-TASK-BOUNDARY-002` | error | `blocked` | Git不在により明示TASKの変更境界を検査できない |
| `SPEC-IMPACT-OUTDATED-001` | warning | `passed_with_warnings` | 強い依存先変更により再確認が必要な可能性がある |
| `SPEC-STYLE-H1-001` | error | `failed` | H1が不在、複数、またはFrontmatterと不一致 |
| `SPEC-STYLE-SECTION-001` | error | `failed` | 必須H2がない |
| `SPEC-STYLE-SECTION-002` | error | `failed` | H2が未定義、または定義順に反する |
| `SPEC-STYLE-PLACEMENT-001` | error | `failed` | EARS-AI規範文が許可セクション外にある |
| `SPEC-STYLE-PSEUDO-001` | warning | `passed_with_warnings` | 太字ラベルが標準セクションを代替する |
| `SPEC-STYLE-EMPTY-001` | warning | `passed_with_warnings` | 空の任意セクションがある |
| `SPEC-STYLE-HISTORY-001` | error | `failed` | `Revision History`が最終H2でない、表の列が不正、または履歴行がない |

Diagnosticの共通フィールドと終了コードは
[共通アーキテクチャ](../../02.設計書/01_共通アーキテクチャ.md)を使用する。同じ原因に対して
ファイル単位と規範文単位の診断を重複して出さない。OWNERとコード形式は
[ADR-011](../../02.設計書/10_決定記録/ADR-011_Diagnostic所有者とコード命名規約.md)を正とする。
severityとresult statusの分離は
[ADR-021](../../02.設計書/10_決定記録/ADR-021_Diagnostic-severity・操作status・source-Schemaの分離.md)に従う。
各Diagnosticインスタンスの`resultStatus`、file sourceの`workspaceId`、集約順序は
[ADR-027](../../02.設計書/10_決定記録/ADR-027_Diagnostic結果効果・集約・workspace-sourceの確定.md)に従う。
モノレポの`SPEC-ID-DUPLICATE-001`は同一workspace内の重複へ適用し、別workspaceの同じローカルIDは
正常とする。workspace、横断参照、所有境界の診断は[モノレポSPEC連合仕様](12_モノレポSPEC連合仕様.md) §10を使用する。
