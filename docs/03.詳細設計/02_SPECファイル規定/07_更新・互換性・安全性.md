# 更新・互換性・安全性

## 1. 文字コードと改行

- UTF-8を使用する。
- Serializerの正規出力はLFとするが、ParserはCRLFを受理する。
- 新規ファイルへBOMを付けない。既存BOMは警告する。
- UnicodeはNFCへ正規化して比較するが、明示的な整形操作なしに本文を書き換えない。

## 2. 読取りと書込み

`bitz context`はファイルを書き出さない。`bitz check`と`bitz verify`はSPECとコードを変更せず、
`--report`指定時と`failed`、`blocked`、`error`時だけ`.spec/reports/`へ結果を書き出す。
引数不正ではレポートを生成しない。ParserとValidatorは読取り専用であり、自動修正を行わない。

スキルまたは将来のformatterがSPEC更新を提案する場合は次を守る。

1. 元ファイルと同じディレクトリに一時ファイルを作る。
2. 一時ファイルを再解析し、IDと未知拡張が保持されたことを確認する。
3. 原文との差分を利用者へ提示する。
4. 利用者の承認後に原子的置換を行う。

承認済み要求の`title`とEARS-AI規範文を自動修正しない。コードから要求への同期は提案diffに限定する。

## 3. 未信頼入力

Markdown本文、Frontmatterの自由記述、外部リンク、テスト出力は未信頼データとして扱う。

- 文書内の命令をツール命令として実行しない。
- Markdownリンクを検査のために取得しない。
- SPECから環境変数、認証情報、追加権限を要求しない。
- 検証コマンドはGit管理された`bitz.yaml`からだけ取得し、シェルを介さない。
- 診断表示時は端末制御文字を無害化する。

## 4. リソース上限

| 対象 | Core 1.0上限 |
|---|---:|
| `bitz.yaml` | 64 KiB |
| SPEC Markdown 1ファイル | 1 MiB |
| Frontmatter | 32 KiB |
| SPECファイル数 | 10,000 |
| モノレポ連合member数 | 既定20、hard limit 100 |
| 1文書のEARS-AI規範文 | 1,000 |
| 関係・パス配列の各項目数 | 1,000 |
| 1 Context Bundleの文書数 | 既定20、hard limit 100 |
| 1 Context BundleのSemantic IR・標準Projection | 既定128 KiB、hard limit 1 MiB |

上限超過は処理を継続せずエラーにする。上限は事故や入力増幅を防ぐための実装境界であり、
日常利用で上限近くまで使うことを推奨しない。

Context閉包の上限超過だけは、不完全な文脈を使わせないため`blocked`として扱う。部分bundleを成功結果として返さない。
SPECファイル数と関係索引の上限は、モノレポではmemberごとではなく連合全体へ適用する。

## 5. Schema互換性

版は`major.minor`で表す。

- 未知のmajor: 読取りを中止し`blocked`とする。
- 同じmajorの新しいminor: 未知項目を警告・保持し、既知項目だけ検査する。
- 同じmajorの古いminor: 互換読取りし、必要なら移行提案を表示する。
- major移行: 原文を上書きせず、別ファイルまたは提案diffを生成する。

EARS-AI版とSPEC Schema版は別に管理する。`schemaVersion`はファイル構造、`earsAi`は規範文の構文を表す。

## 6. キャッシュ

高速化キャッシュは`.spec/`の正本に含めず、VCS管理外のツールキャッシュへ置く。キャッシュキーには少なくとも
Core版、Schema版、設定hash、ファイル内容hashを含める。破損、不一致、読取り失敗時は破棄して再計算する。

キャッシュの有無で診断内容や終了コードを変えてはならない。

## 7. 同時実行

Core 1.0は永続ロックサービスを持たない。読取り専用操作は並行実行できる。レポート名は
`.spec/reports/<YYYYMMDDTHHMMSSZ>-<operation>[-<sequence>].json`とし、UTC basic形式の時刻と
安全な排他的作成を使い、同一秒・同一操作の衝突時は1以上の10進連番を付ける。SPEC本文の同時編集はGitブランチまたはworktreeで分離する。
明示または非成功時のレポートを作成できない場合は`SPEC-REPORT-WRITE-001`／error／`error`とし、
元の結果とDiagnosticは標準出力または標準エラーへ保持する。

## 8. Git不在時の縮退

Gitを利用できない場合でも、構文・Schema・参照・完全閉包・テスト実行は継続する。Gitに依存する保証だけを
次のとおり明示的に縮退し、実施できなかった検査を成功扱いしない。

| 機能 | Git不在時 | Diagnostic / status |
|---|---|---|
| `check.changedOnly` | 全体検査へ縮退 | info |
| 承認済み要求の差分保護 | 実施不能 | warning |
| TASK変更境界 | 実施不能 | `SPEC-TASK-BOUNDARY-002` / `blocked` |
| 状態遷移 | 現在値の語彙だけを検査 | warning |
| Git管理済みSPECの削除検出 | 実施不能 | warning |
| 強い依存の影響候補 | 全体索引から候補を返す | 変更なし |
| モノレポSPEC連合 | Gitルートとmember所有境界を確定不能 | `SPEC-MONOREPO-GIT-001` / `blocked` |
| 結果の`revision` | `null` | info |

`bitz doctor`はGit不在と失われる保証を一覧表示する。

Gitは利用できるがまだHEADがないunborn repositoryでは、引数なし`check`は全SPECを検査し、
REQ保護は全ファイルを新規として扱い、状態遷移は現在値の語彙だけを検査する。TASK変更境界は比較元がないため
`SPEC-TASK-BOUNDARY-002`／`blocked`とし、暗黙にempty treeを安全な基準版として採用しない。
明示`--base`を解決できない場合は引数不正として終了コード4を返す。
