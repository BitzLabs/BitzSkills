# SPECファイル規定 1.0

## 1. 目的

本規定は、`.spec/`に置くファイルの配置、名前、Frontmatter、参照、検証、安全な更新方法を定める。
対象は個人から数人のチームであり、仕様管理基盤そのものを運用対象にしない。

SPECは人間とAIが共有する小さな契約面である。要求の正本はMarkdown、プロジェクト設定の正本は
`.spec/bitz.yaml`とし、チャット履歴、生成AST、キャッシュ、通常実行のログは正本にしない。

## 2. Core 1.0の設計原則

1. EARS-AI要求を最優先の成果物とする。
2. 人間がGit diffで読めるMarkdownとYAMLだけを正本にする。
3. 必須項目を少なくし、同じ事実を複数ファイルへ複製しない。
4. `bitz check`は読取り専用とし、成功時に生成物を残さない。
5. SPEC本文を未信頼データとして扱い、本文からコマンドや権限を取得しない。
6. 検証結果は実行ごとの事実であり、要求文書の永続状態と混同しない。
7. 未知の将来拡張は保持するが、Coreの判定へ暗黙に影響させない。

## 3. 規範性

本ディレクトリの文書はSPECファイル形式の規範である。EARS-AI規範文の字句・構文・ASTについては
[EARS-AI規格](../01_EARS-AI規格/README.md)を正とし、本規定では重複定義しない。

矛盾した場合の優先順位は次のとおりとする。

1. EARS-AIの字句・構文・AST: EARS-AI規格
2. ファイル配置、Frontmatter、参照、検証: 本規定
3. 全体方針と非機能要件: [設計書](../../02.設計書/README.md)

## 5. Core 1.0の非目標

- 要求管理サーバーや外部承認サービス
- 永続run、ロック台帳、イベントストア
- 文書間の任意DAGを使ったワークフローエンジン
- シンボル単位の実装トレース
- AIによる意味的承認や自動的な要求本文の書換え
- DOCX、PDF、データベースを正本とする運用
- 複数Gitリポジトリ、Git submodule、ネットワーク越しのSPEC連合
