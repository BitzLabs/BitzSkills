# ガバナンス

## 貢献・変更プロセス

- 変更は「提案→合意→実装→閉じ戻し（promotion gate）」の流れに従う。エージェントは
  `docs/` へ書き込まず、`.spec/` に契約・状態を書く。フィーチャ完了時のみ、
  `.spec/STATE.md` の恒久的な学びを `docs/05_リリース・運用/教訓.md` とADRへ
  **人間承認で昇格** させる（`docs/_conventions.md`）。
- ADRを要する変更の基準: 分岐点となる設計判断、後戻りしにくい構造変更、
  公開契約（3マニフェスト・スキルI/F・`.spec/requirements/`）に触れる変更。
- 新しいプラグインの追加、スキルの追加・変更は `AGENTS.md` の定型手順
  （3マニフェスト作成 → `SKILL.md` 追加 → `marketplace.json` 登録 →
  `scripts/release_check.py` 検証）に従う。
- 危険操作の禁止・事前確認・検証義務は `AGENTS.md` のガードレール節が正で、
  `.claude/settings.json` の permissions と各プラグイン同梱フックが機械的に強制する。
  緩めるときは両方を見直す。

## バージョニング方針

- 文書（`docs/`配下）は `changeImpact` に応じたsemver bumpを行う
  （low→patch、medium→minor、high→major。`docs/_conventions.md` 参照）。
- パッケージ（プラグイン）は `python3 scripts/bump_version.py <plugin名> [major|minor|patch]`
  で3マニフェストを同時に更新する。スキルの内容を変更したら、そのスキルのversionと
  所属プラグインのversionの両方をbumpする。
- リリース周期は定期スケジュールを持たず、1 PR = 1関心事の随時リリース
  （squash merge、PRタイトル = マージコミットタイトル、Conventional Commits準拠）。

## ロードマップの意図

- 直近の重点は、Discovery Gateで条件付きGoとされたH-D2・H-D3・H-F1・H-V1の
  継続追跡（`.spec/discovery/assumptions.md`）と、実利用プロジェクトが増えた際の
  成功指標・プロファイルの再評価。理由: Feasibilityは既存6プラグイン・3マニフェスト・
  release checkで部分支持されているが、実利用データと組織受容はまだ検証段階のため。
- 意図的に後回しにしていること: OS/コンテナ/IDE本体/言語ランタイムのプロビジョニング、
  標準プロファイルの一括導入コマンド、複数AIプラットフォームの機能差の完全な隠蔽
  （`docs/00_はじめに/対象外.md` の「Won't」と対応）。
- 実行可能なマイルストーン・進捗は `.spec/`（ROADMAP・STATE）が正。ここは順序づけの理由のみ。
