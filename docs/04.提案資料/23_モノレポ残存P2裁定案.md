# モノレポ残存P2裁定案

- 状態: Accepted（ADR-043と正本へ反映済み）
- 作成日: 2026-09-03
- 対象: `FED-CTX-003`、`FED-CLI-004`、`FED-SEC-004`、`FED-MIG-005`、
  `FED-IMP-004`、`FED-IMP-005`
- 前提: [ADR-041](../02.設計書/10_決定記録/ADR-041_verify対象別証跡とreport明示保存の分離.md)、
  [ADR-042](../02.設計書/10_決定記録/ADR-042_モノレポ連合のidentity・所有境界・公開契約を確定する.md)

## 1. 目的

モノレポCore 1.0横断レビューで残ったP2 6件を、実装受入試験までに判定できる契約へ落とす。
P1で確定した公開Schema、global preflight、canonical所有境界、resource上限、性能fixtureは変更せず、
次の不足だけを閉じる。

1. 同じ横断参照失敗へ複数のDiagnosticを返さない優先順位
2. workspace非成功後に継続または遮断する処理単位
3. TASK directory prefixとsymlinkを組み合わせた境界比較
4. 連合結果consumerの切替とrollback
5. hard limit付近の計算量とmemory受入条件
6. status、終了コード、Diagnostic、reportを固定する適合matrix

本資料を裁定入力とし、採用結果をADR-043と`docs/02.設計書`、`docs/03.詳細設計`へ反映した。

## 2. 結論

6件はCore 1.0へ追加機能を持ち込まず、既存契約の優先順位、処理単位、受入条件を固定することで解消できる。
一括採用を推奨する。

| ID | 推奨裁定 | 主な反映先 |
|---|---|---|
| `FED-CTX-003` | qualifier、workspace、target、型の順で1 edge 1 Diagnosticにする | 関係モデル、Context、連合仕様、共通結果 |
| `FED-CLI-004` | global preflightだけ全停止し、その後は文書・target・binding依存閉包で継続する | 連合仕様、check、verify、doctor |
| `FED-SEC-004` | TASK境界の許可判定は字句path、所有判定はbase/current双方のcanonical pathで行う | 関係モデル、check、安全な入出力 |
| `FED-MIG-005` | consumerを先にdual-read化し、移行単位とrollback単位を一致させる | 運用手順、共通結果、実装計画 |
| `FED-IMP-004` | 索引memoryを入力graphへ線形、target一時memoryを最大閉包へ線形に制限する | 連合仕様、品質属性、実装計画 |
| `FED-IMP-005` | version管理fixtureと期待JSON matrixをCore 1.0受入gateにする | 実装計画、各操作仕様 |

Diagnostic整理では、未リリースの初回1.0であることを利用して
`CTX-RELATION-MISSING-001`を公開結果から除き、欠落targetを`SPEC-RELATION-MISSING-001`へ統一する。
既に公開されたcodeの意味変更や移行互換は発生しない。

## 3. A. Diagnostic所有者と優先順位

### 3.1 1 edge 1 primary Diagnostic

関係edgeは次の順に検査し、最初に成立した1つだけをprimary Diagnosticとして返す。先行段階で構造を
解釈できなければ、後続の参照・型Diagnosticを追加しない。

| 順序 | 条件 | Diagnostic |
|---:|---|---|
| 1 | Frontmatter、`relations`、値の構文または型が不正 | その構文・Schema所有code |
| 2 | 修飾IDの字句が不正 | `SPEC-MONOREPO-REF-001` |
| 3 | 非修飾targetがsource workspaceに不在だが、別workspaceに同じlocal IDが存在する | `SPEC-MONOREPO-REF-001` |
| 4 | 修飾されたworkspace IDがcatalogに存在しない | `SPEC-MONOREPO-REF-001` |
| 5 | workspaceは存在するがtarget local IDが存在しない | `SPEC-RELATION-MISSING-001` |
| 6 | targetは存在するがrelationで許可されない文書種別・statement種別である | `CTX-RELATION-TYPE-001` |

非修飾targetがsource workspaceにも他workspaceにも存在しない場合は、横断参照の意図を推測せず
`SPEC-RELATION-MISSING-001`とする。source workspaceに同じlocal IDが存在する場合は常にそのlocal targetへ解決し、
別workspaceの同名IDを候補にもDiagnosticにも含めない。

CLI引数として渡した起点IDが不在なら、edgeの欠落ではないため`CTX-ROOT-MISSING-001`を維持する。
設定または文書を読めないためtarget索引を構成できない場合も、読込み・構文Diagnosticを根本原因とし、
同じfileに対する関係欠落を派生生成しない。

### 3.2 code整理

- `SPEC-MONOREPO-REF-001`の「targetを解決不能」を、修飾構文、非修飾横断参照、未知workspaceに限定する。
- `SPEC-RELATION-MISSING-001`を単一workspaceと連合に共通する「存在するworkspace内のstrong target不在」とする。
- `CTX-RELATION-MISSING-001`はCore 1.0の公開結果で使用せず、予約済みcodeとして移行表に残す。
- `CTX-RELATION-TYPE-001`は、存在を確認できたsource／target間の型不適合だけに使う。

Diagnosticの並び順は既存のsource順を変えない。優先順位は「どれを生成するか」であり、表示のsort keyではない。

### 3.3 受入条件

- 未知workspaceと、その中のtarget不在を同時に返さない。
- 存在するworkspaceのtarget不在へ`SPEC-MONOREPO-REF-001`を返さない。
- 構文不正fieldから推測したrelation missingを返さない。
- `context`、`check`、`verify`で同じedgeのprimary codeが一致する。

## 4. B. 非成功後の継続規則

### 4.1 全停止境界

ADR-042でglobal preflightとした次の不適合だけは、全workspaceの文書処理、Context解決、command実行を開始せず、
`workspaces: []`で停止する。

- federation rootとcatalogの構文・型・identity
- member ID、path、設定対応、nested federation
- Git repository、worktree、submoduleとGit既知未登録設定
- 未対応Schema／EARS-AI major
- 連合resource hard limit

これは安全な処理順を構成できない失敗であり、通常のworkspace非成功とは区別する。

### 4.2 継続判定の単位

preflight通過後は、workspace全体の静的な成功／失敗だけで継続可否を決めない。次を処理単位とする。

| 操作 | 独立して継続する単位 | 依存として遮断する条件 |
|---|---|---|
| check | 文書と、その文書をsourceとするedge | 必要なtargetを解釈できない、または所有境界を確定できない |
| context | request targetごとのstrong relation閉包 | 閉包内文書が不適合、欠落、適用不能、上限超過 |
| verify | targetごとのContextとbinding | Context非成功、または必要bindingを安全に構成不能 |
| doctor | 前提を共有しないcheck項目 | 先行checkの出力がないと判定不能 |

`requires`、`refines`、`addresses`、`supersedes`と、verify targetが参照するbinding ownerを依存とする。
`related`は継続を遮断しない。`tests[].covers`は宣言の妥当性を検査するedgeだが、別targetのcommand実行を
遮断する依存にはしない。

あるworkspaceの1文書がfailedでも、別workspaceの無関係な文書、target、bindingはworkspace処理順に継続する。
一方、非成功文書をstrong閉包に必要とするtargetは、完全なContextを作れないため継続対象にしない。

### 4.3 操作別アルゴリズム

checkは全workspaceの読取り可能な文書を処理し、source edgeごとに根本Diagnosticを所有させる。別workspaceの
非成功だけを理由に、依存しない文書検査を省略しない。

verifyは既存方針どおり次の2段階にする。

1. 全targetのContextを解決し、通過targetだけからbinding和集合を作る。
2. bindingをowner workspace順、command名順にすべて実行する。

1つのcommandがfailed／errorでも後続の独立bindingを実行する。command結果は、それを参照する全targetとowner
workspaceのstatusへ反映するが、参照しないtargetへ波及させない。Context非成功targetだけが要求するbindingは実行しない。

doctorは先行checkが非成功でも、入力を必要としない後続checkを続ける。例えば設定をparseできなくてもCore、plugin、
Gitの検査は保持できるが、その設定にあるcommand／cwd検査は実行しない。

### 4.4 派生遮断Diagnostic

根本原因を持つunitとは別のtargetまたはdoctor checkが、依存出力を得られないため実行不能になった場合だけ、
`SPEC-MONOREPO-DEPENDENCY-001`／`blocked`を追加する。`evidence`は次を持つ。

```json
{
  "stage": "context",
  "dependencyWorkspaces": ["api"],
  "dependencySpecRefs": ["api::TECH-010"]
}
```

配列は重複なし辞書順とする。既に同じunitへmissing、type、state、coverageなど具体的Diagnosticがある場合は、
同義の`SPEC-MONOREPO-DEPENDENCY-001`を重ねない。`source`は遮断されたtargetの所有SPEC、doctorでは判定不能な
workspaceの設定とし、根本原因fileは`evidence`だけから参照する。workspace statusは処理したunit、派生遮断、
所有command、workspace Diagnosticを既存の最悪値順で集約する。

## 5. C. TASK directory境界

### 5.1 許可集合と所有集合を分ける

TASK `changes`は、変更を許可する**字句Git path集合**を表す。symlink解決後の実path集合やglobではない。

- file entryは正規化後のpathと完全一致する変更だけを許可する。
- 末尾`/`のdirectory prefixは、同じpath segment列をprefixに持つ子孫fileを許可する。
- `src/`は`src/a.ts`を許可するが、`src2/a.ts`、`alias/a.ts`を許可しない。
- directory prefix自身と変更pathはUnicode NFC、`/` separator、filesystemのcase比較keyを用いる。
- trailing `/`は再帰許可を示す型印であり、`*`や任意の文字列prefixとして扱わない。

許可集合との比較とは別に、宣言pathと変更pathの双方へADR-042のcanonical所有判定を適用する。
所有境界不適合を先に`SPEC-MONOREPO-OWNERSHIP-001`とし、安全なpathだけをTASK境界と比較する。

### 5.2 symlink

symlink entry自体の変更は、そのentryがある字句Git pathのfile変更として扱う。directory prefixは配下にある
symlink entryの変更を許可できるが、symlink解決先の別の字句pathへ許可を拡張しない。

例えば`src/link -> ../generated`が同じworkspace内にあっても、`changes: [src/]`は`src/link` entryの変更を
許可するだけで、`generated/file.ts`の変更を許可しない。後者には`generated/`を別途宣言する。

追加pathはcurrent、削除pathはbase、変更pathとsymlink entry変更はbase/current双方で所有境界を検査する。
renameはsourceの削除とdestinationの追加として2 pathを比較する。base treeのsymlinkはGit treeに記録された
modeとlink target、currentは`lstat`結果から解決し、repository外、別workspace、member `.spec/`へ至るものを拒否する。
symlink loop、解決不能、途中の別repository境界も所有境界不適合とする。

TASK自身のfileと明示生成reportを比較対象から除く既存規則は維持し、その除外後の変更集合へ上記を適用する。

### 5.3 受入条件

- `src/`と`src2/`を区別する。
- 同一workspace内symlink entryの変更と、解決先fileの変更を別pathとして判定する。
- baseでは安全、currentでは別memberを指すよう変更したsymlinkを所有境界違反にする。
- deleted pathとrename sourceをbase側で検査する。
- 所有境界違反とTASK境界外を同じpathへ重複して返さない。

## 6. D. consumer移行とrollback

### 6.1 結果の識別

JSON consumerは最初に`schemaVersion` majorを検査し、その後に次の排他的外形で単一／連合を識別する。

| 外形 | 判定 |
|---|---|
| `workspace`あり、`federation`／`workspaces`なし | workspace単独結果 |
| `workspace`なし、`federation`と`workspaces`あり | 連合全体結果 |
| 両方ある、または必要fieldが両方ない | consumer側Schema error |

修飾IDの`::`、report file名、current directoryから結果種別を推測しない。連合操作を有効にするadapter／CIは、
事前のdoctorまたはCore API handshakeで`monorepo.v1`を確認する。check／verify結果そのものへCapabilityを複製しない。

### 6.2 切替順序

連合化は次の順序で行う。

1. 全consumerを単一／連合のdual-readへ更新し、旧単一fixtureと新連合fixtureの両方を通す。
2. CIへ新Coreと`monorepo.v1`確認を導入するが、まだ単一操作を維持する。
3. ADR-042の原子的変更集合としてcatalog、member設定、修飾参照、CI全体操作を切り替える。
4. `doctor --all-workspaces`、`check --all-workspaces`、`verify --all-workspaces`を実行する。
5. 明示`--report`を使うjobだけ連合reportの保存・artifact収集へ切り替える。

Coreは過去reportを入力にしない。旧単一reportは履歴artifactとして読取り専用で保持できるが、連合reportの
workspace件数、status、時系列集約へ混ぜない。同じ`schemaVersion: "1.0"`でも上記の排他的外形で区別する。

### 6.3 rollback単位

rollback可能なのは、連合化変更とその後の変更を安全に分離できる間だけである。次を同じrollback releaseへ含める。

- root catalogと全member設定
- 修飾した関係、coverage、TASK参照
- CIの`--all-workspaces`呼出しとCapability gate
- report収集、annotation、dashboardなどproducer依存consumer
- 連合化に伴うroot ID写像後の参照

consumerのdual-read対応は残してよいが、producerだけを単一形式へ戻して混在結果を1回の集約へ入れない。
過去の連合reportを単一形式へ書き換えず、rollback時点でartifact系列を分ける。

rollback後は単一workspaceの`doctor`、`check --full`、`verify`を実行する。連合化後に追加された横断要求、member固有SPEC、
code変更を失わずに上記一式を戻せない場合、Core 1.0は自動down migrationを行わず、rollbackではなく連合状態の
forward fixを選ぶ。

### 6.4 受入条件

- dual-read consumerが単一結果と連合結果を排他的に識別する。
- 両外形を混ぜた結果を拒否する。
- 旧reportを現在の連合集約へ混ぜない。
- migration commitのrevert fixtureで単一操作へ戻り、修飾参照が残らない。
- 部分rollback fixtureを成功扱いしない。

## 7. E. 計算量とmemory

### 7.1 記号

| 記号 | 内容 |
|---|---|
| `B` | 設定とSPEC Markdownのraw byte合計 |
| `F` | SPEC file数 |
| `S` | statement数 |
| `E` | relation edge数 |
| `T` | trace entry数 |
| `C` | command定義数 |
| `Q` | verify target数 |
| `V` | verify計画の重複排除後binding数 |
| `Dq`、`Eq`、`Tq` | target `q`のContext閉包に含まれる文書、edge、trace数 |
| `Bw` | 完全検査中の1 workspaceで同時に保持する本文byte数 |
| `Bq` | target `q`のContext閉包に含まれる本文byte数 |
| `R` | 公開結果へ保持するtarget、statement、binding参照の合計数 |

### 7.2 受入れる上界

- catalog discoveryと上限計数は`O(B + F)`時間とし、可能なdimensionは完全parse前に打ち切る。
- global Frontmatter／関係索引は`O(B + F + S + E + T + C)`時間、`O(F + S + E + T + C)`memoryとする。
  全file本文を索引の一部として同時保持しない。
- 1 targetのContext解決はvisited集合を使い、到達部分graphに対して`O(Bq + Dq + Eq + Tq)`時間・memoryとする。
- 全体verifyのContext解決時間は`O(Σq(Bq + Dq + Eq + Tq))`を許容する。異なるtargetの意味閉包を同一と推定して
  省略することは要求しない。
- 全体verifyの一時memoryはglobal索引、最大1 target閉包、binding集合、公開結果に対して
  `O(F + S + E + T + C + max(Bw, maxq(Bq + Dq + Eq + Tq)) + V + R)`とする。
- targetごとの完全Bundle本文を全target分同時保持しない。Digest、statement、binding参照へ縮約後、次targetへ進む。
- 決定論的出力のsortは要素数`K`ごとに`O(K log K)`を許容するが、workspaceまたは文書の全組合せmatrixを作らない。
- commandの実行時間とtest runner自身のmemoryはCoreの計算量から除き、Coreが保持するstdout／stderrは既存上限を守る。

これらは公開結果を減らすための近似を許す規則ではない。完全性と決定論を維持したうえで、不要な全組合せと
全Context同時保持を禁止する実装制約である。

### 7.3 hard-limit受入

各resource dimensionは、他dimensionを通常規模に保った独立fixtureで`limit - 1`、`limit`、`limit + 1`を検査する。
全dimensionの最大値を1つのfixtureへ同時投入することは要求しない。

- `limit - 1`と`limit`は当該dimensionだけを理由に遮断しない。
- `limit + 1`は`SPEC-MONOREPO-LIMIT-001`／blocked、command未実行、部分workspace結果なしとする。
- `observedAtLeast`を返した時点で追加読込みを停止でき、正確な総数を求めない。
- 基準環境の最大dimension fixtureで、Core peak RSS増分を1 GiB以下とする。
- 同fixtureを2 GiB memory limitのprocess／containerで正常終了させ、OSのOOM killを許さない。

1 GiBは通常fixtureの200 MiB目標を緩和しない。hard limitが敵対的入力への安全境界として機能するかを確認する
受入上限であり、すべての利用環境へ同じRSSを保証する公開SLOではない。

## 8. F. 適合fixtureと期待matrix

### 8.1 配置と比較方法

実装repositoryに次をversion管理する。

```text
fixtures/conformance/monorepo/<fixture-id>/repo/...
fixtures/conformance/monorepo/<fixture-id>/manifest.json
fixtures/conformance/monorepo/<fixture-id>/expected/<operation>.json
```

manifestは実行directory、argv、環境前提、Git base/current、期待終了コード、report指定有無、正規化対象fieldを持つ。
期待JSONは`durationMs`、生成時刻、実行環境依存のprocess出力を比較対象外にし、それ以外のfield、配列順、nullと空配列を
構造比較する。除外fieldをfixtureごとに任意追加せず、共通normalizerだけを使用する。

### 8.2 最小matrix

| fixture | 主な入力 | operation | status／exit | 必須確認 |
|---|---|---|---|---|
| `MONO-001` | 別workspaceに同じlocal ID | check all | passed／0 | 修飾IDで衝突しない |
| `MONO-002` | 横断`refines`と直接coverage | context、verify | passed／0 | 修飾edge、Digest、coverage |
| `MONO-003` | 非修飾で別workspaceだけにあるtarget | check all | failed／1 | `SPEC-MONOREPO-REF-001`だけ |
| `MONO-004` | 存在workspace内のtarget不在 | context、check | failed／1 | `SPEC-RELATION-MISSING-001`だけ |
| `MONO-005` | 未知`--workspace` | check | 結果なし／4 | stdout結果なし、reportなし |
| `MONO-006` | Git既知の未登録設定 | check all | blocked／2 | `workspaces: []`、commandなし |
| `MONO-007` | member入れ子、submodule、別worktree | doctor all | failed／1 | `SPEC-MONOREPO-PATH-001` |
| `MONO-008` | symlinkで別memberを所有 | check all | failed／1 | ownership code、TASK codeなし |

| `MONO-023` | 単一／連合／混在JSON | consumer test | accept／reject | 排他的外形とdual-read |
| `MONO-024` | migrationと完全／部分rollback | migration test | pass／reject | 原子的切替、部分rollback拒否 |

1つのrepoへ複数の独立原因を混ぜず、同じ行で複数variantを示したfixtureも入力directoryとmanifestを分ける。
各manifestには正確なstatusと終了コードを1つだけ記録する。`MONO-012`ではinvalid文書のowner memberを`failed`、
それを必要とするtargetを`SPEC-MONOREPO-DEPENDENCY-001`／`blocked`、独立targetを通過とし、top-levelは最悪値の
`failed`に固定する。

### 8.3 reportと副作用

全CLI fixtureは実行前後のGit statusとfilesystem manifestを比較する。`--report`なしでは成功・非成功ともfile生成、
既存report更新、cache以外のworkspace書込みを0件とする。`--report`指定時はcheck／verifyだけが指定先に1件を
排他的作成し、引数不正、context、doctorは指定有無にかかわらずreportを作らない。

## 9. 裁定単位と反映案

## 10. 裁定

本案の6項目を一括採用した。これにより新しい公開操作、fail-fast option、migration mode、並列schedulerを追加せず、
残るP2 6件をCore 1.0の既存責務内で閉じられる。

採用後の最終gateは次とする。

- 設計レビュー: P0、P1、P2 Closed
- 実装着手: 可
- Core 1.0受入: version管理されたmatrixと期待JSONの全通過が必要
- 1.0非目標: 自動workspace rename、自動down migration、必須並列化、fail-fast option
