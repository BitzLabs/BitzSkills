# ユースケース・フロー遷移レビューと修正提案

**状態**: **Open（8件未裁定）**

**作成日**: 2026-08-31

## 1. 目的

[ユースケース設計](../02.設計書/09_ユースケース設計.md)の作成にあたり、`docs/02.設計書`と
`docs/03.詳細設計`の利用者フロー、SPEC状態遷移、TASK依存、検証実行を横断して確認した。
本書は、状態遷移matrixの外側に残る不整合と実装分岐を記録し、裁定候補を示す。

現在の正本は`docs/02.設計書`と`docs/03.詳細設計`である。本書の修正例は、裁定と正本反映が完了するまで
実装根拠にしない。

## 2. 結論

REQ/TECH、ADR、TASKの状態遷移matrixは、上位設計、詳細仕様、ADR-024で一致している。
一方、Small FlowとTASK境界、先行TASKの完了条件、verifyの重複排除単位にP1相当の不整合がある。
さらに、変更コードからSPECへの逆引き、Intent起点、Full Flowの戻り先、削除済みID、ADR部分改訂に
実装者が一意に判断できない箇所がある。

## 3. 指摘一覧

| ID | 優先度 | 指摘 | 主な影響 |
|---|:--:|---|---|
| UC-FLOW-001 | P1 | Small Flowの`check`位置とTASK境界検査が接続していない | 境界外変更をDoneまで検出しない |
| UC-FLOW-002 | P1 | `requires`先行TASKが`open`でも後続TASKを停止しない | 未完了の先行作業を飛び越える |
| UC-FLOW-003 | P1 | 単一workspaceと連合でverify重複排除単位が異なる | コマンド実行回数と結果が実装依存になる |
| UC-FLOW-004 | P2 | 変更コード・テストから検査対象SPECへの逆引きが未定義 | コードだけの変更で通常`check`が空になる可能性 |
| UC-FLOW-005 | P2 | Small FlowのIntent起点語彙が一致しない | リファクタリング等の開始方法が不定 |
| UC-FLOW-006 | P2 | Full FlowにDoneとレビュー否決時の戻り先がない | 完了・再作業条件が不定 |
| UC-FLOW-007 | P2 | 削除済みID再利用禁止の履歴範囲が未定義 | commitをまたぐ再利用を検出できない |
| UC-FLOW-008 | P3 | ADRの部分改訂を`related`で表しつつ、READMEは`supersedes`を要求 | accepted ADR間の優先関係が人間依存 |

## 4. 修正提案

### 4.1 UC-FLOW-001: Small Flowの実装後検査

#### 現状

- SDDプロセス設計の図は`Intent -> Context -> Check -> Implement -> Verify -> Done`である。
- 同書は`Check`で変更境界を確認すると説明する。
- 運用設計は編集直後に`bitz check`を実行する。
- ADR-025は、TASK IDまたはTASK pathを明示した`check`だけが`changes`境界を強制すると定める。

#### 問題

実装前の汎用`bitz check`では、新たに生じる変更pathをTASK境界と比較できない。実装後に汎用`check`を
実行しても、TASKを明示しなければ`changes`境界を強制しない。

#### 提案

Small Flowを次へ改訂する。

```text
Intent -> Context -> Pre-check -> Implement -> Post-check -> Verify -> Human Review -> Done
                                     ^             |            |
                                     +-------------+------------+
```

- `Pre-check`はSPECと既存作業ツリーの不適合を確認する。
- `Post-check`は実装後の成果物を確認する。
- TASK起点では`bitz check <TASK-ID>`を必須とし、`changes`境界を検査する。
- test failureは`Implement`へ、仕様矛盾・意味変更は人間確認へ戻す。
- 一時的ツール障害は同じ副作用を増やさない再実行だけを許可する。

#### 主な反映先

- `02.設計書/04_SDDプロセス設計.md`
- `02.設計書/06_運用設計.md`
- `02.設計書/08_実装ロードマップ.md`
- `03.詳細設計/02_SPECファイル規定/05_補助SPEC仕様.md`

#### 受入条件

- TASK起点のfixtureで境界外コード変更が`Post-check`で必ず検出される。
- 実装後に静的検査を行わずDoneへ到達するedgeがない。

### 4.2 UC-FLOW-002: 先行TASKの状態ガード

#### 現状

TASK `requires`は先行TASKを表し、TASK間循環を禁止する。一方、Contextの状態表は`open` TASKをWork、
`done` TASKをHistoryとするだけで、`open`の先行TASKをblocking条件にしていない。

#### 問題

`TASK-B(open) requires TASK-A(open)`でもTASK-Bの`implement`を開始でき、「先行TASK」という意味と一致しない。

#### 提案

- TASKを起点とする`purpose=implement|verify`では、`requires`先TASKがすべて`done`であることを要求する。
- `open`の先行TASKが残る場合は`CTX-TASK-DEPENDENCY-001`／error／`blocked`を返す。
- `interpret`では停止せず、未完了先行TASKをwork dependencyとして表示する。
- 単に関連する作業は`related`とし、`requires`を使わない。

#### 主な反映先

- `03.詳細設計/02_SPECファイル規定/05_補助SPEC仕様.md`
- `03.詳細設計/02_SPECファイル規定/10_Context Resolution仕様.md`
- `03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md`

#### 受入条件

- `open -> open`、`done -> open`の先行TASK fixtureで開始可否が一意になる。
- 循環検査と状態ガードを別Diagnosticで識別できる。

### 4.3 UC-FLOW-003: verify実行bindingの統一

#### 現状

- ADR-018はテストpathの重複排除を`argv`と`cwd`の組で行う。
- `{tests}`がないコマンドは設定argvを1回だけ実行する。
- 連合仕様は実行済み判定を`(workspace-id, command, test-path)`とする。

#### 問題

同一command bindingに複数test pathがある場合、単一workspaceでは1回、連合ではpathごとに複数回と
解釈できる。command名が異なるが`argv`と`cwd`が同じ場合も、ADR-018と連合キーで結果が異なる。

#### 提案

1. command bindingの正規識別子を`(workspaceId, normalized argv template, normalized cwd)`とする。
2. 同じbindingへ属するtest pathをworkspace相対pathで重複排除し、辞書順にする。
3. `{tests}`ありは、重複排除後の全pathを1回展開してbindingを1回実行する。
4. `{tests}`なしは、test path数にかかわらずbindingを1回実行する。
5. 実効timeoutは実行結果に保持するが、bindingの同一性は設定timeoutを含むContext Digestで保護する。
6. 単一workspace、引数なしverify、連合全体verifyで同じ規則を使用する。

#### 主な反映先

- `03.詳細設計/02_SPECファイル規定/02_bitz.yaml仕様.md`
- `03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md`
- `03.詳細設計/02_SPECファイル規定/12_モノレポSPEC連合仕様.md`
- `02.設計書/10_決定記録/ADR-018_*`の後継ADRまたは明示的な裁定記録

#### 受入条件

- 同一binding・複数path、別名同一binding、同名別workspace、`{tests}`なしの実行回数fixtureを持つ。
- 単一workspaceと連合で、同じ所有workspaceの実行回数が一致する。

### 4.4 UC-FLOW-004: 変更コード・テストからSPECへの逆引き

#### 現状

`check`はGit変更集合を起点にする一方、詳細な通常実行の記述は変更SPEC、その強い依存、直接逆参照を
主語としており、変更コード・テストをどのSPECへ正規化するか定義していない。上位設計の`outdated`説明は
実装変更の影響候補を含む。

#### 提案

- 変更SPEC pathは所有文書へ正規化する。
- 変更code pathは`implements`の逆索引から所有REQ/TECHを選択する。
- 変更test pathは`tests[].path`の逆索引から所有REQ/TECHを選択する。
- 選択した文書の強い依存閉包と直接逆参照を検査する。
- 未所有のcode/test pathをwarningにするか対象外にするかを、性能測定と運用意図に基づき裁定する。
- 実装変更を`outdated`候補に含めない場合は、上位設計の状態説明から「実装変更」を削除する。

#### 主な反映先

- `02.設計書/01_共通アーキテクチャ.md`
- `02.設計書/02_specディレクトリ仕様.md`
- `02.設計書/05_QA品質保証設計.md`
- `03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md`

### 4.5 UC-FLOW-005: Small FlowのIntent起点

#### 現状

Small FlowのIntentはREQまたはEARS-AI規範文を要求するが、プリフライトは「対象REQまたは意図」とする。
`bitz context`は生の意図文字列を起点にせず、SPECまたは規範文IDを要求する。

#### 提案

- Small Flowの機械起点をREQ、TECH、規範文、open TASKのいずれかに限定する。
- TASK起点は`addresses`と`requires`から適用要求を解決する。
- 生の意図しかない場合は、実装前にREQ、TECH、TASKのいずれかへ記録する。
- SPECを作るほどでない作業を許す場合は、Core保証外の簡易フローとして明示的に分離する。

### 4.6 UC-FLOW-006: Full Flowの完了と戻り先

#### 現状

Full Flow図は`Human Review`で終了し、`Done`へのedge、Requirement ReviewとDesign Reviewの否決edge、
実装・検証失敗時の戻り先を示していない。

#### 提案

```text
Intent -> Context -> Requirement Review -> Design Review -> Pre-check
   ^          ^              |                  |
   |          +--------------+                  |
   +--------------------------------------------+

Pre-check -> Implement -> Post-check -> Verify -> Human Review -> Done
                ^             |           |             |
                +-------------+-----------+-------------+
```

- Requirement Review否決はIntentまたはREQ改訂へ戻す。
- Design Review否決はContext再取得または設計改訂へ戻す。
- 要求または設定変更後はDigestを再照合する。
- Human Review否決は理由に応じてIntent、Context、Implementのいずれかへ戻す。

### 4.7 UC-FLOW-007: 削除済みID再利用禁止の保証範囲

#### 現状

文書IDと規範文IDは削除後の再利用を禁止し、`EAI-CORE-ID-003`を定義する。一方、通常検査が参照する
履歴範囲は現在値と1つのGit基準版であり、過去に削除・commit済みのIDを探索する規則がない。

#### 提案

次のどちらかを裁定する。

1. **Core保証にする**: 対象branchの到達可能Git履歴からID tombstone索引を構築する範囲、性能上限、
   shallow clone時の縮退を定義する。
2. **レビュー規則にする**: Coreが保証するのは現在集合とGit基準版間の再利用検出までと明記し、
   長期的な再利用禁止はGitレビューの責務とする。

軽量Coreの方針からは2を初期案とし、実際のID再利用事故が確認された場合に履歴索引を再評価する。

### 4.8 UC-FLOW-008: ADR部分改訂の表現

#### 現状

決定記録READMEはDecision変更時に後継ADRの`supersedes`と旧ADRの`superseded`を要求する。
ADR-020は`Amends`、`Clarifies`相当を`related`で表す。ADR-009は公開操作を3つとしたまま`accepted`で、
ADR-010が`context`を追加して4つへ改訂している。

#### 問題

`related`は閲覧用の弱い関係であり、どのDecision項目が後続ADRで変更されたかを機械的に示さない。
accepted ADRだけを読んだ実装者は、物語上の後発順序を知らなければ衝突を解消できない。

#### 提案

- 部分改訂を許すなら、設計資料用の`x-amends`と改訂対象Decision番号を明示する。
- Core共通関係へ追加せず、`docs/02.設計書/10_決定記録`のローカル規約としてよい。
- 部分改訂を許さないなら、現行決定を統合した後継ADRを作り、旧ADRを`superseded`へ変更する。
- README、ADR-020、既存の部分改訂ADRを同じ規則へ移行する。

## 5. 推奨裁定順

1. UC-FLOW-001を裁定し、Small/Full Flowの共通骨格を確定する。
2. UC-FLOW-002でTASK依存の実行可能性を確定する。
3. UC-FLOW-003でverifyの実行回数を確定する。
4. UC-FLOW-004と005で通常変更の起点選択を確定する。
5. UC-FLOW-006を確定済みSmall Flowへ同期する。
6. UC-FLOW-007と008はCore保証範囲と記録規約として個別に裁定する。

P1の3件は機械契約または既存ADRの意味へ影響するため、正本編集前にADR要否を判断する。
