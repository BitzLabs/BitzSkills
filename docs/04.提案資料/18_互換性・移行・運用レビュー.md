# 互換性・移行・運用レビュー

- 状態: P1 Closed / P2 Pending
- 実施日: 2026-09-02
- 基準: branch `bitz_next`、HEAD `0097f2839e15a697cea5a8e4cb413a77562201ab`＋未コミット設計
- 規範文書digest: `b292eed96f8d607c49e380bdb500c10a0c896c2e2c41bea415c4fd14aa38aaba`
- 観点: Schema互換、旧Core、単一workspace移行、ID安定性、段階導入、rollback

## 1. 結論

ADR-040がADR-039のモノレポ延期部分だけを改訂し、Profile、改番、hash等を戻していない点は適切である。
また、単一workspaceを引き続き同じ操作形で扱うため、連合を使わない利用者への機能的な影響は小さい。

ただし、`schemaVersion: "1.0"`の未知fieldをwarningとして無視する旧Coreが既に存在するなら、同じ設定を単一workspaceと
誤解して実行できる。`monorepo.v1` Capabilityは新Coreを選ぶ目印にはなるが、旧Coreが設定を読むこと自体を止めない。
安全性は「まだ1.0を公開していない」というrelease前提、または旧Coreが拒否できるSchema契約のどちらかに依存する。

## 2. 指摘一覧

| ID | 優先度 | 指摘 | 影響 |
|---|---|---|---|
| FED-MIG-001 | P1 | 同じSchema majorで旧Coreが`monorepo`を無視できる | 連合設定を単一workspaceとして誤実行する |
| FED-MIG-002 | P1 | 単一workspaceの固定ID `root`から必須`workspace.id`への移行契約がない | result key、Digest、report参照が一斉に変わる |
| FED-MIG-003 | P1 | root catalogとmember設定の段階導入順序がない | 移行途中が恒常的なfailed／blockedになる |
| FED-MIG-004 | P2 | workspace ID rename・member移動・削除の同一性規則がない | Git基準版比較で削除・新規として誤判定する |
| FED-MIG-005 | P2 | 修飾出力への切替とrollback手順がない | adapter、保存report、CIの互換が不明になる |

## 3. FED-MIG-001 旧Coreとの互換条件

[ADR-040 Decision 7](../02.設計書/10_決定記録/ADR-040_モノレポSPEC連合をCore-1.0へ再導入する.md#decision)は
`monorepo.v1` Capabilityを公開する。しかしCapabilityは実行後の識別情報であり、旧Coreがroot設定の未知`workspace`、
`monorepo`をwarningとして読み飛ばし、root配下全体を単一workspaceとして検査・verifyすることを防げない。

次のいずれかをrelease gateとして明記すべきである。

1. ADR-040はCore 1.0初回公開前の設計変更であり、モノレポ非対応の1.0を配布していない
2. 既配布1.0は`monorepo`存在時に必ず拒否するよう更新され、最低Core版を運用で固定する
3. 連合設定は旧Coreが未知majorとして拒否するSchema versionまたは必須feature markerを使う

1が事実なら破壊的移行ではなく、文書へrelease前提を記録すればよい。既配布版がある場合、Capability確認だけを
安全策にしてはならない。

## 4. FED-MIG-002 単一workspace ID

連合内の機械結果はworkspace IDで修飾され、単一workspaceでID不在時に使っていた固定`root`との関係がない。
既存repositoryを連合化してrootへ`workspace.id: platform`を追加すると、同じ文書でも
`REQ-001`、`root::REQ-001`、`platform::REQ-001`のどれがbase/currentの同一性キーになるか決定できない。

連合化した最初の比較だけ旧固定IDを新root IDへ写像するのか、ID変更を明示的なrenameとして扱うのか、
初回から新しいidentityとして扱うのかを固定する必要がある。Context Digestが変わること、保存reportと外部参照を
再生成することも移行手順へ含めるべきである。

## 5. FED-MIG-003 段階導入

rootへcatalogを先に追加するとmember設定不在でfailedになり、memberへ`workspace.id`を先に追加してもcatalog外
`.spec/`として選択時blockedになり得る。複数PRで安全に移行する契約はなく、現行仕様は実質的に原子的な切替を要求する。

Core 1.0では、次の運用手順を最小契約として記載すれば十分である。

1. migration branch上で全member設定とroot catalogを同じ変更集合へ追加する
2. 新Coreの`doctor --all-workspaces`、`check --all-workspaces`を通す
3. CIの最低Core版とCapability確認を先に更新する
4. 旧単一workspace reportをarchiveし、連合reportを新しい正本にする
5. 失敗時は設定とCIを同じcommit単位で戻す

段階的な不完全catalogをCoreが許容する必要はない。

## 6. FED-MIG-004 ID rename・移動・削除

workspace IDは修飾ID、Context Digest、report path、Git基準版の文書同一性に入るが、不変IDなのかrename可能な表示名なのかが
明記されていない。member path移動とID維持、ID変更とpath維持、catalogからのmember削除では判定が異なる。

Core 1.0ではworkspace IDを永続identityとしてrename非対応にするのが最小である。path移動は同じIDとして許可し、
base/current両catalogからID対応を取る。member削除はそのworkspaceの管理済みSPEC削除規則を適用し、単にcatalogから
消して検査対象外にできないようにする必要がある。

## 7. FED-MIG-005 adapterとrollback

連合化するとmember単独操作でもID、target、Diagnostic `specRefs`が修飾される。既存のJSON consumer、保存report、
CI annotationは単一workspace形式を前提にしている可能性がある。`monorepo.v1`をconsumerが確認する順序、
単一形式と連合形式を同じSchema majorで識別するfield、旧reportを再読込むかどうかを運用契約へ置くべきである。

rollbackは連合設定だけを消すと修飾参照を含むmember文書が読めなくなるため、設定、横断参照、CI、report consumerを
同じrelease単位で戻す必要がある。

## 8. 成立を確認した互換性

- 連合を宣言しない単一workspaceの探索と非修飾出力を維持する。
- 設定を継承せず、member単位の既存Schemaを再利用する。
- ADR-039のcommand名binding、Profile延期、自動改番延期を維持する。
- ADR-017を復活させず、現行構造の正本へ連合差分を置く。
- `monorepo.v1`により新しいconsumerは機能有無を判定できる。

## 9. 判定

初回1.0公開前の変更であればFED-MIG-001の危険はrelease事実の明記で閉じられる。そうでなければ同一majorでの
silent ignoreを許容できない。FED-MIG-001〜003を裁定し、移行fixtureを用意してから連合設定を実運用へ導入する。

## 10. P1裁定（2026-09-03）

Core 1.0が未リリースであることを確認し、`FED-MIG-001`は追加version gateなしで解消した。`FED-MIG-002`と003は
[ADR-042](../02.設計書/10_決定記録/ADR-042_モノレポ連合のidentity・所有境界・公開契約を確定する.md)で採用し、
永続workspace ID、初回`root`写像、原子的連合化を正本へ反映した。rename／移動／削除の同一性も固定したため
`FED-MIG-004`は随伴してClosedとする。P1はClosedとし、consumer rollback詳細`FED-MIG-005`のP2だけを残す。
