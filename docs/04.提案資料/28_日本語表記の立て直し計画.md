# 日本語表記の立て直し計画

- 状態: 実施中（2026-09-27。フェーズ1とパイロットを実施）
- 作成日: 2026-09-27
- 参考: 前回の方針（2026-09-17確定の用語集。コミット`9675ee74`時点の`docs/用語集.md`）。本計画は前回の方針を参考にとどめ、方針そのものを改める

## 1. 背景

2026-09-17に用語集を定め、設計資料とfixtureの記録を書き直した。そのとき「英語をカタカナへ転記するだけの語は英語で書く」
（用語集 §2.1-3、§4.1.4、§4.2）と決め、file、path、command、test、workspace、catalog、field、reviewなど約100語を
英語のまま本文へ残した。その結果、次の問題が生じている。

1. **説明文が読めない。** 1文の中にバッククォートのない英単語が何語も入り、日本語の文として読めない。
   例: 「共通argv解析、重複option、空値、target不存在は…に従う」「単一workspaceでは非修飾IDだけを受け付ける」
2. **識別子と一般語の区別がつかない。** `failed`（値）とfailed（一般語）、`check`（操作名）とcheck（検査）が
   同じ見た目で混ざり、どれが機械の読む値なのかが分からない。
3. **用語の意味を引く場所がない。** 用語集は「表記だけを定め、意味は各仕様が定義する」としたため、
   Context BundleやConstraint Ledgerが何を指すかを一覧で確かめられない。

実測した混在の量を示す（散文の行のうち日本語を含む行で、バッククォートとコードブロックの外にある英単語の数。
表の行を含む。IDとリンク先は除く）。

| 範囲 | ファイル数 | バッククォート外の英単語 | 日本語の文字数 |
|---|---:|---:|---:|
| `docs/03.詳細設計/` | 20 | 8,462 | 42,801 |
| `docs/02.設計書/`（決定記録を除く） | 6 | 1,183 | 7,506 |

path 210、error 184、Git 178、verify 162、target 159、test 136、command 133、Diagnostic 131、field 127。

## 2. 目標と完了基準

### 2.1 目標

1. 説明文を日本語で書く。英語で残すのは、機械が読む識別子と、規格名・製品名・略語だけとする。
2. 本プロジェクト固有の定義語にも日本語の正式名を付け、英語名はユビキタス言語一覧と、その語を定義する文書の初出にだけ併記する。
3. ユビキタス言語一覧を整備し、日本語名、英語名、コード上の識別子、定義、定義元を1か所で引けるようにする。
4. 規範の意味を変えない。書き直しは表現だけとし、条件、数値、識別子、義務の強さを保つ。
5. ファイル名も見出しと同じ規則にそろえる。

### 2.2 完了基準

| 項目 | 基準 |
|---|---|
| 残存英語 | 対象ファイルの散文で、バッククォート外の英単語が許可リスト（規格名・製品名・略語）の語だけになる |
| 識別子の保存 | 書き直しの前後で、バッククォート内の文字列、Diagnostic code、ID、数値、リンク先の集合が失われていない（追加は可） |
| 用語の統一 | ユビキタス言語一覧の「使わない表記」が対象ファイルに現れない |
| リンク | 全Markdownのリンク切れが増えない。2026-09-27の実測は112件（置換済みの旧文書を指す決定記録55件、提案資料52件、検討資料1件、fixtureの記録のアンカー切れ4件）。fixtureの記録の4件はフェーズ8で直す |
| 既存検証 | 監査が終了コード1・`pending` 1件、単体試験が全件成功、Gate A再認定が`Allowed` |
| 独立レビュー | 意味の不変と読みやすさを、作業者と別のレビュー担当が確認し、指摘が解消している |
| 読みやすさ | ユーザーがパイロット文書と各段階の抜き取りを読み、了承している |

## 3. 表記方針の骨子

新しい表記規則の要点を示す。確定版はフェーズ1で`docs/表記規則.md`として書く。

本節は起案時の骨子である。現行の規則は[表記規則](../表記規則.md)、訳語は[用語集](../用語集.md) §13を正とする。
本節の例には、その後に改めた書き方が残っている（「コンテキストバンドル」は「コンテキスト一式」に、
「状態`failed`の診断`X`」は「診断`X`（`failed`）」に、各文書の初出での併記は、その文書が定義する語だけの併記に改めた）。

### 3.1 英語で残すもの

| 区分 | 扱い | 例 |
|---|---|---|
| 識別子 | 英語のまま、必ずバッククォートで囲む | `check`、`failed`、`workspaceId`、`--format`、`.spec/bitz.yaml`、`CTX-ROOT-MISSING-001` |
| 出力に現れる文字列 | 英語のまま、バッククォートで囲む | Markdown提示の節名`Bundle Manifest`、検証プログラムの報告値`Passed` |
| 規格名・製品名・略語 | 英語のまま、バッククォートなし | Git、JSON、YAML、UTF-8、SHA-256、CLI、LLM、CPython、EARS-AI、Core |
| 文書種別の記号 | 英語のまま、バッククォートなし | REQ、TECH、ADR、TASK（IDの接頭辞と一致するため。扱いはフェーズ1で確定） |

これ以外は日本語で書く。本文で値そのものを指すときだけ識別子を使い、意味を述べるときは日本語を使う。

- 「状態`failed`の診断`CTX-ROOT-MISSING-001`を返す」（値を指す）／「検査に失敗した場合」（意味を述べる）
- 「`check`操作」（操作名）／「差分を検査する」（一般の動作）

### 3.2 一般語

前回§4.2で英語と決めた語は、カタカナまたは定着した漢語で書く。

| 前回の表記 | 新しい表記 |
|---|---|
| file、directory、path | ファイル、ディレクトリ、パス |
| command、test、review、report | コマンド、テスト、レビュー、レポート |
| field、key、option、value | フィールド、キー、オプション、値 |
| workspace、repository、catalog、member | ワークスペース、リポジトリ、カタログ、メンバー |
| target、source | 対象、参照元（関係の向きを言うとき）。文脈で決める |
| argv、cwd、timeout | 引数列、作業ディレクトリ、タイムアウト |
| byte、code point | バイト、コードポイント |

### 3.3 定義語

定義語は日本語の正式名で書く。各文書の初出にだけ「コンテキストバンドル（Context Bundle）」のように英語名を併記する。
カタカナにするか漢字の訳語にするかは語ごとにユビキタス言語一覧で決め、一覧にない訳語を作業者が作らない。

### 3.4 前回から引き継ぐ規則と廃止する規則

| 区分 | 規則 |
|---|---|
| 引き継ぐ | カタカナ語の語末の長音（ユーザー、パラメーター）、公用文のひらがな（できる、すべて、ただし）、複合名詞の送り仮名（読取り、書込み）、句読点と全角括弧、和文と英数字の間にスペースを入れない、だ・である調、見出しは体言止め |
| 引き継ぐ | 機械が照合する文字列は検証プログラムと同時にしか変えない。ハッシュ値を固定した文書は再レビュー記録を残してハッシュ値を更新する |
| 廃止する | 「カタカナへ転記するだけの語は英語で書く」（§2.1-3）、英語のまま書く一般語（§4.1.4）、英語で書く一般語（§4.2）、「本書は表記だけを定める」（冒頭） |

### 3.5 書き直し例

`docs/03.詳細設計/03_操作仕様/01_context.md`から3か所を示す。

| 現在 | 書き直し後 |
|---|---|
| 起点SPECまたはEARS-AI statementから、解釈・実装・検証に必要な文書を型付き関係で完全解決し、目的別Context Bundleを返す。 | 起点に指定した仕様文書またはEARS-AIの規範文から、解釈・実装・検証に必要な文書を型付きの関係でもれなくたどり、目的に応じたコンテキストバンドル（Context Bundle）を返す。 |
| 構文上妥当な起点がcatalogに存在しない場合は操作を開始し、`CTX-ROOT-MISSING-001`／failedを返す。既知起点へ置換しない。 | 起点が構文上は正しいもののカタログに存在しない場合は、操作を開始したうえで状態`failed`の診断`CTX-ROOT-MISSING-001`を返す。既知の別の起点へ置き換えることはしない。 |
| `purpose=verify`のBundleがbindingとして収録した場合だけの、bindingを1件以上収録したworkspaceの既定値適用後`verify.timeoutSeconds`。 | 目的が`verify`のバンドルがテスト割当てを収録した場合に限り、割当てを1件以上収録したワークスペースごとの`verify.timeoutSeconds`（既定値を適用した後の値）。 |

## 4. ユビキタス言語一覧の設計

### 4.1 文書の構成

現在の`docs/用語集.md`は、表記の規則と語の振り分けを1つにまとめ、意味を扱っていない。これを2つに分ける。

| ファイル | 役割 |
|---|---|
| `docs/用語集.md` | ユビキタス言語一覧。用語の意味と、日本語名・英語名・識別子の対応の正本 |
| `docs/表記規則.md`（新設） | 書き方の規則。英語で残すものの基準、一般語の表記、送り仮名、記号 |

`AGENTS.md`の「用語」の参照先に表記規則を加える。

### 4.2 一覧の列

| 列 | 内容 |
|---|---|
| 日本語名 | 本文で使う正式名 |
| 英語名 | 概念の英語名。初出の併記と英語の資料との対応に使う |
| 識別子 | コード、JSON、設定、CLIに現れる名前（バッククォート付き）。ない語は空欄 |
| 定義 | 1〜2文の定義。仕様の文言を要約し、新しい意味を加えない |
| 定義元 | 定義している仕様の節へのリンク |
| 関連語・使わない表記 | 混同しやすい語、言い換えてはいけない表記（実際の用語集では「備考」の列にまとめ、使わない表記は「使わない:」で示した） |

### 4.3 分類

仕様の所有境界（[詳細設計 §1](../03.詳細設計/README.md)）に合わせて次の10区分に分ける。

1. 製品と構成（Core、`bitz`コマンド、アダプター、スキル、プラグイン）
2. ワークスペースと設定（単一・複合ワークスペース、ルートワークスペース、メンバー、カタログ、修飾ID）
3. 仕様文書モデル（仕様文書、文書種別、フロントマター、文書の状態、置換）
4. EARS-AI（規範文、要求レベル、アクター、発動条件、意味中間表現、構文解析器）
5. 関係とトレース（関係型、強い関係と弱い関係、閉包、対象展開、対象規範文、隣接規範文、役割、カバレッジ）
6. コンテキスト（コンテキストバンドル、コンテキストダイジェスト、制約台帳、目的、詳細度、提示形式、展開、鮮度切れ検出）
7. 検査と検証（`check`、`verify`、`doctor`、基準版、対象選択、テスト割当て）
8. 結果と診断（結果、状態、診断、重大度、条件ID、継続単位、主診断、終了コード、レポート、全体結果）
9. 適合性と品質ゲート（適合フィクスチャ、期待マトリクス、ハーネス、正規化器、ゴールデン、Gate、Step、認定）
10. 開発フロー（Small Flow、Full Flow、Human Review、Pre-check、Post-check）

## 6. 変更時の制約

調査で分かった、書き直しで壊れやすい箇所である。作業者への指示に必ず含める。

### 6.1 ハッシュ値で固定された文書

### 6.3 リンクとアンカー

見出しを変えるとアンカーが変わる。監査のリンク検査は`docs/03.詳細設計/`、`docs/02.設計書/`、受理済みの決定記録しか見ないため、
fixtureの記録、提案資料、Pythonのコメントからのリンクは、全Markdownを対象にした検査で確かめる。

### 6.4 並行作業

`docs/`は他のGit worktreeでも頻繁に変わる（ADRの追加など）。1つのPRを小さく保ち、フェーズごとに`origin/main`から切って早くマージする。
前のPRがマージされる前に次のPRを積み重ねない。

### 7.1 フェーズ1〜3: 一覧と規則を先に固める

前回は規則を決めてから全体へ適用し、読みにくさに気づいたのが適用後だった。今回は、一覧と規則を起案した段階でパイロット文書を
1件書き直し、ユーザーが読んで了承してから全体へ広げる。

1. `docs/03.詳細設計/`と`docs/02.設計書/`から定義語を抜き出す（用語の表、「〜とは」「〜を定義する」の文、頻出語）。
2. 語ごとに日本語名、英語名、識別子、定義、定義元を埋める。定義は仕様の文言の要約にとどめる。
3. 前回の§4の振り分け表を新方針で引き直す（英語から日本語への移行表として表記規則の付録に置く）。
4. パイロットで出た迷いを一覧と規則へ反映してから確定する。

### 7.2 フェーズ4〜8: 本文の書き直し

1. 作業担当（`worker`）へ、一覧、表記規則、§6の制約、パイロット（`01_context.md`）の書き直しを見本として渡して、ディレクトリ単位で書き直させる。同時に動かすのは5体までとする。
2. 一覧にない語や、意味の取り方が分かれる文は作業担当に決めさせず、司令塔が集めてユーザーへ上げる。
3. 司令塔が§8の検査を実行し、レビュー担当（`reviewer`）が意味の不変と読みやすさを独立に確かめる。
4. ハッシュ値を固定した文書を変えたPRでは、本文、ハッシュ台帳の更新、Gate A再認定の記録を別コミットにする（前回と同じ分け方）。

### 7.3 フェーズ9: コメント・docstring

Pythonのコメント、docstring、例外メッセージを表記規則に合わせる。識別子、検証プログラムの報告値（`Passed`、`Not run`、
`full Gate A fresh-checkout repeatability`など。CIが照合する）、Coreの出力文言は変えない。testがメッセージを照合している箇所は同時に直す。
fixtureのプログラムとCoreは別コミットにする。

JSON Schemaの`title`と`description`、比較タスクの課題文と正解表も同じフェーズで直す。比較タスクの文言を変えたら、
`protocol.json`のprotocol versionを上げる（表記規則 §8の7）。契約の正本のスキーマ（`docs/03.詳細設計/schemas/`、ADR-050）とfixtureのスキーマ、比較タスクは監査の検証プログラム（`fixtures/conformance/schemas.py`など）が読むので、Gate Aを再認定する。

### 7.4 フェーズ10: ファイル名

本文と見出しが確定してから、見出しと同じ規則でファイル名を改める。プログラムが読むファイル（`*.py`、`*.json`、
`manifest.json`、`expected/`配下）、fixture IDのディレクトリ、`README.md`は変えない。改名と同時に次を直す。

- リンク（全Markdown）
- プログラム内のパス（`validate_conformance.py`、`step_assignment.py`、`environment_fixtures.py`、`target_vectors.py`、`diagnostic_coverage.py`など）
- `diagnostic-coverage.json`の`sources`のキー
- 決定記録のフロントマターの`title`とH1、決定記録の索引

## 8. 検証方法

| 検査 | 方法 | 実行時点 |
|---|---|---|
| 識別子の保存 | 書き直し前後のファイルから、バッククォート内の文字列、Diagnostic code、ID、数値、リンク先を抜き出して比べる。失われたものがあれば不合格 | 各フェーズ |
| 残存英語 | 散文中のバッククォート外の英単語を数え、許可リスト外の語を列挙する | 各フェーズ |
| 用語の統一 | 一覧の「使わない表記」を対象ファイルで検索する | 各フェーズ |
| リンク | 監査のリンク検査に加え、全Markdownを対象にした検査を実行する | 各フェーズ |
| 監査 | `uv run fixtures/validate_conformance.py`（終了コード1、`pending` 1件が正常） | 各フェーズ |
| 単体試験 | `uv run --project plugins/bitz-core python tests/bitz-core/run_test_files.py tests/bitz-core/test_*.py` | フェーズ9以降は必須、それ以前も各PRで実行 |
| 適合試験 | `uv run fixtures/run_conformance.py --core plugins/bitz-core --step N` | フェーズ9、10 |
| Gate A再認定 | `uv run fixtures/certify_gate_a.py`（クリーンな作業ツリーで） | ハッシュ台帳かfixtureを変えたPR |
| 意味の不変 | レビュー担当が差分を読み、条件、例外、義務の強さ、数値が変わっていないことを確かめる | 各PR |
| 読みやすさ | ユーザーがパイロットと各PRの抜き取りを読む | フェーズ2と各PR |

## 9. リスクと対策

| リスク | 対策 |
|---|---|
| 書き直しで規範の意味が変わる | 識別子の保存検査を機械で行い、意味の不変をレビュー担当が独立に確かめる。迷う文は変えずに司令塔へ上げる |
| 見出しの変更でリンクが切れる | 全Markdownのリンク検査を各フェーズで実行する |
| 検証プログラムの照合文字列を壊す | §6.2の一覧を作業指示に含め、監査の実行で確かめる |
| 訳語が作業者ごとに揺れる | 一覧にない訳語を作らせない。一覧を先に確定する |
| 他のGit worktreeの変更と衝突する | PRを小さく分け、`origin/main`から切り、早くマージする |
| Coreの出力文言（診断の`summary`）に英語が残り、仕様の引用と見た目がそろわない | 今回は対象外として残す。別の計画で、Core、期待値、Gate再認定を含めて扱う |
