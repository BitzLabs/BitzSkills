# 並行開発におけるID重複対策の検討と提案

**状態**: **Open（未裁定・採決事項9件、P1 3件は適用差分あり）**

**作成日**: 2026-09-01

**対象**: `docs/02.設計書`、`docs/03.詳細設計`

**目的**: 並行branchで独立採番された文書IDの衝突を、merge後ではなくPR時点で決定論的に解決する

## 1. 結論

現行設計はID重複を**検出できるが、mergeされた後にしか検出できない**。予防機構と早期検出機構は
存在しない。本提案は、統合先branchを勝者とする**先勝ち**規則と、敗者側（PR側）の**自動振り直し**を
導入し、PR時点で解決してからmergeできるようにする。

新しい入力機構、永続台帳、Git履歴走査は追加しない。`--base`へ渡す値を統合先先端へ変えることで、
既存のGit基準版（ADR-025）と`(workspaceId, documentId)`索引（ADR-037）だけで勝敗が決まる。

| 項目 | 提案 |
|---|---|
| 先勝ちの基準 | 統合先branchに既に存在するIDが勝つ。時刻に依存しない |
| 検出 | Coreが担う。`--base <統合先先端>`で勝敗と振り直し箇所を機械可読に出力 |
| 適用 | Skill／拡張プラグインが担う。Coreは読取り専用契約を維持 |
| 新IDの採番 | 基準版と現在集合の全IDの最大値+1 |
| 対象種別 | REQ、TECH、TASK、ADR |

## 2. 現状

### 2.1 一意性のスコープ

| 階層 | 範囲 | 正本 |
|---|---|---|
| 文書ID | ワークスペース内、大小文字区別 | [配置・命名・探索規則](../03.詳細設計/02_SPECファイル規定/01_配置・命名・探索規則.md) §4 |
| 規範文ID | 同一`.spec/`内 | [Core構文仕様](../03.詳細設計/01_EARS-AI規格/01_Core構文仕様.md) §2 |
| 連合 | `<workspace-id>::<document-id>`。別workspaceの同一ローカルIDは重複としない | [参照・トレース・検証仕様](../03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md) §12 |

### 2.2 検出機構

`EAI-CORE-ID-002`（error／`failed`）と`SPEC-ID-DUPLICATE-001`（error／`failed`）が重複を検出する。
`draft`でもerrorのままとする（[要求SPEC仕様](../03.詳細設計/02_SPECファイル規定/04_要求SPEC仕様.md) §5）。

検出範囲は**現在集合＝作業ツリーのスナップショットに限る**。ADR-037 Decision 6でそう限定し、
`EAI-CORE-ID-003`はCore 1.0から削除した。

### 2.3 採番規則

`REQ-[0-9]{3,}`などの連番形式であり、**採番の手続きと調停機構は定義されていない**。
「採番の連続性は要求しない。欠番は正常とする」だけが規定である。公開操作`context`／`check`／
`verify`／`doctor`に採番操作はなく、IDは人間またはSkillが決める。

## 3. 課題

### 3.1 同一IDの同時新規作成（本提案の対象）

branch XとYが独立に`REQ-005`を作成した場合の経過を示す。

1. 各branch単独では現在集合に重複がないため、`bitz check`は`passed`となる。
2. 正規ファイル名は`<ID>.md`または`<ID>-<slug>.md`であり、slugが異なれば
   `REQ-005-cache.md`と`REQ-005-login.md`という別ファイルになる。**Gitはadd/add conflictを出さず、
   両方をmergeする**。
3. merge後の初回`check`で初めて`SPEC-ID-DUPLICATE-001`／`failed`となる。

検出時点で両branchとも実装、テスト、TASKが完成している。振り直しは`refines`、`requires`、`covers`、
TASK `addresses`、モノレポ修飾参照へ波及し、最も費用の高い時点で顕在化する。

### 3.2 削除と再作成の交差（本提案の対象外）

branch Xが`REQ-005`を削除し、Yが別の意味で`REQ-005`を作成した場合、merge後は基準版にも現在版にも
`REQ-005`が存在するため、ADR-037 Decision 2により同一文書のrename・改訂と判定される。

これは既定の裁定であり、ADR-037 Consequencesが「Core検査を経ずに過去の削除がcommitされた場合、
後日のID再利用はCoreだけでは検出できない」と明記し、Gitレビューの責務としている。本提案は
この裁定を変更しない。

### 3.3 モノレポ

workspaceが異なれば同一ローカルIDは正当であるため、memberをまたぐ並行開発では衝突しない。
衝突は**同一workspace内の並行branchに限られる**。

## 4. 提案

### 4.1 先勝ちの定義

**統合先branchに既に存在するIDを勝者とし、PR側が振り直す。**

commit時刻を基準にしない。時刻は書き換え可能であり、shallow cloneやrebaseで変動するため、
「同一入力から同一Diagnosticを再現する」という決定論の要求を満たせない。統合先の有無は
既存のGit基準版索引だけで判定でき、決定論的である。

### 4.2 検出規則

CIは**両者を含む木**（merge結果、または統合先へrebase済みの自branch）に対し、統合先先端を
`--base`へ渡す。

```text
bitz check --full --base <integration-tip>
```

このとき、現在集合に同一`(workspaceId, documentId)`が2件現れたなら、

| 条件 | 判定 |
|---|---|
| 基準版に存在する側 | **勝者**（incumbent）。変更しない |
| 基準版に存在しない側 | **敗者**（challenger）。振り直す |
| 両方が基準版に存在しない | 勝敗を決定できない。重複はerrorとするが振り直しを提案しない |
| 両方が基準版に存在する | 発生しない（Gitが単一ファイルへmergeするかconflictにする） |

第3行が、`--base`へmerge-baseではなく統合先先端を渡す理由である。merge-baseを基準にすると
両者とも新規となり、勝敗が付かない。

fork前から存在するIDは、両者が編集してもGitが単一ファイルへmergeするかconflictにするため、
現在集合に2件並ばない。したがって**2件並ぶのは独立生成のときだけ**であり、`semanticHash`による
推測を必要としない。ADR-037 Decision 2の「キーの有無で判定し、hash差から再利用を推測しない」という
方針と一貫する。

merge運用とrebase運用のどちらでも同じ規則が成立する。

### 4.3 承認済みREQ保護との関係

振り直し対象は定義上つねに「基準版に存在しない新規ID」である。要求SPEC仕様 §7の

> Git基準版に存在しない新規ファイルは変更前状態との比較対象外とする。

により、`safety.protectApprovedRequirements`に抵触しない。branch内で`approved`まで進んだREQを
振り直しても保護違反にならない。新規文書であるため`Revision History`への追記も要求しない。

### 4.4 採番規則

新IDは**基準版と現在集合の全IDの最大値+1**とする。

- 欠番を埋めない。「採番の連続性は要求しない。欠番は正常とする」と整合し、削除済みIDの
  再利用（配置・命名・探索規則 §4）も避けられる。
- 複数衝突時は、衝突した元IDの昇順に連番を割り当てる。決定論性を保つ。
- 桁数は`[0-9]{3,}`の範囲で必要に応じて繰り上げる。

### 4.5 振り直しの影響範囲と分担

Coreが関係索引から**完全に導出できる**書き換え箇所を`tracked`、本文中の文字列一致に依存し
**Coreが保証しない**箇所を`textual`とする。

| 対象 | 区分 |
|---|---|
| Frontmatter `id` | tracked |
| ファイル名（先頭IDとFrontmatter `id`の一致は必須） | tracked |
| `refines`／`requires`／`related`／`supersedes` | tracked |
| `covers`の規範文参照（`REQ-005:AC-01`） | tracked |
| TASK `addresses` | tracked |
| モノレポ修飾参照（`web::REQ-005`） | tracked |
| **本文中のMarkdownリンクと散文引用** | **textual** |
| **コード・テスト内のコメント、テスト名** | **対象外** |

規範文ID（`AC-01`）は文書ローカルであるため、文書IDが直れば連動して解決する。別問題としない。

`textual`が必要な理由は、Coreが文書間の正を`relations`とし、本文のMarkdownリンクを検査対象に
していないためである（参照・トレース・検証仕様 §2）。**とくにADRは散文中で番号引用され、
ファイル名変更によりリンクpathも壊れる**。したがって`textual`の探索は旧ID文字列と旧ファイル名の
双方を対象とし、Coreは列挙のみ、置換の可否は人間が判断する。

### 4.6 検出と適用の分離

`bitz check`は読取り専用であり、公開操作4つはすべて非変更系である。振り直しはSPECを書き換えるため、
Coreへ入れると5つ目の書込み操作となり、Core 1.0の輪郭が変わる。

そこで**検出と適用を分離**する。

- **Core**: 勝敗、提案する新ID、`tracked`／`textual`の書き換え箇所を`check`結果JSONへ出力する。
  逆索引は既に保持しており、新しい解析を要しない。
- **Skill／拡張プラグイン**: 出力を読んで適用し、commitする。

ADR-009の「SDDの段階管理やAIエージェントの進行は、これらの操作を呼び出す薄い拡張Skillとして
実現する」という方針と整合し、`check`の読取り専用契約を維持できる。

### 4.7 結果Schema

`check`結果へ`idCollisions`を追加する。Diagnostic Schema（ADR-021）は変更しない。勝敗と振り直し
候補は診断メッセージではなく構造化データであり、`selection`と同じ位置づけとする。

```json
"idCollisions": [
  {
    "workspaceId": "web",
    "documentId": "REQ-005",
    "incumbent": {"path": ".spec/requirements/REQ-005-cache.md"},
    "challenger": {"path": ".spec/requirements/REQ-005-login.md"},
    "proposedId": "REQ-014",
    "rewriteSites": [
      {"path": ".spec/requirements/REQ-005-login.md", "field": "id", "kind": "tracked"},
      {"path": ".spec/requirements/REQ-005-login.md", "field": "filename", "kind": "tracked"},
      {"path": ".spec/technical/TECH-003-session.md", "field": "relations.refines", "kind": "tracked"},
      {"path": ".spec/tasks/TASK-007-login.md", "field": "addresses", "kind": "tracked"},
      {"path": ".spec/decisions/ADR-004-token.md", "line": 42, "kind": "textual"}
    ]
  }
]
```

勝敗を決定できない場合、`proposedId`と`rewriteSites`を省略し、`incumbent`／`challenger`の代わりに
`instances`へ両方のpathを並べる。`SPEC-ID-DUPLICATE-001`／`failed`は従来どおり返す。

### 4.8 PR時のフロー

1. PR CIが`bitz check --full --base <integration-tip>`を実行し、`SPEC-ID-DUPLICATE-001`／`failed`
2. 結果JSONの`idCollisions`が敗者、提案新ID、書き換え箇所を示す
3. Skillが`tracked`を適用し、`textual`を提示する
4. commit、push、再CI、`passed`、merge

## 6. 採用しない案

| 案 | 不採用理由 |
|---|---|
| commit時刻で先勝ちを決める | 書き換え可能で非決定論的。rebaseとshallow cloneで結果が変わる |
| Coreへ`bitz renumber`を追加 | 公開操作がすべて非変更系という契約を破り、配布形態とdoctorへ波及する |
| branch／開発者ごとの番号レンジ予約 | Core 1.0が持たない調停と台帳の性格が入り、レンジ枯渇と設定同期の運用負荷が生じる |
| ULID等の衝突耐性IDへ変更 | 重複を設計から排除できるが、`REQ-[0-9]{3,}`の字句規則、ADR-005、ADR-013、人間可読性を全面的に見直すことになる |
| merge-baseを`--base`に維持し衝突検出を別invocationにする | 呼出しが2本になり、同一木に対する基準版が2つ存在する状態を持ち込む |
| `semanticHash`で同一性を判定 | ADR-037が正当なrenameの誤検出を理由に不採用としており、判断を覆す新事実がない |
| ファイル名を`<ID>.md`正規形へ強制しGitのadd/add conflictへ委ねる | slugによる可読性を失い、かつconflict解決を人手に戻すだけで振り直しは支援されない |
| 改番を表すFrontmatter項目（`renumberedFrom`、`x-renumbered-from`）を追加 | Gitから導ける情報をFrontmatterへ持ち込み統合後も陳腐化する。ADR-015 Decision 4および旧SPEC知見と同型。詳細は附録A.0 |
| Git rename検出で改番を認識する | 類似度閾値と`diff.renameLimit`に依存し、同一入力に対する決定論を失う |

## 7. 受入条件

- 同一workspaceで独立生成された同一IDを、merge結果とrebase後branchの双方で敗者側だけ特定できる。
- 基準版に両方が存在しない場合に、勝敗を決定せず`failed`を返し、誤った振り直しを提案しない。
- fork前から存在するIDを両者が編集した入力で、衝突として誤検出しない。
- `rewriteSites`の`tracked`をすべて適用した木が`SPEC-ID-DUPLICATE-001`を出さず、参照切れを生じない。
- `approved`まで進んだ新規REQを振り直しても承認保護に抵触しない。
- ADRを振り直したとき、`relations`が`tracked`で解決し、本文リンクが`textual`として列挙される。
- 同一入力から同一の`proposedId`と`rewriteSites`順序を再現できる。

P1適用後の受入条件は附録A.5を正とする。

## 8. 残るリスクと未決事項

### 8.1 振り直しレース

新IDを最大値+1で採るため、並行する2本のPRが同じ番号を取り合う。片方がmergeされると他方は
再度振り直しになる。収束はするが、並行度が高いと繰り返す。

Core側で完全には解消できない。merge queueによる直列マージで担保する運用前提とし、Coreは検出と
決定論のみを保証する。

### 8.2 未決事項

- 振り直しcommitとTASK `changes`境界の関係。境界検査の対象外とするか、`changes`へ含めるか。
- 同一内容がcherry-pickで両branchへ入った場合、Coreは独立生成と区別できない。振り直すと重複文書が
  残るため、人間の確認を要する旨をSkillの契約に含めるか。
- `--base <integration-tip>`へ統一した場合の、承認保護と状態遷移の検査範囲がmerge-base基準と
  厳密に一致するかの確認。

### IDDUP-001: 振り直しがSPEC削除と誤判定される（P1）

**指摘**

ADR-037 Decision 3と[参照・トレース・検証仕様](../03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md) §4は、
基準版に存在するキーが現在版に存在しない場合を**種別や状態を問わず**SPEC削除とし、
`SPEC-STATE-TRANSITION-001`／error／`failed`とする。

振り直しは`(workspaceId, documentId)`のキー自体を`REQ-005`から`REQ-014`へ変える。ADR-037 Decision 2が
renameとして扱うのはpath変更だけであり、**ID変更を表現できない**。したがって基準版が旧IDを含む状態で
`check`を実行すると、正当な振り直しが削除として拒否される。

影響範囲は限定されるが、最も影響が大きい箇所に当たる。

| 基準版 | 旧IDを含むか | 判定 |
|---|---|---|
| 統合先先端（CI、§4.2） | 含まない | 正常 |
| merge-base（従来CI） | 含まない | 正常 |
| **`HEAD`（既定、振り直しをcommitする前）** | **含む** | **誤ってerror** |
| `HEAD~n`（branch内の先行commit） | 含む | 誤ってerror |

すなわち、Skillが振り直しを適用した直後に自身の作業を`bitz check`で確認する経路が通らない。

**修正候補**

| 案 | 内容 | 評価 |
|---|---|---|
| 案1 | 敗者へ`x-renumbered-from`を記録し、Coreは旧IDのキー消失をrenameとして扱う | 推測ではなく明示宣言であり、ADR-037の「hash差から再利用を推測しない」方針と両立する。Frontmatter共通仕様へ1項目追加 |
| 案2 | 振り直しを単一commitで完結させる運用規約に限定し、Coreを変更しない | 未commit状態の`check`が通らず、Skillが自己検証できない。運用の遵守に依存し脆い |
| 案3 | 削除検出を「統合先へ到達済みのSPEC」に限定する | Coreは到達済みかを知らず、統合先の指定を新たな入力として要求することになる |
| 案4 | 振り直し時だけ削除検査を抑止する`check`オプションを追加 | 安全検査の明示的な無効化であり、セキュリティとガバナンス設計の方針に反する |
| 案5 | 合流をGitへ記録した後の木で振り直すことを正規手順とし、基準版の重複キーだけを規則化する | 勝者が旧IDを保持するためキーが消えず、削除判定が発動しない。ADR-037とFrontmatter Schemaを変更しない |

**推奨**: **案5（附録Aで確定）**。上記4案はいずれも採らない。振り直しを統合先との合流をGitへ記録した

同一キーに複数pathを持つ場合の定義だけとなり、ADR-037のDecisionもFrontmatter Schemaも変更しない。
案1・案2の不採用理由と案5の詳細は附録A.0およびA.1を正とする。

**受入条件**

受入条件は附録A.5へ集約した。

### IDDUP-004: 振り直しと状態遷移契約・置換語彙の関係（P2）

**指摘**

振り直しはstatusを変えないため、§6.3の遷移図に新しいedgeは要らない。しかし次の3点が未定義である。

1. 振り直しが`supersedes`による置換ではないこと。ADR-012は置換済みREQ・TECHの適用を遮断するため、
   振り直しを置換と誤って記録すると、正当な文書が適用対象から外れる。
2. 終端状態の文書を振り直せるか。ADR-036は終端状態からの再オープンを禁止するが、ID変更は再オープンでは
   ない。`rejected` REQや`cancelled` TASKが敗者となる場合の可否が読み取れない。
3. 振り直し後の文書が統合先へ初めて現れるときの遷移。`[new] -> approved`は§6.3で許可済みであり、
   追加の裁定を要しないが、明記がない。

**修正候補**

振り直しを「同一文書の識別子変更であり、置換でも状態遷移でもない」と定義し、次を明記する。

- `supersedes`、`superseded`、`outdated`、`rejected`のいずれも使用しない。
- 終端状態の文書も振り直しの対象とする。理由欄と`Revision History`は変更しない。
- 振り直し後の文書は、統合先から見て`[new]`からの遷移として扱う。

**受入条件**

- 振り直した`rejected` REQが、置換済み扱いにならず、Historyとして保持され続ける。
- 振り直しが§6.3のいずれのedgeにも該当しないことを本文から確認できる。

### IDDUP-005: 振り直しcommitとTASK `changes`境界（P2）

### IDDUP-006: `--base`統一時の承認保護・状態遷移の検査範囲（P2）

## 附録A. P1修正案（適用可能な差分）

作成日: 2026-09-01。IDDUP-001〜003について、正本へそのまま適用できる修正を示す。

### A.0 方針の見直しと`renumberedFrom`の撤回

§9 IDDUP-001は`x-renumbered-from`、次いでCore共通項目`renumberedFrom`を推奨した。**両案を撤回する。**

撤回の理由は3点ある。

1. **既存の不採用判断と同型である。** [旧SPEC知見の評価](../03.詳細設計/02_SPECファイル規定/09_旧SPEC知見の評価.md) §4は
   「成果物ごとのversion、updated」を「Git履歴と重複し、同期ずれを生むため不採用」とし、
   ADR-015 Decision 4も独自`version`・`updated`を導入しないと定めた。`renumberedFrom`は
   Gitの変更集合から導ける情報をFrontmatterへ持ち込み、統合後は無効になっても残り続ける。同じ型の負債である。
2. **Digestの例外分類を生む。** 削除判定にだけ使い、Context DigestとProjection Digestへは影響させない、
   という例外をSerializerとDigest計算へ持ち込む必要がある。
3. **そもそも正規手順では不要である。** A.1のとおり、振り直しを合流後の木で行えば旧IDのキーは消えない。
   宣言を必要とするのは非推奨の手順だけである。

`x-`拡張の規則（[Frontmatter共通仕様](../03.詳細設計/02_SPECファイル規定/03_Frontmatter共通仕様.md) §7の
「Coreは値を変更せず保持し、合否判定へ使用しない」）は**維持する**。この規則は健全であり、
本設計はこれを迂回しない。

改番の人間向け記録は`Revision History`へ置く。ADR-015 Decision 8により`Revision History`は
非規範メタデータであり、Constraint Ledger、coverage、Context Digestの意味集合から既に除外されている。
新しい例外を作らずに済む。

### A.1 IDDUP-001: 改番を合流後の木で行う

#### A.1.1 正規手順の確定

振り直しをどの木の上で適用するかで結果が変わる。**合流後の木で行うことを正規手順とする。**

| 適用時点 | 基準版`HEAD`のキー`REQ-005` | 振り直し後の現在集合 | 判定 |
|---|---|---|---|
| **合流をcommitした後（正規）** | 敗者・勝者の2件 | 勝者`REQ-005`と`REQ-014` | **キーが残るため削除にならない**。基準版の重複だけを規則化すればよい |
| 合流をcommitせず一括commit | 敗者1件 | 勝者`REQ-005`と`REQ-014` | キーは残るが、基準版の敗者と現在版の勝者が同一文書と誤対応する |
| 合流前の自branch | 敗者1件 | `REQ-014`のみ | 旧キーが消え、SPEC削除として`failed`となる |

正規手順では、勝者が旧IDを保持し続けるためキーが消えない。したがって**ADR-037 Decision 3の削除規則を
変更する必要がなく、新しいFrontmatter項目も要らない**。必要な追加規則は、基準版が同一キーに複数pathを持つ
状態の定義だけである。

第2行は、合流と振り直しを1つのcommitへまとめた場合に、基準版の敗者（例えば`rejected`）と現在版の勝者
（例えば`draft`）を同一文書として遷移検査し、`rejected -> draft`を禁止遷移として誤検出する経路である。
第3行は合流前に振り直した場合である。いずれも正規手順を定義し、`Integrate`（A.2）で合流を先行させることで
回避する。回避できなかった場合はerrorとなり、利用者は合流をcommitしてから再実行する。

#### A.1.2 Frontmatter共通仕様 §5 状態遷移

現行§5は「遷移検査には[Git基準版]を使用する」とだけ述べ、**基準版の文書と現在版の文書をどう対応付けるかを
述べていない**。対応付け規則はADR-037にしか存在せず、`id`と`status`を所有する本仕様から読み取れない。
仕様検討段階の欠落として補う。

**before**

```text
禁止遷移は`SPEC-STATE-TRANSITION-001`／error／`failed`とする。遷移検査には
[Git基準版](../../02.設計書/10_決定記録/ADR-025_Git基準版とcheck明示対象の確定.md)を使用する。
基準版を利用できない場合も現在値の語彙は検査するが、過去状態を推測して遷移合格を宣言しない。
```

**after**

```text
禁止遷移は`SPEC-STATE-TRANSITION-001`／error／`failed`とする。遷移検査には
[Git基準版](../../02.設計書/10_決定記録/ADR-025_Git基準版とcheck明示対象の確定.md)を使用する。
基準版を利用できない場合も現在値の語彙は検査するが、過去状態を推測して遷移合格を宣言しない。

基準版の文書と現在版の文書は`(workspaceId, documentId)`で対応付ける。pathの一致は要求せず、
pathだけが異なる場合はrenameとして同一文書に扱う。対応付けと削除の効果は
[ADR-037](../../02.設計書/10_決定記録/ADR-037_Git基準版間のSPEC同一性と削除規則.md)を正とする。

基準版で同一の`(workspaceId, documentId)`が複数pathへ解決する場合、そのキーの対応付けを一意に定められない。
このとき当該キーの遷移検査と削除判定を実施不能とし、`SPEC-BASE-AMBIGUOUS-001`／warning／
`passed_with_warnings`とする。現在集合の重複検査、現在値の語彙検査、他キーの遷移・削除判定は
通常どおり実施する。基準版の重複は、並行branchのID衝突を解決する過程で一時的に生じる
（[UC-13](../../02.設計書/09_ユースケース設計.md)）。
```

#### A.1.3 Frontmatter共通仕様 §2 共通項目

現行の`id`の説明は「文書の安定ID」だけであり、**一意性の範囲と、IDを変更してよい条件が本仕様にない**。
一意性は[配置・命名・探索規則](../03.詳細設計/02_SPECファイル規定/01_配置・命名・探索規則.md) §4、
改番の可否はどこにも書かれていない。`id`を所有する本仕様へ集約する。

**before**

```text
`title`は1行で1文字以上120文字以下とする。配列は重複を許さず、正規出力ではIDまたはパスの辞書順に並べる。
```

**after**

```text
`title`は1行で1文字以上120文字以下とする。配列は重複を許さず、正規出力ではIDまたはパスの辞書順に並べる。

`id`はworkspace内で一意な安定識別子とし、意味を持たない。ディレクトリ移動、ファイル名変更、本文改訂で
変更しない。ID形式と一意性の範囲は[配置・命名・探索規則](01_配置・命名・探索規則.md) §4を正とする。

`id`を変更してよいのは、並行branchのID衝突を解決する改番だけとする。改番はGit基準版に到達していない
文書に限り、基準版に存在する文書のIDを変更してはならない。基準版に存在するIDを持つ文書が現在版から
消えた場合は、改番ではなく削除として扱う（ADR-037 Decision 3）。改番の判定、勝敗、手順は
[UC-13](../../02.設計書/09_ユースケース設計.md)を正とする。
```

```text
### UC-13 統合先との合流とID衝突の解決

**目的**: 並行branchで独立採番された文書IDの衝突を、統合前に決定論的に解消する。

**事前条件**: 統合先branchの先端を解決でき、合流をGitへ記録した木を構成できる。

**基本フロー**:

1. 利用者は統合先先端を作業branchへ合流させ、Gitへ記録する。
2. 利用者またはCIは統合先先端を`--base`へ渡して`bitz check`を実行する。
3. Coreは現在集合の重複を検出し、基準版における各インスタンスの有無から勝者と敗者を決定する。
4. Coreは敗者、提案する新ID、`tracked`と`textual`の書き換え箇所を`idCollisions`へ出力する。
5. Skillは`tracked`をすべて適用し、敗者の`Revision History`へ旧IDと改番理由を1行追記する。
6. Skillは`textual`を人間へ提示する。Coreは`textual`の適用を保証しない。
7. 利用者は再度`check`を実行し、通過statusを確認してからmergeする。

**代替・例外フロー**:

- 合流を記録する前に振り直した場合、旧IDが基準版にだけ残るため`SPEC-STATE-TRANSITION-001`／`failed`と
  なる。利用者は合流を記録してから再実行する。
- 基準版で文書IDが重複する場合、当該キーの対応付けと削除判定を実施不能とし
  `SPEC-BASE-AMBIGUOUS-001`／warningとする。振り直しの完了により解消する。
- 基準版に両インスタンスが存在しない場合、勝敗を決定せず`instances`だけを返し、振り直しを提案しない。
  重複そのものは従来どおり`SPEC-ID-DUPLICATE-001`／`failed`とする。
- 勝者と敗者の内容が同一の場合、Skillは振り直しと敗者の削除を選択肢として提示する。
- Git不在では現在集合の重複検査だけを実施し、勝敗判定を実施不能としてwarningにする。
- `textual`が未適用でも`check`は通過する。本文リンクの整合は人間が確認する。
- 連合では`idCollisions`を全体で1配列へ集約し、勝敗判定は同一`workspaceId`内に閉じる。

**完了条件**: 現在集合に重複がなく、`tracked`をすべて適用した木が参照切れを生じない。

**正本**: [参照・トレース・検証仕様 §4](../03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md#4-bitz-check)
```

### A.4 ADR-038の骨子

**ADR-038 並行開発のID衝突解決と統合段階**

- `relations.requires`: ADR-025、ADR-037
- `relations.related`: ADR-015、ADR-024、ADR-028、ADR-033

**Decision**

1. ID衝突の勝者は統合先branchの先端に存在する側とする。commit時刻を判定に使用しない。
2. 振り直しは統合先との合流をGitへ記録した後の木で行う。合流前の振り直しは削除として拒否する。
3. CIは統合先先端を`--base`へ渡し、合流後の木に対し`check`を実行する。
4. 敗者の新IDは、基準版と現在集合の全IDの最大値+1とする。複数衝突時は元IDの昇順に連番を割り当てる。
5. 振り直しの検出と提示をCoreが行い、適用はSkill／拡張が行う。`check`は読取り専用契約を維持する。
6. 基準版で同一`(workspaceId, documentId)`が複数pathへ解決する場合、当該キーの対応付けと削除判定を
   実施不能とし`SPEC-BASE-AMBIGUOUS-001`／warningとする。
7. 改番を表すFrontmatter項目を追加しない。改番の記録は`Revision History`へ置く。
8. 開発フローの骨格へ`Integrate`を追加する。ADR-028を部分改訂し、文書全体は置換しない。
9. UC-13を新設する。振り直しの対象種別はREQ、TECH、TASK、ADRとする。
10. 本文中のMarkdownリンクと散文引用は`textual`として列挙するのみとし、Coreの保証範囲へ含めない。

**Consequences**

- 衝突をmerge後ではなくPR時点で解決でき、実装完了後の高費用な改番を避けられる。
- ADR-037のDecisionを変更せず、削除禁止の強度を維持する。
- Frontmatter Schemaへ項目を追加しないため、Digestの例外分類とFrontmatterの陳腐化を生まない。
- Coreの公開操作は4つのまま、すべて非変更系を維持する。
- 合流を記録する前に振り直すと拒否される。手順の前後関係が利用者に見える形で強制される。
- ADR本文の散文引用はCoreが追跡せず、リンク切れの確認は人間に残る。
- 並行度が高い場合、最大値+1の採番により振り直しが繰り返される可能性が残る。

**Alternatives**

| 案 | 不採用理由 |
|---|---|
| `renumberedFrom`をCore共通項目へ追加 | Gitから導ける情報をFrontmatterへ持ち込み、統合後も残って陳腐化する。ADR-015 Decision 4および旧SPEC知見の「成果物ごとのversion、updated」と同型。Digestの例外分類も生む |
| `x-renumbered-from`を使う | `x-`拡張を合否判定へ使用しない規則（Frontmatter共通仕様 §7）に反する |
| Git rename検出で改番を認識する | 類似度閾値と`diff.renameLimit`に依存し、同一入力に対する決定論を失う。ADR-037がsemanticHashを退けた理由と同型 |
| 削除禁止を統合先到達済みSPECへ限定 | Coreは基準版が統合先かを判定できず、統合先の指定を新たな入力として要求することになる |
| 振り直し時だけ削除検査を抑止するオプション | 安全検査の明示的な無効化であり、セキュリティとガバナンス設計の方針に反する |
