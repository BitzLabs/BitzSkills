# 並行開発におけるID重複対策の検討と提案

**状態**: **Closed（採決事項9件・裁定事項16件をすべて裁定し、正本へ反映済み。ADR-038として記録）**

**作成日**: 2026-09-01

**対象**: `docs/02.設計書`、`docs/03.詳細設計`

**目的**: 並行branchで独立採番された文書IDの衝突を、merge後ではなくPR時点で決定論的に解決する

## 1. 結論

現行設計はID重複を**検出できるが、mergeされた後にしか検出できない**。予防機構と早期検出機構は
存在しない。本提案は、統合先branchを勝者とする**先勝ち**規則と、敗者側（PR側）の**自動振り直し**を
導入し、PR時点で解決してからmergeできるようにする。

新しい入力機構、永続台帳、Git履歴走査は追加しない。`--base`へ渡す値を統合先先端へ変えることで、
既存のGit基準版（ADR-025）と`(workspaceId, documentId)`索引（ADR-037）だけで勝敗が決まる。

| 項目 | 提案 |
|---|---|
| 先勝ちの基準 | 統合先branchに既に存在するIDが勝つ。時刻に依存しない |
| 検出 | Coreが担う。`--base <統合先先端>`で勝敗と振り直し箇所を機械可読に出力 |
| 適用 | Skill／拡張プラグインが担う。Coreは読取り専用契約を維持 |
| 新IDの採番 | 基準版と現在集合の全IDの最大値+1 |
| 対象種別 | REQ、TECH、TASK、ADR |

## 2. 現状

### 2.1 一意性のスコープ

| 階層 | 範囲 | 正本 |
|---|---|---|
| 文書ID | ワークスペース内、大小文字区別 | [配置・命名・探索規則](../03.詳細設計/02_SPECファイル規定/01_配置・命名・探索規則.md) §4 |
| 規範文ID | 同一`.spec/`内 | [Core構文仕様](../03.詳細設計/01_EARS-AI規格/01_Core構文仕様.md) §2 |
| 連合 | `<workspace-id>::<document-id>`。別workspaceの同一ローカルIDは重複としない | [参照・トレース・検証仕様](../03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md) §12 |

### 2.2 検出機構

`EAI-CORE-ID-002`（error／`failed`）と`SPEC-ID-DUPLICATE-001`（error／`failed`）が重複を検出する。
`draft`でもerrorのままとする（[要求SPEC仕様](../03.詳細設計/02_SPECファイル規定/04_要求SPEC仕様.md) §5）。

検出範囲は**現在集合＝作業ツリーのスナップショットに限る**。ADR-037 Decision 6でそう限定し、
`EAI-CORE-ID-003`はCore 1.0から削除した。

### 2.3 採番規則

`REQ-[0-9]{3,}`などの連番形式であり、**採番の手続きと調停機構は定義されていない**。
「採番の連続性は要求しない。欠番は正常とする」だけが規定である。公開操作`context`／`check`／
`verify`／`doctor`に採番操作はなく、IDは人間またはSkillが決める。

## 3. 課題

### 3.1 同一IDの同時新規作成（本提案の対象）

branch XとYが独立に`REQ-005`を作成した場合の経過を示す。

1. 各branch単独では現在集合に重複がないため、`bitz check`は`passed`となる。
2. 正規ファイル名は`<ID>.md`または`<ID>-<slug>.md`であり、slugが異なれば
   `REQ-005-cache.md`と`REQ-005-login.md`という別ファイルになる。**Gitはadd/add conflictを出さず、
   両方をmergeする**。
3. merge後の初回`check`で初めて`SPEC-ID-DUPLICATE-001`／`failed`となる。

検出時点で両branchとも実装、テスト、TASKが完成している。振り直しは`refines`、`requires`、`covers`、
TASK `addresses`、モノレポ修飾参照へ波及し、最も費用の高い時点で顕在化する。

### 3.2 削除と再作成の交差（本提案の対象外）

branch Xが`REQ-005`を削除し、Yが別の意味で`REQ-005`を作成した場合、merge後は基準版にも現在版にも
`REQ-005`が存在するため、ADR-037 Decision 2により同一文書のrename・改訂と判定される。

これは既定の裁定であり、ADR-037 Consequencesが「Core検査を経ずに過去の削除がcommitされた場合、
後日のID再利用はCoreだけでは検出できない」と明記し、Gitレビューの責務としている。本提案は
この裁定を変更しない。

### 3.3 モノレポ

workspaceが異なれば同一ローカルIDは正当であるため、memberをまたぐ並行開発では衝突しない。
衝突は**同一workspace内の並行branchに限られる**。

## 4. 提案

### 4.1 先勝ちの定義

**統合先branchに既に存在するIDを勝者とし、PR側が振り直す。**

commit時刻を基準にしない。時刻は書き換え可能であり、shallow cloneやrebaseで変動するため、
「同一入力から同一Diagnosticを再現する」という決定論の要求を満たせない。統合先の有無は
既存のGit基準版索引だけで判定でき、決定論的である。

### 4.2 検出規則

CIは**両者を含む木**（merge結果、または統合先へrebase済みの自branch）に対し、統合先先端を
`--base`へ渡す。

```text
bitz check --full --base <integration-tip>
```

このとき、現在集合に同一`(workspaceId, documentId)`が2件現れたなら、

| 条件 | 判定 |
|---|---|
| 基準版に存在する側 | **勝者**（incumbent）。変更しない |
| 基準版に存在しない側 | **敗者**（challenger）。振り直す |
| 両方が基準版に存在しない | 勝敗を決定できない。重複はerrorとするが振り直しを提案しない |
| 両方が基準版に存在する | 発生しない（Gitが単一ファイルへmergeするかconflictにする） |

第3行が、`--base`へmerge-baseではなく統合先先端を渡す理由である。merge-baseを基準にすると
両者とも新規となり、勝敗が付かない。

fork前から存在するIDは、両者が編集してもGitが単一ファイルへmergeするかconflictにするため、
現在集合に2件並ばない。したがって**2件並ぶのは独立生成のときだけ**であり、`semanticHash`による
推測を必要としない。ADR-037 Decision 2の「キーの有無で判定し、hash差から再利用を推測しない」という
方針と一貫する。

merge運用とrebase運用のどちらでも同じ規則が成立する。

### 4.3 承認済みREQ保護との関係

振り直し対象は定義上つねに「基準版に存在しない新規ID」である。要求SPEC仕様 §7の

> Git基準版に存在しない新規ファイルは変更前状態との比較対象外とする。

により、`safety.protectApprovedRequirements`に抵触しない。branch内で`approved`まで進んだREQを
振り直しても保護違反にならない。新規文書であるため`Revision History`への追記も要求しない。

### 4.4 採番規則

新IDは**基準版と現在集合の全IDの最大値+1**とする。

- 欠番を埋めない。「採番の連続性は要求しない。欠番は正常とする」と整合し、削除済みIDの
  再利用（配置・命名・探索規則 §4）も避けられる。
- 複数衝突時は、衝突した元IDの昇順に連番を割り当てる。決定論性を保つ。
- 桁数は`[0-9]{3,}`の範囲で必要に応じて繰り上げる。

### 4.5 振り直しの影響範囲と分担

Coreが関係索引から**完全に導出できる**書き換え箇所を`tracked`、本文中の文字列一致に依存し
**Coreが保証しない**箇所を`textual`とする。

| 対象 | 区分 |
|---|---|
| Frontmatter `id` | tracked |
| ファイル名（先頭IDとFrontmatter `id`の一致は必須） | tracked |
| `refines`／`requires`／`related`／`supersedes` | tracked |
| `covers`の規範文参照（`REQ-005:AC-01`） | tracked |
| TASK `addresses` | tracked |
| モノレポ修飾参照（`web::REQ-005`） | tracked |
| **本文中のMarkdownリンクと散文引用** | **textual** |
| **コード・テスト内のコメント、テスト名** | **対象外** |

規範文ID（`AC-01`）は文書ローカルであるため、文書IDが直れば連動して解決する。別問題としない。

`textual`が必要な理由は、Coreが文書間の正を`relations`とし、本文のMarkdownリンクを検査対象に
していないためである（参照・トレース・検証仕様 §2）。**とくにADRは散文中で番号引用され、
ファイル名変更によりリンクpathも壊れる**。したがって`textual`の探索は旧ID文字列と旧ファイル名の
双方を対象とし、Coreは列挙のみ、置換の可否は人間が判断する。

### 4.6 検出と適用の分離

`bitz check`は読取り専用であり、公開操作4つはすべて非変更系である。振り直しはSPECを書き換えるため、
Coreへ入れると5つ目の書込み操作となり、Core 1.0の輪郭が変わる。

そこで**検出と適用を分離**する。

- **Core**: 勝敗、提案する新ID、`tracked`／`textual`の書き換え箇所を`check`結果JSONへ出力する。
  逆索引は既に保持しており、新しい解析を要しない。
- **Skill／拡張プラグイン**: 出力を読んで適用し、commitする。

ADR-009の「SDDの段階管理やAIエージェントの進行は、これらの操作を呼び出す薄い拡張Skillとして
実現する」という方針と整合し、`check`の読取り専用契約を維持できる。

### 4.7 結果Schema

`check`結果へ`idCollisions`を追加する。Diagnostic Schema（ADR-021）は変更しない。勝敗と振り直し
候補は診断メッセージではなく構造化データであり、`selection`と同じ位置づけとする。

```json
"idCollisions": [
  {
    "workspaceId": "web",
    "documentId": "REQ-005",
    "incumbent": {"path": ".spec/requirements/REQ-005-cache.md"},
    "challenger": {"path": ".spec/requirements/REQ-005-login.md"},
    "proposedId": "REQ-014",
    "rewriteSites": [
      {"path": ".spec/requirements/REQ-005-login.md", "field": "id", "kind": "tracked"},
      {"path": ".spec/requirements/REQ-005-login.md", "field": "filename", "kind": "tracked"},
      {"path": ".spec/technical/TECH-003-session.md", "field": "relations.refines", "kind": "tracked"},
      {"path": ".spec/tasks/TASK-007-login.md", "field": "addresses", "kind": "tracked"},
      {"path": ".spec/decisions/ADR-004-token.md", "line": 42, "kind": "textual"}
    ]
  }
]
```

勝敗を決定できない場合、`proposedId`と`rewriteSites`を省略し、`incumbent`／`challenger`の代わりに
`instances`へ両方のpathを並べる。`SPEC-ID-DUPLICATE-001`／`failed`は従来どおり返す。

### 4.8 PR時のフロー

1. PR CIが`bitz check --full --base <integration-tip>`を実行し、`SPEC-ID-DUPLICATE-001`／`failed`
2. 結果JSONの`idCollisions`が敗者、提案新ID、書き換え箇所を示す
3. Skillが`tracked`を適用し、`textual`を提示する
4. commit、push、再CI、`passed`、merge

## 6. 採用しない案

| 案 | 不採用理由 |
|---|---|
| commit時刻で先勝ちを決める | 書き換え可能で非決定論的。rebaseとshallow cloneで結果が変わる |
| Coreへ`bitz renumber`を追加 | 公開操作がすべて非変更系という契約を破り、配布形態とdoctorへ波及する |
| branch／開発者ごとの番号レンジ予約 | Core 1.0が持たない調停と台帳の性格が入り、レンジ枯渇と設定同期の運用負荷が生じる |
| ULID等の衝突耐性IDへ変更 | 重複を設計から排除できるが、`REQ-[0-9]{3,}`の字句規則、ADR-005、ADR-013、人間可読性を全面的に見直すことになる |
| merge-baseを`--base`に維持し衝突検出を別invocationにする | 呼出しが2本になり、同一木に対する基準版が2つ存在する状態を持ち込む |
| `semanticHash`で同一性を判定 | ADR-037が正当なrenameの誤検出を理由に不採用としており、判断を覆す新事実がない |
| ファイル名を`<ID>.md`正規形へ強制しGitのadd/add conflictへ委ねる | slugによる可読性を失い、かつconflict解決を人手に戻すだけで振り直しは支援されない |
| 改番を表すFrontmatter項目（`renumberedFrom`、`x-renumbered-from`）を追加 | Gitから導ける情報をFrontmatterへ持ち込み統合後も陳腐化する。ADR-015 Decision 4および旧SPEC知見と同型。詳細は附録A.0 |
| Git rename検出で改番を認識する | 類似度閾値と`diff.renameLimit`に依存し、同一入力に対する決定論を失う |

## 7. 受入条件

- 同一workspaceで独立生成された同一IDを、merge結果とrebase後branchの双方で敗者側だけ特定できる。
- 基準版に両方が存在しない場合に、勝敗を決定せず`failed`を返し、誤った振り直しを提案しない。
- fork前から存在するIDを両者が編集した入力で、衝突として誤検出しない。
- `rewriteSites`の`tracked`をすべて適用した木が`SPEC-ID-DUPLICATE-001`を出さず、参照切れを生じない。
- `approved`まで進んだ新規REQを振り直しても承認保護に抵触しない。
- ADRを振り直したとき、`relations`が`tracked`で解決し、本文リンクが`textual`として列挙される。
- 同一入力から同一の`proposedId`と`rewriteSites`順序を再現できる。

P1適用後の受入条件は附録A.5を正とする。

## 8. 残るリスクと未決事項

### 8.1 振り直しレース

新IDを最大値+1で採るため、並行する2本のPRが同じ番号を取り合う。片方がmergeされると他方は
再度振り直しになる。収束はするが、並行度が高いと繰り返す。

Core側で完全には解消できない。merge queueによる直列マージで担保する運用前提とし、Coreは検出と
決定論のみを保証する。

### 8.2 未決事項

- 振り直しcommitとTASK `changes`境界の関係。境界検査の対象外とするか、`changes`へ含めるか。
- 同一内容がcherry-pickで両branchへ入った場合、Coreは独立生成と区別できない。振り直すと重複文書が
  残るため、人間の確認を要する旨をSkillの契約に含めるか。
- `--base <integration-tip>`へ統一した場合の、承認保護と状態遷移の検査範囲がmerge-base基準と
  厳密に一致するかの確認。

### IDDUP-001: 振り直しがSPEC削除と誤判定される（P1）

**指摘**

ADR-037 Decision 3と[参照・トレース・検証仕様](../03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md) §4は、
基準版に存在するキーが現在版に存在しない場合を**種別や状態を問わず**SPEC削除とし、
`SPEC-STATE-TRANSITION-001`／error／`failed`とする。

振り直しは`(workspaceId, documentId)`のキー自体を`REQ-005`から`REQ-014`へ変える。ADR-037 Decision 2が
renameとして扱うのはpath変更だけであり、**ID変更を表現できない**。したがって基準版が旧IDを含む状態で
`check`を実行すると、正当な振り直しが削除として拒否される。

影響範囲は限定されるが、最も影響が大きい箇所に当たる。

| 基準版 | 旧IDを含むか | 判定 |
|---|---|---|
| 統合先先端（CI、§4.2） | 含まない | 正常 |
| merge-base（従来CI） | 含まない | 正常 |
| **`HEAD`（既定、振り直しをcommitする前）** | **含む** | **誤ってerror** |
| `HEAD~n`（branch内の先行commit） | 含む | 誤ってerror |

すなわち、Skillが振り直しを適用した直後に自身の作業を`bitz check`で確認する経路が通らない。

**修正候補**

| 案 | 内容 | 評価 |
|---|---|---|
| 案1 | 敗者へ`x-renumbered-from`を記録し、Coreは旧IDのキー消失をrenameとして扱う | 推測ではなく明示宣言であり、ADR-037の「hash差から再利用を推測しない」方針と両立する。Frontmatter共通仕様へ1項目追加 |
| 案2 | 振り直しを単一commitで完結させる運用規約に限定し、Coreを変更しない | 未commit状態の`check`が通らず、Skillが自己検証できない。運用の遵守に依存し脆い |
| 案3 | 削除検出を「統合先へ到達済みのSPEC」に限定する | Coreは到達済みかを知らず、統合先の指定を新たな入力として要求することになる |
| 案4 | 振り直し時だけ削除検査を抑止する`check`オプションを追加 | 安全検査の明示的な無効化であり、セキュリティとガバナンス設計の方針に反する |

同一キーに複数pathを持つ場合の定義だけとなり、ADR-037のDecisionもFrontmatter Schemaも変更しない。
案1・案2の不採用理由と案5の詳細は附録A.0およびA.1を正とする。

受入条件は附録A.5へ集約した。

### IDDUP-004: 振り直しと状態遷移契約・置換語彙の関係（P2）

**指摘**

振り直しはstatusを変えないため、§6.3の遷移図に新しいedgeは要らない。しかし次の3点が未定義である。

1. 振り直しが`supersedes`による置換ではないこと。ADR-012は置換済みREQ・TECHの適用を遮断するため、
   振り直しを置換と誤って記録すると、正当な文書が適用対象から外れる。
2. 終端状態の文書を振り直せるか。ADR-036は終端状態からの再オープンを禁止するが、ID変更は再オープンでは
   ない。`rejected` REQや`cancelled` TASKが敗者となる場合の可否が読み取れない。
3. 振り直し後の文書が統合先へ初めて現れるときの遷移。`[new] -> approved`は§6.3で許可済みであり、
   追加の裁定を要しないが、明記がない。

**修正候補**

振り直しを「同一文書の識別子変更であり、置換でも状態遷移でもない」と定義し、次を明記する。

- `supersedes`、`superseded`、`outdated`、`rejected`のいずれも使用しない。
- 終端状態の文書も振り直しの対象とする。理由欄と`Revision History`は変更しない。
- 振り直し後の文書は、統合先から見て`[new]`からの遷移として扱う。

**受入条件**

- 振り直した`rejected` REQが、置換済み扱いにならず、Historyとして保持され続ける。
- 振り直しが§6.3のいずれのedgeにも該当しないことを本文から確認できる。

## 附録A. P1修正案（適用可能な差分）

作成日: 2026-09-01。IDDUP-001〜003について、正本へそのまま適用できる修正を示す。

### A.0 方針の見直しと`renumberedFrom`の撤回

§9 IDDUP-001は`x-renumbered-from`、次いでCore共通項目`renumberedFrom`を推奨した。**両案を撤回する。**

撤回の理由は3点ある。

1. **既存の不採用判断と同型である。** [旧SPEC知見の評価](../03.詳細設計/02_SPECファイル規定/09_旧SPEC知見の評価.md) §4は
   「成果物ごとのversion、updated」を「Git履歴と重複し、同期ずれを生むため不採用」とし、
   ADR-015 Decision 4も独自`version`・`updated`を導入しないと定めた。`renumberedFrom`は
   Gitの変更集合から導ける情報をFrontmatterへ持ち込み、統合後は無効になっても残り続ける。同じ型の負債である。
2. **Digestの例外分類を生む。** 削除判定にだけ使い、Context DigestとProjection Digestへは影響させない、
   という例外をSerializerとDigest計算へ持ち込む必要がある。
3. **そもそも正規手順では不要である。** A.1のとおり、振り直しを合流後の木で行えば旧IDのキーは消えない。
   宣言を必要とするのは非推奨の手順だけである。

`x-`拡張の規則（[Frontmatter共通仕様](../03.詳細設計/02_SPECファイル規定/03_Frontmatter共通仕様.md) §7の
「Coreは値を変更せず保持し、合否判定へ使用しない」）は**維持する**。この規則は健全であり、
本設計はこれを迂回しない。

改番の人間向け記録は`Revision History`へ置く。ADR-015 Decision 8により`Revision History`は
非規範メタデータであり、Constraint Ledger、coverage、Context Digestの意味集合から既に除外されている。
新しい例外を作らずに済む。

### A.1 IDDUP-001: 改番を合流後の木で行う

#### A.1.1 正規手順の確定

振り直しをどの木の上で適用するかで結果が変わる。**合流後の木で行うことを正規手順とする。**

| 適用時点 | 基準版`HEAD`のキー`REQ-005` | 振り直し後の現在集合 | 判定 |
|---|---|---|---|
| **合流をcommitした後（正規）** | 敗者・勝者の2件 | 勝者`REQ-005`と`REQ-014` | **キーが残るため削除にならない**。基準版の重複だけを規則化すればよい |
| 合流をcommitせず一括commit | 敗者1件 | 勝者`REQ-005`と`REQ-014` | キーは残るが、基準版の敗者と現在版の勝者が同一文書と誤対応する |
| 合流前の自branch | 敗者1件 | `REQ-014`のみ | 旧キーが消え、SPEC削除として`failed`となる |

正規手順では、勝者が旧IDを保持し続けるためキーが消えない。したがって**ADR-037 Decision 3の削除規則を
変更する必要がなく、新しいFrontmatter項目も要らない**。必要な追加規則は、基準版が同一キーに複数pathを持つ
状態の定義だけである。

第2行は、合流と振り直しを1つのcommitへまとめた場合に、基準版の敗者（例えば`rejected`）と現在版の勝者
（例えば`draft`）を同一文書として遷移検査し、`rejected -> draft`を禁止遷移として誤検出する経路である。
第3行は合流前に振り直した場合である。いずれも正規手順を定義し、`Integrate`（A.2）で合流を先行させることで
回避する。回避できなかった場合はerrorとなり、利用者は合流をcommitしてから再実行する。

#### A.1.2 Frontmatter共通仕様 §5 状態遷移

現行§5は「遷移検査には[Git基準版]を使用する」とだけ述べ、**基準版の文書と現在版の文書をどう対応付けるかを
述べていない**。対応付け規則はADR-037にしか存在せず、`id`と`status`を所有する本仕様から読み取れない。
仕様検討段階の欠落として補う。

**before**

```text
禁止遷移は`SPEC-STATE-TRANSITION-001`／error／`failed`とする。遷移検査には
[Git基準版](../../02.設計書/10_決定記録/ADR-025_Git基準版とcheck明示対象の確定.md)を使用する。
基準版を利用できない場合も現在値の語彙は検査するが、過去状態を推測して遷移合格を宣言しない。
```

**after**

```text
禁止遷移は`SPEC-STATE-TRANSITION-001`／error／`failed`とする。遷移検査には
[Git基準版](../../02.設計書/10_決定記録/ADR-025_Git基準版とcheck明示対象の確定.md)を使用する。
基準版を利用できない場合も現在値の語彙は検査するが、過去状態を推測して遷移合格を宣言しない。

基準版の文書と現在版の文書は`(workspaceId, documentId)`で対応付ける。pathの一致は要求せず、
pathだけが異なる場合はrenameとして同一文書に扱う。対応付けと削除の効果は

基準版で同一の`(workspaceId, documentId)`が複数pathへ解決する場合、そのキーの対応付けを一意に定められない。
このとき当該キーの遷移検査と削除判定を実施不能とし、`SPEC-BASE-AMBIGUOUS-001`／warning／
`passed_with_warnings`とする。現在集合の重複検査、現在値の語彙検査、他キーの遷移・削除判定は
通常どおり実施する。基準版の重複は、並行branchのID衝突を解決する過程で一時的に生じる
（[UC-13](../../02.設計書/09_ユースケース設計.md)）。
```

#### A.1.3 Frontmatter共通仕様 §2 共通項目

現行の`id`の説明は「文書の安定ID」だけであり、**一意性の範囲と、IDを変更してよい条件が本仕様にない**。
一意性は[配置・命名・探索規則](../03.詳細設計/02_SPECファイル規定/01_配置・命名・探索規則.md) §4、
改番の可否はどこにも書かれていない。`id`を所有する本仕様へ集約する。

**before**

```text
`title`は1行で1文字以上120文字以下とする。配列は重複を許さず、正規出力ではIDまたはパスの辞書順に並べる。
```

**after**

```text
`title`は1行で1文字以上120文字以下とする。配列は重複を許さず、正規出力ではIDまたはパスの辞書順に並べる。

`id`はworkspace内で一意な安定識別子とし、意味を持たない。ディレクトリ移動、ファイル名変更、本文改訂で
変更しない。ID形式と一意性の範囲は[配置・命名・探索規則](01_配置・命名・探索規則.md) §4を正とする。

`id`を変更してよいのは、並行branchのID衝突を解決する改番だけとする。改番はGit基準版に到達していない
文書に限り、基準版に存在する文書のIDを変更してはならない。基準版に存在するIDを持つ文書が現在版から
```

### B.1 IDDUP-001-a: `idCollisions`の正本定義

**指摘**

§5の反映案は参照・トレース・検証仕様へ「`idCollisions`と勝敗規則、`tracked`／`textual`の定義、
Diagnostic 1行を追加」と書くが、附録A.1.5はDiagnostic 1行しか示していない。一方でA.3.2のUC-13は
**正本**として同仕様 §4を指す。附録Aをそのまま適用すると、UC-13の正本が存在しない定義を指す。

`idCollisions`は§4.7に例示があるだけであり、要素の順序、`tracked`／`textual`の判定根拠、
`check`が書き換えを行わないことのいずれも正本にない。UC-13だけが規則を持つ状態は、
「ユースケースは正本を指し、規則は詳細設計が持つ」という既存の分担に反する。

**設計案**

参照・トレース・検証仕様 §4の「基準版と現在版のSPECは……ADR-037を正とする。」の段落直後へ次を挿入する。
`selection`・`revision`と同じ結果JSONの構造化データとし、Diagnostic Schema（ADR-021）は変更しない。

```text
現在集合で同一の`(workspaceId, documentId)`が2件以上へ解決する場合、`SPEC-ID-DUPLICATE-001`に加えて
勝敗と改番候補を結果JSONの`idCollisions`へ記録する。`idCollisions`はDiagnosticではなく、`selection`と
同じ構造化データとする。`check`はこの出力に基づく書き換えを行わない。適用はSkill／拡張が担う（UC-13）。

勝敗は基準版での有無だけで決める。commit時刻、`semanticHash`、Git rename検出を使用しない。

| 基準版での有無 | 判定 |
|---|---|
| 基準版に存在する | `incumbent`。IDを変更しない |
| 基準版に存在しない | `challenger`。改番の対象とする |
| いずれも存在しない | 勝敗を決定しない。`instances`へ全pathを列挙し、`proposedId`と`rewriteSites`を省略する |
| 2件以上が存在する | 基準版の重複として`SPEC-BASE-AMBIGUOUS-001`とし、当該キーの勝敗を決定しない |

`challenger`の`proposedId`は次のとおり決める。

- 番号空間は種別prefixとworkspaceの組ごとに独立とする。`REQ`の採番に`TECH`のIDを参照しない。
- 候補集合は、基準版と現在集合に現れる同一workspace・同一種別の全IDとする。Git履歴を走査せず、
  基準版と現在集合のどちらにも現れないIDは考慮しない。過去に削除されたIDの再利用防止は
  [配置・命名・探索規則](01_配置・命名・探索規則.md) §4のとおりGitレビューの責務であり、Coreは保証しない。
- 数値部を10進として解釈し、その最大値+1を新しい数値とする。欠番を埋めない。
- 桁数は、改番前IDの桁数と、新しい数値の表現に必要な桁数の大きい方とし、左を`0`で埋める。
- 同一keyに複数の`challenger`があるとき、および複数キーが同時に衝突するときは、
  `(workspaceId, documentId, path)`の辞書順に1つずつ数値を増やして割り当てる。

数値部が既存の最大値より大きいため、ゼロ埋め幅が異なる既存ID（`REQ-015`と`REQ-0015`は別IDとする）とも
文字列として一致しない。

`rewriteSites`は、Coreが関係索引から完全に導出できる箇所を`tracked`、本文の文字列一致に依存し
Coreが保証しない箇所を`textual`とする。

| 対象 | 区分 |
|---|---|
| Frontmatter `id`、ファイル名 | `tracked` |
| `refines`／`requires`／`related`／`supersedes` | `tracked` |
| `covers`の規範文参照、TASK `addresses`、`<workspace-id>::`修飾参照 | `tracked` |
| 本文中のMarkdownリンクと散文引用（旧IDと旧ファイル名の双方を探索する） | `textual` |
| コード・テスト内のコメント、テスト名 | 対象外 |

規範文IDは文書ローカルであり、文書IDの改番に連動して解決する。

出力順序は`workspaceId`、`documentId`の辞書順とし、`rewriteSites`は`tracked`を先、`textual`を後、
それぞれ`path`の辞書順、同一pathでは`field`の辞書順、`textual`は`line`の昇順とする。
同一入力から同一の`proposedId`と同一順序を再現する。
```

`idCollisions`の要素構造は§4.7の例を正とし、`instances`は勝敗を決定しない場合にだけ現れる。

### B.2 IDDUP-001-b: `Integrate`の`--base`必須化

**指摘**

附録A.1.1の表は基準版を`HEAD`として3行を評価するが、§4.2とA.3.2のUC-13は`--base <統合先先端>`を渡す。
**同じ木に対して2つの基準版がありうる**ため、どちらを正規とするかで結果が変わる。

|---|---|---|---|
| `--base <統合先先端>` | 勝者だけを含む | 決定できる | 正しい |
| 既定`HEAD`（合流commit） | 勝者と敗者の両方を含む | 決定できない | 当該キーは実施不能 |
| 既定`HEAD`（合流を記録していない自branch先端） | 敗者だけを含む | **誤って敗者を勝者と判定する** | **基準版の敗者と現在版の勝者を同一文書へ誤対応する** |

第3行がA.1.1第2行に対応する。A.1.1は「回避できなかった場合はerrorとなり」と述べるが、
これは保証されない。敗者が`rejected`で勝者が`draft`なら禁止遷移として観測できるが、両方が`draft`なら
**誤対応のまま通過する**。承認保護も同じ基準版を使うため、敗者が`approved`であれば
`SPEC-SAFETY-APPROVED-001`の偽陽性、逆であれば見逃しになる。Coreは合流の有無を入力から知り得ない。

**設計案**

Coreに検出を求めず、**`Integrate`の入力契約で防ぐ**。B.1で挿入した本文の末尾へ次を追加する。

```text
`Integrate`段階の`check`は`--base <統合先先端>`を明示する。未指定（`HEAD`既定）で得た結果を、
ID衝突の勝敗、改番の適用、承認保護の根拠にしない。Coreは合流をGitへ記録したかを入力から判定できず、
合流前の基準版では敗者を勝者と誤って判定する。
```

UC-13の事前条件へ「統合先先端をrevisionとして解決でき、`--base`へ明示できる」を加え、
代替・例外フローの第1項を次へ置き換える。

```text
- `--base`を明示せずに実行した結果は勝敗の根拠にしない。合流を記録する前に改番した場合は、旧IDが
  基準版にだけ残るため`SPEC-STATE-TRANSITION-001`／`failed`となる。利用者は合流を記録してから再実行する。
```

これによりA.1.1第2行は「発生しても正規手順の根拠にならない実行」となり、Coreの契約を増やさずに閉じる。

### B.3 IDDUP-001-c: `SPEC-BASE-AMBIGUOUS-001`の効果

**指摘**

附録A.1.2は基準版の重複を`warning`／`passed_with_warnings`とし、当該キーの遷移検査と削除判定を
実施不能とする。ここに2つの問題がある。

1. **通過statusのまま安全検査が抜ける。** 改番を適用し終えた木を既定`HEAD`（合流commit）基準で
   `check`すると、現在集合の重複は解消しているため`SPEC-ID-DUPLICATE-001`が消え、
   `SPEC-BASE-AMBIGUOUS-001`だけが残る。`passed_with_warnings`はフローの通過statusであるため
   （SDDプロセス設計 §2、ADR-035）、**勝者の遷移検査と削除判定を実施しないまま`Done`へ進める**。
   これは§6が案4「振り直し時だけ削除検査を抑止するオプション」を
   「安全検査の明示的な無効化」として退けた理由と、実質的に同じ結果になる。
2. **承認保護の扱いがない。** `safety.protectApprovedRequirements`も同じ基準版を使うが、
   A.1.2は遷移検査と削除判定にしか触れていない。基準版の対応付けが一意でないなら承認保護も実施できない。

既存の正本では、検査を実施できない場合は`blocked`とする。Git不在でTASK境界を検査できない
`SPEC-TASK-BOUNDARY-002`が`error`／`blocked`であり、「Gitが利用できない場合は境界検査を`blocked`とし、
暗黙に通過させない」と明記されている。基準版の重複はこれと同型である。

**設計案**

severityを`error`、`resultStatus`を`blocked`へ変更し、承認保護を実施不能の対象へ含める。
附録A.1.2の追加段落の後半を次へ置き換える。

```text
基準版で同一の`(workspaceId, documentId)`が複数pathへ解決する場合、そのキーの対応付けを一意に定められない。
このとき当該キーの遷移検査、削除判定、承認済みREQ保護を実施不能とし、`SPEC-BASE-AMBIGUOUS-001`／error／
`blocked`とする。暗黙に通過させない。現在集合の重複検査、現在値の語彙検査、他キーの遷移・削除・保護判定は
通常どおり実施する。基準版の重複は、合流をGitへ記録してから改番を記録するまでの間に既定`HEAD`を
基準版とした場合に生じる。`Integrate`は`--base <統合先先端>`を明示するため、正規手順では発生しない
（[UC-13](../../02.設計書/09_ユースケース設計.md)）。
```

附録A.1.5のDiagnostic行を次へ置き換える。

```text
| `SPEC-BASE-AMBIGUOUS-001` | error | `blocked` | 基準版で文書IDが重複し、対応付け、遷移・削除判定、承認保護を実施できない |
```

`blocked`が正規手順を止めないことは次で確認できる。

| 実行時点 | 基準版 | 現在集合 | 結果 |
|---|---|---|---|
| 合流後・改番前、`--base <統合先先端>` | 勝者のみ | 重複あり | `SPEC-ID-DUPLICATE-001`／`failed` |
| 改番後、`--base <統合先先端>` | 勝者のみ | 重複なし | 通過 |
| 合流後・改番前、既定`HEAD` | 重複あり | 重複あり | `failed`（重複が優先） |
| 改番後・改番commit前、既定`HEAD` | 重複あり | 重複なし | **`blocked`**。誤った通過を防ぐ |
| 改番commit後、既定`HEAD` | 重複なし | 重複なし | 通過 |

第4行だけが`blocked`となり、利用者は`--base`を明示するか改番をcommitすれば解消する。

UC-13の該当する代替・例外フローも`warning`から`error`／`blocked`へ改める。

### B.5 IDDUP-002-a: UC-06・UC-07への反映差分

```text
9. 統合先branchの先端を作業branchへ合流させてGitへ記録し、合流後の木へ
```

### B.6 IDDUP-002-b: `Integrate`とPR mergeの前後関係

**指摘**

附録A.2.1は`Integrate`を`Done`の**前**へ置く。一方、A.3.2のUC-13は基本フロー第7項を
「利用者は再度`check`を実行し、通過statusを確認してから**merge**する」とし、§4.8も第4項をmergeとする。
`Done`はTASKを`done`へ変更し、Revision Historyを更新し、`bitz check <TASK-ID>`を経て完了結果を
Gitへ記録する段階である。したがって現在の記述では、**統合先へmergeした後にDoneのcommitを作る**ことになり、
そのcommitはPRに含まれない。

**設計案**

`Integrate`の完了条件を「統合先先端を基準版とする再検査が通過status」までとし、
**統合先branchへのmergeを段階に含めない**。理由は3点ある。

- Coreはbranch、merge、rebase、commit、pushを実行しない。mergeを段階の完了条件へ置くと、
  段階の終端がCoreの契約外の操作に依存する。
- `Done`のcommitはPRに含める必要があり、mergeはその後にしか置けない。
- merge queueによる直列マージを前提とする以上（§8.1）、mergeの実行時点はフローの外側にある。

附録A.2.1のステップ8末尾へ次を追加する。

```text
`Integrate`は再検査の通過をもって完了とし、統合先branchへのmergeを含まない。mergeは`Done`を記録した後に
[運用設計](06_運用設計.md)の手順で行う。
```

UC-13基本フロー第7項を次へ置き換える。

```text
7. 利用者は`--base <統合先先端>`で再度`check`を実行し、通過statusを確認する。統合先branchへのmergeは
   UC-13の範囲外とし、`Done`の記録後に行う。
```

UC-13の完了条件を「現在集合に重複がなく、`tracked`をすべて適用した木が参照切れを生じず、
統合先先端を基準版とする再検査が通過statusである。」へ改める。§4.8第4項の「merge」も同様に、
`Done`記録後の運用として位置づける。

### B.7 IDDUP-002-c: 合流commitと改番commitの分離

**指摘**

附録A.1.1は「合流をcommitせず一括commit」を非正規としながら、正規手順を強制する規約が正本にない。
SDDプロセス設計 §1は「変更を伴うIntent、Requirement Review、Design Review、Implement、Done
またはStopped」を個別commitへ記録すると列挙するが、`Integrate`が列挙にない。

**設計案**

SDDプロセス設計 §1第2段落の列挙へ`Integrate`を加え、段落末へ次を追加する。

```text
`Integrate`では、統合先先端の合流と改番を別のcommitへ記録し、1つのcommitへまとめない。合流を記録する前に
改番すると旧IDが基準版にだけ残り、SPEC削除として拒否される。合流と改番を同一commitへまとめると、
基準版の敗者と現在版の勝者を同一文書として誤対応する。いずれもCoreは入力から判別できないため、
commit単位の規約として分離する。
```

これによりB.2の入力契約（`--base`必須）とcommit規約の双方から正規手順が支えられ、
どちらか一方の逸脱では誤対応に至らない。

### B.8 IDDUP-002-d: `Integrate`からの取り止め

**指摘**

SDDプロセス設計 §2.1は「`Done`へ到達する前のどの段階でも」`Stopped`へ終了できるとする。
`Integrate`を`Done`の前へ挿入すると`Integrate`も対象になるが、合流commitが既に存在する状態での
取り止めが読み取れない。取り止めても合流commitは自branchに残る。

**設計案**

§2.1へ1段落を追加する。新しい状態も操作も追加しない。

```text
`Integrate`の段階でも取り止められる。合流commitと改番commitは自branchの履歴に残り、統合先へは
mergeしないため、統合先の内容へ影響しない。取り止め時にこれらのcommitをrevertすることは要求しない。
起点文書の`Rejection Rationale`または`Cancellation Rationale`へ、改番済みIDと取り止め理由を記録する。
```

`SPEC-BASE-AMBIGUOUS-001`／error／`blocked`とする。暗黙に通過させない。現在集合の重複検査、
現在値の語彙検査、他キーの遷移・削除・保護判定は通常どおり実施する。

承認済みREQ保護を実施不能の対象へ含める点は、附録A.1.2が遷移検査と削除判定にしか触れていなかった
欠落の補完であり、案の選択とは独立に必要な修正である。承認保護も同じ基準版の対応付けを使う。

**根拠**

1. 検査を実施できない場合を`blocked`とし暗黙に通過させない扱いは、Git不在でTASK境界を検査できない
   `SPEC-TASK-BOUNDARY-002`（error／`blocked`）と同型である。`blocked`を返す既存診断は
   `SPEC-CONFIG-SCHEMA-001`、`SPEC-VERIFY-BLOCKED-001`を含めすべて`error` severityであり、例外を作らない。
2. `blocked`の定義は[共通アーキテクチャ](../02.設計書/01_共通アーキテクチャ.md) §5の**「前提不足」**であり、
   「対応付けの前提が欠ける」という本件の性格に意味論として一致する。
3. warningとした場合、改番を適用した後・改番をcommitする前に既定`HEAD`で検査すると、現在集合の重複が
   解消しているため`SPEC-ID-DUPLICATE-001`が消え、本診断のwarningだけが残って
   `passed_with_warnings`となる。これはフロー通過statusであるため、**勝者の遷移検査・削除判定・
   承認保護を実施しないまま`Done`へ進める**。§6が案4「振り直し時だけ削除検査を抑止するオプション」を
   *安全検査の明示的な無効化*として退けた判断と、明示的でないだけで結果が同じになる。
4. 正規手順は`--base <統合先先端>`を渡すため、統合先には勝者しか存在せず本診断は発火しない。
   `blocked`は通過経路を止めない。

**中間案が存在しないこと**

`warning`／`blocked`という組み合わせは[ADR-021](../02.設計書/10_決定記録/ADR-021_Diagnostic-severity・操作status・source-Schemaの分離.md)
Decision 4が禁じている。同項は「`warning`だけが存在する操作は`passed_with_warnings`とする」と定め、
`blocked`への対応を`error` severityにだけ認めている。したがって選択肢は
`warning`／`passed_with_warnings`と`error`／`blocked`の2つに限られ、ADR-021を改訂しない限り
中間の強度を取れない。ADR-021の改訂は本件1件のためにDiagnostic契約の基盤を変更することになるため行わない。

**発火条件と各時点の結果**

| 実行時点 | 基準版 | 現在集合 | 結果 |
|---|---|---|---|
| 合流後・改番前、`--base <統合先先端>` | 勝者のみ | 重複 | `SPEC-ID-DUPLICATE-001`／`failed` |
| 改番後、`--base <統合先先端>` | 勝者のみ | 重複なし | 通過 |
| 合流後・改番前、既定`HEAD` | 重複 | 重複 | `failed`（集約順位により`blocked`を吸収） |
| 改番後・改番commit前、既定`HEAD` | 重複 | 重複なし | **`blocked`** |
| 改番commit後、既定`HEAD` | 重複なし | 重複なし | 通過 |

第4行が本裁定で挙動の変わる唯一の時点である。`--base <統合先先端>`を渡すか改番をcommitすれば解消し、
手詰まりにならない。

**受容するコスト**

- `blocked`は`failed`・`error`と同じく再現用の最小レポートを自動保存する対象であるため
  （共通アーキテクチャ §5）、第4行の一過性の状態でレポートが1件生成される。
- Core検査を迂回して重複IDのままcommitされた履歴が存在する場合、そのcommitが`HEAD`である限り
  既定`check`は当該キーで`blocked`となる。解消には修正のcommit、または重複のないcommitへの
  `--base`明示を要する。

**併せて不採用とする案**

基準版の重複pathから代表を1つ選び（例: path辞書順最小）対応付ける案は採らない。誤った側と
対応付けたときに誤った遷移判定を静かに返すためであり、ADR-037の「キーの有無で判定し、hash差から
再利用を推測しない」方針と衝突する。ADR-038のAlternativesへ記録する。

**ADR-038への反映**

附録A.4のDecision 6を次へ置き換える。

```text
6. 基準版で同一`(workspaceId, documentId)`が複数pathへ解決する場合、当該キーの対応付け、状態遷移検査、
   削除判定、承認済みREQ保護を実施不能とし、`SPEC-BASE-AMBIGUOUS-001`／error／`blocked`とする。
   暗黙に通過させない。
```

### C.2 甲-1: 先勝ちの基準（裁定済み・2026-09-01）

**裁定**: 案A、すなわち**基準版（統合先branchの先端）に存在する側を勝者**とする。commit時刻、
`semanticHash`、Git rename検出を判定に使用しない。§4.2の判定表は本裁定とC.1で置き換える。

**確定する判定表**

| 条件 | 判定 |
|---|---|
| 基準版に存在する側 | 勝者（incumbent）。IDを変更しない |
| 基準版に存在しない側 | 敗者（challenger）。改番する |
| 両方が基準版に存在しない | 勝敗を決定しない。`instances`を返し、`proposedId`と`rewriteSites`を省略する。重複は`SPEC-ID-DUPLICATE-001`／`failed` |
| 基準版で当該キーが複数pathへ解決する | 対応付け不能。`SPEC-BASE-AMBIGUOUS-001`／error／`blocked`（C.1） |

**根拠**

1. **統合済みのIDを動かさない。** 統合先に存在するIDは、他のPR、他のbranch、merge済みのコード・テスト・
   散文から参照され得る。勝者を統合先側に固定すれば、改番はまだ誰も参照していない新規文書にだけ及ぶ。
   これが§4.3（承認済みREQ保護に抵触しない）と附録A.1.3（「基準版に存在する文書のIDを変更してはならない」）
   を同時に成立させる。commit時刻を基準にすると、統合済みのIDが敗者になり得る。
2. **決定論を満たす。** 時刻は書き換え可能でrebaseとshallow cloneにより変動するが、基準版での有無は
   既存のGit基準版（ADR-025）と`(workspaceId, documentId)`索引（ADR-037）だけで判定できる。
   同じ木と同じ基準版から常に同じ答えが出る。
3. **新しい解析を要さない。** Coreは基準版索引と現在版索引を既に保持しており、勝敗判定に
   新しい入力機構、永続台帳、Git履歴走査を追加しない。

**衝突の観測時点**

2本のPRがどちらもmergeされていない間は、各PRの木に自分の文書しかないため衝突は観測されない。
一方がmergeされて初めて、他方が統合先先端を合流させた時点で2件並ぶ。したがって**衝突は必ず
「片方が既に統合済み」の形で現れ**、勝敗が付かない状況は正規手順では生じない。

**§4.2判定表第4行の訂正**

§4.2の原文は第4行を「両方が基準版に存在する｜発生しない（Gitが単一ファイルへmergeするかconflictにする）」
としていたが、**これは誤りである**。§3.1のとおり`REQ-005-cache.md`と`REQ-005-login.md`はslugが異なるため
Gitはadd/add conflictを出さず両方をmergeする。したがって合流commitのtreeには同一IDのファイルが2件入り、
既定`HEAD`を基準版とすれば「両方が基準版に存在する」状態が現実に生じる。付されていた根拠は
fork前から存在するIDには当てはまるが、独立生成されたIDには当てはまらない。§3.1と§4.2が矛盾していた。
訂正後の扱いはC.1の`SPEC-BASE-AMBIGUOUS-001`／error／`blocked`とする。

**受容する性質**

- 勝敗はmerge順に依存する。同じ2本のPRでも、先にmergeされた側が勝者になる。これは非決定論ではなく
  先勝ち規則の定義そのものである。
- 改番レースは残る（§8.1）。Core側では解消せず、merge queueによる直列マージを運用前提とする。

**不採用**

| 案 | 不採用理由 |
|---|---|
| 勝敗を判定せず`instances`の列挙に留める | Coreは最小になるが、「PR時点で決定論的に解決する」という本提案の目的が失われ、改番対象の選択が人間の判断へ戻る。IDDUP-001は人間が改番する以上そのまま残るため、甲-2・甲-4・甲-5の必要性も減らない |
| commit時刻の先後で決める | 非決定論であり、統合済みのIDが敗者になり得る（§6） |

### C.3 甲-2: 改番を合流後の木で行う（裁定済み・2026-09-01）

**裁定**: 案5、すなわち**統合先との合流をGitへ記録した後の木で改番する**ことを正規手順とする。
ADR-037のDecisionを変更せず、Frontmatter Schemaへも項目を追加しない。

**確定する規則**

改番は`(workspaceId, documentId)`のキー自体を変えるが、勝者が旧IDを保持し続けるため、
基準版のキーは現在版から消えない。したがってADR-037 Decision 3の削除規則は発動しない。

| 改番の適用時点 | `--base <統合先先端>`のキー`REQ-005` | 改番後の現在集合 | 削除判定 |
|---|---|---|---|
| 合流を記録した後（正規） | 勝者として存在する | 勝者`REQ-005` ＋ `REQ-014` | 発動しない |
| 合流前の自branch | 統合先とは無関係 | `REQ-014`のみ | 自branch基準では旧キーが消え`failed` |

より正確には、**敗者の`REQ-005`は統合先の基準版に一度も存在しない**。統合先の`REQ-005`は勝者のもので
あり、改番後も勝者はそこに残る。削除判定は敗者を見ていない。

**根拠**

1. ADR-037 Decision 2がrenameとして扱うのはpath変更だけであり、ID変更を表現できない。案5は
   この制約を回避するのではなく、**ID変更が削除として観測されない木の上で行う**ことで成立させる。
2. 追加で必要な規則は、基準版が同一キーに複数pathを持つ場合の定義だけであり、C.1で確定済みである。
3. ADR-037のDecisionもFrontmatter Schemaも変更しないため、影響範囲が最小になる。

**受容するコスト**

手順の前後関係が守られないと拒否される。これは欠点ではなく設計意図であり、乙-2（`--base`の扱い）と
附録B.7（合流commitと改番commitの分離）が同じ前後関係を別の側から支える。

**不採用**

| 案 | 不採用理由 |
|---|---|
| 案1 改番宣言項目（`renumberedFrom`）を追加 | C.4のとおり |
| 案2 単一commitで完結させる運用規約 | 未commit状態の`check`が通らずSkillが自己検証できない。運用の遵守だけに依存し脆い |
| 案3 削除検出を統合先到達済みSPECへ限定 | Coreは基準版が統合先かを判定できず、統合先の指定を新たな入力として要求することになる |
| 案4 改番時だけ削除検査を抑止するオプション | 安全検査の明示的な無効化であり、セキュリティとガバナンス設計の方針に反する |

### C.4 甲-3: 改番を表すFrontmatter項目（裁定済み・2026-09-01）

**裁定**: `renumberedFrom`と`x-renumbered-from`を**ともに撤回し、Frontmatter項目を追加しない**。
改番の人間向け記録は`Revision History`へ置く。`x-`拡張を合否判定へ使用しない規則
（Frontmatter共通仕様 §7）は維持し、迂回しない。

**根拠**

1. **既存の不採用判断と同型である。** [旧SPEC知見の評価](../03.詳細設計/02_SPECファイル規定/09_旧SPEC知見の評価.md) §4は
   「成果物ごとのversion、updated」を「Git履歴と重複し、同期ずれを生むため不採用」とし、
   ADR-015 Decision 4も「成果物ごとの独自`version`や`updated`は導入しない」と定める。`renumberedFrom`は
   Gitの変更集合から導ける情報をFrontmatterへ持ち込み、統合後は無効になっても残り続ける。
2. **Digestの例外分類を生む。** [Context Resolution仕様](../03.詳細設計/02_SPECファイル規定/10_Context%20Resolution仕様.md) §8.1は
   「`semanticHash`は正規化Frontmatterと`Revision History`を除く現行本文から計算する」と定め、
   `CTX-STALE-001`の根拠もSemantic IR、Frontmatter、edgeの差分としている。すなわち**Frontmatterは
   `semanticHash`に含まれる**ため、項目を追加すればContext Digestが変わる。「削除判定にだけ使い
   Digestへは影響させない」扱いを実現するには、SerializerとDigest計算へ例外を持ち込むほかない。
3. **正規手順では不要である。** C.3の案5では旧IDのキーが消えない。宣言を必要とするのは非推奨の手順だけである。
4. `x-renumbered-from`はFrontmatter共通仕様 §7の「Coreは値を変更せず保持し、合否判定へ使用しない」に反する。

`Revision History`はADR-015 Decision 8により非規範メタデータとして、Constraint Ledger、coverage、
Context Digestの意味集合から既に除外されている。新しい例外を作らずに済む。

**附録A.5の受入条件の訂正**

附録A.5の次の行は成立しないため置き換える。

```text
- 改番によりContext DigestとProjection Digestが変化しない（`Revision History`はADR-015 Decision 8により
  意味集合から除外済み）。
```

改番は`id`と関係参照を変更し、Frontmatterは`semanticHash`に含まれるため、当該文書を含むContext Digestは
変化する。またContext Resolution仕様 §8.1は「履歴だけの訂正ではContext Digestを変えず、
**Projection Digestと`fileHash`を変える**」と明記しており、`Revision History`への1行追記は
Projection Digestを変える。次へ置き換える。

```text
- `Revision History`への追記だけではContext Digestが変化しない。改番による`id`と関係参照の変更は
  Context Digestを変える。
```

### C.5 甲-4: `Integrate`段階の追加（裁定済み・2026-09-01）

**裁定**: 案1、すなわち開発フローの骨格へ`Integrate`を追加し、
`Pre-check -> Implement -> Post-check -> Verify -> Human Review -> Integrate -> Done`とする。
ADR-028はADR-033の3点記録による部分改訂とし、`accepted`のまま置換しない。

**確定する規則**

- `Integrate`が他段階と異なるのは、基準版に統合先branchの先端を用いる点だけである。ID衝突は自branchの
  現在集合だけでは観測できず、合流した木の上でしか勝敗が決まらない（C.2）。
- **`Integrate`でCoreが実行するのは`bitz check`だけとする。** Coreはbranch、merge、rebase、commit、pushを
  実行しない既存方針を維持する。
- `Integrate`にPR mergeを含めるかは乙-3で別に決める。

**根拠**

ADR-028の骨格とユースケース設計 §6.1のCore垂直フローは「人間による最終diff確認」で終わり、PR、
統合先との合流、mergeが図に現れない。一方でID衝突はPost-check完了後にしか観測できず、現行の骨格には
衝突解決を置く場所がない。

**不採用**

| 案 | 不採用理由 |
|---|---|
| Post-checkの代替フローとして記述する | Post-checkは実装直後の検査であり、統合先の状態に依存する検査を同一段階へ置くと意味が混ざる |
| CI運用の記述だけに留める | UC-06／UC-07から衝突解決が見えず、Skillの実装根拠が本文に存在しなくなる |

### C.6 甲-5: UC-13の新設と検出・適用の分離（裁定済み・2026-09-01）

**裁定**: 案1、すなわち**UC-13「統合先との合流とID衝突の解決」を新設**し、
**Coreは`check`で検出と提示、適用はSkill／拡張**とする。UC-04の完了条件は変更せず、

**確定する規則**

- UC-13の正本は参照・トレース・検証仕様 §4の`idCollisions`定義（附録B.1）を指す。
- Coreの公開操作は`context`／`check`／`verify`／`doctor`の4つのままとし、すべて非変更系を維持する。

**根拠**

2. 改番はSPECを書き換えるため、Coreへ入れると5つ目の書込み操作となり、Core 1.0の輪郭が変わる。

**不採用**

| 案 | 不採用理由 |

| UC-04の代替フローへ`idCollisions`の出力だけを追記する | Core視点では正確だが、合流から再検査までのフロー全体が設計書本文から追えない |

### C.7 乙-2: `--base`未指定時の勝敗出力（裁定済み・2026-09-01）

**裁定**: 案B、すなわち入力契約を明記した上で、**`--base`未指定（既定`HEAD`）のときは
`incumbent`、`challenger`、`proposedId`、`rewriteSites`を出力せず、`instances`だけを返す**。
`SPEC-ID-DUPLICATE-001`／`failed`は従来どおり返す。

**確定する規則**

参照・トレース・検証仕様 §4の`idCollisions`定義（附録B.1）へ次を加える。

```text
`Integrate`段階の`check`は`--base <統合先先端>`を明示する。`--base`が未指定の場合、`idCollisions`の
各要素は`instances`だけを持ち、`incumbent`、`challenger`、`proposedId`、`rewriteSites`を出力しない。
未指定で得た結果を、ID衝突の勝敗、改番の適用、承認保護の根拠にしない。
```

UC-13の事前条件へ「統合先先端をrevisionとして解決でき、`--base`へ明示できる」を加える。

**根拠**

既定`HEAD`は、新規の衝突について**正しい勝敗を出すことが原理的にない**。衝突が現在集合に現れるには
統合先の勝者が作業ツリーに入っている必要があるが、自branchのHEADは敗者作成後のどのcommitにも
敗者を含むため、「勝者だけを含む」状態にならない。

| 合流の状態 | 既定`HEAD`の中身 | 現在集合 | 勝敗判定 |
|---|---|---|---|
| 作業ツリーのみ（未commit） | 敗者`REQ-005`だけ | 勝者＋敗者 | **敗者が「基準版に存在する側」となり勝者と判定される** |
| commit済み（正規） | 勝者＋敗者の2件 | 勝者＋敗者 | 対応付け不能。`SPEC-BASE-AMBIGUOUS-001`／`blocked`（C.1） |

第1行は`git merge`がconflictで停止した場合、`--no-commit`、`--squash`を使った場合に自然に発生し、
**Coreが統合先に既に存在する勝者の側へ改番を提案する**。甲-1の「統合済みのIDを動かさない」という根幹が
裏返る。C.1の`blocked`は基準版に`REQ-005`が1件しかないためこれを捕まえない。

したがって出力を抑制して失うのは誤答だけであり、正規手順（`--base <統合先先端>`）では何も失わない。
判定は`--base`が指定されたかどうかだけで決まるため、決定論を損なわない。

**不採用**

| 案 | 不採用理由 |
|---|---|
| 文書上の入力契約のみ | 上記の逆転経路が残る。合流を未commitのまま検査した利用者へ、勝者側の改番を提案してしまう |
| 専用Diagnosticを追加して`--base`を促す | 出力抑制で害は除ける。Diagnosticコードを増やす必要がない。将来、利用者への説明が不足すると判明した場合に再評価する |

### C.8 乙-3: `Integrate`とPR mergeの前後関係（裁定済み・2026-09-01）

**裁定**: 案A、すなわち**`Integrate`の完了条件を「統合先先端を基準版とする再検査が通過status」までとし、
統合先branchへのmergeを段階に含めない**。mergeは`Done`を記録した後に運用設計の手順で行う。

**確定する規則**

附録A.2.1のステップ8末尾へ次を加える。

```text
`Integrate`は再検査の通過をもって完了とし、統合先branchへのmergeを含まない。mergeは`Done`を記録した後に
[運用設計](06_運用設計.md)の手順で行う。
```

UC-13基本フロー第7項を次へ置き換える。

```text
7. 利用者は`--base <統合先先端>`で再度`check`を実行し、通過statusを確認する。統合先branchへのmergeは
   UC-13の範囲外とし、`Done`の記録後に行う。
```

UC-13の完了条件を「現在集合に重複がなく、`tracked`をすべて適用した木が参照切れを生じず、
統合先先端を基準版とする再検査が通過statusである。」とする。§4.8第4項のmergeも`Done`記録後の運用として
位置づける。

**根拠**

1. Coreはbranch、merge、rebase、commit、pushを実行しない。mergeを段階の完了条件へ置くと、
   段階の終端がCoreの契約外の操作に依存する。
2. `Done`のcommitはPRに含める必要があり、mergeはその後にしか置けない。現行の記述では
   **統合先へmergeした後に`Done`のcommitを作る**ことになり、そのcommitがPRに含まれない。
3. merge queueによる直列マージを前提とする以上（§8.1）、mergeの実行時点はフローの外側にある。

**不採用**

| 案 | 不採用理由 |
|---|---|
| `Integrate`を`Done`の後ろへ移し終端をmergeとする | §2.1「`Done`へ到達する前のどの段階でも」の対象から`Integrate`が外れ、統合段階で取り止められなくなる。改番が完了記録の後になり、`Done`後にSPECが書き換わる |
| 現状のまま | mergeと`Done`の順序矛盾が残る |

### C.9 乙-4: ゼロ埋め幅の異なるID（裁定済み・2026-09-01）

**裁定**: 案A、すなわち`REQ-015`と`REQ-0015`を**別IDとする**。既存の「大文字・小文字を区別して一意」と
いう字句一致規則の延長とし、ID比較へ新しい正規化を導入しない。桁を揃える配慮はSkillの推奨事項に留め、
Coreの合否判定へ使用しない。

**根拠**

新IDは同一workspace・同一種別の最大値+1であり、その数値は既存のどのIDより大きい。文字列が一致する
2つのIDは数値も一致するため、**ゼロ埋め幅をどう選んでも既存IDと衝突しない**。したがって附録B.1の桁数規則
（改番前IDの桁数と、新しい数値の表現に必要な桁数の大きい方）はそのまま成立し、安全性を損なわない。

**不採用**

| 案 | 不採用理由 |
|---|---|
| 数値へ正規化して同一IDとみなす | ID比較へ正規化を導入するため、配置・命名・探索規則 §4、ID解決、関係索引、修飾参照、Digestへ波及する。得られる可読性に対して影響範囲が大きい |
| 混在を警告する | Diagnosticが1つ増え、既存の混在文書が一斉に警告対象になる。Skillの推奨事項で足りる |

### E.1 IDDUP-004: 改番と状態遷移契約・置換語彙

#### P1で確定済みの部分

[Frontmatter共通仕様](../03.詳細設計/02_SPECファイル規定/03_Frontmatter共通仕様.md) §2へ次を反映済みである。

> 改番はstatusを変更せず、`supersedes`による置換でもない。改番した文書は`Revision History`へ1行追記し、
> `Summary`へ旧IDと改番の理由を記録する。Coreはこの追記を強制しない。

§9 IDDUP-004の論点1（改番を置換と誤って記録するとADR-012により適用対象から外れる）は、これで正本に
根拠を持つ。残るのは論点2と論点3である。

#### 丙-1: 終端状態の文書を改番できるか

**指摘**

`rejected`のREQ／TECH、`cancelled`のTASK、`superseded`のADRが敗者になり得る。ADR-036は終端状態からの
再遷移を禁止するが、改番はstatusを変更しないため遷移ではない。可否が本文から読み取れない。

**設計案**

終端状態の文書も改番の対象とする。ユースケース設計 §6.3の遷移図の直後へ次を追加する。

```text
改番は文書の識別子変更であり、状態遷移でも`supersedes`による置換でもない。上図のいずれのedgeにも
該当せず、終端状態の文書も改番の対象とする。`Rejection Rationale`と`Cancellation Rationale`は
変更しない。改番の判定と手順はUC-13を正とする。
```

ADRについては[ADR-015](../02.設計書/10_決定記録/ADR-015_SPEC改訂履歴の必須化.md) Decision 7が
「旧ADRの履歴には作成、非意味的訂正、後継化だけを要約する」と定めるため、**改番は非意味的訂正として
`Revision History`へ記録できる**ことを明記する。Decision 7の解釈を広げるものではなく、ID変更が
Decisionの変更に当たらないことの確認である。

**受入条件**

- 改番した`rejected` REQが置換済み扱いにならず、Historyとして保持され続ける。
- 改番が§6.3のいずれのedgeにも該当しないことを本文から確認できる。
- `superseded`のADRを改番しても`accepted -> superseded`の再判定が発生しない。

#### 丙-2: 基準版に存在しない文書の初出状態

**指摘**

§9 IDDUP-004の論点3は「`[new] -> approved`は§6.3で許可済みであり、追加の裁定を要しない」としていたが、
**これはREQ／TECHにしか当てはまらない**。

§6.3とFrontmatter共通仕様 §5の遷移表は、TASKの作成時状態を`open`だけとし、`[new] -> open`しか許可して
いない。ところがUC-06とUC-07は、1つのフローの中でTASKを作成し`open -> done`まで進めてGitへ記録する。
統合先先端またはmerge-baseを基準版とすると、そのTASKは**基準版に存在せず、現在版に`done`で現れる**。
すなわち`[new] -> done`となり、許可された遷移に含まれない。

| 種別 | 初出し得る現在値 | §6.3の作成時許可 | 判定 |
|---|---|---|---|
| REQ／TECH | `draft`、`approved`、`rejected` | `draft`、`approved`、`rejected` | 一致する |
| ADR | `proposed`、`accepted`、`rejected` | `proposed`、`accepted`、`rejected` | 一致する |
| **TASK** | `open`、`done`、`cancelled` | **`open`のみ** | **`done`と`cancelled`が初出で拒否され得る** |

これは改番に固有の問題ではない。**TASKを1つのPR内で完了させる通常フローすべてに及ぶ**。Core 1.0が未実装で
あるため観測されていないが、実装すれば`bitz check --full --base <merge-base>`が`done` TASKを含むPRを
一律に`failed`にする。IDDUP-004の検討中に見つかった仕様上の欠落であり、P2の中で最も優先度が高い。

**修正候補**

| 案 | 内容 | 評価 |
|---|---|---|
| **案1** | 基準版に存在しない文書は現在値の語彙だけを検査し、`[new]`からの遷移として扱う。TASKが`done`／`cancelled`で初出することを許可する | 実装が単純で、既存のフローをそのまま通す。「作成時`open`」は文書を新規に書くときの規約として残る |
| 案2 | TASKの`[new] -> done`／`[new] -> cancelled`を§6.3へ明示的に追加する | 案1と結果は同じだが、遷移図に「作成時にdoneで作る」と読める行が増え、規約としての意図が濁る |
| 案3 | フローがTASKを`open`で先にcommitすることを要求する | 遷移表を変えずに済むが、Small Flowへcommitを1つ強制し、TASK作成と実装を同一branchで完結できなくなる |

**推奨**: 案1。Frontmatter共通仕様 §5とユースケース設計 §6.3へ次の趣旨を明記する。

```text
遷移表の「作成時」列は、文書を新規に作成するときに書いてよい状態を定める規約である。Git基準版に
存在しない文書の遷移検査は、現在値が当該種別の語彙として妥当かだけを検査し、`[new]`からの遷移として
扱う。branch内で`open -> done`まで進めたTASKが基準版に存在しない場合も、初出として許可する。
```

**受入条件**

- TASKを作成し`done`まで進めた入力を`--base <統合先先端>`で検査し、`SPEC-STATE-TRANSITION-001`を出さない。
- 基準版に存在するTASKの`done -> open`は従来どおり禁止遷移として検出する。
- 語彙にない状態値で初出した文書は従来どおり拒否する。

### E.2 IDDUP-005: 改番commitとTASK `changes`境界（丙-3）

#### P1で確定済みの部分

[SDDプロセス設計](../02.設計書/04_SDDプロセス設計.md) §1へ、`Integrate`では合流commitと改番commitを
別のcommitへ記録する規約を反映済みである。またUC-06・UC-07の基本フローは、`Integrate`（step 9）の後に
`Done`のTASK明示check（step 10）を置く。

#### この順序で問題が消えること

`Done`の`bitz check <TASK-ID>`は基準版を指定しないため、既定`HEAD`を使う。`Integrate`が改番を
commitしているので、そのときの`HEAD`は改番commitである。

| 検査 | 基準版 | 変更集合 | `changes`境界 |
|---|---|---|---|
| `Integrate`の`check --full --base <統合先先端>` | 統合先先端 | 合流＋改番＋PRの寄与 | `--full`と明示対象は排他であるため境界検査を行わない |
| `Done`の`check <TASK-ID>`（既定`HEAD`） | 改番commit | TASKファイルのstatus変更のみ | **改番pathが変更集合に入らず、違反しない** |

つまりP1で確定した順序とcommit規約が、そのままIDDUP-005の解になっている。

#### 案1が実装できないこと

§9 IDDUP-005の推奨は案1「改番による変更pathを境界検査の対象外とする。`idCollisions`の`rewriteSites`から
機械的に判定できる」であったが、**これは実装できない**。

境界検査を行うinvocationは`Done`の`bitz check <TASK-ID>`である。その時点で重複は解消しており、
`idCollisions`は空になる。Coreは過去のinvocationの結果を保持しないため、どのpathが改番由来かを知る手段が
ない。同一invocationで検出と境界検査を同時に行うこともできない。`--full`と明示対象が排他だからである。

**設計案**

Coreを変更せず、基準版の条件として明記する。参照・トレース・検証仕様 §4のTASK境界の段落へ1文を加える。

```text
`Integrate`で合流と改番を記録した場合、TASK境界検査の基準版はそれらのcommitを含むものとする。既定`HEAD`は
この条件を満たす。改番より前のcommitを`--base`へ渡すと、改番による変更pathが変更集合へ入り境界違反となる。
```

**修正候補の再評価**

| 案 | 評価 |
|---|---|
| **案1 改番pathを境界検査の対象外とする** | **実装できない**。境界検査の時点で`idCollisions`が空であり、改番由来のpathを識別できない |
| 案2 `changes`へ改番pathを追記させる | TASKの作業境界が改番作業で膨らみ、境界の意味が薄れる |
| **案3 順序と基準版で解決する（推奨）** | P1のcommit規約とフロー順序で既に成立している。追加するのは基準版の条件1文だけ |

**推奨**: 案3。§9の推奨（案1）を撤回する。

**受入条件**

- `Integrate`で改番をcommitした後の`bitz check <TASK-ID>`が、改番だけを理由に境界違反を報告しない。
- 改番より前のcommitを`--base`へ渡した場合は境界違反となり、基準版の誤りとして説明できる。
- 改番以外の境界外変更は従来どおり検出する。

### E.3 IDDUP-006: CIの標準invocation（丙-4）

#### 現状

P1では[運用設計](../02.設計書/06_運用設計.md) §4の標準を変更せず、`Integrate`との関係を追記するに留めた。
したがって正本には2つの基準が併存する。

| 用途 | 基準版 |
|---|---|
| CIの標準invocation（運用設計 §4） | `<merge-base>` |
| `Integrate`のID衝突検査（SDDプロセス設計 §2、UC-13） | `<統合先先端>` |

#### ADR-025 Alternative 1に抵触しないこと

ADR-025 Alternative 1は「常に`HEAD`だけを使う」案を、clean checkoutのCIでPR内の承認済みREQ変更を
検出できないことを理由に不採用とした。統合先先端はこれと別物である。merge結果の木に統合先先端を
基準版として与えると、差分は**PRの寄与そのもの**になり、PR内の承認済みREQ変更は差分に現れる。
不採用理由に抵触しない。

#### 両基準の差

| 観点 | `<merge-base>` | `<統合先先端>` |
|---|---|---|
| PR内の承認済みREQ変更 | 検出できる | 検出できる |
| 統合先がfork後に加えた変更 | **差分に含まれ、PR側CIで二重に報告される** | 含まれない |
| ID衝突の勝敗 | 両者とも新規となり勝敗が付かない | 勝敗が付く |
| 前提条件 | なし | **検査対象の木が統合先先端を含むこと** |

最後の行が決定的である。**統合先先端を含まない木に対して`--base <統合先先端>`を使うと、統合先にあって
自branchにないSPECがすべてSPEC削除として`failed`になる**。fork後に統合先が新しいREQを追加し、自branchが
まだ合流していない場合がこれに当たる。§4.2が「両者を含む木（merge結果、または統合先へrebase済みの
自branch）」と限定しているのはこのためであり、標準invocationへ昇格させるならこの前提を運用設計へ
明記しなければならない。

#### 修正候補

| 案 | 内容 | 評価 |
|---|---|---|
| **案1（推奨）** | CIの標準を`--base <統合先先端>`へ変更し、**検査対象の木が統合先先端を含むことを前提として明記する** | 基準が1つになり、二重報告が消え、ID衝突の勝敗も同じinvocationで付く。GitHub Actionsの`pull_request`イベントは既定でmerge commitをcheckoutするため前提を満たす |
| 案2 | `<merge-base>`を維持し、`Integrate`だけ統合先先端とする（P1反映後の現状） | 変更が要らないが、基準が2つ併存し、統合先の変更が二重報告される |
| 案3 | 木の形に応じてworkflowが基準を選ぶ | 同一木に対する基準が状況で変わり、結果の再現条件が複雑になる |

**推奨**: 案1。反映先は運用設計 §4、[QA品質保証設計](../02.設計書/05_QA品質保証設計.md) §4、
[実装ロードマップ](../02.設計書/08_実装ロードマップ.md) §3の「HEAD既定と明示merge-baseで……」の受入条件行の3箇所である。
P1で運用設計 §4へ入れた「CIの標準invocationを統合先先端へ統一するかは未裁定」の1文も削除する。

**受入条件**

- PR内で承認済みREQを変更した入力を、統合先先端基準で検出できる。
- 統合先が承認済みREQを変更した入力を、PR側のCIで二重に報告しない。
- 統合先先端を含まない木へ`--base <統合先先端>`を渡した入力で、SPEC削除が大量に報告されることを
  fixtureで確認し、前提条件の記述と対応付ける。
- 運用設計、QA品質保証設計、実装ロードマップの記述が同じ基準を指す。

### E.4 IDDUP-007: 連合での集約とスコープ（丙-5）

#### P1で確定済みの部分

- 参照・トレース・検証仕様 §4.1: 番号空間は種別prefixとworkspaceの組ごとに独立。出力順序は`workspaceId`、
  `documentId`の辞書順。
- UC-13の代替・例外フロー: 連合では`idCollisions`を全体で1配列へ集約し、勝敗判定は同一`workspaceId`内に
  閉じる。

#### 残る論点

1. `idCollisions`の各要素で`workspaceId`が**必須**であることを明記していない。単一workspaceでも
   実効workspace IDを補う既存規則との対応が読み取れない。
2. memberの追加・削除が基準版と現在版で異なる場合の勝敗判定範囲。ADR-037 Decision 5のcatalog両読みと
   組み合わせたときの扱いが定まらない。
3. `SPEC-BASE-AMBIGUOUS-001`のworkspaceスコープ。`SPEC-ID-DUPLICATE-001`は
   [モノレポSPEC連合仕様](../03.詳細設計/02_SPECファイル規定/12_モノレポSPEC連合仕様.md) §10の周辺で
   「同一workspace内の重複へ適用し、別workspaceの同じローカルIDは正常とする」と明記されているが、
   新しい診断には同じ記述がない。

#### 設計案

参照・トレース・検証仕様 §4.1の末尾へ次を追加する。

```text
`idCollisions`の各要素は`workspaceId`を必須とする。単一workspaceでも実効workspace IDを補う。
`--all-workspaces`では連合全体で1つの配列へ集約し、要素の順序は連合の処理順（連合ルート、workspace ID
辞書順）と一致させる。勝敗判定と採番は同一`workspaceId`内に閉じ、別workspaceの同じローカルIDを衝突と
しない。基準版catalogと現在版catalogの双方から索引を作る規則（ADR-037 Decision 5）をそのまま適用し、
基準版にのみ存在するmemberのSPECを勝敗判定から隠さない。現在版にのみ存在するmemberのSPECは基準版に
存在しないため、同一キーが2件並んでも勝敗を決定しない。
```

参照・トレース・検証仕様 §8のDiagnostic一覧の後段、`SPEC-ID-DUPLICATE-001`のworkspaceスコープを述べた
段落へ1文を加える。

```text
`SPEC-BASE-AMBIGUOUS-001`も同一workspace内のキー重複へ適用し、別workspaceの同じローカルIDを
基準版の重複としない。
```

**受入条件**

- 複数memberで同時に衝突した入力から、workspaceごとに正しい敗者を特定できる。
- 基準版にのみ存在するmemberのSPECを勝敗判定から隠さない。
- 別workspaceの同じローカルIDが`idCollisions`にも`SPEC-BASE-AMBIGUOUS-001`にも現れない。
- `--all-workspaces`の`idCollisions`の順序が連合の処理順と一致する。

### E.5 適用順序

1. 丙-2（初出状態）。TASKを完了する通常フロー全体に及ぶため最優先とする。
2. 丙-1（終端状態の改番）。丙-2と同じ§6.3・Frontmatter共通仕様 §5を触るため続けて適用する。

### F.1 丙-2: 基準版に存在しない文書の初出状態（裁定済み・2026-09-01）

**裁定**: 案1、すなわち**基準版に存在しない文書は現在値の語彙だけを検査し、`[new]`からの遷移として
扱う**。TASKが`done`／`cancelled`で初出することを許可する。

**確定する規則**

[Frontmatter共通仕様](../03.詳細設計/02_SPECファイル規定/03_Frontmatter共通仕様.md) §5と
[ユースケース設計](../02.設計書/09_ユースケース設計.md) §6.3へ次の趣旨を明記する。

```text
遷移表の「作成時」列は、文書を新規に作成するときに書いてよい状態を定める規約である。Git基準版に
存在しない文書の遷移検査は、現在値が当該種別の語彙として妥当かだけを検査し、`[new]`からの遷移として
扱う。branch内で`open -> done`まで進めたTASKが基準版に存在しない場合も、初出として許可する。
```

**根拠**

1. **既存の先例と一致する。** [要求SPEC仕様](../03.詳細設計/02_SPECファイル規定/04_要求SPEC仕様.md) §7は
   承認済みREQ保護について「Git基準版に存在しない新規ファイルは変更前状態との比較対象外とする」と定める。
   比較対象がない検査は成立しないという原則であり、遷移検査へ同じ原則を適用する。
2. **改番に固有の問題ではない。** §6.3とFrontmatter共通仕様 §5はTASKの作成時状態を`open`だけとするが、
   UC-06・UC-07は1つのフローでTASKを作成し`open -> done`まで進めてGitへ記録する。基準版は統合先先端か
   merge-baseであり自branchの外側にあるため、そのTASKは基準版に存在せず`[new] -> done`となる。
   実装すれば`done` TASKを含むPRを一律に`failed`にする。
3. **「先にcommitしておく」では解けない。** 基準版は自branchの外側にあるため、branch内でcommitを
   いくつ積んでも基準版には入らない。TASKが基準版に現れるのはPRがmergeされた後である。

**受容するコスト**

`done`で直接書かれたTASKを検出できない。ただしCoreは`open`でcommitしてから`done`にした場合と区別できず、
もともと保証していない。TASKの`changes`境界、coverage、ADR-034の完了時checkは従来どおり適用する。

**不採用**

| 案 | 不採用理由 |
|---|---|
| §6.3へTASKの`[new] -> done`／`[new] -> cancelled`を明示追加する | 振る舞いは同じだが、遷移図が「作成時にdoneで作ってよい」と読め、作成時規約の意図が濁る。REQ／TECH／ADRとの非対称も残る |
| 初出でも作成時の許可値だけを認める | TASKをbranch内で完了できなくなり、UC-06・UC-07の基本フローが成立しない |

### F.2 丙-1: 終端状態の文書の改番（裁定済み・2026-09-01）

**裁定**: 案A、すなわち**終端状態の文書も改番の対象とする**。`rejected`のREQ／TECH、`cancelled`のTASK、
`superseded`のADRを含む。

**確定する規則**

ユースケース設計 §6.3の遷移図の直後へ次を追加する。

```text
改番は文書の識別子変更であり、状態遷移でも`supersedes`による置換でもない。上図のいずれのedgeにも
該当せず、終端状態の文書も改番の対象とする。`Rejection Rationale`と`Cancellation Rationale`は
変更しない。改番の判定と手順はUC-13を正とする。
```

ADRについては[ADR-015](../02.設計書/10_決定記録/ADR-015_SPEC改訂履歴の必須化.md) Decision 7が
「旧ADRの履歴には作成、非意味的訂正、後継化だけを要約する」と定めるため、改番を**非意味的訂正**として
`Revision History`へ記録する。Decision 7の解釈を広げるものではなく、ID変更がDecisionの変更に当たらない
ことの確認である。

**根拠**

改番はstatusを変更しないためADR-036の終端規則に抵触しない。終端状態を例外にすると、勝敗規則に
状態依存の分岐が入り、敗者が終端状態のときだけ衝突が自動解決できず`failed`のまま人手待ちになる。

**不採用**

| 案 | 不採用理由 |
|---|---|
| 人間の判断へ委ねる | 勝敗規則に状態依存の例外が入り、自動解決できない経路が残る |
| 終端の敗者は削除を既定とする | 敗者は基準版にないため削除は拒否されないが、ADR-036が保持しようとした不採用・中止の履歴を失う |

### F.3 丙-3: 改番commitとTASK `changes`境界（裁定済み・2026-09-01）

**裁定**: 案A、すなわち**基準版の条件を明記する**。§9 IDDUP-005の推奨（案1）を撤回する。

**確定する規則**

[参照・トレース・検証仕様](../03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md) §4の
TASK境界の段落へ次を追加する。

```text
`Integrate`で合流と改番を記録した場合、TASK境界検査の基準版はそれらのcommitを含むものとする。既定`HEAD`は
この条件を満たす。改番より前のcommitを`--base`へ渡すと、改番による変更pathが変更集合へ入り境界違反となる。
```

**根拠**

P1で確定したcommit規約とフロー順序が既に解になっている。

| 検査 | 基準版 | 変更集合 | 境界 |
|---|---|---|---|
| `Integrate`の`check --full --base <統合先先端>` | 統合先先端 | 合流＋改番＋PRの寄与 | `--full`と明示対象は排他のため境界検査を行わない |

**案1が実装できないこと**

同一invocationで検出と境界検査を同時に行うこともできない。実装手段が存在しないため撤回する。

**不採用**

| 案 | 不採用理由 |
|---|---|
| 改番結果を`changes`へ追記させる | TASKの作業境界が改番作業で膨らみ、境界の意味が薄れる |
| 明記せず暗黙の前提にする | `--base`を改番commitより前へ渡したときの境界違反を本文から説明できない |

### F.5 丙-4: CIの標準invocation（裁定済み・2026-09-01）

**裁定**: 案1、すなわち**CIの標準invocationを`--base <統合先先端>`へ変更する**。あわせて、検査対象の木が
統合先先端を含むこと（merge結果、または統合先へrebase済みの自branch）を前提として明記する。

**確定する規則**

[運用設計](../02.設計書/06_運用設計.md) §4のCI標準を次へ変更する。

```text
bitz check --full --base <統合先先端>
bitz verify
```

```text
bitz check --all-workspaces --base <統合先先端>
bitz verify --all-workspaces
```

前提条件として次を明記する。

```text
この標準は、検査対象の木が統合先先端を含むこと（merge結果、または統合先へrebase済みの自branch）を前提と
する。統合先先端を含まない木へ`--base <統合先先端>`を渡すと、統合先に存在して自branchに存在しないSPECが

```

P1で運用設計 §4へ入れた「CIの標準invocationを統合先先端へ統一するかは未裁定であり、本節の`<merge-base>`は
変更していない」の1文を削除する。[QA品質保証設計](../02.設計書/05_QA品質保証設計.md) §4の比較元の説明と、
[実装ロードマップ](../02.設計書/08_実装ロードマップ.md) §3の「HEAD既定と明示merge-baseで……」の受入条件行も
同じ基準を指すよう更新する。

**根拠**

1. **ADR-025 Alternative 1に抵触しない。** 同項は「常に`HEAD`だけを使う」案をclean checkoutのCIで
   PR内の承認済みREQ変更を検出できないことを理由に不採用とした。merge結果の木へ統合先先端を基準版として
   与えると差分はPRの寄与そのものになり、PR内の承認済みREQ変更は差分に現れる。
2. **二重報告が消える。** merge-baseを基準にすると、mergeで取り込んだ統合先の変更もPR側の差分へ入り、
   統合先で既に検査済みの変更をPR側CIが再び報告する。
3. **基準が1つになる。** ID衝突の勝敗判定と、承認保護・状態遷移・変更範囲の検査が同じinvocationで揃う。
   merge-baseを基準にすると衝突した両者とも新規となり勝敗が付かない。
4. **丙-2により前提が満たされた。** 統合先先端を標準にするとbranch内で完了した`done` TASKが基準版に
   存在しない状態で検査されるが、F.1により初出として許可されるため問題にならない。

**受容するコスト**

前提条件が破れる木（fork後に統合先が進み、自branchが未合流）では、統合先にあって自branchにないSPECが
SPEC削除として大量に報告される。CIはmerge結果またはrebase済みbranchを検査対象とする必要がある。
GitHub Actionsの`pull_request`イベントは既定でmerge commitをcheckoutするため前提を満たす。

**不採用**

| 案 | 不採用理由 |
|---|---|
| `<merge-base>`を維持する | 同じ木に対して基準が2つ併存し、統合先がfork後に加えた変更が二重報告される |
| 木の形に応じてworkflowが基準を選ぶ | 同一木に対する基準が状況で変わり、結果の再現条件が複雑になる |

含めなければ「再実行なしに改番を適用できる」が成立せず、丁-2でCoreの判定を変えれば`semanticHash`から

### H.1 丁-1: レポート保存と非成功結果の復旧

**確定した規則**

[更新・互換性・安全性](../03.詳細設計/02_SPECファイル規定/07_更新・互換性・安全性.md) §2へ次を反映した。

```text
非成功時のレポートは結果JSONと同じ構造を保持し、`selection`、`revision`、`idCollisions`を含める。
ID衝突による`failed`のレポートから、`check`を再実行せずに改番を適用できるようにするためである。
適用側は、レポートの`revision`の`base`、`commit`、`dirty`が適用時点の木と一致することを確認してから
適用する。一致しない場合は`check`を再実行する。`--base`未指定で得たレポートの`idCollisions`は
`instances`だけを持ち勝敗を含まないため、改番の適用根拠にしない。
```

[ユースケース設計](../02.設計書/09_ユースケース設計.md) UC-11の代替・例外フローへ1項を追加した。

**設計上の追加**

§9 IDDUP-008の修正候補は「`idCollisions`を結果JSONの一部として自動保存レポートへ含める」だけであったが、
**レポート生成時点の木と適用時点の木が一致する保証がない**。レポートは`revision`（`base`、`commit`、
`dirty`）を保持するため、適用側がこれを照合すればよい。照合を要求しないと、古いレポートの`proposedId`を
別の木へ適用して新たな重複を作り得る。丁-1の裁定にこの照合を含めた。

あわせて、乙-2により`--base`未指定のレポートは勝敗を含まないため、適用根拠にしないことを明記した。

### H.2 丁-2: cherry-pick由来の同一内容

**確定した規則**

UC-13の代替・例外フローの該当項を次へ置き換えた。

```text
- 同一内容がcherry-pickで両branchへ入った場合、Coreは独立生成と区別しない。`semanticHash`から同一性を
  推測しないためである。Skillは改番の適用前に勝者と敗者の内容差を人間へ提示し、同一内容であれば改番と
  敗者の削除を選択肢として示す。敗者を削除しても勝者が同じ文書IDを保持するため、基準版のキーは
  現在版に残り、SPEC削除としては扱われない。削除を選んだ場合、Skillは敗者を指す`relations`と
  `addresses`を同時に始末する。
```

**§9の記述の訂正**

§9 IDDUP-009は、敗者の削除が許される理由を「削除はGitへ記録する前であればADR-037 Decision 4により
検査対象外となる」としていたが、**正規手順では当てはまらない**。ADR-037 Decision 4が対象とするのは
「Git基準版に存在しない**未追跡**の新規SPEC」であり、敗者は自branchで既にcommitされている。

正しい理由は甲-2と同じ構造である。基準版（統合先先端）のキー`REQ-005`は勝者が保持しており、敗者を
削除しても現在版からキーが消えない。したがってADR-037 Decision 3の削除判定が発動しない。訂正して
反映した。

**設計上の追加**

敗者を削除すると、敗者を指す`relations`と`addresses`が解決できなくなり
`SPEC-RELATION-MISSING-001`／`failed`となる。§9の修正候補はこれに触れていなかったため、Skillが
参照を同時に始末する契約を加えた。
