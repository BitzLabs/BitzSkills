## 1. 作業と記録の運用

利用者の指示: 「提案の計画で、進めましょう。計画と進捗を、残して下さい。また、各作業を開始する前には、どの作業の何を実施するのか表記の上で作業を開始してください。」

1. 各作業の開始前に、会話へ `作業 Rxx「作業名」を開始します。実施内容は…` と表記する。
2. 開始時に下表と進捗履歴へ、対象・実施内容・状態を記録する。
3. 実行後に対象ref、実コマンド、終了結果、必要な一次証拠、独立検分、残件を記録する。対応済みの記録は§1.1に従って集約する。
4. 状態は未着手／進行中／検分待ち／停止／完了で管理する。停止理由と再開条件を残す。
5. Gate通過・是正済み・工程完了は、作業者と独立した文脈の検分後に記録する。
6. 現在の判断と継続に必要な履歴だけを保持する。失敗・中断・欠測の事実と必要な消費数を集約に残し、異なる条件の結果を合算しない。試作や不要な途中結果の原ファイルを一律に保存しない。
7. 計画の採用を、push・PR公開・main統合・リリース・承認済みREQ/TECHの意味変更へ拡張しない。

### 1.1 評価資産と結果の保存・削除方針（2026-11-03改定）

利用者の指示により、必要な履歴だけを残し、試作や判断に使えない結果を残し続ける方針をやめる。
保存する理由は、現在の判定、未解決事項の調査、評価の継続、再発防止のいずれかに具体的に結び付ける。
古いこと、失敗したこと、対応済みであることだけでは削除を決めず、今後の用途があるかで判断する。

| 対象 | 残すもの | 整理するもの |
|---|---|---|
| 現行の評価基盤 | 使用中のコード、ケース、Schema、契約、回帰試験に必要な入力と期待値 | 利用側のない試作コード・候補・生成物。依存があるものは先に移設または依存を解消する |
| 現在の受入れ・リリース判定 | 判定の再確認に必要な条件、集計、一次証拠、独立検分 | 同じ判定を裏付ける重複物、使われていない中間出力 |
| 未解決・停止中・継続予定の評価 | 原因調査と再開に必要な原記録、契約、台帳、先行台帳、消費・停止・再試行の証拠 | 調査・継続のどちらにも使わない出力。対象範囲を確定してから除く |
| 対応済みで確認も終わった指摘 | 問題、修正コミット、確認方法と結果、残る制限を短い完了記録に集約し、必要な回帰試験を残す | 指摘ごとの重複報告、修正途中のレビュー、試行ログ、一時的な再現物 |
| 修正済みだが確認待ちの指摘 | 未確認であることと、確認に必要な最小限の差分・再現情報・原記録 | 確認に不要な中間出力。確認待ちを解消済みとして扱わない |
| 完了・置換・中止した評価 | 現在の決定や制限に影響する結論だけを集約する。比較不能・未測定・未認定は必要な範囲で明記する | 役割を終えた試作、旧候補、旧バッチ、実行結果、圧縮した軌跡、詳細な作業経過 |
| 判断に使えない結果 | 現在の分母、停止、費用、制限に影響する場合だけ、無効の理由と必要な件数を集約する | 重複実行、準備の失敗、取得に失敗した出力など、今後の診断にも使わない原ファイル |

集約は作業・問題・評価条件の単位で行う。同じ内容をMarkdown、JSON、圧縮ファイルへ重複して保存しない。
機械処理で必要なJSONと人向けの説明は、それぞれに用途がある場合だけ併存させる。
今後の用途がない記録は、ファイルごとの代替記録や恒久的な退避先を新設せず削除する。
必要な履歴は、既存の計画・決定記録・簡潔な結果一覧へ集約する。

対応済み事項は、関連する確認が終わり、未解決の依存がないことを確かめてから整理する。
作業一覧には状態と結論を残し、詳細な追記を続けない。再発防止に必要な部分は過去の全ログではなく回帰試験へ移す。
現在の受入れや継続が原記録のバイト列やハッシュ値に依存する場合は、その用途が終わるまで原記録を残す。
ADR-060の比較結果と判定限界、およびADR-068の再試行・後継台帳に必要な原記録とeventは、この条件で扱う。
それらの判定条件や原記録の保護を変える場合は、計画の整理に含めず、該当するADR・評価契約の改訂として扱う。

本節は、過去の進捗にある「原結果を保持」「元の失敗記録は変更しない」などの一律保存の運用を置き換える。
過去に何が起きたかを改変したり、削除した失敗を成功へ変更したり、分母・消費枠を減らしたりするものではない。
必要な集約を残したうえで、詳細な進捗履歴も整理対象にする。
通常のGit履歴は書き換えず、削除前の内容は当時のコミットで参照できるが、現行文書のリンクは集約先へ直す。
履歴内のファイルの存在だけを、現行の判定や再開に必要な証拠の代わりにはしない。

R10では次の順で実施する。

1. 評価資産・結果・進捗履歴を、使用中、未解決、対応済み、役割終了に分類し、コード・試験・文書・台帳の参照を確認する。
2. 判断に必要な履歴を集約し、対応済み事項の確認結果と、未完了・未測定・未認定の範囲を残す。
3. 不要な試作・結果・中間記録を削除し、必要な検証コードや回帰入力は使用先に合う場所へ移す。ファイル形式や作成日だけで対象範囲を限定しない。
4. 削除・移設に伴う参照とハッシュ値の依存を確認し、文書のリンク、評価契約の監査、影響する単体試験を検証する。
5. 整理した範囲、分類ごとの件数、検証結果、保留したものと理由を簡潔に記録する。作業で生じた一時出力も同じ基準で整理する。

完了条件は、現在の判断・継続・回帰試験に必要な資産と履歴を参照でき、用途のない試作・結果・途中経過が現行ツリーに残っていないこととする。
保存物を別のディレクトリへ移すだけでは完了としない。整理後も、残した理由がなくなった時点で見直す。

## 4. 開発順序と評価条件

1. R01/R02で修正の検分と取得後の判定経路を閉じる。
2. R03を1件ずつ予約→取得→原照合→独立採点→親再照合の順で進める。途中失敗・中断・不適合で残枠を停止する。
3. R04〜R06を、発火判断と実操作の行動を区別して測る。まずSOLで試作基準を確認する。
4. R07の実地評価とR08のCore認定、R09/R10の配布準備を進める。
5. R11でリリース候補の基準と人間の受入れを確認する。

評価起動前に、対象ref、候補版、ケース/入力hash、分母、反復、環境、有限予算、停止規則、出力先を固定する。
公開カナリアはSDK 1 turn、300秒、通常/stream retry 0、一次最大4・独立最大4、各予約を起動前に消費する。API観測閾値はモデル推論3・一覧2であり、送信前hard capではない。
保持入力・期待値・生軌跡は既承認の非公開領域へ保存し、公開repoには集合版・件数・hash・集計のみを残す。
対象refを変更した測定は別記録とし、過去の適合を現在refの全体認定へ読み替えない。
リリースの分母・閾値・反復・モデル系統数は提案30 §7.6と適用する版付き評価契約による。
fixture変更時はGate Aを再認定し、Core変更時は該当適合・単体を実行する。認定はcleanな確定refで行う。

## 6. 後継台帳への移行手順（原記録を持つ環境で行う）


1. [原記録による原因の再検査](../../evals/skills/results/2026-10-27-public-survey-failure-streak/report.md#2026-11-04-原記録による原因の再検査)の独立検分は完了している。固定した現行候補の公開少数枠で一次取得・独立採点・親確認を完走する。補助通知への既存修正を含む候補を使い、83枠目で確認したホスト引数不適合の停止を緩めない。旧結果を再採点して成功へ変更しない。

2. 継続台帳を読取り専用で検査し、`predecessor`と引き継ぐ状態を保存する。`carry`で、正解2・中断1・次の枠4・
   再試行の候補1を確かめる。`retryPriorArtifacts`の値は手順5の`--prior-artifact`に使う。この段階では継続台帳に印を置かない。

   ```text
   uv run --project plugins/bitz-core --with jsonschema==4.23.0 python \
     evals/skills/routing/production_heldout_successor_setup.py predecessor --kind continuation-0.2.0 > predecessor.json
   ```

3. 新しい bundle のディレクトリ（`.venv/heldout-bound-<名前>`）を作り、いまの bundle から`deployment.json`、
   `input-contract.json`、`sdk-manifest.json`を複写する。入力は実行時に sourceCommit と非公開ケースから読むので、
   複写しない。そのうえで、実行契約0.3.0を作る。

   ```text
   uv run --project plugins/bitz-core --with jsonschema==4.23.0 python \
     evals/skills/routing/production_heldout_successor_setup.py execution --execution <いまのexecution.json> \
     --deployment <deployment.json> --predecessor predecessor.json --campaign heldout-matrix-<新しいID> \
     --harness-retries <再試行の上限> --output .venv/heldout-bound-<名前>/execution.json
   ```

4. 新しい実行契約に対して、開始前の独立検分（prelaunch review・report・隔離の証明）を作り直し、新しい bundle に置く。
   `production_heldout_run.py --bundle <新しいbundle> --preflight-only`で資源と検分を確かめる。この段階では台帳を開かない。
5. 最初に台帳を開いたとき（手順6の承認か手順7の評価）に、継続台帳へ印が置かれ、旧い入口からは追記できなくなる。
6. 旧停止の枠1を再試行する場合は、10/20の停止の独立検分の記録を付けて承認する。停止理由は`evidence_invalid`
   なので独立検分が必須。`--prior-artifact`には手順2の`retryPriorArtifacts`の値（旧停止の`global-stop.json`のhash）を使う。

   ```text
   uv run --project plugins/bitz-core --with jsonschema==4.23.0 python \
     evals/skills/routing/production_heldout_run.py --bundle <新しいbundle> --authorize-retry 1 \
     --stop-reason evidence_invalid --prior-artifact <retryPriorArtifactsの値> --evidence <証拠のhash> \
     --independent-review <独立検分の記録> --reason "<理由>"
   ```

7. 通常どおり`production_heldout_run.py --bundle <新しいbundle>`で最大2枠ずつ評価する。同じ型の失敗が2枠続いたら
   止まるので、原因を調べてから確認記録を置く。
