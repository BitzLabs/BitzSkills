# 仕様構造の再編とCore 1.0簡素化提案

- 対象: `docs/02.設計書`、`docs/03.詳細設計`
- 状態: **Closed（11件採用・正本反映済み）**
- 作成日: 2026-09-01
- 裁定日: 2026-09-01（[ADR-039](../02.設計書/10_決定記録/ADR-039_Core-1.0仕様構造の再編とscope縮小.md)）
- 観点: 構造化設計、KISS、YAGNI、DRY

## 1. 結論

現行設計は、個々の判断はよく詰められており、主要な契約矛盾も既存レビューで解消されている。
一方、レビューで判断を追加するたびに、同じ契約を設計書、詳細設計、ユースケース、運用手順、ADRへ同期したため、
**仕様の正しさを保つ仕組みそのものがCore 1.0の主要な複雑性になっている**。

Core 1.0の実装前に、次の再編を行うことを提案する。

1. 規範の所有者を「共通契約」「言語」「文書モデル」「操作」「フロー」に分け、1規則1正本にする。
2. `check`と`verify`が同居する巨大仕様、およびContextの解決モデルと提示モデルを責務別に分割する。
3. 概要、ユースケース、運用手順から詳細契約の再掲を除き、正本への参照へ置き換える。
4. ADRを判断理由の記録へ戻し、現在の実行契約の正本として参照しない。
5. モノレポ連合、ID衝突の自動改番支援、Profile実行基盤、公開Projection DigestをCore 1.0から外し、
   実測後に再評価する。
6. 必須`Revision History`、厳格な本文スタイル検査、verify bindingの内容同一性による重複排除を簡素化する。

この案はEARS-AI、単一workspaceの`.spec/`、型付き依存、完全Context、静的検査、対象テスト実行という
製品の垂直スライスを残す。削る対象は、中心価値を成立させる前に追加された拡張・運用自動化・表示再現性である。

## 2. 調査結果

### 2.1 規模

2026-09-01時点で、`docs/02.設計書`はADRを含め4,977行、`docs/03.詳細設計`は3,370行ある。
詳細設計の中では、次の2文書だけで980行を占める。

| 文書 | 行数 | 混在している主な責務 |
|---|---:|---|
| `06_参照・トレース・検証仕様.md` | 486 | ID解決、path、`check`、Git差分、TASK境界、ID改番、`verify`、process実行、report、Diagnostic |
| `10_Context Resolution仕様.md` | 494 | 関係モデル、状態、閉包、提示、履歴表示、coverage、hash、stale検出、adapter契約 |

行数自体は欠陥ではない。しかし、この2文書は別の変更理由を持つ機能を同時に所有しており、
1つの変更が広い再レビューを要求する。

### 2.2 横断的な再掲

同じ語彙の出現状況は次のとおりである。件数は設計の良否を直接示さないが、変更波及の大きさを示す。

| 契約・概念 | 出現文書数 | 出現数 |
|---|---:|---:|
| `passed_with_warnings` | 21 | 64 |
| Context Digest | 20 | 56 |
| Revision History | 50 | 107 |
| モノレポ | 31 | 119 |
| `idCollisions` | 6 | 22 |
| `SPEC-BASE-AMBIGUOUS-001` | 5 | 9 |

例えば、checkの通過status、TASK完了手順、取り止め手順、モノレポ集約、ID衝突時の`--base`は、
アーキテクチャ、プロセス、QA、運用、ユースケース、詳細操作仕様の複数箇所に記述される。
これまでのレビューが反映漏れを繰り返し発見したのは、内容の難しさだけでなく、この同期構造にも原因がある。

### 2.3 規範階層の逆転

`docs/04.提案資料/README.md`は、設計本文を現在の決定、ADRを判断理由の記録と位置づける。
一方、現行本文には「ADRを正とする」「ADRに従う」という参照が複数あり、詳細設計からADRへ実行契約を
逆参照している。

この状態では、現在の仕様を理解する読者が、設計本文、詳細仕様、過去の判断記録を往復しなければならない。
ADRは理由と代替案を保持し、規範本文は現在値だけを保持するという境界へ戻す必要がある。

## 3. 原則別の評価

### 3.1 構造化設計

現在は「機能名で分けた文書」の内部に、入力選択、ドメイン規則、Git連携、process実行、表示、保存が混在する。
変更理由が異なるため、凝集度が下がり、文書間の結合も増えている。

特に次の境界を明示すべきである。

| モジュール | 所有するもの | 所有しないもの |
|---|---|---|
| 共通契約 | status、Diagnostic、結果外形、report条件、revision表現 | 操作固有の対象選択 |
| EARS-AI言語 | 字句、構文、Semantic IR、言語Diagnostic | SPEC状態、Git、テスト実行 |
| SPEC文書モデル | 配置、Frontmatter、文書種別、状態、関係、path | CLI文法、subprocess |
| Context解決モデル | 型付きグラフ、適用可能性、完全閉包、coverage | Markdown表示、CLI adapter手順 |
| 操作仕様 | 各操作の入力、選択、処理順、結果、固有Diagnostic | 他操作の詳細手順 |
| SDDフロー | 操作を呼ぶ順序、人間判断、戻り先 | CoreのSchema・判定ロジック |

### 3.2 KISS

現行Core 1.0は、中心機能に加えて次を同時に解こうとしている。

- 複数workspaceの連合と所有境界
- 並行branchでのID衝突の勝敗判定と改番候補
- 3種類の将来ProfileとManifest契約
- 4種類のhash/digestの公開
- 文書内改訂履歴の表示Projection
- command内容を正規化したbinding同一性
- Full Flow、Spike、Stopped、Integrateを含む運用フロー

いずれも単独では合理性があるが、最小垂直スライスの成立前に相互作用まで確定している。
Core 1.0では「単一workspaceで、要求を解決し、検査し、テストを実行できる」までを先に閉じる方が単純である。

### 3.3 YAGNI

次の機能は、必要性を測るPhase 0/4より前に詳細契約が固定されている。

| 機能 | 現状 | 提案 |
|---|---|---|
| モノレポ連合 | Core 1.0必須 | 1.1候補。単一workspace実証後に再評価 |
| ID衝突の自動改番支援 | Core結果SchemaとIntegrateへ組込み | Coreは重複を`failed`にするだけ。改番支援は事故頻度を測って追加 |
| Profile実行基盤 | 実ProfileはDeferredだがManifestと設定予約を規定 | opaqueな名前空間保持だけ残し、Manifest/Validator/移行は延期 |
| Projection Digest | 表示再現性用に公開 | stale防止に必要なContext Digestだけ公開 |
| 必須Revision History | 全SPECで必須 | Gitを正とし、必要な文書だけ任意記録 |
| 厳格な本文スタイル検査 | H2順序・空節・疑似節までCoreが検査 | 正規テンプレート提供を基本とし、合否は最小構造だけに限定 |

延期は恒久的な否定ではない。再評価条件と適合fixtureが揃った時点で、新しいADRから導入する。

### 3.4 DRY

DRY違反の中心は文章の重複ではなく、**同じ判断が複数箇所で合否を左右すること**である。

- status集約規則は共通契約だけが所有する。
- Git基準版と変更集合は`check`操作仕様だけが所有する。
- TASKの状態と変更境界は文書モデルとSDDフローで役割を分け、手順を二重定義しない。
- モノレポを延期する場合、各操作仕様からworkspace横断分岐を除く。
- ADRは採用理由だけを保持し、詳細仕様はADRなしで実装可能にする。

なお、DRYは同じ語を1回しか書かないという意味ではない。概要や例で同じ語を使うことは許容するが、
規範値、状態遷移、Schema、Diagnostic効果を再定義してはならない。

## 4. Core 1.0の再定義案

### 4.1 残す中心機能

1. EARS-AI Coreの決定論的ParserとSemantic IR
2. 単一workspaceの`.spec/bitz.yaml`とREQ/TECH/ADR/TASK
3. 文書ID、規範文ID、型付き関係、参照切れ・循環検査
4. 強い依存の完全閉包と単一のContext Digest
5. `bitz context`、`bitz check`、`bitz verify`、`bitz doctor`
6. `MUST`句とテストpathの対応、および設定済みcommandの実行
7. 共通status、Diagnostic、終了コード、最小report
8. Git差分を使う変更範囲checkと承認済みREQ保護

### 4.2 Core 1.0から外す候補

#### S1: モノレポSPEC連合

`workspace.id`は将来互換のため結果上の`root`として残してよいが、`monorepo.members`、修飾ID、横断所有、
`--all-workspaces`は実装しない。単一workspaceの性能と利用価値が実証された後、独立したCapabilityとして追加する。

再評価条件は、パイロット5件のうち2件以上で複数`.spec/`が必要となり、単一root `.spec/`ではContext上限、
所有境界、運用時間のいずれかに測定可能な問題が出ることとする。

#### S2: ID衝突の自動改番支援

Coreは現在集合の重複IDを`SPEC-ID-DUPLICATE-001`で失敗させる。`idCollisions`、incumbent/challenger、
`proposedId`、`rewriteSites`、`SPEC-BASE-AMBIGUOUS-001`、専用Integrate段階は1.0から外す。
小規模チームは衝突時に人間が最大番号+1へ改番し、通常の`check --full`で確認する。

再評価条件は、パイロットまたは初期運用でID衝突が複数回発生し、手動解決が平均作業時間または欠陥率へ
無視できない影響を与えることとする。

#### S3: Profile実行基盤

Core Parserは`[namespace:TERM]`をopaqueな拡張として保持し、未知拡張をwarningにできる。
一方、Profile Manifest、外部Validator、Profile固有Serializer／migration、`profiles`互換性判定は実Profileが1件もない
Core 1.0では実装しない。SDD/Quality/DDDの3文書は1つの非規範な将来候補へ統合する。

#### S4: 必須Revision History

正確な差分、変更者、時刻はGitを正とする。全SPECへの3列表を必須にせず、重要な変更理由はADR、PR、commitへ置く。
現在契約の理解に必要な短い理由がある場合だけ、任意の`Notes`へ安定参照を記録する。

これに伴い、Context Bundleの`revisionHistory`、`#revision-history`展開、履歴専用Projection規則、
履歴だけで変化する`fileHash`の公開を削除できる。

#### S5: 公開hashの縮小

公開契約はstale検出用の`contextDigest`だけにする。文書単位の内容hashやファイルhashは実装内部のcache keyとし、
API互換性の対象にしない。提示結果のcacheが必要になった時点で、Projection Digestを追加する。

#### S6: verify bindingの単純化

command名をbinding IDとする。同じcommand名へ属するtest pathを辞書順で1回にまとめる。
異なるcommand名が同じargv/cwdを持っていても、利用者が別名を定義した意図を尊重して別々に実行する。
これによりCanonical JSONによるbinding同一性と代表command名の選択を削除できる。

#### S7: 本文スタイル検査の縮小

Coreの合否対象はFrontmatter、H1、EARS-AI構文、必須の意味節に限定する。
H2順序、空の任意節、太字の疑似節はformatter/linter候補とし、Core 1.0の合否から外す。
REQの`Intent`、`Acceptance Criteria`、`Verification`は維持し、その他の文書種別はテンプレートを推奨形として提供する。

- Frontmatter、状態、文書種別は同じ文書モデルだが、本文テンプレートとは分離する。
- ID、関係、path、coverageは全操作が使うトレースモデルへ置く。
- `context`、`check`、`verify`、`doctor`は入力、処理、出力、Diagnosticを各自で所有する。
- モノレポ仕様はCore 1.0の正本構造へ置かず、将来Capabilityの提案資料へ移す。

ADRを読まなくても現行実装を決定できることを必須とする。

## 7. 適用順序

大規模なファイル移動と意味変更を同時に行うと、レビュー不能になる。次の順で段階適用する。

### Phase A: scope裁定

S1〜S7を個別に採否決定する。採用する削減ごとに既存ADRを改訂し続けず、Core 1.0 scopeを置き換える
新しいADRを1件作る。旧ADRは判断履歴として残す。

### Phase B: 共通契約の抽出

意味を変えず、status、Diagnostic、report、revisionの正本を`00_共通契約`へ集約する。
各操作の重複表は削除し、固有差分だけを残す。

### Phase C: 操作仕様の分離

現`06_参照・トレース・検証仕様`からトレースモデル、`check`、`verify`を分離する。
現Context仕様から関係・coverageモデルをトレースモデルへ移し、`context`固有の入出力とDigestだけを残す。

### Phase D: 上位文書の縮約

設計書とユースケースから詳細手順、Schema、Diagnostic、状態遷移表を削除し、目的、境界、シナリオへ戻す。
運用文書はコピーした契約ではなく、正本操作をどう呼ぶかだけを記載する。

### Phase E: 垂直スライスで検証

単一workspaceのREQ 1件について、作成、Context取得、check、実装、verifyまでを実装またはfixtureで通す。
実証できない拡張点は文書へ戻さず、再評価条件だけを提案資料に保持する。

## 8. 受入条件

再編完了は行数削減だけで判定しない。次を満たすことを条件とする。

1. 各Schema field、状態遷移、Diagnostic効果、対象選択規則に正本が1つだけある。
2. ADRを読まずに、Core 1.0の全公開操作を実装できる。
3. 設計書はJSON Schema、完全なDiagnostic表、subprocess手順を再掲しない。
4. 各操作仕様は他操作の分岐を所有しない。
5. `context -> check -> verify`の単一workspace垂直fixtureが、ネットワークとLLMなしで通る。
6. 各必須機能は少なくとも1つの利用シナリオと失敗fixtureを持つ。
7. 将来機能は実装可能性ではなく、測定可能な再評価条件を持つ。
8. 全Markdownリンクが解決し、「正とする」参照が規範本文同士の一方向参照に限られる。
9. 同じ状態表、結果Schema、CLI文法を複数文書へコピーしていない。
10. 文書移動と意味変更を別commitにし、各段階でレビュー可能なdiffを保つ。

## 9. 残すべき複雑性

簡素化しても、次は中心価値または安全性に直結するため削らない。

- EARS-AI規範文の安定IDと原子性
- Parserの決定論性と不正候補行の検出
- 型付き依存の参照切れ・型違反・循環検査
- 強い依存の完全閉包。上限超過時に部分成功しないこと
- `MUST`句単位のテスト対応
- 承認済みREQを無断変更しないGit差分保護
- SPEC本文からコマンド、権限、外部送信先を導出しないこと
- テストprocessのtimeout、出力上限、秘密情報を保存しないこと
- `failed`、`blocked`、`error`を区別すること

KISSは必要な安全境界を弱める原則ではない。中心機能の成立に直接必要な複雑性は残し、
利用事実のない拡張と表示・運用自動化を後段へ送る。

## 11. 最終提案

最初にSTRUCT-001〜003、011を採用し、正本の責務境界を直す。その後、単一workspaceの垂直スライスを
Core 1.0の基準にしてSTRUCT-004〜010を裁定する。

現行設計をそのまま実装すると、仕様レビューで解消した多数の境界条件を一度に実装・試験する必要がある。
先に仕様構造とscopeを小さくすれば、EARS-AIの価値を早く検証でき、必要と判明した機能だけを安定した境界へ追加できる。
