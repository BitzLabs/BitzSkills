# 提案資料

## 1. 位置づけ

本ディレクトリは、確定した設計（[02.設計書](../02.設計書/README.md)、
[03.詳細設計](../03.詳細設計/)）に対するレビューの原文と、その裁定の状況を保持する。

- 設計書の本文は「現在の決定内容」を述べる
- [決定記録](../02.設計書/10_決定記録/README.md)は「なぜその決定に至ったか」を保持する
- 各レビュー文書は「決定を変えるべきかもしれない材料」を、[用語集](../用語集.md)による文言の統一を除き原文のまま保持する
- 本READMEは「何を採用し、何を残したか」の最新の状態を保持する

提案が裁定されたら、設計書の本文と決定記録へ反映する。レビュー文書の中の行番号や
改訂例はレビュー時点のスナップショットであり、裁定した後の仕様の正にはしない。

## 4. Core 1.0で採用しない事項

| 事項 | 1.0での判断 | 再評価条件 |
|---|---|---|
| 汎用のテストを選ぶ指定と`nodeid` | ファイル単位を維持 | 複数のランナーで偽陽性が日常的に発生し、共通契約を定義できる |
| 目的ごとの`refines`の省略 | 完全閉包を維持 | 上限の超過が実際の作業で繰り返し起き、意味を欠落させない、規範文を起点とする規則を証明できる |
| `bitz check --strict` | 共通の終了コードと可視化を維持 | 警告の種類ごとに、CIで昇格させる需要が確認される |
| `bitz fmt` | 公開操作へ追加しない | EARS-AIの表記の揺れが、主要な運用負荷になる |
| 後置のプロファイル拡張 | 前置の拡張だけを確定 | 実際のプロファイルで、前置の表現が不十分になる |
| `implements.addresses` | TASKの`addresses`と、テストの`covers`を維持 | 実装の漏れを、現行の規範文単位のTASKとカバレッジで防げない |
| TASK境界の警告化と自動承認 | `blocked`を維持 | 失敗時の通過にせず、開始時点の差分を再現できる契約が成立する |
| 削除済みIDについて、Git履歴から作る削除済みIDの索引 | 管理済みの仕様文書の削除禁止と、現在の集合での重複の検出に限定 | Coreの検査を迂回したIDの再利用の事故が確認され、シャロークローンでも決定論的な検出範囲を定義できる |
| 未所有のコードとテストのパスの警告化 | 対象外（件数のみ）を維持 | 仕様文書の整備率が高い運用で、未所有のパスの見落としが実害として確認される |
| ADRの改訂関係の型付き語彙と`x-amends` | 3点記録の規約を維持 | 改訂関係の機械追跡が実測で必要になる（ADR-020の`Decision`の4番目の項目、ADR-033） |
| ファイル数によるキャッシュの迂回 | 固定の閾値を設けない | ベンチマークで、キャッシュのI/Oが支配的と判明する |

## 5. クローズ判定

- 次期版の構想、共通設計、EARS-AI規格、仕様文書のファイルの規定は設計済み
- 旧版の試行錯誤から、有効な依存の解決と境界の検証を選別し、軽量な中核へ反映済み
- 全提案に採否、理由、反映先または再評価条件を記録済み
- 実装の前に解消すべき契約の矛盾は、正本へ反映済み
- 実装のコード、性能のベンチマーク、1.1以降の拡張機能は未着手

したがって、レビュー01と02の設計レビューのゲートは**完了**とする。次の工程は、Core 1.0の最小の垂直スライスの実装である。
将来候補は本ディレクトリから直接実装せず、新しい実測結果と裁定を伴う提案またはADRから開始する。

| 先勝ちの基準 | 統合先のブランチの先端に存在する側を勝者とする。コミットの時刻、`semanticHash`、Gitのリネーム検出を使わない |
| 正規手順 | 統合先との合流をGitへ記録した後の木で改番する。勝者が旧IDを保持するため、キーが消えない |
| 改番の実行主体 | スキルまたは拡張へ委譲し、Coreは検出と機械可読な提示に限る。公開操作は4つのまま非変更系 |
| 新IDの採番 | 同じワークスペースにあり、同じ種別である全IDの最大値+1。0埋めの幅が異なるIDは別のIDとする |
| 対象種別 | REQ、TECH、TASK、ADR |
| フロントマター | 改番を表す項目を追加しない。記録は`Revision History`へ置く |
| 開発フロー | 骨格へ`Integrate`を追加。完了条件はPRのマージを含めず、統合先の先端を基準版とする再検査の通過まで |
| CIの基準版 | `--base <統合先先端>`へ統一。検査する対象の木が、統合先の先端を含むことを前提とする |

新しい入力の機構、永続する台帳、Git履歴の走査は追加していない。ADR-037が裁定した「削除と再作成の交差」に対する
保証範囲も変更していない。

### 15.2 検討中に見つかった既存設計の欠落

裁定の過程で、改番に固有ではない欠落と、提案の本文自体の誤りが見つかった。いずれも訂正して反映した。

- **TASKをPRの中で完了できない。** §6.3と当時のフロントマター共通仕様 §5の遷移表は、TASKの作成時の状態を`open`だけと
  するが、基準版は自分のブランチの外側にあるため、ブランチの中で`open -> done`まで進めたTASKは`[new] -> done`と
  なり、許可された遷移に含まれない。実装すれば、状態`done`のTASKを含むPRを一律に`failed`にする。基準版に存在
  しない文書は、現在の値の語彙だけを検査する規則を確定した（丙-2）。承認済み要求の保護が
  「Git基準版に存在しない新規fileは変更前状態との比較対象外とする」としているのと同じ原則である。
- **§4.2の判定表が§3.1と矛盾していた。** 「両方が基準版に存在する＝発生しない」としていたが、スラッグの
  異なる、同じIDのファイルは、Gitが競合にせず、合流コミットのツリーオブジェクトには2件入る。診断`SPEC-BASE-AMBIGUOUS-001`
  （重大度`error`、結果への効果`blocked`）として扱う（甲-1、乙-1）。
- **IDDUP-005の推奨が実装できなかった。** 改番するパスを`rewriteSites`から境界検査の対象外にする案は、境界検査の時点で
  重複が解消し、`idCollisions`が空になるため成立しない。P1で確定したコミットの規約とフローの順序がすでに解に
  なっており、追加したのは基準版の条件1文だけである（丙-3）。
- **改番でコンテキストのハッシュ値が変化しないという受入条件が成立しなかった。** `semanticHash`は正規化したフロントマターを含む
  ため、`id`の変更はコンテキストのハッシュ値を変える。`Revision History`への追記だけが、意味の集合の外にある（甲-3）。
- **IDDUP-009の理由付けが誤っていた。** 敗者の削除が許されるのは、ADR-037の`Decision`の4番目の項目（未追跡の仕様文書の破棄）
  によるものではなく、勝者が同じ文書IDを保持し、キーが消えないためである（丁-2）。

### 15.3 安全側へ倒した判断

- 診断`SPEC-BASE-AMBIGUOUS-001`は、重大度を`error`、結果への効果（`resultStatus`）を`blocked`とした。重大度を`warning`にすると、改番を適用した後に、
  勝者の遷移の検査、削除の判定、承認済み要求の保護が、通過状態のまま抜ける。重大度`warning`と結果への効果`blocked`の組合せは
  ADR-021の`Decision`の4番目の項目が禁じるため、中間の強度は取れない。
- `--base`を指定しないときは、`idCollisions`へ`instances`だけを返す。既定の`HEAD`は、新規の衝突について正しい勝敗を
  出せず、合流をコミットしないまま検査すると、統合済みの勝者の側へ改番を提案してしまう。

### 15.4 不採用とした案

`renumberedFrom`および`x-renumbered-from`は撤回した。前者は、Gitから導ける情報をフロントマターへ持ち込み、
ADR-015の`Decision`の4番目の項目と、旧SPEC知見の「成果物ごとのversion、updated」と同型の陳腐化を生む。
後者は、`x-`で始まる拡張フィールドを合否の判定に使わない規則に反する。Coreへの`bitz renumber`の追加、コミットの時刻による先勝ち、
番号の範囲の予約、ULIDなどへの変更、基準版の重複したパスから代表を選ぶ案も採らない。不採用の理由は、ADR-038の`Alternatives`（18件）を
正とする。
