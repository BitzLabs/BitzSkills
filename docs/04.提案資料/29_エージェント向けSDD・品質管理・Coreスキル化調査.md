# エージェント向けSDD・品質管理・Coreスキル化調査

- 状態: `Draft`（調査記録。規範ではない）
- 調査日: 2026-09-29
- 対象: `bitz-sdd`、`bitz-quality`、`bitz-core`のエージェント向けスキル
- 関連: [実装計画](30_bitz-sdd・品質管理・Coreスキル化実装計画.md)、[SDDフロー](../02.設計書/03_SDDフロー.md)、
  [品質属性と安全境界](../02.設計書/02_品質属性と安全境界.md)

## 1. 目的

Core 1.0の公開操作をエージェントが安全に利用し、要求、実装、検証、品質判断を一貫して進めるため、
次の問いを調査した。

1. 2025年以降の仕様駆動開発（SDD）は、どのような構造へ収束しつつあるか。
2. コーディングエージェントの実例から、何が有効で、何が失敗しているか。
3. 品質管理を、テスト合格や単一スコアへ縮退させずに運用するには何が必要か。
4. エージェント向けスキルを、誤発火、過剰な指示、権限逸脱から守るにはどう設計すべきか。
5. 1系の`bitz-sdd`と`bitz-quality`から何を学び、何を2系へ持ち込まないか。

本書は調査した事実、証拠の限界、設計への含意を残す。採用する計画は[実装計画](30_bitz-sdd・品質管理・Coreスキル化実装計画.md)へ分離する。
1系のブランチ`archive/v1`は読取りだけとし、1系の規則、スクリプト、テンプレートを2系へ移植しない。

## 2. 調査方法

### 2.1 情報源の優先順位

| 優先 | 情報源 | 用途 | 限界 |
|---|---|---|---|
| A | 規格本体、政府機関、査読論文、製品の公式仕様 | 契約、安全、品質モデル、確認できる機能 | 規格への適合は別途評価が必要 |
| B | 一次研究のプレプリント | 新しい研究結果、研究課題 | 査読前であり、再現性が未確定の場合がある |
| C | 提供者の技術記事、実運用報告 | 実例、運用上の知見 | 自社事例であり、一般化できない |
| D | 本リポジトリの履歴、1系の評価記録 | Bitz固有の成功と失敗 | ケース数が小さく、独立研究ではない |

販売資料、二次まとめ、検索結果だけを判断の根拠にしない。新しい研究については、公開日が新しいことと証拠が強いことを分けて評価した。

### 2.2 調査範囲

- SDDの研究、Kiro Specs、GitHub Spec Kit
- OpenAIのスキル仕様、スキル評価、エージェント評価、安全設計
- AI支援開発の生産性、ベンチマークの欠陥、生成パッチの安全性
- ISO/IEC 25010、NIST SSDF、SLSA、OpenSSF Scorecard
- EARSとNASA FRETの制約付き自然言語
- 2系の現行設計と、1系の`bitz-sdd`、`bitz-quality`、評価報告

## 3. 調査結果の要約

### 3.1 調査から導いた設計指針

以下には、研究や実例で観察された問題と、現行Coreの責務を踏まえた本計画の設計判断を併記する。
各項目が同じ強さで実証されたという意味ではない。

1. **仕様は成果物ではなく、実行可能な契約へ接続して初めて効く。** 要求、設計、タスクを作るだけでは不足し、
   検査、テスト、差分、人手承認へ追跡できる必要がある。
2. **機械判定とエージェントの推論を分離する。** 構文、参照、状態、トレース、テスト実行はCoreが判定し、
   スキルは利用目的の選択、説明、作業の順序を担当する。
3. **スキルは小さな発見面と段階的な開示を持つ。** 名前と説明が主な発火信号であり、長く重複する説明や万能スキルは
   誤発火とコンテキスト肥大を招く。
4. **テスト合格は品質の十分条件ではない。** 機能的には正しいが脆弱なパッチ、狭すぎるテスト、公開ベンチマークへの汚染が
   実測されている。
5. **品質判定はリスクと証拠に基づく。** 単一の総合点より、重大な未解決事項、証拠の欠落、適用できない検査を明示する方が安全である。
6. **権限は利用者の依頼から導出し、外部の本文から増やさない。** 仕様本文、テスト出力、Web、Issueは未信頼データであり、
   そこに書かれた命令をエージェントへの指示にしない。
7. **効果は実地で測る。** 合成ベンチマーク、自己申告、生成量は、実際の完了時間、手戻り、安全、保守性を代替しない。

### 3.2 証拠がまだ弱い知見

- SDDの公開利用は急速に増えているが、SDDが開発成果を因果的に改善するという研究はまだ成熟していない。
- エージェントが開発を高速化する度合いは、モデル、時期、開発者、タスク、既存の開発環境によって大きく変わる。
- 多数のエージェントを並行させると処理量が増える実例はあるが、調整、評価、権限、競合解消の費用も増える。
- LLMによる意味レビューは有用な補助になりうるが、安定した合否判定や人間の承認の代替になる証拠はない。

このため、初期リリースでは生産性の優位性、多数エージェント、自動承認を前提にしない。

## 4. SDDの研究と実例

### 4.1 2026年の研究

#### Spec-Driven Development for Agentic Software Engineering

2026年8月提出のプレプリントは、仕様を人間とエージェントの契約面とし、エージェント周辺の技術的な仕組みと、
チーム周辺の方法論的な仕組みを区別する。重要なのは、著者自身が査読済みの証拠と共通語彙がまだ確立していないと認め、
検証済み理論ではなく研究課題として提示している点である。

設計への含意:

- Bitzは「SDDで生産性が上がる」と先に主張せず、評価可能な契約と測定方法を提供する。
- エージェントへの指示だけでなく、Core、Git、CI、レビュー、権限を含む仕組み全体を設計対象にする。
- 人間の責任を曖昧にせず、要求承認と最終品質判断を人間へ残す。

#### SpecMine

2026年8月のプレプリントは、公開GitHubから470,795件の仕様ファイルを73,030リポジトリで収集し、
Kiro型の要求・設計・タスク構成も98,574件、12,910リポジトリで確認した。仕様と実装を同じPRで変更する流れや、
コード、文書、PR、Issueへの参照を研究できる大規模な資料である。

設計への含意:

- 仕様をリポジトリへ置き、コードと同じ変更履歴で扱う方式には十分な実例がある。
- ただし、普及件数は品質向上の証明ではない。Bitzでは参照の存在だけでなく、Coreによる型、状態、カバレッジの検査を維持する。
- 将来の実地評価では、仕様と実装の同時変更、追跡の維持、手戻りを測れる。

#### From Code to Contract

2026年1月のプレプリントは、SDDを`spec-first`、`spec-anchored`、`spec-as-source`の3段階で整理し、
常に最大の厳格さを使うのではなく、領域に応じて選ぶ考え方を示す。

設計への含意:

- 2系は、現行の設計どおり、通常の変更には簡易フロー、高リスク変更には完全フロー、未知の技術にはスパイクを使う。
- EARS-AIを正本とする範囲を明示し、すべての設計資料やコードを生成物へ変える`spec-as-source`を初期目標にしない。

### 4.2 Kiro Specs

Kiroは機能向けに要求、設計、タスクの3成果物を持ち、バグ修正には再現条件、現在の動作、期待する動作、
変えてはならない動作を扱う別経路を設けている。タスクの依存をグラフにし、独立したタスクを波ごとに並行実行する。
また、よく分かった小さな変更には軽量経路、複雑または規制対象の変更には明示的な承認点を推奨している。

採用する知見:

- 機能、バグ修正、スパイクを同じ雛形へ押し込まない。
- バグ修正では、再現、現在、期待、非変更、回帰テストを1組にする。
- タスクの依存を先に確認し、独立性を証明できたものだけを並行化する。
- 小さな変更に完全フローの成果物を常に要求しない。

採用しない知見:

- エージェントが既存コードを見てタスクを自動的に完了扱いにする機能は、CoreのTASK境界と人手確認を迂回しうるため採用しない。
- 成果物をKiro固有の3ファイルへ固定せず、現行のEARS-AIと仕様文書モデルを正本にする。

### 4.3 GitHub Spec Kit

Spec Kitは、方針、仕様、明確化、計画、チェックリスト、タスク、分析、実装、収束という流れを示す。
品質ゲートを任意に挿入し、分析で問題が見つかった場合は末端の出力だけを直さず、問題を作った上流へ戻る考え方を持つ。
また、機能開発、バグ修正、既存システムの調査を独立した入口として扱う。

採用する知見:

- 仕様、計画、実装、収束を分け、問題を上流の正本で直す。
- 各段階を独立して再開できるようにし、巨大な1回のプロンプトに依存しない。
- 最終段階では「何を作ったか」ではなく「仕様と証拠が収束したか」を確認する。

留意点:

- Bitzには既にEARS-AI、Coreの4操作、仕様文書の状態遷移がある。Spec Kitのファイル構成やコマンド体系を重ねない。

### 4.4 EARSとNASA FRET

EARSは、制約のない自然言語にある曖昧さ、複雑さ、検証不能性を、小数の文型で減らす方式として2009年に提案された。
NASA FRETは、制約付き自然言語を明確な意味、図、時相論理、対話的なシミュレーションへ接続する。

設計への含意:

- 自然言語を完全に自由にせず、EARS-AIの構造を維持する。
- 文型に合うことと、利用者の意図に合うことを分ける。Coreは前者を検査し、後者は要求レビューで確認する。
- 将来、形式検証へ接続する場合も、自然言語、意味表現、検証器の境界を保つ。

## 5. エージェント向けスキルの設計知見

### 5.1 発見と段階的な開示

OpenAIのスキル仕様では、最初にモデルへ見える主な情報は名前と説明であり、選択された後に`SKILL.md`が読み込まれる。
最近のモデル向け指針は、説明が長く重複する多数のスキルが、切詰め、混同、誤った経路選択を起こすと報告している。

採用する原則:

1. 名前は利用者の目的を表し、製品の内部構成を表さない。
2. 説明には使う条件、使わない条件、明確な境界を書く。
3. `SKILL.md`は短い経路案内と停止条件にし、詳細な契約は必要な参照だけを読む。
4. 決定論的な反復処理だけをスクリプトにし、CLIと同じ判定を再実装しない。
5. モデルの能力を過小評価した長い手順書を避け、失敗しやすい非自明な規則へ集中する。

### 5.2 評価を先に定義する

OpenAIのスキル評価の指針は、スキルを書く前に成功を定義し、入力、実行の軌跡と成果物、検査、得点を1組にする。
明示的な依頼だけでなく、暗黙の依頼、会話の文脈、発火してはならない負例を含める。

評価する4軸:

| 軸 | 問い | 主な検査 |
|---|---|---|
| 成果 | 利用者の目的を満たしたか | 決定論的な成果物検査、保持した試験ケース |
| 過程 | 正しい操作と順序を選んだか | 軌跡、コマンド、引数、停止点 |
| 安全 | 権限、秘密、未信頼入力を守ったか | 禁止操作、承認点、敵対的ケース |
| 効率 | 不要な読取り、生成、再試行を避けたか | 呼出し回数、時間、トークン、差分量 |

初期評価はローカルで再現できるJSONLの軌跡と成果物を正とし、特定の提供者の評価サービスへ依存しない。

### 5.3 過剰なスキル分割と万能スキル

両極端を避ける必要がある。

- 1操作ごとにスキルを分けると、発見情報が増え、同じ前提を重複して持つ。
- すべての開発作業を1つのスキルにすると、常時発火し、巨大な手順と権限を抱える。

初期仮説は、Core 1、SDD 3、品質管理2の計6スキルとする。この数は研究から導かれた最適値ではない。
Phase 0でCore、SDD、品質管理の3入口と内部参照にまとめる案を、同じ発火・行動ケース、読取り量、費用で比較して決める。
運用後も発火評価または利用記録が境界の問題を示した場合は分割または統合する。

## 6. 品質と安全の調査

### 6.1 ISO/IEC 25010:2023

ISO/IEC 25010:2023は、ソフトウェアを含むICT製品の品質を9つの特性と下位特性で扱い、要求、設計、テスト、
品質管理、受入基準、測定に使える参照モデルとする。

設計への含意:

- 品質を機能テストだけに限定しない。
- 変更に関係する品質特性を選び、測定可能な受入条件へ変換する。
- 初期版で「ISO準拠」を主張せず、品質観点の漏れを防ぐ分類として参照する。

### 6.2 NIST SSDF

NIST SP 800-218のSSDFは、安全なソフトウェア開発を、組織の準備、ソフトウェアの保護、安全なソフトウェアの生産、
脆弱性への対応の4群で整理する。NISTはSSDFを一律のチェックリストではなく、リスク、費用、適用性に合わせて調整する
成果志向の基盤として説明している。2025年12月には1.2の草案が公開されているため、初期設計は最終版の1.1を基準とし、
1.2確定時に差分を確認する。

設計への含意:

- 品質管理スキルは固定工程を全変更へ強制せず、リスクに応じた証拠計画を作る。
- 脆弱性を見つけた後の根本原因、類似箇所、再発防止まで評価対象にする。
- 供給網、権限、秘密、更新、応答を機能品質から切り離さない。

### 6.3 SLSA 1.2とOpenSSF Scorecard

SLSA 1.2は2025年11月に公開された現在の承認済み仕様で、ビルドの来歴に加え、ソースの履歴と管理を扱う経路を持つ。
OpenSSF Scorecardは、ブランチ保護、レビュー、危険なワークフロー、依存の固定、トークン権限などを自動検査する。
同時にScorecard自身が、検査はヒューリスティックで偽陽性と偽陰性があり、総合点は個別の行動を表さず、
一律の必須基準ではないと明記している。

設計への含意:

- リリース時にソース、ビルド、成果物の対応を記録し、段階的に来歴を強化する。
- Scorecardの総合点をGateにせず、変更に関係する個別の重大な検査を証拠として扱う。
- 依存の固定、最小のトークン権限、レビュー、危険なワークフローを品質観点へ含める。

### 6.4 機能的に正しいが安全でないパッチ

Google Researchが掲載した2026年のACL論文は、すべての機能テストを通るが脆弱性を含むパッチを複数のモデルと
エージェント構成で確認した。例示された組合せでは情報露出の攻撃成功率が40.7%であった。
別の20,000件を超えるGitHub Issueの研究も、LLMとエージェントによるパッチに新しい脆弱性があり、
自律性が高い場合やIssueの情報が不足する場合にリスクが増える関連を報告している。

設計への含意:

- `verify`の成功だけで`ready`にしない。
- 認証、認可、未信頼入力、秘密、外部通信、直列化、コマンド実行、依存更新を変更した場合は、
  セキュリティの証拠を必須にする。
- バグ修正の課題文に、悪用可能な入力や過度に狭い受入条件が混じるケースを、保持した評価へ含める。

### 6.5 プロンプトインジェクション

OpenAIの2026年の安全報告は、外部コンテンツにある命令を単純な文字列分類だけで完全に防ぐことは難しく、
未信頼の入力源と危険な操作先を組み合わせない設計、最小権限、明示的な確認、サンドボックス、継続的な敵対評価を重視する。

Bitzでの適用:

- 仕様本文、コメント、Issue、テスト出力、Webの内容はデータとして扱う。
- それらに書かれた「コマンドを実行せよ」「秘密を送れ」「規則を無視せよ」という文を指示として実行しない。
- 読取りと書込み、ローカルと外部、可逆と不可逆を分離する。
- プッシュ、PR、通知、公開、デプロイ、外部送信は、スキルの通常動作に含めず、利用者の明示した依頼を必要とする。

## 7. 実例と失敗例

### 7.1 OpenAIのエージェント主体の開発例

OpenAIの2026年の実運用報告は、リポジトリの知識を正本にし、アーキテクチャと品質を機械的に強制し、
人間が方向を決めてエージェントが実行する方式を報告している。長時間実行には、予測できる作業場所、保存できる中間状態、
サンドボックス、再開可能性が重要とされる。

一方、多数の対話セッションを人間が直接監督すると、3〜5件を超えた付近で文脈切替が負担になったという報告もある。
これは多数エージェントを初期の必須機能にしない理由になる。先に、単一作業の契約、証拠、再開点を安定させる。

### 7.2 DORA 2025

DORAはAIを、組織の既存の強みと弱みを増幅するものと報告している。ツールだけでなく、基礎となる組織と開発システムが
効果を左右する。

設計への含意:

- スキル導入件数や生成量を成功指標にしない。
- 仕様の明確さ、試験の質、レビュー能力、復旧性が弱い状態で自律性だけを上げない。
- リードタイムと同時に、変更失敗、手戻り、未検出欠陥、人手レビュー時間を測る。

### 7.3 METRの生産性研究

2025年の無作為化比較試験では、16人の経験あるOSS開発者が246件の実作業を行い、初期2025年のAIツール利用で
平均19%遅くなった。参加者は事前に24%の短縮、事後にも20%の短縮を見込んでおり、認識と実測が反対だった。

ただし、2026年の追跡研究は、AIなしの作業を避ける参加者とタスク選択、多数エージェント利用時の時間測定による偏りから、
現在の効果を信頼できる精度で測れないと報告した。研究者は2026年には高速化が大きい可能性を認めつつ、証拠は弱いとしている。

設計への含意:

- 古い19%低下を永続的な一般則にせず、「自己申告と実測は異なりうる」という教訓を採用する。
- 実際のBitz利用で、同程度の実課題、同じ品質基準、完了までの人間時間を測る。
- 並行エージェントでは、壁時計の時間だけでなく、人間の監督時間、計算費用、手戻りを測る。

### 7.4 SWE-bench Verifiedの限界

OpenAIは2026年2月、SWE-bench Verifiedを最先端モデルの評価に使わないと発表した。公開ケースへの汚染と、
狭すぎるまたは広すぎるテストが、能力の測定を歪めるためである。

設計への含意:

- 公開ベンチマークだけでスキルを認定しない。
- 非公開または保持したケースを持ち、定期的に入れ替える。
- テストが課題の意味を十分に検査しているかを、評価ケース自体のレビュー対象にする。

## 8. 1系から得た知見

### 8.1 構成

1系の`bitz-sdd`は14スキル、`bitz-quality`は10スキルを持っていた。SDD側は中核、発見、設計、データ、文書、診断、Git、
実装、Issue、運用、計画、報告、レビュー、テストへ分かれ、品質側は中核、設計、診断、ゲート、初期化、測定対象、報告、
レビュー、得点、追跡へ分かれていた。

### 8.2 有効だった点

- `.spec/`を正本にし、レビューと報告を機械的な処理へ接続した。
- 曖昧な「仕様駆動で」という依頼に対し、構造化した成果物と証拠を残した。
- データ保存方式を根拠付きで比較し、採らなかった案の理由を残した。
- データを使わないCLIでは、データ設計のスキルを発火しない負例を評価した。
- 作業者と評価者を分け、評価者が報告スクリプトを再実行した。

### 8.3 失敗と不足

1. **発火範囲が広い。** `sdd-core`は機能実装、仕様、計画など一般的な依頼へ広く発火する説明を持ち、
   SDDを望まない小作業にも入りやすい。
2. **中核が多すぎる責務を持つ。** 状態遷移、同期、採番、Git、ゲート、委譲、雛形、報告を1スキルが案内し、
   読み込む文脈と変更範囲が大きい。
3. **成果物と工程が固定的である。** 品質側は固定した複数フェーズと多数の生成物を要求し、小さな変更でも儀式化しやすい。
4. **公開契約とスクリプトがずれた。** 評価で、報告スクリプトが読む`decision`が公開契約に書かれておらず、
   実行者がソースを読んで初めて分かった。
5. **任意と必須が曖昧だった。** `api-design.md`が任意であるにもかかわらず、成果物の一覧では必須に見えた。
6. **評価が小さい。** 主な一気通貫ケースはToDoアプリ1件で、全体は3ケース、15アサーションだった。
   安全、敵対入力、実リポジトリ、モデル差、反復時の揺れを十分に扱っていない。
7. **二重の正本を生みやすい。** `.spec/`と`docs/`の同期は、どちらを編集するか、同期に失敗したときの扱いを複雑にした。

### 8.4 2系での扱い

- 1系のスクリプトとテンプレートは移植しない。
- 有効だった「正本、証拠、負例、独立検分」という原則だけを、新しいCoreの公開契約で再設計する。
- スキルの数を先に増やさず、発火評価と実地利用で分割の必要性を証明する。
- スキル内に状態遷移、構文解析、品質の合否ロジックを作らない。
- `.spec/`以外に同期する第二の正本を作らない。

## 9. 本調査から導く設計原則

### 9.1 責務の分離

```text
利用者の目的
    |
SDDスキル -------- 品質管理スキル
    |                    |
    +------ Coreスキル --+
               |
       bitz context/check/verify/doctor
               |
       EARS-AI / .spec / Git / test
```

- **Core**: 決定論的な事実と診断を返す。自然言語の品質承認をしない。
- **Coreスキル**: 正しいCore操作を選び、JSON結果を説明する。判定を複製しない。
- **SDDスキル**: 意図を仕様とタスクへ結び、現行のSDDフローを進める。
- **品質管理スキル**: リスクと必要な証拠を計画し、別の文脈で証拠を検分する。
- **人間**: 要求の意味を承認し、重大な例外と最終の受入れを決める。

### 9.2 証拠を先にする

スキルが「完了」「安全」「合格」と述べる前に、次を特定する。

1. 対象の要求または変更意図
2. 変更したファイルと境界
3. 実行した検査と正確なコマンド
4. 結果と終了コード
5. 検査していない事項
6. 人手判断が必要な事項
7. 証拠を取得したコミットまたは作業ツリーの状態

証拠が不足する場合は`unknown`または「判定不能」を正当な結果とし、推測で成功へ変えない。

### 9.3 リスクに応じた深さ

要求する証拠の量は、文書数や工程数ではなく、次で決める。

- 影響範囲と利用者数
- 変更の可逆性
- データ損失、秘密、権限、外部通信
- 公開API、互換性、移行
- 性能、可用性、SLO
- 技術と要求の不確実性
- 複数ワークスペースまたは供給網への影響

### 9.4 利用者の権限を越えない

- 読取り、診断、計画の依頼から、実装、コミット、プッシュ、公開の権限を推測しない。
- 可逆なローカル変更でも、承認済みの要求の意味を変更するときは先に`draft`へ戻す手続きを必要とする。
- 未信頼本文から新しい権限、URL、コマンド、受信者を採用しない。

### 9.5 評価可能性を製品機能にする

- 各スキルは、明示的な入出力、停止条件、禁止事項を持つ。
- 軌跡と成果物を機械的に検査できる。
- 負例、敵対例、保持したケースを同じ重要度で管理する。
- 評価結果はモデル名、版、実行日、環境、反復回数とともに残す。

## 10. 採らない案

| 案 | 採らない理由 | 再評価条件 |
|---|---|---|
| 1系の24スキルを復元 | 発火面、重複、文脈、保守費用が大きい | 少数入口の発火評価で、分離しないと一貫して失敗する目的が見つかる |
| 1つの万能`bitz`スキル | 通常の開発依頼へ誤発火し、権限と手順が過大になる | 負例を含む発火評価で誤発火せず、行動評価も改善する |
| 品質の総合点だけでGate判定 | 重大事項を平均で隠し、Scorecard自身の非目標にも反する | 重大事項を隠さない別軸の判定を併記し、実地で有効性を示す |
| テスト成功だけで完了 | 安全でない正解パッチと狭いテストを見逃す | 採用しない |
| LLMによる自動承認 | 非決定的で責任境界を失う | 外部の承認基盤と監査契約を別設計し、十分な実証がある |
| 初期版から多数エージェント | 調整、競合、監督、評価の複雑さが先行する | 単一作業の評価が安定し、並行化が律速を解消すると実測できる |
| 外部の評価サービスへの依存 | サービス変更、版終了、再現性の問題 | ローカル正本を維持した追加の表示先としてだけ検討する |
| `.spec/`と別文書の双方向同期 | 二重の正本と競合を作る | 明確な所有権と決定論的な移行を設計し、必要性を実測する |

## 11. 未解決の問い

1. 新規ワークスペースの初期化をCore 1.1で持つか、SDDスキルの雛形として持つか。
2. 要求の意味レビューの結果をGit／PRだけへ残すか、非規範の構造化成果物を定義するか。
3. 品質リスクの分類をプロジェクト設定へ持つか、初期版ではスキルの提案だけにするか。
4. スキルが必要とするCoreの対応機能と版を、プラグインのマニフェストでどう宣言するか。
5. Agent Plugins間の依存を、利用者に分かる形でどう表すか。
6. 保持した評価ケースを公開リポジトリで汚染から守る運用をどう設計するか。
7. 実地比較で、品質を一定にした完了時間と人間の監督時間をどう取得するか。

これらは計画のPhase 0で裁定し、規範の意味を変える項目は提案から直接実装せず、決定記録へ移す。
