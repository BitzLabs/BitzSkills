# 02. Antigravity 詳細設計レビューと改訂提案

**状態**: 提案（未裁定）
**作成日**: 2026-08-25

## 総評

本レビューは、BitzNextプロジェクトにおけるAI仕様駆動開発基盤の設計書（`docs/02.設計書`、`docs/03.詳細設計`）に対する独立した評価である。個人から数人向けの軽量性を前提としつつ、AIのコンテキスト希釈防止、仕様依存の確実な解決、および実装漏れの抑止を両立する観点から評価を行った。

全体として、設定レスに近い運用、明確な責務境界（CoreとCLIの分離）、EARS-AIによる宣言的仕様管理は軽量基盤として非常に優れている。一方で、依存関係の完全閉包がもたらすコンテキスト過多リスクや、ファイル単位に留まる実装トレースなど、AIエージェントの解釈ミスを誘発しうる箇所が見受けられる。本提案では、軽量性を維持しつつこれらを補完する改訂を提示する。

## 1. P1 — Context Resolution時のコンテキスト希釈防止

**現状**
`docs/03.詳細設計/02_SPECファイル規定/10_Context Resolution仕様.md`（以下 `10_Context Resolution仕様.md`）の行218-219にて「意味依存には深度上限を設けない。深度で途中打切りすると末端制約を欠落させるためである。」とされ、上限（文書数20、1MiB等）まで完全な閉包を解決する設計となっている。

**問題**
関連するREQ/TECHを完全なMarkdown（自由記述やコード例である `untrustedText` を含む。行143、158-159参照）としてLLMのコンテキストにすべて投入すると、コンテキスト希釈（Context Dilution）が発生する。LLMが本来注目すべき起点タスクの要件と、遠い依存先の参考情報が混ざり、解釈違いや実装のブレを引き起こすリスクが高い。

**提案**
Context Bundle の生成において、依存距離（Depth）に応じた情報の段階的フィルタリング（Context Projection）を導入する。
- **Depth 0〜1（起点と直接の依存）**: 現状通り完全なMarkdown（自由記述を含む）を渡す。
- **Depth 2以上（間接依存）**: 自由記述（`untrustedText`）を除外し、FrontmatterとEARS-AIのAST（規範文のみ）へ投影（Projection）して渡す。
これにより、末端制約の欠落を防ぐという目的を果たしつつ、LLMのトークン消費と処理時間を削減し、指示の焦点（意図）を明確に保つことができる。処理の複雑性増加はASTフィルタのみであり軽微である。

## 2. P2 — 実装ファイルの規範文レベルのトレース（実装漏れ防止）

**現状**
`docs/03.詳細設計/02_SPECファイル規定/06_参照・トレース・検証仕様.md`（以下 `06_参照・トレース・検証仕様.md`）の行10-11において、テストファイルは `tests.covers` により規範文単位でトレースされるが、実装ファイルは `implements ---> 実装ファイル` と文書単位でのみマッピングされる設計である。`docs/02.設計書/02_specディレクトリ仕様.md`の行60-65のFrontmatter例でも `implements` は配列によるパス指定のみとなっている。

**問題**
テストの網羅性は保証されるが、AIエージェントが実装を行う際、「どの実装ファイルが、どの `MUST` 規範文を解決すべきか」の対応付けが静的に提供されない。結果として、1つの要件文書内に複数の `MUST` が存在する場合、エージェントが一部の実装を漏らす、あるいは無関係なファイルへ誤って実装を混入させるリスクがある。

**提案**
`implements` 属性を拡張し、テストと同様に `addresses` (または `covers`) 配列をオプションで指定可能にする。
- 例: `implements: [ { path: src/auth.ts, addresses: [REQ-001:AC-01] } ]`
- 個人や初期段階など軽量性が最優先の場合はファイルパスのみの指定も許容し、厳密なトレースが必要になった段階で規範文レベルへの段階的な詳細化を可能とする。
これにより、`bitz context` が実装タスクにおけるエージェントへの境界指示をより精密に行える。

## 3. P2 — TASK境界検査の厳格すぎる遮断の緩和

**現状**
`06_参照・トレース・検証仕様.md`の行68-70にて、明示されたTASKの変更境界検査はGitの基準版からの変更パスと比較し、境界外変更は `SPEC-TASK-BOUNDARY-001` とする。また、「Gitが利用できない場合は境界検査をblockedとし、暗黙に通過させない。」と定めている。

**問題**
個人〜数人の軽量な開発フローでは、エージェントの作業中や直前に人間が手動で未コミットの修正（フォーマット調整など）を残しているケースが頻発する。現状の設計ではこれらがすべて境界外変更として検出され、検証プロセスが完全に `blocked` されるため、開発体験が著しく損なわれる。

**提案**
`bitz verify` 実行時の境界外変更に対して、即時の `blocked` ではなく、警告（`passed_with_warnings` または対話的承認への委譲）へと緩和する。または、Git diffの比較対象を HEAD ではなく「TASK着手時点のインデックス」または「Context Bundle生成時のスナップショットハッシュ」に変更する。
これにより、安全性を担保しつつ、軽量運用における柔軟性を損なわない。

## 4. P3 — 小規模プロジェクトにおけるファイルIOキャッシュのバイパス

**現状**
`docs/02.設計書/01_共通アーキテクチャ.md`の行139にて「キャッシュは任意で、削除しても正本から再構築できる」とされている。

**問題**
数十ファイル程度の軽量プロジェクトにおいて、ASTやID索引を都度ファイルシステムへキャッシュ（保存・照合）する処理は、純粋なオンメモリ解析（インメモリ・パース）よりもOSのファイルIOオーバーヘッドにより遅くなる可能性がある。設定レスを志向する中で無駄なI/Oが発生する。

**提案**
文書数が一定の閾値（例: 50ファイル）を下回る場合は、明示的な `--force-cache` 指定がない限りファイルキャッシュへのI/Oをバイパスし、完全インメモリでパースからContext Bundle生成までを完結させる。これによりCLIの体感応答速度（性能）を最速化する。

## 既存レビュー（01_詳細設計レビューと改訂提案.md）との比較

既存レビューと本独立レビュー（Antigravity）の比較は以下の通りである。

*   **同意する点**: 既存レビューの「7.4 Context Digest 再照合の粒度が未定義」において、編集ごとの過剰なオーバーヘッドを問題視し、判定のタイミングを緩和する提案には完全に同意する。本レビューのP2（TASK境界検査の緩和）も、厳格すぎるGit検査が小規模開発の体験を損なうという同根の課題意識に基づいている。
*   **異なる点**: 既存レビューは `bitz fmt` の追加（7.5）や実証条件の縮小（8.1）といったプロセスやツールチェインへの介入が中心であったが、本レビューは「AIエージェントがいかに誤読や実装漏れを防ぐか」というContext Resolutionの内部構造とデータモデル（P1, P2）に重点を置いている。
*   **新規発見**: 依存関係が深くなった際の「Context Dilution（希釈）」リスク（本レビューP1）、および実装ファイルとテストファイルのトレース粒度の非対称性（本レビューP2）は、既存レビューでは指摘されておらず、設計の根幹に関わる新規の発見である。

## 採用優先順位

1.  **P1**: 依存深度に応じた Context Projection（希釈防止） — *LLM性能と実装品質に直結するため最優先*
2.  **P2**: `implements` への `addresses` 追加 — *実装漏れを防ぐためのスキーマ拡張*
3.  **P2**: Git境界検査の `blocked` 緩和 — *開発体験（DX）向上のため*
4.  **P3**: 小規模向けのインメモリパース（IOバイパス） — *余力があれば実装*
