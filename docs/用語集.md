## 2. 表記規則

### 2.1 言語の選び方

1. 日本語を基本とする。
2. 機械が読む語、機械が照合する語は英語のまま書く（§4.1.3）。本文で識別子として指すときはバッククォートで囲む。
   validatorが本文から照合している文字列（例: 「Gitは2.30以上」、matrix行の書式）も変えない。変えるときはvalidatorと同時に直す。
3. 英語をカタカナへ転記するだけになる語は英語で書く（§4.1.4、§4.2）。ソフトウェア設計で広く使われるカタカナ語も、§4.2に挙げた語は
   英語で書く。§4.6の語は日本語（カタカナまたは漢字）で書く。
4. 技術文書で定着した漢語の訳がある語は日本語で書く（§4.3）。定着していない訳語は作らない。
5. 同じ英単語が定義語・値と一般語の両方で使われる場合、定義語・値はバッククォート付きの英語、一般語は§4.2〜§4.4の表記で書く。
   例: `check`操作と検査、`status` fieldと状態、`warning` severityと警告。
6. 固有名と定義語は§4.1.1・§4.1.2の大文字小文字に固定する。一般の英語名詞は小文字・単数形で書く。
7. 1つの概念には1つの語を使う（§4.4）。

### 2.2 カタカナ語

8. カタカナで書く語は、英語の語末の-er、-or、-arなどに当たる音に長音符号を付けて書く（ユーザー、サーバー、パラメーター、インストーラー、フィルター）。
   語末が-yの語には付けない（カテゴリ、エントリ）。
9. 複合語は構成語ごとに本書の表記に従い、中黒を入れない。英語どうしは半角スペースで区切り（test command、lock file）、
   英語と漢字・かなはスペースなしで連結する（fixture作成、Digest材料、`bitz` commandの起動）。

### 2.3 漢字・かな・送り仮名

10. 「公用文作成の考え方」（2022年）に従い、次はひらがなで書く: できる、すべて、または、および、ただし、など、ため、とき、こと。
11. 複合語の名詞は送り仮名を省く（読取り、書込み、組合せ、割当て、切替え、呼出し、受取り、置換え、貼付け、打切り、付替え、取止め）。
    動詞は送り仮名を付ける（読み取る、組み合わせる、置き換える）。

### 2.4 記号と書式

12. 和文と英数字の間にスペースを入れない。英数字どうしの間は半角スペースを入れる（Core 1.0、64 KiB）。
13. 句読点は「、」「。」、括弧は全角の「（）」を使う。英数字は半角で書き、全角英数字を使わない。
14. 対比・組合せの併記は「／」（status／exit）、語の並列は「、」または「・」、pathの区切りは半角「/」とする。
15. 文体はだ・である調、見出しは体言止めとする。
16. 識別子、値、path、optionはバッククォートで囲む。

### 2.5 変更の手順

17. 見出しを変えたら、そこを指すlinkも同時に直す。作業中はlink検査の範囲を`docs/04.提案資料/`と`fixtures/`へ広げて確認する。
18. hashを固定している文書（Diagnostic台帳、target vector）は、文言だけの変更でも再review記録（「文言統一のみ、規範の変更なし」）を残してhashを更新する。
19. Pythonのdocstring、コメント、例外メッセージは日本語で書く。識別子、validator reportの値（`"Passed"`、`"Not run"`、`pending`の文言）は英語のままにする。
    testがメッセージを照合している箇所は同時に直す。
20. JSON Schemaの`title`と`description`は日本語で書く。
21. file名は本書に従って改名する。directory名は変えない。プログラムが参照するfile名（`*.py`、`*.json`、`manifest.json`、
    `expected/`配下、fixture ID）と`README.md`は識別子として変えない。改名したら参照を同時に直す。
22. 語の抽出、本書での確認、置換の順に進める。一括の自動置換はせず、出現箇所ごとに識別子か一般語かを確認する。
    置換のたびに回帰試験、統合検証2回の一致、link検査を通し、commitは領域ごとに分ける。
