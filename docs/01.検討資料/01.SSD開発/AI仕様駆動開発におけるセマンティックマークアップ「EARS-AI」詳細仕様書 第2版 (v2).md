### EARS-AI 詳細仕様書 第2版 (v2)：アクター統合型セマンティックマークアップ規格

#### 1\. 規格の概要と策定背景

AI仕様書駆動開発（Spec-Driven Development: SDD）の要諦は、仕様書を単なる静的なドキュメントから「AIエージェントに対する実行可能な決定論的契約」へと昇華させることにある。従来の「Vibe Coding（場当たり的な対話による実装）」では、AIエージェントの自律性が制御不能なハルシネーションを引き起こし、誰がどのコードに対して責任を負うのかという「責任の所在（Accountability）」が極めて曖昧であった。この課題を解消するため、EARS-AI v2ではアクター定義をセマンティックマークアップの核として統合し、マルチエージェント環境における職務分掌を厳密に定義する。

##### 第1版からの主要な変更点

* **アクター・タクソノミー（階層的分類体系）の導入** : 人間、AI、システムコンポーネントの責務境界を階層化。  
* **アクターバインディング構文の拡張** : ACTOR タグを全要件のプレフィックスとして強制し、実行主体の明示的紐付けを実現。  
* **職務分掌（Separation of Duties: SoD）の原則統合** : 実装主体と検証主体の物理的・論理的分離をマークアップレベルで規定。  
* **品質ゲート（Quality Gates）との同期** : 各開発フェーズの承認主体をアクターIDに基づき定義。アクターの責任範囲を明確に定義することは、次章で詳述するセマンティック構文を形式化し、システムの安定性を担保するための不可欠な前提条件となる。

#### 2\. アクター・タクソノミー（階層的分類体系）

システムに関与する「主体」を体系化することは、エージェントの自律性を決定論的な境界内に制御し、ガバナンスを維持するための戦略的要件である。本規格では以下の3レイヤーで構成されるアクター構造を定義する。

##### アクター・レイヤー定義と権限マトリックス

レイヤー,アクターID,役割と責務,権限スコープ  
人間（HITL）,ACTOR: HumanPO,要求仕様の最終承認、ビジネス価値の定義,全仕様の承認、予算・戦略的判断  
,ACTOR: HumanDev,技術設計の承認、最終デバッグ、マージ判断,アーキテクチャ承認、コードマージ権限  
AIエージェント,ACTOR: SpecAgent,REQからのTECH展開、ドキュメント構造維持,詳細設計生成、仕様整合性チェック  
,ACTOR: ImplAgent,TDDに基づく実装、コード生成、テスト実行,実装コード生成、ローカルテスト実行  
,ACTOR: AuditAgent,仕様と実装の突合、品質ゲートの独立検証,検証レポート生成、不適合の指摘  
,ACTOR: SyncAgent,実装知見の蒸留、Memory Bankへの同期,Living Spec更新、コンテキスト蒸留  
システム,ACTOR: TargetSystem,実行環境、外部API、ハードウェア接点,状態遷移の実行、I/O処理  
,ACTOR: Component:{N},内部モジュール、DB、特定のロジック,内部関数実行、データ永続化

##### インタラクションが開発の安定性に与える影響（"So What?" 分析）

アクターをレイヤー化し、各々の境界線を明示することで、AIエージェントは「自己が現在どの権限を行使しているか」をセマンティックレベルで認識する。これにより、ACTOR: ImplAgent が独断で ACTOR: HumanPO の定義したビジネスルールを改変するといった「未承認の自律」を抑制し、開発プロセスの予測可能性を決定論的に向上させる。アクターの責任定義を前提として、これらの主体がマークアップ内でどのように記述されるか、構文の詳細へ移行する。

#### 3\. EARS-AI v2 拡張構文とアクターバインディング

仕様書がAIにとっての「実行可能な契約」として機能するためには、曖昧さを排除した意味論的タグ付けが不可欠である。第2版では、全アクションの先頭に ACTOR: {Name} を配置し、行動と主体を強固にバインドする。

##### 拡張構文の記述形式

基本形式： ACTOR: {Name} CONDITION\_TAG {Context} ACTION\_TAG {Behavior}

##### ドキュメントタイプ別記述例

###### *1\. 要求仕様書（REQ）：人間とシステムの境界定義*

\---  
id: REQ-001  
type: requirement  
status: approved  
\---  
\#\# \[REQ-001\] 計算要求処理  
\- \[ACTOR: HumanPO\] \[ALWAYS\] 算出結果は有効数字3桁で表示することを要求する。  
\- \[ACTOR: TargetSystem\] \[WHEN\] 入力値がJIS規格外である場合 \[THEN\] 警告コード \`W-01\` を表示する。

###### *2\. 詳細仕様書（TECH）：コンポーネント間の相互作用*

\---  
id: TECH-001  
type: technical\_spec  
relations: { parent: REQ-001 }  
\---  
\#\# \[TECH-001\] 計算エンジン詳細  
\- \[ACTOR: Component:CalcEngine\] \[WHILE\] 周囲温度 \> 40℃ である間 \[THEN\] 補正係数を 0.82 に固定する。  
\- \[ACTOR: Component:DB\] \[IF\_ERROR\] 検索対象不在 \[THEN\] \`LineNotFoundError\` をスローする。

###### *3\. スキル定義（SKILL.md）：エージェント自身の権限・制約*

\---  
name: sdd-sync-skill  
description: 実装コードの差分を解析し詳細仕様書（TECH）へ自動反映するスキル  
\---  
\# Skill: SDD-Sync-Skill  
\- \[ACTOR: SyncAgent\] \[WHEN\] 実装コードに仕様未記載の例外処理を検知した場合 \[GENERATE\] {TECH\_SPEC} へのリバース同期案を作成する。  
\- \[ACTOR: SyncAgent\] \[CONSTRAINT\] \[ACTOR: HumanPO\] が定義したビジネスルールを改変してはならない。

##### ハルシネーション抑制の評価

アクターをタグで明示することにより、これらはLLMの注意機構において「高重量のアテンション・アンカー（High-Weight Attention Anchors）」として機能する。AIは文脈を解析する際、自己の制約とシステムの振る舞いを混同（Role Confusion）することなく処理を継続できる。これは、プロンプトインジェクションや役割のドリフトを防ぐための強力なセマンティック制約となる。複数のアクターが介在するプロセスにおいて、不可欠となるセキュリティと品質の制約設計へ移行する。

#### 4\. 職務分掌（Separation of Duties）の原則と検証ロジック

自己承認バイアスを完全に排除し、システムの完全性を担保するためには、職務分掌（SoD）の原則をマルチエージェント・オーケストレーションに組み込むことが戦略的に不可欠である。

##### SoD 制約設計の論理モデル

同一のAIセッションまたはインスタンスが、実装ロールと検証ロールを同時に担うことを禁止する。  
\[Constraint: Anti-Self-Approval\]  
IF (Actor(Activity: Implement) \== Actor(Activity: Audit)) THEN  
    RESULT \= REJECTED  
    LOG \= "Violation: Implementation and Audit actors must be distinct."  
END IF

##### Gate 4（仕様・実装突合検証）における実装方針

Gate 4では、ACTOR: AuditAgent が以下のプロセスを独立して実行し、実装の妥当性を評価する。

1. **アイデンティティ整合性検証** : ACTOR: ImplAgent の成果物メタデータを確認し、SoD違反がないかを検証。  
2. **独立構造比較** : 実装されたコードの抽象構文木（AST）と、{TECH\_SPEC} のデータ契約（ENTITY, INTERFACE）を、実装時のコンテキストを排除した状態でゼロベース比較。  
3. **証跡の永続化** : 検証結果に ACTOR: AuditAgent の一意な識別子と成果物ハッシュを付与し、トレーサビリティを確保。

##### ガバナンスへの寄与（"So What?" 分析）

このSoD設計は、組織のガバナンスとコード品質の信頼性を決定論的に向上させる。AIによる「自己肯定のループ」を論理的に遮断することで、外部監査やセキュリティ基準への適合性を客観的に証明するトレーサビリティ・チェーンが形成される。この論理的制約が、実際の開発サイクルの中でどのように機能するかを具体化する。

#### 5\. SDDライフサイクルおよび品質ゲートとの統合

アクターはライフサイクルの各フェーズにおいて役割をリレーし、定義された品質ゲートを通過させる。各ゲートでは「実行主体（Executor）」と「承認主体（Accountable Approver）」を明確に分離する。

##### フェーズ別アクター・ワークフロー

* **Gate 1: 要求承認 (REQ Gate)**  
* 実行主体: ACTOR: SpecAgent (対話による仕様策定)  
* 承認主体: ACTOR: HumanPO (ビジネス価値の最終合意)  
* **Gate 2: 詳細設計承認 (TECH Gate)**  
* 実行主体: ACTOR: SpecAgent (技術設計への展開)  
* 承認主体: ACTOR: HumanDev (技術的妥当性の審査)  
* **Gate 3: 実装・TDD完了 (Impl Gate)**  
* 実行主体: ACTOR: ImplAgent (テスト先行実装)  
* 承認主体: ACTOR: TargetSystem (テスト通過による自動検証)  
* **Gate 4: 仕様突合検証 (Verify Gate)**  
* 実行主体: ACTOR: AuditAgent (独立レビュー)  
* 監視主体: ACTOR: HumanDev (PR承認を通じたガバナンス維持)  
* **Gate 5: 仕様同期・生体維持 (Sync Gate)**  
* 実行主体: ACTOR: SyncAgent (Memory Bankへの知見同期)  
* 承認主体: ACTOR: HumanPO (Living Specの最終確定)

##### 統合ルール（GSD/cc-sdd/DDD）

* **DDDオプション** : ACTOR: SpecAgent は DOMAIN.md の AGGREGATE\_ROOT を参照し、トランザクション境界を越える直接操作を禁止する制約を自動付与する。  
* **GSD-antigravity統合** : ACTOR: SyncAgent は、タスク完了時に /gsd-commit-memory をトリガーし、アクター別行動ログを永続化する。次に、本仕様を実運用に乗せるための具体的な実装ガイドラインへ移行する。

#### 6\. 実装ガイドラインと自動化方針

本仕様書を単なるドキュメントに留めず、自動化ツールやCLIスキルとして機能させるための技術的要件を定義する。

##### 自動化ロジックとDAG検証

Python（python-frontmatter, networkx）を用いた検証スクリプトは、以下の有向非巡回グラフ（DAG）バリデーションを静的に実行しなければならない。

1. **循環参照の検知** : relations フィールドを走査し、仕様間の依存関係におけるループ（A-\>B-\>A）を排除する。  
2. **ダングリング・ポインタの検知** : parent に指定されたIDが .specs/ 内に実在しない「リンク切れ」を特定する。  
3. **状態整合性チェック** : 上位仕様（REQ）が draft であるにもかかわらず、下位仕様（TECH）が approved または implementing であるといった、ゲート状態の矛盾を拒絶する。

##### Memory Bankとコンテキスト劣化（Context Rot）の防止

ACTOR: SyncAgent は、単なるファイルの更新ではなく、.antigravity/memory/ ディレクトリにおける「コンテキスト蒸留（Context Distillation）」を担当する。

* **蒸留プロセス** : 実装過程の膨大なデバッグログやチャット履歴を直接残さず、重要な意思決定、不採用案（Rejected Ideas）、および技術的知見のみを凝縮した「Knowledge Notes」へと変換し、Memory Bankに永続化する。  
* **防止策** : これにより、LLMのコンテキストウィンドウが不要なログで埋まる「コンテキスト劣化（Context Rot）」を防ぎ、長期プロジェクトにおけるAIの判断精度を維持する。

##### Living Spec 維持の動作条件

ACTOR: SyncAgent は以下の拡張EARS記法に基づき REVERSE\_SYNC を実行する。

* WHEN コード差分が ACTOR: TargetSystem のテストを100%通過している  
* CONSTRAINT 変更が ACTOR: HumanPO の定義した BUSINESS\_RULE を破壊しない  
* ACTION ACTOR: SyncAgent は実装詳細を {TECH\_SPEC} へリバースコミットする

#### 総括

EARS-AI v2は、AIと人間が共創するプロセスにおいて、誰が何を成すべきかを定義する「信頼のプロトコル」である。アクターを仕様に統合し、職務分掌を機械的に検証することで、AIの自律性は制御可能な「専門能力」へと昇華される。本規格の採用は、SDDを真にスケーラブルで堅牢な開発パラダイムへと進化させるための確固たる基盤となる。
