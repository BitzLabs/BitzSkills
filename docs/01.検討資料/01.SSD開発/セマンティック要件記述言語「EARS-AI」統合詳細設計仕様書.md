### EARS-AI 統合技術詳細設計仕様書（決定版） \#\#\#\# 1\. 開発哲学とシステムコンセプト \#\#\#\#\# 1.1 戦略的重要性：セマンティック契約としての仕様書 AIエージェントによる自律型システム開発（AI-SDD）において、仕様書はもはや「人間が読むための文書」ではなく、AIの推論を規定する「セマンティック契約（意味論的契約）」である。EARS-AI（Easy Approach to Requirements Syntax for AI）は、人間とAIが「同一の真実（Single Source of Truth: SSoT）」を共有するためのインターフェースであり、自然言語の柔軟性とコードの厳密性を架橋する設計的意義を持つ。 \#\#\#\#\# 1.2 ハルシネーション抑制の論理的基盤：アテンション制御 従来の自然言語仕様書がAIの誤解（ハルシネーション）を招く主因は、文脈の多義性とそれに伴う「アテンションの分散」にある。EARS-AIは、特定のセマンティックタグを「セマンティック・アンカー」として機能させ、LLMの推論プロセスにおけるアテンションを特定の制約に固定する。 \* **トークン効率と推論精度:** 構造化されたタグは、LLMのKVキャッシュ内での検索空間を圧縮し、設計上の「境界（Boundary）」を明確にする。これにより、不要な潜在空間へのドリフトを抑制し、決定論的（Deterministic）な挙動を保証する。 \* **過剰設計の抑制:** 記述をEARS構文に限定することで、AIが仕様に含まれない「勝手な機能」を付け加える余地を物理的に排除する。 \#\#\#\#\# 1.3 機械可読かつ人間可読な契約の技術的評価 Markdown構造に埋め込まれたEARSタグは、AIにとってはプロンプトのコンテキスト密度を高める高周波信号として機能し、人間にとっては直感的な論理記述として機能する。この二面性が、仕様と実装の乖離（Spec Drift）をリアルタイムで検知・修正可能にする基盤となる。本仕様書は、次章の構文定義を通じて、AIエージェントを「仕様のコンパイラ」へと昇華させる。 \#\#\#\# 2\. EARS-AI 基本構文および拡張セマンティックタグ \#\#\#\#\# 2.1 決定論的挙動を保証する基本6タグ EARS-AIの構文は、システムの非決定性を排除し、いかなるAIモデルであっても同一の論理パスを選択させるための強力なガードレールである。従来の5タグに、状態依存を明示する WHILE を加えた6タグを基本セットとして定義する。 | タグ名 | 定義・用途 | AIに対する具体的な制約内容（セマンティック・アンカー） | | \------ | \------ | \------ | | WHEN | 条件・トリガー | イベント発生時のみ実行。特定の条件下でのみアテンションを起動させる。 | | THEN | 期待される振る舞い | WHEN または WHILE 後の唯一の確定的な応答。出力空間を単一化。 | | WHILE | 状態依存・前提 | 特定の状態が継続している間のみ有効。コンテキスト・ウィンドウ内の前提条件を固定。 | | CONSTRAINT | 設計・非機能制約 | 命名規則、セキュリティ等の「壁」。AIの生成自由度を物理的に制限。 | | \[IF\_ERROR\] | 異常系・例外処理 | 例外時のリカバリーパス。Try-Catchやフォールバックの実装を強制。 | | ALWAYS | 普遍的ビジネスルール | 常に適用されるドメイン不変条件。すべての推論に対する共通背景。 | \#\#\#\#\# 2.2 EARS-AI 拡張構文（AI/状態遷移） 複雑な動的挙動や、AIエージェント自身の推論プロセスを制御するために以下の拡張タグを使用する。 \* **状態遷移定義:** STATE, EVENT, \[NEXT\_STATE\] \* これらはステートマシンの定義として機能する。AIに対し、enum 定義や状態遷移ロジック（C\#のStatelessライブラリ等）への正確なマッピングを強制する。 \* **AI推論ブリッジ:** GENERATE \* 決定論的なロジックでは記述不可能な「AIによる生成」を明示する。入力モデルと期待される出力モデルの型を定義し、推論の境界を定める。 **「So What?」：なぜ構文を厳密化するのか** AIは自由度が高いほどハルシネーションを起こしやすくなる。構文を6タグに制限することで、AIは「どの論理パターンを適用すべきか」の選択において迷うことがなくなり、トークン消費の効率化と出力の再現性が最大化される。 \#\#\#\# 3\. アクター・タクソノミーと職務分掌（v2/第2版） \#\#\#\#\# 3.1 アクター分離によるコンテキスト混線の防止 AIエージェントの多重活用において、アクターの役割を3つのレイヤーで体系化することは、情報の特権分離（Separation of Duties: SoD）を実現し、セキュリティ上の脆弱性やコンテキストの「濁り」を排除するために不可欠である。 \`\`\`mermaid graph TD subgraph Human\_Layer Human Layer \- HITL H\_PO\["ACTOR: HumanPO

DDD（ドメイン駆動設計）統合マークアップ \#\#\#\#\# 4.1 DDDの「オプトイン」戦略 DDD統合は、複雑な業務ドメインを扱うための「オプトイン（選択式）」スキルプラグインとして定義される。これは、単純なCRUDプロジェクトに不要な階層構造を強制し、トークンを浪費（Over-engineering）することを防ぐためである。 \#\#\#\#\# 4.2 ドメインセマンティックタグ \* \*\*\[ENTITY\]\*\* : 一意識別子を持つオブジェクト。AIに対し、ライフサイクル全体での同一性担保を強制。 \* \*\*\[VALUE\_OBJECT\]\*\* : 不変性（Immutability）の強制。等価性比較ロジックと、変更時に新インスタンスを返すロジックの実装。 \* \*\*\[AGGREGATE\_ROOT\]\*\* : トランザクション境界。集約ルートを介さない内部オブジェクトへの直接操作を厳禁。 \* \*\*\[DOMAIN\_EVENT\]\*\* : コンテキスト間通信のトリガー定義。 \*\*「So What?」：なぜDDDをマークアップするのか\*\*
