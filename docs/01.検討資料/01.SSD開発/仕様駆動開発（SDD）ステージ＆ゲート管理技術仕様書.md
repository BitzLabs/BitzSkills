### 仕様駆動開発（SDD）におけるステージ・ゲートおよび実行フロー詳細仕様書 \#\#\#\# 1\. はじめに：SDDアーキテクチャの戦略的意義 仕様駆動開発（Spec-Driven Development: SDD）は、ソフトウェア開発における情報エントロピーの増大、すなわち「コンテキスト崩壊」を数理的・構造的に抑制するためのパラダイムである。従来の「対話やノリ（Vibe）」に依存した開発は、実装の進行とともに仕様の断片化を招き、AIエージェントの推論においてハルシネーションを誘発させる。 SDDは、仕様書を「単なる読み物」から「機械可読かつコンパイラブルなコードの設計図」へと昇華させ、人間とAI、あるいはAIエージェント間の厳格なインターフェース（契約）として定義する。本仕様書では、以下の5つのライフサイクルを通じて、不確実性を排除し、AIの自律性を制御するガードレールを構築する。 1\. **Intent（対話型仕様策定）** : 開発者の意図を構造化された仕様ファイルへ変換。 2\. **Planning（計画とタスク分解）** : 仕様を実行可能な有向非巡回グラフ（DAG）へと分解。 3\. **TDD（自律実装・テスト駆動）** : 仕様からテストを先行生成し、検証ループを自動化。 4\. **Verification（仕様突合検証）** : 実装成果物と仕様の論理的整合性を数学的に監査。 5\. **Synchronization（リビングスペック同期）** : 実装知見を仕様へリバース反映し、SSOT（Single Source of Truth）を維持。 \#\#\#\# 2\. 二層仕様書体系とフロントマター規格 SDDでは、認知負荷の最適化とAIへのコンテキスト注入効率を最大化するため、仕様書を「要求仕様（REQ）」と「詳細仕様（TECH）」の二層に分離し、メタデータによるトレーサビリティを強制する。 \#\#\#\#\# 2.1 仕様書群はrelationsフィールドを介して有向非巡回グラフ（DAG）を構成する。sdd-cliは、networkxライブラリを用いてこのグラフを解析し、以下のバリデーションを自動実行する。 \* **循環参照の検知** : 仕様間の依存関係にループがないかを静的解析。 \* **整合性スコア** : 上位REQがapprovedでない状態で下位TECHをimplementingに遷移させる操作をブロック。 \* **リンク切れバリデーション** : idベースの参照先ファイルの実在性を担保。 \#\#\#\# 3\. SDDライフサイクル：5つの品質管理ゲート 開発プロセスにおける各チェックポイントを「ゲート」として定義し、AIプラグインによる自動品質監査を強制する。 \#\#\#\#\# Gate 1: 要求仕様承認（Requirement Validation） 拡張EARS-AI記法（ACTOR, CAPABILITY, \[BUSINESS\_RULE\]）を用いた妥当性検証を行う。 \* **曖昧さの抽出** : 「〜しやすい」「適切に」といった非定量的表現をAIが検知し、修正を促す。 \* **Testabilityスコア** : 各受入基準（AC）がGiven/When/Then形式に変換可能かを評価し、スコアが閾値（80点）未満の場合は承認を却下する。 \#\#\#\#\# Gate 2: 詳細設計承認（Technical Design Review） 設計の整合性とDDD原則の遵守を確認する。 \* **制約注入** : \[AGGREGATE\_ROOT\]や\[VALUE\_OBJECT\]タグにより、トランザクション境界や不変性の制約がTECHに記述されているかを検証。 \* **インターフェース整合性** : 上位REQの能力（Capability）が、TECHのメソッドシグネチャに過不足なくマッピングされているかを確認。 \#\#\#\#\# Gate 3: 実装・TDD完了（Implementation Guard） エージェントによるRed-Green-Refactorサイクルの完了を担保する。 \* **原則監査** : 生成コードがKISS、DRY、YAGNIを遵守しているか、AIレビューアがKlocwork的視点で監査。 \* **カバレッジ同期** : 指定されたカバレッジ目標（例: 90%以上）に達するまでimplementingステータスを維持。 \#\#\#\#\# Gate 4: 仕様突合検証（Two-Tier Compliance） 実装と仕様の完全一致を二段階で検証する。 \* **Phase A（構造検証）** : コードの抽象構文木（AST）を解析し、TECHで定義された型・シグネチャと実装の100%一致を監査。 \* **Phase B（振る舞い検証）** : パスしたテストケースが、REQの受入基準（AC）を論理的に網羅しているかをAIがマッピング。 \#\#\#\#\# Gate 5: リビングスペック同期（Living Spec Audit） 「生きた仕様」としての最終同期を実行。 \* **Self-Healing** : 実装中に発見されたエッジケースを詳細仕様（TECH）へリバース反映し、差分（Spec Drift）を解消。 \* **ステータス遷移** : すべての検証項目クリアを確認後、ステータスをverifiedへ遷移させ、物理ファイルを更新。 \#\#\#\# 4\. 実行フローの定義とステージ・マッピング 開発コンテキストに応じた最適なプロセスをマッピングする。 \#\#\#\#\# 4.1 フロー別プロセス・マトリクス | フロー | G1: 要求 | G2: 詳細 | G3: 実装 | G4: 突合 | G5: SDD開発エンジン（CLI/Skills）の制御挙動 Pythonベースの sdd-cli およびAIスキルプラグインによる自律制御アルゴラインを定義する。 \#\#\#\#\# 5.1 コマンド実行パイプライン \* sdd verify: Gate 4の実行。 1\. git diff origin/main を取得し、変更シンボルを抽出。 2\. frontmatter.implements から関連するTECHファイルを特定。 3\. LLMにより「仕様の期待構造」と「実装AST」をクロスチェック。 \* sdd sync: Gate 5の実行。 1\. コード内の例外処理や分岐を抽出。 2\. TECHの \[IF\_ERROR\] セクションとの差分を特定。 3\. 差分が妥当な詳細化である場合、TECHファイルを自動上書き（リバース反映）。 \#\#\#\#\# 5.2 自律修復（Self-Healing）アルゴリズム Gate 4/5での失敗検知時、以下の自律復旧パイプラインを走らせる。 1\. **Drift分析** : 仕様と実装の乖離点をベクトル化し、不一致の根本原因を特定。 2\. **仕分け** : 変更が「要件（REQ）違反」か「設計（TECH）の洗練」かを判定。 3\. **アクション** : \* 設計の洗練であれば、仕様書側のMarkdownを自動更新。 \* 要件違反であれば、実装コードへの修正パッチを生成し、再度G3へ差し戻す。 \#\#\#\# 6\. 高度な仕様記述：拡張EARS-AIとドメイン制約 AIの解釈エラーを最小化するためのセマンティック・タグセット。 \#\#\#\#\# 6.1 EARS-AI 構文カタログ \* ALWAYS: 普遍的なビジネスルール。 \* WHEN {Event}: トリガー条件。 \* THEN {System} は : 決定論的応答。 \* \[IF\_ERROR\] {Condition}: 異常系ハンドリングの強制。 \* GENERATE {Input} \-\> {Output}: AIエージェントへの推論委譲。 \#\#\#\#\# 6.2 状態遷移モデルとMermaid自動変換 以下の記述形式を sdd-cli がパースし、コードおよび図解を自動生成する。 markdown \*\*\[INIT\_STATE\]\*\* \`Idle\` \* \*\*\[STATE: Idle\]\*\* \- \*\*\[WHEN\]\*\* \`\[EVENT: Start\]\` 発生 \- \*\*\[THEN\]\*\* \*\*\[NEXT\_STATE: Running\]\*\* へ遷移  \#\#\#\#\# 6.3 DDDオプションの統合 \[AGGREGATE\_ROOT\] や \[VALUE\_OBJECT\] タグが指定された場合、AIスキルは以下の制約をコードに注入する。 \* **不変性の強制** : 値オブジェクトに対するSetterの禁止、全フィールドのreadonly化。 \* **カプセル化の強制** : 集約ルート以外からのドメインエンティティへの直接アクセスの禁止。 \#\#\#\# 7\. 運用プラクティス：Gitワークフローと境界制御 \#\#\#\#\# 7.1 アトミック・コミット・プロトコル 仕様変更とコード実装、そして tasks.md（進捗）の更新を同一コミットに含める「三位一体コミット」を必須とする。 \#\#\#\#\# 7.2 Boundaryアノテーションによる並列制御 マルチエージェント実行時の衝突回避のため、tasks.md に以下の形式で作業境界を定義する。 \* Boundary: src/Domain/Order.cs, src/API/OrderController.cs Agent Managerは、このシンボル（ファイルパスおよびクラス名）が重なるタスクを並列実行キューから除外し、直列化する。 \#\#\#\#\# 7.3 回避記憶の管理（RESEARCH.md） 過去の棄却されたアプローチやトレードオフの記録を RESEARCH.md に集約する。AIはタスク開始時に本ファイルをコンテキストとしてロードし、過去の失敗（先祖返り）を回避する「外部記憶」として利用する。 \#\#\#\# 8\. 結論：持続可能なAI駆動開発の実現 本ドキュメントで定義したステージ・ゲート体系は、AIの生成能力を最大化しつつ、人間のガバナンスを「検証」に集約させるものである。この「検証中心（Validation-Centric）」へのパラダイムシフトにより、開発規模が拡大しても品質が劣化しない、真にスケーラブルなソフトウェアエンジニアリングを実現する。 AIを「単なるコード出力機」としてではなく、「厳格な仕様のコンパイラ」として駆動させ続けることが、次世代の開発品質を決定づける。
