# Step 0Bの適合fixture準備

リポジトリのルートで次を実行する。

```text
uv run fixtures/validate_conformance.py
```

このコマンドは、公開する結果・診断・マニフェストのJSONの例、スキーマの構造、EBNFの参照、診断レジストリの構造、
matrixの一覧、現行の設計契約と承認済みのADRの相対リンクを監査する。Step 0-Pの検証とfixture基盤の自己試験も実行する。
固定した依存はスクリプトに宣言してあり、初回はパッケージのダウンロードが必要である。

この監査は部分的なものであり、終了コードは常に1である。自分が新しいチェックアウトで動いているかを判定できないため、
`pending`に`full Gate A fresh-checkout repeatability`を必ず残す。それ以外の未完了の証拠やエラーがあれば、
レポートに個別に列挙される。未作成のfixtureも同様である。

上限境界の24件は入力を生成するため、実寸の照合は次のコマンドで行う。

```text
uv run fixtures/validate_scale.py
```

Gate Aの判定は次のコマンドで行う。作業ツリーにコミットされていない変更がないことを確かめたうえで、`HEAD`から独立した
クローンを2つ作り、それぞれで上の2つのコマンドを実行する。監査のエラーが0件、未完了の証拠が上記の1項目だけで、
レポートが2つのクローンでバイト列として一致し、規模の検証が両方で成功して所要時間を除いて一致すれば、`gateA: "Allowed"`と
終了コード0を返す。出力には対象のコミット、各レポートのSHA-256、実行環境を含む。

```text
uv run fixtures/certify_gate_a.py
```

各Stepの完了fixtureは`steps.json`に置く。正本は実装計画であり、監査が両者の一致を検査する（ADR-052）。
実装計画の完了条件を変えるときは、`steps.json`も同じコミットで直す。

Gate Aの認定の後にmatrixやfixtureを変更するときは、
[適合fixture仕様 §1.1](../../docs/03.詳細設計/00_共通契約/04_適合fixture仕様.md#11-matrixとfixtureの変更)に従う。
Coreの出力は期待値を直す根拠にならず、期待値の訂正と削除・緩和には人間の管理者の承認を要する。
静的な検査では、fixtureが独立した原因を1つだけ持つことを証明できない。診断の対応は、レビュー済みの診断の網羅表で管理する
（[診断の意味の網羅のレビュー](診断の意味の網羅のレビュー.md)）。監査は網羅表の整合と根拠文書の鮮度を検査し、自然言語の意味は検査しない。

## 開発時の検証とCIの分割

関連するfixtureだけを試す場合は`--fixture ID`を反復して指定する。変更を固めた後に全件を1回実行する。
直前と同じ差分の全件の実行を、状況の確認のためだけに繰り返さない。

```sh
uv run fixtures/run_conformance.py --core plugins/bitz-core --step 5 --suite standard
uv run fixtures/run_conformance.py --core plugins/bitz-core --step 5 --suite scale
uv run fixtures/run_conformance.py --core plugins/bitz-core --step 5 --shards 4 --shard 1 \
  --progress --output <result.json> --timings <timings.json>
```

`standard`は上限境界の、入力を生成するfixture以外、`scale`は`MULTI-020-*`と`MULTI-021-*`である。
両者は互いに重複せず、全件を構成する。分割は選択した集合へ適用し、各分割の中は従来の順序を維持する。
部分的な実行の成功は、全件の認定を意味しない。

`--timings`は、合否のレポートとは別のJSONへ、fixtureごとの`durationMs`と`phasesMs`を保存する。
`environment`はwheelのビルドと仮想環境の準備を含み、最初に必要になったfixtureへ計上する。
総時間はスキーマの検査や後片付けも含むため、記録した工程ごとの時間の合計とは一致しない。
各fixtureが完了するたびに計時のJSONを更新し、`--progress`では完了数、ID、結果、秒数を標準エラー出力へ出す。

CIの分割は、直近の`main`のCIで得た独立2組の中央値を、次元と境界の内側・外側ごとに保持し、LPT法で配分する。
`fixtures/plan_conformance.py`は各分割のfixture数と予測したジョブの時間をJSONで出力する。CIでは同じ予測を
ジョブ名とStep Summaryへ表示する。予測値は配分と所要時間の目安だけに使い、fixtureの選択や合否の条件は変更しない。

CIは[ADR-056](../../docs/02.設計書/10_決定記録/ADR-056_適合試験の分割実行とCIのGate-B集約を確定する.md)に従い、
PRは独立1組、`main`、週次、手動は独立2組の4分割を実行する。各ワーカーは新しいクローンでCoreをビルドする。
`tests/bitz-core/ci_gate_b.py collect`は全分割の証跡を検査し、全件の欠落、重複、改変を拒否する。
2組の結果と構文解析器の出力が一致した場合だけ、Gate Bを`Passed`とする。

```sh
uv run tests/bitz-core/ci_gate_b.py run --step 5 --replica 1 --shard 1 --shards 4 \
  --run-id <run-attempt> --output <artifact-directory>
uv run tests/bitz-core/ci_gate_b.py collect --step 5 --replicas 2 --shards 4 \
  --run-id <run-attempt> --input <all-artifacts-directory> --output <gate-result.json>
```

`run`と`collect`はクリーンなコミットを対象にする。成果物はリポジトリの外、またはGitの対象外のディレクトリへ保存する。
独立2組の認定には、組1と組2それぞれの分割1〜4が必要である。同じCIの実行と試行の組の証跡だけを受け入れるため、
CIの再実行は全ジョブを対象にする。既存の`certify_gate_b.py`によるローカルの認定も利用できる。
