# 複合ワークスペースの他のワークスペースの循環のfixtureのレビュー記録

[適合fixture仕様 §7](../../../docs/03.詳細設計/00_共通契約/04_適合fixture仕様.md#7-最小matrix-複合ワークスペース)の
`MULTI-050-01`〜`MULTI-050-06`を扱う。いずれもレビュー済みの期待値であり、Coreの挙動を観測したものではない
（[ADR-051](../../../docs/02.設計書/10_決定記録/ADR-051_適合fixtureの変更手続きを確定する.md)の追加）。
生成器と監査は`fixtures/conformance/multi_cross_cycle_fixtures.py`である。

## 追加の理由

複合ワークスペースの`context`と`verify`は、循環の診断`CTX-CYCLE-001`を、作業ワークスペース（起点を所有するワークスペース）の文書が宣言した辺に絞っていた。
その結果、次の2つが起きた。実装の確認事項C44に対応する。

- ワークスペースをまたぐ循環（`platform::REQ-030` → `api::REQ-130` → `platform::REQ-030`）では、作業ワークスペースの辺しか報告せず、もう一方の辺を落とした。
  `check <修飾ID>`は両側を返していた。
- 閉包に入った他のメンバーの中だけで閉じる循環（`platform::REQ-040` → `api::REQ-140` ⇄ `api::REQ-141`）は、まったく報告しなかった。
  `context`と`verify`は成功し、`contextDigest`まで出していた。

ユーザーの決定（2026-10-26）で、関係・トレースモデル §6.3の最後の文に、複合ワークスペースの他のワークスペースの文書についても、閉包の文書が宣言する強い関係の循環
（ワークスペースをまたぐ循環を含む）を検査し、`check`の完全検査と同じく、閉包に入ったどのワークスペースの文書が宣言する辺でも報告すると書いた。
参照先の不在などそれ以外の関係は、これまでどおり検査しない。この群は、その範囲を固定する。

`MULTI-038`のレビュー記録は、他のメンバーの文書が循環に参加する入力を固定していなかった（「規範から導けなかった点」の最後の項目の一つ）。この群がそれを固定する。

## 根拠の規範文

- 関係・トレースモデル §6.3の最後の文: 上記。§6: 「型、状態、循環、上限を満たさない場合は、閉包の全体を非成功とする」。§7: 「循環を隠さない」。§4: 禁止された循環に参加するエッジを
  宣言した文書ごとに診断する。
- 診断レジストリの`RELATION-CYCLE`（`CTX-CYCLE-001`）。条件、重大度、結果への効果は変わらない。
- 結果・診断・終了コード §7: 診断はワークスペースID、`path`の辞書順に並べる。
- `context` §3: 強い関係の一部を解決できない（禁止された循環を含む）コンテキスト一式を成功にしない。`verify` §9: 検証対象ごとに目的`verify`のコンテキストを完全解決する。
- コンテキストのハッシュ値の正規化仕様 §3: `strongRelations`は、強い関係のうち参照先を解決できたものだけを持つ。参照先を解決できない関係
  （検査しない他のワークスペースの文書の参照切れなど）は含めない。宣言そのものは`frontmatter.relations`に含まれる（ユーザーの決定、2026-10-28。次節）。

## 入力と起動

基本のリポジトリは、ルート`platform`（`.`）、メンバー`web`（`apps/web`）と`api`（`services/api`）で、すべてコミットし、`--format json`で起動する。
文書はすべて`approved`のREQ（`MUST`1件、規範文`AC-01`）である。`platform`だけがテスト対応のコマンド`frontend`を持つ。fixtureごとに必要な文書だけを置く。

| fixture | 文書と関係 | 実行ディレクトリと引数 | 結果 |
|---|---|---|---|
| `MULTI-050-01` | `platform::REQ-030` → `api::REQ-130` → `platform::REQ-030` | `.`、`context REQ-030 --purpose interpret` | `failed`／1。`CTX-CYCLE-001`が2件（`api`、`platform`） |
| `MULTI-050-02` | `platform::REQ-040`（テスト対応あり）→ `api::REQ-140` ⇄ `api::REQ-141` | `.`、`context REQ-040 --purpose interpret` | `failed`／1。`CTX-CYCLE-001`が2件（`api`） |
| `MULTI-050-03` | `MULTI-050-02`と同じ | `.`、`verify REQ-040` | `failed`／1。検証対象の`diagnostics`に`CTX-CYCLE-001`が2件 |
| `MULTI-050-04` | `platform::REQ-050` → `api::REQ-150` → `api::REQ-999`（不在） | `.`、`context REQ-050 --purpose interpret --detail compact` | `passed`／0（対照） |
| `MULTI-050-05` | `platform::REQ-060` → `api::REQ-160` → `web::REQ-260` → `platform::REQ-060` | `.`、`context REQ-060 --purpose interpret` | `failed`／1。`CTX-CYCLE-001`が3件（`api`、`platform`、`web`） |
| `MULTI-050-06` | `platform::REQ-001`（関係なし）。`api::REQ-170` ⇄ `api::REQ-171`（閉包の外） | `.`、`context REQ-001 --purpose interpret --detail compact` | `passed`／0（対照） |

## 期待値の導き方（Coreの出力を根拠にしない）

1. **診断**。`reference_diagnostics`が、`multi_closure_alias_fixtures`の閉包と循環の参照計算で、閉包に入ったすべての文書の辺のうち循環に参加するものを導く。
   報告の範囲は、閉包に入ったどのワークスペースの文書でもよい。参照切れと型違反は、作業ワークスペースの文書だけを検査する。リテラルの期待値がこの結果と一致することを要求する。
   診断の並びは、ワークスペースID、`path`の辞書順（結果・診断・終了コード §7）である。
2. **失敗の形**。`context`は`MULTI-038-02`と同じ形（`contextDigest: null`、`documents`は空、`resolution.complete: false`、`unresolvedStrongRelations`は0）、
   `verify`は`MULTI-038-03`と同じ形（検証対象の`contextDigest: null`、`statements`と`bindingRefs`は空、`commands`は空）である。
3. **対照`MULTI-050-04`**。他のメンバーの文書の参照切れは検査しないので、診断は0件で成功する。`documents`は起点（役割`root`）と`api::REQ-150`（役割`requirement`）、
   横断するエッジは`platform::REQ-050 → api::REQ-150`の1件。`unresolvedStrongRelations`は0とし、解決は完了とする（検査しない関係を未解決として数えない）。
4. **ハッシュ値**。`MULTI-050-04`と`06`は、独立に書いた2系統の参照計算の正規JSONのバイト列の一致を要求する。A（`reviewed_digest_input`）は文書ごとの材料をリテラルで書き、
   B（`multi_closure_alias_fixtures.derived_material`）は入力の木構造から導く。`MULTI-050-04`の`api::REQ-150`は、`frontmatter.relations.requires`が`api::REQ-999`を持ち、
   `strongRelations`は空である（次節）。
5. **欠陥を検出できる入力であること**（陰性対照の構成）。`defective_diagnostics`が修正前の範囲（作業ワークスペースの辺だけ）の報告を再現し、`check_conditions`が、失敗する4件で
   修正前の報告が期待する報告の真部分集合であること（`MULTI-050-02`と`03`では空）を要求する。`MULTI-050-04`では、全文書を検査する参照計算なら参照切れが1件導かれること、
   `MULTI-050-06`では、循環が閉包の外の他のメンバーの2文書にあることを要求する。

## ハッシュ値の材料の強い関係（ユーザーの決定）

`MULTI-050-04`を最初に作ったとき、`api::REQ-150`の`strongRelations`に、解決できない`api::REQ-999`を含める参照計算A・Bと、含めないCoreが食い違った
（`contextDigest`だけが異なり、材料の違いは`strongRelations`の1か所だけだった）。正規化仕様 §3は「強い関係」とだけ書き、解決できない宣言を含めるかを定めていなかった
（単一ワークスペースでは、参照切れは`failed`でハッシュ値を作らないので表に出なかった）。ユーザーが2026-10-28に「解決できたものだけ」と決め、正規化仕様 §3の表に明記した。

この決定に合わせて、次の参照計算Bを直した（解決できない関係を`strongRelations`から外す）。

- `digest_crosscheck.build`（単一ワークスペース）、`multi_crosscheck.build`（複合ワークスペース）、`multi_closure_alias_fixtures.derived_material`、
  `multi_binding_missing_fixtures`の材料の導出。共有の判定は`digest_crosscheck.resolves`（文書ID、または文書IDと規範文IDの参照先が実在するか）である。

既存のfixtureの期待値は変わらない。`validate_conformance.py`の既存の検査（参照計算AとBのバイト列の一致を含む）は、この変更の後もすべて通る。

## 規範から導けなかった点・固定の程度

- 失敗した`context`の`resolution.workspaces`と`crossWorkspaceEdges`。閉包の他のワークスペースに到達しても、`documents`が空の失敗では起点ワークスペースだけを持ち、横断するエッジは空とする。
  規範が明示していない点で、`MULTI-038-02`、`MULTI-027-01`の既存の形に合わせた。
- 禁止された循環を`unresolvedStrongRelations`に数えるか。規範が定めていないので、`MULTI-038`の解釈（数えない）に合わせて0とした。
- 他のメンバーの文書の参照切れがあるときの`resolution.complete`と`unresolvedStrongRelations`（`MULTI-050-04`）。「検査しない」から、解決は完了、未解決は0とした。
- 循環1件の診断の件数。`MULTI-038`の解釈（循環に参加する辺を宣言した文書ごとに1件）に合わせた。3つのワークスペースの循環（`MULTI-050-05`）は3件になる。

この群の範囲外とするもの。

- `verify --all-workspaces`。単体試験（`tests/bitz-core/test_multi_closure_alias_evidence.py`の`CrossWorkspaceCycleTests`）で固定している。
- 目的`implement`と`verify`の`context`。診断は目的に依存せず、`interpret`で固定した（単体試験が3つの目的を確かめる）。
- `check`の出力。変更していない。
