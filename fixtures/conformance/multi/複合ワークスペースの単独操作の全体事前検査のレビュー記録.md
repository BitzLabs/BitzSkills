# 複合ワークスペースの単独操作の全体事前検査のfixtureのレビュー記録

[適合fixture仕様 §7](../../../docs/03.詳細設計/00_共通契約/04_適合fixture仕様.md#7-最小matrix-複合ワークスペース)の
`MULTI-036-01`〜`MULTI-036-13`を扱う。いずれもレビュー済みの期待値であり、Coreの挙動を観測したものではない
（[ADR-051](../../../docs/02.設計書/10_決定記録/ADR-051_適合fixtureの変更手続きを確定する.md)の追加）。
生成器と監査は`fixtures/conformance/multi_single_precheck_fixtures.py`である。

## 追加の理由（実装の確認事項C27）

Coreは、複合ワークスペースの単独の`context`、`check`、`verify`、`doctor`でも全体事前検査を行っていたが、非成功のときは診断を返さずに
単一ワークスペースの経路へ進んでいた。このため、カタログに登録していない`.spec/`の中で実行すると、その設定を単独のワークスペースとして使って成功した。
複合ワークスペース仕様 §3の手順4は、この場合を診断`SPEC-MULTI-UNREGISTERED-001`（`blocked`）と定めており、実装が規範に反していた。
[ADR-063](../../../docs/02.設計書/10_決定記録/ADR-063_複合ワークスペースの単独操作の全体事前検査を確定する.md)がこの停止の規則と、停止しない境界を確定したので、
13件を追加する。既存の379件の入力と期待値は変えない。

## 根拠の規範文

- 複合ワークスペース仕様 §3の手順4・5と直後の段落: 複合ワークスペース内で選択した別の`.spec/`がカタログにないときは、`SPEC-MULTI-UNREGISTERED-001`（`blocked`）。
  `--workspace`または修飾IDで置き換える場合も照合する。カタログにない`--workspace`のIDでも、§7の全体事前検査が非成功なら結果を返す（終了コード4にしない）。
  ルートの設定を読めないときは複合と判定せず、メジャーバージョンが非対応なら`multiWorkspace`の宣言があれば複合とする。Gitを利用できないときは、
  最も近い設定が`multiWorkspace`を宣言していれば`SPEC-MULTI-GIT-001`、宣言していなければ単一ワークスペース。
- 複合ワークスペース仕様 §7: 単独の操作は、作業ワークスペースの処理の前に全体事前検査を行い、非成功なら処理を始めずに単独結果を返す。
  単独の`context`、`check`、`verify`はGitが認識する設定の列挙と比較を行わず、§3の手順4の照合を行う。単独の`doctor`は`HEAD`と現在のスナップショットで比較する。
- 複合ワークスペース仕様 §8・§10: 全体事前検査の対象（カタログ、メンバーの設定の対応、Gitの境界、メジャーバージョン）と、`SPEC-MULTI-GIT-001`。
- 結果・診断・終了コード §2: 停止した単独結果の`workspace`（選択した設定が登録されて有効なIDを持つときだけ`id`を持つ。`path`は候補のリポジトリのルートからの相対パス）、
  `revision`（Gitを利用できない、またはGitの境界を確定できない状態の停止と、コミットのないリポジトリで`null`）、`context`の停止結果が複合固有のフィールドを持たないこと、処理を始める前に停止した結果の件数は0・配列は空。
  `check`の`scope: changed`は`revision`を`null`にせず、Git不在の縮退は`scope: full`。
- `doctor` §3: 単独の`doctor`の全体事前検査が非成功のときは、ワークスペース固有の検査を行わず、`--all-workspaces`の停止結果と同じ最上位の検査項目を同じ順と状態で置く。
- 診断レジストリ: `MULTI-MEMBER`は`failed`、`MULTI-GIT`と`MULTI-UNREGISTERED`は`blocked`。
- ADR-063の決定1〜7（ユーザーの決定を含む）。診断の文言は、`Coreの出力文言のレビュー記録.md`の承認済みの文字列と、ADR-063の決定7の
  「選択した設定ファイルがカタログに登録されていません」である。

## 期待値の導き方（Coreの出力を根拠にしない）

1. **停止の有無**。`reference_decision`が、入力の木構造とGitの状態から導く。ルートの設定を読める（禁止されたYAMLを含まない）か、`multiWorkspace`を宣言するか、
   Gitがあるか、最も近い設定の位置と登録、メンバーの設定の実在、メジャーバージョン、`doctor`ではGitが認識する設定の集合を使う。
2. **`workspace`**。選択した設定は、現在のディレクトリから親へ探索した最も近い設定である（§3の手順2）。カタログに登録されていて有効なIDを持てば`{id, path}`、
   未登録なら`{id: null, path: <候補のパス>}`（`tools/x`）。`--workspace`があっても、選択した設定が基準である（`MULTI-036-02`、`-09`）。単一ワークスペースは`path: .`で、
   設定を読めなければ`id: null`（`MULTI-036-08`は`SINGLE-091`と同じ）。Git不在で複合を宣言するルートの設定が最も近い設定のときは、ルートワークスペースなので`path: .`。
3. **`revision`と`scope`**。Gitを利用できない、またはGitの境界を確定できない状態の停止と、コミットのないリポジトリで`revision: null`（結果・診断・終了コード §2）。この群では`SPEC-MULTI-GIT-001`の停止がこれにあたる（Gitのあるfixtureは必ずコミットを持つ）。そのとき`check`はGit不在の縮退で`scope: full`、`checkedDocumentCount`と`checkedStatementCount`は0。
   Gitがあって引数なしの`check`は`scope: changed`で、`selection`の3件は0（処理を始める前の停止）。`revision`は`{base, commit, dirty}`（`context`と`verify`は`{commit, dirty}`）。
4. **診断**。未登録は`SPEC-MULTI-UNREGISTERED-001`で、単独の`check`・`context`・`verify`と、選択した設定の照合は「選択した設定ファイルがカタログに登録されていません」、
   `doctor`のGitが認識する設定の比較は「Gitが認識する設定ファイルがカタログに登録されていません」。`source`は`{file, workspaceId: null, path: <リポジトリのルートからの相対パス>}`。
   単独の`check`は列挙しないので、追跡している未登録の設定に対しても「Gitが認識する…」の診断は出ない。`SPEC-MULTI-MEMBER-001`の`summary`は承認済みの「メンバーの.spec/bitz.yamlがありません」、
   `source`は既存のカタログの診断（`MULTI-007-01`の`SPEC-MULTI-PATH-001`）と同じく、ルートの`.spec/bitz.yaml`のキー`multiWorkspace.members`。
5. **`doctor`**。ワークスペース固有の検査項目を置かず、`--all-workspaces`の停止結果と同じ最上位の検査項目: Gitの境界を確定できなければ`core`（`passed`）、`git`（`blocked`）の2件
   （`MULTI-019`と同じ）、それ以外は`core`、`git`（ともに`passed`）、`catalog`（`blocked`）の3件（`MULTI-007-01`、`MULTI-033`と同じ順）。`revision`、`multiWorkspace`、`workspaces`を持たない。
6. **`context`**。`SINGLE-150`と同じ形の失敗結果（`contextDigest: null`、`resolution`は`{complete: false, documentCount: 0, unresolvedStrongRelations: 0}`、`documents`・制約台帳・カバレッジは空）で、
   複合固有の`resolution.workspaces`と`crossWorkspaceEdges`を持たない。
7. **停止しない境界**。`MULTI-036-06`（最も近い設定が複合を宣言しないので、ルートが複合を宣言していてもGitなしでは単一ワークスペース。件数は`web`の文書だけ）、
   `-08`（ルートの設定を読めないので、複合の診断を返さない）、`-12`（単独の`verify`は列挙しない。結果は`MULTI-034-05`と同じで、参照計算とハッシュ値の2系統の照合もその群のものを使う）。

## 規範から導けなかった点・固定の程度

起案の時点で規範が定めていなかった次の点は、その後、規範の文で確定した。期待値は確定した文と一致する。

- `context`の停止結果の`roots`: 引数をNFCへ正規化し、重複を除き、コードポイント順に並べた値とし、修飾しない（結果・診断・終了コード §2、
  複合ワークスペース仕様 §4、ADR-063の決定6）。`MULTI-036-02`と`-07`は引数を修飾IDで渡しており、どちらの読みでも同じ値になる。
- `--workspace`があるときの停止結果の`workspace`: `--workspace`で置き換える前の、§3で選択した最も近い設定を基準にする（結果・診断・終了コード §2、
  ADR-063の決定2・3・6。ユーザーの決定D10からの帰結）。`MULTI-036-02`、`-09`が固定する。
- Git不在で複合を宣言するルートの設定が最も近い設定のときの`workspace.path`: 選択した設定のワークスペースの候補の相対パスであり、
  候補がリポジトリのルートの候補そのものなので`.`（結果・診断・終了コード §2）。
- 単独の`doctor`で、Gitが認識する設定の比較と選択した設定の照合が同じ設定に重なる場合: Gitが認識する設定の比較の診断1件だけを返す
  （複合ワークスペース仕様 §7、ADR-063の決定2）。この群は重なりを作らず、単体試験（`tests/bitz-core/test_multi_single_precheck_stop.py`）が押さえる。参照計算はこの重なりを拒否する。

次は、規範が文字列や配置を1つに定めていないため、既存の扱いに合わせて固定した。

- 引数なしの`check`の停止結果の`scope`と`selection`。`MULTI-036-01`は`scope: changed`、`selection`の3件は0とした（§2の「処理を始める前に停止した場合、派生する件数は0」）。
  `-08`と`-09`は`--full`を付けて、この点に依存しない。
- `SPEC-MULTI-MEMBER-001`（メンバーの設定の不在）の`source`。既存のカタログの診断と同じ、ルートの`.spec/bitz.yaml`のキー`multiWorkspace.members`とした。
- `MULTI-036-08`の「読めない設定」。承認済みの`summary`が確定しているのは禁止されたYAMLのアンカー（`SINGLE-091`）だけなので、構文エラーそのものではなくこれを使った。

この群の範囲外とするもの。

- テキスト形式の出力。この群はJSONだけを固定する。
- 単独の`verify`のリソースの上限の優先（実装の確認事項C40、ADR-063の決定8）。
