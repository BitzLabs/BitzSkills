# リソースの上限の境界のfixtureのレビュー記録

[適合fixture仕様 §7](../../../docs/03.詳細設計/00_共通契約/04_適合fixture仕様.md#7-最小matrix-複合ワークスペース)の
`MULTI-020-01..16`と`MULTI-021-01..08`を扱う。いずれもレビュー済みの期待値であり、Coreの挙動を観測したものではない。

## 入力はコミットせず、データセットのマニフェストから生成する

8つの次元の`limit - 1`、`limit`、`limit + 1`を、実際の木構造としてコミットすると、リポジトリは1 GiBを超える。
[ADR-048](../../../docs/02.設計書/10_決定記録/ADR-048_適合fixtureの生成入力とGit構造operationを確定する.md)に従い、
各fixtureは`repo/`の代わりにデータセットのマニフェストを持ち、`setup.generate.treeDigest`で、生成した木構造を固定する。
期待結果と副作用の期待値も生成物なので、`expect.resultDigest`と、副作用の`stateDigest`で固定する。
レビューの対象は、生成器（`multi_generator.py`）とデータセットのマニフェストである。

生成器は、狙った次元だけを指定した値にし、ほかを通常の規模に保つ。データセットのマニフェストは8つの次元の
実測値をすべて持ち、監査は「狙った以外の次元が上限を超えていないこと」をその実測値から確かめる。
計数（`count`）は、生成計画を読まず、生成したバイト列だけから数え直す。

## 入力側の上限とぶつけない

生成物は、[安全な入出力・互換性 §4](../../../docs/03.詳細設計/00_共通契約/02_安全な入出力・互換性.md)の
入力の上限（設定64 KiB、仕様文書1 MiB、1文書の配列の項目と規範文1,000件）を越えない形に分けている。

- コマンドはワークスペースあたり800件までに分け、10,000件の定義には13のワークスペースを使う。
- 100万件の関係のエッジは、1,000件ずつ別の文書へ置き、参照先は重複しない実在の文書（参照先専用の
  補充文書を最大1,000件用意し、各エッジの文書はそこから重複なく参照する）にする
  （2026-09-25訂正。下の節を参照）。
- `verify`のテスト割当ての境界は、1ワークスペース分のテスト対応を`BINDINGS_PER_DOCUMENT`（300）件ごとの複数の文書へ分け、
  1文書のフロントマターを32 KiB以下に保つ（2026-09-25訂正。下の節を参照）。
- 100万件のトレースの項目は、TASKの`changes`へ1,000件ずつ置く。`changes`は字句の許可集合なので、パスの実在を要求しない。
- 256 MiBの入力は、1 MiB未満の補充文書を並べ、最後の1件でちょうどの値に合わせる。

規範文は、TECHの`Contract`の節へ置く。[文書種別・本文テンプレート §3](../../../docs/03.詳細設計/02_SPECモデル/03_文書種別・本文template.md)が
ほかの節の規範文の行を、診断`SPEC-STYLE-PLACEMENT-001`とするためである。

## 越える側は早期に停止する

`MULTI-021-*`は、診断`SPEC-MULTI-LIMIT-001`（`blocked`）と終了コード2を返し、`workspaces: []`で、メンバーの処理もコマンドの実行も
始めない。`evidence`は`dimension`、`limit`、`observedAtLeast`を持つ。`observedAtLeast`は越えたことがわかる
最小の値（`limit + 1`）とし、正確な総数を求めない。

`MULTI-021-08`だけは、`verifyBindingCount`がコマンド定義の部分集合であるため、`commandDefinitionCount`も
同時に超える。複合ワークスペース仕様 §10へ「複数のdimensionが同時に超過する場合は、verify実行計画のdimensionを
優先して報告する」を加え、データセットのマニフェストの`companionDimensions`へ、同時に超える次元を明示した。
監査は、宣言していない次元の超過を拒否する。

## 検証は2段階に分ける

既定の監査（`uv run fixtures/validate_conformance.py`）は、同じデータセットのマニフェストを一定の比率で縮小した生成計画で、
生成器の決定論と次元の計数を照合する。上限も同じ比率で縮めるので、越える／越えないの関係は保たれる。
実寸の生成、木構造のハッシュ値、期待結果のハッシュ値、副作用の状態のハッシュ値の照合は`uv run fixtures/validate_scale.py`が行い、
Gate Aの認定にはその記録を必要とする。

## 訂正（2026-09-25）：関係のエッジの配列内の参照先の重複

根拠の規範文：[文書・フロントマター・状態仕様 §11](../../../docs/03.詳細設計/02_SPECモデル/02_文書・Frontmatter・状態仕様.md#11-yaml制約)
「scalar配列の重複は、YAML解釈後の値と型の完全一致で判定し…重複配列はfieldの値域不正として
`SPEC-FM-SCHEMA-001`を返す」。

食い違い：`multi_generator.render_edge_document`は、1つのエッジの文書の`relations.requires`の配列へ、
**同じ参照先のID**（`TECH-000001`）を`edges`件並べていた。これは規範文の配列の重複の規則に反し、
Coreが実際にこの文書を検査すれば、配列の項目の値域不正として診断`SPEC-FM-SCHEMA-001`を返し、
`MULTI-020-09`・`MULTI-020-10`（境界内の`passed`を期待）が成立しない。`MULTI-021-05`
（`relationEdgeCount`の超過。境界を超過した場合は、入力を検査する前に`SPEC-MULTI-LIMIT-001`で早期に停止するため
実害はないが、同じ生成器を使うため、入力の木構造の形は同じ問題を持っていた）も同様である。

訂正内容：`multi_generator.py`を、エッジの文書1件につき、重複しない参照先を並べるよう直した。
`relationEdgeCount`の1つの生成計画につき、参照先専用の補充文書（`render_filler_document`と同形で、
`relations`を持たない）を、`min(ITEMS_PER_DOCUMENT, 最大のchunk size)`件だけ生成し、各エッジの文書は
そこから重複なく`targets[:edges]`を参照する。参照先の文書自身は`requires`を持たないため、
エッジの文書どうしや参照先の文書を経由した循環（`requires`と`refines`をあわせた、禁止された循環。
[関係・トレースモデル §4](../../../docs/03.詳細設計/02_SPECモデル/04_関係・トレースモデル.md#4-型制約)）
は生じない。影響を受けた`MULTI-020-09`・`MULTI-020-10`・`MULTI-021-05`のデータセットのマニフェスト、
木構造のハッシュ値、期待結果のハッシュ値、副作用の状態のハッシュ値を、生成器の実行から作り直した
（`specFileCount`が、参照先の文書の分だけ増える。ほかの次元の値と、境界の超過の判定は変えていない）。

## 訂正（2026-09-25）：`verifyBindingCount`の境界でのフロントマターの32 KiBの超過

根拠の規範文：[安全な入出力・互換性 §4](../../../docs/03.詳細設計/00_共通契約/02_安全な入出力・互換性.md#4-リソースの上限)
のフロントマターの32 KiBの上限（[文書・フロントマター・状態仕様 §11](../../../docs/03.詳細設計/02_SPECモデル/02_文書・Frontmatter・状態仕様.md#11-yaml制約)）。

食い違い：`verifyBindingCount`の境界（`MULTI-020-15`・`MULTI-020-16`・`MULTI-021-08`、値9,999〜10,001）は、
1ワークスペース分のテスト対応（最大約770件）を、1つのTECHの文書のフロントマターへ置いており、実測で最大64,758バイト
（32 KiB=32,768バイトの約2倍）に達していた。Coreが実際にこの文書を検査すれば、フロントマターの超過として、
診断`SPEC-INPUT-LIMIT-001`（継続単位`skip-document`。診断レジストリの条件`INPUT-LIMIT-FRONTMATTER`）を返し、
「境界内はすべてのテスト割当てを実行して`passed`」という期待が成立しない。

訂正内容：`multi_generator.py`に`BINDINGS_PER_DOCUMENT = 300`（実測で389件が32 KiB以内に収まる上限。
安全側に300とした）を導入し、1ワークスペース分のテスト対応を、この件数ごとの複数のTECHの文書へ分けて生成するよう
直した（`emit`のワークスペースのループ）。`verifyBindingCount`以外の次元は、1ワークスペースあたりのテスト割当ての件数が小さいため
（既定1件）、分割は起こらず、生成物は変わらない。参照計算の側（`multi_limit_fixtures.binding_documents`・
`passed_binding_result`、`validate_scale.py`の`binding_digests`、`fake_core.py`の`_binding_digests`）も、
1つのワークスペースが複数のテスト割当ての文書を持てるよう直した。影響を受けた3件のデータセットのマニフェスト、木構造のハッシュ値、
期待結果のハッシュ値、副作用の状態のハッシュ値を、生成器の実行から作り直した（テスト割当ての数とほかの次元の値は保った）。

## 訂正（2026-09-25）：メンバー数の境界での`maxMembers`の省略

根拠の規範文：[複合ワークスペース仕様 §2](../../../docs/03.詳細設計/02_SPECモデル/05_複合workspace仕様.md#2-配置とカタログ)
「`multiWorkspace.maxMembers`の既定は20…`members`が実効上限を超えれば`blocked`とする」。

食い違い：`MULTI-020-01`（メンバー数99）・`MULTI-020-02`（メンバー数100）は、ルートワークスペースの設定へ`maxMembers`を
明示せず、既定値20が効く状態で、「境界内は`passed`」を期待していた。既定20のままCoreが実際に検査すれば、
メンバー数99と100はどちらも既定の上限20を超えて`blocked`になり、期待と矛盾する。この2件と、その対の
`MULTI-021-01`（メンバー数101、超過）は、Coreの絶対上限100そのものの境界を検査する意図である。

訂正内容：`multi_generator.render_config`を、`dimension == "memberCount"`の生成計画では、
ルートワークスペースの設定へ`multiWorkspace.maxMembers: 100`（`LIMITS["memberCount"]`）を明示するよう直した。
`MULTI-021-01`の期待（`evidence.limit: 100`で`blocked`）は、複合ワークスペース仕様 §10の、上限の診断の
`evidence.limit`が「適用した上限」を表すこと、かつ明示した`maxMembers`がCoreの絶対上限100と同値であることから、
そのままでよいと確認した（値の変更なし。入力の配置だけ訂正）。影響を受けた
3件のデータセットのマニフェスト、木構造のハッシュ値、期待結果のハッシュ値、副作用の状態のハッシュ値を、生成器の実行から作り直した。

## 限界

- Coreは実行していない。実際に上限で遮断するか、境界内を通すかはGate Bで判定する。
- 期待結果は生成物であり、ハッシュ値で固定する。人が読むのは、生成器とデータセットのマニフェストである。
- 1つのfixtureは、1つの次元だけを越える。すべての次元を同時に最大にした入力は扱わない。
- 基準環境でのピークRSSが1 GiB以下という受入条件は、Coreの実行を伴うためGate Bで測定する。
