# 複合ワークスペースの除外と入れ子のfixtureのレビュー記録

[適合fixture仕様 §7](../../../docs/03.詳細設計/00_共通契約/04_適合fixture仕様.md#7-最小matrix-複合ワークスペース)の
`MULTI-037-01`〜`MULTI-037-23`を扱う。いずれもレビュー済みの期待値であり、Coreの挙動を観測したものではない
（[ADR-051](../../../docs/02.設計書/10_決定記録/ADR-051_適合fixtureの変更手続きを確定する.md)の追加）。
生成器と監査は`fixtures/conformance/multi_exclude_fixtures.py`である。

## 追加の理由

[ADR-064](../../../docs/02.設計書/10_決定記録/ADR-064_複合ワークスペースの除外と入れ子の複合ワークスペースを確定する.md)は、検証用のデータ（適合fixtureなど）を
Gitで追跡したまま複合ワークスペースの照合から外せるように、ルートワークスペースの設定の`multiWorkspace.exclude`を定めた。除外した範囲の中では、
探索の開始位置から、入れ子の複合ワークスペース、単一ワークスペース、除外の外の規則のどれかを決める（複合ワークスペース仕様 §2.1）。
この規則はこれまでfixtureに固定されていないので、23件を追加する。既存の392件の入力と期待値は変えない。

## 根拠の規範文

- ADR-064 決定1: `multiWorkspace.exclude`は複合ワークスペースのルート相対のディレクトリを0〜100件。字句はメンバーのパスと同じ規則（絶対パス、`.`、空のパス〈末尾の`/`を含む〉、`..`、globを禁止）。
  実在しなくてよく、字句だけでディレクトリの単位の前方一致で比べる。重複と入れ子、名前が`.spec`のセグメントを含む除外は`SPEC-MULTI-CONFIG-001`（`failed`）。
  メンバーのパスが除外のパスと同じまたはその配下なら`SPEC-MULTI-PATH-001`（`failed`）。メンバーの配下のディレクトリは除外に書ける。
- ADR-064 決定2・複合ワークスペース仕様 §2.1: 除外した範囲は、Gitが認識する設定の比較（§8）、単独操作の選択した設定の照合（§3の手順4）、作業ワークスペースの決定だけで外とみなす。所有境界は変えない。
- ADR-064 決定3・同 §2.1の第3段落: 外側のルートの設定が読めなければ、除外も入れ子も決めず、単一ワークスペースの探索を使う。`exclude`が§2の規則を満たさなければ、除外を決めず、外側の規則で決めて外側の全体事前検査で停止する。
  `exclude`が妥当なら、外側のほかの非成功は、除外した範囲の中で決まった操作を止めない。
- ADR-064 決定4・同 §2.1の第4段落: 除外した範囲の中では、除外のディレクトリ自身を含め、そこから開始位置までの経路の上の設定で決める。`multiWorkspace`を宣言した設定のうち、除外のディレクトリに最も近いものを入れ子のルートとする。
  なければ開始位置に最も近い設定を単一ワークスペースとし、`--all-workspaces`は終了コード4。経路の上に設定がなければ外側の規則。
- ADR-064 決定5・6・同 §2.1の第5段落: 結果の`workspace.path`、`workspaces[].path`、未登録の設定の`source.path`は複合ワークスペースのルート相対。入れ子の複合ワークスペースはGitの列挙と変更集合を入れ子のルートの配下に限り、ルートの外のパスは属さないものとして比較から除く。
- ADR-064 決定7: 外側と入れ子は互いのカタログに含まれず、全体操作は探索の開始位置から決まる複合ワークスペースだけを対象にする。
- ADR-064 決定8: 7件の診断の`summary`（`Coreの出力文言のレビュー記録.md`の2026-10-18の節）。
- 結果・診断・終了コード §2: 停止した単独結果の`workspace`（選択した設定が登録されていないとき`id`は`null`、`path`は候補の複合ワークスペースのルート相対）、`--all-workspaces`の停止結果は`workspaces: []`、
  `check`の`scope: changed`の`selection`、`revision`（Gitがあり、コミットがあれば`null`にしない）。
- 診断レジストリ: `MULTI-CONFIG`と`MULTI-PATH`は`failed`、`MULTI-UNREGISTERED`は`blocked`。`stop-multi-workspace`で停止し、`priority`が最小の行を主診断にする。
- `doctor` §3・§8: 単独の`doctor`の全体事前検査が成功したときは`catalog`を`passed`で置く。複合ワークスペースの診断に`suggestedAction`を付けない。
- `check` §3・§6: `--all-workspaces`は`--full`を含意し、カタログ内のすべての仕様文書を数える。対象0件は`passed`。引数なしの変更集合は、作業ワークスペースが所有する変更されたパスだけを出発点にし、
  どの逆索引にも該当しないコードのパスは件数だけを残す。

## 期待値の導き方（Coreの出力を根拠にしない）

1. **場所の決定**。`reference_scope`が、入力の木構造とGitの状態から導く。ルートの設定を読めるか、`multiWorkspace`を宣言するか、版が対応しているか、`exclude`が§2の規則を満たすか（`exclude_problem`）、
   開始位置が除外のパスにディレクトリの単位の前方一致で含まれるか、除外のディレクトリから開始位置までの経路の上の設定と`multiWorkspace`の宣言（読めない設定は宣言しないものとみなす）を使う。
   入れ子の複合ワークスペースは、同じ規則を入れ子のルートについて再帰的に適用する。
2. **停止の原因**。除外の不正（`SPEC-MULTI-CONFIG-001`／`SPEC-MULTI-PATH-001`）、メンバーの設定の不在、Gitが認識する設定の未登録（`--all-workspaces`と`doctor`だけ。除外した範囲と、入れ子では入れ子のルートの外を除く）、
   選択した設定の未登録の順に、診断レジストリの優先順位で1件ずつ導く。除外した範囲の中で単一／入れ子に決まった操作は、外側の原因で止まらない。
3. **結果のパス**。`workspace.path`、`workspaces[].path`、`source.path`は決まった複合ワークスペースのルートからの相対（単一ワークスペースは`.`）。`--all-workspaces`の`workspaces[]`は
   カタログから導き、ルートワークスペースを先頭に、その後をIDのコードポイント順に並べる。
4. **件数**。`checkedDocumentCount`と`checkedStatementCount`は、ワークスペースの`.spec/`の文書と規範文を入力から数える。`selection`は`git status`の変更集合を決まったルートの配下に限って数える
   （`MULTI-037-23`は内側2件、外側3件）。`revision.dirty`はGitの作業ツリーの状態から導く。
5. **ハッシュ値**。`MULTI-037-08`は`SINGLE-055`と同じ入力・結果で、`contextDigest`は`SINGLE-055`のgolden値と、`digest_crosscheck`の木構造からの導出（別の直列化処理）の一致を要求する。
   単一ワークスペースのハッシュ値の材料は位置に依存しない（`workspaces`は`{id, path: .}`）。
6. **陰性対照**。監査は、除外がなければ`MULTI-037-01`の4件の設定が未登録になること、`MULTI-037-18`の除外が信用できれば`cases/single`が除外の中の単一ワークスペースになること、
   `MULTI-037-19`の同じ入力でルートから実行すれば`SPEC-MULTI-MEMBER-001`で止まること、`MULTI-037-22`でリポジトリ全体を列挙すれば入れ子の外の設定も未登録になること、
   `MULTI-037-23`で変更集合をリポジトリのルートで数えれば5件になること、`MULTI-037-06`の最寄りの設定が入れ子のルートではなくメンバー`m`であることを、入力から確かめる。

## 規範から導けなかった点・固定の程度

起案の時点で規範が1つに定めていない、または明示していない次の点は、既存のfixtureの扱いに合わせて固定した。規範を確定すれば、期待値をその文に合わせる。

- 除外の診断（`SPEC-MULTI-CONFIG-001`、`SPEC-MULTI-PATH-001`）の`source.workspaceId`と`multiWorkspace.id`。ルートの設定が読めており、ルートの`workspace.id`が妥当なので、
  ワークスペースの同一性は構成できる（結果・診断・終了コード §2・§5）として`platform`にした（`null`ではない）。`MULTI-007-01`の`SPEC-MULTI-PATH-001`、`MULTI-036-03`の`SPEC-MULTI-MEMBER-001`と同じ。
- 除外の診断の`source.key`。`SPEC-MULTI-CONFIG-001`は`multiWorkspace.exclude`、除外した範囲にあるメンバーの`SPEC-MULTI-PATH-001`は`multiWorkspace.members`（診断レジストリの条件はメンバーのパスの不正であり、
  `MULTI-007-01`と同じキー）にした。
- `MULTI-037-18`: `exclude`が不正なとき、単独の`check`の停止結果は`SPEC-MULTI-CONFIG-001`の1件だけとし、選択した`cases/single`が未登録である診断（`SPEC-MULTI-UNREGISTERED-001`）を加えない。
  `stop-multi-workspace`は全体事前検査を確定した診断で止まるため、不正な`exclude`を持つカタログに対して選択した設定の登録を判定しないと読んだ。`workspace`は`{id: null, path: cases/single}`。
- `MULTI-037-21`: 外側のルートの設定が読めないとき、最も近い設定として使う`cases/nested`は`multiWorkspace`を宣言しているが、単一ワークスペースとして使い、診断を返さない。
  単一ワークスペースの設定が`multiWorkspace`を持つ場合の扱いは、規範が明示していない（`SPEC-MULTI-CONFIG-001`の「配置」の条件にも書かれていない）。ルートの設定の診断も返さない（選択した設定ではない）。
- 検査の順（複数の不正が重なるとき）。この群のfixtureは1つの原因だけを持つので、重なる場合の主診断は固定しない（診断レジストリの`priority`が同じ`MULTI-CONFIG`の中の順は規範が定めていない）。
  参照計算は、型、件数、字句、`.spec`、重複、入れ子、メンバーの重なりの順に検査する。
- `--all-workspaces`の終了コード4（`MULTI-037-04`）の標準エラー出力。`cli-output.json`で、標準出力が空、標準エラー出力が`bitz: check: `で始まる理由1行であることだけを固定し、理由の文言は固定しない（既存の終了コード4のfixtureと同じ）。
- 基準版と`HEAD`のスナップショットの除外（ADR-064 決定2、複合ワークスペース仕様 §2.1）。この群のfixtureは、基準版と現在版で同じ除外を使い、スナップショットごとの除外の違いは固定しない。

この群の範囲外とするもの。

- テキスト形式の出力。この群はJSONだけを固定する。
- 除外のパスのUnicode NFC正規化と、大文字と小文字の区別（複合ワークスペース仕様 §2.1）。この群では固定しない。
- 除外した範囲の中の`--workspace`（単一ワークスペースの規則）。
