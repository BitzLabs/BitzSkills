# verifyの規範文の並びのfixtureのレビュー記録

[適合fixture仕様 §7](../../../docs/03.詳細設計/00_共通契約/04_適合fixture仕様.md#7-最小matrix-複合ワークスペース)の
`MULTI-044-01`〜`MULTI-044-05`を扱う。いずれもレビュー済みの期待値であり、Coreの挙動を観測したものではない
（[ADR-051](../../../docs/02.設計書/10_決定記録/ADR-051_適合fixtureの変更手続きを確定する.md)の追加）。
生成器と監査は`fixtures/conformance/multi_verify_order_fixtures.py`である。単一ワークスペースの入力（`01`、`02`、`04`、`05`）も、
`MULTI-042-03`と同じく、同じ原因の群として`multi/`に置いた。

## 追加の理由

### 実装の確認事項C52（`01`〜`04`）

`verify`は`targetResults[].statements`を、対象規範文の内部の並び（起点の規範文を文書順・行番号で並べ、その後に具体化文書の規範文を足した順）の
まま出力していた。`verify` §8の`targetResults[]`の表は、`statements`を「検証対象が検証する規範文。重複なし辞書順」と定める。
そのため、次の入力で辞書順にならなかった。既存のfixtureは、たまたますべて辞書順の入力だった。

- 文書の中で、規範文を番号の順に書かないとき（`AC-10`を`AC-02`より前に書く）: `01`。
- 起点より辞書順で前の文書が起点を具体化するとき（`TECH-003`が`TECH-005`を具体化する）: `02`。
- 複合ワークスペースで、他のメンバーの文書が起点を具体化するとき（`api::TECH-010:C-01`が`platform::REQ-001:AC-01`の前）: `03`。
  辞書順の比較の対象は、出力する修飾IDである（複合ワークスペース仕様 §4・§6。`MULTI-042`と同じ読み）。
- `04`は対照で、最初から辞書順の入力は修正の前後で同じ順に出力される。

### 実装の確認事項C60（`05`と`01`のハッシュ値）

`01`を作る途中で、`contextDigest`の期待値がCoreの出力と食い違った（`statements`の並びはC52の修正後のCoreと一致していた）。
期待値は、ハッシュ値の材料の`documents[].statements`を`id`のコードポイント辞書順に置いた値である。Coreは、材料の規範文を文書に書いた順
（`AC-10`、`AC-02`）のまま置いていた。`bitz.digest.canonical_bytes`を差し替えてCoreが実際にハッシュ値を求めるバイト列を取り出して確かめた。
参照計算の材料の規範文を文書に書いた順に並べ替えると、Coreの値と一致する。ほかの材料は一致していた。

この食い違いは`verify`の`statements`の並び（C52）とは別の欠陥で、`context`の`contextDigest`にも同じ影響が出る
（規範文を番号の順に書かない文書がある閉包）。修正前（`5312f867`）とC52だけを直した時点（`df26cb1e`）のCoreで同じ値が出ていた。
期待値をCoreの出力に合わせず、食い違いを報告して止めた。ユーザーは2026-10-25に、Coreを直すことを決め、この欠陥を実装の確認事項C60として
C52と同じPRで直す。修正は、ハッシュ値の材料の`documents[].statements`を`id`で並べる（`context.py`と`verify.py`）。
`MULTI-044-05`が`context`の側を固定する。`verify`の側は`01`の`contextDigest`が固定する。

## 根拠の規範文

- `verify` §8の`targetResults[]`の表: `statements`は「検証対象が検証する規範文。重複なし辞書順」。`target`、`statements`、`covers`は、複合ワークスペースでは修飾IDで返す。
- 複合ワークスペース仕様 §4・§6: 各文書ID、規範文IDは修飾IDで出力する。
- 関係・トレースモデル §6.4: 検証対象が文書なら、その文書が所有するすべての規範文と、それらの具体化文書の規範文が対象規範文である。
- `verify` §3・§4: 全`MUST`に1件以上のテスト対応を要求し、通過した検証対象のテスト割当てを`<ワークスペースID>::<コマンド名>`ごとにまとめて1回実行する。
  テストのパスは所有ワークスペース相対で重複排除して辞書順に並べる。
- コンテキストのハッシュ値の正規化仕様 §3の表: 材料の`statements`は「`id`のコードポイント辞書順」。`tests[].covers`は修飾IDにして辞書順。
  提示の順は材料に含めない。目的`interpret`と`implement`は、コマンドとタイムアウトを材料に含めない。

## 入力と起動

すべてコミットして`--format json`で起動する。テスト対応のコマンドは`/bin/true`である。

| fixture | 入力 | 起動 |
|---|---|---|
| `MULTI-044-01` | 単一ワークスペース（`workspace.id`は`root`）。REQ-001（`MUST`2件）が規範文を`AC-10`、`AC-02`の順に書く。テスト対応は1件で、`covers`は`[REQ-001:AC-02, REQ-001:AC-10]` | `.`、`verify REQ-001` |
| `MULTI-044-02` | 単一ワークスペース。TECH-005（`C-01`）を、TECH-003（`C-01`）が`TECH-005:C-01`を`refines`する。どちらもテスト対応を持つ | `.`、`verify TECH-005` |
| `MULTI-044-03` | ルート`platform`（`.`）、メンバー`api`（`services/api`）。`platform::REQ-001`（`AC-01`）にテスト対応はない。`api::TECH-010`（`C-01`）が`platform::REQ-001:AC-01`を`refines`し、テスト対応が`api::TECH-010:C-01`と`platform::REQ-001:AC-01`を`covers`する | `.`、`verify REQ-001` |
| `MULTI-044-04` | 単一ワークスペース。REQ-001（`AC-01`、`AC-02`の順）を、TECH-010（`C-01`）が`REQ-001:AC-01`を`refines`する。どれもテスト対応を持つ（対照） | `.`、`verify REQ-001` |
| `MULTI-044-05` | `MULTI-044-01`と同じ入力 | `.`、`context REQ-001 --purpose interpret --detail compact` |

`03`は、ルートの文書にテスト対応を持たせず、テスト割当てを`api::backend`の1件にした。単一の操作が複数のワークスペースのテスト割当てを実行するときの
`commands`の並びの解釈（ワークスペースの処理順が単独の操作で何を指すか）を、この群では固定しないためである。

## 期待値の導き方（Coreの出力を根拠にしない）

1. **規範文の並び**。`reference_statements`が、`multi_closure_alias_fixtures.interpret_closure`で入力の木構造から閉包を導き、
   `multi_context_order_fixtures.reference_targets`で対象規範文を内部の並びで導く。期待値は、その出力する規範文IDの重複なし辞書順（`sorted(set(...))`）で、
   リテラルの`EXPECTED_STATEMENTS`と一致することを要求する。
   - `01`: `["REQ-001:AC-02", "REQ-001:AC-10"]`。 `02`: `["TECH-003:C-01", "TECH-005:C-01"]`。
   - `03`: `["api::TECH-010:C-01", "platform::REQ-001:AC-01"]`（修飾IDの辞書順で`api::`が`platform::`より前）。
   - `04`: `["REQ-001:AC-01", "REQ-001:AC-02", "TECH-010:C-01"]`。
2. **テスト割当て**。`reference_bindings`が、閉包の文書の`tests`のうち、対象規範文を`covers`するものを、所有ワークスペースとコマンド名ごとにまとめる。
   全`MUST`にテスト対応があることを要求し、テストのパスと`covers`を辞書順に置く。`bindingRefs`は`<ワークスペースID>::<コマンド名>`の辞書順、
   `commands[]`の`argv`は`{tests}`を展開した値。リテラルの`EXPECTED_BINDINGS`と一致することを要求する。
3. **ハッシュ値**。独立に書いた2系統の参照計算の正規JSONのバイト列の一致を要求する。A（`reviewed_digest_input`）は文書ごとの材料を表からリテラルで書き
   （規範文は`id`の辞書順）、B（`digest_crosscheck.build`、複合ワークスペースは`multi_crosscheck.build`）は入力の木構造から導く。
   `01`〜`04`は目的`verify`、`05`は目的`interpret`（コマンドとタイムアウトを材料に含めない）である。
4. **欠陥を検出できる入力であること**（陰性対照の構成）。`check_conditions`が、修正前の並び（`DEFECTIVE_STATEMENTS`）が入力からの参照計算の内部の並びと
   一致し、辞書順と異なること（`01`、`02`、`03`、`05`）、対照の`04`では同じであることを要求する。`01`と`05`では、起点の文書に番号の大きい規範文を先に書いていること、
   `02`では起点より辞書順で前の文書が起点を具体化していること、`03`では他のメンバーの文書が起点を具体化していることを入力から確かめる。

`05`では`627be71d…`（期待値）に対してCoreの`fdd2de92…`である。

## 規範から導けなかった点・固定の程度

- `commands[].covers`の並び。`verify` §8は、`covers`の並びを明記しない。この群は、正規化仕様 §3.1.1の`tests[].covers`（修飾IDの辞書順）と同じ辞書順で固定した。
  Coreの出力と一致した。
- 単独の操作が複数のワークスペースのテスト割当てを実行するときの`commands[]`の並び。`03`は`api::backend`の1件にして、固定しない。
- `01`・`05`の`covers`の宣言の並び。フロントマターの`covers`は辞書順（`AC-02`、`AC-10`）で書き、宣言の並びが結果の`commands[].covers`の並びを決めないようにした。
- 具体化文書が文書IDだけで`refines`するときの対象規範文（`MULTI-042`のレビュー記録の同名の項目と同じ）。この群は、規範文IDで`refines`する入力だけを置く。

この群の範囲外とするもの。

- テキスト形式の出力。この群はJSONだけを固定する。
- 複数の検証対象を並べた`verify`と、`verify --all-workspaces`。この群は、単一の検証対象の`statements`だけを固定する。
- 目的`implement`の`context`のハッシュ値。材料の規範文の並びは目的に依存しない。
