# 関係・パス・カバレッジのfixtureのレビュー記録

2026-09-11。SINGLE-020、021、023、024、025、026の6件の入力と完全な期待値を固定する。
Coreの関係の解決、パスの検査、カバレッジの判定を実装・実行した結果ではない。

## 単一原因

各fixtureは、正常なREQ-001、必須のH2、妥当なAC-01を保持する。明示した`HEAD`と現在版は同じ木構造で、
`check --full --base HEAD --format json`を計画する。Gitの変更・承認済み要求の保護を別の原因にしない。

| ID | 原因の固定 | 診断 / 結果の状態 / 終了コード | 完全検査文書 / 規範文 |
|---|---|---|---|
| SINGLE-020 | `requires`が存在しないREQ-999を参照 | SPEC-RELATION-MISSING-001 / `failed` / 1 | 1 / 1 |
| SINGLE-021 | REQが、存在する`approved`のTECH-001を`refines`する | CTX-RELATION-TYPE-001 / `failed` / 1 | 2 / 1 |
| SINGLE-023 | 旧`refs`が存在するTECH-001を参照 | SPEC-RELATION-LEGACY-001 / `failed` / 1 | 2 / 1 |
| SINGLE-024 | `approved`のREQの`implements`が、未作成の`src/missing.py`を宣言 | SPEC-PATH-INVALID-001 / `failed` / 1 | 1 / 1 |
| SINGLE-025 | 024の`status`だけ`draft`へ変更 | SPEC-PATH-INVALID-001 / `passed_with_warnings` / 0 | 1 / 1 |
| SINGLE-026 | 実在するテストの`covers`が、存在しない同一REQのAC-99を参照 | SPEC-TEST-COVERAGE-001 / `failed` / 1 | 1 / 1 |
| SINGLE-133（2026-09-26追加） | `requires`が存在しないREQ-997とREQ-998を2件参照 | SPEC-RELATION-MISSING-001 ×2 / `failed` / 1 | 1 / 1 |

020は、参照先のIDの語彙・型自体は正しく、横断の意図を推測しない。
021では参照先を実在させ、REQ→TECHの`refines`の型違反だけを返す。TECHは規範文なしを許され、
正常なH1・フロントマター・コンテキストを持つため、規範文の不足という別の原因を作らない。
023も同じTECHを置き、旧`refs`だけを拒否する。未知のフィールドの警告、参照切れ、`requires`への自動変換を追加しない。

024と025は、`status`以外のバイト列を同じにし、存在しない通常の相対ファイルパスを宣言する。
絶対パス、親ディレクトリへの遡り、ディレクトリ、シンボリックリンク、ワークスペースの外の所有境界は混ぜない。
026はテストのファイルを通常のファイルとして配置し、既定のコマンド、`cwd`、実行ファイルも用意する。
コマンドはLinux環境の`/bin/true`、`cwd`は`.`。準備の検証では実行可能性だけを確認して起動しない。
テストのファイルは誤って実行すれば失敗する内容だが、`check`でテストを実行しないことの実証はGate Bで行う。
`MUST`の規範文が未テストであることに対する`verify`の`blocked`を`check`へ追加せず、`covers`の不在の診断だけを返す。

## 完全な期待JSONと副作用

レジストリの関係3件は`skip-edge`であり、文書自体の独立した検査を続ける。
パスと`covers`は`continue`なので、いずれも正常な本文の完全検査の件数を保持する。
`check`の文書の検査の完了を、非成功の関係を含むコンテキストの閉包が完全であることの証明には使わない。

- 各原因の主診断は1件だけとする。重大度`error`、結果への効果`failed`を基本とし、025だけ重大度`warning`、結果への効果`passed_with_warnings`。
- 発生元の種類は`file`、`workspaceId`は`root`、`path`は`.spec/requirements/REQ-001.md`。
  `source.key`は順に`relations.requires`、`relations.refines`、`refs`、`implements`、`implements`、`tests[0].covers`。
  配列の原因の要素が各1件であるため、関係と`implements`はフィールドのキーで固定する。
- `line`、`column`、`specRefs`、`suggestedAction`は付加しない。`summary`は`expected`のJSONの固定の日本語の文字列とする。
  `evidence`は2026-09-26の訂正（下記参照）で、関係のエッジを単位とする診断（020、021、026）だけへ追加した。
- Git IDと所要時間だけ既存の正規化器用の代表値を使う。件数・診断の順・任意のフィールドを比較から除外しない。
- リポジトリ、`git status`の結果とインデックス、`HOME`、キャッシュ、`TMPDIR`の読取り専用の実行前後を固定し、許可する書込みを0件とする。

これらの任意のフィールド・文字列は今回の受入の期待値の選択であり、既存のCoreから採取したものではない。
根拠は[関係・トレースモデル §4・§5.1・§9](../../../docs/03.詳細設計/02_仕様文書モデル/04_関係・トレースモデル.md)、
[文書・フロントマター・状態仕様 §3・§4・§5](../../../docs/03.詳細設計/02_仕様文書モデル/02_文書・フロントマター・状態仕様.md)、
[診断レジストリ](../../../docs/03.詳細設計/00_共通契約/05_診断レジストリ.md)、

[適合matrix](../../../docs/03.詳細設計/00_共通契約/04_適合fixture仕様.md)である。

## 準備検証

`trace_fixtures.py`は、固定した入力のバイト列、レビュー済みのフロントマターの値のスキーマ、マニフェスト、完全な期待JSON、
副作用のスキーマを照合する。フロントマターのYAML原文と対応する値は固定した組であり、汎用のYAMLの構文解析器は実装しない。
各2回の隔離した準備手順を固定したスナップショットと比較し、余分なファイル、原因の修復、別の原因の混入を拒否する。
回帰試験は、二重診断、参照切れと型違反の取り違え、独立したTECHの検査漏れ、`draft`の場合の重大度、`covers`の発生元、
レポートの指定、キャッシュへの書込みの期待、参照先・テスト・コマンドの欠落、パスの作成、`refs`の自動変換を拒否する。

[ID重複・循環の4件](文書IDの重複と循環のレビュー記録.md)と[基準版の5件](基準版・状態遷移のレビュー記録.md)と[保護対象外変更の5件](approvedのREQの保護対象外の変更のレビュー記録.md)を追加し、50/311件を準備済み、実fixture残261件とする。goldenのハッシュ値、全体の副作用の期待値、
新しいチェックアウトの全Gate A検証は引き続き残る。Gate Aは`Blocked`である。
