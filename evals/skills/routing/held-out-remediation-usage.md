# 保持集合0.4の収集と監査

集合0.4は初期収集の後続条件で、既存9件の再利用候補と新規3件を区別する。
確定refの `held-out-collection-v0.4.json` に予算・入力・出力・除外・停止条件を固定する。
実装sourceの確定コミットをCLIへ渡す。結果文書のコミット等でHEADが動いても、
固定した12 source filesのbytesが同じなら条件変更と扱わない。

収集前にSOLの準備独立1枠で監査/契約/合成回帰を検分する。
作成SOL1枠は新規候補を最大3件だけ作成する。retention.jsonは上書きしない。
旧集合の9件はcaseId以外の全fieldsを同一に保つ。違いが必要なら契約を停止する。
新しい12件を同じdirectoryのcases.jsonへ、別の根拠をevidence.jsonへ排他新規保存する。
evidenceのrouting/lineageは全12件、noveltyComparisonsは新規3件、newCasePairsは全3組とする。
旧ID/新ID/個別hashや根拠は非公開で扱い、新規12件と報告しない。

各適用判定は主たる依頼と固定本文から導く。6スキルをすべて確認し、
個別不適用を全体不適用へ変換しない。安全上の停止は選択経路を残す。
参照path/hash/anchorは固定snapshotの対象SKILL.mdに一致させる。
anchorは本文中に存在する原文を使う。参照先は読取り専用の根拠であり実操作を伴わない。
機械監査が受理するのは根拠の構造・束縛で、説明の意味的な正しさは独立検分で検査する。

新規ケースは公開46件・初期12件・旧0.3の12件・新規候補同士へ比較する。
作成対象ラベルの変更だけを新規性の根拠にしない。
同じ最終経路でも決定条件が異なるかを検査し、差を近い条件へ戻した影響を説明する。
新規性や一意の判断を示せなければ不足で停止し、別候補への自動再試行をしない。

監査例（CPython3.12以上、固定jsonschema環境を使用）:

```sh
python -B evals/skills/routing/audit_remediated_held_out.py \
  --source <確定sourceの40桁commit> \
  --cases <承認済み非公開領域>/collection-04/cases.json
```

CLIは確定refから契約を読み、開始/完了のsource照合・公開一覧/hash・旧集合/hash・来歴/hash・
固定候補/hash・全体期待経路・比較網羅を検査する。公開出力はhashと集計に限定し、
失敗時は例外typeだけを返す。schemaの診断文を公開しない。

最後に別SOL1枠で全12件を独立検分する。原詳細は非公開へ保存し、親が保存証拠を再監査する。
P1/P2なしの永続証拠が揃うまで一次発火測定へ接続しない。今回の一次モデル枠は0。
